Фича channel-groups: объединять каналы бренда в группы по признакам (тема + диапазон подписчиков + диапазон ER), назначать аккаунты в группы (аккаунт ∈ ровно одной группе), измерять приток подписчиков per-группа через её именованную invite-ссылку (`GetChatInviteImporters`, абсолют + дневная дельта). Бренд = рекламная кампания, группа = направление. Надстройка над [[channel-discovery-feature]].

**Why:** ответить на бизнес-вопрос «с какой группы каналов идёт больше подписчиков» в общий приватный канал бренда; заложить основу под «кампании агентов».

**Статус (2026-06-19):** этап аналитики, прошло ревью БСА. Design doc `docs/design/channel-groups/channel-groups-v1.md` — 12 ФТ (User Story + Gherkin AC) + 5 алгоритмов (матчинг 6.1, пере-матч пула 6.2, валидация непересечения 6.3, round-robin 6.4, атрибуция 6.5). Документ переупорядочен по приоритету (FT-1…FT-12). Код не писался. Источник истины по сущностям — `channel-groups-er.puml` (4 сущности: brand, group, account, discovered_channel). Реестр наполняется из ДВУХ источников: `source`=`discovery` (внешний сервис по keywords) | `similar` (поиск похожих по MTProto, сид — все каналы группы); оба пишут в общий реестр бренда, раскладку делает общий матчинг (FT-5→FT-6). Это реверс относительно channel-discovery-similar-v1 (был прямой round-robin по агентам). Открытые вопросы В1–В11 закрыты/приняты в тексте.

**Находки ревью БСА (2026-06-19), ждут правок оператора:** (1) ER заявлен источником истины, но НЕ содержит сущность снапшотов атрибуции, которой оперируют FT-9 + алг.6.5 (saveSnapshot/lastSnapshot/snapshotExists) — пробел ER↔ФТ; §7 признаёт её новой. (2) FT-9 дельта при отсутствии prev-снапшота = «0 ИЛИ недоступна» — нетестируемое «или», алгоритм делает 0. (3) `discovered_channel.group_id/assigned_agent` без `<<FK>>` намеренно (результат раскладки, §3 стр.42), но нотация ER непоследовательна (brand_id=FK). (4) `status` enum не зафиксирован в ER (source — зафиксирован в note). (5) `brand.topics_a` не потребляется ни одним ФТ/алгоритмом — висящее поле либо UI-справочник, уточнить. Перекрёстные ссылки FT-N, инварианты, источник `source`, реверсы §3.1 — проверены, согласованы.

**Реверсы относительно discovery v1 (данность):** реестр теперь хранит `topic/subscribers/er/group_id/status` (было 2 колонки); раскладка по признакам в группу + round-robin ВНУТРИ группы (было RR по всем агентам); появился `status` и пул `unassigned`.

**Согласованные с заказчиком решения (НЕ оспаривать):** атрибуция только per-группа (не per-канал); аккаунт ∈ ровно одной группе; матчинг = topic ∈ topics_b И subs ∈ [min..max] И er ∈ [min..max]; критерии разных групп не пересекаются (проверка при заведении/правке); диапазоны только расширяются; нет ребаланса; пере-матч unassigned-пула в начале прогона (только чтение); RR внутри группы → join_queue.

**Главные открытые вопросы (заданы оператору, ждут ответа):** В2 — откуда берётся `topic` канала на входе discovery (discovery v1 ищет по keywords и тему не присваивает; LLM-тег есть только per-пост в channel-content-analysis). В4 — точное правило нормализации/сравнения текстовых тем (от него зависит и матчинг, и проверка непересечения). В1 — bind «группа↔invite_link»: кто заводит, можно ли назначать каналы в группу без ссылки. В10 — порядок вставок реестр→join_queue и молчаливая потеря доставки (унаследовано от discovery v1).

**How to apply:** при возврате к фиче — сначала проверить, не ответил ли оператор на В2/В4 (блокирующие: без источника темы и правила сравнения группировка не работает). ER/размер канала уже умеет считать channel-content-analysis (ERR=forwards/views, размер живьём) — переиспользовать, не изобретать.
