Для funnel-tracking v2 (этапы 1-4: каналов у агента / просмотрено / активно /
отправлено+ошибки) принято решение хранить новые сырые данные в **двух новых
append-only таблицах внутри существующей `tg-channels.db`** (per-agent), не в
`funnel.db` (admin-агент, платформенный артефакт для этапов 5-7):

- `channel_visits` (Q3) — журнал визитов монитора в канал, `outcome`
  (`empty`/`active`/`error`) + `messagesCount`. Пишется в `monitor.ts` на
  каждой итерации цикла по каналам (3 точки: нет непрочитанных, ошибка
  `get_messages`, обычный визит).
- `send_errors` (Q4) — журнал ошибок отправки по попытке/каналу, с полем
  `source` (`monitor`/`dm_send`) и `errorCode` (значения, которые код уже
  вычисляет: `peer_flood`/`flood_wait`/...). Отдельно от `runs`/`runs-summary.ts`
  — у `runs` гранулярность «весь прогон скилла», здесь нужна «попытка/канал».

**Why:** обе величины уже вычисляются в коде `monitor.ts`/`dm-send.ts` на
каждой итерации, но живут только в локальных переменных рана. Этапы 1-4 — не
дельты снапшотов (в отличие от 5-7), пересчитываются из первоисточника при
каждом построении отчёта — отдельная таблица дневных агрегатов для них не
нужна, она дублировала бы быстрый прямой запрос по дню.

**How to apply:** полный документ —
`docs/design/funnel-tracking/architecture-v2.md`. Один открытый вопрос
оставлен разработчику (не модель данных): нужно ли оборачивать отправку
ответа в группе в `monitor.ts` (`sendReply`, шаги 5.4/5.5/5.6) в свой
try/catch, чтобы её ошибки попадали в `send_errors`/«проблемные каналы»
(AC-3.5) вместо проброса наверх и падения всего прогона — см. §6 документа.
Связано: [[project_error_normalization]] (другая инициатива, другая
гранулярность — отчёты диспетчера на уровне прогона, не попытки).
