## Requirements
### Requirement: Персональная инвайт-ссылка с подтверждением заявки

Система SHALL по запросу оператора создавать для указанного агента инвайт-ссылку в
приватный канал воронки **его персоны** через аккаунт `REPORT_AGENT_ID` (администратор
всех персональных каналов, Модель A), со следующими параметрами: обязательное
подтверждение заявки на вступление (`requestNeeded: true`), без лимита использований, без
срока действия, без требования платной подписки, название ссылки (`title`) равно
`agentId` целевого агента. Целевой канал SHALL резолвиться как
`funnelPrivateChannelId` из `profile_data.json` персоны агента (поле `persona` в его
`tg-account.json`). Если у персоны агента не задан `funnelPrivateChannelId`, ссылка для
этого агента SHALL не создаваться — агент помечается пропущенным, обработка остальных
продолжается.

#### Scenario: Ссылка создана с нужными параметрами

- **WHEN** оператор запрашивает генерацию ссылки для агента X персоны P, у которой задан `funnelPrivateChannelId`
- **THEN** создаётся инвайт-ссылка в приватный канал персоны P: вступление требует одобрения администратора, ссылка не ограничена по числу использований и сроку действия, не требует платной подписки, её название в Telegram равно `X`

#### Scenario: У персоны агента не задан приватный канал

- **WHEN** у персоны агента X не задан `funnelPrivateChannelId`
- **THEN** ссылка для агента X не создаётся, он помечается пропущенным с причиной, обработка остальных агентов из запроса продолжается

### Requirement: Реестр инвайт-ссылок по агентам

Система SHALL хранить по одной актуальной инвайт-ссылке на агента в таблице
`private_invite_links` (`agent_id` — первичный ключ, `invite_link`, `created_at`) в
`~/.openclaw/workspace-<FUNNEL_ADMIN_AGENT_ID>/private-invites.db`. Повторная генерация
ссылки для уже обработанного агента SHALL заменять предыдущую запись, а не добавлять
дубль.

#### Scenario: Первая генерация для агента

- **WHEN** для агента X ссылка создаётся впервые
- **THEN** в `private_invite_links` появляется новая строка `(agent_id=X, invite_link, created_at)`

#### Scenario: Повторная генерация для того же агента

- **WHEN** для агента X, уже имеющего запись в `private_invite_links`, ссылка создаётся повторно
- **THEN** существующая строка обновляется новыми `invite_link`/`created_at`, число строк для агента X не растёт

### Requirement: Вставка ссылки в закреплённый пост агента

Система SHALL вставлять инвайт-ссылку агента в его собственный закреплённый в профиле
пост (`personalChannelMessage`, тот же пост, что использует трекинг просмотров воронки),
редактируя пост от имени самого агента. Существующие строки, целиком являющиеся ссылкой,
SHALL удаляться перед вставкой; новая ссылка SHALL добавляться тремя одинаковыми строками
в конец текста поста. Остальной текст поста SHALL оставаться без изменений.

#### Scenario: В посте уже есть старая ссылка

- **WHEN** текст поста агента оканчивается одной или несколькими строками-ссылками (например, тремя строками прежней инвайт-ссылки)
- **THEN** эти строки удаляются, к оставшемуся тексту дописываются три строки новой ссылки

#### Scenario: В посте ссылок ещё нет

- **WHEN** текст поста агента не содержит строк, целиком являющихся ссылкой
- **THEN** к существующему тексту дописываются три строки новой ссылки, остальной текст не меняется

#### Scenario: У агента нет personal channel или поста

- **WHEN** у агента не задан `personalChannelId`/`personalChannelMessage`
- **THEN** вставка для этого агента пропускается с пометкой, ссылка в реестре при этом сохраняется, обработка остальных агентов из запроса продолжается

### Requirement: OpenClaw-инструмент по списку агентов от пользователя

Система SHALL предоставлять OpenClaw-инструмент (`tg_private_invite_links`) и
сопровождающий скилл (`skills/private-invite-links/`), вызываемые оператором из чата.
Список целевых агентов SHALL передаваться параметром вызова (`agentIds: string[]`), а не
определяться автоматически. Для каждого агента из списка инструмент SHALL создать
ссылку, сохранить её в реестр и вставить в его закреплённый пост. Сбой обработки одного
агента SHALL не прерывать обработку остальных агентов из того же вызова.

#### Scenario: Вызов с явным списком агентов

- **WHEN** оператор вызывает `tg_private_invite_links` с `agentIds: ["agent4", "agent7"]`
- **THEN** обрабатываются только агенты `agent4` и `agent7`, остальные агенты платформы не затрагиваются

#### Scenario: Один агент из списка недоступен

- **WHEN** при обработке одного из агентов списка происходит ошибка (создание ссылки или вставка в пост)
- **THEN** ошибка логируется, этот агент помечается пропущенным в возвращаемом тексте, обработка остальных агентов из списка продолжается

### Requirement: Отсоединённое исполнение вне watchdog хода агента

Система SHALL исполнять прогон `private-invite-links` (во всех трёх режимах:
обычный, `retryPendingOnly`, `verifyOnly`) отсоединённым фоновым процессом,
отвязанным от хода оператора в чате, так чтобы длительность прогона не была
ограничена per-tool-call таймаутом runtime агента. Число обрабатываемых агентов
за один прогон SHALL не ограничиваться этим таймаутом.

#### Scenario: Оператор запускает прогон

- **WHEN** оператор запускает прогон invite-links (с `agentIds`, либо
  `retryPendingOnly`, либо `verifyOnly`)
- **THEN** система запускает прогон отсоединённым фоновым процессом и сразу
  возвращает подтверждение, а прогон продолжается после завершения хода в чате

#### Scenario: Прогон дольше таймаута тула

- **WHEN** последовательная обработка N агентов (создание ссылки + правка поста
  через сессию каждого) идёт дольше per-tool-call таймаута runtime агента
- **THEN** прогон всё равно завершается полностью и доставляет отчёт, а не
  обрывается на этом таймауте

### Requirement: Отчёт прогона в Saved Messages получателя отчётов

Система SHALL доставлять итоговый отчёт прогона (сводку созданных/вставленных/
совпавших/расходящихся ссылок и ошибок, в зависимости от режима) в Saved Messages
агента `REPORT_AGENT_ID` по завершении прогона — тот же адресат, что у дневной
сводки — вместо синхронного возврата вызывающему тул.

#### Scenario: Прогон завершился

- **WHEN** прогон обработал всех целевых агентов (успешно или с частичными
  пропусками/ошибками)
- **THEN** система доставляет отчёт со сводкой и построчными причинами пропусков/
  ошибок в Saved Messages `REPORT_AGENT_ID`

#### Scenario: Доставка отчёта не удалась

- **WHEN** прогон завершён и его результат сформирован, но доставка отчёта в Saved
  Messages не удалась (например, транзиентная ошибка Telegram/сети)
- **THEN** результат прогона (записи реестра, `post_updated`, лог) сохраняются, а
  ошибка доставки логируется, а не отбрасывает готовый результат

### Requirement: Завершение процесса после доставки отчёта

Система SHALL принудительно завершать процесс после доставки отчёта (или попытки
доставки) при любом исходе, включая непредвиденное исключение, чтобы висящие
после таймаута прокси GramJS-клиенты не держали event loop бесконечно.

#### Scenario: Отчёт доставлен, затем выход

- **WHEN** отчёт отправлен в Saved Messages (или отправка не удалась и
  залогирована)
- **THEN** процесс завершается и не зависает на оставшихся таймерах/сокетах
  MTProto-клиентов

#### Scenario: Непредвиденное исключение всё равно доставляет и завершает

- **WHEN** прогон бросает непредвиденное исключение до формирования нормального
  отчёта
- **THEN** система доставляет отчёт с текстом ошибки в Saved Messages, затем
  завершает процесс, а не теряет сбой молча и не зависает
