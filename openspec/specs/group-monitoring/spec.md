## Requirements
### Requirement: Agent scores and queues DM candidates
После обработки каждой группы агент SHALL оценивать интересные сообщения на потенциал для DM по шкале 0.0–1.0 и записывать кандидатов в `dm_candidates`, если `score >= 0.6`. Запись происходит в конце шага обработки группы, после отправки ответов в группу.

Критерии оценки:
- 0.9–1.0: сильный личный вопрос, явная экспертиза, живой интерес к теме канала
- 0.6–0.8: есть зацепка, но повод для DM не очевиден
- ниже 0.6: пропустить, не записывать

Поля для записи: `userId`, `userAccessHash` (из поля сообщения, только если не min-entity), `sourceChatId`, `msgId`, `msgText`, `score`, `scoreReason`.

Агент SHALL НЕ отправлять DM непосредственно из этого скилла.

#### Scenario: High-score message queued
- **WHEN** агент нашёл сообщение с оценкой ≥ 0.6 и у пользователя есть `userAccessHash`
- **THEN** вызывается `dm_candidates_insert` с полными данными; DM не отправляется

#### Scenario: Low-score message skipped
- **WHEN** агент оценил сообщение ниже 0.6
- **THEN** `dm_candidates_insert` не вызывается для этого сообщения

#### Scenario: min-entity user — queued without accessHash
- **WHEN** `userAccessHash` отсутствует (min-entity)
- **THEN** запись всё равно создаётся, но `userAccessHash` = null; Cron 2 не сможет отправить DM такому кандидату

#### Scenario: Duplicate message not duplicated
- **WHEN** одно и то же сообщение встречается на двух прогонах (одинаковые `sourceChatId`, `msgId`)
- **THEN** второй вызов `dm_candidates_insert` молча игнорируется (ON CONFLICT IGNORE)

### Requirement: Agent processes unread messages in two passes
После получения непрочитанных сообщений из группы агент SHALL разделить их на два потока до любой LLM-логики:
1. **Thread-replies** — сообщения с `replyToMsgId`, чей ID найден в `group_thread_agent_msgs` для данного chatId (или в `replies` как первый ответ)
2. **General messages** — все остальные сообщения

Thread-replies обрабатываются первыми с полным контекстом треда. General messages обрабатываются по существующему алгоритму (выбор одного релевантного, ответ).

#### Scenario: Mix of thread-replies and general messages
- **WHEN** в батче непрочитанных сообщений присутствуют как ответы на сообщения агента, так и обычные сообщения
- **THEN** сначала обрабатываются thread-replies (с контекстом треда), затем general messages (существующий флоу — одно сообщение, ответ)

#### Scenario: Only general messages
- **WHEN** ни одно из непрочитанных сообщений не является ответом на сообщение агента
- **THEN** выполняется только существующий флоу обработки general messages без изменений

#### Scenario: Only thread-replies
- **WHEN** все непрочитанные сообщения являются ответами на сообщения агента
- **THEN** обрабатываются только thread-replies; шаги выбора и ответа на general message не выполняются

### Requirement: Agent uses tg_classify_messages to split messages into categories

После вызова `telegram_mark_as_read` агент SHALL вызывать `tg_classify_messages` для разбивки входящих сообщений на категории. Агент SHALL НЕ вызывать `tg_group_thread_find` или `tg_replies_find_by_reply_msg_id` напрямую — эти инструменты больше не доступны.

Порядок обработки для каждого канала:
1. `telegram_get_messages` → сырые сообщения
2. `telegram_mark_as_read`
3. `tg_classify_messages` → `{ generalMessages, newThreadMessages, threadReplies }`
4. Обработать `newThreadMessages` (создать треды, ответить)
5. Обработать `threadReplies` (ответить, включая expired)
6. Обработать `generalMessages` — **одним структурированным LLM-вызовом** на канал, который одновременно: (а) выбирает не более одного сообщения для ответа и (б) скорит сообщения как DM-кандидатов. Отдельного шага извлечения тем (`extractTopics`) больше нет.

Обработка `generalMessages` SHALL:
- сначала отбрасывать дешёвой эвристикой (без LLM) заведомо непроходные сообщения (слишком короткие, только эмодзи/пунктуация, без буквенных символов);
- выполнять **один** структурированный LLM-вызов на канал, возвращающий выбор сообщения для ответа (или его отсутствие) и список оценок DM-кандидатов;
- отправлять **не более одного ответа** на канал за прогон;
- записывать DM-кандидатов по прежнему критерию (`score >= 0.6`) и с прежним набором полей.

#### Scenario: tg_classify_messages called after mark_as_read
- **WHEN** агент получил непустой список сообщений из `telegram_get_messages`
- **THEN** агент вызывает `telegram_mark_as_read`, затем вызывает `tg_classify_messages` с теми же сообщениями; результат классификации используется для дальнейшей обработки

#### Scenario: expired thread reply is handled by skill
- **WHEN** `tg_classify_messages` возвращает `ThreadReplyEntry` с `threadStatus = 'expired'`
- **THEN** агент отвечает на сообщения в этом записанном треде (обрабатывает как продолжение диалога), не перекладывает их в `generalMessages`

#### Scenario: Empty category is skipped
- **WHEN** одна из категорий (`generalMessages`, `newThreadMessages`, или `threadReplies`) пуста
- **THEN** агент пропускает шаг обработки этой категории без ошибок

#### Scenario: generalMessages обрабатываются одним LLM-вызовом
- **WHEN** после классификации `generalMessages` непуст
- **THEN** выполняется один структурированный LLM-вызов на канал, возвращающий выбор сообщения для ответа и оценки DM-кандидатов; отдельные вызовы извлечения тем не выполняются

#### Scenario: Не более одного ответа на канал
- **WHEN** структурированный вызов выбрал сообщение для ответа
- **THEN** агент отправляет ровно один ответ в этот канал за прогон

#### Scenario: Нечего отвечать
- **WHEN** структурированный вызов вернул отсутствие подходящего сообщения для ответа
- **THEN** агент не отправляет ответ в общий поток канала, но всё равно может записать DM-кандидатов из оценок

#### Scenario: Префильтр отбрасывает реакции до LLM
- **WHEN** среди `generalMessages` есть слишком короткие сообщения / только эмодзи / без буквенных символов
- **THEN** они отбрасываются эвристикой и не попадают в структурированный LLM-вызов

### Requirement: SKILL document uses flat step numbering with one parent for generalMessages handling

Файл `skills/telegram-group-monitor/SKILL.md` SHALL использовать плоскую сквозную нумерацию шагов уровня `5.x`: классификация (`tg_classify_messages`), обработка `newThreadMessages`, обработка `threadReplies` — каждая как самостоятельный шаг без точечного префикса вида `5.2.6`. Шаги, относящиеся к обработке `generalMessages` (определение тем, отбор релевантных, генерация ответов, отправка), SHALL быть сгруппированы под одним родительским шагом `5.6 Обработать generalMessages` с подшагами `5.6.1–5.6.4`.

Целевая структура:

```
5.1   Получить непрочитанные сообщения        (telegram_get_messages)
5.2   Пометить как прочитанные                (telegram_mark_as_read)
5.3   Классифицировать сообщения              (tg_classify_messages)
5.4   Обработать newThreadMessages
5.5   Обработать threadReplies
5.6   Обработать generalMessages
      5.6.1 Определить темы обсуждения        (LLM)
      5.6.2 Отобрать релевантные сообщения    (LLM)
      5.6.3 Сгенерировать ответы              (LLM)
      5.6.4 Отправить ответы                  (telegram_reply_to_message)
5.7   Сохранить прогресс                      (tg_channels_mark_processed)
5.8   Оценить сообщения для DM-кандидатов     (dm_candidates_insert)
```

Поведенческие требования (какие инструменты вызываются, в каком порядке, с какими параметрами) NOT changed — структурное изменение касается только нумерации и группировки в SKILL-документе.

#### Scenario: Steps for classification and thread handling are flat
- **WHEN** агент читает `SKILL.md`
- **THEN** шаги классификации и обработки тредов имеют номера `5.3`, `5.4`, `5.5` соответственно, без точечной вложенности типа `5.2.x`

#### Scenario: GeneralMessages handling has one parent step with substeps
- **WHEN** агент достигает обработки `generalMessages`
- **THEN** в `SKILL.md` это один родительский шаг `5.6` с подшагами `5.6.1` (определить темы), `5.6.2` (отобрать), `5.6.3` (сгенерировать), `5.6.4` (отправить)

#### Scenario: Intro range matches actual step set
- **WHEN** агент читает вводную строку перед перечислением шагов 5.x
- **THEN** диапазон шагов в intro соответствует реальному перечню (включая 5.8)

#### Scenario: Forward references point to current numbering
- **WHEN** в тексте шага встречается ссылка на номер другого шага (например, «из результата шага N»)
- **THEN** N соответствует текущей нумерации (`5.3` для классификации, `5.6.2/5.6.3` для отбора/генерации внутри родителя 5.6, и т. д.) — никаких упоминаний устаревших `5.2.6/5.2.7/5.2.8`

#### Scenario: Tools table uses new step numbers
- **WHEN** агент смотрит таблицу «Инструменты» в конце `SKILL.md`
- **THEN** колонка «Шаг» для `tg_classify_messages` содержит `5.3`, для `tg_group_thread_create` — `5.4`, для `tg_group_thread_update` — `5.4, 5.5`, для `telegram_reply_to_message` — `5.4, 5.5, 5.6.4`

#### Scenario: Behavior is unchanged
- **WHEN** агент проходит ренумерованный SKILL шаг за шагом
- **THEN** последовательность вызовов инструментов, параметры и LLM-промпты остаются такими же, как до изменения — меняется только то, как пронумерованы шаги в документе

### Requirement: Channel status supports comment-watch and sleep states
Поле `channels.status` SHALL поддерживать два дополнительных значения,
наравне с уже существующими `banned`/`suspend`/`format_error`: `only_comment`
и `sleep`. Канал SHALL находиться только в одном значении `status`
одновременно. Таблица `channels` SHALL иметь дополнительные поля
`lastSeenChannelPostId` (id последнего поста канала, на который агент
отреагировал) и `watchedThreadRootMsgId` (id служебной копии этого поста в
чате обсуждения) — оба nullable, заполняются только при успешной отправке
комментария к посту (`channel-post-watch`).

#### Scenario: Новое значение статуса не конфликтует с существующими
- **WHEN** канал получает `status = only_comment` или `status = sleep`
- **THEN** предыдущее значение `status` (если было) заменяется, `channels`
  хранит ровно одно текущее значение статуса для канала

### Requirement: General-message reply text is grounded in the real message, not the LLM's restated text
После того как `analyzeChannelMessages` вернул `ответитьНа: { id, текст }`,
агент SHALL использовать для генерации ответа (`generateReply`) и для записи
в `replies.db` (`saveReply`) реальный текст сообщения с данным `id`,
полученный детерминированным поиском среди сообщений, реально переданных в
этот LLM-вызов (`generalById`/эквивалент) — не поле `текст` из ответа LLM.
Поле `текст` в ответе LLM SHALL продолжать запрашиваться (часть рассуждения
модели при выборе), но SHALL NOT использоваться как источник содержимого
сообщения где-либо далее по конвейеру.

#### Scenario: LLM выбирает сообщение, текст в ответе совпадает с реальным
- **WHEN** `analyzeChannelMessages` возвращает `ответитьНа` с `id`,
  присутствующим среди сообщений этого прогона
- **THEN** `generateReply` вызывается с реальным текстом сообщения по `id`, и
  этот же реальный текст сохраняется в `replies.db.msgText`

#### Scenario: LLM выбирает сообщение, текст в ответе LLM не совпадает с реальным
- **WHEN** `analyzeChannelMessages` возвращает `ответитьНа` с `id`,
  присутствующим среди сообщений этого прогона, но полем `текст`, не
  совпадающим с реальным содержимым этого сообщения
- **THEN** генерация ответа и запись в БД всё равно используют реальный текст
  сообщения по `id` — расхождение в поле `текст` не влияет на итоговый ответ

#### Scenario: LLM возвращает несуществующий id
- **WHEN** `analyzeChannelMessages` возвращает `ответитьНа` с `id`,
  отсутствующим среди сообщений, реально переданных в этот LLM-вызов
- **THEN** ответ на общие сообщения в этом прогоне для этого канала не
  отправляется, обработка канала (треды, DM-скоринг, пометка обработанным)
  продолжается как обычно

### Requirement: Запись визита монитора в канал

Скилл `monitor` SHALL на каждой итерации цикла по каналам записывать визит в
таблицу `channel_visits` (`chatId`, `visitedAt`, `outcome`, `messagesCount`),
синхронно с `tg_channels_mark_processed`, независимо от исхода визита:

- нет непрочитанных сообщений → `outcome = 'empty'`, `messagesCount = 0`
- `get_messages` завершился ошибкой (кроме повторного `FLOOD_WAIT`) →
  `outcome = 'error'`, `messagesCount = 0`
- получено `messages.length === 0` сообщений → `outcome = 'empty'`,
  `messagesCount = 0`
- получено `messages.length > 0` сообщений → `outcome = 'active'`,
  `messagesCount = messages.length`

#### Scenario: Канал без непрочитанных

- **WHEN** у канала нет непрочитанных сообщений (`readInboxMaxId` не определён)
- **THEN** записывается визит с `outcome = 'empty'`, `messagesCount = 0`

#### Scenario: Ошибка получения сообщений

- **WHEN** `get_messages` завершается ошибкой, отличной от повторного `FLOOD_WAIT`
- **THEN** записывается визит с `outcome = 'error'`, `messagesCount = 0`, канал помечается обработанным, прогон переходит к следующему каналу

#### Scenario: Канал с активностью

- **WHEN** `get_messages` возвращает непустой список сообщений
- **THEN** записывается визит с `outcome = 'active'`, `messagesCount` равным числу полученных сообщений

#### Scenario: Повторный FLOOD_WAIT не пишет визит

- **WHEN** `get_messages` или отправка ответа завершаются повторным `FLOOD_WAIT` (`FloodAbortError`)
- **THEN** визит для этого канала не записывается, весь прогон скилла завершается с ошибкой

### Requirement: Запись ошибки отправки в канале

Скилл `monitor` SHALL записывать в таблицу `send_errors` (`chatId`,
`occurredAt`, `source = 'monitor'`, `errorCode`) каждый случай ошибки
`get_messages` (`errorCode = 'get_messages_error'`) и каждый случай не-flood
ошибки отправки ответа (`sendReply`), не изменяя существующую обработку
повторного `FLOOD_WAIT`.

#### Scenario: Ошибка get_messages записывается

- **WHEN** `get_messages` завершается ошибкой, отличной от повторного `FLOOD_WAIT`
- **THEN** в `send_errors` добавляется строка с `source = 'monitor'`, `errorCode = 'get_messages_error'`, `chatId` этого канала

#### Scenario: Ошибка отправки ответа записывается

- **WHEN** `sendReply` завершается не-flood ошибкой
- **THEN** в `send_errors` добавляется строка с `source = 'monitor'`, `errorCode` ошибки, `chatId` канала

### Requirement: Ошибка отправки ответа в группе не прерывает прогон

Скилл `monitor` SHALL при не-flood ошибке отправки ответа (`sendReply`, шаги
5.4/5.5/5.6) записывать ошибку (см. «Запись ошибки отправки в канале»),
помечать канал обработанным и переходить к следующему каналу батча, не
прерывая прогон для оставшихся каналов. Повторный `FLOOD_WAIT`
(`FloodAbortError`) SHALL продолжать прерывать весь прогон скилла, как и
прежде.

#### Scenario: Не-flood ошибка отправки ответа пропускает канал

- **WHEN** отправка ответа в канале завершается ошибкой, отличной от `FloodAbortError`
- **THEN** ошибка записывается в `send_errors`, канал помечается обработанным, прогон продолжается со следующего канала батча

#### Scenario: Повторный FLOOD_WAIT при отправке прерывает весь прогон

- **WHEN** отправка ответа завершается повторным `FLOOD_WAIT` (`FloodAbortError`)
- **THEN** прогон скилла завершается с ошибкой `repeated_flood_wait`, как и до этого изменения

### Requirement: Монитор различает CHAT_WRITE_FORBIDDEN

При не-flood ошибке отправки ответа монитор SHALL отдельно распознавать
`CHAT_WRITE_FORBIDDEN` и для этого случая помечать канал `status = 'banned'`
(`markChannelStatus`), помимо существующей записи ошибки и пропуска канала.
Постановка в отдельную очередь `banned_channels` SHALL не выполняться —
источником очереди на выход служит сам `channels.status` (capability
`leave-banned-channels`). Прочие не-flood ошибки ответа (не
`CHAT_WRITE_FORBIDDEN`) SHALL обрабатываться как прежде — без изменения
`status` канала на `banned`.

#### Scenario: CHAT_WRITE_FORBIDDEN помечает статус канала

- **WHEN** отправка ответа в канале завершается ошибкой `CHAT_WRITE_FORBIDDEN`
- **THEN** `channels.status` для этого `chatId` устанавливается в `'banned'`, канал помечается обработанным, прогон продолжается со следующего канала

#### Scenario: Прочая не-flood ошибка не меняет статус на banned

- **WHEN** отправка ответа завершается не-flood ошибкой, отличной от `CHAT_WRITE_FORBIDDEN`
- **THEN** канал пропускается как прежде, `status` канала не устанавливается в `'banned'`

#### Scenario: Повторный FLOOD_WAIT не затрагивается

- **WHEN** отправка ответа завершается повторным `FLOOD_WAIT` (`FloodAbortError`)
- **THEN** весь прогон прерывается как прежде, `status` канала не изменяется

### Requirement: Monitor determines unread status for every channel in its batch

Для каждого канала из батча монитора (`getChannelsBatch`) агент SHALL определить
достоверный статус непрочитанности перед принятием решения об `outcome`: канал
SHALL считаться найденным, если он встретился в ответе Telegram (`iterDialogs`)
с любым значением `unreadCount` (в том числе 0), а не только если у него
`unreadCount > 0`.

Агент SHALL дозапрашивать страницы диалогов Telegram (пагинация), пока не
выполнено одно из условий:
- каждый `chatId` батча встретился в ответе Telegram;
- Telegram вернул страницу диалогов короче запрошенного размера (диалоги
  закончились);
- достигнут потолок числа страниц за один прогон монитора.

Канал, статус которого не подтверждён ни одним из этих путей (диалоги Telegram
исчерпаны или достигнут потолок страниц, а канал так и не встретился), SHALL
считаться неопределённым и обрабатываться как `outcome: "error"` — он SHALL НЕ
помечаться `outcome: "empty"` без подтверждения.

Для каждого диалога, встреченного в процессе дозапроса страниц (независимо от
того, входит он в текущий батч или нет), агент SHALL заполнять `peerCache` —
без этого `mark_as_read`/`reply` для таких чатов окажутся недоступны.

#### Scenario: Channel found with unread on first page
- **WHEN** канал из батча встретился на первой странице диалогов Telegram с
  `unreadCount > 0`
- **THEN** монитор получает его `readInboxMaxId` и переходит к чтению сообщений;
  дополнительные страницы не запрашиваются для этого канала

#### Scenario: Channel found with zero unread on later page
- **WHEN** канал из батча не встретился на первой странице, но встретился на
  второй с `unreadCount = 0`
- **THEN** монитор останавливает дозапрос по этому каналу, считает его
  подтверждённо пустым и помечает `outcome: "empty"`

#### Scenario: All batch channels covered before pages exhausted
- **WHEN** все каналы батча встретились (с любым `unreadCount`) до того, как
  диалоги Telegram закончились
- **THEN** дозапрос страниц останавливается немедленно, дальнейшие страницы не
  запрашиваются

#### Scenario: Dialogs exhausted before batch fully covered
- **WHEN** Telegram вернул страницу диалогов короче запрошенного размера
  (диалоги закончились), а часть каналов батча так и не встретилась
- **THEN** дозапрос останавливается; не найденные каналы получают `outcome:
  "error"`, а не `outcome: "empty"`

#### Scenario: Page cap reached before batch fully covered
- **WHEN** число дозапрошенных страниц достигло потолка, а часть каналов батча
  так и не встретилась
- **THEN** дозапрос останавливается; не найденные каналы получают `outcome:
  "error"`, а не `outcome: "empty"`

#### Scenario: peerCache filled for dialogs outside the batch
- **WHEN** в процессе дозапроса страниц встречается диалог, не входящий в
  текущий батч монитора
- **THEN** этот диалог тоже попадает в `peerCache` (как и при текущем
  однократном вызове `getDialogs`)

### Requirement: Флуд/slow-mode при отправке ответа не считается сбоем канала

При отправке ответа в канал/группу монитор SHALL отличать флуд-ограничение
(`FLOOD_WAIT`, slow-mode) от прочих ошибок отправки. Флуд-ограничение с ожиданием ниже
согласованного порога SHALL приводить к одной повторной попытке отправки в рамках того
же прогона перед тем, как канал будет считаться пропущенным.

#### Scenario: Короткий флуд не мешает отправить ответ

- **WHEN** отправка ответа в канал получает флуд-ограничение с ожиданием ниже порога
- **THEN** монитор ждёт и повторяет отправку один раз; при успехе повторной попытки
  канал не считается пропущенным и не попадает в число каналов с ошибкой отправки за
  этот прогон

#### Scenario: Длинный флуд или повторный флуд пропускает канал на этот прогон

- **WHEN** отправка ответа в канал получает флуд-ограничение с ожиданием на пороге или
  выше, либо флуд повторяется после одной попытки ожидания
- **THEN** канал пропускается на этот прогон (поведение остановки прогона при
  повторном `FLOOD_WAIT` — без изменений)

#### Scenario: Пропуск по флуду не искажает отчёт о проблемных каналах

- **WHEN** канал пропущен из-за флуд-ограничения (короткого повторного или длинного/
  выше порога)
- **THEN** это фиксируется отдельным кодом ошибки, отличным от кода обычного сбоя
  отправки — ежедневный отчёт воронки не показывает такой канал наравне с каналами,
  где отправка действительно не удалась по содержательной причине

### Requirement: Схема `channels.status`

Таблица `channels` SHALL получить колонки `status` (`banned` |
`format_error` | отсутствие значения) и `statusUpdatedAt` (unix-время
последнего обновления статуса) — аддитивная миграция, как существующие
миграции `channels.ts`.

#### Scenario: Канал без статуса — обычная работа
- **WHEN** канал ещё не сталкивался с ошибками, требующими статуса
- **THEN** `status` пуст, канал обрабатывается монитором как обычно

### Requirement: `channels.status = 'banned'` при потере права записи

`monitor-v2` SHALL проставлять `channels.status = 'banned'` и
`statusUpdatedAt = now()` сразу на шаге обработки исхода попытки отправить
ответ в канал (та же точка, где сегодня вызывается `recordSendError`), при
получении `CHAT_WRITE_FORBIDDEN` либо `USER_BANNED_IN_CHANNEL` (в контексте
отправки — не при вступлении, см. `join-queue` Requirement «Ошибки при
попытке вступления → error»). Оба кода обрабатываются одной веткой —
`USER_BANNED_IN_CHANNEL` не получает отдельного статуса. Отдельная очередь
`banned_channels` SHALL не использоваться — источником очереди на выход
служит сам `channels.status` (capability `leave-banned-channels`).

#### Scenario: CHAT_WRITE_FORBIDDEN помечает канал banned
- **WHEN** `monitor-v2` получает `CHAT_WRITE_FORBIDDEN` при отправке ответа
- **THEN** `channels.status = 'banned'`, `statusUpdatedAt = now()`

#### Scenario: USER_BANNED_IN_CHANNEL при отправке — то же поведение
- **WHEN** `monitor-v2` получает `USER_BANNED_IN_CHANNEL` при отправке ответа
- **THEN** поведение идентично `CHAT_WRITE_FORBIDDEN` — `channels.status =
  'banned'`

### Requirement: `channels.status = 'banned'` останавливает обработку канала

`monitor-v2` SHALL проверять `channels.status` непосредственно перед
обработкой канала (перед проверкой/ответом на сообщения). Если
`status = 'banned'` — канал пропускается, обработка переходит к следующему.
Любой другой статус (включая `format_error` или отсутствие статуса) SHALL
не влиять на это решение — канал обрабатывается как обычно.

#### Scenario: Забаненный канал пропускается
- **WHEN** `monitor-v2` формирует батч каналов к обработке, и у канала
  `status = 'banned'`
- **THEN** канал пропускается без попытки прочитать/ответить, обработка
  переходит к следующему каналу

#### Scenario: format_error не останавливает обработку
- **WHEN** у канала `status = 'format_error'`
- **THEN** канал обрабатывается как обычно — читается, при наличии
  подходящего сообщения отправляется ответ

### Requirement: `channels.status = 'format_error'` при запрете формата контента

`monitor-v2` SHALL проставлять `channels.status = 'format_error'` и
`statusUpdatedAt = now()` при получении `CHAT_SEND_PLAIN_FORBIDDEN`,
`CHAT_SEND_MEDIA_FORBIDDEN` или `ALLOW_PAYMENT_REQUIRED` при отправке ответа
— та же точка, что и для `banned`. Статус обновляется заново при каждом
повторном получении любой из этих ошибок для канала (естественное следствие
Requirement «`channels.status = 'banned'` останавливает обработку канала» —
поскольку `format_error` не блокирует обработку, повторная попытка и,
соответственно, повторная ошибка возможны). `format_error` SHALL НЕ
попадать в очередь на выход (capability `leave-banned-channels`) — агент из
канала не выходит.

#### Scenario: Запрет текстового контента помечает канал format_error
- **WHEN** `monitor-v2` получает `CHAT_SEND_PLAIN_FORBIDDEN` при отправке
  ответа
- **THEN** `channels.status = 'format_error'`, `statusUpdatedAt = now()`,
  канал не попадает в очередь на выход, агент из канала не выходит

#### Scenario: Платные сообщения помечают канал format_error
- **WHEN** `monitor-v2` получает `ALLOW_PAYMENT_REQUIRED` при отправке ответа
- **THEN** поведение идентично `CHAT_SEND_PLAIN_FORBIDDEN`

### Requirement: PEER_FLOOD при отправке ответа в канал

`PEER_FLOOD`, возникший при отправке ответа в канал (`monitor-v2`), SHALL
немедленно останавливать текущий прогон — по аналогии с существующим
поведением `dm-send` при `PEER_FLOOD`. Не является ошибкой конкретного
канала — `channels.status` не проставляется. См. `agent-restrictions`
Requirement «Триггеры создания ограничения» (`suspend`, триггер 1) и
`account-error-log` Requirement «Точки записи».

#### Scenario: PEER_FLOOD при ответе в группу останавливает прогон
- **WHEN** `monitor-v2` получает `PEER_FLOOD` при отправке ответа
- **THEN** прогон немедленно останавливается; `channels.status` этого
  канала не меняется; создаётся `agent_restrictions(suspend,
  restriction_duration=86400)` и запись в `error_log`

### Requirement: Политика повтора FLOOD_WAIT/SLOWMODE_WAIT

При `FLOOD_WAIT_N`/`FLOOD_PREMIUM_WAIT_N`/`SLOWMODE_WAIT_N` система SHALL
повторять операцию до 2 раз подряд, если время ожидания меньше 2 минут.
Порог 2 минуты SHALL перепроверяться заново на каждом повторе — если
очередное время ожидания окажется ≥ 2 минут, цикл повторов обрывается
раньше, не дожидаясь второй попытки. Если после 2 повторов ошибка
сохраняется, либо время ожидания на очередном шаге ≥ 2 минут — выполнение
SHALL переходить к следующему действию вне скоупа этой ошибки (пропуск
канала/кандидата/ссылки). Политика SHALL быть единой для подключения,
вступления и отправки — одна реализация, не три раздельные копии.

#### Scenario: Один повтор с быстрым флудом
- **WHEN** операция получает `FLOOD_WAIT_5` (5 секунд), повтор получает
  `FLOOD_WAIT_3`
- **THEN** система ждёт 5с, повторяет; ждёт 3с, повторяет второй раз;
  третий раз не выполняется — операция считается завершённой по исходу
  второго повтора

#### Scenario: Порог превышен на втором повторе — цикл обрывается раньше
- **WHEN** первый `FLOOD_WAIT` — 10 секунд (повтор выполняется), второй —
  150 секунд (≥ порога)
- **THEN** после первого повтора цикл останавливается без второй попытки
  ожидания, операция считается завершённой по исходу первого повтора

#### Scenario: Ожидание с самого начала выше порога
- **WHEN** первый `FLOOD_WAIT` — 150 секунд (≥ порога)
- **THEN** повторов не выполняется, операция сразу считается завершённой по
  этому исходу

### Requirement: Проверка удалённых сообщений агента при визите канала

При каждом визите канала (due-батч `monitor-v2`) агент SHALL проверять, сколько
сообщений, отправленных им в этот канал за последние
`MESSAGE_DELETION_CHECK_WINDOW_SECONDS` (14 дней), были удалены. Проверка SHALL
выполняться независимо от наличия непрочитанных сообщений в канале и SHALL
пропускаться, если за окно агент не отправлял сообщений в этот канал.

Источник сообщений агента — записи из `replies` (ответы вне тредов) и
`group_thread_agent_msgs` (сообщения в тредах), объединённые по времени
отправки.

#### Scenario: Канал без сообщений агента — проверка пропущена
- **WHEN** за последние 14 дней агент не отправлял ни одного сообщения в канал
- **THEN** проверка удаления не выполняется, запрос к Telegram не отправляется

#### Scenario: Удалений не найдено
- **WHEN** все проверенные сообщения агента ещё существуют в канале
- **THEN** статус канала не меняется

### Requirement: Приостановка канала при массовом удалении сообщений агента

Если число удалённых сообщений агента за окно проверки превышает
`MESSAGE_DELETION_THRESHOLD` (2), агент SHALL установить каналу
`status = 'suspend'` со сроком действия `CHANNEL_SUSPEND_DURATION_SECONDS`
(3 дня) и текстовым описанием причины. Событие SHALL записываться в
`send_errors` (`source = 'monitor_v2'`, `errorCode = 'messages_deleted'`).

Пока канал в статусе `suspend`, `monitor-v2` SHALL полностью пропускать его
обработку (не читать сообщения, не отвечать) — так же, как канал в статусе
`banned`.

#### Scenario: Превышен порог удалений
- **WHEN** за окно проверки удалено больше 2 сообщений агента в канале
- **THEN** каналу присваивается `status='suspend'` на 3 дня, событие записывается в `send_errors`

#### Scenario: Suspended-канал пропускается
- **WHEN** канал имеет активный `status='suspend'`
- **THEN** `monitor-v2` не читает сообщения канала и не отправляет в него ответы на этом прогоне

#### Scenario: Порог не превышен
- **WHEN** удалено 2 или меньше сообщений агента
- **THEN** статус канала не меняется

### Requirement: Срок действия статуса канала и автоматическое снятие

Каждый статус канала (`banned`, `format_error`, `suspend`) SHALL иметь
связанную длительность действия. Для `banned` и `format_error` длительность
SHALL быть бессрочной (без изменения текущего поведения). Для `suspend`
длительность SHALL быть ограниченной (`CHANNEL_SUSPEND_DURATION_SECONDS`).

В начале каждого прогона `monitor-v2` агент SHALL снимать статусы, срок
действия которых истёк — статус, длительность и описание причины сбрасываются,
канал возвращается к обычной обработке.

#### Scenario: Suspend истекает
- **WHEN** с момента установки `status='suspend'` прошло больше 3 дней
- **THEN** в начале следующего прогона `monitor-v2` статус канала сбрасывается, канал обрабатывается как обычно

#### Scenario: Banned не истекает
- **WHEN** канал находится в `status='banned'`
- **THEN** статус не снимается автоматически по времени — только явными механизмами (выход из канала)

### Requirement: Выборка каналов на обработку исключает покинутые каналы

Общая выборка каналов на обработку (`getChannelsBatch`, используется
`monitor`/`monitor-v2`/`monitor-v5`) SHALL исключать каналы со статусом
`banned` или с активным `suspend` — такие каналы заведомо не будут обработаны
в этом прогоне; канал со статусом `format_error` SHALL оставаться в выборке —
этот статус не блокирует обработку. Дополнительно выборка SHALL исключать
каналы со статусом `'leaved_from_banned'` или `'leaved_manual'` (см.
capability `leave-banned-channels`, «Терминальный статус после выхода») —
агент уже не участник этих каналов.

#### Scenario: Suspended-канал не попадает в батч
- **WHEN** канал имеет активный `status='suspend'`
- **THEN** он не включается в батч назревших каналов, даже если `lastProcessedAt` указывает на давнюю обработку

#### Scenario: format_error-канал остаётся в выборке
- **WHEN** канал имеет `status='format_error'`
- **THEN** он участвует в обычной выборке батча наравне с каналами без статуса

#### Scenario: Покинутый канал не попадает в выборку

- **WHEN** у канала `channels.status` равен `'leaved_from_banned'` или `'leaved_manual'`
- **THEN** этот канал не попадает в выборку `getChannelsBatch`, даже если срок его последней обработки истёк
