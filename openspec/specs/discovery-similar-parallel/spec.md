## Requirements
### Requirement: Параллельный запуск искателей

Все искатели SHALL запускаться одновременно. Каждый искатель держит собственную
Telegram-сессию открытой на весь обход — от старта до завершения BFS. Время прогона
определяется самым медленным искателем, а не суммой всех.

#### Scenario: Одновременный старт сессий

- **WHEN** `runSimilarDiscovery` вызывается с N искателями
- **THEN** все N Telegram-сессий открываются в начале прогона, не последовательно

#### Scenario: Фаза распределения после всех искателей

- **WHEN** последний из N искателей завершает работу (по цели, по исчерпанию графа или по остановке)
- **THEN** фаза распределения запускается и назначает каналы агентам round-robin

### Requirement: Регистрация канала без агента

Во время BFS-фазы скрипт SHALL регистрировать найденный канал в реестре без назначения
агента (`assigned_agent = NULL`). Агент назначается только в фазе распределения.

#### Scenario: Успешная регистрация кандидата

- **WHEN** кандидат прошёл все гейты
- **THEN** канал записывается в `discovered_channels` с `assigned_agent = NULL` и общий счётчик `totalCollected` инкрементируется

#### Scenario: Дублирующая регистрация отклоняется

- **WHEN** два искателя одновременно нашли один и тот же канал
- **THEN** в реестр попадает только первый; второй получает `inserted=false` и не инкрементирует `totalCollected`

### Requirement: Остановка по общей цели

Каждый искатель SHALL проверять общий счётчик `totalCollected` после каждой успешной
регистрации. При `totalCollected >= goal` искатель прекращает обход. `goal = target × N`,
где N — число агентов платформы.

#### Scenario: Достижение цели

- **WHEN** `totalCollected` достигает `goal`
- **THEN** текущий искатель при следующей проверке прекращает обход; другие искатели также останавливаются при своей следующей проверке

#### Scenario: Допустимый overshoot

- **WHEN** несколько искателей параллельно регистрируют каналы в момент достижения цели
- **THEN** итоговое число найденных каналов может превышать `goal` не более чем на N_searchers — 1; отчёт отражает фактическое число

### Requirement: Независимость искателей при сбоях

Сбой одного искателя SHALL NOT прерывать работу остальных. Прогон доходит до фазы
распределения при наличии хотя бы одного завершившегося успешно.

#### Scenario: Ошибка сессии при старте

- **WHEN** сессия искателя не поднимается при старте
- **THEN** этот искатель пропускается; остальные продолжают работу; прогон идёт до фазы распределения

#### Scenario: Двойной FLOOD_WAIT

- **WHEN** искатель получает два FLOOD_WAIT подряд
- **THEN** этот искатель останавливается; остальные продолжают до достижения `goal` или исчерпания своих графов

#### Scenario: Сохранность найденных каналов после сбоя

- **WHEN** искатель падает с ошибкой после регистрации нескольких каналов
- **THEN** зарегистрированные каналы остаются в реестре и участвуют в фазе распределения

### Requirement: Per-searcher статистика в отчёте

Отчёт оператора SHALL содержать для каждого искателя отдельно: число успешно
зарегистрированных каналов и счётчики отсева по каждому гейту. Отчёт SHALL содержать
агрегированную строку суммарных значений по всем искателям.

#### Scenario: Строка per-searcher

- **WHEN** прогон завершён
- **THEN** в отчёте для каждого искателя присутствует строка: имя, найдено, отсеяно по каждому гейту (подписчики / нет группы / вовлечённость / тема), статус

#### Scenario: Итоговая строка

- **WHEN** прогон завершён
- **THEN** в отчёте присутствует строка «ИТОГО» с суммарными значениями по всем искателям

#### Scenario: Пометка проблемного искателя

- **WHEN** искатель остановлен по FLOOD_WAIT или упал с ошибкой
- **THEN** его строка в отчёте содержит явную пометку с причиной остановки рядом со счётчиками
