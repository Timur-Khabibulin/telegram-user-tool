## Requirements
### Requirement: Обнаружение агентов

Система SHALL в начале каждого прогона динамически получать список агентов через `listAgentIds()` (каталоги `~/.openclaw/workspace-<agentId>/`) и собирать метрики по каждому из них.

#### Scenario: Появился новый агент

- **WHEN** в `~/.openclaw/` присутствует каталог `workspace-agentN`, ранее не существовавший
- **THEN** при следующем прогоне agentN включается в сбор метрик без изменения конфигурации

#### Scenario: Агентов нет

- **WHEN** `listAgentIds()` возвращает пустой список
- **THEN** прогон завершается без ошибок и без записи снапшотов

### Requirement: Обнаружение публичного канала агента

Система SHALL определять публичный канал агента автоматически как канал, закреплённый в профиле аккаунта (personal channel), через `users.GetFullUser(self)` (`personalChannelId` + `personalChannelMessage`), используя `access_hash` из массива `chats` ответа. Если у агента не задан personal channel, агент SHALL быть пропущен с пометкой.

#### Scenario: У агента задан personal channel

- **WHEN** `GetFullUser` возвращает непустой `personalChannelId`
- **THEN** система использует этот канал и `personalChannelMessage` как id поста для метрик охвата

#### Scenario: У агента нет personal channel

- **WHEN** `GetFullUser` возвращает пустой `personalChannelId`
- **THEN** агент пропускается с пометкой в отчёте, прогон остальных агентов продолжается

### Requirement: Метрики активности из БД агента

Система SHALL за завершившийся день UTC+5 считать по каждому агенту число каналов, в которые отправлено хотя бы одно сообщение группы (DISTINCT `chatId` из `replies.sentAt` окна дня, `tg-replies.db`). Личные сообщения (`dm_history`) SHALL не учитываться ни в этом, ни в каком-либо другом показателе сбора воронки.

#### Scenario: Подсчёт каналов с отправкой за день

- **WHEN** прогон считает метрики за день UTC+5
- **THEN** показатель «каналов с отправкой» равен числу DISTINCT `chatId` в `replies` с `sentAt` в окне дня, независимо от числа сообщений в каждый канал

#### Scenario: Несколько сообщений в один канал

- **WHEN** агент отправил за отчётный день несколько сообщений в один и тот же канал
- **THEN** канал засчитывается в показателе один раз

#### Scenario: Только личные сообщения за день

- **WHEN** агент за отчётный день отправлял только личные сообщения (DM), без сообщений в группы
- **THEN** показатель «каналов с отправкой» для этого агента равен 0

#### Scenario: БД агента отсутствует или недоступна

- **WHEN** `tg-replies.db` агента отсутствует или не читается
- **THEN** показатель берётся как 0 либо агент пропускается с пометкой, прогон не падает

### Requirement: Снапшот охвата публичного канала

Система SHALL снимать снапшот просмотров поста (`messages.GetMessagesViews` по `personalChannelMessage`) и числа подписчиков (`channels.GetFullChannel.participantsCount`) публичного канала каждого агента раз в день и сохранять абсолютные значения в `channel_snapshots`.

#### Scenario: Успешный снапшот охвата

- **WHEN** публичный канал агента определён
- **THEN** в `channel_snapshots` записываются `post_id`, `post_views`, `public_channel_subs` с текущим `snapped_at`

### Requirement: Снапшот заявок в приватный канал

Система SHALL для каждого активного агента с настроенной персональной пригласительной
ссылкой (`private_invite_links`) снимать число неодобренных заявок на вступление в
приватный канал воронки **его персоны** по этой конкретной ссылке
(`messages.GetChatInviteImporters(peer=<канал персоны агента>, requested=true,
link=<ссылка агента>)`) от имени администратора приватных каналов (`REPORT_AGENT_ID`,
Модель A) и сохранять в `channel_snapshots.private_pending_requests` строки снапшота
этого агента. Целевой `peer` SHALL резолвиться как `funnelPrivateChannelId` из
`profile_data.json` персоны агента.

Если у персоны агента не задан `funnelPrivateChannelId`, подсчёт заявок для агентов этой
персоны SHALL пропускаться: значение SHALL быть NULL (не 0), MTProto-запрос для них не
выполняется. У агента без настроенной ссылки значение SHALL быть NULL (не 0), запрос для
него не выполняется. Итог заявок SHALL вычисляться **по персонам** — как сумма значений
по агентам в разрезе персоны, а не единым платформенным числом. При недоступности сбора
по конкретному каналу (нет прав, ошибка запроса) метрика заявок для агентов
соответствующей персоны SHALL быть пропущена с пометкой, прогон не падает.

#### Scenario: У агента настроена ссылка

- **WHEN** у агента есть запись в `private_invite_links`, у его персоны задан `funnelPrivateChannelId`, и `REPORT_AGENT_ID` имеет право `invite_users` в этом канале
- **THEN** число pending-заявок по ссылке этого агента в канале его персоны записывается в `private_pending_requests` его строки снапшота

#### Scenario: У персоны агента не задан приватный канал

- **WHEN** у персоны агента не задан `funnelPrivateChannelId`
- **THEN** `private_pending_requests` для агентов этой персоны — NULL, MTProto-запрос по ним не выполняется, прогон остальных персон продолжается

#### Scenario: У агента нет настроенной ссылки

- **WHEN** для агента нет записи в `private_invite_links`
- **THEN** `private_pending_requests` для него — NULL, MTProto-запрос по нему не выполняется

#### Scenario: Недостаточно прав

- **WHEN** `GetChatInviteImporters` для канала персоны возвращает `CHAT_ADMIN_REQUIRED`
- **THEN** заявки помечаются недоступными в отчёте для агентов этой персоны, остальные метрики и остальные персоны собираются как обычно

#### Scenario: Платформенный итог

- **WHEN** вычисляется итог заявок
- **THEN** он считается отдельно на каждую персону как сумма `private_pending_requests` её агентов (NULL трактуется как 0 в сумме), единого смешанного платформенного числа по всем персонам не выводится

### Requirement: Хранение снапшотов и дневных агрегатов

Система SHALL хранить сырые снапшоты в таблице `channel_snapshots` и предвычисленные дневные агрегаты в таблице `daily_stats` в БД `~/.openclaw/workspace-agent1/funnel.db`, создавая схему идемпотентно (`CREATE TABLE IF NOT EXISTS`).

#### Scenario: Первый прогон

- **WHEN** `funnel.db` ещё не существует
- **THEN** таблицы `channel_snapshots` и `daily_stats` создаются, прогон записывает данные без ошибки

### Requirement: Вычисление дневных дельт

Система SHALL вычислять дельту метрики как разность текущего снапшота и предыдущего снапшота того же `agent_id` и сохранять в `daily_stats` и дельту, и абсолютное значение (`*_delta` и `*_abs`).

#### Scenario: Есть предыдущий снапшот

- **WHEN** для агента существует снапшот за предыдущий день
- **THEN** `post_views_delta`/`public_subs_delta`/`private_requests_delta` равны разности текущего и предыдущего значений, а `*_abs` — текущим значениям

#### Scenario: Предыдущего снапшота нет

- **WHEN** это первый снапшот агента
- **THEN** дельта равна 0 (или помечается как недоступная), `*_abs` заполняется текущим значением

### Requirement: Защита от двойного прогона

Система SHALL перед записью снапшота проверять наличие снапшота того же `agent_id` с `snapped_at` в пределах текущего дня UTC+5 и при наличии SHALL пропускать повторную запись, не дублируя данные.

#### Scenario: Повторный запуск в тот же день

- **WHEN** скрипт запускается повторно в пределах одного дня UTC+5
- **THEN** новые снапшоты за этот день не добавляются, данные не дублируются

### Requirement: Изоляция сбоев по агенту

Система SHALL обрабатывать сбор данных по каждому агенту в двух независимых группах: этапы 1-4 (локальные данные — `channels`, `channel_visits`, `send_errors`, `replies`, `dm_history`) и этапы 5-7 (MTProto — охват публичного канала, заявки в приватный канал). Сбой одной группы SHALL приводить к пометке только этой группы как пропущенной для агента, не затрагивая данные другой группы. Сбой подключения, прокси, MTProto или БД одного агента SHALL приводить к пропуску затронутой группы этого агента с пометкой, не прерывая прогон остальных агентов.

#### Scenario: MTProto недоступен, локальные данные собраны

- **WHEN** при сборе по агенту MTProto-вызовы (этапы 5-7) завершаются ошибкой, а локальные SQLite-данные (этапы 1-4) читаются успешно
- **THEN** в отчёте по этому агенту этапы 1-4 заполнены, этапы 5-7 помечены как пропущенные, прогон остальных агентов продолжается

#### Scenario: Локальная БД недоступна, MTProto-данные собраны

- **WHEN** `tg-channels.db` агента временно заблокирована (например, монитор пишет в неё в этот момент), а MTProto-вызовы (этапы 5-7) выполняются успешно
- **THEN** в отчёте по этому агенту этапы 5-7 заполнены, этапы 1-4 помечены как пропущенные, прогон остальных агентов продолжается

#### Scenario: Один агент полностью недоступен

- **WHEN** при сборе по agentK обе группы (1-4 и 5-7) завершаются ошибкой
- **THEN** agentK пропускается полностью с пометкой по каждой группе, метрики остальных агентов собираются и записываются

### Requirement: Зарезервированный агент-получатель не участвует в сборе метрик

Сбор метрик воронки SHALL не включать `REPORT_AGENT_ID` — он не выполняет рабочих задач
(мониторинг групп, DM, охват публичного канала), поэтому метрики по нему не имеют
смысла. Исключение обеспечивается тем, что `REPORT_AGENT_ID` отсутствует в результате
`listAgentIds()`, которую использует сбор метрик для перечисления агентов.

#### Scenario: Зарезервированный агент отсутствует в отчёте

- **WHEN** строится отчёт-воронка за день
- **THEN** `REPORT_AGENT_ID` не появляется ни строкой в таблице агентов, ни в подсчёте «Итого», даже если у него есть workspace-каталог с `tg-account.json`

### Requirement: Единая константа периода обхода канала

Система SHALL хранить номинальный период обхода канала монитором как одну
константу `CHANNEL_CHECK_PERIOD_SECONDS` в `core/config.ts`, переиспользуемую
скиллом `monitor` для отбора назревших каналов (`getChannelsBatch`), а не
задаваемую отдельным значением в нескольких местах.

#### Scenario: monitor использует общую константу периода

- **WHEN** `monitor` формирует батч назревших каналов
- **THEN** порог «канал не обрабатывался дольше периода» берётся из
  `CHANNEL_CHECK_PERIOD_SECONDS`, а не отдельной локальной константы

### Requirement: Подсчёт каналов у агента

Система SHALL за каждый агент считать общее число каналов как `COUNT(*) FROM channels` его `tg-channels.db` — абсолютное значение на момент построения отчёта, не дельта.

#### Scenario: Подсчёт каналов агента

- **WHEN** система строит отчёт за день
- **THEN** значение «каналов у агента» равно текущему числу строк в таблице `channels` этого агента

### Requirement: Подсчёт просмотренных и активных каналов за день

Система SHALL считать число каналов, просмотренных за день, как `COUNT(*)` строк `channel_visits` агента с `visitedAt` в окне дня UTC+5, независимо от `outcome`. Система SHALL считать число активных каналов как `COUNT(*)` строк того же окна с `outcome = 'active'`.

#### Scenario: Канал с пустым визитом тоже считается просмотренным

- **WHEN** за день в `channel_visits` есть визит канала с `outcome = 'empty'`
- **THEN** этот визит увеличивает счётчик «каналов просмотрено», но не «каналов активно»

#### Scenario: Канал с ошибкой визита тоже считается просмотренным

- **WHEN** за день в `channel_visits` есть визит канала с `outcome = 'error'`
- **THEN** этот визит увеличивает счётчик «каналов просмотрено», но не «каналов активно»

### Requirement: Подсчёт ошибок отправки за день

Система SHALL считать число ошибок отправки за день как `COUNT(*)` строк `send_errors` агента с `occurredAt` в окне дня UTC+5, и SHALL группировать их по `errorCode` для разбивки по типу, агрегированной по всем агентам платформы.

#### Scenario: Подсчёт ошибок агента

- **WHEN** система строит отчёт за день
- **THEN** значение «ошибок» равно числу строк `send_errors` этого агента за день, независимо от `source` (`monitor` или `dm_send`)

#### Scenario: Разбивка по типу ошибки общая для платформы

- **WHEN** система формирует блок «Ошибки за день»
- **THEN** разбивка по `errorCode` считается по строкам `send_errors` всех агентов вместе, не по одному агенту

### Requirement: Фильтр активных агентов

Система SHALL перед сбором метрик воронки определять список активных агентов — агентов, у которых на момент формирования отчёта включена (enabled) задача мониторинга (`monitor` либо `monitor-v2`) — и собирать метрики только по ним. Неактивные агенты SHALL не создавать никакой записи в результате сбора.

#### Scenario: У агента включена задача мониторинга

- **WHEN** у агента enabled хотя бы одна из задач `monitor`/`monitor-v2`
- **THEN** агент включается в сбор метрик наравне с остальными активными агентами

#### Scenario: У агента отключены обе версии мониторинга

- **WHEN** у агента `enabled=0` и для `monitor`, и для `monitor-v2`
- **THEN** агент полностью исключается из сбора — метрики по нему не считаются, он не встречается в результате ни в каком виде

#### Scenario: Активность проверяется на момент сбора

- **WHEN** мониторинг агента был включён в течение отчётного дня, но выключен к моменту формирования отчёта
- **THEN** агент исключается — используется состояние enabled на момент сбора, истории включённости за день система не хранит

### Requirement: Разбивка отправленных сообщений по каналам

Система SHALL за завершившийся день UTC+5 собирать по каждому активному агенту построчную разбивку сообщений группы по каналам: `chatId`, число сообщений, заголовок канала и данные для переходимой ссылки (username чата либо числовой id супергруппы/канала и id последнего сообщения агента в этом канале за день). Личные сообщения (DM) SHALL не входить в разбивку.

#### Scenario: Сообщения в несколько каналов

- **WHEN** агент за отчётный день отправил сообщения в несколько разных каналов
- **THEN** разбивка содержит отдельную запись на каждый такой канал с числом сообщений именно в него

#### Scenario: Канал без публичного username

- **WHEN** канал агента — приватная супергруппа/канал без публичного username
- **THEN** данные для ссылки берутся из числового id канала и id последнего сообщения агента за день, а не из username

### Requirement: Пропуск агентов с несовместимым ограничением на этапах охвата

Перед снятием снапшота охвата публичного канала (просмотры поста, число подписчиков) и заявок в приватный канал по конкретному агенту система SHALL проверять активное ограничение агента (`agent_restrictions`, `getActiveRestriction`). Если `restriction_type` агента — `need_update_session` или `banned`, MTProto-подключение SHALL не выполняться для этого агента на этих метриках, попытка пропускается без установки пометки о сбое сбора (см. `funnel-report`, «Пометки о пропущенных данных»). Ограничение `suspend` SHALL не приводить к пропуску — сессия остаётся рабочей, ограничена только отправка.

#### Scenario: Агент с need_update_session пропущен без попытки подключения
- **WHEN** у агента активна запись `agent_restrictions` с `restriction_type = need_update_session`
- **THEN** система не вызывает `tg.loadAccount`/MTProto для этого агента на этапах охвата, снапшот не снимается, `note5to7` не устанавливается

#### Scenario: Агент с banned пропущен без попытки подключения
- **WHEN** у агента активна запись `agent_restrictions` с `restriction_type = banned`
- **THEN** система не вызывает `tg.loadAccount`/MTProto для этого агента на этапах охвата, снапшот не снимается, `note5to7` не устанавливается

#### Scenario: Агент с suspend не пропускается
- **WHEN** у агента активна запись `agent_restrictions` с `restriction_type = suspend`
- **THEN** система выполняет попытку снятия снапшота как обычно, ограничение не влияет на этот шаг

#### Scenario: Локальные метрики (этапы 1-4) не зависят от ограничения
- **WHEN** у агента активное ограничение любого типа (`need_update_session`, `banned` или `suspend`)
- **THEN** метрики из локальных БД агента (число каналов, ответы в группах, ошибки отправки) собираются как обычно — эти метрики не требуют MTProto-подключения

### Requirement: Пер-агентный teardown MTProto-сессии при сборе

При сборе метрик, требующих MTProto (этапы 5-7), система SHALL закрывать сессию
агента сразу после завершения его этапов 5-7 и SHALL выдерживать паузу перед
освобождением замка сессии (`session-lock`) — защита от `AUTH_KEY_DUPLICATED`,
поскольку сервер Telegram убирает запись о старом подключении не мгновенно, —
прежде чем переходить к следующему агенту. Сессии SHALL не удерживаться открытыми
до конца прогона.

Teardown SHALL не выполняться для агента, пропущенного без подключения из-за
несовместимого ограничения (`need_update_session`/`banned`), — для такого агента
сессия не открывалась. Teardown SHALL закрывать только сессию текущего агента и SHALL
не затрагивать сессии других агентов, переиспользуемые в этом же прогоне (в частности
`REPORT_AGENT_ID`, через которого в конце прогона отправляется отчёт).

Путь сбора по требованию (переиспользующий один общий долгоживущий MTProto-клиент,
например плагин-гейтвей) SHALL не выполнять пер-агентный teardown — управление
жизненным циклом общего клиента остаётся за вызывающей стороной.

#### Scenario: Сессия агента закрывается сразу после его этапов 5-7

- **WHEN** таймерный сбор завершил этапы 5-7 очередного агента (успехом или с пометкой о сбое)
- **THEN** MTProto-сессия этого агента закрывается, выдерживается пауза перед снятием замка сессии, и только затем начинается подключение следующего агента

#### Scenario: Сессии не удерживаются до конца прогона

- **WHEN** таймерный сбор обходит всех активных агентов подряд
- **THEN** в каждый момент прогона удерживается открытой сессия не более одного собираемого агента (плюс сессия `REPORT_AGENT_ID` для отправки отчёта), а не накопленные сессии всех уже обработанных агентов

#### Scenario: Агент пропущен по ограничению — teardown не вызывается

- **WHEN** у агента активно ограничение `need_update_session` или `banned`, из-за чего его этапы 5-7 пропущены без попытки подключения
- **THEN** teardown для этого агента не выполняется (закрывать нечего), сбор переходит к следующему агенту

#### Scenario: Путь сбора по требованию не рвёт общий клиент

- **WHEN** сбор выполняется по требованию через общий долгоживущий MTProto-клиент (не таймерный процесс)
- **THEN** между агентами пер-агентный teardown не выполняется, общий клиент остаётся подключённым, его закрытие — ответственность вызывающей стороны
