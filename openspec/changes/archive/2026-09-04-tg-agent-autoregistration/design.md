## Context

Полный анализ и обоснования — `docs/design/tg-agent-autoregistration/`:
`requirements-v1.md` (правила R-1…R-13, R-D1…R-D5), `architecture.md`
(технические решения с альтернативами), `tg-agent-autoregistration-sequence.puml`
(сценарий по шагам). Здесь — сводка для реализации, без повторного обоснования.

Сейчас в проекте: онбординг агента — штучная ручная операция
(`skills/tg-agent-create`, `tg-agent-create-v2`, гранулярные OpenClaw-тулы,
которые LLM-агент ведёт по `SKILL.md`). Расшифровки tdata-сессий и методов
изменения аккаунта (2FA, профиль, каналы) в коде нет вообще.

## Goals / Non-Goals

**Goals:**
- Один вызов скилла обрабатывает пачку tdata-архивов последовательно,
  детерминированным кодом, без LLM-цикла внутри прогона.
- Никакого нового деплой-рантайма (остаёмся в Node/TS, без Python/venv).
- Прозрачный статус на каждый аккаунт: `done` / `proxy_failed` /
  `setup_failed` / `needs_manual_code`.
- Недорегистрированный агент не виден платформенным cron-скриптам
  (`listAgentIds()`), пока не дойдёт до `done`.

**Non-Goals:**
- Параллельная обработка аккаунтов (constraint — строго последовательно).
- Идемпотентный ретрай `setup_failed`, когда 2FA уже сменён частично
  выполненным прогоном — известное ограничение, не решается в этой фиче.
- Read-back верификация каждого MTProto-вызова отдельным шагом — избыточна,
  ошибки Telegram API (RPCError с кодом) уже дают достаточный статус.
- Автоматизация `needs_manual_code` — восстановление полностью ручное.

## Decisions

**D1. Структура: один OpenClaw-тул → in-process core-модуль, без LLM-цикла.**
`index.ts` регистрирует один тул, `execute()` делегирует прямым вызовом функции
в `src/core/tg-agent-autoregistration/run.ts` (+ тонкий CLI-двойник
`src/scripts/tg-agent-autoregistration.ts`, по паттерну `core/+scripts/`
остального репозитория). Альтернатива — гранулярные тулы + LLM-цикл, как у
`tg-agent-create*`, — отклонена: весь процесс (R-1…R-13) детерминирован, ни
на одном шаге не требуется суждение оператора внутри цикла; LLM-цикл был бы
антипаттерном, ради ухода от которого `docs/decisions/0001-scripts-over-openclaw-agent.md`
увёл фоновые скиллы в код.

**D2. Расшифровка tdata → рабочая MTProto-сессия: `@mtcute/convert`.**
Рассмотрены три варианта: (A1) портировать личный TS-gist автора GramJS —
неподдерживаемый источник, сборку итоговой сессии пришлось бы писать самим;
(A2, выбран) npm-пакет `@mtcute/convert` — maintained-зависимость,
`convertFromTdata()`+`convertToGramjsSession()` уже дают всё нужное, сборка
GramJS-сессии сверена побайтово с `node_modules/telegram/sessions/StringSession.js`;
(C) Python/`opentele` subprocess — самый обкатанный на реальных данных
инструмент, но добавляет второй управляемый рантайм на VPS (venv, отсутствие
journald-видимости, второй каталог ошибок Telegram) при том же версионном
риске, что и A1/A2. Версионный риск (формат tdata не документирован, привязан
к версии TDesktop) неустраним ни одним вариантом — это свойство формата.

**D3. Две MTProto-сессии на аккаунт, обе остаются активными.**
Bootstrap-сессия (из tdata через D2) готовит аккаунт (2FA, сброс сессий,
очистка, профиль, канал) и принимает входящий код авторизации. Агентская
сессия регистрируется отдельно (`authSendCode`/`authSignIn`, общие
apiId/apiHash персоны) и пишется в `tg-account.json`. Bootstrap-сессию после
получения агентской намеренно не разлогинивают — два активных устройства
ближе к поведению обычного пользователя, чем аккаунт с единственной сессией
из ниоткуда.

**D4. Стейджинг вне `workspace-<agentId>`, атомарный перенос на `done`.**
Данные аккаунта в процессе живут в
`~/.openclaw/tg-agent-autoregistration/staging/agent<N>/` — не в
`workspace-agent<N>/`, потому что сам факт существования папки
`workspace-*` делает агента видимым для `listAgentIds()` и, соответственно,
для платформенных cron-скриптов (`discovery`, `distribute-channels`,
`distribute-pool`, `channel-coverage-update`, `backfill-schedule-defaults`,
`join-queue-backfill`), у которых для него ещё нет `tg-account.json`.
`status.json` пишется через tmp-файл+`renameSync`. На `done` — сначала в
стейджинге полностью собирается итоговое содержимое (`tdata/`+
`tg-account.json`+`SOUL.md`), затем один `renameSync(staging, workspace)` —
атомарен на уровне ОС в пределах одной файловой системы.

**D5. Безусловная очистка унаследованных фото/публичных каналов.**
Перед применением нового профиля/канала персоны — удаляются все существующие
фото профиля (`photos.getUserPhotos`+`deletePhotos`) и все публичные каналы,
которыми аккаунт уже админит (`channels.getAdminedPublicChannels`+
`deleteChannel`), безусловно, а не только при фактическом упоре в лимит
`CHANNELS_ADMIN_PUBLIC_TOO_MUCH`. Необратимая операция — явное решение
координатора выполнять её автоматически в каждом прогоне без подтверждения
на аккаунт (осознанное отступление от общего принципа проекта «Обратимость»,
`docs/agent-playbook.md`, принятое для этого процесса).

**D6. `provision-proxy-for-new-agent.ts` переиспользуется без изменений.**
Вызывается подпроцессом на каждую попытку подбора прокси (существующие
режимы `--create-candidate`/`--delete-candidate`) — трогать/рефакторить
существующий продакшн-скрипт ради этой фичи решено не делать.

## Risks / Trade-offs

- [Формат tdata не документирован, версия TDesktop закупленных аккаунтов
  неизвестна заранее; ошибка версии может не дать явного сбоя, а вернуть
  мусорный `authKey`] → Митигация: спайк на реальном образце (`3453453453/tdata/`)
  перед продакшен-использованием — **не проведён**, открытый риск на момент
  этого документа.
- [`auth.resetAuthorizations` не работает первые 24 часа после логина текущей
  сессии — возраст закупленных tdata-сессий неизвестен] → Митигация: падает
  как обычная ошибка Telegram API при подготовке → `setup_failed` (R-1),
  видно оператору в отчёте.
- [Необратимое удаление каналов/фото (D5) — отступление от принципа
  обратимости проекта] → Митигация: явное, зафиксированное решение
  координатора; риск принят, не смягчается кодом.
- [`@mtcute/convert@0.31.0` — sub-1.0 пакет; сам мейнтейнер предупреждает о
  версионной нестабильности парсинга tdata] → Митигация: нет технической —
  риск вскрывается спайком, не устраняется архитектурой.
- [Падение процесса между «стейджинг полностью собран» и `renameSync` на
  `done` — окно маленькое, но не нулевое] → Митигация: не закрывается
  отдельным статусом — явное решение координатора не усложнять модель
  статусов ради маловероятного окна.

## Migration Plan

Аддитивная фича, миграции данных нет. Деплой — стандартный
(`scp`+`chown`+`openclaw gateway restart`) плюс `npm install @mtcute/convert`
(тянет `@mtcute/node` в рантайме). Новая директория на ВПС
`~/.openclaw/tg-agent-autoregistration/` создаётся при первом запуске
(`templates/` заполняется оператором вручную до первого прогона персоны).
Откат — удалить новый тул/модули; существующие агенты и остальные скрипты
платформы не затрагиваются (ничего в `service.ts`/`dispatcher.ts` не
меняется).

## Open Questions

- Таймбокс на спайк варианта A2 (`@mtcute/convert` на реальных данных) —
  управленческое решение, не техническое.
- Бросает ли `convertFromTdata` различимые доменные исключения (для
  классификации под `setup_failed`) или все ошибки нужно ловить общим
  `catch` — не проверялось чтением исходников, требует эмпирической проверки.
- Точные TS-интерфейсы/сигнатуры `core/tg-agent-autoregistration/run.ts` и
  `core/tdata/*.ts` — определяются в `tasks.md`/при реализации, не
  зафиксированы здесь.
