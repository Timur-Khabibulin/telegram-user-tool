## Context

26 агентов платформы (список растёт, +6/+15 в день на момент написания) находятся в
ограничении `need_update_session` (`agent_restrictions`, причина — `406: AUTH_KEY_DUPLICATED`).
Это агенты, созданные вручную до появления `tg-agent-autoregistration` — для них есть
tdata-сессия Telegram Desktop, полученная оператором при первичной настройке аккаунта и
хранящаяся у него локально.

Существующий `tg-agent-autoregistration` (`src/core/tg-agent-autoregistration/`,
`src/core/tdata/`) уже умеет: (1) расшифровывать tdata в рабочее MTProto-соединение
(`connectBootstrap`, через `@mtcute/convert`), (2) регистрировать вторую, независимую
MTProto-сессию аккаунта, автоматически перехватывая код авторизации через уже
залогиненное bootstrap-соединение (`registerAgenticSession` + `readIncomingCode`). Но весь
пайплайн целиком (`prepareAccount`) рассчитан на НОВЫЕ аккаунты и делает необратимые
деструктивные шаги — смену 2FA, удаление всех фото профиля, удаление всех публичных
каналов, применение нового шаблона персоны. Прогонять его на уже настроенном, рабочем
агенте недопустимо — уничтожит существующий профиль/канал/персону.

`tg-agent-reauth` (старый скилл) умеет реавторизовать существующего агента, не трогая его
настройки — но требует, чтобы оператор вручную получил код из Telegram и передал его
скиллу. Не автоматизируется без участия человека на каждый агент.

Нужна возможность, сочетающая оба свойства: не трогать существующие настройки агента (как
`tg-agent-reauth`) + не требовать участия оператора в получении кода (как
`tg-agent-autoregistration`).

## Goals / Non-Goals

**Goals:**
- Реавторизовать существующего, уже настроенного агента новой MTProto-сессией, используя
  локальную tdata-сессию как источник авторизации, без участия оператора в получении кода.
- Не менять ничего в существующей конфигурации агента, кроме поля `sessionString`.
- Переиспользовать существующий, уже проверенный на реальных прогонах код tdata/agentic-session
  без изменений внутри него.

**Non-Goals:**
- Не создаёт новых агентов (это делает `tg-agent-autoregistration`).
- Не меняет 2FA-пароль аккаунта, не удаляет фото/каналы, не применяет шаблон персоны.
- Не автоматизирует массовую реавторизацию всех 26 агентов одним вызовом — инструмент
  принимает одного `agentId` за вызов; массовость (если понадобится) — отдельная задача
  поверх этого инструмента, не часть этого change.
- Не решает первопричину `AUTH_KEY_DUPLICATED` (параллельное использование одного и того
  же аккаунта посторонним) — только устраняет её следствие (мёртвая сессия) для одного
  конкретного вызова.

## Decisions

**D1. Взять из `tg-agent-autoregistration` только `connectBootstrap` + `registerAgenticSession`,
без `prepareAccount`.** Обе функции уже экспортированы и не связаны напрямую с
деструктивными шагами `prepareAccount` — вызываются как соседние, а не вложенные шаги в
`processAccount` (`run.ts:163-175`). Альтернатива — скопировать/переписать логику заново —
отклонена: увеличивает риск рассинхронизации с уже проверенным на реальных прогонах кодом
(`docs design/tg-agent-autoregistration` отмечает нестабильность прокси/bootstrap-соединения
как известный источник багов — переиспользование существующей обработки этих случаев
важнее, чем чистота нового модуля).

**D2. `tdataPath` не параметр, а фиксированная конвенция `workspace-<agentId>/tdata/`.**
Совпадает с финальным расположением tdata, которое использует сама `tg-agent-autoregistration`
после переноса из стейджинга (`design.md` этого change, D4). Один путь — один способ его
вычислить (`tdataPath(agentId)` в `config.ts`, по образцу `channelsDbPath`/`tasksDbPath`),
вместо параметра, который пришлось бы передавать и валидировать на каждом вызове.

**D3. 2FA-пароль — параметр с дефолтом, не обязательное поле.**
`Password2FA.txt` внутри tdata хранит пароль на момент выгрузки tdata — для части агентов
он уже устарел (подтверждено оператором на живом примере). Единственный сейчас известный
работающий кандидат — пароль шаблона персоны `maria`
(`~/.openclaw/tg-agent-autoregistration/templates/maria/default_agent_data.json`, поле
`2fa`) — совпадает с тем, что эти агенты, судя по всему, заводились под той же персоной
ещё до автоматизации. Инструмент принимает `password2fa` необязательным параметром,
по умолчанию — значение из этого файла; если он не подходит — `authSignIn` вернёт явную
ошибку (`needsPassword`/неверный пароль), не тихий сбой, и оператор передаст пароль явно
следующим вызовом.

**D4. Bootstrap-соединение НЕ разлогинивается после получения новой сессии.**
Тот же выбор, что и в `tg-agent-autoregistration` (D3 из его design.md) — закрывается
только локальный сокет процесса (`client.disconnect()`), сессия на стороне Telegram
остаётся активной. Причина та же: две активных сессии ближе к обычному поведению
пользователя, чем одна «из ниоткуда».

**D5. Перезапись только поля `sessionString` в существующем `tg-account.json`.**
Тот же приём, что Шаг 6 в `tg-agent-reauth` — остальные поля (`apiId`, `apiHash`, `device`,
`proxy`, `accountId`) читаются из уже существующего файла и не меняются: они уже рабочие
для этого агента (прокси уже подтверждён предыдущей эксплуатацией), пересоздавать их нет
причины.

**D6. Отдельный тул + отдельный скилл, не расширение `tg-agent-reauth`.**
Совпадает с уже принятой в проекте практикой развилки `tg-agent-create`/`tg-agent-create-v2`
— разные предпосылки (наличие/отсутствие tdata) оформляются разными скиллами, а не веткой
внутри одного, чтобы не усложнять существующий рабочий `tg-agent-reauth` условной логикой.

**D7. `connectBootstrap` вызывается с `ignoreVersion: true` (не с дефолтным `false`).**
Обнаружено на реальном прогоне: `@mtcute/convert` 0.31.0 (последняя опубликованная,
свежее не выходило — проверено по npm и по исходникам на GitHub `master`) понимает
формат tdata только до версии `5008003` (~TDesktop 5.8.3). Реальные архивы (TDesktop
6.9.3/7.0.x — агенты созданы до автогенерации) новее и падают с `Unsupported version`
без `ignoreVersion`. Проверено изолированным скриптом (вне production-кода) на 20
реальных аккаунтах с `ignoreVersion: true`: 19 успешно подключились и прошли
`getMe()`, один (agent130) упал с `401: AUTH_KEY_UNREGISTERED` — это означает, что
MTProto-рукопожатие прошло и ключ распознан Telegram корректно (иначе ошибка была бы
на уровне соединения, не API-вызова) — то есть эта конкретная сессия уже мертва сама
по себе, не следствие порчи ключа. `connectBootstrap` (`src/core/tdata/client.ts`)
получил `ignoreVersion` седьмым необязательным параметром (default `false` —
`tg-agent-autoregistration` вызывает без изменений, её осторожность по-прежнему в
силе для НОВЫХ, непроверенных архивов); `reauthFromTdata` передаёт `true` явно.

## Risks / Trade-offs

- **[Риск] `Password2FA.txt`/дефолтный пароль устарел для конкретного агента.** →
  Смягчение: `authSignIn` возвращает явную ошибку вместо порчи состояния; скилл запрашивает
  у оператора актуальный пароль и повторяет вызов с ним.
- **[Риск] Повторное использование tdata локально (Telegram Desktop) после переноса на
  сервер снова спровоцирует `AUTH_KEY_DUPLICATED`** — не для новой сессии (она независима,
  D4), а для самой bootstrap/tdata-сессии, если её продолжают открывать параллельно. →
  Не устраняется этим change технически; операционная рекомендация — не использовать
  локально ту же tdata после переноса на сервер, зафиксировать в SKILL.md как явное
  предупреждение оператору.
- **[Риск] Нестабильность bootstrap-соединения/мобильного прокси при ожидании кода** —
  тот же класс проблем, что уже документирован в `tg-agent-autoregistration`
  (`readIncomingCode`, комментарий про обрывы соединения на живом прогоне agent220). →
  Не требует новой митигации — `readIncomingCode` уже переиспользуется как есть, с уже
  реализованным двойным источником (push-событие + опрос).
- **[Trade-off] Один агент за вызов, не пакетная обработка.** Осознанно (Non-Goals) —
  проще для первой версии; при необходимости массовой реавторизации 26+ агентов можно
  добавить обёртку поверх этого инструмента отдельным change.

## Migration Plan

1. Реализовать `tdataPath(agentId)` в `config.ts`.
2. Реализовать `src/core/tg-agent-reauth-from-tdata/run.ts` — тонкая обвязка вокруг
   `connectBootstrap` + `registerAgenticSession` + перезапись `tg-account.json`.
3. Добавить тул `tg_agent_reauth_from_tdata` в `index.ts`.
4. Добавить `skills/tg-agent-reauth-from-tdata/SKILL.md`.
5. Задеплоить на сервер (`scp` изменённых/новых файлов, `chown`, `openclaw gateway restart`).
6. Проверить на одном реальном агенте из списка `need_update_session` (например, agent207 —
   самое свежее ограничение) прежде, чем предлагать оператору использовать массово.

Откат — тривиальный: новый тул/скилл не меняет существующие модули, при проблеме просто не
вызывается; для уже перезаписанного `tg-account.json` — вернуться к `tg-agent-reauth`
(ручной код) как запасному пути, он не убирается и продолжает работать.
