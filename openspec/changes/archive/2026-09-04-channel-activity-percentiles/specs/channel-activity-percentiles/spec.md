## ADDED Requirements

### Requirement: Хранение p50/p90 активности канала

Система SHALL хранить в таблице `channels` (per-agent `tg-channels.db`) для каждого канала 50-й и 90-й перцентиль числа уникальных отправителей сообщений в сутки за последние 7 дней (`active_writers_p50`, `active_writers_p90`) и время последнего пересчёта (`activity_updated_at`), добавляя колонки аддитивной миграцией без потери существующих данных.

#### Scenario: Первый пересчёт канала

- **WHEN** канал ещё не имеет значения `activity_updated_at`
- **THEN** после пересчёта `active_writers_p50`, `active_writers_p90` и `activity_updated_at` заполняются текущими значениями

#### Scenario: Существующая БД без новых колонок

- **WHEN** `tg-channels.db` создана до появления этой фичи
- **THEN** колонки добавляются через `ALTER TABLE` при следующей инициализации, существующие строки `channels` не теряются

### Requirement: Вычисление перцентиля уникальных отправителей

Система SHALL для каждого канала строить ряд из 7 значений — по одному на каждые календарные сутки окна (граница дня — UTC+5), где значение суток равно числу уникальных `fromId` среди сообщений чата (`channels.chatId`) за эти сутки; сутки без сообщений SHALL входить в ряд со значением 0, а не исключаться из выборки. Перцентиль (p50, p90) SHALL вычисляться линейной интерполяцией между соседними рангами отсортированного ряда.

#### Scenario: Канал с постоянной активностью

- **WHEN** канал имеет сообщения в каждые сутки 7-дневного окна
- **THEN** ряд состоит из 7 ненулевых значений, p50/p90 считаются по всем 7

#### Scenario: Канал с тихими днями

- **WHEN** в части суток окна сообщений не было
- **THEN** эти сутки входят в ряд как 0, а не пропускаются — p50/p90 отражают реальную нерегулярность канала

### Requirement: Источник данных — сессия участника чата

Система SHALL считать историю сообщений чата только через MTProto-сессию агента, уже состоящего в этом чате (`channels.chatId` принадлежит агенту, чья сессия используется). Система SHALL NOT использовать для чтения истории отдельный аккаунт, не состоящий в чате — доступ к истории мегагруппы (в отличие от вещательного канала) недоступен без членства ни через `access_hash` другого аккаунта, ни через резолв username чата сторонним аккаунтом.

#### Scenario: Плановый пересчёт канала агента

- **WHEN** система пересчитывает активность канала `chatId`, принадлежащего агенту `agentId`
- **THEN** история читается сессией именно `agentId`, загруженной через `loadAccount(agentId)`

### Requirement: Плановый пересчёт по TTL

Система SHALL раз в 30 дней выбирать для пересчёта все каналы агента (`channels`, без исключения `banned`/`suspend`), у которых `activity_updated_at` не задан либо истёк 30-дневный TTL, и обрабатывать агентов последовательно одним `TelegramService` (без параллельной обработки нескольких агентов одновременно).

#### Scenario: Просроченный канал

- **WHEN** у канала `activity_updated_at` старше 30 дней либо не задан
- **THEN** канал попадает в выборку планового прогона и пересчитывается

#### Scenario: Свежий канал

- **WHEN** у канала `activity_updated_at` моложе 30 дней
- **THEN** канал не пересчитывается в плановом прогоне

#### Scenario: Несколько агентов в прогоне

- **WHEN** плановый прогон обрабатывает нескольких агентов
- **THEN** агенты обрабатываются один за другим (не параллельно), сбой одного агента не прерывает обработку остальных

### Requirement: Ручной запуск по списку агентов

Система SHALL предоставлять ручной запуск с явным списком `agentId` на входе, при котором TTL игнорируется и пересчитываются все каналы каждого перечисленного агента. Ручной запуск SHALL поддерживать необязательный параметр `--limit N`, ограничивающий число обрабатываемых каналов отдельно для каждого агента списка (без ограничения — по умолчанию обрабатываются все каналы агента). Обработка агентов в ручном запуске SHALL быть последовательной, без параллелизма.

#### Scenario: Ручной запуск без ограничения

- **WHEN** запущен ручной пересчёт со списком агентов без `--limit`
- **THEN** пересчитываются все каналы каждого перечисленного агента, независимо от `activity_updated_at`

#### Scenario: Ручной запуск с ограничением

- **WHEN** запущен ручной пересчёт со списком агентов и `--limit N`
- **THEN** у каждого перечисленного агента обрабатываются только первые N его каналов

### Requirement: Интерактивный запуск через OpenClaw

Система SHALL предоставлять интерактивный инструмент OpenClaw-плагина, запускающий ручной пересчёт (список `agentId`, обязателен; необязательный `limit`) через systemd, без использования общего `TelegramService` процесса плагина. Инструмент SHALL NOT дожидаться завершения пересчёта — SHALL возвращать только факт успешного запуска.

#### Scenario: Успешный запуск

- **WHEN** интерактивный инструмент вызван со списком `agentId`
- **THEN** запускается systemd-юнит ручного пересчёта для этих агентов, инструмент немедленно возвращает подтверждение запуска, не дожидаясь результата вычислений

#### Scenario: Невалидный agentId

- **WHEN** в списке `agentId` встречается значение, недопустимое для имени systemd-юнита
- **THEN** инструмент возвращает ошибку валидации до обращения к systemd, ничего не запускает

### Requirement: Изоляция сбоев по каналу

Система SHALL обрабатывать пересчёт каждого канала изолированно: ошибка чтения истории (FLOOD_WAIT, недоступность чата, сетевой сбой) SHALL приводить к пропуску этого канала без записи новых значений, не прерывая обработку остальных каналов агента и остальных агентов прогона.

#### Scenario: Ошибка чтения одного канала

- **WHEN** при чтении истории конкретного канала возникает ошибка
- **THEN** канал пропускается (его `active_writers_p50/p90/activity_updated_at` не изменяются), обработка остальных каналов агента продолжается

#### Scenario: FLOOD_WAIT

- **WHEN** Telegram возвращает FLOOD_WAIT при чтении истории канала
- **THEN** система ожидает указанное время и повторяет попытку для этого канала, не прерывая прогон

### Requirement: Человеческий темп чтения MTProto

Система SHALL читать историю чата батчами по случайному числу сообщений в диапазоне 5-10 на батч, со случайной паузой 10-20 секунд между батчами. Система SHALL читать посты канала (для `avg_views`) по одному сообщению за сетевой вызов, со случайной паузой 10-30 секунд между постами.

#### Scenario: Чтение истории чата

- **WHEN** система читает историю чата для расчёта активности
- **THEN** каждый сетевой запрос возвращает от 5 до 10 сообщений (случайно), между запросами — случайная пауза 10-20 секунд

#### Scenario: Чтение постов канала

- **WHEN** система читает посты канала для расчёта охвата
- **THEN** каждый сетевой запрос возвращает один пост, между запросами — случайная пауза 10-30 секунд
