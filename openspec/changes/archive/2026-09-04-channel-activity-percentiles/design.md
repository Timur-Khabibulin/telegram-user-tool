## Context

Отчёт-воронка (`funnel-tracker`, ежедневно 19:10 UTC) уже содержит CSV-разбивку каналов, куда агент отправлял сообщения за день (`buildFunnelCsv`, вторая таблица). Нужно обогатить её метрикой реальной активности канала — устойчивой к выбросам оценкой того, сколько разных людей пишет в чат обсуждения (`channels.chatId`) за сутки, за последний месяц.

Аналогичный по форме прецедент в кодовой базе — `channel-coverage-report` (`avg_views`/`subs_count`): плановый пересчёт раз в 30 дней по TTL, кэш в `channels`, скрипт `channel-coverage-update.ts` с последовательным циклом по агентам. Эта фича повторяет форму, но не источник данных: `avg_views` читает 11 последних постов канала (дёшево), эта фича читает всю историю чата за 7 дней (окно сокращено с изначальных 30 — Decision 10) — на порядки дороже даже при более узком окне.

## Goals / Non-Goals

**Goals:**
- Посчитать p50/p90 уникальных отправителей сообщений в сутки за 7 дней на канал, сохранить в `channels`.
- Плановый пересчёт раз в 30 дней (TTL) + ручной запуск по списку агентов.
- Отразить p50/p90 в CSV дневного funnel-отчёта, в таблице каналов с отправкой.

**Non-Goals:**
- Не ограничивать объём читаемой истории на канал и не размазывать плановый прогон по дням — осознанно принято, что прогон может быть долгим (см. Decision 3).
- Не вводить параллельную обработку агентов — осознанно отвергнуто (см. Decision 2).
- Не создавать отдельный «недельный» отчёт — в проекте есть только дневной funnel-tracker; метрика встраивается в него.
- Не поддерживать чтение для каналов без резолвленного `chatId` (обычные приватные чаты без записи в `channels` не в скоупе — таких не бывает, `channels` и есть реестр).

## Decisions

### 1. Источник данных — `GetHistory` чата сессией самого рабочего агента, без альтернатив

Рассматривались и отклонены два способа обойтись без чтения полной истории чата рабочим агентом:

**а) Чтение через комментарии поста канала (`messages.GetReplies`/`getPostComments`, уже есть в кодовой базе для `monitor-v4-comment-signal`)** — отклонено пользователем: нужен именно поток сообщений чата (`chatId`), а не выборка, привязанная к постам.

**б) Отдельный «пустой» read-only аккаунт, не участвующий в чате** — проверено экспериментально на проде (2026-08-21, три пробы через временный diagnostic-скрипт, не вошедший в репозиторий):

1. `channels.GetFullChannel` с `channelId`/`channelAccessHash`, сохранёнными ДРУГИМ агентом → `CHANNEL_INVALID`. `access_hash` в Telegram привязан к аккаунту, которым он получен; чужой `access_hash` нерабочий для другой сессии.
2. Резолв группы обсуждения по её собственному `chatUsername` с аккаунта, который не состоит в группе → `Error: No user has "<username>" as username` (тот же username тем же вызовом резолвится нормально с аккаунта-участника). Т.е. Telegram не отдаёт `contacts.ResolveUsername` для megagroup стороннему аккаунту, даже когда username существует и виден участнику — в отличие от вещательных каналов (там резолв работает для любого, проверено на публичном канале Дурова).
3. Из этого следует: у группы обсуждения нет способа прочитать историю без членства в ней — ни через identity канала, ни через username группы.

Рабочий агент **уже состоит** в каждом своём чате (это необходимое условие отправки сообщений туда) — значит дополнительного «входа» для чтения не требуется, только увеличение числа MTProto-вызовов на существующей сессии.

### 2. Без параллелизма между агентами

`TelegramService` хранит один активный аккаунт в мутируемом поле `accountConfig` (`service.ts:207`, `loadAccount()` его перезаписывает) — конкурентные вызовы разных агентов на одном инстансе гонка. Технически возможная альтернатива — свой `TelegramService` на агента + `Promise.all` — рассмотрена и отклонена: это новый паттерн (все существующие скрипты — `channel-coverage-update.ts`, `funnel-tracker.ts`, `daily-summary.ts` — используют один инстанс последовательно), и он снимает защиту, которую даёт последовательный цикл: параллельный прогон по всем агентам вне `tg-agents.slice`/flock-семафора scheduled-диспетчера рискует пиковой нагрузкой на VPS. Решено: последовательный цикл, как у существующих скриптов — и для планового прогона, и для ручного.

### 3. Без потолка на объём чтения и без размазывания по дням

`avg_views` читает 11 постов на канал; эта метрика — всю историю чата за окно (7 суток — Decision 10), потенциально на порядки больше сообщений на активный канал. Рассматривались смягчения (потолок сообщений на канал, разнесение TTL-пересчёта по дням вместо разового прогона раз в 30 дней) — отклонены пользователем: прогон может идти долго, это фоновая штука, время выполнения не ограничиваем.

### 4. Перцентиль — линейная интерполяция, не nearest-rank

Выбрана линейная интерполяция между рангами (`numpy.percentile` / Excel `PERCENTILE.INC` по умолчанию) — узнаваемый стандарт, воспроизводимый вручную в Excel при сверке, в отличие от nearest-rank.

### 5. Сутки без сообщений — 0, не пропуск

Ряд из 30 значений всегда полной длины (по одному на каждые календарные сутки окна, граница UTC+5 — `startOfUtcPlus5Day`, как у воронки); канал без сообщений в конкретные сутки даёт 0 в этом дне ряда, а не выпадение дня из выборки — иначе p50 тихих каналов был бы искусственно завышен подсчётом только по «живым» дням.

### 6. Селекция каналов — все строки `channels`, TTL по образцу `getChannelsForCoverageUpdate`

Без исключения `banned`/`suspend` (в отличие от батча монитора) — метрика описывает канал как площадку независимо от текущего статуса агента в нём.

### 7. Ручной запуск — список агентов + необязательный `--limit N` на агента

Вход — явный список `agentId` (не TTL-driven автовыбор), TTL полностью игнорируется — пересчитываются все каналы каждого перечисленного агента. `--limit N` (опционально, по умолчанию — все каналы) ограничивает число каналов **на каждого** агента отдельно — для точечной проверки перед полным прогоном.

### 8. Слияние с `channel-coverage-report` в один скрипт/юнит

`channel-coverage-update.ts` (существующий, в проде) и новый скрипт активности решают одну и ту же организационную задачу — раз в 30 дней обойти все каналы агента и обновить кэш метрик в `channels` — просто разными метриками (`avg_views`/`subs_count` vs `active_writers_p50/p90`). Рассмотрены два варианта:

- **Оставить раздельно** — минимальный риск для уже работающего `avg_views`, но два независимых скрипта/таймера ежемесячно обходят один и тот же список каналов агента по отдельности — дублирование прохода без причины.
- **Слить в один скрипт `channel-activity-update.ts`** (выбрано) — один проход по каналам агента на прогон; на каждый канал независимо проверяется TTL каждой из двух групп метрик (`coverage_updated_at` для `avg_views`/`subs_count`, `activity_updated_at` для перцентилей) и выполняется то, что просрочено. `channel-coverage-update.ts` и `tg-channel-coverage-update.service`/`.timer` удаляются; `getChannelsForCoverageUpdate` (`src/core/db/channels.ts`) и `saveCoverage` переиспользуются как есть — меняется только вызывающий скрипт, не контракт БД.

Раз TTL двух групп метрик независимы, они могут разойтись во времени (например, `avg_views` канала пересчитан, а `activity` — ещё нет, если раньше отставал по объёму истории) — это ожидаемо и не проблема: каждая колонка обновляется по своему расписанию, ряд `channels` просто может быть частично заполнен в моменте.

### 9. Интерактивный ручной запуск — через systemd, не через общий `TelegramService` плагина

Оператор хочет запускать ручной пересчёт из чата с агентом (`tg_channel_activity_update`), не только по SSH. Прогон при этом может идти минуты-часы (Decision 3), а у OpenClaw-плагина **один `TelegramService` на весь процесс**, общий для интерактивных инструментов ВСЕХ агентов (`index.ts:110-112`, комментарий в коде это явно фиксирует). Если бы инструмент ждал завершения синхронно, используя этот общий `tg`, он держал бы `accountConfig` (мутируемое поле, `loadAccount()` его перезаписывает) занятым на всё время прогона — все остальные интерактивные вызовы любых других агентов в это время либо блокировались, либо ловили гонку за текущий загруженный аккаунт.

Рассмотрены варианты:

- **Синхронно ждать результат** — простой ответ инструмента с реальным итогом, но недопустимо занимает общий `tg` на минуты-часы.
- **`child_process.spawn` в обход systemd** — работает, поддерживает произвольные аргументы напрямую, но вводит первый в проекте случай прямого порождения процесса из интерактивного инструмента, в обход уже устоявшегося паттерна (`triggerTaskNow` в `scheduler-control.ts` всегда дёргает systemd через `systemctl start <unit>`, никогда не спавнит процессы сам).
- **Новый шаблонный systemd-юнит `tg-channel-activity-update-manual@.service`** (выбрано) — по образцу `tg-agent@.service` (`%i` = `agentId`). Инструмент вызывает `systemctl start tg-channel-activity-update-manual@<instance>.service` через уже существующий приватный помощник `systemctl()` (`scheduler-control.ts`, `execFile`, без shell — без риска инъекции) и сразу возвращает факт запуска, не дожидаясь. Сам прогон выполняется отдельным процессом под управлением systemd (свой `TelegramService`, как у любого systemd-юнита) — общий `tg` плагина не трогается вообще.

`instance` шаблонного юнита кодирует оба параметра одной строкой (допустимые символы имени systemd-юнита — только `[A-Za-z0-9:_.\-]`, без запятых/пробелов): `agentId1-agentId2-...` с необязательным суффиксом `.limitN`. Разбор `%i` обратно в `--agents`/`--limit` живёт в отдельном файле `src/scripts/channel-activity-update-manual.sh`, вызываемом с `%i` как позиционным аргументом — **не** инлайн-`bash -c` в `ExecStart=`, как сперва было сделано и сломалось на практике: systemd сам разворачивает `$`/`${...}`-конструкции в строке `ExecStart=` (это касается и содержимого внутри `bash -c '...'`) ДО того, как её увидит bash, и принимает bash-параметр-expansion (`${I%.limit*}`) за обращение к переменной окружения с недопустимым именем («Invalid environment variable name evaluates to an empty string») — юнит стартовал, но `%i` не разбирался, скрипт получал пустые аргументы и по умолчанию уходил в плановый режим по всем агентам вместо одного. `tg-agent@.service` избегает этой ловушки тем, что его `%i` используется как простая подстановка значения (`--agent %i`), без операторов `${...#...}`/`${...%...}` вокруг него.

`agentId` проверяется по строгому паттерну (`AGENT_ID_PATTERN`, `scheduler-control.ts`) ДО подстановки в имя юнита — это не про безопасность самого вызова (`execFile` и так не пропускает через shell), а про то, чтобы отдать понятную ошибку до похода в systemd, а не невнятный отказ `systemctl` от кривого имени юнита.

**Побочная находка при этом решении**: у планового `tg-channel-activity-update.service` не был выставлен `TimeoutStartSec` — дефолтный таймаut systemd (обычно 90с) убил бы прогон на середине, что напрямую противоречит Decision 3 («без ограничения времени»). Добавлен `TimeoutStartSec=infinity` в оба юнита (плановый и ручной) — до этого решения баг был бы незаметен, пока кто-то не подождал бы полный суточный прогон вживую.

### 10. Окно активности сокращено с 30 до 7 дней; TTL пересчёта остался 30 дней

После продовых инцидентов с OOM (см. Risks) пользователь решил сократить окно данных с 30 до 7 суток — меньше сырых сообщений на канал при том же порядке величины проблемы (аномально активные каналы остаются аномально активными и на 7 днях, просто пропорционально меньше). Перцентиль по-прежнему считается по ряду из `WINDOW_DAYS` значений (теперь 7, не 30) — формула (линейная интерполяция, сутки без сообщений = 0) не меняется, меняется только константа `WINDOW_DAYS` в `activity-percentile.ts`.

TTL пересчёта (`activity_updated_at`, `ACTIVITY_CACHE_TTL_SECONDS` в `channel-activity-update.ts`) осознанно оставлен 30 дней, не сокращён до 7 — совпадение окна и TTL не требуется: TTL определяет, как часто значение обновляется, окно — какой период данных оно описывает. Компромисс явный: значение может отражать конкретную неделю месячной давности, пока не наступит следующий пересчёт — принято как приемлемое, метрика и так устойчива к точечным изменениям (percentile, не среднее).

### 11. Отдельный `tg-channel-activity-update.slice` (1GB) вместо общего `tg-agents.slice`

Три подряд OOM-падения (2026-08-23, дважды 2026-08-25) — общий бюджет `tg-agents.slice` (2GB) делился с диспетчерами агентов; даже после фикса потокового чтения (Risks) прогон падал по совокупному потреблению слайса при параллельной нагрузке от обычного трафика агентов, не от собственного потребления процесса (RSS убитого процесса на момент последнего падения — ~440МБ, при том что на всей VPS было занято 2.8 из 3.8Gi). Решено — вынести оба юнита (`tg-channel-activity-update.service` и `-manual@.service`) в свой `tg-channel-activity-update.slice` (`MemoryMax=1G`), без общего бюджета с `tg-agents.slice`.

### 12. Человеческий темп чтения: батчи 5-10 сообщений / посты по одному

Пользователь запросил менее «ботский» паттерн трафика: история чата — случайными батчами по 5-10 сообщений с случайной паузой 10-20с между батчами (вместо одного большого пакетного `GetHistory`, которым фактически была реализация после Decision 9); посты канала (`avg_views`) — по одному сообщению за вызов с случайной паузой 10-30с (вместо одного вызова на 11 постов сразу).

Реализация — в `TelegramService`, не в скрипте:
- `iterChatHistorySince` переведён с `client.iterMessages` (сама решает размер страницы, не даёт вставить паузу между сетевыми вызовами) на ручную пагинацию через `client.getMessages` с `offsetId`, батч 5-10 (рандомно на каждый батч), пауза 10-20с между вызовами.
- Новый метод `getPostsOneByOne` (не правка `getRecentPosts`) — `getRecentPosts` используется другими потребителями (`channel-metrics`, `channel-discovery`, `channel-content-analysis`, `channel-niche`), которым такой темп не нужен и только замедлил бы их без причины; общий маппер сообщения в `ChannelPost` вынесен в `mapMessageToPost`, чтобы не дублировать логику между двумя методами.

Случайные паузы — локальные inline-выражения (`(10 + Math.random()*N) * 1000`), по образцу уже существующего `randomDelay` в `joinDiscussionGroups` (service.ts) — не импорт `sleepRandom` из `skills/util.ts`: `core/` не зависит от `skills/` ни в одном другом месте кодовой базы, это правило слоёв (skills строятся поверх core, не наоборот).

## Risks / Trade-offs

- **[Риск] Прогон может занимать часы на агента** (объём истории на порядки больше, чем у `avg_views`) → осознанно принято (Decision 3); смягчение — при необходимости позже добавить потолок/размазывание отдельным изменением, без изменения контракта `channels`/CSV.
- **[Риск] FLOOD_WAIT чаще, чем у `avg_views`-джоба** из-за объёма `GetHistory`-вызовов → обрабатывать тем же паттерном, что `channel-coverage-update.ts` (`FloodWaitError`, retry с ожиданием `waitSeconds`).
- **[Риск] Долгий прогон одного агента блокирует чтение остальных** (последовательный цикл, без параллелизма, Decision 2) → осознанно принято как компромисс в пользу простоты и защиты VPS; при необходимости ускорить — отдельное решение позже, не блокирует эту фичу.
- **[Trade-off] Нет отдельного потолка на объём** → метрика может быть недоступна дольше 30 дней после деплоя для каналов, до которых прогон ещё не дошёл (TTL-очередь) — не хуже текущего поведения `avg_views`.
- **[Риск] Слияние с `channel-coverage-report` (Decision 8) удлиняет прогон на канал** — теперь на канал с истёкшим TTL обеих групп метрик приходится и дешёвая часть (`avg_views`/`subs_count`, 2 вызова), и дорогая (история чата) в одном проходе → не меняет итоговый объём работы (то же самое суммарно выполнялось бы в двух отдельных прогонах), но делает время одного прохода по каналу менее предсказуемым; смягчение не требуется — оба поднабора работ уже терпимы к сбоям по отдельности (Requirement «Изоляция сбоев по каналу»).
- **[Устранено] OOM-kill планового/ручного прогона** — первый реальный ночной прогон `tg-channel-activity-update.service` (2026-08-23, 03:00 UTC) и три последующих ручных прогона (2026-08-25) убиты ядром по лимиту cgroup `tg-agents.slice` (`MemoryMax=2G`, constraint=CONSTRAINT_MEMCG). Две независимые причины, устранены по отдельности:
  1. **Неограниченное накопление истории в памяти** (`TelegramService.getChatHistorySince`, ранее `getMessages` без пагинации наружу) — канал с 42690 сообщениями за 30 дней ронял процесс за счёт одного этого массива. Исправлено переходом на потоковое чтение: `iterChatHistorySince` (async-генератор поверх GramJS `iterMessages`, страница за страницей) + `ActivityAccumulator` (`activity-percentile.ts`) — держит только `WINDOW_DAYS` множеств `fromId` (7 — Decision 10), а не сырые сообщения. Проверено на канале со 104234 сообщениями/30д — обработан без падения (RSS процесса ~440МБ на пике).
  2. **Общий бюджет `Slice=tg-agents.slice`** (2GB) делился с диспетчерами агентов — даже после фикса (1) прогон падал по совокупному потреблению слайса при параллельной нагрузке от обычного трафика агентов. Исправлено вынесением в отдельный `tg-channel-activity-update.slice` (`MemoryMax=1G`) — планового и ручного юнитов, без общего бюджета с `tg-agents.slice`.

## Migration Plan

1. Аддитивная миграция колонок `channels` (`active_writers_p50`, `active_writers_p90`, `activity_updated_at`), по образцу `migrateCoverageColumns` — существующие БД получают колонки через `ALTER TABLE`, без потери данных. Колонки `avg_views`/`subs_count`/`coverage_updated_at` уже существуют, не трогаются.
2. Новый `channel-activity-update.ts` разворачивается вместе с новым systemd `.service`/`.timer` (`tg-channel-activity-update`); после проверки его работы — `tg-channel-coverage-update.timer`/`.service` останавливаются (`systemctl disable --now`) и удаляются вместе с `channel-coverage-update.ts`, юниты убираются из `/etc/systemd/system/`.
3. Первый плановый прогон после деплоя видит все каналы с `activity_updated_at IS NULL` — считает всё сразу (аналогично холодному старту `avg_views` в своё время); не ограничивается специально. `avg_views`/`subs_count` продолжают обновляться по их собственному `coverage_updated_at` без разрыва — старые значения в `channels` остаются валидными до следующего TTL, независимо от смены скрипта-исполнителя.
4. `funnel-collect`/`funnel-report` — p50/p90 в CSV изначально `null` для ещё не посчитанных каналов, до отдельного бэкафилла ручным запуском (доступен сразу, `channel-activity-update.ts --agents ...`).
5. Откат — при проблемах новый юнит отключается (`systemctl disable --now`); колонки `channels` остаются (аддитивны, не ломают существующих читателей). Если требуется откатить и слияние — временно вернуть `channel-coverage-update.ts`/его юнит из git-истории, схема БД совместима без изменений.
