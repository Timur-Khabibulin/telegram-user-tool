## Context

`tg_agent_reauth_from_tdata` и `tg_private_invite_links` — синхронные plugin-тулы
`index.ts`, исполняются внутри хода LLM-агента, где watchdog codex режет один вызов
тула на ~90 s. Обе операции его пробивают (reauth — ожидание кода авторизации;
invite-links — batch по N агентов через прокси). Проблема и её решение уже пройдены
для `tg-agent-autoregistration` (change `tg-autoreg-detached-report`): прогон
вынесен в отсоединённый `systemd-run`-юнит поверх тонкого ops-скрипта, отчёт уходит
в Saved Messages `REPORT_AGENT_ID`, а сам скрипт принудительно завершает процесс.
Этот change тиражирует тот же рецепт на два оставшихся тула.

Готовность двух тулов к переезду разная:
- **reauth** — логика уже вынесена в чистую `reauthFromTdata(agentId, password2fa,
  log): ReauthFromTdataOutcome` (`src/features/tg-agent-reauth-from-tdata/run.ts`),
  тул в `index.ts` — однострочная обёртка. Нужен только ops-скрипт.
- **private-invite-links** — вся логика (три режима) живёт инлайн в `execute` тула
  (`index.ts` ~1310–1465), работает напрямую с `tg`-сервисом и db-хелперами. Перед
  ops-скриптом её нужно извлечь в чистую функцию.

## Goals / Non-Goals

**Goals:**
- Оба прогона исполняются detached (`systemd-run`), не ограничены watchdog'ом.
- Итог обоих доставляется в Saved Messages `REPORT_AGENT_ID` при любом исходе.
- Оба ops-скрипта принудительно завершают процесс после доставки отчёта.
- Поведение самих операций (что делает reauth; три режима invite-links) не меняется.

**Non-Goals:**
- Не трогаем логику reauth и три режима invite-links по существу — только модель
  запуска и доставки.
- Не вводим общий «job runner»/очередь — тиражируем проверенный точечный рецепт
  автpрега (три скилла — не повод для абстракции).
- Не сохраняем интерактивный STOP-автомат reauth (см. D2).
- Не переносим отчёты в БД `run-log`/`skill-run-report` — доставка только в Saved
  Messages, как у автpрега.

## Decisions

### D1 — Тиражировать рецепт автpрега, а не строить общий механизм
Каждый тул получает свой тонкий ops-скрипт `src/scripts/ops/<name>.ts` по образцу
`tg-agent-autoregistration.ts`: parse argv → вызвать чистую функцию → `renderReport`
→ `console.log` + доставка в Saved Messages `REPORT_AGENT_ID` → `process.exit`.
Скилл запускает его через `systemd-run` (транзиентный `Type=oneshot`, `--collect`,
cwd плагина, `EnvironmentFile=-/root/.openclaw/secrets.env`).
_Альтернатива:_ единый generic detached-runner для всех тяжёлых тулов — отклонено:
преждевременная абстракция ради трёх точечных операторских скиллов, рецепт автpрега
уже проверен в бою.

### D2 — reauth: все данные вперёд, отказ терминален, gateway restart убран
Оператор в скилле задаёт `agentId` и 2FA-пароль сразу (Шаг 1). Detached fire-and-
forget не может спросить пароль/подтверждение посреди прогона, поэтому прежний
STOP-автомат (`password_rejected` → «пришли пароль», `connect_failed` →
«повторить?») убирается: любой `ReauthFromTdataOutcome` — терминальный статус в
отчёте, повтор = новый detached-прогон. Шаг `openclaw gateway restart` удаляется —
в systemd-timer-архитектуре диспетчер читает `tg-account.json` заново каждый тик,
долгоживущего gateway со stale-сессией нет. `password2fa` остаётся опциональным на
уровне функции (дефолт из шаблона персоны), но скилл просит его явно.
_Альтернатива:_ оставить sync-тул для интерактивной первой попытки, detached — как
запасной путь — отклонено: две модели запуска на один тул сложнее и путают оператора.

### D3 — invite-links: сначала извлечь `run.ts`, тул станет обёрткой
Логика тула переносится из `index.ts` в
`src/features/private-invite-links/run.ts` как
`runPrivateInviteLinks(params, log): Result` с сохранением трёх режимов
(обычный / `retryPendingOnly` / `verifyOnly`) и текущего текста отчёта (`renderText`).
Тул `tg_private_invite_links` в `index.ts` становится тонкой обёрткой над ней —
идентично тому, как `tg_agent_autoregistration_run` и `reauthFromTdata` уже
устроены. Ops-скрипт `src/scripts/ops/private-invite-links.ts` парсит
`--agent-ids a,b,c` / `--retry-pending-only` / `--verify-only` и вызывает ту же
функцию. Так тул и CLI гарантированно ведут себя одинаково (один источник логики).
_Альтернатива:_ дублировать логику в ops-скрипте, не трогая `index.ts` — отклонено:
две копии разъедутся, нарушает «один факт — один дом».

### D4 — Доставка отчёта при любом исходе + `process.exit` в хвосте
В обоих ops-скриптах формирование и отправка отчёта в Saved Messages оборачиваются
так, чтобы случиться при любом исходе, включая исключение из чистой функции
(try/catch вокруг прогона → отчёт с текстом ошибки). `process.exit(0)` стоит самым
последним шагом (в `.then`/`.finally` от `main()`), после доставки: висящие после
таймаута прокси GramJS-клиенты не гасят `_updateLoop` даже после `disconnect()` и
иначе держат процесс живым вечно (в detached убивать watchdog'ом некому) — ровно
как задокументировано в ops-скрипте автpрега.

## Risks / Trade-offs

- **Секрет 2FA-пароля reauth в свойствах юнита `systemd-run` и journal** → как и у
  автpрега (там `--two-fa-password` тем же путём): не новый класс риска, помечаем
  явно; пароль уже сегодня передаётся аргументом.
- **Потеря интерактивного ретрая reauth** (D2) → оператор при `password_rejected`
  перезапускает прогон с верным паролем; терминальный статус приходит в Saved
  Messages, а не в чат — приемлемо для точечной операторской операции.
- **Рефакторинг invite-links может изменить поведение непреднамеренно** (D3) →
  извлечение без изменения логики; сверка `renderText` и трёх режимов на прогоне
  одного-двух агентов до архивации (см. tasks «Проверка»).
- **Отчёт в Saved Messages, а не в чат вызвавшего** → как у автpрега/daily-summary:
  фиксированный адресат `REPORT_AGENT_ID`, ошибиться нельзя; оператор знает, где
  смотреть.

## Migration Plan

1. reauth: добавить ops-скрипт (логика уже вынесена) → перевести скилл на
   `systemd-run` → убрать шаг gateway restart.
2. invite-links: извлечь `run.ts` → тул-обёртка в `index.ts` → ops-скрипт →
   перевести скилл на `systemd-run`.
3. Doки `docs/operation.md`. Typecheck изменённых файлов.
4. Операторская проверка каждого на реальном агенте (см. tasks).

Откат: plugin-тулы остаются на месте (D1) — при проблеме скилл временно
возвращается на синхронный вызов тула без потери способности.
