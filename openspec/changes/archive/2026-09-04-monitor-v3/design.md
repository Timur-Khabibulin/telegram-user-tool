## Context

Полный алгоритм и схема БД уже проработаны и зафиксированы отдельно —
`docs/design/monitor-v3/design-v1.md` (пошаговый алгоритм по разделам §0-§2)
и `docs/design/monitor-v3/algorithm-flow.puml` (activity-диаграмма того же
алгоритма, узлы пронумерованы теми же §-ссылками). Это результат
последовательного обсуждения с оператором проекта — этот design.md не
переизобретает алгоритм, а фиксирует технические решения и их обоснование
вокруг уже согласованной логики.

Текущее состояние: `monitor-v2` обходит все каналы батчами по 40 раз в 72ч
(`post-freshness-gate`, R5) — периодичность признана слишком редкой для
правила свежести R1 (комментировать пост только младше 24ч): часть постов
физически не успевает попасть под проверку до истечения окна.

## Goals / Non-Goals

**Goals:**
- Обнаруживать новый пост в публичных каналах намного чаще (каждые 5ч вместо
  72ч), не увеличивая расход MTProto-лимитов аккаунта на сам факт проверки.
- Инициативно комментировать свежий (< 24ч) пост по его содержанию, если LLM
  сочтёт это уместным.
- Ограниченное по времени слежение за ответами на этот комментарий (2 суток),
  затем полный сон канала (ещё 1 сутки, итого 3 суток), без лишней нагрузки.
- Максимально переиспользовать существующие механизмы `monitor-v2`
  (классификация ошибок, `channel-suspend-on-deletion`, ведение тредов) без
  изменений в самом `monitor-v2`.

**Non-Goals:**
- Каналы без публичного username — вне охвата; по ним продолжает работать
  только `monitor-v2`, как сейчас. Отдельный fallback не проектируется в этой
  итерации.
- Изменение поведения `monitor-v2` (общие сообщения в чате обсуждения,
  DM-скоринг, периодический батч-обход) — не меняется ни строкой, `monitor-v3`
  работает параллельно, а не вместо.
- Обнаружение в реальном времени — по-прежнему периодический опрос (5ч), не
  push/webhook.
- Вынесение общей обвязки обработки ошибок отправки в модуль, разделяемый
  между `monitor-v2` и `monitor-v3` — сознательно отложено (см. Decisions).

## Decisions

**1. Обнаружение нового поста — публичное веб-превью (`t.me/s/<username>`),
не MTProto.**
Альтернатива (чистый MTProto-опрос каждого канала раз в 5ч) рассматривалась
и технически не заблокирована на этом кадансе, но веб-превью не расходует
лимиты сессии аккаунта вообще — это анонимный HTTP-запрос, не привязанный к
конкретному аккаунту. Ограничение: работает только для каналов с публичным
username (Non-Goals).

**2. Реализация скрейпинга — `cheerio` + встроенный `fetch`, свой модуль в
`src/core/`, без сторонней scraper-библиотеки.**
Проверены нишевые npm-пакеты вида `telegram-scraper` — заброшены (последний
релиз ~2 года назад, единицы тысяч загрузок/неделю). Сам RSSHub (зрелый,
активно поддерживаемый проект) для своего маршрута Telegram-канала тоже не
использует специализированный пакет — просто HTTP + `cheerio`, тем же путём
идёт и это решение. Селекторы (`tgme_widget_message_wrap`,
`tgme_widget_message_date`, `tgme_widget_message_bubble`) взяты из исходников
RSSHub. Headless-браузер (Puppeteer) не нужен — страница статический HTML без
JS-рендеринга.

**3. Состояние канала — новые значения существующего поля `channels.status`
(`only_comment`, `sleep`), а не отдельные timestamp-поля.**
Первая версия дизайна использовала два новых поля (`postSleepUntil`,
`commentWatchUntil`); заменено на переиспользование существующего `status`
(общего с `banned`/`suspend`/`format_error` из `channel-suspend-on-deletion`)
— канал в проекте по построению может быть только в одном статусе
одновременно, для этого поле и заведено. `only_comment` истекает не в `NULL`
(в отличие от `banned`/`suspend`/`format_error`), а в `sleep` — этот переход
делает сам `monitor-v3` при визите канала, а не общий механизм снятия
просроченных статусов.

**4. Выборка каналов для цикла — фильтр на уровне запроса, не проверка в
цикле.**
`monitor-v3` обрабатывает только каналы с публичным username и активным
статусом (`NULL`/`format_error`/`only_comment`); `banned`/`suspend`/`sleep`
исключаются на уровне SQL-выборки — тот же подход, каким `monitor-v2` уже
исключает `banned`/`suspend` в `getChannelsBatch` (`channel-suspend-on-deletion`).

**5. `lastSeenChannelPostId` — явная защита от повторной реакции на тот же
пост, отдельно от проверки возраста (R1).**
В канале, где посты выходят редко, один и тот же пост может оставаться
«последним» много прогонов подряд; полагаться только на проверку возраста
(< 24ч) недостаточно надёжно как единственная защита от дублирования реакции
— добавлено отдельное поле-guard.

**6. Каданс — фиксированные 5ч (не диапазон).**
Решение оператора проекта; вариант 4-5ч (round-robin разброс) рассматривался,
отклонён в пользу простоты.

**7. Отдельный скилл `monitor-v3.ts`; обвязка классификации ошибок отправки
(`FLOOD_WAIT`/`PEER_FLOOD`/бан/формат) копируется из `monitor-v2.ts`, не
выносится в общий модуль.**
Проверено: `monitor.ts` (v1) и `monitor-v2.ts` уже сегодня не делят такую
обвязку — у каждого своя независимая копия. Это существующий прецедент в
проекте (эволюция v1 → v2 через копирование, не через extraction общей
абстракции), `monitor-v3` следует тому же пути.

**8. Новый LLM-промпт для инициативного комментария к посту.**
`generateReply`/`generateThreadReply` рассчитаны на ответ конкретному
сообщению пользователя (сигнатура берёт текст сообщения пользователя); для реакции
на пост канала от своего имени (без предшествующего сообщения пользователя)
нужен отдельный промпт с иной задачей генерации.

**9. Новый метод `TelegramService` поверх `messages.getDiscussionMessage`.**
Официальный MTProto-метод, резолвящий корневое сообщение ветки обсуждения по
каналу и id поста БЕЗ вступления в сам канал — используется и чтобы найти
служебную копию свежего поста (первый комментарий), и чтобы дёшево проверить
`unread_count` в уже отслеживаемой ветке (слежение за ответами).

## Risks / Trade-offs

- **Неофициальная разметка `t.me/s/`** может измениться без предупреждения →
  парсинг ограничен четырьмя селекторами (минимальная поверхность), мониторинг
  деградации не автоматизирован в этой итерации (см. Open Questions).
- **Несколько постов канала в одном 5-часовом интервале** — реагируем только
  на последний, более ранние комментарий не получают → осознанный компромисс,
  тот же характер потерь, что уже описан в R5 (`post-freshness-gate`).
- **Дублирование обвязки ошибок между `monitor-v2.ts` и `monitor-v3.ts`**
  (решение 7) → риск расхождения при будущих изменениях `monitor-v2`
  (например, в рамках `telegram-error-handling`, ещё in-progress) без
  синхронного обновления `monitor-v3`. Осознанно принято, соответствует уже
  существующему прецеденту v1/v2 в проекте.
- **Общее поле `status` для `monitor-v2` и `monitor-v3`** → канал, ушедший в
  `banned`/`suspend` во время `only_comment`/`sleep`, теряет прогресс
  слежения за комментариями без возможности его возобновить после снятия
  бана/suspend — статус один, состояния взаимоисключающие по построению.
  Принято намеренно (решение пользователя): канал может быть только в одном
  статусе.

## Migration Plan

- Все изменения схемы аддитивны: 2 новые nullable-колонки в `channels`
  (`lastSeenChannelPostId`, `watchedThreadRootMsgId`), 2 новых допустимых
  значения `ChannelStatus` — миграция через `ALTER TABLE ... ADD COLUMN` с
  проверкой `PRAGMA table_info`, тот же паттерн, что уже используется в
  проекте (`runs.cpuUserMs`/`cpuSystemMs`, `channels` статусные колонки).
  Бэкфилл не требуется.
- Включение — по агенту, через существующий пульт-механизм расписания
  (`upsertTask`), тот же путь, каким сегодня включаются `monitor`/`monitor-v2`.
  Не требует одновременного включения на всех агентах.
- Откат — отключить задачу `monitor-v3` (`disableTask`) на нужных агентах;
  новые колонки остаются неиспользуемыми, но безвредными при выключенном
  скилле.

## Open Questions

- Нужен ли уже в первой версии мониторинг/алерт на деградацию парсинга
  `t.me/s/` (например, счётчик подряд неудачных разборов), или отложить до
  появления реальных сбоев на проде.
- Достаточно ли реагировать только на последний пост при нескольких постах
  за 5-часовой интервал, или после первых метрик стоит пересмотреть (см.
  Risks).
- Какие поля веб-превью нужны сверх id/даты/текста поста (просмотры,
  реакции?) — в текущем алгоритме не используются, могут понадобиться позже
  для скоринга/приоритизации.
