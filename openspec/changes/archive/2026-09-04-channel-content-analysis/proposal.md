## Why

Чтобы наполнять канал основного агента сильным контентом, оператору нужно понимать, о
чём и насколько успешно пишут самые крупные каналы в нишах его агентов. Сейчас таких
данных нет: каналы агентов известны (`channels.db`), но их размер, вовлечённость постов
и темы нигде не собираются. Оператор не может за один шаг увидеть «что заходит» у топ-
каналов и взять оттуда идеи.

## What Changes

- Новый интерактивный тул `channel_content_analysis` (OpenClaw-плагин, запуск
  оператором on-demand, не по таймеру). Вход: `agents` (список agentId), `n` (постов с
  канала), `m` (процент самых крупных каналов).
- Агент состоит в основном в мегагруппах-обсуждениях, привязанных к каналам. Идентичность
  привязанного broadcast-канала (`channelId`, `accessHash`, `username`) кэшируется в
  `channels.db` **один раз при синхронизации** (тик монитора / `tg_channels_sync`) — анализ
  её не резолвит на каждом прогоне.
- Для каждого агента по очереди: каналы берутся из кэша идентичности, сортируются по числу
  подписчиков по убыванию (размер — живьём, не кэшируется), отбираются верхние `m%`; с
  каждого отобранного канала собираются последние `n` постов.
- По каждому посту вручную (из объекта MTProto) считается
  **ERR = forwards / views × 100%** (пересылки-репосты / просмотры) и формируется ссылка на пост.
- LLM используется **только** для тега темы и суммаризации (тезисы/мысли/выводы) каждого
  поста — без прозаической сводки по каналу/прогону.
- Результат — CSV-файл (одна строка = один пост) с колонками `agent, channel,
  channel_size, topic, summary, ERR, views, reactions, comments, forwards, age_days, link`. Файл
  сохраняется в workspace админ-агента (`reports/channel-analysis-<UTC-timestamp>.csv`)
  и отправляется оператору в Telegram вместе с коротким сообщением-статистикой.
- Расширяется Telegram-сервис: извлечение `reactions`/`forwards`/`replies` из постов
  (сейчас достаётся только `views`) и новый метод отправки документа в Telegram (сейчас
  сервис умеет только текст).

## Capabilities

### New Capabilities

- `channel-content-analysis`: по запросу оператора собрать и оценить контент топ-каналов
  агентов — отбор `m%` крупнейших broadcast-каналов на агента, последние `n` постов,
  расчёт ERR, LLM-тег темы и суммаризация, ссылка на пост; выгрузка CSV-отчёта на сервер и в Telegram.

## Impact

- **Код:**
  - `src/core/telegram/service.ts` — извлечение `reactions`/`forwards`/`replies` из
    постов; новый метод отправки документа (`sendFile`/`sendDocument`); отдача идентичности
    привязанного канала по чату при синхронизации (на базе существующего
    `resolveLinkedBroadcast`).
  - `src/core/db/channels.ts` — новые колонки идентичности канала (`channelId`,
    `channelAccessHash`, `channelUsername`, метка «без канала») + аддитивная миграция +
    сохранение/чтение в синхронизации.
  - `src/core/` — новый модуль оркестрации анализа (читает идентичность из кэша → размеры →
    отбор `m%` → ERR → ссылки → генерация CSV + статистика прогона).
  - `src/skills/monitor.ts` — на шаге синхронизации резолв + запись идентичности
    новых/непрорезолвленных чатов.
  - `src/llm/` — тег темы и суммаризация поста.
  - `index.ts` — регистрация тула `channel_content_analysis`; `tg_channels_sync` зеркалит
    логику синхронизации с кэшированием идентичности.
- **Данные:** новый каталог `~/.openclaw/workspace-<adminAgentId>/reports/` с CSV-файлами
  прогонов. Таблица `channels` получает колонки идентичности канала (миграция аддитивная).
- **Зависимости:** новых нет — CSV формируется без сторонних библиотек (принцип простоты).
- **Telegram API:** на прогоне — `getChannelSubsCount` (размер, живьём) и `getMessages` (на
  отобранные `m%`); резолв привязанного канала вынесен в синхронизацию и кэшируется. Риск
  FLOOD_WAIT обрабатывается имеющимся `FloodWaitError`.
