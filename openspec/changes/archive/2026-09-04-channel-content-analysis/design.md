## Context

Оператору нужен быстрый способ понять, о чём и насколько успешно пишут самые крупные
каналы в нишах его агентов, чтобы брать оттуда идеи для контента основного канала. Каналы
агентов уже известны (`channels.db`: `chatId`, `title`, `lastProcessedAt`), но их размер,
вовлечённость постов и темы нигде не агрегируются.

Опорные точки в коде:
- `src/core/db/channels.ts` — `channels.db` агента (источник списка каналов).
- `src/core/telegram/service.ts` — `getChannelSubsCount` (число подписчиков),
  `getRecentPostViews`/`getRecentPostTexts` (образцы выборки постов), `ChannelHandle`
  (`username`, `isBroadcast`, `inputChannel`), `FloodWaitError`. Сейчас из постов
  извлекается только `views`; отправка умеет только текст (`sendMessage`).
- `src/core/discovery/run.ts` + `renderReport` — образец core-оркестрации on-demand-прогона
  и текстового отчёта; тот же поток доступен интерактивным тулом `discovery_run` в `index.ts`.
- `src/core/config.ts` — `workspaceDir`, `discoveryDbPath`/`funnelDbPath` (образец
  платформенного артефакта в workspace админ-агента).

Решение принималось в explore-сессии; метрика вовлечённости (ERR по охвату) согласована с
`docs/design/channel-discovery/channel-discovery-v1.md` §3.4.

## Goals / Non-Goals

**Goals:**
- On-demand тул, отбирающий верхние `m%` broadcast-каналов на агента и собирающий последние
  `n` постов с расчётом ERR, тегом темы и суммаризацией.
- Выгрузка единого CSV-отчёта на сервер и в Telegram оператору.
- Устойчивость к частичным сбоям: один плохой канал/агент не валит прогон.
- Никаких внешних сервисов и новых зависимостей.

**Non-Goals:**
- Запуск по расписанию (systemd-таймер) — только ручной вызов.
- Прозаическая LLM-сводка по каналу/прогону и отдельные текстовые файлы — LLM только для
  темы и суммаризации отдельного поста.
- Сохранение метрик/истории прогонов в БД — артефакт прогона это CSV-файл.
- Жёсткий фильтр свежести постов — возраст лишь показывается колонкой `age`.
- Анализ самих групп/обсуждений как чатов — анализируем только broadcast-каналы (в т.ч.
  восстановленные из привязанных к ним обсуждений).

## Decisions

**Источник каналов и размер — только из агента, без внешних сервисов.**
Каналы агента — из его собственных чатов (`channels.db`), без TGStat и т.п. Альтернатива
(кешировать размер из TGStat при discovery) отвергнута: оператор явно исключил внешние
сервисы.

**Идентичность привязанного канала кэшируется при синхронизации, а не резолвится на каждом
прогоне.** Агент состоит в основном в мегагруппах-обсуждениях, а не в самих каналах (так
устроено вступление). Раньше анализ на каждом прогоне восстанавливал привязанный канал
через `resolveLinkedBroadcast` для всех ~200 чатов — сотни `GetFullChannel` с паузами,
минуты и FLOOD_WAIT. Маппинг «обсуждение → канал» неизменен, поэтому он резолвится **один
раз при синхронизации** (тик монитора + `tg_channels_sync`) и сохраняется в `channels.db`
(`channelId`, `channelAccessHash`, `channelUsername`; чаты без канала помечаются, чтобы не
резолвиться повторно). Резолвятся только новые/непрорезолвленные чаты — стоимость размазана
по тикам монитора и платится один раз. Анализ читает идентичность из кэша и собирает
`InputChannel` из `channelId`+`accessHash`; при `CHANNEL_INVALID` (устаревший accessHash) —
разовый пере-резолв по `channelUsername`.

**Размер канала не кэшируется — берётся живьём каждый прогон** (`getChannelSubsCount`), т.к.
число подписчиков меняется, а ранжирование top-`m%` должно быть актуальным. Это оставляет на
прогон ~200 вызовов размера, но убирает ~200 вызовов резолва (≈2× быстрее). Отдельный
refresh-механизм не нужен — `channels.db` и так обновляется на каждом тике монитора.

**Метрика = ERR по репостам.** `ERR = forwards / views × 100%` (пересылки-репосты /
просмотры) — нормированный %, сравнимый между каналами любого размера. Репосты выбраны как
сигнал «контент, которым делятся» — самый дорогой для пользователя жест, ближе всего к
цели (что стоит брать в свой контент). Счётчики `reactions` (сумма
`m.reactions.results[].count`), `comments` (`m.replies.replies`) и `forwards` (`m.forwards`)
всё равно сохраняются в отчёт отдельными колонками для контекста.

**Отбор m% — на каждого агента отдельно (вариант B).** У каждого агента своя персона/ниша;
идеи для агента осмысленны внутри его ниши. m% и сбор идут по агентам по очереди, что также
естественно: каналы агента читает его же сессия. Результат складывается в один CSV
(разделение колонкой `agent`). Альтернатива «общий пул всех агентов» отвергнута: мешает
ниши, требует дедупа, а сравнение ERR между нишами малоинформативно для генерации контента.

**LLM — тег темы и суммаризация поста.** Соответствует принципу «LLM только для текста».
Один вызов на канал отдаёт по каждому посту тему и суммаризацию (тезисы/мысли/выводы) —
без прозаической сводки по каналу/прогону. Анализ изолирован: его сбой деградирует отчёт
(CSV с пустыми темой/суммаризацией), но не роняет метрики.

**Отчёт — CSV-файл, без сторонних библиотек.** Объём (агенты × m% каналов × n постов) не
влезает в TG-сообщение (лимит 4096), поэтому таблица — файл. CSV (а не XLSX) — по принципу
простоты: открывается в Excel/Sheets, не требует зависимостей. В Telegram уходит короткое
сообщение-статистика + CSV как документ.

**Путь файла — workspace админ-агента.** `~/.openclaw/workspace-<adminAgentId>/reports/
channel-analysis-<UTC-timestamp>.csv` — по тому же принципу, что `discovery.db`/`funnel.db`
(артефакт уровня платформы, не одного агента). Timestamp в имени — прогоны не перезатираются,
старые отчёты можно скачать через skill `vps`.

**Расширение сервиса.** В `service.ts` добавляется (а) извлечение `reactions`/`forwards`/
`replies` при выборке постов и (б) метод отправки документа (`sendFile`). Оркестрация —
новый core-модуль по образцу `discovery/run.ts`; тул в `index.ts` — тонкая обёртка.

## Risks / Trade-offs

- **Стоимость прогона: ~1 `GetFullChannel` на канал** (`getChannelSubsCount` для размера) —
  резолв вынесен в синхронизацию и закэширован, на прогоне его нет. При ~200 каналах это
  ~200 вызовов с паузами (было ~400) → прогон ~вдвое короче, но FLOOD_WAIT всё ещё возможен.
  → On-demand запуск; FLOOD_WAIT обрабатывается `FloodWaitError` (короткое ожидание / стоп
  агента на 2 подряд с записью в отчёт); при частых стопах — запускать по меньшему числу
  агентов за раз.
- **Стоимость синхронизации: резолв привязанного канала на новые чаты** (на тике монитора) —
  для уже прорезолвленных чатов резолва нет; за тик резолвится лишь горстка новых чатов
  (join-queue добавляет каналы постепенно). Разовый бэкафилл ~200 старых строк размазан по
  ближайшим тикам. FLOOD_WAIT при синке — то же, что в анализе.
- **Устаревший `accessHash` в кэше** (`CHANNEL_INVALID`). → Разовый пере-резолв канала по
  `channelUsername` только для сбойных каналов; идентичность можно обновить.
- **Незрелые свежие посты занижают ERR.** → Колонка `age_days` показывает возраст; оператор сам
  видит «пост 2 часа назад». Жёсткий фильтр не вводим ради простоты.
- **Устаревание `channel_size`.** → Размер берётся «на момент прогона» и фиксируется в CSV;
  отчёт — снимок, не хранимое состояние.
- **Сбои сети/LLM/прав на отдельных элементах.** → Двухуровневая изоляция (по агенту, по
  каналу): пропуск с записью причины, секция «пропущено» в итоге; LLM-сбой → CSV с
  пустыми темой/суммаризацией.
- **Один канал у двух агентов даёт две строки.** → Допустимо: при варианте B канал
  анализируется в контексте каждого агента; дедуп не требуется.
