## Context

`report-agent-isolation` (реализован и задеплоен) закрепил `REPORT_AGENT_ID` (agent27)
как единственного получателя отчётов и исключил его из `listAgentIds()`. По ходу
обсуждения этой задачи выяснилось: agent27 фактически уже имеет права администратора
приватного канала (`getPendingJoinRequests` → `count: 38`), а `FUNNEL_ADMIN_AGENT_ID`
(agent1) их не имеет — не виден в диалогах вообще. `funnel-collect.ts` при этом всё ещё
считает заявки внутри цикла `for (const agentId of listAgentIds())` через
`agentId === adminAgentId` — условие, которое перестало быть достижимым для
`REPORT_AGENT_ID` ровно из-за исключения, введённого в предыдущем change.

`getOwnPersonalChannel()` (`src/core/telegram/service.ts`) уже даёт `postId =
personalChannelMessage` — тот же пост, что использует трекинг просмотров (этап 5
воронки). Переиспользуется как «первый пост» для вставки ссылки.

Существующая конвенция интерактивных инструментов — `tg_funnel_report`,
`tg_channel_coverage_report`, оба зарегистрированы в корневом `index.ts` (реальная точка
входа OpenClaw-плагина) и сопровождаются `skills/<name>/SKILL.md`, описывающим агенту,
как и когда их вызывать. Эта задача следует тому же паттерну — не standalone-скрипт по
SSH (как `discovery-backfill.ts`), а chat-вызываемый tool: список целевых агентов
пользователь передаёт параметром вызова, а не выбирает скрипт из готового набора флагов.

## Goals / Non-Goals

**Goals:**
- Подсчёт заявок в приватный канал работает через аккаунт, у которого реально есть
  права (`REPORT_AGENT_ID`), без потери непрерывности истории `funnel.db`.
- Персональные, атрибутируемые по агенту инвайт-ссылки с подтверждением заявки,
  реестр ссылок в одном месте.
- Вставка ссылки в существующий закреплённый пост агента, без создания нового поста.
- Вызов — из чата, список агентов оператор указывает в момент вызова.

**Non-Goals:**
- Автогенерация ссылки при создании нового агента (`tg-agent-create`) — future work.
- Одобрение (`approve`) заявок, пришедших по новым ссылкам — существующий процесс
  (ручной или отдельный) не меняется этим change.
- Сохранение форматирования поста (entities — жирный текст и т. п.) при правке —
  `messages.EditMessage` в этой реализации переносит только текст.
- Ограничение прав вызова инструмента (кто из операторов может его вызывать) —
  не отличается от прав вызова любого другого tool плагина, отдельно не решается.

## Decisions

**Подсчёт заявок — отдельный шаг до цикла `listAgentIds()`, не внутри него.**
`collectFunnel` делает `tg.loadAccount(REPORT_AGENT_ID)` + `getPendingJoinRequests` один
раз в начале, до `for (const agentId of listAgentIds())`. Значение (`privateAbs`) —
локальная переменная, используется внутри цикла в точке `agentId === adminAgentId`
(agent1), без изменения того, под каким `agent_id` пишется снапшот. Альтернатива
(переключить снапшот на `agent_id = REPORT_AGENT_ID`) отклонена — потребовала бы
отдельной миграции истории дельт и создала бы строку для агента, которого большинство
отчётов намеренно не видят.

**Chat-tool, не standalone-скрипт.** Список целевых агентов не хранится в конфиге и не
берётся автоматически из `listAgentIds()` — вызывающий пользователь указывает его в
параметрах при обращении к скиллу. Это осознанное отличие от `discovery-backfill.ts`
(тот берёт `--agents` из CLI одноразового запуска оператором по SSH) — здесь вызов идёт
через Telegram-бота OpenClaw, параметры приходят от LLM-агента, разбирающего запрос
пользователя в чате.

**Параметры инвайт-ссылки — `requestNeeded: true`, без `usageLimit`, без
`expireDate`, без `subscriptionPricing`, `title = agentId`.** Все явно зафиксированы
пользователем. Отсутствие `subscriptionPricing` — единственный способ в MTProto API не
делать ссылку платной (объект передаётся, только если канал требует подписку; его
отсутствие ⇒ бесплатная ссылка). `title` — служебное поле Telegram (видно в списке
инвайт-ссылок канала в приложении), не часть текста поста.

**`exportChatInvite`/`updatePersonalChannelPostLink` — новые методы
`TelegramService`.** Соответствует существующей структуре файла: каждая MTProto-операция
— свой метод с резолвом peer по паттерну `findChannelPeer` → `getDialogs` fallback
(как `getPendingJoinRequests`/`leaveChannel`).

**Реестр ссылок — новый файл `private-invites.db` в `workspace-agent1`.** Отдельная
сущность (не снапшоты воронки, не реестр каналов), но тот же приём размещения
платформенных данных — один дом, независимо от того, чьей сессией они наполняются.
Схема: `agent_id TEXT PRIMARY KEY, invite_link TEXT NOT NULL, created_at INTEGER NOT
NULL` — `PRIMARY KEY(agent_id)` означает, что повторный вызов для уже обработанного
агента перезаписывает ссылку.

**Формат вставки — замена строк-ссылок, три строки новой ссылки в хвосте.** Регэксп
`^https?:\/\/\S+$` по построчному разбору текста поста: убирает строки, целиком
являющиеся URL (старые ссылки, в любом количестве), остаток текста обрезается от
хвостовых переносов, затем дописывается `\n<link>\n<link>\n<link>`. Формат зафиксирован
пользователем на примере реального поста.

**Три разных `agentId` в одном потоке — не путать.** У инструмента одновременно
участвуют: (1) `REPORT_AGENT_ID` — чьей MTProto-сессией создаётся ссылка
(`exportChatInvite`, требует прав администратора канала); (2) `FUNNEL_ADMIN_AGENT_ID` —
под каким ключом пишется строка в `private-invites.db` (владелец платформенных данных,
не меняется этим change); (3) сам целевой `agentId` из параметра вызова — чьей сессией
редактируется его собственный пост (`updatePersonalChannelPostLink`, чужой пост править
нельзя). Реализация обязана передавать каждый явно в нужном месте, не выводить один из
другого и не путать с тем, что в моменте загружено в `tg` (`tg.loadAccount(...)`
переключается три раза за один прогон по одному агенту: REPORT_AGENT_ID → сам агент →
следующий агент).

**Инструмент обрабатывает список агентов последовательно, ошибка одного не
прерывает остальных.** Соответствует существующему паттерну изоляции ошибок
(`collectFunnel`, `discovery-backfill.ts`) — агент без личного канала или с недоступной
сессией пропускается с пометкой в возвращаемом тексте, обработка продолжается.

## Risks / Trade-offs

- **[Риск] `updatePersonalChannelPostLink` заменяет текст поста через
  `messages.EditMessage` без переноса entities (форматирование).** → Не устраняется в
  этом change — если пост использует форматирование помимо обычных ссылок, оно будет
  потеряно при правке. Стоит проверить на реальном посте перед массовым вызовом.
- **[Риск] Агент без `personalChannelMessage`** (встречалось в логах, например agent6)
  **пропускается молча по вставке.** → Логируется как `reason: "no personal channel or
  post"`, обработка остальных агентов из списка продолжается; ссылка в
  `private_invite_links` для него всё равно создаётся и сохраняется.
- **[Trade-off] Ссылка без лимита использований и без срока действия.** По решению
  пользователя — проще эксплуатационно, но нет автоматической ротации, если ссылка
  когда-то потребует отзыва.

## Migration Plan

Новый файл `private-invites.db` создаётся идемпотентно при первом вызове инструмента.
Существующий `funnel.db` не меняет схему, продолжает расти под тем же
`agent_id = FUNNEL_ADMIN_AGENT_ID` — миграции нет.

Откат: перестать вызывать новый tool; `agentId === adminAgentId` внутри цикла
`funnel-collect.ts` можно вернуть на старое поведение без потери данных.
