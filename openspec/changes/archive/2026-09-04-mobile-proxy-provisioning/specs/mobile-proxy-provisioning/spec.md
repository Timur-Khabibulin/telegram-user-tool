## ADDED Requirements

### Requirement: Автоматический подбор рабочего мобильного прокси для списка агентов

Система SHALL по заданному списку `agentId` автоматически подбирать рабочий мобильный прокси
через API asocks.com: для каждого агента последовательно создавать кандидата (страна/регион/
город из входных параметров), проверять его реальным MTProto-подключением с сессией этого же
агента, и при неудаче удалять кандидата и создавать следующего — до конфигурируемого предела
попыток (`--max-attempts`, по умолчанию 5).

#### Scenario: Рабочий прокси найден с первой попытки

- **WHEN** первый созданный кандидат успешно проходит проверку подключения
- **THEN** его данные сохраняются в `tg-account.json` агента, попытки прекращаются, дальнейшие
  кандидаты не создаются

#### Scenario: Несколько кандидатов подряд не работают

- **WHEN** кандидат не проходит проверку подключения
- **THEN** он удаляется на стороне asocks, создаётся следующий кандидат, попытки продолжаются до
  успеха или до исчерпания `--max-attempts`

#### Scenario: Предел попыток исчерпан

- **WHEN** ни один из `--max-attempts` кандидатов не прошёл проверку
- **THEN** `tg-account.json` агента остаётся без изменений, в итоговом отчёте по этому агенту
  явно указано, что рабочий прокси не найден за N попыток

### Requirement: Конфигурация агента изменяется только при подтверждённом успехе

Проверка кандидата прокси SHALL происходить без записи на диск — `tg-account.json` агента
изменяется ровно один раз, при первом успешно прошедшем проверку кандидате, и ни разу иначе
(в т.ч. при полном исчерпании попыток или падении скрипта посреди цикла).

#### Scenario: Падение скрипта посреди цикла не портит конфиг

- **WHEN** скрипт прерывается (ошибка, ручная остановка) после создания и неудачной проверки
  нескольких кандидатов, но до нахождения рабочего
- **THEN** `tg-account.json` агента остаётся точно таким же, каким был до запуска скрипта

### Requirement: Повторный прогон переиспользует и очищает существующий прокси

Если `tg-account.json` агента уже содержит `proxy.name` (сохранённый предыдущим успешным
прогоном), система SHALL проверить этот существующий прокси первым (как кандидата №0) — при
успехе новый прокси не создаётся; при неудаче существующий прокси удаляется на asocks по имени
перед созданием новых кандидатов. Если `proxy.name` отсутствует (прокси не был создан этим
механизмом), шаг проверки/удаления старого прокси пропускается.

#### Scenario: Существующий прокси снова заработал

- **WHEN** у агента есть `proxy.name`, и он проходит проверку подключения
- **THEN** новые кандидаты не создаются, `tg-account.json` не изменяется, попытка засчитывается
  как успех

#### Scenario: Существующий прокси окончательно сломан

- **WHEN** у агента есть `proxy.name`, и он не проходит проверку
- **THEN** он удаляется на asocks по имени, дальше запускается обычный цикл создания новых
  кандидатов

#### Scenario: Прокси без сохранённого имени

- **WHEN** у агента есть `proxy`, но нет поля `name` (создан не этим механизмом)
- **THEN** шаг проверки/удаления старого прокси пропускается, цикл сразу начинается с создания
  кандидата №1

### Requirement: Итоговый отчёт по каждому агенту

По завершении обработки списка агентов система SHALL вывести отчёт: для каждого `agentId` —
либо успех с адресом рабочего прокси, либо явное указание, что рабочий прокси не найден за
`--max-attempts` попыток. Отчёт SHALL выводиться в stdout/консоль — интеграция с отчётами в
Saved Messages не требуется (разовый интерактивный запуск, не плановая задача).

#### Scenario: Отчёт по смешанным результатам

- **WHEN** из списка агентов часть получила рабочий прокси, а часть исчерпала попытки
- **THEN** итоговый вывод перечисляет оба исхода по каждому agentId отдельно, без прерывания
  обработки остальных агентов из списка при неудаче одного
