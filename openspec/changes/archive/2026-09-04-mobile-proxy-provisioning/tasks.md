## 1. Клиент asocks API: `src/core/proxy/asocks-client.ts`

- [x] 1.1 Сделать реальный запрос с ключом к `create-port`/справочным (`Dir`) эндпоинтам, чтобы
      зафиксировать точную форму `type_id`/`proxy_type_id`/`server_port_type_id` для «мобильный» —
      документация не даёт точных ID (design.md, Open Questions). Найдено и подтверждено реальным
      созданием+удалением порта: `country_code` — код страны ("US"), `state`/`city` — ИМЕНА
      строкой (не ID, несмотря на то что `Dir`-эндпоинты отдают числовые ID — используются только
      для резолва человекочитаемых значений в подтверждённые названия), `type_id` и
      `proxy_type_id` — оба обязательны, оба `3` = мобильный (`1` = residential, подтверждено по
      67 существующим портам аккаунта: `proxy_type_id:3` ⟷ `-mobile-` в логине, `1` ⟷ `-res-`).
      `server_port_type_id` в реальном ответе не встретился и не потребовался — судя по всему,
      устаревшее/опциональное поле схемы, не блокирует создание. Важная находка: новый порт
      создаётся на **порту 9999, не 443** — текущие 443 у агентов, видимо, ручная настройка, не
      дефолт API; сохранять в `tg-account.json` нужно `port`, который вернул API, не хардкодить.
      Отдельно подтверждено: свежесозданный мобильный кандидат тоже может словить тот же
      MTProto-блок (проверено `probe-literal.ts` с реальной сессией agent42) — ретрай-цикл
      подтверждённо необходим, не теоретическая предосторожность
- [x] 1.2 `resolveLocation(apiKey, country, state?, city?)` — резолв человекочитаемых значений
      через `/dir/countries,states,cities`; ловит опечатки явной ошибкой до `create-port`
- [x] 1.3 `createMobileProxy(apiKey, name, country, state?, city?, log)` — `POST

## 3. Override в `TelegramService`: `src/core/telegram/service.ts`

- [x] 3.1 `ensureClient()`/`requireClient()` принимают необязательный параметр override:
      `{ proxy?: ProxyConfig; maxAttempts?: number; connectTimeoutMs?: number }`. Интерфейс
      `EnsureClientOverride` вынесен на уровень модуля (экспортирован) — TS не позволяет
      объявлять `interface` внутри тела класса. Добавлен также новый ПУБЛИЧНЫЙ метод
      `verifyConnection(override)` — `ensureClient`/`requireClient` приватные, снаружи класса
      override был бы недостижим без отдельной публичной точки входа; не было явно расписано в
      design.md, обнаружено по ходу реализации
- [x] 3.2 При наличии override — использовать переданные прокси/бюджет вместо
      `account.proxy`/дефолтных `MAX_ATTEMPTS=3`/`CONNECT_TIMEOUT_MS=60_000`, не читая и не
      изменяя `AccountConfig`/`tg-account.json`. Дополнительно: при override клиент НЕ попадает
      в кэш `this.clients` (ни на чтение существующего, ни на запись нового) — иначе в
      gateway-режиме (один `TelegramService` на все агенты) тестовый клиент с
      прокси-кандидатом мог бы просочиться в обычный путь подключения того же агента
- [x] 3.3 Без override — поведение идентично сегодняшнему (регресс-проверка: типопроверка всего
      `service.ts`, где ~30 существующих вызовов `requireClient()` без аргументов, прошла чисто)
- [x] 3.4 Классификация ошибок (`ConnectTimeoutError`/`SessionRevokedError`/
      `MissingAccountConfigError`) работает одинаково для override и обычного пути — общий код,
      различается только переменная `proxy` (override.proxy ?? account.proxy)
