## Why

За последнюю неделю разобрали причину `Client not connected`/`ConnectTimeoutError` у 14 из ~45
агентов: мобильный прокси-провайдер (asocks.com) выдаёт sticky-сессии, часть которых блокирует
именно MTProto-хендшейк на уровне оператора/exit-узла (TCP и SOCKS5 поднимаются нормально,
Telegram-сервер обрывает соединение через ~350мс после `InvokeWithLayer` — подтверждено прямым
воспроизведением через реальный GramJS-клиент с debug-логом и кросс-тестом сессия↔прокси, см.
`deterministic-connection-errors/design.md`). Провайдер уже присылал «новые» сессии по запросу
в поддержку — сработало 1 из 14. Ручной цикл «попросить новую сессию → проверить руками через
временный скрипт → если не работает, попросить ещё» неприемлем на масштабе 45+ агентов — именно
так ушла неделя на разбор 14 агентов вручную.

У asocks.com есть API (`docs.asocks.com`) для создания и удаления мобильных прокси-портов с
таргетингом по стране/региону/городу — весь цикл «создать → проверить → если не работает,
удалить и создать снова» можно автоматизировать без участия человека на каждой итерации.

## What Changes

- Новый модуль `src/core/proxy/asocks-client.ts` — тонкая обёртка над API asocks.com:
  создание мобильного прокси-порта (страна/регион/город/имя), удаление порта по имени,
  резолв справочников (страна/штат/город → id, которых ждёт API).
- `src/core/telegram/service.ts`: `ensureClient()`/`requireClient()` принимают необязательный
  override — прокси и бюджет попыток/таймаута — не читая и не изменяя `tg-account.json`.
  Без override поведение не меняется (обычные 3×60с на реальном аккаунт-конфиге).
- `src/core/config.ts`: `ProxyConfig` получает новое поле `name?: string` — имя прокси-порта на
  стороне asocks, нужно для последующего удаления по имени при повторных прогонах.
- Новый скрипт `src/scripts/provision-mobile-proxy.ts` — реализует цикл (design.md) для списка
  `agentId`: create → verify (override, 3×20с) → delete-if-bad → repeat, до `--max-attempts`
  (по умолчанию 5). `tg-account.json` агента изменяется только при подтверждённом успехе.
- Новый Claude-skill `.claude/skills/mobile-proxy-provision/SKILL.md` — по образцу `vps`/
  `funnel-stats`: принимает список агентов, шаблон имени, страну/регион/город, опционально
  `--max-attempts`; подключается по ssh к VPS и запускает скрипт.
- API-ключ asocks — переменная окружения в `~/.openclaw/codex-auth/.env` на VPS (тот же файл,
  что уже хранит секреты LLM), не в `tg-account.json` (платформенный секрет, не per-agent).

## Capabilities

### New Capabilities

- `mobile-proxy-provisioning`: по списку агентов с проблемой подключения автоматически
  подбирается рабочий мобильный прокси через API asocks.com — создание, проверка реальным
  MTProto-хендшейком, удаление неудачных кандидатов, сохранение в `tg-account.json` только при
  подтверждённом успехе. Отчёт по каждому агенту — в консоль/чат.

### Modified Capabilities

- `telegram-connection-errors`: `ensureClient()` дополнительно поддерживает временный override
  прокси и бюджета попыток, не затрагивая персистентный `AccountConfig` — существующее поведение
  (без override) не меняется.

## Impact

- Код: `src/core/proxy/asocks-client.ts` (новый), `src/core/telegram/service.ts`,
  `src/core/config.ts`, `src/scripts/provision-mobile-proxy.ts` (новый),
  `.claude/skills/mobile-proxy-provision/SKILL.md` (новый).
- Данные: `ProxyConfig.name` — новое опциональное поле, обратная совместимость сохраняется
  (существующие `tg-account.json` без этого поля продолжают работать как раньше).
- Секреты: новая переменная окружения для API-ключа asocks на VPS.
- Вне скоупа (см. design.md Non-Goals): интеграция в скилл создания нового агента (упомянута
  пользователем как следующий шаг, отдельная задача); параллельная обработка списка агентов;
  ротация/очистка **уже существующих** (сегодняшних) 14 сломанных прокси, у которых в
  `tg-account.json` нет поля `name` — для них шаг «удалить старый по имени» просто не сработает
  (имени нет), прогон стартует сразу с создания нового кандидата.
