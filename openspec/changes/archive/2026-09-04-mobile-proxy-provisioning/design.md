## Context

`TelegramService.ensureClient()` (`src/core/telegram/service.ts`) сегодня — единственная точка
подключения, читает прокси из `AccountConfig`, загруженного `loadAccount(agentId)` из
`tg-account.json`, с фиксированным бюджетом `MAX_ATTEMPTS=3`, `CONNECT_TIMEOUT_MS=60_000`
(`deterministic-connection-errors`). Для верификации кандидата прокси этот бюджет избыточен:
блокировка MTProto ловится за ~350мс на попытку (воспроизведено многократно debug-логом GramJS),
а 3×60с на кандидата при `--max-attempts=5` дало бы до 15 минут на одного агента.

`ProxyConfig` (`src/core/config.ts`) — `{type, host, port, username?, password?}`, без понятия
«имя порта на стороне провайдера». asocks.com identifies порты по внутреннему `id`, но create/
delete API (см. proposal.md) позволяет искать/маркировать порты по `name` — если сохранять его
в конфиге, повторный прогон скрипта (например через полгода, когда сегодняшний рабочий прокси
тоже протухнет) сможет найти и удалить именно тот порт, который был выдан этому агенту, не
перебирая все порты аккаунта asocks вручную.

Диагностика этой недели (см. `deterministic-connection-errors/design.md` и переписку) дала два
готовых строительных блока:
- Классификация ошибок подключения (`ConnectTimeoutError`/`SessionRevokedError`/
  `MissingAccountConfigError`) — «проверка прокси» это не новый примитив, а вызов `ensureClient()`
  с новым прокси и разбор того, какой из трёх классов вернулся.
- Кросс-тест сессия↔прокси экспериментально подтвердил: блокировка живёт на стороне прокси-пути,
  не аккаунта — поэтому проверка кандидата безопасно делается сессией самого целевого агента (не
  нужен отдельный «тестовый» аккаунт).

## Goals / Non-Goals

**Goals:**
- Заменить ручной цикл «попросить у поддержки → проверить руками → повторить» автоматическим
  скриптом, вызываемым Claude-skill'ом по списку агентов.
- Гарантировать, что `tg-account.json` агента меняется только при подтверждённом успехе — при
  любом сбое (в т.ч. исчерпании попыток) конфиг агента остаётся ровно таким, каким был до запуска.
- Не плодить мусорные прокси-порты на стороне asocks — каждый неудачный кандидат удаляется сразу
  после проверки, известным именем.

**Non-Goals:**
- Параллельная обработка списка агентов — сознательно оставлена вне скоупа (см.
  `deterministic-connection-errors`-переписку: этот же VPS, 2 vCPU, уже показал деградацию под
  несколькими одновременными MTProto-хендшейками при разборе `funnel-collect.ts`; параллелить
  проверку кандидатов — отдельная работа, если последовательный прогon окажется неприемлемо
  медленным на практике).
- Очистка уже существующих 14 сломанных прокси-портов без поля `name` в `tg-account.json` —
  для них скрипт просто создаёт кандидатов с нуля, не пытаясь найти и удалить старый порт
  (сопоставить с ним нечем).
- Интеграция в скилл создания нового агента — упомянута пользователем как следующий шаг,
  отдельная задача не в этом change.
- Общий механизм повторных попыток/backoff поверх `MAX_ATTEMPTS` внутри одной проверки —
  переиспользуется существующая петля `ensureClient` с иным (меньшим) бюджетом, не новый механизм.

## Decisions

**`ensureClient()` получает необязательный override, а не отдельная копия логики подключения.**
Альтернатива — написать для скрипта свою функцию установления MTProto-соединения (как черновой
`probe-connect.ts`, которым пользовались для диагностики). Отклонено: дублирует ~70 строк логики
подключения (прокси, таймаут-гонка, `GramJsBridgeLogger`, обработка `TelegramClient`), которую уже
поддерживает `ensureClient`. Override — параметр вида `{ proxy?: ProxyConfig; maxAttempts?: number;
connectTimeoutMs?: number }`, при отсутствии — поведение идентично сегодняшнему.

**Проверка кандидата не пишет в `tg-account.json` до подтверждения.** Обсуждались два варианта
(писать на диск и тестировать «на месте», как делали руками при разборе, или держать кандидата в
памяти) — выбран вариант «в памяти»: конфиг агента ни на мгновение не указывает на непроверенный
прокси, нет промежуточного состояния на диске при падении скрипта посреди цикла.

**Бюджет проверки — 3 попытки × 20с, отдельно от 3×60с обычной работы `ensureClient`.**
Число попыток то же (3), различается только таймаут на попытку — блокировка проявляется быстро
(~350мс), 20с — с большим запасом, не 60с, рассчитанные на реальную перегрузку VPS в обычной
работе диспетчера (другой сценарий, другая причина таймаута).

**Удаление неудачного кандидата — по имени, которое скрипт сам присвоил при создании.** Не через
поиск/листинг портов asocks — имя уже известно из ответа `create-port`, лишний GET не нужен.

**Проверка старого прокси (если у агента уже есть `proxy.name` от предыдущего прогона) — как
кандидат №0 той же петли**, не отдельная ветка кода: если он вдруг снова заработал — экономим
попытку и обращение к asocks; если нет — удаляется тем же путём, что и любой другой неудачный
кандидат. Для сегодняшних 14 агентов (без `proxy.name`) этот шаг — no-op, петля стартует сразу с
создания кандидата №1.

**API-ключ asocks — в `~/.openclaw/codex-auth/.env`, не в `tg-account.json`.** Это секрет уровня
платформы (один аккаунт asocks на всех агентов), а не per-agent — по аналогии с тем, как уже
хранятся секреты LLM.

## Risks / Trade-offs

- **[Риск] Пул мобильных прокси asocks в конкретном городе/регионе может быть системно
  заблокирован целиком** (как было у альтернативного провайдера — 1 рабочая сессия из 14). →
  Митигация: `--max-attempts` настраивается пользователем; при исчерпании — явный отчёт «не
  нашли», решение о смене города/региона остаётся за оператором, не автоматизируется в этом
  change (см. Non-Goals — эскалация на другой город не реализуется сейчас).
- **[Trade-off] Последовательная обработка агентов может быть медленной** при большом списке и
  плохом пуле (до `--max-attempts` × ~60с на агента в худшем случае). → Осознанно принято ради
  простоты и безопасности для CPU VPS (см. Non-Goals).
- **[Риск] `create-port`/`delete-port` API asocks может иметь недокументированные rate limits
  или минимальную стоимость порта независимо от времени жизни.** → Не выяснено на этапе дизайна
  (документация не раскрывает лимиты/тарификацию в деталях) — уточняется в процессе реализации,
  первый прогон стоит делать на 1-2 агентах, не сразу на всех 14.

## Migration Plan

Миграции данных нет — `ProxyConfig.name?` опционально, существующие `tg-account.json` без этого
поля продолжают работать (проверка «есть ли имя» просто даёт `false`/пропуск шага очистки старого
прокси). `ensureClient()` без override ведёт себя как раньше — обратная совместимость для всех
существующих ~30 вызывающих мест в `service.ts`.

Откат: убрать override-параметр из `ensureClient`, удалить `asocks-client.ts`,
`provision-mobile-proxy.ts`, skill-файл — поле `name` в `ProxyConfig` можно оставить (не мешает,
просто перестаёт заполняться).

## Open Questions

- Точный формат полей `type_id`/`proxy_type_id`/`server_port_type_id` в теле `create-port` API
  asocks (документация показывает их как generic «object», не раскрывает точные ID/enum для
  «мобильный») — уточняется первым реальным запросом с ключом на этапе реализации, не блокирует
  дизайн.
- Тарификация/rate limits asocks на создание-удаление портов — не выяснено, см. Risks.
