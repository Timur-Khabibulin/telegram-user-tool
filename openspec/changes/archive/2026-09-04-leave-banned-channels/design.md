## Context

Полная аналитика фичи для человека — `docs/design/leave-banned-channels/leave-banned-channels-v1.md`
(источник истины по мотивации, потоку и решениям; здесь — техническая суть,
не дублируется подробно).

Текущее состояние: монитор (`src/skills/monitor.ts`) при не-flood ошибке ответа
вызывает `recordSendError(... 'reply_failed')` и пропускает канал (введено в
`funnel-tracking-stages`). `CHAT_WRITE_FORBIDDEN` отдельно не различается.
Реестр каналов — `discovered_channels` в `discovery.db` (ключ `canonical_link`,
`assigned_agent`, без статуса). Метода выхода из канала в `TelegramService` нет.

## Goals / Non-Goals

**Goals:**
- Реактивно (по факту ошибки записи) выводить агента из каналов, где он забанен
  на запись, и убирать их из его рабочих данных.
- Сохранить пометку бана в реестре для будущей логики переназначения.

**Non-Goals:**
- Логика переназначения освободившегося канала на другого агента.
- Проактивный опрос прав (`GetParticipant`) для «тихих» банов без попытки записи.
- Надёжная связь `chatId ↔ canonical_link` при join (резолв здесь best-effort,
  явная связь — Future Work).
- Реакция на прочие ошибки ответа (`flood_wait`, `peer_id_invalid`, generic
  `reply_failed`) — поведение не меняется.

## Decisions

**Триггер — только `CHAT_WRITE_FORBIDDEN`.** Монитор различает эту ошибку по
тексту/коду MTProto в ветке ошибки `sendReply` и кладёт `chatId` в
`banned_channels`. Прочие не-flood ошибки остаются в текущей ветке (`reply_failed`,
пропуск канала). Альтернатива (реагировать на любой `reply_failed`) отклонена —
большинство таких ошибок транзиентны, выход из канала по ним вреден.

**Очередь работ — отдельная per-agent таблица `banned_channels`, не `send_errors`.**
`send_errors` служит отчётности; использовать лог как очередь связало бы действие
с форматом отчёта. `banned_channels` имеет одну цель и самоочищается после
обработки. `INSERT OR IGNORE` по `chatId` (PK) — без дублей.

**Гигиена — скилл диспетчера, не standalone-скрипт.** Исполнение per-agent с уже
подключённым клиентом агента ложится на паттерн `monitor`/`dm-send`
(`(ctx) => SkillStatus`, регистрация в `dispatcher.ts`, планирование задачей).
Standalone-скрипт пришлось бы поднимать клиент каждого агента отдельно.

**Выход раньше удаления.** `syncChannels` добирает каналы из диалогов: удалить
данные, не выйдя, — следующий синк вернёт канал. Поэтому порядок: `leaveChannel`
→ чистка. Если выход не удался — чистку и пометку не делаем, строка очереди
остаётся (повтор на следующем прогоне).

**Пометка реестра — колонка `banned_at`, без отдельной таблицы.** `assigned_agent`
сохраняется (видно, кто забанен) — этого достаточно будущему переназначению,
чтобы исключить агента. Отдельная `channel_bans(link, agent)` отклонена как
избыточная.

**Резолв `chatId → canonical_link` — best-effort.** Через `GetFullChannel.username`
→ `normalizeChannelLink`. Если username нет (приватная группа-обсуждения) —
шаги выход/чистка/самоочистка выполняются, пропускается только пометка реестра.

**Что удаляется / что нет.** Удаляются рабочие данные агента по `chatId`:
`channels`, `channel_visits`, `dm_candidates` (`sourceChatId`) в `tg-channels.db`;
`replies`, `group_threads`, `group_thread_agent_msgs` в `tg-replies.db`; затем
`banned_channels`. НЕ удаляются: `send_errors` (история для отчёта),
`dm_threads` (активные личные диалоги — другой peer, бан на запись в канал на
них не влияет).

## Risks / Trade-offs

- **[Риск] `CHAT_WRITE_FORBIDDEN` не всегда вечен** (бывает при временных
  ограничениях, slow-mode). → Митигация: принято осознанно реагировать выходом в
  любом случае (решение заказчика); повторное вступление в публичный канал
  возможно. Историю данных потеряем — приемлемо для забаненного канала.
- **[Риск] Резолв username не удался → канал выведен, но в реестре не помечен.**
  → Митигация: выход/чистка всё равно происходят (главная цель достигнута);
  пометка — best-effort. Закрывается явной связью `chatId↔link` (Future Work).
- **[Trade-off] Осиротевшие `send_errors` без строки `channels`.** Отчёт-воронка
  (`problemChannels`) делает LEFT JOIN с `channels.title` → после удаления канал
  показывается по `chatId`, а не по имени. Принято: не ломается, история
  сохранена.
- **[Риск] Удаление данных необратимо.** → Митигация: срабатывает строго по
  подтверждённому `CHAT_WRITE_FORBIDDEN`, не по предположению.

## Migration Plan

Аддитивные миграции, без переноса данных: `banned_channels` создаётся идемпотентно
(`CREATE TABLE IF NOT EXISTS`) при первой записи; колонка `banned_at` добавляется
в `discovered_channels` через `ALTER TABLE` (как уже сделано для `added_at`).
Существующие забаненные каналы (до выкатки) попадут в очередь при следующей
неудачной попытке записи монитора — отдельный бэкафилл не нужен.

Откат: новые таблица/колонка остаются неиспользуемыми; скилл можно снять с
планирования в диспетчере.
