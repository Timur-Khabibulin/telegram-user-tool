## Context

Период задачи задаётся cron-выражением + `tz` в `tasks.db` каждого агента
(`src/core/db/tasks.ts`), независимо по агентам — это уже не тронуто. Но
дефолтные значения `schedule`, которые скилл `scheduler-control` подставляет,
когда пользователь их не указал, сейчас — статичная таблица в
`skills/scheduler-control/SKILL.md` (Шаг 3-A), **одинаковая для всех
агентов**. Heartbeat-таймер (`tg-agent@.timer`, `deploy/systemd/tg-agent@.timer`,
`OnCalendar=*:0/10`) — это granularity планирования (тик 10 мин), не период
задачи; он не решает проблему синхронных дефолтов.

`agentId` не последователен и не пригоден как ключ распределения (в проде уже
есть `agent1..agent8` вперемешку с опечаткой `ageng3`; на 150+ агентах это
станет только хуже).

## Goals / Non-Goals

**Goals:**
- Дефолтная фаза старта периодической задачи (`monitor`, `monitor-v2`,
  `join-queue`, `account-warmup`, `dm-replies`) SHALL распределяться между
  агентами гарантированно равномерно (round-robin), не статистически.
- Явно заданный пользователем `schedule` не пересчитывается — round-robin
  работает только как источник дефолта.
- Период задачи не меняется — меняется только фаза (минута/час старта внутри
  периода).
- Механизм не должен требовать нового хранилища сверх уже существующего
  `tasks.db` каждого агента.

**Non-Goals:**
- Календарные суточные задачи (`dm-send` 14:00, `leave-banned` 05:00) — вне
  охвата этой итерации; остаются с фиксированным временем.
- Изменение тика heartbeat-таймера (10 мин) — не меняется.
- Перебалансировка фазы у уже существующих задач при удалении/отключении
  других агентов — не делается (см. Риски).

## Decisions

### 1. Round-robin по числу уже существующих агентов, не хэш

Рассматривались: (A) хэш `agentId` → слот, (B) сканирование `tasks.db` всех
агентов в поисках свободного слота, (C) отдельный реестр `agentId → offset`.

Выбор — вариант, близкий к (B), но без поиска «дыр»: просто **счётчик**
агентов, уже имеющих включённую задачу данного `type`, по модулю числа слотов.

- (A) хэш отклонён: даёт только статистическую, не гарантированную
  равномерность (проверено эмпирически — на 150 агентах разброс 5..14 при
  среднем 8.3 на слот). Требование — гарантия, не статистика.
- (C) отдельный реестр отклонён: дублирует факт, который уже есть в
  `tasks.db` каждого агента («один факт — один дом», `agent-playbook.md`).
- Выбранный вариант использует только существующие источники данных
  (`listAgentIds()` в `src/core/config.ts` + `listTasks(agentId)` в
  `src/core/db/tasks.ts`), не требует нового хранилища и даёт точную гарантию:
  после каждого полного круга (кратно числу слотов) каждый слот использован
  ровно одинаковое число раз; в любой момент разброс между слотами ≤ 1 агент.

### 2. Формула

```
N_SLOTS(type) = период(type) в минутах / TICK_MINUTES   // TICK_MINUTES = 10
slot          = countAgentsWithEnabledTask(type) % N_SLOTS(type)
offsetMin     = slot * TICK_MINUTES
```

Генерация cron по типу периода:

- **Период кратен часу** (`monitor`/`monitor-v2`/`join-queue` — 180 мин;
  `account-warmup` — 300 мин):
  ```
  stepHours  = период / 60
  hourOffset = offsetMin ÷ 60          // 0 .. stepHours-1
  minute     = offsetMin % 60
  cron       = "{minute} {hourOffset}-23/{stepHours} * * *"
  ```
- **Период короче часа** (`dm-replies` — 30 мин):
  ```
  minute = offsetMin                    // 0 .. период-TICK_MINUTES
  cron   = "{minute}-59/{период} * * * *"
  ```

Оба варианта проверены через `cron-parser` (та же библиотека, что уже в
`tasks.ts`) — период сохраняется точно, различается только фаза.

### 3. Таблица периодов переезжает в код

Сейчас cron-строки и их период существуют только как markdown-таблица в
`SKILL.md` — не машиночитаемо, не может участвовать в вычислении. Периоды по
`TaskType` (в минутах) и `tz` по умолчанию переезжают в `src/core/db/tasks.ts`
(или `scheduler-control.ts`) как единственный источник истины; `SKILL.md`
перестаёт хранить таблицу дефолтов.

### 4. `schedule`/`tz` в `createOrUpdateTask` становятся опциональными

`src/core/scheduler-control.ts`: если `schedule` не передан — вычисляется по
формуле выше и возвращается в `UpsertTaskResult` (уже возвращает `schedule` —
поле не новое, просто теперь оно может быть вычисленным, а не переданным).
Скилл показывает пользователю фактически применённый `schedule`.

### 5. `TICK_MINUTES` — новая константа в коде

Тик сейчас существует только в `deploy/systemd/tg-agent@.timer`
(`OnCalendar=*:0/10`), в TS-коде не отражён. Заводится константа
`DISPATCHER_TICK_MINUTES = 10` в `src/core/config.ts` с комментарием,
явно указывающим на systemd-файл как на второй конец связи (два места должны
меняться вместе — задокументировать, не пытаться устранить дублирование
технически, т.к. systemd-юнит не генерируется из TS-кода).

## Risks / Trade-offs

- **[Риск] Разные `type` у одного агента получают независимо посчитанные
  слоты** → возможно, `monitor` и `dm-replies` одного агента внутри своего
  периода стартуют не в одну и ту же минуту относительно границы часа. Это
  не проблема: цель — не совпадать с ДРУГИМИ агентами, а не выравнивать типы
  задач внутри одного агента (они и так выполняются последовательно в одном
  диспетчере).
- **[Риск] `account-warmup` (300 мин) не делится нацело на 24ч** →
  `hourOffset-23/5` даёт укороченный последний интервал раз в сутки. Не новая
  проблема — уже существует в текущем дефолте (`0 */5 * * *`: 0,5,10,15,20,
  разрыв 4ч до полуночи). Наследуется, не создаётся заново.
- **[Риск] Отключение/удаление агента не освобождает его слот задним числом**
  → округление слотов может со временем немного просесть в сторону начала
  диапазона. Смягчение: не требуется — переисчисление задним числом усложнит
  систему без практической пользы при текущем масштабе (≤ 150 агентов).
- **[Риск] `TICK_MINUTES` дублируется (TS-константа и systemd `OnCalendar`)**
  → рассинхронизация при ручном изменении одного без другого. Смягчение:
  комментарий у константы, явно указывающий на связанный файл (см. Decision 5).

## Migration Plan

- Изменение затрагивает только **вычисление дефолта** при создании НОВОЙ
  задачи без явного `schedule` — существующие строки `tasks.db` не трогаются,
  откат = не использовать новый путь (передавать `schedule` явно, как
  сейчас), данные не мигрируют.
- Деплой обычный (код), без изменений systemd-юнитов и без изменения схемы
  `tasks.db`.

## Open Questions

- Распространять ли аналогичный round-robin на суточные календарные задачи
  (`dm-send`, `leave-banned`)? Оставлено вне охвата — решить отдельным
  change, если синхронный суточный всплеск станет заметной проблемой.
