## Why

Дефолтное расписание одного `type` задачи сейчас одинаковое для всех агентов
(`skills/scheduler-control/SKILL.md`, таблица дефолтов) — все агенты стартуют
`monitor`/`dm-replies`/`account-warmup` в одну и ту же минуту каждый период.
При росте числа агентов (сейчас 8, платформа рассчитана на рост) это даёт
синхронные всплески нагрузки на Telegram MTProto и LLM вместо равномерного
потока. Нужен механизм, который при создании задачи агенту без явно
указанного `schedule` сам выбирает фазу старта так, чтобы агенты были
гарантированно равномерно распределены по доступным стартовым минутам
периода — не статистически (хэш даёт разброс), а точным round-robin.

## What Changes

- `createOrUpdateTask` (`src/core/scheduler-control.ts`) принимает `schedule`
  опциональным: если не передан — вычисляет его сам по формуле round-robin
  (см. design.md), вместо того чтобы дефолт брал сам скилл из markdown-таблицы.
- Новая функция подсчёта: сколько уже существующих агентов имеют включённую
  задачу данного `type` (источник — `listAgentIds()` + `tasks.db` каждого
  агента, без нового реестра).
- Таблица периодов и базового времени по `TaskType` переезжает из
  `skills/scheduler-control/SKILL.md` (markdown) в код (`src/core/db/tasks.ts`
  или `scheduler-control.ts`) — единый источник истины вместо дублирования.
- `skills/scheduler-control/SKILL.md` Шаг 3-A: вместо таблицы дефолтов —
  вызов инструмента без `schedule`, показать пользователю фактически
  применённый `schedule` из ответа.
- Не меняется: явно заданный пользователем `schedule` используется как есть,
  без пересчёта (round-robin — только для дефолта).
- Вне охвата (осознанно): календарные суточные задачи (`dm-send`,
  `leave-banned`) остаются с фиксированным временем — не размазываются по
  round-robin в этой итерации (одиночный всплеск раз в сутки менее критичен).

## Capabilities

### Modified Capabilities
- `task-scheduler`: требование «Управление расписанием из Telegram» дополняется
  правилом равномерного распределения дефолтной фазы старта между агентами
  (round-robin по количеству уже созданных агентов с этой задачей), когда
  `schedule` не передан явно.

## Impact

- `src/core/scheduler-control.ts` — сигнатура `createOrUpdateTask`, вычисление
  дефолтного `schedule`.
- `src/core/db/tasks.ts` — таблица периодов/базового времени по `TaskType`,
  функция подсчёта агентов с включённой задачей типа.
- `src/core/config.ts` — константа тика диспетчера (сейчас захардкожена только
  в `deploy/systemd/tg-agent@.timer`), используется формулой смещения.
- `skills/scheduler-control/SKILL.md` — Шаг 3-A (убрать таблицу дефолтов).
- Существующие агенты и их уже созданные задачи не трогаются — механизм
  применяется только при создании новой задачи без явного `schedule`.
