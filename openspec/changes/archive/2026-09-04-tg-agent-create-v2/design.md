## Context

Это вторая версия скилла создания агента — новый скилл `skills/tg-agent-create-v2/`, отдельный
от `skills/tg-agent-create/` (v1), который остаётся включённым и без изменений. `tg-agent-
create-proxy-provisioning` оставило Шаг создания структуры агента в исходном виде:
`openclaw agents add`, вычисление и запись биндинга, добавление `telegram_user_id` в
`channels.telegram.accounts.agentsBot.allowFrom`, создание `~/.openclaw/agents/<agentName>/
agent/` с копией `auth-profiles.json`/`models.json`, и создание `AGENTS.md`/`HEARTBEAT.md`/
`USER.md`/`BOOTSTRAP.md`/`IDENTITY.md`/`TOOLS.md`/`MEMORY.md` в workspace.

Explore-сессия (архитектурный разбор) установила фактическое разделение платформы на два
независимых контура:

- **Разговорный контур OpenClaw** — `agents.list` + `bindings` + плагин (`index.ts`) + markdown
  скиллы в `~/.openclaw/workspace/skills/`. Используется только `main` (административный агент,
  которым управляет человек) для one-off задач: создание/реавторизация агента, починка прокси.
- **Операционный контур** — systemd-таймер `tg-agent@<id>.timer` → `dispatcher.ts` →
  `src/skills/*.ts` напрямую → `TelegramService` (GramJS) и `src/llm/client.ts` напрямую. Ноль
  обращений к OpenClaw-платформе (подтверждено grep по всему `src/`).

Регистрация персона-агента как сущности первого контура (`agents.list`, `agentDir`, биндинг на
`agentsBot`) не потребляется ничем во втором контуре:
- `listAgentIds()` (`src/core/config.ts`) перечисляет агентов по каталогам `workspace-<agentId>`
  на диске, не по `agents.list`.
- `tg-agent@.service` (`deploy/systemd/tg-agent@.service`) вызывает
  `tsx src/scripts/dispatcher.ts --agent %i` напрямую — без единого обращения к `openclaw` CLI.
- `createLlmClient()` (`src/llm/client.ts`) читает один общий `~/.openclaw/codex-auth/auth.json`
  на всех агентов — `agentDir`/`auth-profiles.json`/`models.json` конкретного агента не
  открываются никогда.
- Health-monitor гейтвея (`node_modules/openclaw/docs/gateway/health.md`) работает на уровне
  канала/аккаунта, не per-agent.
- `openclaw cron list --json` на VPS вернул `{"jobs": [], "total": 0}` — механизм, который
  теоретически мог бы запустить per-agent разговорную сессию в обход биндингов
  (`openclaw cron add --agent <id> --session isolated`, как делает легаси-скилл
  `tg-cron-setup`), нигде фактически не используется.
- Канал `agentsBot` уже забанен.

## Goals / Non-Goals

**Goals:**
- Создание агента перестаёт регистрировать его как разговорную сущность OpenClaw — только
  файловая структура, реально потребляемая операционным контуром.
- `verify-agent.sh` проверяет только то, что реально создаётся после этого change.
- Сократить число шагов/вызовов в создании агента ещё раз (после `tg-agent-create-proxy-
  provisioning`) — meньше bash-вызовов, меньше токенов.

**Non-Goals:**
- Удаление канала `agentsBot` из `openclaw.json` — административное действие вне этого change.
- Ретроактивная чистка уже существующих ~45 агентов из `agents.list`/`bindings`/`allowFrom` —
  не требуется для работы платформы (мёртвая конфигурация, не мешает), отдельная задача при
  желании.
- Отключение или удаление v1 (`skills/tg-agent-create/`) — остаётся включённым, обе версии
  доступны одновременно (см. Decisions).
- Изменение `tg-agent-reauth` — не обращается к `agents.list`/биндингам, не затронут.
- Ревизия легаси root-скиллов (`dm-send`, `account-warmup`, `telegram-group-monitor`,
  `*-cron-setup` и т.п.) — их судьба не часть этого change.
- Переписывание флоу из `tg-agent-create-proxy-provisioning` — выбор локации прокси (готовые
  значения/пошаговый подбор), цикл create→probeProxy→delete, `countryCode/state/city` в
  `tg-account.json`, авторизация через `tg_auth_send_code`/`tg_auth_sign_in`. В `tg-agent-
  create-v2` эти шаги переносятся из v1 без изменения поведения (копия с адаптацией нумерации) —
  меняются только шаг регистрации/структуры (текущие Шаг 2 и Шаг 4 v1) и `verify-agent.sh`.

## Decisions

**Новый скилл `tg-agent-create-v2`, а не правка v1 на месте.** Альтернатива — отредактировать
`skills/tg-agent-create/SKILL.md` in-place (как в `tg-agent-create-proxy-provisioning`).
Отклонено: это более рискованное изменение поведения (убирается целый пласт действий —
регистрация в OpenClaw), и откат к прежнему поведению должен быть мгновенным (просто вызвать
другой скилл), а не через git history. Отдельная папка `skills/tg-agent-create-v2/` со своим
`SKILL.md` и `scripts/verify-agent.sh` (копия v1 с правками) даёт это бесплатно — обе версии
существуют параллельно.

**v1 остаётся включённым в `openclaw.json`, не отключается.** Обсуждались варианты — отключить
v1 (`skills.entries["tg-agent-create"].enabled = false`) или удалить его совсем. Выбрано
«оставить как есть»: минимальный риск на переходный период (пока v2 не проверена на реальном
создании агента, см. tasks §4), явный и простой rollback (просто продолжить звать v1), не
требует отдельного администативного решения прямо сейчас. Выбор версии при вызове — на
усмотрение того, кто создаёт агента.

**Создание структуры — `mkdir -p`, отдельный скрипт упраздняется.** После удаления регистрации
в OpenClaw единственное действие, которое остаётся — создание каталога `workspace-<agentName>/`.
Отдельный bash-скрипт (`create-agent-scaffold.sh`) для одной команды избыточен — альтернатива
(оставить скрипт-обёртку) отклонена: не даёт пользы при таком объёме логики, лишний файл
поддержки. Команда выполняется прямо в шаге SKILL.md.

**`tg-account.json` и `SOUL.md` создаются как раньше (v1), без изменений.** Это не относится к
регистрации в OpenClaw — оба файла читаются операционным контуром напрямую по пути
(`loadAccountConfig`, `soulPath`), их создание не пересматривается в этом change.

**`verify-agent.sh` — убрать неактуальные проверки, а не переписать с нуля.** Правки точечные:
удалить блоки A1/A2/A3/B5, оставить B1/B2, добавить проверку каталога workspace. Полная
переработка скрипта не нужна — большая часть структуры (сбор `results[]`, вывод) переиспользуется
как есть.

**`agentsBot`/`allowFrom`/биндинг не трогаются в `openclaw.json` для уже существующих агентов.**
Обсуждались варианты — вычистить ретроактивно все ~45 записей или оставить как есть. Выбрано
«оставить»: мёртвая конфигурация не мешает работе (ничто её не читает), а ретроактивная чистка —
необратимая правка живого конфига без прямой пользы, риск несоразмерен выгоде. Если понадобится
— отдельная задача с явным подтверждением.

## Risks / Trade-offs

- **[Риск] Если когда-либо в будущем понадобится разговорная OpenClaw-сессия для персона-агента**
  (например, ручная отладка через его собственный Telegram-аккаунт) — придётся регистрировать
  агента задним числом (`openclaw agents add`), это несложно, но не бесплатно. → Осознанно
  принято: сегодня такой потребности не подтверждено (см. Context — cron пуст, весь контур
  проверен), а откат простой (см. Migration Plan).
- **[Trade-off] `verify-agent.sh` после правки проверяет меньше** (только 3 пункта вместо 6) —
  меньше диагностики при разборе проблем создания. → Приемлемо: убираемые проверки проверяли
  именно то, что этот change перестаёт создавать, оставлять их означало бы всегда показывать FAIL.

## Migration Plan

Миграции данных нет — изменения затрагивают только процесс создания **новых** агентов, не
данные уже существующих. Существующие агенты (с их `agents.list`/`bindings`/`allowFrom`
записями) продолжают работать как раньше — их никто не трогает. v1 не удаляется и не
отключается, оба скилла сосуществуют.

Откат: тривиальный — просто продолжать вызывать `tg-agent-create` (v1) вместо `tg-agent-
create-v2`. Ничего не нужно восстанавливать из git history, оба варианта уже на диске.
