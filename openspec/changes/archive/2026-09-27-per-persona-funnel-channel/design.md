## Context

Приватный канал воронки задан единой константой `FUNNEL_PRIVATE_CHANNEL_ID`
(`src/core/config.ts`), общей на всю платформу. Все инвайт-ссылки агентов ведут в этот
один канал, а сбор воронки (`collectFunnel`) читает заявки по одному `privateChannelId`.
При нескольких персонах требуется отдельный приватный канал на персону.

Ключевые действующие лица (не меняются по сути):
- `REPORT_AGENT_ID` (agent27) — админ канала(ов), создаёт ссылки и читает заявки.
- `FUNNEL_ADMIN_AGENT_ID` (agent1) — владелец платформенных БД (`funnel.db`,
  `private-invites.db`); одна БД на платформу, строки по `agentId`.
- Персона агента — поле `persona` в `tg-account.json`, резолвится `buildPersonaIndex()`.

Потребители константы: `apply-persona.ts:55`, `private-invite-links/run.ts:123`,
`funnel-collect.ts` (`collectFunnel`), `index.ts:1170`, `funnel-tracker.ts:41`.

## Goals / Non-Goals

**Goals:**
- Приватный канал воронки резолвится per-persona из `profile_data.json`
  (`funnelPrivateChannelId`), а не из константы.
- Создание ссылок и сбор заявок используют канал персоны агента.
- Персона без канала — подсчёт заявок пропускается без ошибки.
- Итог заявок в отчёте разнесён по персонам.
- Константа `FUNNEL_PRIVATE_CHANNEL_ID` и аргумент `--private-channel` удалены.

**Non-Goals:**
- Не вводить отдельный админ-аккаунт на персону (Модель B отклонена). `REPORT_AGENT_ID`
  остаётся единым админом всех каналов.
- Не менять хранение `funnel.db`/`private-invites.db` — остаются платформенными, ключ
  `agentId`.
- Не автоматизировать создание самих приватных каналов и выдачу прав admin agent27 —
  это операционный шаг (как и раньше id заводился вручную).
- Не переносить существующие ссылки между каналами — ссылка создаётся один раз в канал,
  актуальный на момент создания.

## Decisions

### 1. Модель A: единый админ, меняется только id канала

`REPORT_AGENT_ID` — админ всех персональных каналов. Меняется только целевой `peer`
запроса. Альтернатива (Модель B, свой админ на персону) отклонена: требует поле
`funnelAdminAgentId` в шаблоне, загрузку разных сессий в сборе и создании ссылок,
ломает «один `loadAccount(REPORT_AGENT_ID)` на весь цикл». Для планируемого числа персон
не оправдано.

### 2. Хранение id — поле `funnelPrivateChannelId` в `profile_data.json`

Персона — естественный владелец своего канала; `profile_data.json` уже загружается
per-persona. Поле опциональное (`ProfileData.funnelPrivateChannelId?: string`), формат —
marked peer id `-100…`. Имя выбрано отлично от `channelName` (публичный канал персоны),
чтобы не путать публичный и приватный каналы.

### 3. Лёгкий ридер вместо `loadPersonaTemplate`

`loadPersonaTemplate(persona, requireChannel)` требует фото/пост и падает при их
отсутствии — тяжело и хрупко ради одного id. Ввести лёгкую функцию (например
`readPersonaFunnelChannelId(persona): string | null`), читающую только
`profile_data.json`. Возвращает `null` при отсутствии файла/поля — вызывающий трактует
как «канал не задан».

### 4. Резолвинг `agentId → persona → funnelPrivateChannelId`

`buildPersonaIndex()` даёт `agentId → persona`. Поверх — построить один раз на прогон
карту `persona → funnelPrivateChannelId` (лёгкий ридер, по одному чтению на персону, не
на агента). Резолвинг канала агента = двойной lookup. Отсутствие персоны в карте или
`null` id → «канал не задан» для этого агента.

### 5. `collectFunnel` — канал per-agent, итог per-persona

Сейчас `opts.privateChannelId` — одно значение; цикл ссылок бьёт по нему. Изменения:
- Убрать `privateChannelId` из `CollectOptions`; строить карту `persona → channelId`
  внутри (или принимать готовую карту).
- Для каждого агента со ссылкой: `channel = map[personaOf(agent)]`; если нет — пропуск
  заявок (значение NULL, запрос не делается).
- `getPendingJoinRequests(channel, {link})` вызывается с каналом персоны агента.
- Итог: вместо единого `privateRequestsAbs`/`Delta` — агрегаты по персоне. Тип
  `FunnelResult` получает разрез по персонам (например
  `privateRequestsByPersona: Map<persona, {abs, delta, note?}>`); поля per-agent
  (`privateRequestsAbs/Delta` в `AgentFunnelRow`) сохраняются как есть.
- Блок «неактивные агенты со ссылкой» (`inactiveLinkedAgents`) тоже резолвит канал по
  персоне и вливается в персонные итоги.

### 6. `funnel-report` — итог по персонам

`renderFunnel` и `buildFunnelCsv` выводят итог заявок отдельным значением на персону
(сумма по агентам персоны) вместо единой платформенной суммы. Ячейка агента
(«дельта (абсолют)») не меняется; прочерк — если у агента нет ссылки ИЛИ у его персоны
нет канала.

### 7. Удаление константы и `--private-channel`

`FUNNEL_PRIVATE_CHANNEL_ID` удаляется из `config.ts`; все импортёры переводятся на
резолвинг. Аргумент `--private-channel` в `funnel-tracker.ts` теряет смысл (канал теперь
per-persona) и удаляется. Комментарий в `deploy/systemd/tg-funnel-tracker.service` и
строку в `docs/configuration.md` — обновить.

## Risks / Trade-offs

- **Лимит Telegram на число каналов, где agent27 админ** → при большом числе персон
  agent27 может упереться в лимит. Митигация: Модель A рассчитана на умеренное число
  персон; при росте — вернуться к Модели B (отдельный админ на персону). Зафиксировать
  как известное ограничение.
- **Миграция существующего канала** → если не вписать `-1003698044714` в
  `profile_data.json` персоны maria до/сразу после выката, её заявки перестанут
  считаться (канал не задан → пропуск). Митигация: миграционный шаг в tasks + проверка
  после деплоя.
- **Неверный peer для чужой ссылки** → если карта персон соберётся неверно, запрос уйдёт
  с не тем каналом и вернёт не те заявки. Митигация: резолвинг строго через
  `persona` агента; отсутствие соответствия → пропуск (NULL), а не запрос по дефолтному
  каналу.
- **Рассинхрон `profile_data.json` (сервер) и кода** → поле читается в рантайме с
  сервера; забытое поле у персоны молча отключает заявки этой персоны. Митигация: пометка
  в отчёте («канал персоны не задан») делает пробел видимым.

## Migration Plan

1. Выкатить код (поле опционально — отсутствие не ломает загрузку шаблонов).
2. На сервере вписать `funnelPrivateChannelId` в `profile_data.json` каждой персоны:
   - maria → `-1003698044714` (существующий канал, сохранить непрерывность);
   - остальные персоны → их собственные приватные каналы (оператор создаёт канал,
     добавляет agent27 админом с правом `invite_users`, вписывает id).
3. Проверить: следующий прогон `funnel-tracker` показывает заявки по персонам, у maria —
   прежнее значение.
4. Откат: вернуть код с константой; данные (`profile_data.json`) можно оставить — старый
   код просто игнорирует новое поле.
