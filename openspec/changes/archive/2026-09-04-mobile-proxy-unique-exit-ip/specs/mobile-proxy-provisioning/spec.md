## MODIFIED Requirements

### Requirement: Автоматический подбор рабочего мобильного прокси для списка агентов

Система SHALL по заданному списку `agentId` автоматически подбирать рабочий мобильный прокси из
существующего инвентаря asocks.com (`GET /proxy/search`, фильтр только `country`+`types=mobile`,
без `state`/`city`): для каждого агента последовательно брать из полученного списка следующего
ещё не использованного (ни одним другим агентом, ни в рамках уже обработанных агентов этого же
прогона) кандидата, проверять его реальным MTProto-подключением с сессией этого же агента, и при
неудаче переходить к следующему кандидату из того же списка — до конфигурируемого предела попыток
(`--max-attempts`, по умолчанию 5) либо до исчерпания списка. Кандидаты SHALL NOT создаваться или
удаляться на стороне asocks — это существующий ресурс аккаунта, не новый.

#### Scenario: Рабочий прокси найден с первой попытки

- **WHEN** первый взятый из списка кандидат успешно проходит проверку подключения
- **THEN** его данные сохраняются в `tg-account.json` агента, дальнейшие кандидаты для этого
  агента не берутся

#### Scenario: Несколько кандидатов подряд не работают

- **WHEN** кандидат не проходит проверку подключения
- **THEN** система берёт следующего ещё не использованного кандидата из того же списка,
  на asocks ничего не удаляется, попытки продолжаются до успеха, исчерпания `--max-attempts`
  либо исчерпания списка кандидатов

#### Scenario: Предел попыток исчерпан

- **WHEN** ни один из `--max-attempts` кандидатов не прошёл проверку
- **THEN** `tg-account.json` агента остаётся без изменений, в итоговом отчёте по этому агенту
  явно указано, что рабочий прокси не найден за N попыток

#### Scenario: Пул кандидатов страны исчерпан

- **WHEN** в списке, полученном от `/proxy/search` для заданной страны, не осталось ни одного
  ещё не использованного кандидата (все уже закреплены за другими агентами)
- **THEN** система явно сообщает, что свободных прокси для этой страны не осталось, не выдаёт
  уже занятый другим агентом логин, `tg-account.json` агента не изменяется

### Requirement: Конфигурация агента изменяется только при подтверждённом успехе

Проверка кандидата прокси SHALL происходить без записи на диск — `tg-account.json` агента
изменяется ровно один раз, при первом успешно прошедшем проверку кандидате, и ни разу иначе
(в т.ч. при полном исчерпании попыток, исчерпании пула или падении скрипта посреди цикла).
Сохраняемые поля прокси — `type/host/port/username/password` и `countryCode` (страна, по которой
запрашивался `/proxy/search`); `state`/`city`/`name` SHALL NOT заполняться для новых подборов
(эндпоинт-источник их не предоставляет).

#### Scenario: Падение скрипта посреди цикла не портит конфиг

- **WHEN** скрипт прерывается (ошибка, ручная остановка) после нескольких неудачных проверок, но
  до нахождения рабочего кандидата
- **THEN** `tg-account.json` агента остаётся точно таким же, каким был до запуска скрипта

### Requirement: Итоговый отчёт по каждому агенту

По завершении обработки списка агентов система SHALL вывести отчёт: для каждого `agentId` —
либо успех с адресом рабочего прокси (`host:port`), либо явное указание, что рабочий прокси не
найден (за `--max-attempts` попыток либо из-за исчерпания пула страны). Отчёт SHALL выводиться в
stdout/консоль.

#### Scenario: Отчёт по смешанным результатам

- **WHEN** из списка агентов часть получила рабочий прокси, а часть — нет
- **THEN** итоговый вывод перечисляет оба исхода по каждому `agentId` отдельно, без прерывания
  обработки остальных агентов из списка при неудаче одного

## ADDED Requirements

### Requirement: Уникальность прокси между агентами

Перед выдачей кандидата агенту система SHALL исключить из рассмотрения логины, уже
зафиксированные в `proxy.username` любого другого агента (`tg-account.json` во всех
`workspace-<agentId>/`), а также логины, уже выданные другим агентам в рамках текущего запуска
скрипта на список из нескольких `agentId`. Сверка SHALL производиться по строковому значению
логина, без дополнительного сетевого обращения к внешнему сервису для проверки IP.

#### Scenario: Кандидат уже используется другим агентом

- **WHEN** очередной кандидат из списка `/proxy/search` совпадает по логину с `proxy.username`
  какого-либо `tg-account.json` в `workspace-*/`
- **THEN** система пропускает этот кандидат без попытки подключения через него, переходит к
  следующему в списке

#### Scenario: Два агента обрабатываются в одном запуске

- **WHEN** список `--agents` содержит несколько `agentId`, и первому уже выдан рабочий кандидат
- **THEN** этот логин исключается из рассмотрения при подборе для всех последующих агентов того
  же запуска, даже если он ещё не записан на диск в момент их обработки

## REMOVED Requirements

### Requirement: Повторный прогон переиспользует и очищает существующий прокси

**Reason**: относилось к жизненному циклу `create-port` (созданный ресурс имеет `name`, можно
и нужно удалить при поломке). Кандидаты из `/proxy/search` — существующий ресурс аккаунта, не
создаются и не удаляются этим потоком; понятие «удалить старый прокси по имени» больше не
применимо.

**Migration**: проверка уже сохранённого прокси агента (кандидат №0, «а вдруг ещё работает») по
смыслу переносится в задачи реализации (`tasks.md`, п. 3.2) как самостоятельное решение, не как
формальное требование спецификации — она не завязана на удаление, только на «проверить прежде чем
искать новый».
