## Context

`mobile-proxy-provisioning` (2026-07-19) и `tg-agent-create-proxy-provisioning` (2026-07-20)
построили автоматический подбор мобильного прокси вокруг `POST /v2/proxy/create-port` —
провайдер (asocks.com) создаёт новый прокси-порт под явно переданный
`country_code`/`state`/`city`. На практике `state`/`city` в проде всегда одна точка (Флорида/
Майами) — так исторически сложилось при первом провижининге персон. Разбор коллизии прокси
2026-08-25/26 (у агентов с `monitor-v5` несколько групп по 2-3 агента делили один и тот же
`host+port+username+password`) показал: инвентарь реальных мобильных устройств asocks под эту
конкретную гео-точку — единицы. Правка типа порта (`type_id`, `server_port_type_id`,
2026-08-26) не устранила проблему — воспроизводимо (5 попыток) один и тот же exit IP
(`12.75.74.65`/`99.27.15.209`/`172.59.69.86`) возвращался независимо от того, shared или
dedicated запрашивался порт, потому что оба режима на этом аккаунте черпают из одного и того же
маленького пула под Майами.

Параллельно найден `GET /v2/proxy/search?country=<cc>&types[]=mobile&limit=<n>` — эндпоинт,
которым `mobile-proxy-provisioning`/`tg-agent-create-proxy-provisioning` не пользовались (не
упомянут в их design.md). Он не создаёт новый ресурс, а перечисляет уже существующие
прокси-сессии аккаунта, без фильтра `state`/`city` (только `country`+`types`). Проверено прямыми
запросами к API (2026-08-27):
- `country=US, types=mobile, limit=5000` → 1642 уникальных логина (весь пул страны, не города);
- список стабилен между вызовами: два подряд запроса с одинаковыми параметрами вернули один и тот
  же состав, только в другом порядке (не пересдача случайной выборки);
- логин↔exit IP стабилен: повторный запрос через один и тот же логин дал тот же exit IP; три
  разных логина дали три разных exit IP (`172.56.222.42`/`172.58.54.179`/`172.59.120.244`,
  T-Mobile US) — в отличие от `create-port`-логинов формата `hold-query`, которые ротируют IP на
  каждое новое подключение даже с одним и тем же логином.

## Goals / Non-Goals

**Goals:**
- Гарантировать (не просто удешевить вероятность), что два одновременно активных агента не
  получат один и тот же exit IP — сверкой по логину перед выдачей кандидата, а не оптимистичным
  созданием нового ресурса и надеждой на большой пул устройств в узкой гео-точке.
- Упростить жизненный цикл кандидата в мобильном потоке: `/proxy/search` не создаёт и не удаляет
  ресурс — кандидат либо подходит (сверка + проверка подключения), либо пропускается в пользу
  следующего элемента уже полученного списка. Никаких DELETE-вызовов к asocks для этого потока.
- Сохранить существующую форму цикла retry/verify в каждой из четырёх точек входа (`ensureClient`/
  `verifyConnection` в репейр-потоке, `probeProxy` в auto-probe создании агента, ручная проверка
  человеком в v2-потоке, `proxy-selection.ts` в автопостановке) — меняется только источник
  кандидата, не форма цикла вокруг него.

**Non-Goals:**
- Починка тихого зависания `ensureClient` при обрыве MTProto-соединения через новый/чужой
  прокси-кандидат (найдено 2026-08-26, воспроизведено 5/5 на `create-port`-кандидатах) — отложено
  явным решением пользователя. Если зависание воспроизведётся и на кандидатах из `/proxy/search`,
  это отдельная задача, не блокирующая эту работу.
- Расширение подбора на несколько стран одновременно (`/proxy/search` поддерживает
  `country=US.KZ`) — не требуется на текущем масштабе (~200 агентов против пула 1642), явно
  оставлено на будущее.
- Повторный провижининг уже существующих агентов с коллизией прокси — операционная задача после
  реализации и проверки этого change на 1-2 агентах, не часть самой работы.
- Изменение эндпоинта `/proxy/search` под `state`/`city` (он их не поддерживает) — гео-точность
  сознательно приносится в жертву размеру пула; если для персоны агента когда-то понадобится
  привязка к конкретному штату/городу «по легенде», это отдельный компромисс, не решаемый в рамках
  этой работы (см. Risks).
- Периодическая ревалидация стабильности логин↔exit IP (мониторинг на случай, если asocks
  когда-нибудь начнёт переиспользовать логин для другого физического устройства) — не
  реализуется, инвариант принимается на основании эмпирической проверки на момент написания.

## Decisions

**Сверка занятости — по логину, не по live-проверке exit IP.** Проверять реальный exit IP через
`curl`/аналог перед каждой выдачей кандидата было бы надёжнее в теории, но избыточно на практике:
логин↔exit IP уже подтверждён стабильным (см. Context), а лишний сетевой вызов на каждую сверку
замедляет подбор и добавляет точку отказа (сверка недоступна = блокирует выдачу прокси даже когда
логин объективно свободен). Сверка — чистое сравнение строк, без сети.

**Источник правды «кто чем пользуется» — `proxy.username` в `tg-account.json` каждого агента, без
отдельной БД.** Альтернатива — общий реестр занятых логинов (по образцу `agent-restrictions.db`,
одна БД в workspace админ-агента). Отклонено: `tg-account.json` уже единственный источник истины
о том, какой прокси у агента — заводить отдельную БД означало бы дублировать этот факт и следить
за его синхронностью (что бывает, если ручная правка `tg-account.json` разойдётся с реестром).
Сканирование `workspace-*/tg-account.json` на каждый подбор дороже по I/O, чем чтение одной
таблицы, но агентов — сотни, не миллионы; при росте на порядок пересмотреть можно тогда же, когда
пересматривается и вопрос масштаба страны (см. Non-Goals, п. «расширение на несколько стран»).
Гонки при этом не рассматриваются как риск: все вызывающие скрипты уже работают строго
последовательно по отдельным агентам (тот же принцип, что зафиксирован в
`mobile-proxy-provisioning` Non-Goals) — два подбора никогда не идут одновременно.

**`create-port`/`delete-port` полностью выводятся из мобильного потока подбора, но не удаляются
из `asocks-client.ts`.** Функции могут быть нужны для других типов прокси/сценариев вне скоупа
этой работы (например, ручное создание конкретного порта оператором). Новый поток — `search →
исключить занятые → verify → при неудаче взять следующий из того же списка» — не создаёт ничего
на стороне asocks, поэтому и удалять нечего.

**`--state`/`--city` выводятся из CLI/скиллов мобильного потока, `--country` остаётся.**
Гео-таргетинг до города признан несостоятельным для мобильных прокси на этом аккаунте (пул —
единицы устройств). Пошаговый подбор региона/города в `skills/tg-agent-create/SKILL.md` убирается
— остаётся только выбор страны (сценарий «ввести готовое значение» из существующего требования
«Выбор локации прокси — два режима» вырождается в «ввести код страны»; сценарий «пошаговый подбор»
теряет уровни регион/город, при необходимости может остаться только выбором страны из
`/dir/countries` либо быть убран вовсе — уточняется в tasks.md при реализации).

## Risks / Trade-offs

- **[Риск] Пул `/proxy/search` тоже конечен** (1642 сегодня для `country=US, types=mobile`).
  При росте числа агентов далеко за текущие ~200 пул может быть исчерпан. → Митигация: при
  исчерпании система должна явно сообщать «свободных прокси не осталось» (тот же принцип, что
  сегодняшнее «не найден за N попыток»), не тихо переиспользовать уже занятый другим агентом
  логин. Расширение на несколько стран (`country=US.KZ`) — готовый, но не реализуемый сейчас клапан
  (см. Non-Goals).
- **[Риск] Стабильность логин↔exit IP не задокументирована asocks** — подтверждена только
  эмпирически, на нескольких прямых замерах в момент разработки. Если провайдер когда-либо
  перевяжет логин на другое физическое устройство без предупреждения, инвариант уникальности
  перестанет выполняться незаметно для нас (сверка по логину покажет «свободно/занято» корректно
  для НАШЕГО учёта, но два логина после перевязки могут указывать на один и тот же физический
  exit IP). Не устраняется в рамках этой работы — периодическая ревалидация исключена из скоупа
  (Non-Goals).
- **[Trade-off] Потеря гео-точности (штат/город) для персон.** Решено пользователем
  (2026-08-27): привязка персоны к конкретному городу/штату сегодня не используется — оставляем
  только страну, `state`/`city` в подборе прокси не нужны.
- **[Риск] `/proxy/search` не даёт способа гарантированно повторно проверить исчерпание** —
  список от `/proxy/search` рандомизирован по порядку, но подтверждённо стабилен по составу
  (см. Context); если это когда-нибудь изменится (провайдер начнёт отдавать частичные/устаревающие
  выборки), логика «получить список один раз на весь прогон, дальше просто идти по нему» может
  пропустить часть реально свободных кандидатов. Не проверяется автоматически — принимается на
  основании замера на момент разработки.

## Migration Plan

Миграции данных нет — `ProxyConfig.state/city` остаются опциональными полями типа, существующие
`tg-account.json` с уже заполненными `state`/`city` (созданные до этого change) продолжают
работать как есть, просто не участвуют в новом подборе (сверка по стране использует
`countryCode`, который остаётся обязательным для сохранённой локации). Повторный провижининг уже
существующих коллизирующих агентов (188/204/208 и другие группы, разобранные 2026-08-25/26) — не
часть этого change, выполняется отдельно после реализации и smoke-теста на 1-2 агентах.

Откат: вернуть `createMobileProxy`/`deleteProxyByName` как источник кандидатов в трёх скриптах,
восстановить `--state`/`--city` в CLI и пошаговый подбор в `SKILL.md`. Новая функция сверки
занятости (сканирование `tg-account.json`) безвредна сама по себе — можно оставить неиспользуемой
при откате.

## Open Questions

Закрыт при реализации: `--delete-candidate` удалён, `--create-candidate` получил `--exclude
<login1,login2,...>` — вызывающая сторона (`proxy-selection.ts`, либо LLM, ведущий
`skills/tg-agent-create-v2/SKILL.md`) сама копит список отвергнутых в этом прогоне логинов в
памяти/контексте разговора и передаёт его явным аргументом на каждую следующую попытку. Временный
файл не потребовался — жизненный цикл кандидата и так укладывается в один процесс-вызывающий
(`proxy-selection.ts`) либо один диалог (LLM-скилл).
