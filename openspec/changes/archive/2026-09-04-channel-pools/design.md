## Context

`discovery.db` (в workspace `FUNNEL_ADMIN_AGENT_ID`) — единственный реестр каналов платформы: `discovered_channels(canonical_link PK, assigned_agent, added_at, banned_at)`. Два существующих пути наполнения:
- `discovery-add-pool.ts` + `distribute-pool.ts` — автоматический пайплайн (discovery-similar): каналы заводятся без агента (`assigned_agent = NULL`), затем round-robin по всем агентам платформы поровну.
- Ручные точечные вызовы (`registerChannel(..., assignedAgent)` уже поддерживает прямое назначение, но сейчас им никто не пользуется).

Внешний сегментационный анализ (пример — `channels/health_segmented.csv`) уже решает, какому агенту какой канал принадлежит, через колонку `pool_id`/`agent` — весь пул одного сегмента идёт одному агенту. Задача — провести это готовое сопоставление в платформу напрямую, без повторного round-robin, и закрепить имя пула за агентом для последующей аналитики (`funnel-report`).

## Goals / Non-Goals

**Goals:**
- Хранить имя пула за агентом один раз (первое присвоение), доступное для чтения `funnel-report`.
- Массово завести канал→агент из CSV с прямым назначением (без round-robin), переиспользуя существующий реестр `discovery.db` и `join_queue`.
- Защититься от несогласованных данных на входе: конфликт пула для уже известного агента и конфликт владельца канала (переезд с забаненного) обрабатываются явно, не молча.

**Non-Goals:**
- Не меняем `distribute-pool.ts`/`discovery-add-pool.ts` — это отдельный путь для другого источника (discovery-similar), сосуществует независимо.
- Не вводим ре-балансировку пулов, смену пула агента постфактум, матчинг по критериям (topic/subs/ER) — в отличие от нереализованного `docs/design/channel-groups/channel-groups-v1.md`, это не «умное» распределение, а прямой перенос уже готового внешнего решения.
- `subs`/`охват` из CSV нигде не сохраняются — они существуют только для внешнего анализа перед импортом, платформе они не нужны.
- Не трогаем текстовый отчёт воронки (`renderFunnel`) — колонка «пул» идёт только в CSV-вложение (`buildFunnelCsv`), текст и так ограничен шириной экрана (см. комментарий в `funnel-report.ts`).

## Decisions

**Хранилище пула — новая таблица `agent_pools` в `discovery.db`, не поле в `tg-account.json`.** Пул — это факт о распределении каналов, а не о телеграм-сессии агента; он живёт рядом с `discovered_channels`, которым и оперирует. `tg-account.json` остаётся конфигурацией подключения (apiId/proxy/device), а не платформенным реестром. Alternative (отклонена): поле `poolName` в `AccountConfig` — проще технически, но смешивает два независимых источника истины и требует читать/писать файл на каждом агенте вместо одной таблицы в одном файле.

**Прямое назначение через существующий `registerChannel(adminAgentId, link, assignedAgent)` — без нового round-robin.** Функция уже принимает `assignedAgent` (сейчас вызывается только без него из `discovery-add-pool.ts`). CSV поставляет агента per-row — round-robin не нужен и был бы неверен (сломал бы соответствие канала своему сегменту).

**Правило пропуска строки при конфликте пула.** Если `agent_pools[agentId]` уже задан и не совпадает с `pool_name` строки — строка целиком пропускается (канал не регистрируется, в очередь не идёт), в лог — предупреждение с обоими значениями. Пустой/отсутствующий `pool_name` в строке не создаёт конфликт и не трогает уже сохранённый пул агента (обратная совместимость со «старым способом» добавления каналов без пула).

**Правило для уже известного канала: skip vs reassign по статусу бана.** Известный `discovered_channels`-канал:
- `banned_at IS NULL` (агент активен на канале, неважно — тот же или другой, чем в строке CSV) → пропустить: канал уже размещён и работает, трогать нечего.
- `banned_at IS NOT NULL` → переназначить: `assigned_agent` = agentId строки, `banned_at` = NULL, канал добавляется в `tg-join-queue.db` нового агента. Банальная логика «мёртвый канал навсегда» заменяется возможностью пересдать его другому агенту через тот же CSV-механизм — иначе забаненные каналы копятся в реестре бесполезным балластом.

**Новый скрипт, не модификация `discovery-add-pool.ts`/`distribute-pool.ts`.** Разный формат входа (CSV с тройкой полей и явным агентом на строку vs список голых ссылок) и разная семантика распределения (прямое vs round-robin) — совмещение усложнило бы оба флага параметров без выгоды. Оба пути продолжают писать в один и тот же `discovery.db`/`join_queue`, поэтому расхождения в данных между ними исключены инвариантом `canonical_link PK`.

**`funnel-collect.ts` читает пул через `discovery.ts`, а не заново парсит `tg-account.json`.** Уже импортирует функции `discovery`-домена? Нет — но это тот же паттерн, что чтение `listPrivateInviteLinks` (тоже из соседнего `db/*`-модуля). Один новый вызов `getAgentPool(adminAgentId, agentId)` на агента, без побочных эффектов.

## Risks / Trade-offs

- **[Риск] Переназначение забаненного канала новому агенту не проверяет, не забанен ли канал у ВСЕХ агентов (например, в самом Telegram, а не только у конкретного аккаунта).** → Не смягчается в этой версии: бан в `discovered_channels` — это бан конкретного `assigned_agent`, у нового агента могут быть другие права на вступление. Это то же допущение, что уже действует в `markChannelBanned`/`leave-banned-channels`; не новый риск, унаследован.
- **[Риск] CSV с ошибочным `pool_name` для нового (ещё без пула) агента навсегда закрепляет опечатку — механизм не позволяет её исправить.** → Осознанное ограничение проекта («пул назначается один раз и не меняется»); если понадобится ручное исправление — прямой `UPDATE` в `agent_pools`, не через скрипт (не предусмотрено CLI-флагом в этой версии).
- **[Trade-off] Нет валидации, что `agentId` из CSV существует среди `listAgentIds()`.** → Строка с несуществующим агентом создаст `agent_pools`/`join_queue` запись для несуществующего workspace; `addJoinQueue`/скрипты уровня агента и так падают fail-soft на отсутствующий workspace в других местах. Явная проверка с понятным сообщением — дешёвое дополнение, включена в tasks.
