## Context

`ensureClient` (service.ts) — единственная точка подключения к сессии на всех
потребителей (диспетчер, скиллы, скрипты, gateway, funnel, reauth); там же уже взят
реентрантный per-agent лок сессии (`acquireSession`, защита от AUTH_KEY_DUPLICATED).
Сейчас `ensureClient` ретраит один и тот же прокси (3×60с) и при неуспехе бросает.
Мобильные прокси asocks интермиттентно не пробрасывают туннель до Telegram (порт открыт,
MTProto-хендшейк не проходит) — подтверждено данными funnel-tracker и прогоном
`probeProxy` по когорте. Есть готовые кирпичи: `probeProxy` (MTProto-хендшейк пустой
сессией, без tdata), `fetchAvailableMobileProxies`/`createProxyPicker` (инвентарь/пул
asocks), `toProxyConfig`/`saveProxyToAccountConfig`/`parseProxyCountry`. Существующий
`provisionProxyViaTdata` verify'ит кандидата через `connectBootstrap` (tdata) — это для
СЛОМАННЫХ сессий; для проверки самого прокси tdata не нужна.

## Goals / Non-Goals

**Goals:**
- Не входить в аккаунт через заведомо мёртвый прокси — probe перед каждым входом.
- При отказе прокси подобрать рабочий ДО входа и переключить агента на него (persist).
- Единый дом (`ensureClient`) → поведение для всех потребителей без дублирования.

**Non-Goals:**
- Не менять бюджет/поведение боевого `connect` (остаётся 3×60с; probe — отдельно).
- Не вводить last-good кэш (probe строго каждый раз — решение оператора).
- Не трогать `provisionProxyViaTdata`/reauth-путь по сути (только свести точку подбора).
- Не гарантировать «вечноживой прокси» — гарантия best-effort по пулу с чётким отказом.

## Decisions

### D1 — Гейт в `ensureClient`, внутри существующего лока
Probe и подбор — в `ensureClient`, после `acquireSession(agentId)` и до цикла боевого
`connect`. Так поведение применяется ко всем потребителям автоматически (точка одна), а
лок уже сериализует одного агента в пределах процесса и отдаёт `SessionBusyError`
чужому процессу — отдельная синхронизация для swap `tg-account.json` не нужна.

### D2 — Probe: `probeProxy`, к Telegram DC, 2×10с, без tdata, без кэша
Проверяем текущий прокси `probeProxy` (пустая сессия + apiId/apiHash агента) — это
MTProto-хендшейк именно к Telegram, не к канарейке. 2 попытки × 10с. Кэша «последнего
рабочего» нет: probe строго перед каждым входом (решение оператора — строгость важнее
экономии хендшейка). `probeProxy` уже принимает `{apiId, apiHash, proxy}` и параметры
попыток/таймаута задаются на месте вызова.
_Альтернатива:_ last-good кэш на N минут — отклонено оператором (нужна строгая гарантия).

### D3 — Подбор: probe-based, без tdata, до 10 кандидатов
Новый подборщик (рядом с `provisionProxyViaTdata`, напр. `provisionProxyViaProbe`):
`fetchAvailableMobileProxies(country)` → `createProxyPicker` → до 10 раз: взять
кандидата → `probeProxy` → первый прошедший `toProxyConfig` + `saveProxyToAccountConfig`
и вернуть. Страна — из текущего прокси агента (`parseProxyCountry`). tdata не нужна:
verify'им ПРОКСИ, а не сессию/аккаунт. Отличие от `provisionProxyViaTdata` — только
метод verify (`probeProxy` вместо `connectBootstrap`); инвентарь/пул/запись общие.
_Альтернатива:_ переиспользовать `provisionProxyViaTdata` — отклонено: он требует tdata
и verify'ит через bootstrap (для сломанной сессии), для живых агентов не годится.

### D4 — Триггер подбора — только провал probe (бюджеты раздельны)
Подбор запускается ТОЛЬКО при провале обеих попыток probe. Если probe прошёл, а боевой
`connect` затем упал — подбор НЕ запускаем; `connect` отрабатывает свой бюджет (3×60с) и
падает как сегодня (решение оператора — не сводить бюджеты). Так probe-гейт и боевой
`connect` — два независимых уровня; логика простая и предсказуемая.

### D5 — Терминал: throw, прогон завершается ошибкой
10 кандидатов не прошли / нет `ASOCKS_API_KEY` / пустой инвентарь → `ensureClient`
бросает (тип — как у существующего отказа подключения), `tg-account.json` не трогаем.
Вызвавший прогон завершается с ошибкой, как при обычном connect-fail.

## Risks / Trade-offs

- **+1 хендшейк к Telegram на каждый вход** → happy-path ~1–2с; объём хендшейков растёт
  (диспетчер тикает по каждому агенту каждые ~10 мин). Принято: строгая гарантия важнее.
- **Мёртвый прокси удорожает вход** (2×10с probe + до 10 probe-проверок кандидатов до
  входа) → осознанная цена; после успешного swap следующий вход уже дешёвый.
- **Флейки-прокси могут иногда провалить probe и спровоцировать замену** → «2 попытки»
  — минимальный гистерезис; churn признан оператором приемлемым (ситуации оправданы).
- **Регрессия в едином critical path** (гейт трогает ВСЕ подключения) → покрыть проверкой
  happy-path (probe OK → обычный вход) и отказного пути до деплоя.
- **Дубль с reauth-sweep-proxy-repair** → его connect_failed-подбор через tdata
  пересекается; свести точку подбора при реализации (tdata-verify оставить для сломанных
  сессий, где сам аккаунт надо доказать).

## Migration Plan

1. `provisionProxyViaProbe` (новый, probe-verify, без tdata) в `src/features/proxy/`.
2. `ensureClient`: probe-гейт (2×10с) + вызов подборщика при провале + throw при
   исчерпании, внутри лока, перед боевым циклом `connect`.
3. Свести connect_failed-ветку `reauth-sweep-proxy-repair` с общим гейтом.
4. Проверка: happy-path, отказ прокси→успешный swap, исчерпание 10→ошибка.

Откат: probe-гейт за флагом/легко снимаем — `ensureClient` возвращается к прежнему
поведению (ретрай того же прокси).
