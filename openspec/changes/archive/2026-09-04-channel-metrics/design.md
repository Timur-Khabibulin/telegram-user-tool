## Context

Оператору нужно оценивать произвольные списки Telegram-каналов (не обязательно уже отслеживаемых каким-либо агентом) по четырём метрикам: подписчики, средний охват поста, открыты ли комментарии, тип канала (broadcast/группа). Похожая механика уже есть в трёх местах кодовой базы, но ни одна не подходит напрямую:

- `src/scripts/channel-coverage-update.ts` — считает `avg_views`/`subs_count`, но только для каналов, уже отслеживаемых конкретным агентом (`getChannelsForCoverageUpdate`), раз в месяц, пишет в `channels.db`. Не даёт `comments_open`/`is_broadcast`, не принимает произвольный список ссылок.
- `src/core/channel-analysis/run.ts` — метрики вовлечённости постов, тоже только по кэшированным каналам агента.
- `src/core/discovery/run.ts` (D1–D8 в `channel-discovery-avg-post-reach`) — MTProto-фолбэк на TGStat для `avg_post_reach` по одному каналу за раз, в рамках гейта discovery. Источник основной — TGStat; не годится как основа, поскольку задача явно не использует TGStat.

Все три уже используют примитивы `TelegramService` (`resolveChannelByUsername`, `getRecentPosts`, `getChannelGateInfo`/`getChannelSubsCount`) — новый скрипт переиспользует их, а не изобретает MTProto-вызовы заново.

Обсуждение и решения по контракту, источнику данных, масштабу и резюмируемости — см. переписку в сессии (explore mode), зафиксированы ниже как Decisions.

## Goals / Non-Goals

**Goals:**
- Скрипт `channel-metrics.ts`: вход — CSV с колонкой `link`, выход — CSV с метриками на канал, построчная (инкрементальная) запись.
- Резюмируемость: повторный запуск с тем же `--output` не повторяет уже обработанные (успех или ошибка) ссылки.
- Единая сессия одного агента (`--agent`) на весь прогон, масштаб — сотни ссылок за раз.
- Устранить дублирование формулы среднего охвата между `channel-coverage-update.ts` и новым скриптом.
- Claude Code skill `channel-metrics` как операторский интерфейс (upload → run → download).

**Non-Goals:**
- Несколько агентов/аккаунтов в одном прогоне (балансировка нагрузки между сессиями) — не нужно при масштабе «сотни».
- TGStat как источник данных — недостаточен для `comments_open`/`is_broadcast`.
- Резолв приватных ссылок (`t.me/+...`, `t.me/joinchat/...`) через `CheckChatInvite` — такие строки уходят в `error`, не блокируют прогон.
- Автоматический retry ошибочных строк при повторном запуске — оператор решает вручную (например, вручную удалив строку из выходного файла).
- Запись через `dispatcher`/systemd — это ручной инструмент оператора, не задача агента.

## Decisions

### D1. Источник данных — чистый MTProto, без TGStat

`comments_open` и `is_broadcast` — телеграм-нативные признаки (`GetFullChannel.linkedChatId`, `Api.Channel.broadcast`), которых TGStat не отдаёт. Поскольку MTProto-вызов всё равно обязателен для этих двух полей, брать `subs_count`/`avg_views` из TGStat, а остальное — из MTProto, добавляет второй источник данных и токен-зависимость без экономии MTProto-вызовов (тот же `GetFullChannel` уже даёт `subscribers` заодно с `linkedChatId` — см. D3). Решение: всё через один и тот же набор MTProto-вызовов на канал.

**Отклонено**: TGStat как основной источник (как в discovery), MTProto — только для `comments_open`/`is_broadcast`. Два источника вместо одного ради экономии одного вызова (`channels.GetFullChannel` и так нужен) — не оправдано.

### D2. Один MTProto-проход на канал: resolve → GetFullChannel → getMessages

```
normalizeChannelLink(link)
        │
        ▼
resolveChannelByUsername(username)  ──null──▶ error: "канал не найден"
        │
        ├─▶ isBroadcast (Api.Channel.broadcast, новое поле ChannelHandle)
        ▼
getChannelGateInfo(inputChannel)  ──▶ subscribers, linkedChatId
        │                              │
        │                              └─▶ comments_open = linkedChatId != null
        ▼
getRecentPosts(inputChannel, 11)  ──▶ computeAvgViews(posts)
```

3 MTProto-вызова на канал (`ResolveUsername`, `GetFullChannel`, `getMessages`), каждый через уже существующие методы `TelegramService`. Ссылки без резолвимого username (приватные) не доходят до MTProto — сразу `error`.

**Отклонено**: параллельные запросы (Promise.all resolve+full+messages) — `getChannelGateInfo`/`getRecentPosts` требуют `InputChannel` с `accessHash`, который даёт только `resolveChannelByUsername`; вызовы строго последовательны для одного канала. Между каналами — тоже последовательно (см. D6, один аккаунт).

### D3. `comments_open` и `subs_count` — один вызов `getChannelGateInfo`, не два

`getChannelGateInfo` уже возвращает `{subscribers, linkedChatId, about}` из одного `channels.GetFullChannel`. Использовать его вместо раздельных `getChannelSubsCount` + отдельного запроса на `linkedChatId` — меньше вызовов на канал, меньше риска `FLOOD_WAIT`. `comments_open = linkedChatId != null`.

### D4. `isBroadcast` — новое поле `ChannelHandle`, заполняется в `resolveChannelByUsername`

Сейчас `resolveChannelByUsername` (`service.ts:1113-1131`) резолвит `Api.Channel`, но использует только `username`/`title`, отбрасывая `channel.broadcast`. `DialogChannel` (соседний тип) уже имеет `isBroadcast` — паттерн именования и семантики переиспользуется, поле добавляется в `ChannelHandle`.

**Отклонено**: отдельный метод `isChannelBroadcast(handle)` с ещё одним MTProto-вызовом — избыточно, флаг уже есть в ответе `ResolveUsername`, просто не пробрасывается.

### D5. Среднее по постам — вынесенная функция, методология без изменений (coverage-update)

Текущая формула в `channel-coverage-update.ts`:
```ts
if (posts.length < 2) avgViews = null;
else {
    const sample = posts.slice(1, 11);
    avgViews = sample.reduce((sum, p) => sum + p.views, 0) / sample.length;
}
```
Выносится в переиспользуемую функцию `computeAvgViews(posts: ChannelPost[]): number | null` (кандидат размещения — рядом с `ChannelPost`/`getRecentPosts` в `src/core/telegram/service.ts`, либо соседний модуль `src/core/telegram/metrics.ts` — решается на этапе реализации по месту меньшего связывания). Используется и в `channel-coverage-update.ts` (замена инлайн-кода, без изменения поведения), и в `channel-metrics.ts`. Один факт (формула среднего охвата) — один дом.

**Отклонено**: новая формула для `channel-metrics.ts` (например, без пропуска самого свежего поста) — решение сессии явно зафиксировало «методологию бери от coverage-update»; вторая формула охвата в кодовой базе создала бы путаницу при сравнении чисел из разных источников.

### D6. Один агент, последовательная обработка, пейсинг и circuit-breaker как в `channel-analysis/run.ts`

`--agent <agentId>` — обязательный параметр, оператор указывает сессию явно (тот же паттерн, что `avgReachAgentId` в discovery и `agents` в channel-analysis: скрипт не выбирает аккаунт сам). Пейсинг между MTProto-вызовами — `pacingMs()` (0.8–1.2 с, тот же разброс, что в `channel-analysis/run.ts`). Circuit-breaker: 2 `FLOOD_WAIT` подряд → `FloodStop`, весь прогон останавливается (не только текущий канал) — переиспользуется `makeFloodAware` паттерн. При масштабе «сотни» и одном аккаунте это не редкий случай — резюмируемость (D7) существует именно для того, чтобы обрыв не стоил повторного прохода по уже обработанным ссылкам.

### D7. Резюмируемость через сравнение уже записанных ссылок в `--output`

При старте, если `--output` существует, скрипт читает его и строит множество уже обработанных ссылок — по `normalizeChannelLink` от значения колонки `link` каждой строки, независимо от того, `error` там или полные метрики. Ссылки из `--input`, отсутствующие в этом множестве, обрабатываются; присутствующие — пропускаются без MTProto-вызова. Запись — `fs.appendFileSync` (или открытый write stream в режиме append) сразу после обработки каждого канала, не буферизация в памяти до конца прогона.

**Отклонено**: retry ошибочных строк при резюме — усложняет модель («сколько раз ретраить», «какие ошибки временные, а какие постоянные») без запроса от оператора; явно вне скоупа (см. Non-Goals). Оператор, которому нужен retry конкретной ссылки, удаляет её строку из `--output` вручную и перезапускает.

**Отклонено**: отдельный файл состояния (`--output.state.json`) вместо чтения самого `--output` — лишняя сущность; выходной CSV и так содержит всё нужное для определения «что уже сделано».

### D8. Входной/выходной контракт — минимальный, без джойна с исходной таблицей

Вход: любой CSV с колонкой `link` (порядок и наличие остальных колонок не важны, игнорируются). Выход: `link,subs_count,avg_views,comments_open,is_broadcast,error` — фиксированный набор колонок, без переноса title/agentId/etc. из входа. Если оператору нужна обогащённая таблица (с названием канала и т.п.) — это делается отдельным шагом вне скрипта (join по `link`, например через Claude Code при подготовке финального отчёта), не заботой `channel-metrics.ts`.

**Отклонено**: пробрасывать все входные колонки в выход — усложняет CSV-парсинг (неизвестная заранее схема входа), увеличивает площадь для багов экранирования; оператору эта функция не была нужна (решение сессии: «минимальный контракт»).

### D9. Приватные ссылки — сразу `error`, без попытки `CheckChatInvite`

Ссылки вида `t.me/+...`/`t.me/joinchat/...` после `normalizeChannelLink` не дают валидного `username` для `resolveChannelByUsername`. Строка сразу пишется с пустыми метриками и `error="приватная ссылка, резолв по username невозможен"`, без похода в `messages.CheckChatInvite` (который к тому же не гарантирует полных данных без вступления в канал).

## Risks / Trade-offs

**[Риск] Один MTProto-аккаунт делает GetFullChannel/ResolveUsername по сотням каналов, в которых не состоит.**
Ранее такой паттерн использовался только точечно (discovery-фолбэк — один канал за раз, `channel-analysis` — только по уже присоединённым каналам агента). Массовый обход чужих/непосещённых каналов одним аккаунтом — новый профиль нагрузки, потенциально заметный для анти-спам эвристик Telegram.
→ Смягчение: пейсинг 0.8–1.2 с + circuit-breaker на 2 подряд `FLOOD_WAIT` (тот же минимальный барьер, что уже принят в `channel-analysis`); масштаб ограничен оператором («сотни», не тысячи); резюмируемость снижает цену повторных попыток вместо ретраев с нуля. Дальнейшее ужесточение (например, более длинные паузы) — по факту наблюдения, не заранее.

**[Риск] Долгий прогон (десятки минут — часы на сотнях ссылок с FLOOD_WAIT) — обрыв SSH-сессии/скрипта на VPS теряет процесс.**
→ Смягчение: инкрементальная запись в `--output` (D7) means любой обрыв теряет максимум текущий необработанный канал, не весь прогон; резюмируемость восстанавливает без пересчёта готового.

**[Риск] `computeAvgViews`, вынесенная из `channel-coverage-update.ts`, может неявно изменить его поведение при рефакторинге.**
→ Смягчение: функция — точный перенос существующей формулы без изменений логики; после рефакторинга `channel-coverage-update.ts` должен давать те же значения `avg_views`, что и до изменения (регресс проверяется на этапе реализации).

## Migration Plan

Аддитивное изменение, миграции данных не требуется:
1. Добавить `isBroadcast` в `ChannelHandle` — обратно совместимо (новое поле).
2. Вынести `computeAvgViews`, обновить `channel-coverage-update.ts` на использование — поведение не меняется, деплой как обычно (`scp` + `chown` + `gateway restart`, см. `docs/operation.md`).
3. Добавить `channel-metrics.ts` и `.claude/skills/channel-metrics/SKILL.md` — новые файлы, не затрагивают существующие потоки выполнения (не вызывается dispatcher'ом).
4. Откат — удаление новых файлов и поля `isBroadcast` (не используется другим кодом до этого изменения).

## Open Questions

- Точное место размещения `computeAvgViews` (рядом с `ChannelPost`/`getRecentPosts` в `service.ts`, или отдельный модуль) — решается при реализации по фактическому импорт-графу, не блокирует дизайн.
