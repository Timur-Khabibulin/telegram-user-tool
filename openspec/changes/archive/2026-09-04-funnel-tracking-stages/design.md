## Context

Аналитика фичи для человека уже полностью проработана и согласована с
пользователем в трёх документах (источник истины для этого design.md, не
дублируется здесь подробно):

- `docs/design/funnel-tracking/funnel-tracking-v2.md` — воронка (7 этапов),
  формулы (`activityRate`, дельты снапшотов), формат отчёта.
- `docs/design/funnel-tracking/requirements-v2.md` — User Stories, Acceptance
  Criteria, бизнес-правила (BR-1...BR-4).
- `docs/design/funnel-tracking/architecture-v2.md` — модель данных и точки
  записи в пайплайне (полный текст решений Q2-Q4 и двух дополнительных
  решений по `collectFunnel`/`monitor.ts`).

Текущая реализация (v1): один общий модуль `core/funnel-collect.ts`
(`collectFunnel`), используемый и таймерным скриптом (`persist=true`), и
инструментом по требованию (`persist=false`), плюс `core/db/funnel.ts`
(`funnel.db` в workspace admin-агента) для снапшотов/дневных агрегатов этапов
5-7. Этот код не меняется по структуре — этапы 1-4 встраиваются в тот же
`collectFunnel`, не создают параллельный пайплайн.

## Goals / Non-Goals

**Goals:**
- Дать видимость по этапам 1-4 воронки (каналов у агента / просмотрено /
  активно / отправлено+ошибки) без новых вызовов к Telegram — все величины
  уже вычисляются в `monitor.ts`/`dm-send.ts`, нужно только их сохранить.
- Не потерять данные этапов 5-7 при сбое сбора этапов 1-4 для того же агента
  (и наоборот) — раздельная изоляция ошибок.
- Не повторно валить весь прогон `monitor.ts` из-за ошибки отправки в одном
  канале.

**Non-Goals:**
- Lag/нагрузка агента (отставание обхода каналов от номинального периода) —
  осознанно вне скоупа (BR-4 в requirements-v2.md). `channel_visits`
  технически делает это вычислимым в будущем без миграции схемы, но в этом
  change метрика не считается и не отображается.
- Новая таксономия типов ошибок — `send_errors.errorCode` использует
  значения, которые код уже вычисляет (`peer_flood`, `flood_wait`, ...); при
  готовности отдельной инициативы нормализации ошибок (`project_error_normalization`)
  источник значения можно заменить без изменения схемы — замена не входит в
  этот change.
- Изменение существующих метрик этапов 5-7 (просмотры/подписчики/заявки) —
  формулы и хранение (`funnel.db`, `channel_snapshots`, `daily_stats`) не
  трогаются.

## Decisions

**Константа `CHANNEL_CHECK_PERIOD_SECONDS` — единственный источник истины.**
Выносится в `core/config.ts`. `monitor.ts` (приватная `PERIOD_SECONDS`) и
`channels.ts` (`DEFAULT_PERIOD_SECONDS`, дефолт параметра `getChannelsBatch`)
ссылаются на неё. Альтернатива (оставить дублирование и просто
синхронизировать значения вручную) отклонена — ровно та проблема, которую
обсуждение с пользователем выявило исходно (activityRate использует
константу как знаменатель, рассинхрон с monitor.ts искажал бы метрику).

**`channel_visits` и `send_errors` — append-only таблицы в существующей
`tg-channels.db` (per-agent), не новый файл БД и не `funnel.db`.**
Причина: это данные конкретного агента (как `channels`/`dm_candidates`),
монитор и dm-send уже открывают этот файл каждый прогон. `funnel.db` —
платформенный артефакт, объединяющий снапшоты всех агентов для отчёта этапов
5-7; этапы 1-4 не дельты и не нуждаются в межпрогонном состоянии, поэтому не
персистятся туда. Полная схема, обоснование полей и альтернативы — см.
architecture-v2.md §3, §4 (не повторяется здесь).

**Раздельные try/catch в `collectFunnel` на группы этапов 1-4 / 5-7.**
Сегодня один `try` покрывает и локальные SQLite-чтения, и MTProto-вызовы;
один `catch` помечает агента целиком пропущенным. Разделение — чтобы сбой
одного источника (например, `tg-channels.db` временно заблокирован
монитором) не терял уже посчитанные данные другого источника (MTProto).
Альтернатива (оставить один try/catch, потенциально терять данные при
частичном сбое) отклонена — цена ниже, чем выигрыш в полноте отчёта.

**Ошибка `sendReply` в `monitor.ts` — пропустить канал, продолжить прогон.**
Сегодня не-flood исключение при отправке ответа в группе пробрасывается и
валит весь прогон для всех оставшихся каналов батча. Меняется на ту же схему,
что уже есть для ошибки `get_messages`: `recordSendError` +
`markChannelProcessed` + переход к следующему каналу. `FloodAbortError`
остаётся особым случаем (повторный flood прерывает весь прогон) — это
поведение `withFloodRetry`, не затрагивается этим решением, потому что
повторный flood — сигнал для всего агента, а не для одного канала.

**`send_errors.errorCode` — без новой таксономии (BR из requirements-v2.md
Q5).** Берёт значения напрямую из существующего кода (`peer_flood`,
`flood_wait`, `privacy_blocked`, `deactivated`, `get_messages_error` и т.п.).
Альтернатива (ввести свою нормализованную таксономию для воронки) отклонена
— дублировала бы будущую инициативу `project_error_normalization`; колонка
`TEXT` без enum/constraint допускает замену источника значения без миграции.

**Формат отчёта: узкая таблица (этапы 1-4) в тексте + CSV-вложение (все 7
этапов).** Полная таблица со всеми этапами не помещается на экране телефона
в моноширинном блоке (Telegram переносит строку, а не скроллит). CSV кладётся
в `reportsDir(adminAgentId)` — тот же путь и конвенция имени (UTC-timestamp),
что уже использует channel-content-analysis, без нового каталога.

## Risks / Trade-offs

- **[Риск] Рост числа строк `channel_visits` при большом числе агентов и
  каналов.** → Митигация: append-only без TTL в этой версии (оценка —
  десятки тысяч строк в год на агента при текущем масштабе, не проблема для
  SQLite); очистка — Future Work, не блокирует этот change.
- **[Риск] Реализация `recordSendError`/`recordChannelVisit` в
  `monitor.ts`/`dm-send.ts` случайно меняет существующий control flow
  (`stopReason`/`floodErrors`/`break`/`continue`).** → Митигация: вызовы
  записи вставляются **перед** существующими ветвлениями, не заменяют их;
  явно зафиксировано в architecture-v2.md §4.3, что флоу не трогается.
- **[Trade-off] Этапы 1-4 не персистятся отдельно (в отличие от 5-7,
  `daily_stats`) — пересчитываются прямым запросом при каждом построении
  отчёта.** Принято осознанно: это не дельты, пересчёт по дню дешевле, чем
  поддерживать ещё одну таблицу агрегатов, дублирующую первоисточник.
- **[Trade-off] Раздельные try/catch в `collectFunnel` требуют двух полей
  пометки (`note1to4`/`note5to7`) вместо одного `note`.** Небольшое
  усложнение интерфейса `AgentFunnelRow` ради того, чтобы частичный отчёт по
  агенту не схлопывался в полное молчание.

## Migration Plan

Нет миграции существующих данных — обе новые таблицы создаются идемпотентно
(`CREATE TABLE IF NOT EXISTS`) при первом обращении, как и все существующие
таблицы проекта. История до выкатки изменения недоступна (например, медиана
`activityRate` за первый день после деплоя посчитается по визитам только с
этого дня) — это ожидаемо и не требует отдельного бэкафилла.

Откат: при необходимости откатить — новые таблицы остаются неиспользуемыми
(не читаются старым кодом), удаление не требуется для отката функциональности.
