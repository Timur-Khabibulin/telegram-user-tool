## MODIFIED Requirements

### Requirement: Метрики активности из БД агента

Система SHALL за завершившийся день UTC+5 считать по каждому агенту число каналов, в которые отправлено хотя бы одно сообщение группы (DISTINCT `chatId` из `replies.sentAt` окна дня, `tg-replies.db`). Личные сообщения (`dm_history`) SHALL не учитываться ни в этом, ни в каком-либо другом показателе сбора воронки.

#### Scenario: Подсчёт каналов с отправкой за день

- **WHEN** прогон считает метрики за день UTC+5
- **THEN** показатель «каналов с отправкой» равен числу DISTINCT `chatId` в `replies` с `sentAt` в окне дня, независимо от числа сообщений в каждый канал

#### Scenario: Несколько сообщений в один канал

- **WHEN** агент отправил за отчётный день несколько сообщений в один и тот же канал
- **THEN** канал засчитывается в показателе один раз

#### Scenario: Только личные сообщения за день

- **WHEN** агент за отчётный день отправлял только личные сообщения (DM), без сообщений в группы
- **THEN** показатель «каналов с отправкой» для этого агента равен 0

#### Scenario: БД агента отсутствует или недоступна

- **WHEN** `tg-replies.db` агента отсутствует или не читается
- **THEN** показатель берётся как 0 либо агент пропускается с пометкой, прогон не падает

### Requirement: Снапшот заявок в приватный канал

Система SHALL для каждого активного агента с настроенной персональной пригласительной ссылкой (`private_invite_links`) снимать число неодобренных заявок на вступление в приватный канал по этой конкретной ссылке (`messages.GetChatInviteImporters(peer, requested=true, link=<ссылка агента>)`) от имени администратора приватного канала (`REPORT_AGENT_ID`) и сохранять в `channel_snapshots.private_pending_requests` строки снапшота этого агента. Платформенный итог заявок SHALL вычисляться как сумма значений по всем агентам, а не отдельным независимым запросом. У агента без настроенной ссылки значение SHALL быть NULL (не 0), MTProto-запрос для него не выполняется. При недоступности шага сбора целиком (нет прав, ошибка запроса) метрика заявок SHALL быть пропущена с пометкой для всех агентов, прогон не падает.

#### Scenario: У агента настроена ссылка

- **WHEN** у агента есть запись в `private_invite_links`, и администратор приватного канала имеет право `invite_users`
- **THEN** число pending-заявок по ссылке этого агента записывается в `private_pending_requests` его строки снапшота

#### Scenario: У агента нет настроенной ссылки

- **WHEN** для агента нет записи в `private_invite_links`
- **THEN** `private_pending_requests` для него — NULL, MTProto-запрос по нему не выполняется

#### Scenario: Недостаточно прав

- **WHEN** `GetChatInviteImporters` возвращает `CHAT_ADMIN_REQUIRED`
- **THEN** заявки помечаются недоступными в отчёте для всех агентов, остальные метрики собираются как обычно

#### Scenario: Платформенный итог

- **WHEN** вычисляется платформенный итог заявок
- **THEN** он равен сумме `private_pending_requests` по всем агентам (NULL трактуется как 0 в сумме), отдельного независимого запроса для итога не выполняется

## ADDED Requirements

### Requirement: Фильтр активных агентов

Система SHALL перед сбором метрик воронки определять список активных агентов — агентов, у которых на момент формирования отчёта включена (enabled) задача мониторинга (`monitor` либо `monitor-v2`) — и собирать метрики только по ним. Неактивные агенты SHALL не создавать никакой записи в результате сбора.

#### Scenario: У агента включена задача мониторинга

- **WHEN** у агента enabled хотя бы одна из задач `monitor`/`monitor-v2`
- **THEN** агент включается в сбор метрик наравне с остальными активными агентами

#### Scenario: У агента отключены обе версии мониторинга

- **WHEN** у агента `enabled=0` и для `monitor`, и для `monitor-v2`
- **THEN** агент полностью исключается из сбора — метрики по нему не считаются, он не встречается в результате ни в каком виде

#### Scenario: Активность проверяется на момент сбора

- **WHEN** мониторинг агента был включён в течение отчётного дня, но выключен к моменту формирования отчёта
- **THEN** агент исключается — используется состояние enabled на момент сбора, истории включённости за день система не хранит

### Requirement: Разбивка отправленных сообщений по каналам

Система SHALL за завершившийся день UTC+5 собирать по каждому активному агенту построчную разбивку сообщений группы по каналам: `chatId`, число сообщений, заголовок канала и данные для переходимой ссылки (username чата либо числовой id супергруппы/канала и id последнего сообщения агента в этом канале за день). Личные сообщения (DM) SHALL не входить в разбивку.

#### Scenario: Сообщения в несколько каналов

- **WHEN** агент за отчётный день отправил сообщения в несколько разных каналов
- **THEN** разбивка содержит отдельную запись на каждый такой канал с числом сообщений именно в него

#### Scenario: Канал без публичного username

- **WHEN** канал агента — приватная супергруппа/канал без публичного username
- **THEN** данные для ссылки берутся из числового id канала и id последнего сообщения агента за день, а не из username
