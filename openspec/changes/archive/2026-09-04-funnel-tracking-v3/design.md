## Context

Действующая архитектура funnel-tracking v2: этапы 1-4 воронки считаются из `tg-channels.db`/`tg-replies.db` каждого агента (`channel_visits`, `send_errors`, `replies`, `dm_history`), пересчитываются заново на каждом прогоне; этапы 5-7 — снапшоты в `funnel.db` (`channel_snapshots`/`daily_stats`, владелец — `FUNNEL_ADMIN_AGENT_ID`), с дельтой к предыдущему снапшоту. Отчёт собирает `src/core/funnel-collect.ts` → рендерит `src/core/funnel-report.ts` → отправляет `src/scripts/funnel-tracker.ts` в Saved Messages раз в день.

Параллельным, ещё не заархивированным изменением `private-invite-links` уже введены: таблица `private_invite_links` (`agentId → ссылка`) в новом файле `private-invites.db`; перенос роли администратора приватного канала с `FUNNEL_ADMIN_AGENT_ID` на `REPORT_AGENT_ID` (у `agent1` больше нет доступа к приватному каналу); инструмент `tg_private_invite_links` для ручной генерации ссылок оператором. Это решение строится поверх уже существующего `private_invite_links`, не вводит собственное хранилище ссылок.

Полное техническое решение по всем пяти изменениям детально проработано в `docs/design/funnel-tracking/architecture-v3.md` — этот документ выжимает из него архитектурные решения и риски; поточную реализацию (сигнатуры, схемы, порядок вызовов) см. там.

## Goals / Non-Goals

**Goals:**
- Реализовать US-1…US-5 и сквозное требование UTC+5 из `docs/design/funnel-tracking/requirements-v3.md`.
- Не сломать контракт `daily_stats` для внешнего потребителя (`funnel-stats`, Excel-отчёт на VPS, читает БД напрямую по SQL).
- Не заводить дублирующее хранилище там, где нужные данные уже существуют (`private_invite_links`, per-agent колонки `channel_snapshots`/`daily_stats`).

**Non-Goals:**
- Автогенерация персональных ссылок для новых агентов — вне скоупа (уже вынесено как future work в `private-invite-links`).
- Историческая проверка «агент был активен весь день» — система не хранит историю `enabled`, вводить её не требуется (US-4 явно проверяет текущее состояние).
- Физическое удаление колонки `daily_stats.dms_sent` — не даёт выгоды сейчас, откладывается.
- Пересмотр формата отчёта voronki v2 за пределами перечисленных пяти изменений.

## Decisions

**1. Хранилище «агент → ссылка» — переиспользовать `private_invite_links`, не заводить новую таблицу.**
Альтернатива (новая таблица в `funnel.db`) отклонена: создала бы второй источник истины для одних и тех же данных без причины — `private-invite-links` уже решает эту задачу целиком, включая ручное редактирование оператором.

**2. `getChannelSendBreakdown` заменяет `getDistinctRepliedChatIds` — один запрос вместо двух.**
Новая функция в `db/replies.ts` группирует `replies` по `chatId` и отдаёт разом count (US-2, `.length`) и построчную разбивку с последним `msgId` (US-5, якорь для ссылки). Альтернатива (оставить старую функцию для US-2, отдельный новый запрос для US-5) отклонена — оба показателя читают одну и ту же таблицу за одно и то же окно, разделять запрос не даёт выгоды и создаёт риск рассинхрона.

**3. `groupReplies` (счётчик сообщений) остаётся в БД без изменений; `channelsWithSending` — новое, только отображаемое поле.**
`daily_stats.group_replies` — вход независимого скилла `funnel-stats`, который строит историческую конверсию «просмотры/ответ» по всей истории БД на VPS. Переименовать смысл поля задним числом сломало бы эту историю без уведомления потребителя, который читает БД напрямую, а не через `funnel-report.ts`. Альтернатива (переиспользовать `group_replies` под новый смысл) отклонена по этой причине.

**4. `dmsSent` — прекращает собираться из `dm_history`, колонка `daily_stats.dms_sent` остаётся в схеме, всегда `0`.**
`funnel-stats` не читает эту колонку (проверено). Физический `DROP COLUMN` не даёт выгоды (никто её не читает) и добавляет риск миграции без причины. Альтернатива (убрать колонку) отклонена как непропорциональная — совпадает с [[Non-Goals]].

**5. Фильтр активных агентов — одна функция, одна точка вызова.**
`isAgentActive(agentId)` в `db/tasks.ts` (переиспользует существующий `listTasks`), вызывается один раз в начале `collectFunnel`, до шага заявок и до основного цикла. Список активных агентов используется в обоих местах. Альтернатива (фильтровать в каждом месте отдельно) отклонена — два независимых обхода `listAgentIds()` рискуют разойтись и дублируют MTProto/БД-обращения для заведомо исключённых агентов.

**6. Платформенный итог заявок — сумма по агентам, отдельный запрос убирается.**
`getPendingJoinRequests` получает необязательный `link`; шаг сбора заявок становится циклом по ссылкам активных агентов (один `tg.loadAccount(REPORT_AGENT_ID)` на весь цикл), итог считается как `SUM` по собранным per-agent значениям. Альтернатива (оставить старый общий запрос для итога параллельно с новым per-agent сбором) отклонена — по AC US-3 итог обязан совпадать с суммой по построению, два независимых способа подсчёта создают риск расхождения.

**7. Ссылка на канал — новая колонка `chatUsername`, без новых MTProto-вызовов; для «базовых» групп ссылки нет.**
Существующая `channels.channelUsername` — это username привязанного broadcast-канала (другая сущность), не самого чата. `chatUsername` — новая колонка, заполняется из уже получаемых, но ранее отбрасываемых данных `listGroupChannels()`. Ссылка строится как `t.me/<username>/<msgId>` (публичный чат) либо `t.me/c/<internal_id>/<msgId>` (приватная супергруппа/канал); для «базовых» (не апгрейженных) групп Telegram не даёt постоянной ссылки в принципе — это свойство платформы, не пробел решения. Альтернатива (требовать резолва идентичности через channel-content-analysis для всех каналов) отклонена — вводит постороннюю зависимость ради одной лишь ссылки, когда нужные данные и так приходят бесплатно другим путём.

**8. Столбец заявок добавляется в текстовую таблицу буквально, не только в CSV.**
AC US-3 явно требует столбец «и в тексте, и в CSV» — несмотря на то что это расширяет узкую, специально спроектированную под мобильный экран таблицу (architecture-v2 §3). Альтернатива (CSV-only агрегат, как у этапа 5 в v2) отклонена как расхождение с буквальным требованием без явного запроса координатора на этот компромисс.

## Risks / Trade-offs

- **[Risk]** Поведение Telegram при одновременных `requested: true` + `link` в `GetChatInviteImporters` не подтверждено живым вызовом (только структурная валидность по TL-схеме GramJS) → **Mitigation**: один смоук-тест на реальном агенте с реальной ссылкой перед тем, как полагаться на цифру в проде; см. tasks.md.
- **[Risk]** Новый столбец «Заяв» увеличивает ширину текстовой таблицы против целенаправленно узкого дизайна v2 (расчёт на мобильный экран) → **Mitigation**: осознанный компромисс по буквальному AC (Decision 8); если на реальных данных таблица переносится на телефоне — отдельный follow-up (например, CSV-only), не блокирует эту реализацию.
- **[Risk]** `private_invite_links` может быть пустой на момент выката (ссылки ещё не сгенерированы для текущих активных агентов) → **Mitigation**: прочерк — штатное отображение, не ошибка; координация с оператором по вызову `tg_private_invite_links` — операционный шаг вне кода.
- **[Risk]** `daily_stats.dms_sent` становится молчаливо-нулевым полем без явной маркировки в схеме → **Mitigation**: комментарий в коде на месте записи, фиксирующий это как осознанное состояние (Decision 4), чтобы не читалось как забытый хвост при будущей работе с этой таблицей.
- **[Risk]** «Базовые» группы никогда не получат ссылку в разбивке US-5 → **Mitigation**: задокументировано как свойство типа чата в Telegram, строка всё равно включается (с пустой ячейкой ссылки) — реальный факт отправки не теряется.

## Migration Plan

Только аддитивные изменения, миграции данных не требуется:
- Новая колонка `channels.chatUsername` — аддитивная миграция по существующему приёму (`migrateChatUsernameColumn`, вызывается из `initChannels`, тот же паттерн что `migrateChannelIdentityColumns`/`migrateCoverageColumns`).
- Схемы `funnel.db` и `private-invites.db` не меняются — существующие колонки используются полнее.
- Порядок выката не завязан на состояние `private_invite_links`: при пустой таблице отчёт корректно показывает прочерки, при заполненной — реальные числа сразу.
- Откат — обычный откат кода; новая колонка безвредна, если остаётся в схеме после отката.

## Open Questions

- Подтверждение поведения `GetChatInviteImporters(requested: true, link: …)` на реальном вызове — не блокирует реализацию, блокирует доверие к цифре в первом проде-прогоне.
- Персональные ссылки для текущих активных агентов — уже сгенерированы, или требуется отдельный вызов `tg_private_invite_links` оператором после деплоя этого изменения? Не влияет на код, влияет на то, что увидит координатор в первом отчёте после выката.
