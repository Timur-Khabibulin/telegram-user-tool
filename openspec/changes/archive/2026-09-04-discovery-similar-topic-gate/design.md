## Context

`similar-channel-discovery` (см. `openspec/changes/channel-discovery-similar/`) собирает
кандидатов в `collectByLevels` (`src/core/discovery/similar.ts:185–283`) с единственным
гейтом — `min_subscribers` через `getChannelSubscribers`. Этот change добавляет в тот же
гейт две проверки и тему прогона, не трогая фазы сбора/распределения, остановку по
FLOOD_WAIT, приоритизацию seeds и реестр.

Опорные точки:
- `similar.ts:238–266` — текущий candidate-гейт (место врезки).
- `service.ts:881→785` — `getChannelSubscribers` → `getChannelSubsCount` → `GetFullChannel`;
  ответ `ChannelFull` уже содержит `participantsCount`, `linkedChatId`, `about`.
- `service.ts:900–924` — `getRecentPostViews`: образец выборки истории канала (для постов
  как fallback-сигнала темы берём `m.message` вместо `m.views`).
- `src/llm/client.ts` — `LlmClient.completeObject(opts, zodSchema)`.
- `src/llm/prompts.ts` — каталог промптов (`scoreForDM` — образец числового скоринга).

## Goals / Non-Goals

**Goals:**
- Не пускать в пул каналы без группы обсуждения (агенту некуда вступать).
- Не пускать в пул каналы не по теме прогона.
- Тему задаёт оператор; одна на прогон.
- Минимум новых MTProto-вызовов; LLM — только для прошедших дешёвые гейты.

**Non-Goals:**
- Per-agent тематика (все агенты платформы одной темы — условие прогона).
- Эмбеддинги/ключевые слова вместо LLM (выбран LLM-судья как «анализ текста»).
- Кэш оценок темы между прогонами.

## Decisions

### D1. Объединить subs + linkedChatId + about в один `getChannelGateInfo`

Гейт подписчиков уже делает `GetFullChannel` на каждого кандидата. Тот же ответ несёт
`linkedChatId` и `about`. Новый метод `getChannelGateInfo(input) →
{ subscribers, linkedChatId, about }` заменяет `getChannelSubscribers` в гейте — три
сигнала за один вызов, без роста нагрузки. FLOOD_WAIT → `FloodWaitError` (как сейчас).

### D2. Порядок гейтов — дешёвые раньше дорогих

```
кандидат
  ├─ visited / нет username / в пуле|реестре   → skip   (как сейчас)
  ├─ getChannelGateInfo → { subs, linkedChatId, about }
  │     ├─ subs == null || subs < minSubscribers   → skip (low_subscribers)
  │     └─ linkedChatId == null                     → skip (no_linked_chat)   ← НОВОЕ
  ├─ текст темы: about; если пуст/короче MIN_ABOUT_LEN → getRecentPostTexts (+1 вызов)
  │     └─ текста нет вовсе                          → skip (off_topic, fail-closed)
  ├─ scoreTopicRelevance(theme, текст) → score                                ← НОВОЕ
  │     ├─ ошибка оценки (failover исчерпан)         → skip (off_topic, fail-closed)
  │     └─ score <= minTopicScore                    → skip (off_topic)
  └─ в пул
```

Тематический гейт — последний: LLM (и возможный history-вызов) тратятся только на
кандидатов, уже прошедших порог подписчиков и проверку группы.

### D3. Сигнал темы — гибрид about → посты

Берём `about`. Если он пустой или короче `MIN_ABOUT_LEN` (≈30 символов) — подтягиваем
текст последних N постов (`getRecentPostTexts`, N≈5) и оцениваем по ним (или по
`about + посты`). Если и описания, и постов нет — оценить нечем → fail-closed skip
(`off_topic`). Дорогой history-вызов платим только при недостаточном описании.

### D4. Оценка темы — LLM числом 0..1, порог `minTopicScore`

Промпт `scoreTopicRelevance(theme, text)` → `completeObject({ score: number, reason })`
по zod-схеме (`score` в `[0,1]`). Кандидат проходит при `score > minTopicScore`
(строго больше; дефолт `0.3`). LLM как «анализ текста» согласуется с архитектурой после
рефакторинга (LLM остаётся только для генерации и анализа текста) и со спекой `llm-layer`.
`LlmClient` инжектится в `runSimilarDiscovery`/`collectByLevels` (раньше скилл был без LLM).

### D5. Fail-closed на сбое оценки

Жёсткая ошибка оценки (LLM-failover исчерпан) или отсутствие текста → кандидат **не**
попадает в пул, событие логируется и идёт в счётчик `off_topic`. Обоснование: фильтр
существует, чтобы не засорять пул; fail-open при сбое LLM вернул бы ровно тот мусор, от
которого уходим. Цена ложного пропуска — потеря одной находки (граф большой). Это не
FLOOD_WAIT — на стоп-счётчик обхода (2 подряд) ошибка оценки не влияет.

### D6. Тема и порог — операторские параметры

`theme: string` (обязателен) и `minTopicScore: number` (дефолт `0.3`) добавляются в
`SimilarParams` и пробрасываются: скилл (вопрос оператору) → скрипт (`--theme`,
`--min-topic-score`) → `RunSimilarParams` → `SimilarParams` → `collectByLevels`. Одна
тема на прогон — все агенты платформы одной тематики (условие прогона, не per-searcher).

### D7. Защита в join-queue остаётся

`joinDiscussionGroups` по-прежнему проверяет `linkedChatId` и скипает канал без группы:
канал мог потерять обсуждение между discovery и join. Discovery-гейт делает это редким,
но инвариант join-queue не ослабляем.

### D8. Счётчики отсева в отчёте

`collectByLevels` возвращает агрегаты `{ noLinkedChat, lowSubscribers, offTopic }`;
`renderSimilarReport` показывает ненулевые. Оператор видит, режет ли фильтр слишком
агрессивно (повод поднять/опустить `minTopicScore`).

### D9. Дата добавления канала в реестр (`added_at`)

В `discovered_channels` добавляется колонка `added_at` — Unix-секунды (как
`join_queue.updatedAt`, единая конвенция). Значение проставляется при вставке в
`registerChannel` (`INSERT … VALUES (…, ?)` с `Math.floor(Date.now()/1000)`); при
повторной регистрации известного канала `INSERT OR IGNORE` строку не трогает, поэтому
дата добавления неизменна (инвариант «один канал — один агент навсегда» распространяется
и на дату). Чтение/отчёт по дате — вне scope (поле копится для будущего использования).

**Миграция существующих БД.** `ensureSchema` делает только `CREATE TABLE IF NOT EXISTS`,
поэтому для уже созданных `discovery.db` колонку добавляем аддитивно: проверить через
`PRAGMA table_info(discovered_channels)`, при отсутствии `added_at` — `ALTER TABLE
discovered_channels ADD COLUMN added_at INTEGER NOT NULL DEFAULT 0`. Старые строки
получают `0` (дата неизвестна), новые — реальный timestamp. Дроп/перезапись строк
запрещены (обратимость, реестр общий).

Колонка `channel-registry` — отдельная способность, чья спека пока живёт в неархивированном
`channel-discovery` (baseline в `openspec/specs/` ещё нет), поэтому здесь это `ADDED`-дельта,
а не `MODIFIED`.

## Risks / Trade-offs

- **LLM-вызов на кандидата** удлиняет прогон и нагружает общий лимит Plus. Mitigation:
  гейт темы — последний (только прошедшие subs+chat), primary codex $0, failover на
  лимите (`llm-layer`).
- **Fail-closed теряет находки** при сбое LLM. Mitigation: сбой редок (failover);
  потеря обратима (следующий прогон), пул обычно велик.
- **`about` ненадёжен как сигнал** (пустой/мусорный). Mitigation: fallback на посты (D3).
- **Порог 0.3 — эвристика.** Mitigation: параметр, крутится по факту прогонов; счётчики
  отсева в отчёте дают обратную связь.

## Open Questions

Нет — три развилки согласованы с владельцем: тема задаётся оператором (одна на прогон,
все агенты одной темы); сигнал гибридный (about → посты); оценка LLM числом 0..1 с
порогом `minTopicScore` (дефолт 0.3, параметр) и fail-closed на сбое.

## v2 — уточнение тематического гейта (2026-06-22)

Контекст: после прогонов оператор зафиксировал, что гейт пропускает каналы не по теме
даже на пороге `0.4`. Разбор (см. `proposal.md` "v2") — два дефекта: сигнал темы строится
по одному случайному куску текста, а шкала описывает «похожесть», не долю контента, и
допускает смежные каналы в зоне, которая формально проходит дефолтный порог.

### D10. Посты — всегда, число постов N — параметр оператора

Убирается условие `text.length < MIN_ABOUT_LEN` как триггер запроса постов
(`scoreCandidateTopic`, `similar.ts:130-158`): `about` + N последних постов
(`getRecentPostTexts(channel, n)`) запрашиваются для **каждого** кандидата, прошедшего
гейты подписчиков и группы, независимо от длины `about`. N добавляется в `SimilarParams`
(`topicPostsCount: number`), дефолт `10`, валидация `N > 2` (агрегация по 1-2 постам
не даёт значимого сигнала о канале в целом). Проброс — как у прочих параметров оператора:
скилл → скрипт (`--topic-posts-n`, опционален) → `RunSimilarParams` → `SimilarParams`.

**Trade-off:** отступление от цели «минимум новых MTProto-вызовов» (см. Goals выше) —
осознанно, в пользу точности гейта; действует только на кандидатов, уже прошедших дешёвые
гейты подписчиков/группы, не на весь граф обхода.

### D11. Промпт — тезисы по постам → тема канала + score (один вызов)

`scoreTopicRelevance(theme, about, posts: string[])` (новая сигнатура, было
`(theme, text: string)`) формулирует два шага внутри одного `completeObject`-вызова:
1. Тезис по каждому посту — короткая фраза, о чём он.
2. По `about` + тезисам в совокупности — `channelTopic` (тема канала, несколько слов) и
   `score` (доля контента канала, относящаяся к теме прогона).

Один LLM-вызов на кандидата, как в v1 — расход не растёт, меняется только содержание
промпта и схемы ответа. `topicSchema` дополняется: `theses: string[]`,
`channelTopic: string`, `score: number`, `reason: string` (как было, не используется,
не убирается — см. D13).

### D12. Новая шкала — доля контента по теме (не «похожесть»)

Заменяет 3-ступенчатую шкалу v1 (`0.8–1.0` / `0.4–0.7` / `0.0–0.3`):

- `0.8–1.0` — почти весь контент канала: по заданной теме
- `0.5–0.7` — заметная часть контента: по теме, но не доминирует
- `0.2–0.4` — смежная сфера: тема затрагивается частично, канал в основном о другом
- `0.0–0.1` — контент канала не относится к теме

### D13. Порог `minTopicScore` — дефолт `0.3 → 0.5`

Дефолт `0.3` лежал внутри диапазона `0.2–0.4` («смежная сфера, контент по факту не об
этом») — формально допускающей зоны новой шкалы. Без подъёма порога смена шкалы не дала
бы эффекта: канал, явно помеченный LLM как «не об этом», проходил бы гейт. Новый дефолт —
`0.5` (нижняя граница «заметная часть контента — по теме»). Порог остаётся операторским
параметром (`--min-topic-score`), `0.5` — только дефолт.

### D14. Лог — только принятые кандидаты, с темой канала по LLM

Текущий лог (`+1 «...» в пул (тема {score}; …)`) показывает только число. Дополняется
`channelTopic` для визуальной калибровки порога оператором (сравнить тему прогона с тему
канала, которую увидела LLM). Пишется **только для принятых** кандидатов (`score >
minTopicScore`) — отклонённые остаются без подробного лога, как в v1 (`skips.offTopic`
инкрементируется молча). Канал без постов и пустым `about` фейлится естественно через
существующий fail-closed (`text.trim() === "" → null`), отдельная ветка не нужна. Через
существующий `Logger` → journald, без новых файлов/БД (`docs/operation.md`: «отдельных
файлов логов нет»). `reason` сохраняется в схеме ответа LLM, но не входит в лог-строку.
