## Why

`channel-discovery-similar` отбирает кандидатов **только** по `min_subscribers`. Из-за
этого в пул попадают каналы, бесполезные агенту:

- **Нет группы обсуждения.** Агент вступает в *discussion-группу* канала, а не в сам
  broadcast. Канал без linked-чата вступить некуда — он доходит до `join-queue` и там
  скипается (`service.ts:645–651`, `no linked discussion group`), уже потратив слот
  `target`. Целевое число *реально вступивших* каналов недобирается.
- **Дрейф темы.** BFS по `getChannelRecommendations` от рекомендации к рекомендации
  уводит от исходной тематики; off-topic каналы проходят гейт подписчиков и засоряют пул.

Оба сигнала уже почти в руках: `getChannelSubscribers` под капотом делает
`channels.GetFullChannel`, ответ которого несёт ещё и `linkedChatId`, и `about` —
сейчас они отбрасываются.

## What Changes

- **Гейт «есть группа обсуждения»** в `collectByLevels`: кандидат без `linkedChatId`
  в пул не попадает. Бесплатно — поле берётся из того же `GetFullChannel`, что и
  число подписчиков (объединяем в один метод `getChannelGateInfo`).
- **Тематический гейт** в `collectByLevels`: LLM оценивает релевантность кандидата
  теме прогона числом `0..1`; кандидат проходит при `score > minTopicScore`
  (дефолт `0.3`, fail-closed). Сигнал — гибрид: `about` канала, а при пустом/слишком
  коротком описании — текст нескольких последних постов (+1 history-вызов только тогда).
- **Тема — операторский параметр `theme`** (обязателен). Одна тема на весь прогон (все
  агенты платформы одной тематики). Проброс — как у `min_subscribers`/`engagementWindowDays`:
  скилл → скрипт → `RunSimilarParams` → `SimilarParams` → `collectByLevels`.
- **Порог `minTopicScore`** — операторский параметр, дефолт `0.3`, строго `>`.
- **Fail-closed.** Жёсткая ошибка оценки темы (LLM-failover исчерпан, нет текста для
  оценки) → кандидат пропускается (не в пул). Сбой фильтра не засоряет пул off-topic.
- **Новый промпт `scoreTopicRelevance`** в `llm-layer`: `completeObject` со схемой
  `zod` `{ score: number, reason: string }`.
- **Отчёт** дополняется счётчиками отсева: нет группы / тема ниже порога / мало
  подписчиков — чтобы оператор видел, насколько агрессивно режет фильтр.
- **Дата добавления в реестре.** В `discovered_channels` добавляется колонка `added_at`
  (Unix-секунды), проставляется при первой регистрации канала и не меняется при повторе.
  Существующие `discovery.db` мигрируются аддитивно (`ALTER TABLE … ADD COLUMN`).

Защитная проверка `linkedChatId` в `joinDiscussionGroups` **остаётся** (канал мог
потерять группу между discovery и join); теперь до неё почти не доходит.

Вне scope: per-agent тематика (все агенты одной темы — D-решение прогона), эмбеддинги
и нечёткие эвристики (выбран LLM-судья), кэш оценок между прогонами.

## Impact

- **Изменяемые способности:** `similar-channel-discovery` (отбор кандидатов, параметры
  запуска, отчёт), `llm-layer` (каталог промптов), `channel-registry` (колонка `added_at`).
- **Новый код:** `TelegramService.getChannelGateInfo` (subs + linkedChatId + about из
  одного `GetFullChannel`), `TelegramService.getRecentPostTexts` (fallback-сигнал темы),
  промпт `scoreTopicRelevance`, гейты + проброс `theme`/`minTopicScore` + счётчики
  отсева в `similar.ts`, вопросы оператору в скилле и аргументы скрипта.
- **LLM-нагрузка:** один `completeObject` на кандидата, прошедшего гейты подписчиков и
  группы. Primary — codex OAuth ($0), failover на лимите (`llm-layer`). `similar.ts`
  получает `LlmClient` (раньше скилл был без LLM — теперь зависит от `llm-layer`).
- **MTProto-нагрузка:** `getChannelGateInfo` заменяет `getChannelSubscribers` без роста
  числа вызовов; `getRecentPostTexts` — только для кандидатов с пустым `about`.
- **Хранилище:** без изменений (новых таблиц/БД нет).

## v2 — уточнение тематического гейта (2026-06-22)

После прогонов на пороге `min_topic_score = 0.4` оператор зафиксировал: гейт пропускает
каналы, не относящиеся к теме. Причина — два независимых дефекта исходной версии:

1. **Сигнал темы — один случайный кусок текста.** Посты подтягивались только при пустом
   `about`, весь текст уходил в LLM одним блоком → одна оценка по случайной выборке, не по
   каналу в целом (один нетипичный пост мог определить оценку).
2. **Шкала описывала «похожесть», а не долю контента.** Диапазон `0.4–0.7` («тема
   затрагивается, но канал шире или смежен») по формулировке сам допускал смежные/широкие
   каналы — дефолтный порог `0.3` лежал внутри допускающей зоны.

**What changes (v2):**

- Сигнал темы: `about` + N последних постов — **всегда** (убирается условие «только при
  коротком `about`»). N — параметр оператора скилла (см. `tasks.md` §8), дефолт `10`,
  валидация `N > 2`.
- Промпт `scoreTopicRelevance` — два шага внутри одного вызова: тезис по каждому посту →
  `channelTopic` (тема канала, несколько слов) + `score` по новой шкале.
- Новая шкала score — по доле контента канала, относящейся к теме (не «похожесть»):
  `0.8–1.0` почти весь контент по теме / `0.5–0.7` заметная часть, не доминирует /
  `0.2–0.4` смежная сфера, контент по факту не об этом / `0.0–0.1` не по теме.
- `min_topic_score` дефолт поднят `0.3 → 0.5` — порог должен лежать за пределами «смежной»
  зоны (`0.2–0.4`), иначе смена шкалы не даёт эффекта на дефолтных настройках.
- Лог: только принятые кандидаты, по каждому — тема прогона, `channelTopic`, `score`,
  ссылка на канал (через существующий `Logger` → journald, без новых файлов/БД). Отклонённые
  кандидаты остаются без подробного лога (только счётчик `offTopic`, как в v1).
- `reason` в схеме ответа LLM сохраняется как есть (не логируется, не убирается).

**Trade-off:** посты теперь тянутся всегда (не только при коротком `about`) → +1
MTProto-вызов на каждого кандидата, прошедшего гейты подписчиков и группы (это
действует только на кандидатов, уже отбракованных дешёвыми гейтами, не на весь граф).
Осознанно отступает от исходной цели «минимум новых MTProto-вызовов» в пользу точности
гейта.
