## Why

За последние 30 дней 419 из 426 OOM-килов на VPS пришлись на процессы `tg-agent@<agentId>.service` (диспетчер агента, `src/scripts/dispatcher.ts`), убиваемые cgroup-лимитом `tg-agents.slice` (`MemoryMax=2G`, хост — 4 ГБ RAM). Планируется рост флота до 150 агентов с переходом мониторинга на период 3ч, что резко повышает плотность одновременных «тяжёлых» прогонов диспетчера. Сейчас нет никаких фактических данных о том, сколько памяти реально потребляет один прогон диспетчера — решения про `MemoryMax`, размер слайса или ограничение параллелизма принимаются по косвенным признакам (число каналов у агента, частота OOM-килов по `journalctl`). Нужны прямые измерения пиковой памяти прогона, чтобы обоснованно закладывать лимиты.

## What Changes

- Диспетчер (`src/scripts/dispatcher.ts`) после обработки всех назревших задач прогона измеряет пиковую резидентную память процесса (`process.resourceUsage().maxRSS`) и записывает её в новую таблицу.
- Новая таблица `dispatcher_runs` в per-agent `tasks.db` — одна строка на один прогон процесса диспетчера (не на каждый скилл): `agentId`, `startedAt`, список выполненных типов задач (`taskTypes`), пиковая память (`peakRssKb`).
- Единица измерения — **процесс целиком**, а не отдельный скилл: это та же сущность, которую убивает cgroup OOM-killer, поэтому измеряется на том же уровне. Декомпозиция по отдельным скиллам в рамках одного прогона не производится (при нескольких задачах в одном прогоне такая декомпозиция даёт смещённые числа, т.к. `maxRSS` монотонна).
- Запись выполняется один раз в конце прогона; данные собираются как сырые записи для последующего ручного анализа (SQL-запросы, `journalctl` для инцидентов) — без встроенной агрегации/отчётности и без отслеживания упавших/OOM-килнутых прогонов (если процесс убит OOM, строка просто не появится).

## Capabilities

### New Capabilities
- `dispatcher-run-memory`: запись пиковой памяти каждого прогона диспетчера агента в новую таблицу `dispatcher_runs`, для последующего ручного анализа расхода памяти по флоту.

### Modified Capabilities
(нет — существующая таблица `runs`/capability `run-log` не меняется)

## Impact

- `src/scripts/dispatcher.ts` — один дополнительный замер и вызов записи в конце `main()`.
- Новый модуль в `src/core/db/` (схема + функция вставки `dispatcher_runs`), по аналогии с `src/core/db/runs.ts`.
- Хранение — существующий файл `~/.openclaw/workspace-<agentId>/tasks.db`, новая таблица, без изменения существующих таблиц `tasks`/`runs`.
- Поведение системы (расписание, обработка задач, отчёты в Saved Messages) не меняется — чисто observability-изменение.
