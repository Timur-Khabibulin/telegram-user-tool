## ADDED Requirements

### Requirement: Запись пиковой памяти прогона диспетчера

Диспетчер SHALL после обработки всех назревших задач прогона (после цикла `for (const task of due)`, до завершения `main()`) измерить пиковую резидентную память процесса через `process.resourceUsage().maxRSS` и записать одну строку в таблицу `dispatcher_runs` (в той же per-agent БД, что и `tasks`/`runs`): `agentId`, `startedAt` (Unix-секунды начала прогона), `taskTypes` (типы выполненных задач через запятую, в порядке выполнения), `peakRssKb` (измеренное значение). Замер SHALL быть единственным за прогон — без раздельного измерения по каждой задаче внутри прогона.

#### Scenario: Прогон с одной задачей
- **WHEN** диспетчер выполнил одну назревшую задачу и завершает `main()`
- **THEN** в `dispatcher_runs` появляется одна строка с `taskTypes`, содержащим один тип задачи, и `peakRssKb`, отражающим пиковую память всего процесса

#### Scenario: Прогон с несколькими задачами
- **WHEN** диспетчер выполнил несколько назревших задач подряд в одном прогоне
- **THEN** в `dispatcher_runs` появляется одна строка на весь прогон, `taskTypes` перечисляет все выполненные типы через запятую, `peakRssKb` — один пик на весь прогон (без разбивки по отдельным задачам)

#### Scenario: Холостой прогон не пишет строку
- **WHEN** у агента нет назревших задач (`due.length === 0`) и диспетчер завершается без подключения к Telegram
- **THEN** строка в `dispatcher_runs` не создаётся

### Requirement: Сбой записи не прерывает прогон

Запись строки в `dispatcher_runs` SHALL не прерывать выполнение диспетчера при сбое (ошибка БД, недоступность файла): диспетчер SHALL залогировать ошибку и продолжить штатное завершение прогона (отправка отчётов, `disconnect`, выход).

#### Scenario: БД недоступна на запись
- **WHEN** запись в `dispatcher_runs` бросает исключение
- **THEN** диспетчер логирует ошибку и завершает прогон штатно, без падения процесса из-за этой ошибки

### Requirement: Идемпотентная схема `dispatcher_runs`

Модуль работы с `dispatcher_runs` SHALL предоставлять идемпотентное создание схемы (аналогично `ensureRunsSchema`/`ensureTasksSchema`): таблица создаётся, только если её ещё нет, без ошибок при повторном вызове.

#### Scenario: Повторное создание схемы
- **WHEN** функция создания схемы `dispatcher_runs` вызывается повторно на уже существующей таблице
- **THEN** таблица не пересоздаётся и не возникает ошибки
