## Context

Диспетчер (`src/scripts/dispatcher.ts`) — один процесс на прогон агента (`tg-agent@<agentId>.service`, systemd, тик раз в 10 минут). За один прогон `main()` последовательно выполняет все назревшие задачи (`for (const task of due)`), затем завершается. cgroup `tg-agents.slice` ограничивает суммарную память всех процессов агентов (`MemoryMax=2G` на хосте с 4 ГБ RAM); при превышении OOM-killer убивает конкретный процесс `tg-agent@<agentId>.service` целиком.

Существующая таблица `runs` (`src/core/db/runs.ts`, capability `run-log`) уже пишет по строке на каждый вызов скилла (`durationMs`, `llmCalls`, `status`) — но не память. Эта гранулярность (строка на скилл) не подходит для памяти: см. Decisions.

## Goals / Non-Goals

**Goals:**
- Получить фактические цифры пиковой памяти прогона диспетчера, на том же уровне сущности, которую убивает OOM-killer (процесс `tg-agent@<agentId>.service` целиком).
- Сохранить данные так, чтобы их можно было разобрать вручную (SQL-запросы, сопоставление с `journalctl -k` по инцидентам) при принятии решений про `MemoryMax`/ограничение параллелизма.

**Non-Goals:**
- Разложение памяти по отдельным скиллам внутри одного прогона (было рассмотрено и отклонено — см. Decisions).
- Автоматическая агрегация/отчётность (avg/p95/max, дашборды, периодические отчёты) — данные собираются, анализ по ним не автоматизируется в рамках этого изменения.
- Отслеживание прогонов, убитых OOM (строка `started` + сверка с `journalctl` из кода) — если процесс убит, строка в `dispatcher_runs` для этого прогона просто не появится. Осознанно принятое ограничение.
- Разделение «базовой» памяти (старт `tsx`, загрузка зависимостей) и «памяти под нагрузкой» — не имеет смысла на уровне процесса целиком: OOM-killer тоже не разделяет.

## Decisions

### Единица измерения — процесс целиком, не отдельный скилл

Рассматривались два уровня измерения:
1. **По скиллу** — `process.resourceUsage().maxRSS` до/после каждого `skill(ctx)` внутри цикла `for (const task of due)`, дельта пишется в существующую таблицу `runs`.
2. **По процессу** — один замер `maxRSS` в конце `main()`, после всех задач прогона.

Выбран вариант 2. Причины:
- `maxRSS` монотонно неубывает с момента старта процесса. Если в одном прогоне выполняется несколько задач подряд, а первая толкнула пик выше, чем когда-либо достигнет вторая, дельта второй задачи покажет заниженное или нулевое значение — задача «прячется в тени» пика предыдущей. Это системное смещение, не шум, который усредняется на большой выборке.
- OOM-killer принимает решение по суммарной памяти cgroup процесса `tg-agent@<agentId>.service` целиком, а не по вкладу отдельного скилла. Чтобы измеренное число было напрямую сопоставимо с порогом `MemoryMax`, нужно мерить ту же сущность.
- Цена: точная привязка «этот пик — от такого-то типа задачи» возможна только для прогонов с одной задачей (`taskTypes` содержит один элемент); для прогонов с несколькими задачами пик общий на все. Это приемлемо, так как основная цель — capacity planning (сколько памяти закладывать на процесс), а не профилирование конкретного скилла.

### Отдельная таблица `dispatcher_runs`, не колонка в `runs`

`runs` построена на гранулярности «строка на вызов скилла» — то есть один прогон с несколькими задачами даёт несколько строк `runs`, но только один пик памяти на весь прогон. Добавление колонки `peakRssKb` в `runs` означало бы дублирование одного и того же числа на все строки одного прогона (или запись только в последнюю строку — неявно и легко сломать при рефакторинге). Отдельная таблица с гранулярностью «строка на прогон процесса» — точнее отражает природу данных и не проектирует стороннюю бизнес-логику на существующую схему `runs`.

### Замер — один раз в конце `main()`, без варианта «до/после»

Поскольку измеряется процесс целиком, а не дельта по задаче, замер «до» не нужен: `process.resourceUsage().maxRSS`, прочитанный один раз после `for`-цикла (перед/внутри `finally { await tg.disconnect(); }`), уже включает весь путь процесса — старт `tsx`, загрузку зависимостей, `tg.loadAccount`, выполнение всех задач. Это соответствует Non-Goal «не разделять базовую память и память под нагрузкой».

### Список типов задач как контекст, не как ключ группировки в БД

`taskTypes` хранится текстом через запятую (взят из уже существующего `due.map((t) => t.type)`, который и так логируется в stdout). Не выносится в отдельную таблицу связей (`dispatcher_runs_tasks`) — избыточно для текущей цели (ручной разбор через SQL, `taskTypes LIKE '%monitor%'` достаточно; нормализация не даёт выгоды без встроенной агрегации, которая явно вне объёма).

## Risks / Trade-offs

- **[Риск] Прогоны, убитые OOM, не оставляют следа** → Осознанно принято (Non-Goals). Разбор конкретных инцидентов остаётся ручным через `journalctl -k` (уже отработанный процесс в этом проекте) — по агенту и времени, без привязки к типу задачи.
- **[Риск] Для прогонов с несколькими задачами пик нельзя отнести к конкретному типу** → При анализе фильтровать по `taskTypes` без запятой (один тип за прогон) для чистого сигнала по типу задачи.
- **[Trade-off] Нет автоматической агрегации** → Осознанно вне объёма; данные собираются, отчётность — отдельное решение при необходимости.

## Migration Plan

- Новая таблица создаётся идемпотентно (`CREATE TABLE IF NOT EXISTS`), как и существующие `tasks`/`runs` — не требует ручной миграции существующих `tasks.db` на агентах, схема применяется при первом прогоне диспетчера после деплоя.
- Деплой — обычный (scp правленых файлов на VPS, как и предыдущие изменения в этом репозитории — коммитов не было больше месяца, правки идут напрямую).
- Откат — безопасен: таблица `dispatcher_runs` независима, её отсутствие/удаление не влияет на работу диспетчера (запись в неё не должна прерывать прогон при сбое — см. tasks.md).

## Open Questions
