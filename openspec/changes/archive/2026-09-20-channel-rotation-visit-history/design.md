## Context

Полное проектирование — `docs/design/channel-rotation/architecture-v2.md` (парный к
`requirements-v2.md`). Здесь — сжатая выжимка для имплементации. Текущее состояние:
`plan.ts` раскладывает round-robin по нагрузке (`countActiveChannels`), курсор
двигается ради размазывания нагрузки внутри прогона.

## Goals / Non-Goals

**Goals:**
- Заменить правило выбора целевого агента: нагрузка → visit-count.
- Сохранить `plan.ts` чистым (без I/O) и покрыть тестом.

**Non-Goals:**
- Изменение сбора кандидатов, группировки по персоне, переноса назначения, таймера.
- Батч-оптимизация запросов истории (преждевременно при суточном прогоне).

## Decisions

- **Выбор per-candidate, без курсора.** v2 убирает нагрузку; каждый кандидат — свой
  канал со своей историей (`chat_id`), назначения других кандидатов в прогоне на его
  visit-count не влияют. Значит курсор round-robin, сортировка целей и
  `attempts`-обход в `plan.ts` не нужны — `plan.ts` упрощается до: для кандидата
  взять активные цели минус источник, найти минимальный visit-count, случайно выбрать
  среди равных.
- **`plan.ts` остаётся чистым.** visit-count передаётся готовой структурой из
  `run.ts` — `Map<chatId, Map<agentId, number>>`; отсутствие агента в карте = 0
  (нули не материализуем).
- **Запрос истории — новая `getChannelVisitCounts(admin, chatId, persona)`** в
  `channel-operations.ts` (один факт — один дом), зеркало `getOwnershipTimeline`:
  тот же мост `chat_id↔canonical_link`, фильтр `persona`, `GROUP BY newAgentId` по
  `type='assigned'`. Per-channel вызов (индекс `idx_ops_chat_type_ts`), N в десятки —
  дёшево; батч отклонён как преждевременная оптимизация.
- **Тай-брейк — `Math.random()`** inline (прецедент уже в `plan.ts`); тест проверяет
  «результат ∈ множеству минимальных не-источников», а не конкретного агента.
- **`countActiveChannels` удаляется** — после снятия нагрузки её единственный
  потребитель (`run.ts`) отпадает (проверено grep'ом).
- **Сортировка кандидатов по `statusUpdatedAt`** в `plan.ts` убирается — без курсора
  порядок нейтрален.

## Risks / Trade-offs

- [Журнал операций с ~2026-09-12 — ранняя история не видна] → канал может уйти агенту,
  где он был до журнала; редко, приемлемо (требования §4).
- [`assigned` пишет и ротация, и распределение] → обе считаются «посещением»; это
  корректно для цели «был ли канал у агента».
- [Per-channel запросы] → N индексированных чтений на прогон; при суточной ротации и
  десятках кандидатов — незначительно.

## Migration Plan

- Миграций БД нет. visit-count читается из существующего журнала операций.
- Выкладка неразрывна: первый же прогон новой логики использует накопленную историю
  `assigned`; при пустой истории (все 0) — случайный выбор среди не-источников (круг 1),
  что не хуже прежнего.
