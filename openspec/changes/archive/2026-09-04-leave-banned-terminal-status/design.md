## Context

`leave-banned-channels` (`leave-banned-human-pacing`, реализован) читает
очередь `channels.status IN ('banned', 'should_leave')`
(`getLeaveQueue`, `src/core/db/channels.ts:1270`), выходит из канала
(`leaveChannel`), чистит `dm_candidates` (`purgeChannelData`) и сбрасывает
статус в `NULL` (`resetChannelStatus`) — одинаково для обоих триггеров.

`should_leave` документирован как «вручную оператором (вне скоупа этого
модуля)» — спроектированный, но пока никем не используемый триггер.

`getChannelsBatch` (общий источник для `monitor`/`monitor-v2`/`monitor-v5`,
`src/core/db/channels.ts:354`) — blocklist:
`WHERE (lastProcessedAt ...) AND (status IS NULL OR status NOT IN ('banned', 'suspend'))`.
`getPostWatchChannels` (monitor-v3/v4/v5, `src/core/db/channels.ts:610`) —
allowlist: `WHERE channelUsername IS NOT NULL AND (status IS NULL OR status IN ('format_error', 'only_comment'))`.

`channels`-строка синхронизируется с живыми Telegram-диалогами
(`syncChannels`): агент, переставший быть участником канала, теряет строку
целиком на следующем полном синке (`toRemove`). Терминальные статусы этого
change живут только в окне между выходом и следующим синком — после синка
строка (и статус вместе с ней) исчезает, что эквивалентно «не обрабатывать».

Сегодняшнее перераспределение каналов (round-robin по CSV) обновило
`discovery.db`/`join_queue`, но не тронуло `channels` (реальное членство в
Telegram) — у части агентов там остались каналы прежнего распределения.

## Goals / Non-Goals

**Goals:**
- Терминальный статус после успешного выхода различает происхождение:
  `'banned'` → `'leaved_from_banned'`, `'should_leave'` → `'leaved_manual'`.
- `getChannelsBatch` не выбирает каналы с этими статусами.
- Разовая миграция: 46 явно перечисленных агентов — проставить `should_leave`
  каналам, отсутствующим в `join_queue`, включить `leave-banned`.

**Non-Goals:**
- Не проектируется общий механизм сверки `channels` ↔ `join_queue` как
  постоянная способность (только разовый скрипт под конкретный список).
- Не меняется поведение `getPostWatchChannels` (уже корректно исключает по
  построению).
- Не меняется `'banned'`-триггер (кто и когда его ставит) — только то, что
  происходит ПОСЛЕ успешного выхода.

## Decisions

### Decision 1 — Два терминальных статуса, не один

Рассматривали единый `'leaved'` на оба триггера. Отклонено: теряется различие
между «канал сам забанил агента» и «оператор/система решили уйти сами» —
это разные факты с разной потенциальной диагностической ценностью (например,
подсчёт `'leaved_from_banned'` за период — это фактически то же самое, что
раньше делал `countRecentlyBannedChannels`, но без временного окна). Два
значения ничего не стоят дороже одного на уровне реализации (обе — просто
строки в blocklist).

### Decision 2 — `getLeaveQueue` возвращает исходный `status`

Функция уже читает `status` в `WHERE`, но не отдаёт его наружу. Минимальное
расширение интерфейса (`LeaveQueueRow.status: 'banned' | 'should_leave'`) —
без него скилл не может выбрать терминальный статус.

### Decision 3 — `resetChannelStatus` → параметризованная функция

Переименование/замена на функцию, принимающую целевой статус явно (а не
жёстко `NULL`). `statusUpdatedAt` = время завершения выхода (не `NULL`) —
терминальный статус получает осмысленное время для `ORDER BY` в
диагностических выборках (например, «сколько каналов ушли по банy за
сутки»). `statusDurationSeconds`/`status_description` — `NULL`, эти поля
были про классификацию ДО выхода, после выхода не несут смысла.

### Decision 4 — Миграция: сравнение по `channelUsername`, не по `chatId`/`chatUsername`; неприкреплённые группы — тоже `should_leave`

`channels.chatId` — внутренний Telegram ID, `join_queue.link` — каноническая
ссылка (`https://t.me/<username>`) на исходный **канал**. Правильный общий
ключ — `channels.channelUsername` (username **привязанного** broadcast-канала,
не `chatUsername` — той для самого чата/группы обсуждения, другая сущность),
нормализованный через `normalizeChannelLink` тем же способом, что и
`join_queue.link`.

**Инцидент во время apply**: изначально сравнение делалось по `chatUsername`.
Рассуждение было ошибочным — `join-queue` вступает не в сам канал, а в его
группу ОБСУЖДЕНИЯ (`joinDiscussionGroups`, `service.ts:1307`); после
вступления `channels`-строка получает `channelUsername` = username исходного
канала из `join_queue.link`, а `chatUsername` = username самой группы
обсуждения (обычно совсем другое имя, см. пример в коде — `letachat`/
`withlera_sh`). Сравнение по `chatUsername` дало **0 совпадений на всех 46
агентах** — сам этот факт (не единичная аномалия, а нулевые совпадения
абсолютно везде) должен был сразу навести на мысль о неверном поле, но был
обнаружен только после ручной проверки пользователем. Поле исправлено на
`channelUsername`.

**Последствие ошибки**: пока баг не был найден, `leave-banned` успел
физически покинуть 204 из 227 каналов, ошибочно помеченных `should_leave`
(они на самом деле входили в новое распределение). Откат статуса в БД
Telegram-членство не восстанавливает — эти 204 канала возвращены в
`join_queue.status='pending'` отдельным разовым запросом (не скриптом,
однострочный SQL через `ATTACH DATABASE`), чтобы `join-queue` вступил в них
заново.

Отдельно: первая версия также пропускала каналы с `channelUsername IS NULL`
(нет привязанного канала) как «нет надёжного способа сравнить». Это тоже
было ошибочным — `join_queue.link` физически не может содержать такую
группу, значит вывод «не в очереди» верен безусловно (кроме случая
`channelResolved=0`, когда сама идентичность ещё не резолвлена монитором —
такие каналы пропускаются, а не помечаются, до следующего резолва).

### Decision 5 — Миграция: разовый скрипт, удалён после использования

Список из 46 `agentId` был захардкожен в `mark-should-leave-reassigned.ts`
(по аналогии с `activate-leave-banned-for-agents.ts` — прецедент
`leave-banned-human-pacing`, где такой скрипт остался в репозитории).
Для этой миграции пользователь решил иначе: скрипт удалён из репозитория и с
VPS сразу после использования — прецедент не соблюдён по прямому запросу
(«зачем ты делал скрипт, если он разовый? удали его»). Если понадобится
повторить операцию для другого списка агентов — писать заново, не
восстанавливать удалённый.

## Migration Plan

1. Задеплоить код (`ChannelStatus`, `getLeaveQueue`, замена
   `resetChannelStatus`, `getChannelsBatch` blocklist).
2. Прогнать разовый скрипт по 46 агентам: для каждого канала со `status IS
   NULL` и `channelResolved=1` — сравнить нормализованный `channelUsername` с
   нормализованными `join_queue.link` этого агента и пометить
   `should_leave`, только если не нашёлся (`channelUsername IS NULL` —
   помечать безусловно). Каналы `channelResolved=0` и каналы с уже другим
   активным статусом — не трогать.
3. Включить задачу `leave-banned` тем из 46, у кого она ещё не `enabled=1`
   (`createOrUpdateTask`, сохраняя существующее расписание там, где строка
   уже есть — тот же приём, что при недавнем включении `leave-banned`/
   `monitor-v5`/`join-queue` этим же агентам). Аналогично включить
   `join-queue` тем из 46, у кого её не было.
4. Дальше `leave-banned` сам, по своему расписанию (180 мин, лимит 20/прогон,
   человекоподобный пейсинг) разберёт накопленную очередь — растянуто во
   времени (сотни каналов на некоторых агентов, см. proposal.md).
5. После инцидента (Decision 4) — проверить весь текущий `should_leave`/
   `leaved_manual` на пересечение с `join_queue` по `channelUsername`;
   найденные пересечения вернуть в `NULL`, а каналы, уже физически
   покинутые (`leaved_manual`) из числа найденных — вернуть в
   `join_queue.status='pending'` для повторного вступления.

## Open Questions

  change — если понадобится, отдельная задача чтения этих статусов для
  отчётности.
