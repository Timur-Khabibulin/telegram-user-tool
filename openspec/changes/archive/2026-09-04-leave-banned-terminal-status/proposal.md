## Why

`leave-banned-channels` (`leave-banned-human-pacing`) сейчас после успешного
выхода из канала одинаково сбрасывает `channels.status` в `NULL` для обоих
триггеров очереди — `'banned'` (канал сам забанил агента) и `'should_leave'`
(оператор решил, что канал больше не нужен). После сброса в `NULL` строка
`channels` неотличима от «канал никогда не имел проблемного статуса» — до
следующей полной синхронизации (`syncChannels`), которая физически удалит
строку, потому что агент больше не участник. В этом окне другие скиллы
(`monitor`/`monitor-v2`/`monitor-v5` через `getChannelsBatch`) видят канал как
обычный и могут попытаться его обработать (прочитать/ответить), хотя агент из
него уже вышел — бессмысленная и потенциально ошибочная попытка.

Отдельно: сегодняшнее перераспределение каналов между агентами (round-robin по
готовому CSV, `discovery.db`/`join-queue` уже обновлены) оставило хвост — у
части агентов в `channels` (tg-channels.db, реальные Telegram-диалоги) остались
каналы из **прежнего** распределения, которых больше нет в их новой
`join_queue`. Их нужно физически покинуть. Готового механизма «канал есть в
`channels`, но не в `join_queue`» → выход не существует;
`should_leave` — уже спроектированный (`leave-banned-human-pacing`), но пока
ничем не используемый триггер именно под ручное/внешнее решение «этот канал
агенту больше не нужен».

## What Changes

- `ChannelStatus` вместо единого сброса в `NULL` после выхода получает два
  новых терминальных (постоянных, не автоматически снимаемых) значения:
  - `'banned'` → после успешного `leaveChannel` → `'leaved_from_banned'`
  - `'should_leave'` → после успешного `leaveChannel` → `'leaved_manual'`
  Терминальный статус зависит от исходного триггера очереди — не единое
  поведение.
- `getLeaveQueue` дополнительно возвращает исходный `status` строки (нужен
  скиллу, чтобы выбрать терминальный статус).
- `resetChannelStatus` заменяется на функцию, принимающую целевой статус
  (`'leaved_from_banned' | 'leaved_manual'`) вместо жёстко зашитого `NULL`;
  `statusUpdatedAt` проставляется временем завершения выхода,
  `statusDurationSeconds`/`status_description` сбрасываются в `NULL` (эти поля
  были про исходную пред-выходную классификацию, после выхода не актуальны).
- `getChannelsBatch` (общий источник каналов для `monitor`/`monitor-v2`/
  `monitor-v5`) исключает оба новых статуса из выборки, помимо уже
  исключаемых `'banned'`/`'suspend'`.
- `getPostWatchChannels` (monitor-v3/v4/v5, комментирование постов) — без
  изменений: уже allowlist (`NULL`/`'format_error'`/`'only_comment'`), новые
  статусы туда не попадают по построению.
- Разовая (не переиспользуемая, не новая постоянная способность) миграция:
  для явно перечисленного списка из 46 агентов (тех же, что получили сегодня
  новое распределение каналов) — по каждому агенту сравнить `channels.chatUsername`
  (tg-channels.db) с `join_queue.link` (tg-join-queue.db, нормализованный) и
  проставить `should_leave` каналам, которых нет в `join_queue`; включить
  задачу `leave-banned` этим агентам (если ещё не включена).

## Capabilities

### Modified Capabilities

- `leave-banned-channels`: терминальный статус после выхода зависит от
  исходного триггера (`'leaved_from_banned'` / `'leaved_manual'` вместо
  единого сброса в `NULL`). Нормативная спека ещё не заархивирована —
  ближайший источник истины: `openspec/changes/leave-banned-human-pacing/specs/leave-banned-channels/spec.md`.
- `group-monitoring`: `getChannelsBatch` дополнительно исключает
  `'leaved_from_banned'`/`'leaved_manual'` из выборки каналов на обработку.

## Impact

- `src/core/db/channels.ts` — `ChannelStatus`, `getLeaveQueue` (возврат
  `status`), замена `resetChannelStatus`, `getChannelsBatch` (blocklist).
- `src/skills/leave-banned-channels.ts` — выбор терминального статуса по
  исходному триггеру строки очереди.
- Разовый скрипт миграции (`src/scripts/`, имя определить на этапе tasks) —
  проставление `should_leave` по разнице `channels`/`join_queue` для 46
  явно перечисленных агентов + включение `leave-banned`.
- `docs/telegram-errors.md` / комментарии в коде, где перечислены значения
  `ChannelStatus` — обновить список.

## Non-Goals

- Не строится общая переиспользуемая способность «автоматическая чистка
  каналов после любого будущего перераспределения» — только точечная
  миграция для сегодняшнего списка агентов. Если понадобится regularly —
  отдельный change.
