## Context

Три независимых потребителя одной и той же сломанной функции:

```
core/telegram/errors.ts::parseFloodWait(err)   ← НОВОЕ единое место
        │
        ├── core/telegram/service.ts
        │     ├── joinWithRetry (JoinChannel, внутри joinDiscussionGroups)
        │     ├── sendDm — инлайн-ретрай (уже соответствует dm-send spec, просто не работал)
        │     └── 6 методов: resolveOwnChannel / resolveLinkedBroadcast /
        │           getChannelRecommendations / getChannelSubscribers /
        │           getChannelGateInfo / getRecentPosts
        │           → при флуде throw core/telegram/errors.ts::FloodWaitError(waitSeconds)
        │             (СВОЙ класс проекта, не GramJS-класс — уже существует,
        │             используется вызывающими через instanceof)
        │
        └── skills/util.ts::withFloodRetry
              └── monitor.ts / monitor-v2.ts — sendReply → sendReplyRaw
```

`skills/util.ts` уже сегодня легитимно ловит сырые исключения GramJS напрямую (не
через `core/telegram/errors.ts::FloodWaitError`) — `replyToMessage()`
(`service.ts:674-688`) ничего не оборачивает, отдаёт `client.sendMessage()` как есть.
Это соответствует собственному описанию файла (`skills/util.ts:3-6`): «Ядро бросает
ошибки Telegram как исключения; скиллы ловят их...» — то есть слой skills по замыслу
уже умеет работать с сырыми исключениями Telegram, а не только с типами
`core/telegram/errors.ts`. Значит перенос `parseFloodWait` в `core/telegram/errors.ts`
и импорт его из `skills/util.ts` не создаёт новую связь между слоями — `skills/*` уже
зависит от `core/*` (в другую сторону зависимостей в проекте нет).

`FloodWaitError`/`SlowModeWaitError` GramJS — конкретные подклассы `FloodError` (код
420), каждый сам объявляет `seconds: number`
(`node_modules/telegram/errors/RPCErrorList.d.ts:10-17`); у базового `FloodError` этого
поля в объявлении типов нет (`RPCBaseErrors.d.ts:64-67`) — проверять нужно объединение
двух конкретных подклассов, не общий `instanceof FloodError`.

Прецедент в этой же кодовой базе: `deterministic-connection-errors` (архив/готово) уже
решал структурно идентичную проблему — классификация ошибок Telegram по тексту вместо
структурных полей GramJS (`err.code`, а не regex на `err.message`), с тем же выводом:
«GramJS не выдумывает текст RPC-ошибок... классификация не требует хрупкого парсинга
человекочитаемого текста». Этот change применяет тот же принцип к флуд-ограничениям.

## Goals / Non-Goals

**Goals:**
- Флуд-ограничение Telegram (`FLOOD_WAIT`, slow-mode) распознаётся по структурному типу
  исключения во всех местах, где сегодня вызывается `parseFloodWait` — одна функция,
  один источник истины.
- join-queue: ссылка, упавшая в флуд на любом из трёх шагов (`ResolveUsername`,
  `GetFullChannel`, `JoinChannel`), маршрутизируется на повторную попытку на следующем
  плановом батче — не помечается `skipped` навсегда.
- Ни один прогон диспетчера не спит дольше согласованного порога из-за одного флуда —
  большой флуд откладывается на следующий плановый тик, а не блокирует текущий прогон
  и, тем самым, остальные задачи агента в этом тике.
- dm-send и monitor/monitor-v2 начинают вести себя так, как уже описано в
  `openspec/specs/dm-send/spec.md` и как задумано `withFloodRetry` — без изменения их
  внешнего контракта (dm-send) и с добавлением недостающего (group-monitoring).
- Существующие 11271 строк `status='skipped'` по всей платформе получают одну честную
  повторную попытку через уже исправленную классификацию — не остаются мёртвым грузом
  навсегда только из-за того, что были неверно классифицированы до фикса.

**Non-Goals:**
- Не вводится верхняя граница ожидания для шести методов `service.ts`, используемых
  только standalone-скриптами (`scripts/channel-metrics.ts`,
  `scripts/discovery-similar.ts` через `core/discovery/similar.ts`,
  `scripts/channel-coverage-update.ts`, `core/channel-analysis/run.ts`) — эти скрипты
  запускаются вручную (`tsx src/scripts/...`), не через `dispatcher.ts`/systemd-таймер,
  не подпадают под `TimeoutStartSec=3600`; многочасовое ожидание там — не системный
  инцидент, а вопрос UX оператора (можно обсудить отдельно, если станет проблемой).
- Не трогается стухшее нормативное требование `task-scheduler` spec «Конечные задачи
  (join-queue) SHALL завершаться терминальным статусом» — код (`join-queue.ts:26-31`)
  уже отклонился от этого требования сознательно (комментарий: «discovery пополняет
  очередь асинхронно, поэтому задача остаётся активной»), это расхождение
  предсуществует этому change и не связано с детекцией флуда — исправление спеки
  (или кода, если спека верна) — отдельная задача.
- Не меняются `MAX_ATTEMPTS`/`PROCESSING_TIMEOUT_SECONDS` в `core/db/join-queue.ts` —
  бухгалтерия повторов `error`-статуса не связана с корректностью детекции.
- Не объединяются `USER_ALREADY_PARTICIPANT`/`CHANNEL_PRIVATE`/`no linked discussion
  group` и прочие по-настоящему постоянные skip-причины с флудом — они остаются
  `skipped` навсегда, это осмысленное поведение (см. предыдущее обсуждение в этом же
  диалоге, не входит в этот change).

## Decisions

**Единая функция в `core/telegram/errors.ts`, не две синхронизируемые копии.**
Рассматривался вариант «просто починить регэксп в обеих копиях» (как было предложено
изначально) — отклонён при формализации: два места с одной и той же логикой уже
привели к тому, что бага не заметили дольше — фикс в одном месте легко забыть
продублировать во втором. `core/telegram/errors.ts` уже единственный дом типов ошибок
Telegram в проекте (`FloodWaitError`, `ClientNotConnectedError` и потомки) — согласуется
с «Один факт — один дом» (`docs/agent-playbook.md`).

**`err instanceof FloodWaitError || err instanceof SlowModeWaitError`, не regex ни в
каком виде.** См. Context — оба класса структурно объявляют `.seconds`, TS видит поле
без каста при проверке через `instanceof` конкретных классов (не абстрактного
`FloodError`, у которого поля в типах нет).

**Порог ожидания — общая константа, не отдельное число в каждом месте.** Рассматривался
вариант оставить логику `sleep` как есть и просто полагаться на то, что реальные флуды
обычно короткие — отклонён: ровно это допущение уже опровергнуто логами (66030с,
~18ч, реальный кейс). Общая константа даёт одну точку принятия решения при выборе
значения и одну точку изменения в будущем.

**join-queue: маршрутизация по `floodWaits` (уже существующее поле), не новый статус
`JoinResult.status`.** `JoinSummary.floodWaits: Array<{link, waitSeconds}>`
(`service.ts:66`) уже существует и уже прокидывается в `skills/join-queue.ts` через
`summary.floodWaits`/`summary.hadFloodWait` (используются в `details` статус-отчёта,
`join-queue.ts:56-58`) — просто сегодня туда пишет только `JoinChannel`-ветка. Добавление
третьего значения в `status: "joined" | "skipped"` (например `"flood_wait"`) отклонено:
расширяло бы публичный тип `JoinResult` и требовало бы правки всех потребителей этого
типа, хотя нужный сигнал уже есть в соседнем поле того же ответа.

**Порог применяется одинаково к join-queue/monitor/dm-send, без раздельной настройки
по каналу.** Каждое место и так уже принимает решение «спать один раз, при повторе —
сдаться» — добавление верхней границы длительности не меняет число попыток, только
верхнюю границу ожидания перед первой попыткой. Единообразие проще объяснить и
проверить, чем три разных порога с тремя разными обоснованиями.

**Бэкфилл — `UPDATE ... WHERE status='skipped'`, не выборочный по причине.** Нельзя
отличить в БД, какие из 11271 строк были флудом, а какие — настоящей постоянной
причиной: `lastError` для `skipped` сегодня всегда `NULL` (`join-queue.ts:45` передаёт
`undefined` независимо от `result.reason` — отдельный, самостоятельный баг, не
предмет этого change, см. Non-Goals). Выборочный сброс потребовал бы восстанавливать
причину из `journalctl` (глубина хранения ограничена, полную историю не покрывает) —
несоразмерно цели. Сброс всех `skipped` в `pending` не опасен: настоящие постоянные
причины после одной новой попытки корректно (уже с починенным кодом) осядут обратно в
`skipped` — разовая, ограниченная стоимость одного лишнего вызова на ссылку, не
повторяющаяся трата.

**Бэкфилл размазывается по времени, не одним запросом по всем 140+ агентам сразу.**
Единомоментный сброс всех `skipped→pending` означает, что на ближайшем плановом батче
join-queue у КАЖДОГО агента резко вырастет число `ResolveUsername`/`GetFullChannel`-
вызовов относительно обычного дня — сам этот всплеск способен спровоцировать новые
флуд-ограничения на аккаунтах, у которых их иначе не было бы. Бэкфилл SHALL запускаться
пакетами по агентам с паузой между пакетами (точный график — задача реализации, не
фиксируется здесь), а не единым UPDATE по всем `workspace-*/tg-join-queue.db` разом.

## Risks / Trade-offs

- **[Риск] Значение порога (120с) не подтверждено данными о реальном распределении
  длительности флудов**, кроме трёх наблюдавшихся точек (15с, 3588с, ~65800с) —
  выборка маленькая, распределение явно бимодальное (короткие per-request паузы
  против многочасовых аккаунт-левел ограничений), точка разреза между ними не
  установлена эмпирически. → Принято пользователем как рабочее значение; константа
  в одном месте (`core/telegram/errors.ts`), пересмотр — одна правка.
- **[Trade-off] Флуд выше порога в join-queue уходит в `error`, ждёт следующего
  планового батча (интервал задачи `join-queue` — 4 часа,
  `docs/task-scheduling.md:17`)** — если реальный флуд короче 4 часов (например,
  наблюдавшийся ~18ч всё равно длиннее), ссылка теряет время до следующего тика вместо
  немедленного повтора сразу после истечения флуда. → Осознанно: альтернатива
  (планировать точный повтор через `waitSeconds`) требует новой инфраструктуры
  отложенных задач, которой в проекте нет; 4-часовая гранулярность — существующее
  ограничение самой модели join-queue, не вносится этим change.
- **[Trade-off] `errorCode: "flood_deferred"` — новое значение колонки, читаемой
  внешним отчётом (`funnel-report`)** — `groupSendErrorsByCode`/`problemChannels`
  группируют по `errorCode` уже сегодня без списка ожидаемых значений, поэтому новый
  код не требует правок в отчётном коде, но появится как новая строка в CSV, которую
  раньше там не было — координатор, читающий отчёт, увидит незнакомую категорию
  впервые после деплоя.

## Migration Plan

Схемной миграции нет — `join_queue` не меняет структуру. Есть однократное изменение
данных: бэкфилл существующих `skipped` строк, обязательно **после** деплоя кода (не до)
— иначе ссылки повторно попадут под старую, ещё сломанную классификацию и снова осядут
в `skipped`.

```sql
UPDATE join_queue SET status = 'pending', attempts = 0 WHERE status = 'skipped';
```
— выполняется по каждому `~/.openclaw/workspace-<agentId>/tg-join-queue.db`, пакетами
по агентам с паузой между пакетами (см. Decisions), не одним проходом по всем сразу.
Идемпотентно: повторный запуск после того, как часть строк уже вернулась в `skipped`
(на этот раз корректно), просто снова даст им ещё одну попытку — не портит данные,
но и не бесплатно (лишние вызовы на уже подтверждённо-постоянные причины), поэтому
запускается один раз, не по расписанию.

Обратная совместимость: `JoinResult`/`JoinSummary`,
`core/telegram/errors.ts::FloodWaitError` (проектный класс) не меняют форму — только
как внутри `service.ts` заполняется уже существующее поле `floodWaits`. Откат кода —
вернуть `parseFloodWait` на regex-версию в `core/telegram/errors.ts` (одно место вместо
двух) и убрать проверку порога. Откат бэкфилла отдельным действием не нужен: строки,
уже переклассифицированные в `pending`/`processing`/`error`/`joined` на момент отката
кода, останутся в этих статусах — откат кода не отменяет уже случившиеся вступления и
не возвращает данные назад в `skipped`.

## Open Questions

Все решены на этапе реализации:

- `MAX_INLINE_FLOOD_WAIT_SECONDS = 120` — подтверждено пользователем.
- Отдельный `errorCode: "flood_deferred"` в `send_errors` — подтверждено. Не требует
  правок в `problemChannels`/`errorBreakdown` (`core/db/channels.ts`) — они уже
  группируют generic `GROUP BY errorCode`, новый код получает отдельную строку
  автоматически, без специального исключения из отчёта.
- График пакетов бэкфилла — не зафиксирован числом здесь; вместо этого
  `scripts/join-queue-backfill.ts` принимает `--batch-size`/`--delay-seconds` как
  CLI-параметры, оператор выбирает значения при запуске (после деплоя, см. Migration
  Plan), а не разработчик на этапе кода.
