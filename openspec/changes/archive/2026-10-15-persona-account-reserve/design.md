## Context

Полный технический дизайн вынесен в парный design-doc
[docs/design/persona-account-reserve/architecture.md](../../../docs/design/persona-account-reserve/architecture.md)
(источник требований — `requirements-v1.md`, R1–R20 / AC-1…AC-13). Здесь — только ключевые
решения уровня change; детали потоков, переиспользования и ФС-представления смотреть в
architecture.md, не дублируя.

Корень проблемы: `USER_RESTRICTED` (403) на `channels.CreateChannel` — ограничение
Telegram на уровне аккаунта, блокирует создание канала независимо от сессии и возраста
(каталог ошибок — `docs/telegram-errors.md`, строка 36). Создание канала проходит только
когда выполняется в один прогон при настройке из tdata (как в `tg-agent-autoregistration`).

## Goals / Non-Goals

**Goals:**
- Третий путь подготовки, создающий публичный канал в момент провиженинга (обход
  `USER_RESTRICTED`), и копящий готовые аккаунты в пер-персонном резерве.
- Активация без создания канала — убрать `USER_RESTRICTED` из момента ввода в работу.
- Резерв как источник замены банов (той же персоны) + ручная активация.

**Non-Goals:**
- Изменение логики настройки аккаунта (`core/tdata/account-setup.ts` не трогаем).
- Изменение двух существующих скиллов (фаза 1 / фаза 2 остаются).
- Воскрешение двухфазного создания канала / change `template-channel-phase1` (тупик).
- Прогрев в резерве, политика старения резерва, спец-онбординг активации (вне скоупа).

## Decisions

Ключевые (обоснования и альтернативы — в architecture.md):

- **D1. Резерв = `workspace-reserve-<persona>-<K>`** в общем пространстве `~/.openclaw/workspace-*`.
  Невидимость рабочему контуру — за счёт префикса: ни один из 4 сканеров (`listAgentIds`,
  `listPoolAccountIds`, `computeNextAgentNumber`, `computeNextPoolNumber`) не матчит
  `workspace-reserve-*`; правок перечислителей не требуется. Размещение в `workspace-*`
  даёт переиспользование `workspaceDir`/`loadAccount`/`validatePoolAccount`/claim без правок.
- **D2. Логика настройки = `tg-agent-autoregistration`** (`prepareAccount` c
  `createPublicChannel=false` + отдельный `createPersonaChannel(..., funnelInviteLink)`);
  ядро не меняется, методы уже экспортированы и принимают нужные параметры.
- **D3. Инвайт-ссылка — в скилле провиженинга** (экспорт от `REPORT_AGENT_ID` + вставка в
  пост), ключ реестра = `reserveId`; аккаунт уходит в резерв полностью готовым (R4/AC-11).
- **D4. Активация** = валидация (`validatePoolAccount`, R19) → атомарный claim (`renameSync`,
  R15) → `finalizeActivation` (перекей инвайт-записи `reserveId → agentId` без Telegram +
  прогрев + join-queue + переходы). Канал/пост не трогаются (R13).
- **D5. Триггер 1** правит только `replaceOne` (источник = резерв персоны; `swap.ts` без
  изменений; без `applyPersonaToAccount`; пер-персонный алерт R20). **Триггер 2** — новый
  скилл, claim `agent<N>` при активации (калька `claimPoolToNewAgent`).
- **D6. Новое `core/reserve-accounts.ts`** (пер-персонный аналог `pool-accounts.ts`);
  валидация/карантин делегируют в `pool-accounts.ts` (общие примитивы, не дублируются).
- **D7. `rekeyPrivateInviteLink`** в `core/db/private-invites.ts` — перенос записи реестра
  на новый ключ без вызовов Telegram.

## Risks / Trade-offs

- **Имя персоны в имени каталога** → ограничение на имена персон (не `<другая>-<число>`);
  для текущих выполнено. Mitigation: отмечено, альтернатива (отдельное дерево) ломает
  переиспользование примитивов.
- **Будущие широкие сканеры `workspace-*`** должны исключать резерв и пул. Mitigation:
  канонический перечислитель один (`listAgentIds`), не плодить обходчиков.
- **Пул-примитивы для резерва** — имена `*PoolAccount*` шире своей семантики. Mitigation:
  комментарии + спека `persona-account-reserve`.

## Migration Plan

- Выкатка кодом; миграции данных нет. Резерв — новое ФС-пространство, существующие данные
  не трогает. Оба существующих скилла продолжают работать.
- Откат: удалить новые модули/регистрации и вернуть `replaceOne` к прежнему источнику;
  данные не затрагиваются.
