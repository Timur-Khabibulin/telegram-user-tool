## Context

Сегодня подготовка каналов к распределению — ручная цепочка ops-скриптов
(`channel-niche.ts` → `channel-activity-update.ts --input` / `channel-metrics.ts`
→ Google-таблица → ручная фильтрация → CSV в бот `/distribute`). Каждый шаг —
отдельный SSH-запуск с ручной склейкой CSV по `link`. Цель change — свести шаги
2–4 (ниша, метрики, выгрузка в таблицу, фильтрация) в один запуск командой бота.

Опорные точки в коде:
- `channel-niche.ts` — проверенная параллельная машинерия: волны по агентам,
  общая очередь, session-lock, обработка `FLOOD_WAIT`, деградация резолвинга,
  резюмируемость по output-CSV. Её и переиспользуем.
- `channel-metrics.ts` — дешёвый `avg_views`/`comments_open`/`is_broadcast` через
  один `GetFullChannel` + `getRecentPosts`.
- `channel-activity-update.ts` (режим `--input`) — `comments_per_day` по постам
  канала (число комментариев уже в посте, историю обсуждения читать не нужно).
- `distribution-listener.ts` — persistent-бот с авторизацией по чату, машина
  состояний диалога, инлайн-исполнение (быстрое, только SQLite).
- Лист `all-processed-channels` (~3000 строк): колонки
  `link, title, niche, источник_ниши, subs_count, avg_views, comments_open,
  is_broadcast, posts_30d, total_comments, comments_per_day, источник_метрик,
  assigned_agent, reestr_sub_count`.

## Goals / Non-Goals

**Goals:**
- Один вход: CSV ссылок + параметры одним сообщением боту → отфильтрованный CSV на
  выходе + полный результат в Google-листе.
- Все метрики канала за один резолв, параллельно по выделенному пулу агентов.
- Бот отзывчив во время многочасового прогона; виден прогресс.
- Дедуп входа против листа; идемпотентная запись результата.

**Non-Goals:**
- Распределение каналов — остаётся отдельным ручным шагом (`/distribute`).
- Замена существующих ops-скриптов — они остаются для ручных прогонов.
- Автоматический перезапуск упавшего воркера — резюм ручной (тем же запуском).
- Ретрай ошибочных каналов внутри прогона (как и в текущих скриптах — вручную).

## Decisions

### D1. Новый объединённый скрипт метрик, а не оркестрация трёх старых

Один резолв канала → `GetFullChannel` (`subs_count`, `comments_open`,
`is_broadcast`, `linkedChatId`) → `getRecentPosts(11)` (`avg_views` по методологии
coverage + текст для LLM-ниши) → `getPostsSince(30д)` (`posts_30d`,
`total_comments`, `comments_per_day`) → LLM-описание ниши (промпт `classifyNiche`:
содержательное описание сути канала в 1+ предложений с различением подниши —
личность/блог vs официальный/тематический канал, — а не короткая категория одним
словом; правка по фидбэку 13.09.2026, промпт общий с channel-niche/channel-metrics).
Каркас воркера,
волн, очереди, session-lock и FLOOD-логики берётся из `channel-niche.ts` почти
дословно; на канал добавляется расчёт метрик.

*Альтернатива:* запускать три существующих скрипта последовательно и джойнить
CSV. Отвергнута: тройной резолв одних каналов (тройная цена MTProto и риск
`FLOOD_WAIT`), три прохода вместо одного, и явное требование пользователя — «один
скрипт считает всё за раз».

### D2. Исполнение — detached-воркер, состояние задачи в БД

Слушатель принимает файл и параметры, пишет строку задачи в новую таблицу SQLite
и запускает **отдельный процесс-воркер** (не считает инлайн). Прогресс воркер
пишет в ту же строку задачи (и в output-CSV построчно — источник резюма).
`/status` и guard «один прогон за раз» читают БД, поэтому переживают рестарт
слушателя (`Restart=always`).

*Альтернатива 1:* инлайн в getUpdates-цикле — отвергнута: цикл встанет на часы,
бот умрёт, при рестарте прогон потерян. *Альтернатива 2:* задачу подхватывает
периодический диспетчер — отвергнута: это разовый длинный джоб, а не повторяемая
по расписанию задача; диспетчер под это не заточен.

### D3. Ввод — одним сообщением, параметры в подписи

CSV прикрепляется, параметры — в подписи к файлу, строгий формат (пример):
`agents: agent40,agent41,agent42 | filter: comments_per_day > 0.5`. Разбор строгий
с валидацией до старта (D7). Одно сообщение = одна атомарная задача, не нужен
многошаговый диалог с хранением промежуточного состояния.

*Альтернатива:* пошаговый диалог (жду CSV → жду агентов → жду фильтр). Отвергнута
по выбору пользователя — одним сообщением.

### D4. Google-доступ — сервис-аккаунт, scope `spreadsheets`

Headless-сервер → сервис-аккаунт с JSON-ключом, а не пользовательский OAuth.
Таблица расшаривается на email сервис-аккаунта как **Редактор**. Scope
`https://www.googleapis.com/auth/spreadsheets` покрывает и чтение (дедуп), и
запись. Drive API/`create`-права не нужны — пишем в существующий лист. Библиотека
— официальная `googleapis` (Sheets `values.get` / `values.append` /
`batchUpdate`). ID таблицы, имя листа, путь к ключу — в конфиг/секреты.

*Альтернатива:* OAuth пользователя (refresh-token) — сложнее на headless, привязка
к живому аккаунту; API-key — только публичное чтение, писать не может.

### D5. Запись в лист — один пакет в конце из финального CSV

После завершения расчёта результат (финальный output-CSV) пишется в лист одним
`values.append`. Идемпотентность обеспечена дедупом входа на старте (D6): в лист
попадают только новые каналы, повторной записи тех же строк нет. Колонки
раскладываются по имени заголовка; несчитаемые метрики — пустые ячейки. Имена
колонок, которые пишет конвейер, — только английские: `link, title, niche,
date_updated, subs_count, avg_views, comments_open, posts_30d, total_comments,
comments_per_day, passed_filter`. `date_updated` = дата прогона (`YYYY-MM-DD`),
`passed_filter` = TRUE/FALSE. Недостающие колонки набора конвейер добавляет в
заголовок (`ensureColumns`). Намеренно НЕ пишет `is_broadcast` и не трогает иные
колонки листа (`статус`, `в_discovery_db`, старые источниковые). Числа пишутся как
числа, boolean — как логические (RAW); локаль листа сама отрисует десятичную
запятую. Реальная схема целевой вкладки сверена с сервера (2971 строка).

*Альтернатива:* построчная запись по мере расчёта. Отвергнута: N сетевых вызовов
вместо одного, и при резюме прогона легко задвоить строки.

### D6. Дедуп на старте, fail-fast при недоступности Sheets

Перед расчётом читаем колонку `link` листа и вычитаем уже присутствующие
(сравнение по `normalizeChannelLink`). Если Sheets недоступен на этом шаге —
задача падает с ошибкой, расчёт не стартует (молча считать без дедупа нельзя —
задвоим лист и потратим часы MTProto зря).

### D7. Фильтр — числовая колонка, оператор `>`, пустое = не прошёл

Допустимые колонки — только числовые метрики (`subs_count`, `avg_views`,
`posts_30d`, `total_comments`, `comments_per_day`); оператор строго `>`; порог —
число. Валидация до старта. Канал с пустой метрикой (ошибка/не найден) →
`прошёл_фильтр=FALSE`.

### D8. Отдельный пул агентов под расчёт

Метрики считаются на выделенном пуле агентов, указанном во входе, а не на боевых.
Так многочасовой прогон с session-lock не конфликтует с обычной работой боевых
агентов (monitor/join-queue). Пул — операторская настройка входа, платформенного
понятия «пул под метрики» не вводим (лишняя сущность).

## Risks / Trade-offs

- **Слияние трёх скриптов → регрессия проверенной FLOOD/session-логики** →
  переносим каркас `channel-niche.ts` дословно, метрики добавляем как новый расчёт
  на канал; не переписываем машинерию волн/очереди.
- **~3000 LLM-вызовов ниши за прогон (стоимость/лимиты)** → primary codex-подписка
  + fallback DeepSeek уже настроены; ниша считается один раз на канал, результат
  резюмируется по output-CSV (повторный прогон не пересчитывает).
- **Тяжёлый `getPostsSince(30д)` на крупных каналах (минуты/канал) → часы на
  прогон и риск `FLOOD_WAIT`** → пейсинг monitor-v5 + волны по пулу; предохранители
  `POSTS_MAX_REQUESTS/POSTS_MAX_POSTS` из `channel-activity-update.ts`.
- **Sheets недоступен/квота на записи в конце** → результат уже в финальном
  output-CSV на диске; запись в лист повторяема из того же файла без пересчёта.
- **Воркер упал (reboot/crash), автозапуска нет** → прогон резюмируем повторным
  запуском той же команды (пропустит обработанные ссылки); при необходимости —
  отдельный systemd-юнит.
- **Строгий парсинг подписи → ошибки формата** → чёткое сообщение с примером
  формата и валидация до старта, задача не создаётся при неверном вводе.
- **Расхождение колонок листа и порядка записи** → маппинг по позиции фиксируется
  константой; при отсутствии `прошёл_фильтр` колонка добавляется скриптом.

## Migration Plan

1. Завести сервис-аккаунт Google, включить Sheets API, положить JSON-ключ в
   секреты VPS; расшарить лист на email сервис-аккаунта как Редактор.
2. Прописать в конфиг ID таблицы, имя листа, путь к ключу.
3. Задеплоить объединённый скрипт метрик и обновлённый `distribution-listener`
   (новая команда + запуск воркера + `/status` из БД); при необходимости — юнит
   воркера.
4. Прогнать на малом CSV (несколько ссылок, один агент пула) — проверить дедуп,
   расчёт, запись в лист, возврат CSV, `/status`.
5. Откат: новая команда и таблица задач изолированы; удаление команды не влияет на
   `/distribute`. Существующие ops-скрипты остаются рабочими.

## Open Questions

Разрешено при реализации/деплое:
- Синтаксис подписи — `/metrics agents: a1,a2 | filter: <колонка> > <порог>`
  (толерантный парсинг, валидация до старта).
- Воркер запускается detached из слушателя (не отдельный systemd-юнит) —
  наследует окружение слушателя (`secrets.env`).
- Метка даты — колонка `date_updated` = `YYYY-MM-DD` (заменила источниковые).
- Целевая вкладка — `🔥all-processed-channels - ВСЕ АНАЛИЗИРОВАННЫЕ`
  (`CHANNELS_SHEET_NAME`), схема сверена с сервера; конвейер пишет только
  английские колонки, не трогая `статус`/`в_discovery_db`/`is_broadcast`.
