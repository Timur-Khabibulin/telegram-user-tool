## Context

Полное техническое проектирование — в `docs/design/channel-write-access/architecture.md`
(парный к `requirements-v1.md`). Здесь — сжатая выжимка ключевых решений для
имплементации. Текущее состояние: право писать выясняется только реактивно
(`CHAT_WRITE_FORBIDDEN` → `status='banned'`), структурный и персональный запреты не
различаются.

## Goals / Non-Goals

**Goals:**
- Проактивно определять право писать и различать причину по перечню спеки.
- Гейтить ротацию по типу причины без правок `channel-rotation`.
- Минимум новых сущностей: одна причина + справочный срок.

**Non-Goals:**
- Реализация правил самой ротации (переиспользуется существующий путь).
- Различение типов контента (право оценивается бинарно).
- Раскрытие скрытых цензов Telegram (join-to-comment / стаж / бот) — они остаются
  реактивными `CHAT_WRITE_FORBIDDEN`.

## Decisions

- **Модель данных — 2 колонки `channels`.** `write_access_reason` (TEXT NULL; признак
  «писать нельзя» = `reason IS NOT NULL`) и `write_access_until` (INTEGER NULL,
  `until_date` справочно). Тип причины не хранится — функция
  `isPermanentReason(reason) ∈ {members_restricted, paid}`. Отдельный boolean и
  колонку времени проверки не заводим (производные/ненужны — простота).
  *Альтернатива (расширение enum `status`)* отклонена: право записи ортогонально
  жизненному циклу (R6).
- **Гейт ротации без правок `channel-rotation`.** Дискриминатор — ставим ли
  `status='banned'`: переменная причина → `banned` → существующий
  `leave-banned-channels` → `leaved_from_banned` → ротация; постоянная → `status` не
  трогаем → канал остаётся читаемым монитором. Ротация уже читает только
  `leaved_from_banned`.
- **Три точки съёма.** Постоянная — при вступлении из уже делаемого `GetFullChannel`
  (`join-queue`), без доп. вызова. Переменная — живой `GetParticipant(self)` раз на
  канал за прогон в `monitor-v5` перед фазой отправок (шаг 5.3c). Реактивный резерв —
  по коду send-ошибки в общем обработчике `core/post-comment-send.ts`
  (`handlePostCommentSendError`), который зовёт `sendReply` v5 (у v5 нет инлайн-ветки,
  в отличие от `monitor-v2`).
- **Классификация — чистый модуль `src/core/write-access.ts`** (сигнал/код → причина +
  `isPermanentReason`), без I/O, тестируется отдельно.
- **`chatId` в `channels.db` — id группы обсуждения**, поэтому проверки относятся к
  строке канала напрямую (R2 соблюдается моделью данных).
- **`allow_payment_required`** в общем обработчике `core/post-comment-send.ts`
  переводится с `format_error` на причину `paid` (действует для всех пост-комментных
  отправителей, включая v5).
- **R17 (одна попытка на канал за прогон)** — новый механизм не нужен: обеспечено
  существующим потоком (`ChannelSkipError` при send-ошибке + пропуск фазы отправок при
  проактивном отказе).

## Risks / Trade-offs

- [Живой `GetParticipant` добавляет вызов на канал за прогон] → раз на канал (не на
  сообщение), переиспользование существующих обёрток флуд-ретрая; постоянная величина
  не перечитывается.
- [Проактивная проверка не ловит скрытые цензы и `paid`] → отказ-отправка остаётся
  обязательным резервным источником, обновляющим причину.
- [Рассинхрон признака с реальностью при разбане] → снятие фиксируется живой проверкой
  перед каждым прогоном отправок (без плановой переоценки `until_date`).

## Migration Plan

- Аддитивная миграция `channels`: добавить `write_access_reason`, `write_access_until`
  (обе nullable, дефолт NULL) — существующие строки валидны без бэкфилла.
- Выкладка не требует единовременности: до первого прогона монитора/вступления
  признак пуст (трактуется как «не проверялось / писать можно»), поведение совпадает с
  текущим.

## Open Questions

Нет — развилки закрыты в `architecture.md` §8 (`write_access_checked_at` не
добавляется; `no_discussion` — на уровне очереди вступления; частота — раз на прогон;
формат-запрет остаётся `format_error`; снятие — только в проверке перед прогоном).
