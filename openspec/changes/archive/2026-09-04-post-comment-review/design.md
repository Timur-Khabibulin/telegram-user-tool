## Context

`monitor-v3` (`channel-post-watch`, ещё не заархивирован —
`openspec/changes/monitor-v3/`) отправляет инициативный комментарий сразу
после того, как LLM даёт `score ≥ POST_COMMENT_SCORE_THRESHOLD`
(`src/skills/monitor-v3.ts`). Нужен ручной gate поверх этого решения —
показать пост и предложенный комментарий человеку в Telegram и отправить
только по подтверждению. Диаграмма потока (кто что делает и в какой момент)
— `docs/design/post-comment-review/review-flow.puml`, узлы диаграммы
ссылаются на разделы этого документа.

Ограничения площадки, выявленные в ходе проработки:
- Inline-кнопки с callback может слать только Telegram-бот (Bot API) — Telegram
  роутит нажатие кнопки боту, отправившему сообщение; обычная MTProto-сессия
  агента технически может прикрепить `reply_markup`, но нажатие никуда не
  долетит — принимать колбеки некому. Значит нужен отдельный бот (Bot API),
  агенты (MTProto-сессии) для этого не годятся.
- `dispatcher.ts` — одноразовый процесс на прогон агента, завершается и
  disconnect'ится по окончании назревших задач; блокировать его ожиданием
  нажатия кнопки означало бы держать открытым MTProto-соединение и весь
  systemd-юнит неопределённо долго.
- `TelegramService.peerCache` (`src/core/telegram/service.ts:205`) — приватный
  `Map`, живёт только в памяти текущего процесса, не персистится. `replyToMessage`
  жёстко требует `peerCache.get(chatId)` и не имеет фолбэка на `getEntity`
  (ADR 0003) — новое MTProto-соединение без предварительного резолва диалогов
  не может отправить сообщение в чат обсуждения.
- `better-sqlite3` (`^12.8.0`) по умолчанию ставит `busy_timeout = 5000ms`,
  override не найден нигде в `src/core/db/*.ts` — конкурентная запись двух
  процессов в одну agent-БД уже сегодня не падает мгновенно, а ждёт до 5с.

## Goals / Non-Goals

**Goals:**
- Показать человеку пост и предложенный комментарий до отправки, дать
  возможность разрешить («Да») или заблокировать («Нет») отправку.
- Не блокировать прогон `monitor-v3`/`dispatcher` ожиданием решения человека.
- Работать при нескольких одновременно активных агентах без коллизий между
  ними на уровне приёма нажатий кнопок.
- Переиспользовать существующую пост-отправочную обвязку и путь
  auto-reject (`markPostSeen`), не дублировать логику.

**Non-Goals:**
- Не по боту на агента — один общий бот, один общий чат ревьюеров,
  агент определяется данными, а не идентичностью бота.
- Не таймаут/авто-expiry для `pending_reviews` — не нажали, значит висит
  бессрочно, разбор ручной (решение пользователя).
- Не webhook — long-poll (`getUpdates`), без веб-сервера/ingress, соответствует
  текущей инфраструктуре проекта (только systemd-юниты).
- Не меняется поведение `monitor-v3`, когда review-gate выключен для агента —
  прямая отправка как сегодня.
- Синхронное блокирующее ожидание внутри `dispatcher`-прогона (альтернатива,
  рассмотренная и отклонённая — см. Decisions, пункт 1) — не реализуется.

## Decisions

**1. Асинхронная постановка в очередь (`pending_reviews`), а не блокирующее
ожидание внутри прогона.**
Альтернатива — `monitor-v3` сам вызывает Bot API `sendMessage`, затем внутри
того же прогона поллит ответ до таймаута, держа открытым MTProto-соединение
и systemd-юнит. Отклонено: блокирует dispatcher на неопределённое время
(человек может ответить через часы), задерживает обработку остальных
каналов батча того же агента, и требует таймаута/дефолтного поведения при
отсутствии ответа — а таймаут явно не нужен (Non-Goals). Выбрано: `monitor-v3`
только ставит запись и продолжает прогон; фактическую отправку по «Да»
выполняет отдельный персистентный процесс в момент нажатия.

**2. Один общий бот и один общий `review-listener`, не по одному на агента.**
Первый вариант — бот и слушатель `getUpdates` на каждого агента — рассматривался,
чтобы не было коллизии нескольких процессов на одном `getUpdates`
(Telegram допускает единственного долгоживущего потребителя long-poll на
токен). При пересмотре выяснилось, что коллизия возникает только между
несколькими *слушателями* одного токена — а `sendMessage` (постановка на
ревью) не long-poll, это обычный REST-вызов, безопасный из скольких угодно
параллельных `dispatcher`-прогонов одновременно. Значит `getUpdates` должен
держать только один процесс на всю платформу, независимо от числа агентов;
принадлежность агенту — поле в `pending_reviews`, не идентичность бота. Это
проще (одна регистрация в BotFather, один секрет) и не теряет ничего.

**3. `review-listener` — новый персистентный процесс, не расширение
`dispatcher.ts`.**
`dispatcher.ts` по архитектуре одноразовый (§3.2 architecture.md) и
рассчитан на «одна задача — один агент — один прогон, затем выход».
`review-listener` принципиально другой: постоянно слушает один общий
источник (Bot API), не привязан к расписанию/агенту. Встраивать его в
одноразовый процесс невозможно без нарушения этого инварианта — отдельный
процесс с собственным systemd-юнитом (persistent service, не таймер).

**4. `review-listener` открывает новое MTProto-соединение агента в момент
callback, не переиспользует соединение `dispatcher`.**
Соединение `dispatcher`-прогона к моменту нажатия кнопки почти всегда уже
закрыто (прогон короткий, решение человека может прийти спустя минуты/часы) —
переиспекать нечего. Открывается новое, независимое соединение по
`TelegramService.loadAccount(agentId)`. Следствие — `review-listener` и
возможный параллельный `dispatcher`-прогон того же агента временно держат
два одновременных MTProto-соединения и два независимых процесса, пишущих в
одну agent-БД — оба риска приняты (см. Risks).

**5. `channels.chatAccessHash` — новая персистентная колонка, а не резолв
диалогов на каждый колбек.**
Альтернатива — `review-listener` перед отправкой вызывает
`populatePeerCacheForIds([chatId])` (то же, что делает сам `monitor-v3` в
§0.6), заново находя чат обсуждения среди диалогов агента. Отклонено:
пользователь предпочёл персистентное решение. Выбрано: `chatAccessHash`
пишется в БД в тот же момент, когда `peerCache` в `TelegramService` и так
узнаёт этот accessHash (`populatePeerCacheForIds`/`getDialogsForBatch`/
`listGroupChannels`) — по аналогии с уже существующим `channelAccessHash`
(accessHash самого канала, отдельная сущность от чата обсуждения). После
этого `InputPeerChannel` строится напрямую из БД (`channelId = chatId`,
`accessHash = chatAccessHash`), без единого похода в `getDialogs`. Не
нарушает ADR 0003 («без `getEntity`») — переиспользуется ранее увиденный
accessHash, новый resolve-вызов не делается.

**6. Конкурентная запись `review-listener` и `dispatcher` в одну agent-БД —
принимается без изменения `journal_mode`.**
`better-sqlite3` уже по умолчанию использует `busy_timeout = 5000ms` —
второй писатель ждёт до 5с вместо мгновенного падения. Единственная
многострочная транзакция в затрагиваемой БД — `syncChannels`
(`channels.ts`, вызывается в начале каждого прогона `monitor-v3`) — на
реальных объёмах каналов агента укладывается в миллисекунды, исчерпать
5-секундный бюджет практически невозможно. WAL специально под эту задачу не
нужен — не меняем.

**7. «Нет» переиспользует существующий `markPostSeen`, «Да» — новая общая
функция `applyApprovedComment`.**
`markPostSeen` (`src/core/db/channels.ts`) уже используется в `monitor-v3`
для auto-reject по префильтру/порогу — отклонение по кнопке человека
структурно то же самое: комментарий не отправлен, пост не должен
переоцениваться повторно. Пост-отправочная обвязка успешной отправки
(`createGroupThread` + `savePostWatchComment` + `markChannelStatus` +
`saveReply`, сейчас инлайн в `monitor-v3.ts`) выносится в отдельную функцию,
общую для прямой отправки (review-gate выключен) и подтверждения человеком
(review-gate включён, «Да») — устраняет дублирование между двумя вызывающими.

**8. Review-gate включается per-agent, не глобально.**
Принято по аналогии с тем, как уже включается сам `monitor-v3` (через
задачу в расписании конкретного агента) — режим тюнинга применяется к
одному агенту за раз, не ко всей платформе сразу. Флаг `reviewGateEnabled`
— новое поле в `tg-account.json` того же агента (рядом с `apiId`/`apiHash`/
`sessionString`) — это поведенческая настройка агента, а не секрет, поэтому
живёт в per-agent конфиге, а не в платформенном `secrets.env` (решение 9).

**9. Токен бота и id чата ревьюеров — платформенный секрет в
`~/.openclaw/secrets.env`, не per-agent конфиг.**
В проекте уже есть паттерн для секретов внешних сервисов, общих на всю
платформу (не привязанных к конкретному агенту) — `ASOCKS_API_KEY`
(`docs/configuration.md`): читается напрямую из `process.env` без
dotenv-загрузки в коде, подключается в systemd-юниты через
`EnvironmentFile=-/root/.openclaw/secrets.env`. Токен бота и id чата
ревьюеров — секрет того же рода (один на платформу, не на агента) —
следует тому же пути: `TELEGRAM_REVIEW_BOT_TOKEN`/`TELEGRAM_REVIEW_CHAT_ID`
в `secrets.env`. `tg-agent@.service` уже подключает этот файл — `monitor-v3`
получает токен без правки юнита; новому `review-listener`-юниту нужно
добавить ту же строку `EnvironmentFile=`.

**10. Сообщение ревью включает оценку LLM, решения человека логируются
безусловно.**
Сообщение в чате ревьюеров содержит текст поста, оценку LLM и предложенный
комментарий — не только текст и комментарий. Каждое решение человека
(«Да»/«Нет») логируется без условий, независимо от исхода — задел на
будущее сопоставление с `llm_log`.

*Обновление после реализации:* активный промпт сменился с `generatePostCommentV2`
(`score`/`оси`) на `generatePostCommentV3` (категориальный `тип` —
история/мнение/новость/нет; `V2` оставлена в коде неиспользуемой, как путь
отката). `pending_reviews.llmScore`/`llmAxes` стали nullable, добавлена
`llmType` — таблица поддерживает обе схемы вывода LLM. Порог
`POST_COMMENT_SCORE_THRESHOLD` убран из `monitor-v3.ts`: решение «писать»
теперь закодировано в самом `тип` (`нет` ⇒ комментарий `null`), сравнивать
не с чем.

**11. Ограничение адресата бота — на уровне приложения, не Bot API.**
Bot API не позволяет привязать токен к одному конкретному чату — бот
технически может писать в любой чат, где состоит участником, и любому
пользователю, который хотя бы раз написал ему `/start`. Гарантия держится
на нескольких условиях, каждое обязательно:

- Единственный модуль вызова Bot API во всём проекте — `sendMessage`/
  `editMessage*` не принимают `chatId` как параметр, всегда шлют в
  захардкоженный `TELEGRAM_REVIEW_CHAT_ID` из конфига. Других вызывающих
  путей (сырых HTTP-запросов к `api.telegram.org` в обход модуля) в
  кодовой базе быть не должно — это дисциплина код-ревью, не проверяется
  типами автоматически.
- Текст поста и комментарий LLM используются только как содержимое
  сообщения, никогда не участвуют в выборе адресата — нет пути, которым
  содержимое (в т.ч. сгенерированное LLM) могло бы повлиять на то, куда
  уйдёт сообщение.
- `review-listener` по умолчанию отклоняет: не только `callback_query` не
  из `TELEGRAM_REVIEW_CHAT_ID`, а вообще любой тип входящего обновления
  (личные сообщения боту, апдейты из чужого чата) — без автоответа,
  который подтвердил бы постороннему, что бот что-то делает.
- Токен не должен попадать в логи. Bot API кодирует токен прямо в URL
  (`api.telegram.org/bot<TOKEN>/sendMessage`), а не в отдельном заголовке —
  логирование полного URL запроса (типичная практика для отладки HTTP-
  вызовов) утечёт токен в journald. Логировать только имя метода и статус
  ответа, не URL целиком.
- Организационно: бот не добавляется ни в какие другие чаты, username не
  публикуется — тот же бот, добавленный в чужой чат, обходит все
  перечисленные проверки на уровне кода (Telegram сам разрешит ему там
  писать).

Потолок этой гарантии — она про то, что *код платформы* не напишет не туда.
Она не защищает от прямого вызова Bot API токеном в обход кода (например,
через `curl`, если кто-то получил доступ к `secrets.env`) — тот же класс
риска, что утечка любого другого секрета платформы (в т.ч. MTProto-сессий
агентов), не специфичный для этой фичи.

**12. Ошибки отправки после «Да» — переиспользуется классификация
`monitor-v3.ts`, не отдельная реализация.**
`review-listener` при ошибке `tg.replyToMessage` в ветке «Да» вызывает ту же
обвязку классификации, что уже есть в `monitor-v3.ts` (`classifyTelegramErrorTag`,
обработка `FLOOD_WAIT`/`PEER_FLOOD`/бана на запись/запрета формата —
`upsertRestriction`, `recordAccountError`, `enqueueBannedChannel`,
`markChannelStatus`). Выносится в общую функцию/модуль вместе с
`applyApprovedComment` (решение 7), а не копируется отдельно — тот же
принцип переиспользования.

## Risks / Trade-offs

- **Два одновременных MTProto-соединения одного агента** (`dispatcher` +
  `review-listener`, решение 4) → GramJS/Telegram поддерживает несколько
  соединений на одну сессию (как несколько устройств), протокольно
  безопасно; риск — только на уровне записи в общую agent-БД, покрыт
  решением 6.
- **`review-listener` — новая единая точка отказа для всей функции
  ревью** (в отличие от `dispatcher`, который на агента и независим от
  других агентов) → если процесс упал, новые посты продолжают копиться в
  `pending_reviews` без обработки; это acceptable для ручного QA-инструмента
  (Non-Goals: не критичная для основного потока платформы часть), но
  требует мониторинга процесса (systemd `Restart=`) при внедрении.
  Основной поток `monitor-v3` (комментирование без ревью) от этого не
  зависит — падение `review-listener` не останавливает прогоны агентов.
- **Один общий чат ревьюеров на всех агентов** → при активном использовании
  несколькими агентами одновременно чат может стать шумным; смягчено тем,
  что каждое сообщение указывает канал/агента, и это осознанно принятый
  компромисс ради простоты (Decisions, пункт 2).
- **Чат ревьюеров — обычная группа, не супергруппа** → функционально не
  влияет (Bot API работает одинаково в обеих), но если группу когда-нибудь
  впоследствии конвертируют в супергруппу (200+ участников или изменение
  прав участников), Telegram молча сменит `chat_id`, и
  `TELEGRAM_REVIEW_CHAT_ID` в `secrets.env` станет невалидным без
  предупреждения — заметят по прекратившимся сообщениям ревью, поправить
  вручную. Принято осознанно (решение пользователя) — чат маленький и
  закрытый, риск случайной конвертации низкий.
- **Отсутствие таймаута `pending_reviews`** (Non-Goals) → пост может ждать
  решения дольше, чем имеет смысл (например, дольше freshness-контекста
  обсуждения) — принято пользователем как приемлемое для ручного режима.

## Migration Plan

- Все изменения схемы аддитивны: новая колонка `channels.chatAccessHash`
  (nullable), новая таблица `pending_reviews` — миграция тем же паттерном,
  что уже используется в проекте (`ALTER TABLE ... ADD COLUMN` с проверкой
  `PRAGMA table_info`). Бэкфилл не требуется — `chatAccessHash` заполняется
  по мере обычной работы `monitor-v3` (следующий раз, когда `peerCache`
  узнаёт accessHash чата).
- Bot API токен и id чата ревьюеров — новые переменные в
  `~/.openclaw/secrets.env` (`TELEGRAM_REVIEW_BOT_TOKEN`,
  `TELEGRAM_REVIEW_CHAT_ID`), тем же паттерном, что `ASOCKS_API_KEY`
  (решение 9); `tg-agent@.service` их уже видит, `review-listener`-юниту
  нужно добавить `EnvironmentFile=`.
- `review-listener` разворачивается как новый persistent systemd-сервис,
  независимый от таймеров `tg-agent@.service` — включение не требует
  изменений в существующих юнитах.
- Включение — per-agent флаг review-gate, по умолчанию выключен: без явного
  включения поведение `monitor-v3` не меняется ни для одного агента.
- Откат — выключить флаг per-agent (прямая отправка возвращается),
  остановить `review-listener`; новая колонка/таблица остаются
  неиспользуемыми, но безвредными.
