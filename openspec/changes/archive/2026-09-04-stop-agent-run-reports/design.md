## Context

Диспетчер (`dispatcher.ts`) после каждой назревшей задачи агента шлёт
человекочитаемый отчёт (`formatReport`/`renderDetails`, спецификация в
`skill-run-report`) в Saved Messages **того же агента**, чья MTProto-сессия
уже загружена (`tg.loadAccount(agentId)` в шаге 1 главного потока — тот же
клиент используется и для рабочих вызовов, и для `sendSavedMessage`). При
~68 реально активных агентах и нескольких задачах в день на агента (`monitor-v2`
каждые ~10 минут, `join-queue`, `account-warmup`...) это создаёт постоянный
поток самосообщений, которые никто не читает: вся диагностика в недавнем
разборе флота (какие агенты ограничены и почему, повторный бан каналов у
agent10, распределение по кластерам простаивающих агентов) велась исключительно
через `runs`/`dispatcher_runs`/`error_log`/`agent_restrictions` — SQL-запросами
по SQLite, ни разу не открывая Telegram.

Второй источник той же категории проблемы — `channel-cleanup.ts`: цикл по
нескольким агентам (`tg.loadAccount(agentId)` на каждого), а в конце —
**один** сводный `sendSavedMessage`, без переключения обратно на админа.
Отчёт улетает тому агенту, что оказался последним в цикле — уже
задокументированный в собственном коде файла баг (`todo` на строках 7-11).

Третий, независимый источник шума — `funnel-collect.ts`: список агентов для
сбора метрик воронки строится через `isAgentActive()` (есть ли включённая
monitor-задача), без учёта `agent_restrictions`. Агент с сессией, сломанной
навсегда (`need_update_session`/`banned`), всё равно получает попытку
MTProto-подключения на этапах 5-7 (просмотры поста, число подписчиков) —
предсказуемо повторяет ту же ошибку, которая и привела к ограничению
(зафиксированный кейс: agent130, `406: AUTH_KEY_DUPLICATED`, лог
`[funnel-collect] agent=agent130 stages 5-7 skipped`).

Референсный, уже корректный паттерн переключения на админа перед отправкой
существует в кодовой базе — `core/channel-analysis/run.ts:311`:
`tg.loadAccount(p.adminAgentId)` непосредственно перед `sendSavedDocument`.

## Goals / Non-Goals

**Goals:**
- Полностью убрать отправку отчёта о прогоне в Saved Messages рабочего
  агента — ни в его собственный чат, ни куда-либо ещё (без перенаправления).
- Сохранить всю текущую наблюдаемость прогонов через БД (`runs`,
  `dispatcher_runs`, `error_log`) и journald — их схема и запись не меняются.
- Исправить `channel-cleanup.ts` тем же принципом: не отправлять отчёт
  ни в чей чат.
- В `funnel-collect.ts` не пытаться MTProto-подключение к агентам с
  `need_update_session`/`banned` на этапах 5-7, и не считать такой пропуск
  «сбоем сбора» в тексте ежедневного отчёта-воронки — эта информация уже
  дублируется существующей таблицей ограничений в CSV (`funnel-report-restrictions`).

**Non-Goals:**
- Не трогать `daily-summary.ts` (агент27) и `funnel-tracker.ts` (agent1) —
  оба продолжают слать в Saved Messages как прежде, это не входит в скоуп.
- Не менять сами ограничения/статусные модели (`agent-restrictions.ts`,
  `monitor-v2.ts`/`monitor-v3.ts`) — только чтение существующего состояния.
- Не добавлять новую таблицу/поле для отслеживания «отправлен ли отчёт» —
  вопрос снимается тем, что отчёта больше нет.
- Не менять этапы 1-4 `funnel-collect.ts` (локальные SQLite-метрики) —
  они не зависят от сети и не должны пропускаться из-за ограничения агента.

## Decisions

**1. Удаление, не редирект.**
Рассматривался вариант перенаправить отчёты диспетчера в Saved Messages
`REPORT_AGENT_ID` (agent27) вместо полного удаления — отклонён по двум
причинам: (а) каждое переключение сессии внутри цикла диспетчера — это
дополнительный MTProto-коннект (agent → agent27 → обратно на agent для
следующей задачи), который умножается на число задач и число агентов;
батчинг «одно сообщение в конце прогона» снижает цену, но не убирает её;
(б) agent27 сам регулярно нестабилен (в этом же разборе видели у него
`AUTH_KEY_DUPLICATED`, таймауты прокси, битый `tg-account.json` —
`daily-summary` неоднократно падал) — заводить через него ещё и весь поток
отчётов о прогонах создаёт для него единую точку отказа, влияющую на все
остальные агенты. Итоговое решение пользователя: не отправлять вовсе.

**2. Удаляемый код в `dispatcher.ts`.**
Блок `tg.sendSavedMessage(formatReport(...))` (шаг 5 главного цикла) удаляется
целиком вместе с try/catch вокруг него. Функции `formatReport`, `renderDetails`,
`truncate`, константа `REPORT_TEXT_LIMIT` — удаляются как более не используемые
(единственный вызывающий — этот же блок; проверено `grep` по `src/`). Запись в
`runs` (через `insertRun`) и строка в journald (`log.info([run] ...)`) —
не трогаются, они уже сделаны отдельным, предшествующим шагом в том же цикле.

**3. `channel-cleanup.ts` — тот же принцип, не редирект на админа.**
Хотя референсный паттерн `channel-analysis/run.ts` (переключение на
`adminAgentId` перед отправкой) технически применим и сюда, решение
пользователя («никуда не слать» — общий принцип для всех отчётов о прогонах)
распространяется и на этот файл: `sendSavedMessage`/`formatSummaryReport`
удаляются, а не чинятся редиректом. `ChannelCleanupResult` по-прежнему
возвращается вызывающей стороне (`index.ts` → `tg_channel_cleanup`) —
данные не теряются, теряется только (никем не читаемое) Telegram-сообщение.

**4. Гейт в `funnel-collect.ts` — только вход в блок этапов 5-7, точечный
`getActiveRestriction` на агента, без батч-функции.**
Рассматривался вариант завести batch-функцию вида
`listActiveRestrictions(adminAgentId): Map<agentId, Row>` вместо N отдельных
вызовов `getActiveRestriction` в цикле — отклонён по принципу простоты
(`agent-playbook.md`): при текущем масштабе (до ~150 агентов в
`activeAgentIds`) N дополнительных открытий уже существующего единого
sqlite-файла (`agent-restrictions.db`) — дешёвая операция (тот же паттерн,
что уже используют `countChannels`/`countVisitsToday` и другие built-in
функции этапов 1-4, вызываемые в этом же цикле по разу на агента). Заводить
новую функцию ради оптимизации, для которой пока нет измеренной необходимости —
преждевременно.

**5. Условие пропуска — `need_update_session`/`banned`, не `suspend`.**
`suspend` не блокирует чтение: анти-спам ограничение действует только на
отправку (`PEER_FLOOD`) или является следствием банов каналов
(`channels_banned`) — сама MTProto-сессия рабочая, `getPostViews`/
`getChannelSubsCount` (read-only вызовы) технически не должны падать по этой
причине. `need_update_session` и `banned` — оба означают, что сессия либо
невалидна (`AUTH_KEY_*`, `SESSION_*`), либо аккаунт удалён/заморожен Telegram
целиком: MTProto-вызов в обоих случаях гарантированно неуспешен, попытка —
чистые потери времени и повторный шум в логах.

**6. `note5to7` не проставляется при пропуске по ограничению — отдельная
ветка, не переиспользование текущего `catch`.**
Текущий код оборачивает весь блок этапов 5-7 в `withTimeout(...).catch(err
=> row.note5to7 = ...)`. Пропуск по ограничению должен произойти **до** входа
в этот блок (без вызова `tg.loadAccount`/MTProto вообще) — отдельная проверка
`if (restricted) continue` (или эквивалент) перед текущим `try`, не новая
ветка внутри `catch`. Это гарантирует, что `note5to7` в этом случае просто не
устанавливается (остаётся `undefined`), и агент не попадает в фильтр
`r.agents.filter(a => a.note1to4 || a.note5to7)` секции «Сбои сбора»
(`funnel-report.ts`).

## Risks / Trade-offs

- [Полная потеря видимости отдельного прогона агента через Telegram] →
  Принято осознанно: вся диагностика уже ведётся через БД (`runs`,
  `dispatcher_runs`, `error_log`), продемонстрировано в этом же разборе.
  Если в будущем понадобится точечно посмотреть прогон одного агента —
  `sqlite3 -readonly tasks.db "SELECT ... FROM runs WHERE ..."` заменяет то,
  что раньше требовало открыть Telegram-аккаунт этого агента.
- [`SkillStatus.details` — богатая разбивка по скиллу (например, у `monitor`:
  «каналов обработано», «ответов отправлено» по типам, «dm-кандидатов
  добавлено») — сейчас нигде, КРОМЕ удаляемого Saved-Messages-отчёта, не
  сохраняется. `insertRun` (`run-log`) пишет только `status`/`error`
  (извлечённый из `details.error`/`.reason`/`.step`)/`durationMs`/`llmCalls`/
  CPU-время — не весь объект `details`. После удаления отчёта эта разбивка
  продолжает вычисляться скиллами (не требует их правки — `SkillStatus`
  возвращается как прежде), но нигде не сохраняется и молча отбрасывается
  диспетчером] → Осознанное решение пользователя (задача — прекратить
  отправку, не завести новое хранилище для этих данных); персистентность
  `details` — вне скоупа этого change, отдельный вопрос при будущей
  необходимости (например, если понадобится агрегированная аналитика по
  содержимому, а не только статусу прогонов).
- [`skill-run-report` капабилити становится полностью неприменимой] →
  Требования удаляются явным `REMOVED Requirements` в дельта-спеке (не
  тихо забрасываются) — при архивации change это корректно уберёт
  капабилити из действующих спек.
- [Расхождение между `funnel-metrics` спекой («SHALL... собирать метрики по
  каждому [агенту]») и уже существующей в коде фильтрацией через
  `isAgentActive`] → Уже существующее расхождение, не вносится этим change;
  новое условие (пропуск по ограничению) добавляется поверх, а не вместо.
  Отдельная синхронизация спеки с уже существующим `isAgentActive`-фильтром —
  вне скоупа.
- [Правки трёх типов файлов сразу — код, нормативные спеки, design-документация
  `docs/design/task-scheduler/*`] → Могут разойтись при частичном
  выполнении tasks.md; задачи сгруппированы так, чтобы код и спека для
  каждой капабилити правились в одной логической группе.

## Migration Plan

Прямого отката/миграции данных не требуется — изменение поведения кода,
не схемы БД. Порядок:
1. Код: `dispatcher.ts`, `channel-cleanup.ts`, `funnel-collect.ts`.
2. Нормативные спеки: дельты для пяти затронутых капабилити.
3. Design-документация: `docs/design/task-scheduler/*`.
4. `tsc --noEmit` — сверить с уже известными несвязанными ошибками среды
   (см. `telegram-error-handling` tasks.md 11.1), новых быть не должно.
5. Деплой на VPS (`scp` изменённых файлов в
   `~/.openclaw/extensions/telegram-user-tool/`, как уже делалось для
   `monitor-v2.ts`/`monitor-v3.ts` в этом же разборе) — systemd-юниты
   `Type=oneshot`, перезапуск сервисов не требуется, новое поведение
   вступает в силу со следующего планового прогона.
6. Ручная проверка на VPS: прогнать диспетчер для одного агента с назревшей
   задачей, убедиться, что Saved Messages этого агента не пополнилось, а
   `runs`/`dispatcher_runs` — как обычно; прогнать `tg-funnel-tracker.service`
   при наличии хотя бы одного `need_update_session`/`banned` агента,
   проверить CSV/текст отчёта.
