## Context

Полное техническое решение — `docs/design/channel-distribution/architecture.md`
(HOW, заземлён в коде); требования — `docs/design/channel-distribution/requirements-v1.md`
(WHAT). Здесь — сжатый нормативный конспект решений для агента-исполнителя; за
обоснованием вариантов обращаться к architecture.md.

Текущее состояние: распределение каналов существует только как ручные ops-скрипты
разработчика (`src/scripts/ops/distribute-channels.ts` и соседи) поверх примитивов
ядра (`discovery.ts`, `join-queue.ts`, `tasks.ts`). Bot API на платформе есть в
единственном виде — голый `fetch` без фреймворка (`core/review-bot-api.ts`,
persistent `review-listener.ts`). Заархивированный `channel-rotation` уже ввёл
кросс-агентную балансировку по нагрузке и релакс инварианта реестра.

## Goals / Non-Goals

**Goals:**
- Администраторский путь распределения каналов через Telegram-бот поверх
  существующих примитивов ядра, без нового алгоритма поверх нового хранилища.
- Детерминированная балансировка «выравнивание итоговой нагрузки» целевых агентов.
- Наблюдаемость прогона (статус, сводка по количествам) и аудит (файлы, история,
  журнал).

**Non-Goals:**
- Проверка существования/доступности канала при распределении — зона `join-queue`.
- Переназначение уже закреплённых каналов — чужой канал пропускается (без релакса
  инварианта реестра).
- Переписывание существующих ops-скриптов — сосуществование.
- Веб-интерфейс; выбор агентов кнопками (`callback_query`).

## Decisions

- **Технология бота — голый `fetch` Bot API** (образец `core/review-bot-api.ts`),
  без grammy/telegraf. Поток из 2 шагов не требует фреймворка. Альтернативы (grammy,
  bot-сессия на GramJS) отвергнуты как лишняя зависимость/нетипичный путь.
- **Один сервис, обработка инлайн.** `distribution-listener` (persistent systemd,
  образец `tg-review-listener.service`) принимает команды и выполняет распределение
  инлайн. Отдельный worker/oneshot не нужен: без MTProto-резолва распределение —
  быстрые записи в SQLite. Отдельный bot-токен (лимит один `getUpdates` на токен;
  review-бот его уже держит) — цена изоляции принята.
- **Поток command-initiated.** Спец-команда → режим приёма → CSV + диапазоны
  `agentId`. Стартовое сообщение предупреждает «файл ≤ 20 МБ» (потолок `getFile`).
- **Валидация — только формат** `t.me/<channelusername>` через `normalizeChannelLink`
  + предикат отбраковки `t.me/+`, `joinchat`, `t.me/c/`, пустого username.
  Существование канала — не здесь.
- **Балансировка — детерминированный water-fill**, старт нагрузки = `assignmentCounts`
  (реестр), тай-брейк по меньшему `agentId`. Чистая функция
  `features/channel-distribution/plan.ts` (тест без БД). НЕ переиспользуем
  `planRotation` (её `Math.random()` нарушает детерминизм, цель обратна). Нагрузку
  меряем по реестру, а не `countActiveChannels`: `channels.db` наполняется только
  после вступления (join асинхронен), иначе два прогона подряд свалят пачки на
  одного агента.
- **Постановка в очередь — батчем**: каналы группируются по агенту, `addJoinQueue`
  один вызов на агента.
- **Модель метрик — одно поле `metrics_json`** в `discovered_channels` (аддитивная
  миграция). Легаси фикс-колонки (`sub_count`/…) и `setChannelMetrics` — мёртвый код
  (проверено grep: ни писателей, ни читателей в `src/`), оставляем на месте, DROP —
  отдельная гигиена позже.
- **Хранилище прогонов — `channel-distribution.db`** (workspace админ-агента, как
  `discovery.db`), одна таблица `distribution_tasks` (статус, счётчики added/skipped/
  error, файл, инициатор, времена). Per-канальную детализацию отдельной таблицей НЕ
  храним — она в journald (один факт — один дом).
- **Авторизация по чату** — `CHANNEL_DISTRIBUTION_CHAT_ID` в `secrets.env` (аналог
  `TELEGRAM_REVIEW_CHAT_ID`), default-deny.
- **Аудит**: файлы → каталог `distribution-uploads/`; история → `distribution_tasks`;
  журнал → journald сервиса.

## Risks / Trade-offs

- **[Риск] Зависшая задача (R24)** → если listener убит между `status='running'` и
  `'done'`, строка блокирует новые задачи. Митигация: политика таймаута по
  `created_at` (пометить прерванной); повторный прогон не задваивает
  (`registerChannel`/`addJoinQueue` — `INSERT OR IGNORE`, известные каналы
  пропускаются R13/R14).
- **[Риск] Расхождение канонизации ссылок** → канал, ранее занесённый под
  нестандартной ссылкой, дедуп может не распознать; искажает `assignmentCounts`, не
  ломает распределение. Митигация: разовая гигиена реестра, вне рамок.
- **[Trade-off] Отдельный bot-токен** — новая операционная сущность (секрет,
  мониторинг сервиса); осознанная цена изоляции от review-бота.
- **[Trade-off] Потолок `getFile` 20 МБ** — принят как данность транспорта,
  чанкования нет; для текстового CSV каналов практически недостижим.

## Migration Plan

Аддитивно: новые файлы (`distribution-bot-api.ts`, `db/distribution.ts`,
`features/channel-distribution/*`, `distribution-listener.ts`), новый systemd-юнит,
аддитивная миграция `metrics_json` (схема реестра расширяется, существующие строки
не трогаются). Секрет `CHANNEL_DISTRIBUTION_CHAT_ID` и bot-токен — в `secrets.env`.
Откат — остановить/снять systemd-юнит; данные в реестре откатывать не нужно (уже
распределённые каналы продолжают жить у своих агентов).

## Open Questions

Все развилки дизайна закрыты заказчиком (см. §9 architecture.md). На этап реализации
вынесены только детали: конкретное имя спец-команды бота и текст стартового
сообщения; точная политика таймаута снятия зависшей задачи (по `created_at`).
