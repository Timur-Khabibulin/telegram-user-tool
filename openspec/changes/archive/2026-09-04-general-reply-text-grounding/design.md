## Context

`analyzeChannelMessages` (шаг 1) получает список общих сообщений батча
(`id=... автор: текст`) и возвращает структурированный JSON:
```
{ "ответитьНа": { "id": <message_id>, "текст": "<текст сообщения>" } | null,
  "dmКандидаты": [ { "id", "score", "reason" } ] }
```
`sel.текст` задумывался как эхо реального текста (видимо, для устойчивости
структурированного вывода), но код ни разу не сверяет его с исходным
сообщением. `generateReply(sel.текст)` (шаг 2) генерирует ответ на этот
текст, а `sendReply(chatId, sel.id, replyText)` отправляет результат как
reply на сообщение `sel.id` — независимо от того, совпадает ли `sel.текст` с
тем, что реально написано в `id`.

Реальный источник сообщений в момент вызова уже в памяти вызывающего кода:
`monitor.ts`/`monitor-v2.ts` — в `filtered`/`generalMessages` (или их
аналоге), `monitor-v5.ts` — в `generalById` (`Map<id, TgMessage>`,
`monitor-v5.ts:491`).

Расследование (2026-08-31, `agent41`, `llm_log.db`, окно 16:26 UTC)
подтвердило конкретный случай рассинхрона на проде — см. `proposal.md` →
Why. Найдено через сопоставление `llm_log` (пишется до отправки, `dispatcher.ts`
оборачивает LLM через `withLlmLogging` для `monitor-v3/v4/v5/channel-context`)
с реальными текстами сообщений в промпте шага 1.

Индустриальная практика (см. explore-обсуждение и источники ниже) — если
фрагмент текста должен быть использован дословно, его не стоит пропускать
через генерацию модели повторно: доставать по детерминированной ссылке
(здесь — `id`) из источника, а не доверять тому, что модель процитировала
("deterministic quoting").

## Goals / Non-Goals

**Goals:**
- Текст, передаваемый в `generateReply`, `saveReply` и (в v5)
  `formatGeneralReplyNotification` для общих сообщений, SHALL быть реальным
  текстом сообщения с `id = sel.id`, полученным детерминированным lookup'ом
  по уже имеющимся в памяти данным — не полем `текст` из ответа LLM.
- Защита от рассинхрона `id`/реальные данные: если `sel.id` не находится
  среди сообщений, переданных в этот LLM-вызов, выбор отбрасывается.

**Non-Goals:**
- Слияние шага 1 (анализ+выбор) и шага 2 (генерация ответа) в один LLM-вызов
  (вариант B из explore-обсуждения) — отдельное архитектурное решение про
  экономику вызовов, не про корректность; не делается в этом change.
- Удаление поля `текст` из схемы `analyzeChannelMessages` — оставлено:
  используется моделью как часть рассуждения при выборе (заставляет её
  явно проговорить, что она выбирает), просто код перестаёт ему доверять.
- Исправление уже сохранённых искажённых строк `replies.db.msgText` —
  затрагивает только новые записи после деплоя.
- `newThreadMessages`/`threadReplies` (треды) — не используют этот механизм,
  текст там и так берётся из реальных `TgMessage`, не из ответа LLM.
- `monitor-v3.ts`/`monitor-v4.ts` — работают с единственным уже известным
  постом напрямую (`latestPost.text`/`discussion`), не выбирают сообщение из
  батча по `id` — структурно не подвержены этой проблеме.

## Decisions

**1. Брать текст по `id` из уже имеющихся в памяти сообщений (explore-вариант A),
не сливать шаги 1+2 в один вызов (вариант B), не убирать поле `текст` из схемы.**
Причина: минимальное изменение, устраняющее причину напрямую — `id` уже
надёжен (используется для `sendReply` и работает), нужно просто использовать
такой же надёжный источник для текста. Вариант B (слияние вызовов) решает ту
же проблему, но меняет архитектуру ради вопроса экономики вызовов, который
не стоит остро для `monitor-v5` (человеко-темповый прогон, лишний вызов не в
бюджете задержки) и не был поднят как отдельная проблема для v1/v2.
*Альтернатива отклонена*: вариант B — годная альтернатива, если в будущем
задержка/стоимость LLM станет узким местом; тогда стоит отдельный change.

**2. Поле `текст` в схеме `analyzeChannelMessages` остаётся, но не используется как источник контента.**
Убирать поле — более чистое решение (модели физически нечего сфабриковать),
но ломает форму существующего структурированного вывода без явной пользы
здесь и требует трогать промпт (`llm/prompts.ts`) вдобавок к трём скиллам.
Оставить как есть безопаснее и достаточно: код просто игнорирует его как
источник истины.
*Альтернатива отклонена*: убрать поле из схемы — можно сделать отдельным
последующим change, если понадобится (например, если галлюцинации в этом
поле продолжат путать будущих читателей кода).

**3. Невалидный `id` (не найден среди переданных сообщений) — общий ответ не отправляется в этом прогоне, канал продолжает обрабатываться дальше.**
Симметрично уже принятому в проекте паттерну (DM-кандидат без
`userAccessHash` не отправляется, но не роняет прогон). Не должно происходить
на практике (LLM видит список `id` в промпте), это defensive-проверка на
случай, если модель всё же вернёт несуществующий `id`.

**4. Правка вносится независимо в три файла (`monitor.ts`, `monitor-v2.ts`, `monitor-v5.ts`), не выносится в общую функцию.**
Тот же прецедент, что уже фиксирует шапка `monitor-v3.ts` (design.md,
решение 7) — когда шаг совпадает по сути между версиями, код копируется и
адаптируется на месте, а не выносится в общий модуль; это уже устоявшийся в
проекте способ, которым разошлись `monitor`→`monitor-v2`→`monitor-v5`.

## Risks / Trade-offs

- [Trade-off] Поле `текст` в ответе LLM после этой правки становится мёртвым
  грузом (модель его возвращает, код не читает) — небольшой риск путаницы
  для будущего читателя кода; смягчается решением 2 (не убирать сейчас,
  задокументировать здесь и в коде комментарием на месте правки).
- [Risk] Правка в трёх файлах параллельно — риск разойтись в деталях
  (например, разное имя переменной для lookup-мапы: `generalById` в v5,
  другое имя в v1/v2) → Mitigation: проверить по месту в каждом файле перед
  правкой, не копировать вслепую.

## Migration Plan

1. `src/skills/monitor.ts` (строки ~316-329): после `sel = analysis.ответитьНа`
   искать реальный текст по `sel.id` в уже отфильтрованном списке общих
   сообщений этого прогона; если не найден — пропустить общий ответ для
   канала в этом прогоне (не бросать ошибку, не ронять прогон).
2. `src/skills/monitor-v2.ts` (строки ~503-513): та же правка, тот же паттерн.
3. `src/skills/monitor-v5.ts` (строки ~578-609): та же правка;
   дополнительно — `formatGeneralReplyNotification` получает реальный текст
   вместо `sel.текст`.
4. Деплой — `scp` + `chown root:root` трёх файлов, рестарт gateway не
   обязателен (`tsx` перечитывается на каждый тик диспетчера).
5. Откат — `git revert`, без миграций БД (поведенческая правка, схема не
   меняется).
