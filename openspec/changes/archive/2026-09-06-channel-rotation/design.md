## Context

`leave-banned-channels` — per-agent скилл диспетчера (`src/skills/leave-banned-channels.ts`),
запускается диспетчером с `--agent <id>` и видит только БД одного агента. После
успешного выхода канал получает терминальный статус `leaved_from_banned`
(`markChannelStatus`/`setLeftChannelStatus`, `src/core/db/channels.ts`) и на этом
обработка останавливается — реестр `discovered_channels` не трогается, канал
никуда не передаётся.

Реестр `discovered_channels` (`src/core/db/discovery.ts`) хранит одну строку на
канал, ключ — `canonical_link` (не `chatId`). Инвариант зафиксирован в спеке
`channel-registry`: «assignment, once written, SHALL NOT change». Историческая
механика `banned_at` + автопереезд канала существовала и была осознанно убрана
(комментарий `discovery.ts:51`: «убрать banned_at (механизм бан/переназначение
упразднён)») — единственный найденный источник, коммит `0dc683c`, без отдельного
ADR с обоснованием. Эта фича возвращает переназначение, но по новому, явному
триггеру, а не как повторение старой механики.

Определяющие для дизайна свойства кодовой базы:
- Агенты — не строка в БД, а директории `~/.openclaw/workspace-<agentId>/`
  (`listAgentIds()`, `src/core/config.ts`).
- У каждого агента своя SQLite `channels.db`/`join-queue.db`; общие для платформы
  БД (`discovery.db`, `agent_restrictions.db`) лежат в workspace `agent1`
  (`FUNNEL_ADMIN_AGENT_ID`).
- `channelUsername` в `channels` — юзернейм broadcast-канала, к которому
  привязан чат обсуждения; это поле, а не `chatUsername`, используется как
  публичная ссылка для повторного вступления (подтверждено пользователем как
  фактическая практика платформы, расходится с первоначальным предположением
  по комментарию в коде).
- `normalizeChannelLink` (`discovery.ts:95-102`) — уже существующая,
  детерминированная функция нормализации ссылки; тот же формат, что кладётся
  в `canonical_link` при первичном discovery.
- `forceAssignChannel` (`discovery.ts:308-320`) и `addJoinQueue`
  (`join-queue.ts:61-81`) — существующие примитивы upsert/insert, ранее
  используемые только оператором (`redistribute-channels.ts`) и discovery-потоком
  соответственно; в этой фиче переиспользуются как есть.
- `isAgentActive` (`tasks.ts:341-347`) и `getActiveRestriction`
  (`agent-restrictions.ts`) — существующие примитивы, уже применяются
  в `funnel-tracker`/диспетчере для похожих целей.

## Goals / Non-Goals

**Goals:**
- Автоматически передавать каналы, покинутые из-за бана, менее загруженному
  активному агенту вместо того, чтобы терять их в статусе `leaved_from_banned`.
- Не концентрировать залповую передачу многих каналов на одном агенте за один
  прогон (риск для здоровья аккаунта — резкий всплеск новых вступлений).
- Держать реестр `discovered_channels` согласованным с фактическим держателем
  канала после ротации.

**Non-Goals:**
- Не решает случай каналов без публичного `channelUsername` — они физически
  непередаваемы (не у кого взять ссылку для нового агента), остаются
  зависшими в `leaved_from_banned`. Обработка этого случая (ручная разборка,
  иной канал восстановления) — вне рамок этой фичи.
- Не пересматривает инвариант ручного оverride (`redistribute-channels.ts`) —
  он продолжает работать как отдельный механизм для оператора.
- Не меняет `leave-banned-channels` — ротация читает его результат
  (`leaved_from_banned`), но не встраивается в его прогон (см. Decisions).
- Не вводит понятие «вместимость агента» как лимит/квоту — только
  относительное сравнение текущей нагрузки для выбора порядка round-robin.

## Decisions

### Отдельный кросс-агентный скрипт, а не задача диспетчера

`src/scripts/periodic/channel-rotation.ts`, systemd timer, запуск раз в сутки —
по образцу `daily-summary.ts`/`funnel-tracker.ts`.

Альтернатива — новый `TaskType` в диспетчерской `tasks`-таблице (как
`leave-banned`) — отвергнута: диспетчер запускается `--agent <id>` и видит
только БД одного агента, а ротации нужна одновременная видимость каналов
и нагрузки **всех** агентов платформы, чтобы корректно посчитать порядок
round-robin. Разбить это на per-agent шаги без общего состояния между ними
невозможно без внешнего файла-накопителя, что сложнее, чем один
кросс-агентный процесс.

### Источник кандидатов — статус, не отдельная очередь

Кандидаты читаются напрямую `SELECT ... WHERE status='leaved_from_banned' AND
channelUsername IS NOT NULL` из `channels.db` каждого агента, без
промежуточной таблицы/очереди.

Альтернатива — заводить отдельную таблицу `rotation_queue` (аналог
`join_queue`) — отвергнута как избыточная сущность: `status` уже несёт нужную
информацию, а ротация — идемпотентная выборка (после переноса строка
удаляется, повторно не попадётся).

### Round-robin по нагрузке, зафиксированной на старте — не мгновенный greedy-min

Список активных целевых агентов сортируется по текущей активной нагрузке один
раз в начале прогона; кандидаты распределяются по кругу этого фиксированного
порядка (со сдвигом при совпадении с агентом-источником конкретного канала).

Альтернатива 1 — чистый greedy: на каждом шаге выбирать агента с минимальной
текущей (постоянно пересчитываемой) нагрузкой. Даёт наилучший теоретический
баланс, но при разнице нагрузок агентов ротация может закинуть большую пачку
каналов (например, все 10 забаненных за день) одному и тому же самому
свободному агенту подряд — залповое вступление в 10 групп за один прогон
для одного аккаунта. Отвергнуто пользователем по этой причине.

Альтернатива 2 — чистый round-robin без учёта нагрузки вообще (как
`distribute-channels.ts`, порядок `listAgentIds()`) — не решает исходное
требование «сначала тем, у кого меньше всего каналов», особенно заметно на
малых пачках (1-3 кандидата в день — обычный случай), где случайный порядок
агентов не даёт никакого выравнивания.

Выбранный вариант — компромисс: учитывает исходный дисбаланс (сортировка на
старте), но не даёт одному агенту забрать больше одного «лишнего» канала за
круг (round-robin, а не пересчитываемый greedy).

### `channelUsername`, не `chatUsername`

Для построения ссылки повторного вступления используется `channelUsername`
(юзернейм привязанного broadcast-канала), а не `chatUsername` (юзернейм
самого чата обсуждения). Несмотря на комментарий в коде
(`channels.ts:206-208`, «не путать»), фактическая практика платформы —
вступление всегда идёт по ссылке на broadcast-канал; это подтверждено
пользователем как источником истины по реальному поведению, а не по
комментарию в коде (agent-playbook.md: «код — источник истины», в данном
случае — фактическое поведение системы, а не текст комментария).

### Обновление реестра через существующий `forceAssignChannel`

Канонический ключ для обновления `discovered_channels.assigned_agent`
строится как `normalizeChannelLink(channelUsername)` и передаётся в уже
существующий `forceAssignChannel(adminAgentId, link, targetAgent)` — тот же
примитив, что использует `redistribute-channels.ts` для ручного override.
Новая функция/миграция схемы не нужны: `forceAssignChannel` уже делает
`INSERT ... ON CONFLICT DO UPDATE SET assigned_agent`, что покрывает и случай
«канал уже был в реестре» (обычный случай), и «канала почему-то не было в
реестре» (создаёт строку).

Альтернатива — добавить `chatId` в `discovered_channels` для прямого
join-ключа между таблицами — отвергнута: `normalizeChannelLink` уже
детерминированно и без дополнительной схемы восстанавливает тот же
`canonical_link`, если канал вообще пригоден для ротации (то есть уже имеет
`channelUsername` — оба условия совпадают).

### Удаление строки канала у агента-источника, а не сброс статуса

После успешного переноса строка `chatId` физически удаляется из `channels`
агента-источника (`DELETE FROM channels WHERE chatId=...`), а не переводится
в `NULL`/другой статус. Иначе мёртвая строка продолжает висеть балластом
в БД агента, у которого канал давно не при делах, и потенциально может
конфликтовать в будущих `INSERT OR IGNORE` при пересоздании чата с тем же
`chatId` (маловероятно, но не нулевая вероятность для Telegram ID).

## Risks / Trade-offs

- **[Риск]** Округление ссылки: если формат `canonical_link`, под которым
  канал был изначально зарегистрирован, отличался от текущей нормализации
  (например, канал занесён вручную через `import-agent-pool` с нестандартной
  ссылкой до того, как `normalizeChannelLink` стала единственной точкой входа)
  → **Митигация**: `forceAssignChannel` делает upsert по вычисленному ключу —
  в худшем случае создастся вторая строка в реестре с тем же каналом под
  слегка другим ключом, что не ломает ротацию (join-queue и назначение всё
  равно корректны для нового агента), но искажает `assignmentCounts()`.
  Разовая гигиена реестра — вне рамок этой фичи, отдельная задача при
  обнаружении.
- **[Риск]** Массовая единовременная активация: если в первый день включения
  фичи в `leaved_from_banned` уже накопилось много каналов (бэклог, не
  обработанный за месяцы) → **Митигация**: round-robin по кругу и так не даёт
  больше одного «лишнего» канала на агента за круг; при очень большом
  бэклоге можно ограничить прогон лимитом кандидатов за раз (аналогично
  `LEAVE_BANNED_BATCH_LIMIT`) — оставлено на этап реализации, не блокер
  дизайна.
- **[Trade-off]** Каналы без `channelUsername` копятся в `leaved_from_banned`
  бессрочно без явного сигнала оператору, кроме числа в логе прогона —
  осознанно принято (см. Non-Goals); если объём окажется значимым, для этого
  можно завести отдельную задачу позже.

## Migration Plan

Новая функциональность, аддитивная: новый файл-скрипт, новый systemd
timer/service (по образцу `funnel-tracker`), без изменений схемы БД (все
задействованные таблицы уже существуют). Откат — выключить/удалить systemd
timer; уже перенесённые каналы откатывать не нужно (перенос идемпотентно
консистентен — канал просто продолжает жить у нового агента).

Время запуска суточного таймера подбирается на этапе деплоя так, чтобы
выдержать интервал ≥12 часов от прогонов `leave-banned-channels` (у которого
собственный per-agent период ~180 минут, без единого фиксированного времени
суток) — конкретный час выбирается из уже используемых для периодических
задач часовых поясов (`Asia/Yekaterinburg`, см. `task-scheduler`).

## Open Questions

- Нужен ли лимит на число каналов, обрабатываемых за один прогон
  (аналогично `LEAVE_BANNED_BATCH_LIMIT`), или достаточно того, что
  round-robin и так ограничивает залповость на одного агента? Решить на
  этапе реализации по факту наблюдаемых объёмов.
- Куда именно уходит суточная сводка прогона (`rotated`, `skipped_no_username`,
  разбивка по целевым агентам) — в лог систeмд-сервиса, или отправка в Saved
  Messages получателю отчётов по аналогии с `daily-summary`? Оставлено на
  реализацию, не блокирует дизайн.
