## Context

`discovery-similar` — скрипт поиска похожих каналов через нативный сигнал Telegram.
Текущая реализация (`src/core/discovery/similar.ts`) обходит искателей последовательно:
открывает сессию, делает BFS, закрывает сессию, переходит к следующему. Три искателя
по 30 мин = 90 мин прогона.

JS event loop однопоточный; `Promise.all` — корутины с кооперативным вытеснением на
`await`. `better-sqlite3` — синхронный API: DB-вызовы не содержат `await` и не
прерываются другими корутинами. Это ключевое свойство, обеспечивающее безопасность
параллельных записей без явных локов.

## Goals / Non-Goals

**Goals:**
- Параллельный запуск всех искателей через `Promise.all`.
- Каждый искатель — изолированный `TelegramService`; падение одного не роняет прогон.
- `assigned_agent` в реестре становится nullable; фаза распределения — отдельным шагом
  после завершения всех искателей.
- Per-searcher статистика (найдено, отсеяно по каждому гейту) в отчёте оператора.

**Non-Goals:**
- Изменение цепочки гейтов (подписчики → группа → вовлечённость → LLM тема).
- Глобальная приоритизация seeds (отложено в Future Work).
- Общий кеш посещённых каналов между искателями.
- Изменение интерфейса запуска скрипта.

## Decisions

### TelegramService per-searcher

Каждый искатель создаёт `new TelegramService(log)` и вызывает `loadAccount(searcherId)`.
Общий экземпляр нельзя: `this.accountConfig` — одно поле, `loadAccount` перезаписывает
его и сломает параллельные сессии.

### Разделяемый счётчик — plain object

`{ totalCollected: number, goal: number }` — разделяемое состояние в памяти.
Безопасно без мьютекса: между двумя `await` event loop не переключается; `totalCollected++`
атомарен с точки зрения корутин.

### Регистрация без агента + отдельная фаза distribute

Искатели пишут в реестр с `assigned_agent = NULL`. После завершения всех искателей
`distribute` читает `getUnassignedChannels`, раскладывает round-robin, вызывает
`addJoinQueue`. Это сохраняет детерминизм назначения и разделяет ответственности.

Альтернатива «назначать агента сразу при находке» отклонена: потребовала бы
синхронизации `roundRobinIndex` между корутинами (точка останова между read и write
могла бы разорвать другой корутиной при наличии async в цепочке).

### Promise.all, не Promise.allSettled

`runSearcher` никогда не реджектит promise — все ошибки перехватываются внутри и
превращаются в поля `SearcherStatus`. `Promise.all` читается проще.

### Dedup — INSERT OR IGNORE

Атомарен на уровне SQLite. Два искателя, нашедшие один канал: первый получает
`inserted=true`, второй — `inserted=false` и не считает канал. MTProto-вызовы (гейты)
могут дублироваться, но это осознанный trade-off в пользу отсутствия общего
кеша visited между искателями.

## Risks / Trade-offs

| Риск | Митигация |
|---|---|
| Висящий NULL-пул при падении процесса между фазами | Предупреждение при старте, если `getUnassignedChannels` возвращает строки; не блокирует следующий прогон |
| Overshoot цели (несколько корутин проходят финальную проверку одновременно) | Допустим; overshoot ≤ N_searchers; фиксируется в отчёте как «Собрано X/Y» |
| Дублирующие MTProto-вызовы при пересечении графов | Незначительно при 2–4 искателях с разными seed-наборами; упрощает код |
| Миграция схемы (assigned_agent NOT NULL → nullable) | SQLite не поддерживает ALTER COLUMN; нужна пересборка таблицы через RENAME + CREATE + INSERT + DROP |
