## Context

`TelegramService.ensureClient()` (`src/core/telegram/service.ts:212-281`) — единственная
точка установления MTProto-соединения, используется через `requireClient()` в ~30
местах сервиса. Три её ветки отказа устроены так:

```
ensureClient()
  ├─ нет apiId/apiHash          → log.error(...); return null
  ├─ нет sessionString          → log.error(...); return null
  └─ 3 попытки connect() истекли → log.error(...); return null
                                        │
requireClient()                        ▼
  throw new ClientNotConnectedError()  ← всегда одно и то же сообщение,
                                          связь с причиной теряется здесь
```

Конкретная причина уже логируется на уровне `ensureClient` (`this.log.warn`/`log.error`
с текстом попытки), но не переживает переход в исключение — а именно исключение
попадает в `runs.error` (через `formatError()`, `dispatcher.ts:226,234`) и в отчёт Saved
Messages. Чтобы узнать причину постфактум, нужен `journalctl` по конкретному агенту и
конкретному временному окну — так была найдена причина обоих инцидентов из proposal.md
(Why).

GramJS не выдумывает текст RPC-ошибок: неизвестные коды (как `AUTH_KEY_UNREGISTERED`,
не входящий в специфичный список `RPCErrorList.js`) падают в generic `RPCError` с
`err.code` (числовой, `401`) и `err.errorMessage` (сырая строка от Telegram) как
отдельными полями (`node_modules/telegram/errors/index.js:20-28`). `err.message`
(человекочитаемый, форматированный: `"401: AUTH_KEY_UNREGISTERED (caused by
users.GetUsers)"`) — тоже стабилен, т.к. собирается самим GramJS по фиксированному
шаблону, а не Telegram-ом.

Существующий прецедент в этом же файле: `parseFloodWait()` (`service.ts:137-140`) уже
парсит `FLOOD_WAIT_N` регэкспом по `err.message`. Классификация `SessionRevokedError`
для 401 идёт тем же путём (сопоставление по тексту/коду RPC-ошибки), это не новый
паттерн для кодовой базы.

`formatError()` (`src/core/errors.ts:19-22`) уже рендерит `.cause`, если он `instanceof
Error` — механизм переиспользуется, новый способ показа причины не нужен.

`disableTask(agentId, type)` (`src/core/db/tasks.ts:139-145`) отключает одну задачу;
используется сегодня только для `join-queue` при исчерпании очереди (терминальный
статус, `dispatcher.ts:254-257`). У отзыва сессии другая семантика: умирают ВСЕ задачи
агента одновременно, не одна за другой по мере срабатывания расписания — именно так вёл
себя инцидент 2026-07-06 (5 агентов ретраили `AUTH_KEY_UNREGISTERED` на каждом типе
задачи независимо, неделю, пока не заметил человек).

Родственный, не пересекающийся change: `openspec/changes/report-agent-isolation`
(активный, не архивирован) решает соседствующую проблему той же природы — изолирует
получателя ежедневных отчётов от потери сессии любым конкретным рабочим агентом.
Пересечения в коде нет (другие файлы), но оба опираются на один и тот же инцидент
2026-07-16 как источник данных.

## Goals / Non-Goals

**Goals:**
- Причина сбоя подключения различима по одному только типу/сообщению брошенной
  ошибки — без чтения `.cause` или сырых логов попыток.
- Подтверждённый отзыв сессии (`SessionRevokedError`) автоматически останавливает все
  задачи агента, а не только текущую — снимает необходимость ручного обнаружения на
  масштабе 45+ агентов.
- Существующие `instanceof ClientNotConnectedError` проверки (control-flow «прогон
  мёртв») продолжают работать без правок в местах использования.

**Non-Goals:**
- Не классифицировать `FROZEN_METHOD_INVALID` и другие RPC-ограничения, всплывающие не
  на `connect()`/`getMe()`, а на конкретных операциях (`sendMessage`, `getDialogs` и
  т.п.) — это отдельный слой (ошибки операций, не ошибки подключения), отдельная работа.
- Не разносить heartbeat-таймеры агентов шире по времени (`RandomizedDelaySec`,
  `AccuracySec`) — обсуждалось как причина волны `ConnectTimeoutError` 2026-07-17, но
  это тюнинг systemd-инфраструктуры сервера, не классификация ошибок в коде; отдельная
  задача.
- Не вводить общий механизм повторных попыток/backoff поверх `MAX_ATTEMPTS` — вне
  скоупа, поведение ретраев не меняется.
- Не трогать `discovery/similar.ts` — три новых класса наследуют
  `ClientNotConnectedError`, существующие `instanceof`-проверки там продолжают ловить
  все три случая без изменений в файле.

## Decisions

**Три конкретных класса, не один класс с полем-дискриминантом.** Рассматривался вариант
`ClientNotConnectedError` с полем `reason: "missing_config" | "timeout" | "revoked"` —
отклонён: имя брошенной/залогированной ошибки оставалось бы одним и тем же
(`ClientNotConnectedError`) для всех трёх причин, различие ушло бы внутрь поля, которое
не видно при беглом чтении лога без специального кода чтения. Отдельные классы (как уже
устроены `FloodWaitError`/`FloodAbortError`/`ChannelSkipError` в этой кодовой базе —
каждый означает ровно одно событие) делают причину видимой по одному имени класса и
`message`, без просмотра дополнительных полей.

**`ClientNotConnectedError` становится абстрактным маркером-предком, не удаляется.**
Альтернатива — убрать общий класс вовсе, перечислять все три конкретных класса в каждом
`instanceof`-месте (`dispatcher.ts` + 4 места в `discovery/similar.ts`). Отклонено:
дублирует один и тот же список условий в пяти местах (нарушает DRY,
`coding-standards.md` §1); при появлении четвёртого класса причины пришлось бы править
все пять точек. Маркер-предок никогда не инстанцируется напрямую — в логах/отчётах
всегда фигурирует конкретный подкласс (`this.name` каждый выставляет сам), предок
невидим снаружи. Это использование наследования для полиморфного `instanceof`
(LSP-совместимо), не сокрытие информации о причине.

**Причина RPC 401 классифицируется по `err.code`, не по regex на `err.message`.**
GramJS отдаёt `err.code`/`err.errorMessage` как структурные поля уже на этапе
`RPCMessageToError` (см. Context) — сравнение `err.code === 401` надёжнее, чем
парсинг форматированной строки `err.message`, которая теоретически может измениться при
апдейте GramJS. Raw `err.errorMessage` (например `"AUTH_KEY_UNREGISTERED"`) кладётся в
сообщение `SessionRevokedError` как есть — не переформулируется.

**`disableAllTasks(agentId)` — новая функция, не цикл `disableTask` по всем типам
задач агента со стороны диспетчера.** Отклонён вариант «диспетчер сам получает список
типов задач агента и вызывает `disableTask` в цикле» — требует SELECT списка типов
до UPDATE, два похода в БД вместо одного, и переносит знание о форме таблицы `tasks`
(колонка `agentId` без фильтра `type`) из `core/db/tasks.ts` в `dispatcher.ts`, нарушая
инкапсуляцию модуля БД.

**Нет действия при `MissingAccountConfigError`.** Решение пользователя: отсутствие
`sessionString`/`apiId`/`apiHash` может быть временным состоянием агента, ещё не до
конца настроенного оператором — авто-отключение задач здесь было бы преждевременным.
Причина всё равно видна в логе/`runs.error` — просто без автоматического действия
поверх неё.

**Нет действия при `ConnectTimeoutError`.** Решение пользователя: временная перегрузка
сети/VPS/прокси — самовосстанавливающееся состояние, отключать задачи агента при
таймауте означало бы останавливать рабочих агентов из-за проблемы инфраструктуры, не
их собственной сессии.

## Risks / Trade-offs

- **[Риск] Классификация по `err.code === 401` шире, чем только
  `AUTH_KEY_UNREGISTERED`** — код 401 у GramJS покрывает весь класс `UnauthorizedError`
  (`AUTH_KEY_INVALID`, `SESSION_REVOKED`, `USER_DEACTIVATED` и т.п., все — MTProto-коды
  401). → Осознанно: все они означают «эта конкретная сессия не годится», отключение
  всех задач агента — корректная реакция на любой из них, отдельно разбирать каждый
  текст не нужно для решения «отключить».
- **[Trade-off] `ClientNotConnectedError` — публичное имя, привычное по логам
  предыдущих недель (`AUTH_KEY_UNREGISTERED`/timeout-инциденты в proposal.md) —
  становится абстрактным и больше не встречается в логах напрямую.** → Поиск по старым
  логам ("Client not connected") продолжит находить только историю до этого change;
  начиная с деплоя в логах — только конкретные имена. Это ожидаемо и есть цель change.

## Migration Plan

Миграции данных нет. Обратная совместимость: `discovery/similar.ts` и любой другой код,
проверяющий `instanceof ClientNotConnectedError`, продолжает работать без изменений —
три новых класса являются его подтипами.

Откат: убрать классификацию в `ensureClient` (вернуть `return null` + generic throw),
удалить три класса и `disableAllTasks` — данные (`tasks.db`) не пострадают, т.к.
`enabled=0` — обратимое состояние (задачу можно включить обратно тем же путём, что и
любую другую).

## Open Questions

Нет — три причины, действие на каждую и форма классификации (структурные поля GramJS,
не regex; отдельные классы, не дискриминант; маркер-предок, не дублирование
`instanceof`) согласованы с пользователем в ходе обсуждения.
