## Context

`skills/tg-agent-create/SKILL.md` — markdown-сценарий, исполняемый LLM пошагово: собрать данные →
`openclaw config set allowFrom` → ~10 отдельных bash-вызовов на создание агента/workspace/
биндинга → авторизация сессии (`tg_auth_send_code`/`tg_auth_sign_in`, тулы над
`TelegramService.authSendCode`/`authSignIn`, `src/core/telegram/service.ts:1461`) → запись
`tg-account.json` → запрос у юзера полного текста `SOUL.md` → `verify-agent.sh`. Сегодня прокси
(`proxy.host/port/username/password`) — часть входных данных Шага 1, создаётся человеком вручную
на asocks до запуска скилла.

`mobile-proxy-provisioning` (отдельный, уже реализованный change) автоматизировала подбор
рабочего прокси для **существующих** агентов: `src/scripts/provision-mobile-proxy.ts` создаёт
кандидата на asocks (`src/core/proxy/asocks-client.ts`), проверяет его через
`TelegramService.verifyConnection` (override прокси поверх уже загруженного `AccountConfig`,
`ensureClient` с `sessionString`, который у существующего агента уже есть), при неудаче удаляет
и создаёт следующего — до `--max-attempts`. Страна/регион/город передаются флагами при каждом
запуске, не сохраняются.

Для **нового** агента `sessionString` не существует до Шага с `authSignIn` — а сам вход
(`authSendCode`) требует прокси уже на этапе отправки кода (создаёт голый `TelegramClient` с
переданным `proxy`, вызывает `client.connect()` до какого-либо `sessionString`). Значит подбор
прокси для создания должен идти **до** авторизации, а не после, и проверка кандидата не может
использовать `ensureClient`/`verifyConnection` (они требуют `sessionString`).

## Goals / Non-Goals

**Goals:**
- Убрать из Шага 1 создания агента ручной ввод `proxy.host/port/username/password` — прокси
  подбирается автоматически тем же способом (asocks), что и в репейр-цикле.
- Убрать передачу полного текста `SOUL.md` через юзера/модель — одна персона на всех агентов,
  копируется файл.
- Свернуть ~10 последовательных bash-вызовов создания структуры агента в один скрипт.
- Сохранить `countryCode/state/city` в `tg-account.json`, чтобы репейр-цикл
  (`mobile-proxy-provisioning`) не запрашивал регион повторно.
- Не отправлять юзеру/в Telegram реальный код авторизации при каждой неудачной попытке прокси —
  верификация кандидата до сессии не должна использовать `Api.auth.SendCode`.

**Non-Goals:**
- Параллельная обработка кандидатов прокси или нескольких агентов одновременно — вне скоупа (то
  же решение, что в `mobile-proxy-provisioning`: последовательно, ради стабильности VPS).
- Смена персоны (`SOUL.md`) на несколько разных шаблонов — сейчас одна персона на всех, вариант
  «несколько персон» не реализуется, пока не появится реальная потребность.
- Архивация change `mobile-proxy-provisioning` в `openspec/specs/` — административное действие,
  не блокирует эту работу и не входит в неё.
- Автоматизация первичной регистрации TG-номера через эмулятор — вне скоупа, остаётся ручным
  шагом чек-листа перед запуском скилла.

## Decisions

**Верификация кандидата прокси до сессии — новый лёгкий probe, не переиспользование
`authSendCode`.** Альтернатива — гонять `authSendCode` в цикле по кандидатам, раз он уже делает
`client.connect()` с переданным прокси. Отклонено: `authSendCode` сразу следом шлёт
`Api.auth.SendCode` — реальный код в Telegram/SMS на каждую попытку. Telegram жёстко лимитирует
повторные запросы кода на один номер; при `--max-attempts=5` можно исчерпать этот лимит ещё до
входа в аккаунт и сломать создание агента целиком. Новый метод `TelegramService.probeProxy({
apiId, apiHash, proxy })` делает только `client.connect()` + `disconnect()` — тот же хендшейк,
чей обрыв (~350мс после `InvokeWithLayer`) и диагностировали в `deterministic-connection-errors`,
без прикладного RPC поверх него. Настоящий `authSendCode` вызывается один раз, уже с
подтверждённым прокси.

**Создание кандидата прокси для нового агента — отдельный скрипт, не расширение
`provision-mobile-proxy.ts`.** Альтернатива — добавить в существующий скрипт режим «без сессии».
Отклонено: верификация принципиально другая (`probeProxy` вместо `ensureClient`/
`verifyConnection`), и входной контракт другой (`provision-mobile-proxy.ts` принимает список уже
существующих `agentId` с готовым `tg-account.json`; create-флоу работает до того, как
`tg-account.json` вообще существует). Общий код (создание/удаление на asocks) переиспользуется
из `asocks-client.ts` — дублируется только сам управляющий цикл (создать → проверить → при
неудаче удалить и повторить), который в обоих местах короткий.

**`countryCode/state/city` — на `ProxyConfig`, а не отдельная структура.** Это атрибуты
конкретного прокси (при смене прокси регион обычно тот же, но не обязан быть жёстко привязан к
аккаунту навечно — юзер может явно захотеть сменить регион при ремонте), логично хранить рядом с
остальными полями прокси, симметрично уже существующему `name`.

**Пошаговый подбор локации через списки asocks — опциональный режим, не единственный.**
Обязательный пошаговый подбор для всех был бы проще в реализации, но принудительно добавляет 3
сетевых обращения к asocks там, где оператор и так точно знает нужный регион (частый случай —
агенты создаются пачками для одного и того же гео). Оставлен выбор в начале Шага 1: ввод готовых
значений текстом (без обращений к asocks до самого создания кандидата) или пошаговый подбор
списками (`/dir/countries` → `/dir/states` → `/dir/cities`), который защищает от опечаток —
`resolveLocation` (`asocks-client.ts`) сейчас бросает жёсткую ошибку на несовпадение имени.

**Создание структуры агента — bash-скрипт, не TypeScript.** Симметрично уже существующему
`skills/tg-agent-create/scripts/verify-agent.sh`: это чистые CLI/FS-операции (`openclaw agents
add`, `config get/set bindings`, `mkdir`, `cp`, `cat`, `touch`) без обращения к GramJS/БД — TS
здесь не даёт дополнительной пользы, только `tsx`-обвязку.

## Risks / Trade-offs

- **[Риск] Пул мобильных прокси asocks в конкретном городе/регионе может быть системно
  заблокирован целиком** (тот же риск, что в `mobile-proxy-provisioning`) — при исчерпании
  `--max-attempts` создание агента не может продолжиться без прокси (он нужен для входа). →
  Митигация: явный отчёт «прокси не найден за N попыток», решение о смене региона — за
  оператором (повторный запуск Шага 1 с другим регионом), не автоматизируется.
- **[Trade-off] Последовательный перебор кандидатов при плохом пуле удлиняет создание агента**
  (до `--max-attempts` циклов create+probe). → Осознанно принято ради простоты и безопасности
  для CPU VPS, то же решение, что в `mobile-proxy-provisioning`.
- **[Риск] `probeProxy` может не поймать все случаи, ловившиеся `authSendCode`** — если проблема
  не в хендшейке, а в чём-то, что проявляется только при реальном RPC поверх соединения. →
  Не подтверждено на этапе дизайна: вся известная на сегодня диагностика (`deterministic-
  connection-errors`) показывает обрыв именно на хендшейке (`connect()`), до прикладных вызовов —
  риск считается низким, но при реализации стоит перепроверить на 1-2 живых кандидатах перед
  массовым использованием.
- **[Риск] Юзер выбирает пошаговый подбор, но на каком-то шаге список пуст или не содержит нужный
  регион** (asocks может не покрывать все страны/регионы мобильными прокси). → Явно сообщить
  юзеру и дать вернуться на предыдущий уровень (например, выбрать другую страну), не блокировать
  создание агента без выхода.

## Migration Plan

Миграции данных нет — `ProxyConfig.countryCode/state/city` опциональны, существующие
`tg-account.json` без них продолжают работать (репейр-цикл просто запрашивает регион у юзера, как
раньше). `skills/tg-agent-create/SKILL.md` переписывается целиком — старая версия перестаёт
использоваться после мёржа, отдельного переходного периода не требуется (создание агента —
разовое интерактивное действие, не фоновый процесс).

Откат: вернуть предыдущую версию `SKILL.md` (ручной ввод прокси + текст SOUL.md), убрать новый
скрипт create-флоу и `probeProxy` — поля `countryCode/state/city` в `ProxyConfig` можно оставить
(не мешают, просто перестают заполняться для новых агентов).
