## ADDED Requirements

### Requirement: Agent detects the last post of a fixed, already-closed calendar day
Для каждого активного канала (`status` — `NULL`, `format_error` или
`only_comment`) с публичным username `monitor-v4` SHALL раз в 5 часов
проверять последний пост канала за фиксированный целевой день —
`сегодня минус 2 суток` по календарю `Asia/Yekaterinburg` — через публичное
веб-превью (`t.me/s/<username>`), не используя MTProto-сессию аккаунта для
этой проверки. Каналы без публичного username SHALL оставаться вне охвата
этого требования. Посты вне целевого дня (более ранние или более поздние,
включая вчерашние и сегодняшние) SHALL NOT рассматриваться этим требованием.

#### Scenario: В целевом дне есть посты
- **WHEN** у канала есть один или несколько постов с датой публикации внутри
  целевого дня (`[сегодня−2 суток 00:00, сегодня−1 суток 00:00)`)
- **THEN** агент определяет среди них пост с самой поздней датой публикации
  как кандидата этого дня

#### Scenario: В целевом дне постов не было
- **WHEN** у канала нет ни одного поста с датой публикации внутри целевого
  дня
- **THEN** агент не находит кандидата за этот день и не выполняет дальнейших
  действий по §2b в этом прогоне; повторная попытка для того же дня SHALL NOT
  выполняться в последующих прогонах

#### Scenario: Пост совпадает с уже обработанным
- **WHEN** id найденного кандидата целевого дня совпадает с сохранённым
  `lastSeenChannelPostId` канала
- **THEN** агент не выполняет дальнейших действий по этому посту

#### Scenario: Найден непроверенный кандидат целевого дня
- **WHEN** id найденного кандидата отличается от `lastSeenChannelPostId`
- **THEN** пост передаётся на решение о комментировании (эвристический
  отсев + LLM), тем же способом, что уже определён для `monitor-v3`

### Requirement: Day resolution is cached per channel until the target day changes
`monitor-v4` SHALL сохранять результат поиска последнего поста целевого дня
(найденный id поста или признак «постов не было») на канал, привязанный к
дате целевого дня, и SHALL переиспользовать этот результат без повторного
обращения к веб-превью, пока вычисленный целевой день на очередном прогоне
совпадает с сохранённым.

#### Scenario: Целевой день не изменился с прошлого прогона
- **WHEN** на текущем прогоне вычисленный целевой день канала совпадает с
  ранее сохранённым
- **THEN** агент использует сохранённый результат (найденный пост или
  признак «постов не было») без обращения к `t.me/s/<username>`

#### Scenario: Целевой день сменился
- **WHEN** на текущем прогоне вычисленный целевой день канала отличается от
  ранее сохранённого (или ранее не сохранялся)
- **THEN** агент выполняет поиск последнего поста нового целевого дня через
  веб-превью и сохраняет результат (найденный id или признак «постов не
  было»), привязанный к новому целевому дню

#### Scenario: Поиск не удался (не путать с «постов не было»)
- **WHEN** проверка последнего поста целевого дня не удалась (сеть, HTTP-
  ошибка, неразобранная разметка на любой странице пагинации)
- **THEN** сохранённый результат для канала SHALL NOT перезаписываться,
  канал не считается обработанным по этому требованию в этом прогоне,
  следующий прогон повторяет поиск с начала

### Requirement: monitor-v4 reuses monitor-v3's channel state machine and error handling
Вне ветки обнаружения поста (Requirement «Agent detects the last post of a
fixed, already-closed calendar day») `monitor-v4` SHALL использовать ту же
статусную модель канала (`status` — `NULL`/`format_error`/`only_comment`/
`sleep`/`banned`/`suspend`), то же поле `lastSeenChannelPostId` для защиты от
повторной реакции, тот же переход в `only_comment` на 2 суток и `sleep` на
дополнительные сутки после успешной отправки комментария, ту же проверку
удалённых сообщений агента и ту же классификацию ошибок отправки
(`FLOOD_WAIT`, `PEER_FLOOD`, бан на запись, запрет формата), что определены
для `monitor-v3`.

#### Scenario: Успешная отправка комментария
- **WHEN** `monitor-v4` успешно отправляет комментарий к посту целевого дня
- **THEN** `status` канала становится `only_comment`, `lastSeenChannelPostId`
  и `watchedThreadRootMsgId` сохраняются — тем же способом, что и у
  `monitor-v3`

#### Scenario: Канал под ограничением не обрабатывается
- **WHEN** `status` канала — `banned`, `suspend` или `sleep`
- **THEN** канал не входит в список каналов, обрабатываемых `monitor-v4` на
  этом прогоне
