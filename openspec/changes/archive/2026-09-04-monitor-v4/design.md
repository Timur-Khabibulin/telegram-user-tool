## Context

`monitor-v3` (`src/skills/monitor-v3.ts`, §2b) в ветке «Открыт» реагирует на
последний пост канала по правилу свежести R1: пост учитывается, если с
момента публикации прошло меньше 24ч (`POST_FRESHNESS_FIRST_COMMENT_MAX_AGE_SECONDS`,
скользящее окно от текущего момента). Обнаружение — через публичное
веб-превью (`t.me/s/<username>`, `src/core/channel-preview/preview.ts`,
`fetchLatestChannelPost`), которое берёт единственный последний элемент ленты
(до ~20 последних постов на странице) — этого достаточно, потому что нужен
только самый свежий пост.

Нужен режим с другим правилом отбора поста: не «недавний», а «последний пост
уже полностью закрытого календарного дня — позавчера» (окно
`[сегодня−2 суток, сегодня−1 суток)` по календарю). Это не сужение/расширение
порога R1, а другая ось отбора (фиксированный день вместо скользящего окна от
`now`), поэтому не совместимо с текущей формулировкой R1 и оформляется отдельным
скиллом `monitor-v4`, по прецеденту `monitor` → `monitor-v2` → `monitor-v3`
(design.md `monitor-v3`, `post-freshness-gate`): предыдущая версия не
меняется ни строкой, новая — независимо включаемый `TaskType`.

Остальной алгоритм `monitor-v3` (§0 подготовка, §1 проверка удалённых
сообщений, §2a `only_comment`, обработка ошибок отправки, переход в `sleep`)
не завязан на правило свежести и переиспользуется без изменений — тем же
приёмом копирования-адаптации, каким `monitor-v3` уже переиспользовал часть
`monitor-v2`.

## Goals / Non-Goals

**Goals:**
- Обнаруживать и комментировать последний пост канала за фиксированный,
  уже закрытый календарный день (позавчера, `Asia/Yekaterinburg`), а не
  самый свежий пост.
- Не тратить лишние HTTP-запросы к `t.me/s/` на повторный поиск поста дня,
  пока целевой день не сменился (кэш резолва на канал).
- Максимально переиспользовать `monitor-v3` (подготовка, `only_comment`,
  обработка ошибок отправки, статусная модель) без изменений в самом
  `monitor-v3`.

**Non-Goals:**
- Изменение поведения `monitor-v3`/`fetchLatestChannelPost` — не трогается
  ни строкой, `monitor-v4` работает параллельно, а не вместо.
- Защита от одновременного включения `monitor-v3` и `monitor-v4` на одного
  агента — сознательно не делается (см. Decisions, тот же прецедент, что уже
  принят для `monitor`/`monitor-v2`).
- Fallback на более ранний день, если у позавчера не было постов — день
  пропускается безвозвратно, следующая проверка того же дня не повторяется.
- Ограничение глубины пагинации веб-превью — не вводится (см. Risks).

## Decisions

**1. Правило отбора поста — фиксированное окно календарного дня, не
скользящее окно свежести.**
Целевой день `D = сегодня − 2 суток` в `Asia/Yekaterinburg` (та же таймзона,
что уже использует `docs/task-scheduling.md` для каданса `monitor-v3`).
Окно — `[startOfDay(D), startOfDay(D+1))` в unix-секундах. Пост учитывается,
если его дата попадает в это окно; из всех таких постов берётся последний по
времени (максимальная дата внутри окна). Постов вне окна (в т.ч. вчерашних и
сегодняшних) v4 не видит вовсе — они не «слишком свежие» в смысле какого-то
порога, они структурно вне области поиска.

Альтернатива (отклонена) — задать это как «R1 с порогом от 24ч до 48ч» на
уровне того же гейта, что и `monitor-v3`: не работает, потому что «48ч»
измерялось бы от `now`, а нужен фиксированный календарный день, который не
сдвигается вместе с временем суток внутри самого дня проверки.

**2. Поиск поста дня — постраничный обход `t.me/s/<username>` через
`?before=`, новая функция в `channel-preview/preview.ts`.**
`fetchLatestChannelPost` берёт только последний элемент ленты — этого
достаточно для «самый свежий пост», но не для «последний пост конкретного
дня»: если канал успел опубликовать больше ~20 постов после конца целевого
дня (очень активный канал), нужная запись выпадает из первой страницы.
Новая функция `fetchLastPostInDateRange(username, startSec, endSec, log)`
идёт по ленте от новых постов к старым (порядок в HTML — от старых к новым,
поэтому итерация — в обратном порядке DOM-узлов):
- пост с датой `>= endSec` — пропускается, идём к более старому;
- первый пост с датой `< endSec` и `>= startSec` — искомый (последний в
  окне, т.к. пришли к нему от более новых постов) — возврат;
- пост с датой `< startSec`, ни разу не встретив попадание в окно — окно
  пусто (в этом дне постов не было) — возврат `{ ok: true, post: null }`;
- если вся текущая страница `>= endSec` — подгрузить следующую страницу
  (`?before=<id самого старого поста страницы>`) и продолжить.
Сетевые/парсинг-ошибки — `{ ok: false }`, тем же контрактом, что и
`fetchLatestChannelPost` (не путать с «постов нет» — см. Risks).

Переиспользование селекторов (`tgme_widget_message_wrap`,
`tgme_widget_message_date`, `tgme_widget_message_bubble`) и cheerio-парсинга —
как в `fetchLatestChannelPost`, без новой зависимости.

**3. Кэш резолва целевого дня — 2 новых nullable-поля в `channels`, не
отдельная таблица.**
```
lastCheckedTargetDate   TEXT NULL   -- "YYYY-MM-DD" (Asia/Yekaterinburg) целевого дня
lastCheckedTargetPostId INTEGER NULL -- id найденного поста; NULL = день резолвлен, постов не было
```
На каждом прогоне: вычислить `targetDate` (строка даты позавчера). Если
`channel.lastCheckedTargetDate === targetDate` — обход `t.me/s/` для этого
канала не выполняется вовсе, используется закэшированный `lastCheckedTargetPostId`
(включая `null`, означающий «пусто»). Если день сменился — выполнить поиск
(Decision 2) и перезаписать оба поля результатом (в т.ч. `null`, если постов
не было — это тоже валидный резолв, не «попробовать снова в следующий раз»).

Отдельная таблица с TTL (как `thread_post_dates` у `post-freshness-gate`) не
нужна: там кэш растёт по числу веток и требует чистки, здесь — ровно одна
строка на канал, которая сама перезаписывается при смене дня. Аналогия —
`lastSeenChannelPostId`/`watchedThreadRootMsgId` у `monitor-v3`: те же простые
nullable-поля на канал для «текущего актуального значения».

Этот кэш — не то же самое, что защита от повторной реакции
(`lastSeenChannelPostId`): кэш экономит сетевые запросы на *обнаружение*
поста дня, `lastSeenChannelPostId` — как и в `monitor-v3`, защищает от
повторной *реакции* на уже обработанный пост. Оба поля используются
последовательно (см. Migration Plan / поток ниже).

**4. `status`, `lastSeenChannelPostId`, `watchedThreadRootMsgId` — общие
поля `channels` с `monitor-v3`, не отдельные v4-версии.**
`channels` — общая таблица на агента (не на скилл/версию монитора).
Заведение отдельных v4-полей под статусную модель и защиту от повторной
реакции дублировало бы то, что уже есть, ради сценария «оба варианта
включены на одном агенте одновременно» — который явно не защищается и для
`monitor`/`monitor-v2` (`post-freshness-gate`, риск 2). Решение того же рода:
взаимоисключающее включение `monitor-v3`/`monitor-v4` — ответственность
оператора при настройке `tasks`/`scheduler-control`, не код. Новые поля
кэша дня (Decision 3) — не конфликтуют, потому что `monitor-v3` их вообще не
знает и не пишет.

**5. Новый скилл `monitor-v4.ts`, копия-адаптация `monitor-v3.ts`.**
Тот же приём, каким `monitor-v3` уже разошёлся с `monitor-v2` (комментарий в
шапке `monitor-v3.ts`, design.md `monitor-v3` решение 7): шаги, совпадающие
по сути (§0, §1, §2a, обработка ошибок отправки), копируются и адаптируются
напрямую, а не выносятся в общий модуль — тот же самый прецедент, не
пересматривается заново в этом change. Меняется только §2b (обнаружение
поста): вызов `fetchLatestChannelPost` + проверка возраста заменяется на
проверку кэша дня (Decision 3) → при промахе `fetchLastPostInDateRange`
(Decision 2) → сравнение результата с `lastSeenChannelPostId`, дальше —
без изменений (отсев текста, LLM-решение, поиск служебной копии в чате
обсуждения, отправка, переход в `only_comment`).

## Risks / Trade-offs

- [Риск] Постраничный обход без ограничения глубины (`?before=`) — на очень
  активном канале первый резолв нового целевого дня может уйти в десятки
  последовательных HTTP-запросов подряд (осознанно принято, без потолка) →
  Митигация: только логирование числа страниц на канал для последующего
  наблюдения; отдельная защита не вводится в этом change.
- [Риск] Неразличение «постов не найдено» (окно пусто, легитимный резолв) и
  «поиск не удался» (сеть/пагинация оборвалась ошибкой) — если не развести
  эти два исхода, канал с оборвавшимся поиском на активном канале будет
  ошибочно считаться «пустым днём» и кэшироваться как `null` навсегда для
  этого дня → Митигация: `fetchLastPostInDateRange` возвращает `{ ok: false }`
  при любой сетевой/парсинг-ошибке на любой странице пагинации (не только
  первой); кэш (`lastCheckedTargetDate`/`lastCheckedTargetPostId`)
  перезаписывается только при `ok: true` — при `ok: false` канал в этом
  прогоне не считается обработанным по §2b, кэш не трогается, следующий
  прогон (через 5ч) повторит попытку с начала.
- [Риск] Неофициальная разметка `t.me/s/` (в т.ч. поведение `?before=`)
  может измениться без предупреждения — тот же риск, что уже принят
  `monitor-v3` для `fetchLatestChannelPost`, не новый для этого change.
- [Trade-off] Взаимоисключающее использование `status`/`lastSeenChannelPostId`/
  `watchedThreadRootMsgId` с `monitor-v3` (Decision 4) — если оператор всё же
  включит оба варианта на одного агента, поведение непредсказуемо (гонка
  записи полей). Явно принятый риск, тот же прецедент, что и у
  `monitor`/`monitor-v2`.

## Migration Plan

1. Миграция `channels`: `ALTER TABLE ... ADD COLUMN lastCheckedTargetDate TEXT`,
   `ADD COLUMN lastCheckedTargetPostId INTEGER` — аддитивная, с проверкой
   через `PRAGMA table_info` (тот же паттерн, что `lastSeenChannelPostId`/
   `watchedThreadRootMsgId` у `monitor-v3`, `cpuUserMs`/`cpuSystemMs` у `runs`).
2. Задеплоить `monitor-v4.ts` + регистрацию `TaskType`/`SKILLS` — код
   неактивен, пока ни у одного агента не включена задача `monitor-v4`.
3. Включить `monitor-v4` точечно на одном-двух агентах через
   `scheduler-control` (без одновременного `monitor-v3` на тех же агентах —
   Decision 4), понаблюдать за логами пагинации/кэша.
4. Расширить на остальных агентов — по решению оператора, вне этого change.

Откат: выключить задачу `monitor-v4` в `tasks` для агента (тот же механизм,
что и для любого `TaskType`); новые поля `channels` остаются неиспользуемыми,
не мешают `monitor-v3`.
