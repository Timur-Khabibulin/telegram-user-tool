## Context

`docs/telegram-errors.md` — единый каталог 35 ошибок MTProto/GramJS с целевым
(to-be) поведением; этот change реализует то, что там помечено как ещё не
сделанное. Источник истины по конкретным реакциям — сам документ; здесь
фиксируются только архитектурные решения о том, где и как эти реакции
реализуются в коде.

Текущее состояние обработки ошибок разрознено:

- `ensureClient()` (`service.ts:233-314`) классифицирует только отказ
  подключения — три подкласса `ClientNotConnectedError`
  (`MissingAccountConfigError`/`ConnectTimeoutError`/`SessionRevokedError`,
  введены `deterministic-connection-errors`, задеплоено, спек ещё не
  архивирован в `openspec/specs/`). `SessionRevokedError` сегодня приводит к
  `disableAllTasks(agentId)` — `enabled=0` для всех строк `tasks`.
- `sendDm()` (`service.ts:737-818`) и `joinDiscussionGroups()`
  (`service.ts:884-1017`) классифицируют ошибки операции по
  `err.message.includes(...)` и возвращают типизированный результат
  (`SendDmResult`/`JoinResult`), не бросают исключение.
- `monitor.ts` и `monitor-v2.ts` независимо друг от друга реализуют
  идентичную обёртку `sendReply`, включая regex `/CHAT_WRITE_FORBIDDEN/i` —
  скопированную, не переиспользуемую.
- Ретрай `FLOOD_WAIT`/`SLOWMODE_WAIT_N` продублирован трижды на двух разных
  архитектурных уровнях: `skills/util.ts:withFloodRetry` (1 ретрай, для
  ответов в группе), `service.ts` внутри `sendDm` (1 ретрай, для DM),
  `service.ts:callWithFloodHandling` внутри `joinDiscussionGroups` (1 ретрай,
  для вступления). Ни одна не покрывает требуемые доком до 2 повторов.
- `USER_DEACTIVATED`/`USER_DEACTIVATED_BAN`, `FROZEN_PARTICIPANT_MISSING`,
  `FROZEN_METHOD_INVALID`, `PEER_FLOOD` — сегодня не классифицируются нигде,
  кроме `USER_DEACTIVATED` внутри `sendDm` (частично, только для DM).
- `leave-banned-channels` (openspec-change, 19/23, не архивирован) уже
  реализует `banned_channels`/`leaveChannel`/`purgeChannelData`, но
  `purgeChannelData` удаляет данные шире, чем требует `telegram-errors.md`
  №24 (to-be) — доке отдан приоритет (решение пользователя в ходе
  обсуждения), `leave-banned-channels` донастраивается под неё.

## Goals / Non-Goals

**Goals:**
- Каждая ошибка из каталога классифицируется в ровно одном месте
  (`core/telegram/errors.ts`), независимо от того, сколько скиллов её сейчас
  вызывает или будет вызывать в будущем.
- Реакция на ошибку — не единая функция, а два разных механизма в
  зависимости от природы ошибки (см. Decisions): аккаунтные ошибки
  перехватываются один раз на самом низком общем уровне
  (`TelegramService`/`dispatcher.ts`), операционные — возвращаются
  типизированным результатом тому скиллу, который владеет затронутой
  сущностью (`channels`/`join_queue`/`dm_candidates`).
- Три копии ретрая флуда сводятся к одной реализации с политикой до 2
  повторов.
- `agent_restrictions` становится единственным механизмом остановки задач
  агента на аккаунтном уровне, заменяя `disableAllTasks`/`tasks.enabled=0`
  для этой цели (см. Decisions).

**Non-Goals:**
- Ротация прокси при повторных TCP-таймаутах (№10) — точное число повторов
  не задано ни доком, ни пользователем («уточняется отдельно» — прямая цитата
  из `telegram-errors.md`); реализация откладывается до отдельного решения.
- Механизм снятия `channels.status = 'format_error'` — дока прямо помечает
  это как открытый вопрос, отложенный на отдельное обсуждение. Снятие
  реализуется только вручную (прямое изменение в БД), автоматического пути
  нет.
- Полная формализация капабилити `join-queue` (добавление ссылок, claim
  батча) — новый спек `join-queue` в этом change покрывает только
  статусную/ошибочную модель, требуемую `telegram-errors.md`.
- Изменение эвристики выбора прокси/провижининга (`mobile-proxy-provision`) —
  вне скоупа, только классификация и подсчёт для будущего триггера.

## Decisions

**Один классификатор, два формата вывода — не единая функция с одним
выходом.** Для ошибок, которые ДОЛЖНЫ останавливать прогон/агент
(аккаунтные — №1-6, 8, 11, 12, 29), классификатор возвращает конкретный
подкласс `Error` — по прецеденту `deterministic-connection-errors`
(«Три конкретных класса, не один класс с полем-дискриминантом» —
`openspec/changes/deterministic-connection-errors/design.md`, Decisions):
имя класса должно быть видно в логе без чтения дополнительного поля. Для
ошибок операции (№13-35, кроме уже покрытых №23/24 в контексте отправки),
которые являются ожидаемым бизнес-исходом, классификатор возвращает
строку-тег внутри уже существующего паттерна типизированного результата
(`SendDmResult`-подобный) — по прецеденту, который уже есть в коде для DM.
Единая функция `classifyTelegramError(err)` внутри
`core/telegram/errors.ts` реализует оба выхода через один `switch`/таблицу
по `err.errorMessage`/`err.code`; какой из двух выходов использовать —
решает не классификатор, а вызывающий уровень (см. следующее решение).

**Аккаунтные ошибки перехватываются один раз — общей обёрткой вокруг MTProto
вызовов в `TelegramService`, не в каждом скилле.** Обёртка
(`invokeChecked`/аналог, вокруг `client.invoke`/`sendMessage`/`getMessages`
и т.п.) классифицирует ошибку; для аккаунтных — бросает типизированный
класс, который дальше ловится в ОДНОЙ точке `dispatcher.ts` (расширение уже
существующего catch-блока `SessionRevokedError`/`ClientNotConnectedError`,
`dispatcher.ts:229-241`). Альтернатива — добавлять проверку в каждом скилле,
который может столкнуться с этой ошибкой — отклонена: доказано кодовой
базой на примере `CHAT_WRITE_FORBIDDEN`, продублированного между `monitor.ts`
и `monitor-v2.ts` без переиспользования, когда для этого не было общей
точки.

**`agent_restrictions` заменяет `disableAllTasks`/`tasks.enabled=0` как
механизм остановки задач агента.** Дока не упоминает `tasks.enabled` вообще,
только `agent_restrictions`, проверяемую диспетчером перед запуском. Держать
оба механизма для одного и того же триггера (отзыв сессии) дублировало бы
состояние — нарушает «один факт — один дом» (`agent-playbook.md`).
`agent_restrictions` строго лучше для этой цели: одна строка вместо N (по
числу типов задач), проверяется до подключения к Telegram (`tasks.enabled=0`
проверяется диспетчером неявно через `WHERE enabled=1` в `getDueTasks` —
эквивалентно по эффекту, но не даёт TTL для временных ограничений).
`disableTask`/`tasks.enabled` остаются для несвязанной цели — терминальное
состояние отдельного типа задачи (`join-queue`, когда очередь исчерпана,
`task-scheduler` Requirement «Конечные задачи завершаются терминальным
статусом») — это другая сущность («эта задача больше не нужна» vs «этот
агент временно/постоянно не может работать»), не трогается.

**Флуд-ретрай сводится к одной функции на уровне `service.ts`, не
`skills/util.ts`.** Сегодня `withFloodRetry` живёт в `skills/`, а две другие
копии — в `service.ts`. Перенос в `service.ts` выбран, а не наоборот, потому
что: (а) там уже живёт `parseFloodWait`/`MAX_INLINE_FLOOD_WAIT_SECONDS`,
которые использует и текущий `skills/util.ts`, импортируя их оттуда — сама
логика уже физически ближе к `service.ts`; (б) `service.ts` — единственное
место, которое знает про все три операции (`sendMessage`, `JoinChannel`,
`ReadHistory` для будущего slowmode-ретрая на mark-as-read), `skills/`
физически не может обернуть операции, которые сервис не экспортирует по
отдельности от их бизнес-обёрток (`sendDm`, `joinDiscussionGroups`).
`skills/util.ts:withFloodRetry` удаляется, `monitor.ts`/`monitor-v2.ts`
переходят на экспортируемую версию.

**Политика до 2 повторов — перепроверка порога на каждом шаге, не
фиксированный список из 2 ожиданий.** Дока: «Порог 2 минуты проверяется
заново на каждом повторе... если очередное время ожидания окажется ≥ 2
минут, цикл повторов обрывается раньше». Реализуется циклом `for (attempt in
0..2)`, не двумя развёрнутыми `try/catch` (как сейчас) — короче и не
дублирует тело обработки.

**`channels.status` проверяется точечно (`=== 'banned'`), не общим «есть
любой статус → skip».** Дока прямо: `format_error` не останавливает
обработку канала, обрабатывается как обычно; пропускается только `banned`.
(Обсуждалось в ходе диалога — сначала было предположение об общей проверке,
дока это опровергает.)

**`USER_BANNED_IN_CHANNEL` не получает отдельного тега от
`CHAT_WRITE_FORBIDDEN` в контексте отправки.** Дока (№23) явно говорит: «Если
ошибка возникает при отправке сообщения в чат... то же поведение [что №24]».
Классификатор возвращает разные теги (структурно это разные ошибки
Telegram), но обработчик в `monitor-v2` реагирует на оба тега одинаково —
одна ветка кода, не дублирование логики №24.

**`error_log` — таблица в `tasks.db`, не отдельный файл.** По прецеденту
`runs`/`dispatcher_runs` (`db/runs.ts`, `db/dispatcher-runs.ts`) — обе живут
в `tasks.db`, диспетчер уже открывает этот файл на каждом прогоне.

**`agent_restrictions` — БД в workspace `FUNNEL_ADMIN_AGENT_ID`, не отдельный
платформенный каталог.** По прецеденту `funnel.db`/`discovery.db`/
`private-invites.db` (`core/config.ts:113-145`) — тот же приём, не вводит
новую инфраструктурную сущность ради одной таблицы.

## Дополнение после первичной реализации: пробел в покрытии №5/6/11/12

При сверке реализации с доком (`docs/telegram-errors.md`) после первого прохода
обнаружен пробел: `invokeChecked` был подключен только к 4 методам, буквально
названным в задаче 2.2 (`markAsRead`, `getMessages`, `getMessageById`,
`getRecentPosts`) — не потому, что остальные вызовы не подпадают под правило
«в любом месте», а потому, что задача 2.2 превратила иллюстративные примеры
дока («замечены в скиллах `channel-coverage-update`... и `monitor-v2`») в
исчерпывающий список вместо того чтобы реализовать сам принцип.

Хуже того: даже там, где `invokeChecked` подключен, скилл-уровневые `catch`
в `monitor.ts`/`monitor-v2.ts` перехватывают ЛЮБУЮ ошибку (кроме
`FloodAbortError`) и трактуют её как «этот канал/сообщение не получилось» —
`markAsRead` (голый catch, только `log.warn`), `getMessages` (общая ветка
`get_messages_error`), `sendReply`/`replyToMessage` (тег-классификатор для
join/send не знает про аккаунтные ошибки). Аналогично в
`joinDiscussionGroups` (`service.ts`) — catch на каждой ссылке никогда не
пробрасывает исключение дальше, весь батч продолжает работать уже мёртвым
аккаунтом. Реальное покрытие `AccountBannedError`/`SessionRevokedError`
работало только там, где это исторически уже было — `sendDm` (свой
explicit-чек на `USER_DEACTIVATED`, не на `FROZEN_*`) и `ensureClient`
(подключение).

**Исправление — два дополнения к решениям выше, не новый механизм:**

1. **`invokeChecked` расширяется на все вызовы, которыми пользуются шесть
   диспетчерских скиллов** (`replyToMessage`, `leaveChannel`, `getDialogs`,
   `getDialogsForBatch`, три вызова внутри `joinDiscussionGroups`,
   `sendDm`'s `client.sendMessage` — там уже есть свой чек на
   `USER_DEACTIVATED`/`USER_DEACTIVATED_BAN`, дополняется `FROZEN_*`).
   Admin-скрипты (`authSendCode`, `authSignIn`, `probeProxy`) не
   оборачиваются — до создания сессии агент не существует как сущность,
   которую можно ограничить через `agent_restrictions`; это не буквальная
   строка дока, а вывод из природы `agent_restrictions` (нечего
   ограничивать).
2. **Правило для любого catch-блока скилла, который трактует ошибку как
   «этот элемент не получился, продолжаем со следующим»**: первой строкой —
   `if (err instanceof ClientNotConnectedError) throw err;`. Без этого
   правила даже полностью корректная классификация на уровне `service.ts`
   не долетает до диспетчера — ловится раньше, локально. Применяется в
   `monitor.ts`/`monitor-v2.ts` (catch у `markAsRead`/`getMessages`/
   `sendReply`), `joinDiscussionGroups` (catch по ссылке), `dm-send.ts`
   (catch вокруг `tg.sendDm`).

Прецедент из внешних библиотек (не изобретено с нуля): в GramJS/Telethon
классификация — часть самого механизма вызова (`instanceof` на объект,
который библиотека и так возвращает), забыть подключить её невозможно
структурно. У нас классификация — отдельная функция, которую конкретный
catch может не вызвать — тот же класс проблемы, что описан в issues
`WhiskeySockets/Baileys` (WhatsApp-библиотека, тоже управляет множеством
сессий): код, реконнектящийся без проверки `DisconnectReason` в каждой
точке, гоняет мёртвую сессию бесконечно.

## Risks / Trade-offs

- **[Risk] Перенос `withFloodRetry` в `service.ts` меняет публичный API
  `skills/util.ts`, используемый `monitor.ts`/`monitor-v2.ts`.** →
  Мех-переезд: сигнатура сохраняется, меняется только путь импорта; поведение
  наблюдаемо не меняется, кроме числа повторов (1 → до 2, требование самой
  доки).
- **[Risk] Замена `disableAllTasks` на `agent_restrictions` — поведенческое
  расхождение с уже описанным (но не архивированным) спеком
  `telegram-connection-errors`.** → Осознанно, отражено в Modified
  Capabilities проposal.md; при архивации `deterministic-connection-errors`
  этот change должен архивироваться после (или спек этого change перекроет
  требование при архивации).
- **[Trade-off] Сужение `purgeChannelData` — по отношению к уже
  задеплоенному (но не завершённому) `leave-banned-channels`, часть его
  верификационных шагов (7.1-7.4, не отмечены) может быть переписана под
  новое поведение.** → Ожидаемо, `leave-banned-channels` не был завершён;
  этот change корректирует его перед завершением, не после.
- **[Risk] Общая обёртка `invokeChecked` вокруг всех вызовов `TelegramService`
  — самое инвазивное изменение change'а, затрагивает ~30 мест использования
  клиента.** → Мех-рефакторинг (оборачивание существующих вызовов), не
  меняет их поведение при отсутствии аккаунтных ошибок; тестируется через
  существующие сценарии (успешный путь не должен наблюдаемо измениться).

## Migration Plan

Аддитивные миграции: `channels.status`/`channels.statusUpdatedAt` (ALTER
TABLE, как существующие миграции в `channels.ts`), новая таблица `error_log`
в `tasks.db` (как `runs`/`dispatcher_runs`), новый файл
`agent-restrictions.db` в workspace админ-агента. Данные не удаляются и не
переносятся из старых мест — `disableAllTasks`/`tasks.enabled=0` не читается
и не мигрируется в `agent_restrictions` задним числом: агенты, уже
отключённые этим механизмом до деплоя, остаются `enabled=0` (эквивалентно
"restricted" на практике) до ручной проверки человеком — новая проверка
`agent_restrictions` для них просто не найдёт записи и позволит запускать
задачи повторно, поэтому перед деплоем нужно вручную создать
`agent_restrictions` строки для агентов, у которых `tasks.enabled=0`
установлен по причине отзыва сессии (список — по `runs.error`).

Откат: убрать проверку `agent_restrictions` из диспетчера, вернуть
`disableAllTasks` в catch-блок — данные (`agent_restrictions.db`,
`error_log`, `channels.status`) не мешают старому поведению, читаться не
будут.

## Open Questions

- Порог повторов TCP-таймаута для ротации прокси (№10) — не задан, вне
  скоупа этого change (см. Non-Goals).
- Механизм снятия `format_error` — не задан доком, вне скоупа.
- Нужно ли ручное решение по каждому агенту с текущим `tasks.enabled=0`
  перед деплоем (Migration Plan) — принимает пользователь/оператор при
  выкатке, не решается в коде.
