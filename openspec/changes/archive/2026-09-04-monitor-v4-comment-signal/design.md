## Context

`monitor-v4` (`src/skills/monitor-v4.ts`, §2b) находит последний пост
фиксированного целевого дня («позавчера», см. change `monitor-v4`) и решает,
комментировать ли его: сначала дешёвый эвристический отсев текста поста
(`passesPrefilter` — длина, наличие букв), затем LLM (`generatePostCommentV3`)
решает по тексту поста, писать ли комментарий и что именно. Обращение к чату
обсуждения (`tg.getDiscussionMessage`) происходит только ПОСЛЕ решения LLM —
единственная цель этого вызова сейчас — найти служебную копию поста, на
которую нужно ответить.

Нужно сменить основание решения: комментарий должен строиться не на тексте
поста самого по себе, а на доминирующем мнении аудитории в комментариях под
постом. Посты с недостаточным откликом (< 3 комментариев) отсеиваются ещё до
LLM — числовой гейт, симметричный по роли текущему `passesPrefilter`, но по
другому критерию и с другим источником данных (не веб-превью, а MTProto).

## Goals / Non-Goals

**Goals:**
- Отсеивать посты с менее чем 3 комментариями до какого-либо обращения к LLM
  (дешёвый числовой гейт, тот же принцип, что `passesPrefilter` сейчас).
- Передавать LLM текст поста и ВСЕ комментарии к нему (без сэмплирования и
  верхнего предела на число комментариев).
- LLM сама решает, достаточно ли сильный сигнал для комментария (новая
  шкала «оценка» 0-4 + явное решение «пропустить»/«комментировать»,
  согласовано отдельно) — вместо бинарного `тип`/`комментарий` v3.
- Переиспользовать без изменений всё, что не зависит от смены критерия
  отбора: §0 подготовка, §1 проверка удалённых сообщений, §2a (`only_comment`),
  переход в `only_comment`/`sleep`, обработка ошибок отправки, кэш резолва
  целевого дня (`lastCheckedTargetDate`/`lastCheckedTargetPostId`).

**Non-Goals:**
- Отдельный контент-фильтр отдельных комментариев (спам/флуд/оффтоп) —
  очистка от шума полностью на стороне промпта (`generatePostCommentV4`,
  §2 промпта), код не отбирает и не фильтрует комментарии перед передачей.
- Верхний предел числа комментариев, передаваемых в промпт — не вводится
  (см. Risks: осознанно принятый риск роста стоимости/токенов на очень
  обсуждаемых постах).
- Изменение `monitor-v3.ts`/`generatePostCommentV3` — не трогаются,
  `monitor-v4` продолжает быть независимой веткой (тот же принцип
  аддитивности, что и в change `monitor-v4`).
- Изменение §2a (`only_comment`, ответы на продолжение обсуждения после
  своего же комментария) — не в объёме этого change, использует прежнюю
  логику monitor-v3/v4 без изменений.

## Decisions

**1. Гейт по числу комментариев — код, до LLM; источник данных —
`messages.GetReplies` (MTProto), не веб-превью.**
Веб-превью (`t.me/s/`) не даёт числа/содержимого комментариев — только сам
пост. `messages.GetReplies({ peer: channel, msgId: latestPost.id, ... })`
(официальный MTProto-метод, уже есть в GramJS-типах проекта, аналог того, что
`getRecentPosts` уже использует для `.replies.replies` — общего числа
комментариев поста) в одном ответе даёт `.count` (общее число, не только
загруженная страница) и `.messages[]` (сами сообщения). Если `.count < 3` —
пост отбрасывается тем же путём, что сейчас отбрасывается текстовый
`passesPrefilter`-отказ (`markPostSeen` + резолв дня, см. Decision 4), без
единого обращения к LLM.

Альтернатива (отклонена) — как в §2a/`only_comment`, резолвить корень ветки
через `getDiscussionMessage` и затем вычерпывать историю чата обсуждения
`getMessages`, отбирая сообщения по `replyToTopId === rootMsgId` (тот же
приём, что использует `monitor-v2`/post-freshness-gate для похожей, но
структурно другой задачи — там переиспользуется общий поток непрочитанных).
Отклонено: `GetReplies` — специализированный API именно под «комментарии
конкретного поста», отдаёт нужное одним вызовом с пагинацией и без риска
захватить чужие ветки того же чата обсуждения; `getMessages`+фильтрация
тратила бы лишние вызовы и требовала бы ручной изоляции по `replyToTopId`.

**2. Пагинация до исчерпания всех комментариев — без верхнего предела.**
`GetReplies` пагинируется (`offsetId`/`addOffset`/`limit`), тот же принцип,
что уже применяет `fetchLastPostInDateRange` (change `monitor-v4`) для
веб-превью — цикл запросов, пока не собраны все `.count` сообщений. Решение
пользователя: передавать LLM все комментарии без потолка (см. Risks —
осознанно принятый риск на очень обсуждаемых постах).

**3. Новая функция промпта `generatePostCommentV4` и новая zod-схема — не
модификация `generatePostCommentV3`.**
Тот же прецедент, что уже применён `monitor-v3-post-comment-axes`
(`generatePostComment` → `V2` → `V3`, каждая версия — отдельная функция,
предыдущие остаются в коде нетронутыми и невызываемыми). `monitor-v3.ts`
использует `generatePostCommentV3` и не подозревает о комментариях — трогать
её нельзя, значит новая рубрика идёт отдельной функцией.

Схема ответа:
```ts
z.object({
    оценка: z.number().min(0).max(4),
    решение: z.enum(["пропустить", "комментировать"]),
    главное_мнение: z.string().nullable(),
    комментарий: z.string().nullable(),
})
```
`решение` — явная ветка отказа (в отличие от промежуточной версии этого
промпта, обсуждённой и отклонённой в процессе — там отказа не было вовсе).
`оценка` не используется кодом как условие ветвления (аналог `оси` в
`monitor-v3-post-comment-axes` — существует в схеме только чтобы модель
проговорила рассуждение и это осело в `llm_log`); ветвится код строго по
`решение`.

**4. Порядок шагов §2b.iv-v меняется: комментарии — вход решения, не только
цель отправки.**
```
БЫЛО (monitor-v4 / monitor-v3):
  post.text → passesPrefilter → LLM(post.text) → getDiscussionMessage (только
  для места ответа) → send

СТАНЕТ:
  GetReplies(post.id) → count < 3? отсеять : собрать все .messages
  → LLM(post.text, comments) → решение="пропустить"? отсеять : найти
    rootMsgId для ответа → send
```
`getDiscussionMessage` (поиск rootMsgId) остаётся нужен для отправки — вызов
не убирается, а перемещается после LLM-решения (как и сейчас), либо
переиспользует `replyToTopId` одного из уже полученных комментариев, если
он есть (реализационная деталь, решение оставлено на этап реализации —
пользователь явно делегировал этот пункт).

При отказе (`решение === "пропустить"`) канал помечается тем же способом, что
сейчас `passesPrefilter`-отказ и LLM-отказ `тип === "нет"` в `monitor-v3`:
`markPostSeen` (пост разобран, повторно не предлагается) + резолв кэша дня
(`saveTargetDayCache`, поле `resolveDay` из change `monitor-v4`) — оба пути
(отсев по числу комментариев до LLM и отказ LLM после) сходятся в одну и ту
же точку пометки поста разобранным.

**5. Резолв `fromName` авторов комментариев — новая логика в
`TelegramService`, не переиспользование `getMessages`.**
`GetReplies` возвращает `messages.ChannelMessages`/`Messages`/`MessagesSlice`
с отдельными `.users`/`.chats` для резолва отправителей — `getMessages`
такую механику уже имеет (маппинг `fromName`/`fromId`), но она заточена под
другой RPC-ответ (`getHistory`). Новый метод сервиса делает эквивалентный
маппинг для ответа `GetReplies` (реализационная деталь, не меняет публичный
контракт `TgMessage`, если формат вывода будет тем же).

**6. Отдельный контент-фильтр комментариев не вводится.**
Промпт `generatePostCommentV4` сам явно инструктирует модель игнорировать
шум (флуд, оффтоп, ботов, личные конфликты, угрозы/травлю/доксинг,
несвязанные ветки) как часть анализа (§2 промпта) — дублировать это кодом
(как `passesPrefilter` для текста поста) избыточно: у комментариев нет
единого дешёвого эвристического признака «шум» уровня «короче N символов»,
который не резал бы заодно короткие, но сильные сигналы (промпт прямо
указывает: «даже одно слово может быть сильным сигналом»).

## Risks / Trade-offs

- [Риск] Отсутствие верхнего предела на число комментариев в промпте — на
  очень обсуждаемых постах (сотни-тысячи комментариев) это дорогой LLM-вызов
  и растущий риск упереться в контекстное окно модели → Митигация: не
  вводится в этом change (осознанное решение пользователя); при необходимости
  — отдельное решение о потолке позже, по факту наблюдения реальных объёмов
  через `llm_log`.
- [Риск] MTProto-нагрузка растёт: теперь `GetReplies` (потенциально
  несколько страниц) вызывается на КАЖДЫЙ найденный пост дня, а не только на
  те, что прошли отбор LLM (раньше `getDiscussionMessage` вызывался один раз,
  после решения писать) → Митигация: не вводится явно; сам гейт по `count`
  дешевле полного вычерпывания (первая страница уже даёт `.count`, полная
  пагинация нужна только когда `count ≥ 3`).
- [Риск] Отсутствие отдельного контент-фильтра комментариев (Decision 6)
  означает, что весь шум (в т.ч. потенциально нежелательный контент — угрозы,
  травля, доксинг) целиком проходит в промпт LLM как контекст, а не
  отбрасывается до него → Митигация: инструкция модели прямо требует не
  использовать такой контент как основание для сигнала (§2 промпта), но это
  не код-уровневая гарантия — модель может отреагировать на него ошибочно,
  риск того же рода, что уже принят для остального LLM-контента в проекте.
- [Trade-off] `оценка` (0-4) существует в схеме, но не используется кодом
  (аналог `оси` в `monitor-v3-post-comment-axes`) — если модель не будет
  последовательно связывать `оценка` и `решение` (например, оценка 2, но
  решение «комментировать»), код всё равно ветвится по `решение` — несогласованность
  видна только по логам, не ловится валидацией.

## Migration Plan

1. Новый метод `TelegramService` (комментарии поста через `GetReplies`) —
   аддитивный, не трогает существующие методы.
2. `generatePostCommentV4` — новая функция рядом с `generatePostCommentV3`.
3. `monitor-v4.ts` §2b.iv-v — переписать по Decision 1/4; `monitor-v3.ts` не
   трогать.
4. Деплой — `monitor-v4` уже задеплоен и потенциально включён операторами;
   изменение поведения применяется с первого прогона после деплоя нового
   `monitor-v4.ts`, без флага/переключателя (то же решение, что уже принято
   для самого `monitor-v4` — только одна активная логика на скилл).

Откат: вернуть §2b.iv-v `monitor-v4.ts` к вызову `generatePostCommentV3` по
тексту поста (старый код придётся восстанавливать из git-истории — в отличие
от `monitor-v3-post-comment-axes`, здесь не сохраняется параллельная старая
пара как мёртвый код, так как меняется весь поток данных, а не только
промпт/схема).
