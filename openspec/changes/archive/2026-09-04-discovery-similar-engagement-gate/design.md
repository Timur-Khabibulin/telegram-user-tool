## Context

`similar-channel-discovery` (`channel-discovery-similar` + `discovery-similar-topic-gate`)
собирает кандидатов в `collectByLevels` (`src/core/discovery/similar.ts`) через цепочку
гейтов: подписчики → группа обсуждения → тема (LLM, `scoreCandidateTopic`). Тематический
гейт — единственный дорогой (LLM-вызов на кандидата). Оператор зафиксировал ТЗ (см.
`docs/design/channel-discovery-similar/er-views-gate-v1.md`) на новый гейт по вовлечённости,
который встаёт перед темой и отсеивает дешевле.

Опорные точки:
- `similar.ts:330–352` — текущий candidate-гейт (место врезки нового шага, перед вызовом
  `scoreCandidateTopic`).
- `similar.ts:213–229` (`gatherAndScoreSeeds`) — существующая seed-приоритизация: median по
  `getRecentPostViews(channel, sinceUnixTs)` с дневным окном `engagementWindowDays`; меняется
  определение окна (дни → число постов), агрегация (median) не меняется.
- `service.ts:1188` (`getRecentPosts`) — уже отдаёт последние N постов канала с `views`, от
  новых к старым; источник данных для нового гейта.
- `similar.ts:106–109` (`SkipCounts`), `:352` (лог принятого кандидата), `renderSimilarReport`
  — точки расширения для нового счётчика/полей лога/отчёта.

## Goals / Non-Goals

**Goals:**
- Отсеивать кандидатов с низкой вовлечённостью до LLM-вызова — дешёвый гейт раньше дорогого.
- Ловить две разные проблемы: «накрученные» подписчики (низкий ER) и микроскопический
  абсолютный охват (низкий avg views) — отдельными порогами.
- Единое оконное правило выборки постов для нового гейта и для seed-приоритизации.

**Non-Goals:**
- Устойчивость к выбросам (median, фильтрация закреплённых постов) для нового гейта —
  оператор осознанно выбрал average без защиты от выбросов.
- Объединение MTProto-вызова нового гейта с вызовом текста для темы (`getRecentPostTexts`) —
  оставлено на решение при реализации, не часть требований.
- Детальный учёт причины отсева (ER vs avg views раздельно) — оператор явно отверг.

## Decisions

### D1. Порядок гейтов — ER/avg views перед темой

```
кандидат
  ├─ подписчики / группа обсуждения        → (как сейчас)
  ├─ getRecentPosts(channel, 20)
  │     ├─ выборка после пропуска 2 свежих пуста   → skip (low_engagement, fail-closed)
  │     ├─ avgViews = average(views выборки)
  │     ├─ ER = avgViews / subscribers
  │     ├─ avgViews <= minAvgViews                  → skip (low_engagement)
  │     └─ ER <= minEngagementRate                  → skip (low_engagement)
  ├─ scoreCandidateTopic(...)                → (как сейчас, без изменений)
  └─ в пул
```

Гейт встаёт строго перед `scoreCandidateTopic` — LLM тратится только на кандидатов,
прошедших и дешёвые гейты, и гейт вовлечённости.

### D2. Метрика — average по count-based окну, без защиты от выбросов

`getRecentPosts(channel, 20)` → отбросить 2 самых свежих поста (просмотры «не дозрели») →
`avgViews = average(views оставшихся, до 18 штук, меньше — то, что есть)`. Закреплённые
посты не фильтруются — выборка строится чисто по позиции в истории. Если после отбрасывания
2 свежих постов выборка пуста (у канала ≤2 постов всего) — fail-closed, гейт не пройден.
Это **average, не median** — осознанный отказ оператора от устойчивости к выбросам
(закреп/виральный пост искажает результат сильнее обычного, но это принятый трейд-офф).

### D3. Два порога — относительный и абсолютный, разная обязательность

`minEngagementRate` (ER, опционален, дефолт `0.1`) ловит «накрученные» подписчики:
вовлечённость низкая относительно размера аудитории. `minAvgViews` (обязателен, без
дефолта) ловит малый абсолютный охват: канал может иметь приемлемый ER, но быть слишком
маленьким, чтобы быть интересным платформе. `minAvgViews` без дефолта — абсолютные просмотры
сильно зависят от ниши/языка, дефолт был бы либо слишком строгим, либо бесполезным; оператор
задаёт порог явно каждый прогон, зная контекст ниши.

Сравнение — строгое (симметрично `minTopicScore`, `similar.ts:343`: `score <=
p.minTopicScore` → skip): кандидат отсеивается при `avgViews <= minAvgViews` ИЛИ `er <=
minEngagementRate`; проходит только если оба значения строго больше порогов.

### D4. Один агрегированный счётчик отсева

`SkipCounts` получает одно новое поле `lowEngagement: number` — инкрементируется при отсеве
по любой из двух причин (ER, avg views, или обе одновременно — инкремент ровно один раз).
Без разбивки на под-причины: оператор явно отверг детальный учёт («канал не подошёл —
забыли про него, можем только посчитать сколько в итоге отбросили»). Отображается в
`renderSimilarReport` рядом с `lowSubscribers`/`noLinkedChat`/`offTopic`.

### D5. Лог — только принятые, с добавлением ER и avg views

Строка лога принятого кандидата (`similar.ts:352`) дополняется рассчитанными `ER` и
`avgViews`. Отклонённые по этому гейту кандидаты построчно не логируются — как и для
прочих гейтов (`lowSubscribers`, `noLinkedChat`, `offTopic`), только агрегированный счётчик.

### D6. Seed-приоритизация — окно по числу постов вместо дней

`gatherAndScoreSeeds` (`similar.ts:213–229`) сейчас берёт `getRecentPostViews(channel,
sinceUnixTs)` с `sinceUnixTs = now - engagementWindowDays * 86400` и считает `median`.
Параметр `engagementWindowDays` заменяется на то же count-based правило, что у нового гейта:
последние N постов минус 2 самых свежих (получаются через `getRecentPosts`, как у
кандидатов, либо эквивалентный вызов без текста — на решение разработчика). **Меняется
только определение окна** (дни → количество постов); агрегация для seeds остаётся `median`
(строка 219, `median()` строка 44) — устойчивость к выбросам нужна для приоритизации seeds,
в отличие от гейта кандидатов, где оператор осознанно выбрал average. Параметр в
`SimilarParams` (`similar.ts:94`) переименовывается или переосмысливается под count-семантику
— конкретное имя (`engagementWindowDays` → `engagementWindowPosts` или иное) оставлено
разработчику; нормативно важно только единое оконное правило.

### D7. Параметры — проброс через CLI и скилл

`minEngagementRate?: number` (дефолт `0.1`) и `minAvgViews: number` (обязателен) добавляются
в `SimilarParams` и пробрасываются: скилл (вопрос оператору, `skills/discovery-similar/
SKILL.md` шаг 1) → скрипт (`src/scripts/discovery-similar.ts`, флаги `--min-er`,
`--min-avg-views`) → `RunSimilarParams` → `SimilarParams`. `--min-avg-views` обязателен —
без него прогон не стартует, по аналогии с текущей обязательной валидацией `--theme`/
`--agents` (`discovery-similar.ts:56–71`).

## Risks / Trade-offs

- **Average без защиты от выбросов** → закреплённый/виральный пост искажает `avgViews`
  сильнее обычного. Mitigation: осознанный трейд-офф оператора, не баг; среднее по 18 постам
  сглаживает единичный выброс частично.
- **`minAvgViews` без дефолта** → оператор может забыть указать и получить ошибку валидации
  при каждом первом запуске в новой нише. Mitigation: явная ошибка при старте (fail fast, до
  начала сбора), не тихий пропуск гейта.
- **Один агрегированный счётчик** → при отладке порогов не видно, какая именно причина
  (ER или avg views) отсекает больше кандидатов. Mitigation: осознанное решение оператора —
  цена детализации (две настройки/два счётчика) признана избыточной для текущей задачи.
- **Замена окна seed-приоритизации** меняет уже работающее поведение (median по дням → median
  по постам) без отдельного флага отказа — старое поведение недоступно. Mitigation: окно по
  постам не меняет смысл метрики (вовлечённость относительно недавней активности), только
  способ её ограничения; риск признан малым.
