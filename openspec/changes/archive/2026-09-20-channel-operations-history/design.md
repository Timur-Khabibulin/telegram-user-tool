## Context

Полный технический дизайн — в
[docs/design/channel-operations-history/architecture.md](../../../docs/design/channel-operations-history/architecture.md)
(парный к
[requirements-v1.md](../../../docs/design/channel-operations-history/requirements-v1.md)).
Здесь — ключевые решения и их обоснование; детали (SQL-схема, запросы, раскладка
источников по точкам) не дублируются, а берутся из architecture.md.

Текущее состояние: статус канала — колонка `channels.status` в пер-агентной
`channels.db` (перезапись, хранится только последний), при ротации строка канала
у прежнего агента удаляется (`deleteChannelRow`). Владение — реестр
`discovered_channels` в `discovery.db` (ключ `canonical_link`). История операций
нигде не копится.

## Goals / Non-Goals

**Goals:**
- Централизованный append-only журнал операций с ключом `chatId`, переживающий
  ротацию.
- Ответы на «сколько раз и когда канал забанен у агента», тайм-линия владения,
  агрегат банов по агенту.
- Аддитивность: нормативное поведение существующих способностей не меняется.

**Non-Goals:**
- UI и регулярные отчёты (v1 — только разовые выгрузки).
- Ретеншн/архивация журнала.
- Ретроспектива до внедрения (журнал стартует «с нуля»).
- Фиксация `should_leave` (нет кодовой точки записи).

## Decisions

- **Выделенный файл `channel-operations.db` в admin-workspace** (через
  `channelOperationsDbPath(FUNNEL_ADMIN_AGENT_ID)`), а не таблицы в `discovery.db`.
  Причина: `discovery.db` при миграциях пересобирает свою таблицу целиком; профиль
  записи иной (много агентских писателей одновременно). WAL + `busy_timeout` под
  конкуренцию. Альтернатива (общий файл) отклонена из-за риска чужих пересборок и
  блокировок.
- **Реквизиты key:value как JSON-поле `attrs`**, не EAV. Запросы R16/R17/R18
  остаются одно-табличными (`json_extract` после индекса `(chat_id,type,ts)`);
  расширяемость без ALTER. EAV дал бы разрыв записи на N строк и pivot в запросах.
  Прецедент — `discovered_channels.metrics_json`.
- **Единый модуль `core/db/channel-operations.ts`** — владелец схемы, белого
  списка переходов (`classifyStatusTransition` — единственное место фильтра R8) и
  всех функций записи/чтения. Точки-писатели только вызывают его.
- **Детект перехода при записи (вариант A)**: в транзакции `channels.db`
  `SELECT old → UPDATE`, затем best-effort append. Гейт `old==new` закрывает дедуп
  (повтор `banned`) и «новый бан» от живого `channels.status`, без отдельного
  состояния в журнале. Альтернатива (append-raw + дедуп на чтении) отклонена:
  `oldStatus` в записи нет, логика дедупа рискует разъехаться по выгрузкам.
- **`assigned` по `chatId` через мост вступления**: `channel_identity(link,
  chatId)` наполняется в точке `joined`; `assigned` после первого join получает
  `chatId`, первичное назначение до join несёт только ссылку и мостится
  ретроспективно. `oldAgentId` читается в `forceAssignChannel` до перезаписи.
- **Источник — явный параметр** из перечня `operator|monitor|timer|module`;
  к `markChannelStatus` добавляется с дефолтом `monitor`, чтобы не править вызовы
  мониторов.

## Risks / Trade-offs

- **Кросс-файловая атомарность append↔status** → В WAL атомарный коммит через
  несколько БД не гарантирован. Разделяем: атомарен `SELECT+UPDATE` в `channels.db`
  (гарантия недвоения), append — отдельный best-effort. Потеря append = недоучёт
  (согласуется с «нет ретроспективной гарантии»), но никогда не двойной счёт.
- **Пакетное снятие статусов по таймеру** → `expireChannelStatuses` гасит
  `suspend` и `sleep` одним `UPDATE`. Перерабатываем на пообъектную обработку с
  чтением старого статуса: журналируем только `suspend` (источник `timer`), `sleep`
  по-прежнему гасится без журнала.
- **Протечка не-R8 статусов** → Единый белый список в `classifyStatusTransition`
  отсекает `format_error`/`only_comment`/`sleep`/`not_found`/`should_leave`.
- **Конкурентная запись многих агентов в один файл** → WAL + `busy_timeout`,
  короткоживущие соединения.
- **Первичный `assigned` без `chatId`** → до первого вступления `chat_id=NULL`;
  тайм-линия владения (R17) мостит такие записи через `channel_identity` после
  первого join. Все реальные каналы рабочего набора рано или поздно вступаются.

## Migration Plan

Новый файл БД, чистая схема — легаси-миграций нет. `ensureChannelOperationsSchema`
идемпотентна (guard-`Set` + `CREATE TABLE IF NOT EXISTS`), создаётся лениво первым
писателем. Правки `channels.ts`/`discovery.ts` аддитивны (чтение old + append),
откатываются снятием вызовов; существующие БД структурно не затрагиваются.
