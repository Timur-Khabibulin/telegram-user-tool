## Context

Полная аналитика фичи (проблема, контур, воронка запросов, сравнение источников,
обоснование решений) — `docs/design/channel-discovery/channel-discovery-v1.md`. Здесь —
только технические решения для реализации; мотивация — в proposal, требования — в specs.

Текущее состояние: агенты вступают в каналы поштучно через существующую очередь
`join_queue` (`addJoinQueue` / per-agent таймер `join-queue`), вступлённые каналы
подхватываются `monitor`/`syncChannels` в таблицу `channels`. Централизованного поиска и
учёта «какой канал чей» нет. Данные — SQLite (better-sqlite3) в
`~/.openclaw/workspace-<agentId>/`; админ-агент (`FUNNEL_ADMIN_AGENT_ID`, по умолчанию
`agent1`) уже держит общий `funnel.db`.

## Goals / Non-Goals

**Goals:**
- Централизованный поиск каналов по ключевым словам в TGStat, фильтр по подписчикам и ER.
- Единый реестр с дедупом и инвариантом «один канал — один агент навсегда».
- Доставка назначенных каналов в `join_queue` агентов без изменения существующего кода
  вступления/мониторинга.
- Детерминированный скрипт; LLM — только генерация ключевых слов в скилле.

**Non-Goals (v1):**
- Поиск по категориям; фолбэк на telemetr.me/telemetr.io; скрейпинг-источники.
- Онлайн-обратная связь `join_queue → discovery.db` (актуализация статуса вступления).
- Автоматический backfill из `channels` (backfill — разовая ручная операция оператора).
- Учёт накопленной нагрузки при раскладке; ребаланс назначений.

## Decisions

### Реестр — отдельная БД `discovery.db` в workspace админ-агента
`~/.openclaw/workspace-<FUNNEL_ADMIN_AGENT_ID>/discovery.db`, тот же приём, что и
`funnel.db`. Модуль `src/core/db/discovery.ts` в стиле `funnel.ts`/`join-queue.ts`
(better-sqlite3, snake_case, `CREATE TABLE IF NOT EXISTS`, camelCase через `AS`).
Таблица из двух колонок: `canonical_link TEXT PRIMARY KEY`, `assigned_agent TEXT NOT NULL`.
_Альтернатива:_ хранить назначение в per-agent БД — отвергнута: непересечение требует
глобального взгляда, который per-agent хранилище не даёт.

### Инвариант непересечения — на `canonical_link PK`, а не на коде раскладки
Уникальность канонической ссылки физически не даёт назначить один канал двум агентам.
Дедуп = проверка наличия `canonical_link`. _Альтернатива:_ проверки в коде assignment —
отвергнута как хрупкая.

### Единая нормализация ссылки — общий примитив дедупа и доставки
Одна функция нормализации (`https://t.me/<username>`, lowercase, без `@`/`/`) применяется
и при записи в реестр, и при `addJoinQueue`, иначе `join_queue` (`link UNIQUE` без своей
нормализации) примет дубль. Краёв у ссылок не ожидается (источник отдаёт публичные
username), поэтому правила простые.

### Детерминированный скрипт, LLM только в скилле
Поиск, фильтр по подписчикам, расчёт ER, дедуп, round-robin — без LLM. Скилл генерирует
ключевые слова (LLM), собирает пороги и запускает скрипт. Согласуется с принципом «LLM
только для текста».

### Инкрементальный отбор до `N`, без глобального top-N
Скрипт останавливается, как только набрал `N`, и не тратит лишние запросы. _Альтернатива:_
собрать всё и отрезать top-N по ER — отвергнута: дороже по запросам.

### ER через `channels/stat.err_percent` (+1 запрос на канал)
ER в выдаче `channels/search` нет; `channels/posts` не отдаёт счётчик репостов, поэтому
ER из постов не посчитать. Берём готовый `err_percent` (ERR %, вовлечённость по охвату)
из `channels/stat` — один запрос на кандидата. Гейт ER — только для прошедших порог
подписчиков (экономия запросов). Источник истины полей — документация TGStat
(`channels/search`, `channels/stat`).

### Развязка центр/агент
discovery пишет только в `join_queue` агента и ничего не запускает; вступление инициирует
существующий per-agent таймер `join-queue`. Центр про инфраструктуру агента не знает.

### Источник v1 — TGStat
RU-first, страница 100, join-ссылка в выдаче, дешевле. telemetr.* — справочно/на будущее,
переключение не реализуется.

## Risks / Trade-offs

- **Backfill из `channels` неполон** (схема `channels` хранит `chatId` обсуждения, не
  username канала) → исторические ручные вступления могут не попасть в реестр и дать
  пересечение. → _Mitigation:_ backfill — разовая ручная операция оператора по публичным
  ссылкам; для каналов из очереди берётся `join_queue.link`.
- **Сбой между записью в реестр и `addJoinQueue`** (две разные БД, не одна транзакция) →
  канал может остаться в реестре без доставки в очередь. → _Mitigation:_ принято как
  пренебрежимое (единичный канал на жёсткий краш); порядок «реестр → очередь» выбран ради
  непересечения, а не ради полноты доставки.
- **Лимит TGStat «каналов/день» / квота запросов** → строгий `er_min` множит запросы
  (+1 на кандидата). → _Mitigation:_ инкрементальная остановка на `N`; пороги задаёт
  оператор осознанно.
- **Параллельный запуск двух прогонов** не предусмотрен → защита на `canonical_link
  UNIQUE` (проигравшая гонку вставка — no-op); как продуктовое правило прогоны не
  пересекаются.

## Migration Plan

1. Добавить модуль реестра и создать `discovery.db` (идемпотентный `CREATE TABLE IF NOT EXISTS`).
2. Разовый ручной backfill оператором перед первым прогоном (известные каналы → реестр).
3. Первый прогон discovery на узком наборе ключевых слов; проверить отчёт и наполнение
   `join_queue` агентов.
4. Откат: discovery не трогает существующие данные агентов кроме добавления строк в
   `join_queue` (идемпотентно); при необходимости — удалить `discovery.db` и добавленные
   `pending`-строки очереди.
