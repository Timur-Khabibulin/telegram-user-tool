## Why

В `tg-agent-create-v2` прокси подбирается автоматической MTProto-пробой (`probeProxy`)
уже после того, как собраны все данные аккаунта, и используется молча внутри флоу —
человек его не видит и сам им не пользуется. Реальная потребность: аккаунт должен
логиниться в официальном Telegram-приложении вручную человеком через тот же мобильный
прокси, которым затем будет пользоваться автоматизированный GramJS-сеанс бота (шаг
`authSendCode`/`authSignIn`) — иначе на аккаунте одновременно существуют две сессии
с разных IP/гео (ручная через приложение и бот через GramJS), чего мы хотим избежать.
Для этого прокси должен быть создан и передан человеку самым первым шагом скилла, до
того как что-либо ещё делается с аккаунтом, а не подбираться в фоне после сбора всех
данных.

## What Changes

- Подбор прокси в `tg-agent-create-v2` становится первым шагом скилла: запрашивается
  только `agentName`, `maxAttempts` (по умолчанию 5) и локация прокси (готовые значения
  `countryCode/state/city` текстом либо пошаговый подбор по списку) — без `apiId`/
  `apiHash`, которые больше не нужны на этом шаге.
- Автоматическая MTProto-проверка кандидата (`TelegramService.probeProxy`) убирается из
  этого флоу: создаётся один кандидат на asocks без пробы. Финальная проверка теперь
  ручная — её делает человек, логинясь в Telegram-приложении через выданный прокси.
- Новый обязательный шаг-чекпоинт: скилл выдаёт человеку `host/port/username/password`
  созданного прокси и **ждёт явного ответа** — удалось войти в аккаунт через приложение
  с этим прокси или нет.
- При неудачном ручном входе — кандидат удаляется на стороне asocks, создаётся новый,
  цикл повторяется до `maxAttempts` попыток (тот же паттерн исчерпания попыток, что и
  сегодня, но триггер — ответ человека, а не автоматическая проба).
- Остальные данные (`apiId`, `apiHash`, `telegram_user_id`, `deviceModel`, `phoneNumber`,
  опционально `sessionString`) запрашиваются **после** подтверждения прокси — прокси на
  этом шаге уже зафиксирован, повторный подбор не выполняется.
- Авторизация сессии бота (`authSendCode`/`authSignIn`) продолжает использовать тот же
  прокси, что был выдан человеку и подтверждён им.
- **BREAKING** (для процесса, не для данных): порядок шагов `tg-agent-create-v2` меняется
  необратимо — предыдущий порядок (сбор всех данных → авто-подбор прокси → авторизация)
  для этого скилла перестаёт существовать. `tg-agent-create` (v1) не затрагивается.

## Capabilities

### Modified Capabilities

- `tg-agent-create-v2`: порядок шагов создания агента меняется — подбор прокси становится
  первым шагом (до запроса `apiId`/`apiHash` и прочих данных аккаунта) и завершается
  обязательной ручной проверкой человеком (вход в приложение через выданный прокси) вместо
  автоматической MTProto-пробы. Остальные уже существующие требования капабилити (минимум
  ручного ввода, копия `SOUL.md`, отсутствие регистрации в OpenClaw, состав проверки
  `verify-agent.sh`) не меняются.

## Impact

- `skills/tg-agent-create-v2/SKILL.md` — переписывается порядок шагов: подбор локации и
  создание прокси переезжают в начало, добавляется шаг ожидания ручного подтверждения,
  запрос остальных данных сдвигается после подтверждения прокси.
- `src/scripts/provision-proxy-for-new-agent.ts` — режим подбора с `probeProxy`-циклом для
  этого флоу больше не используется; нужен способ создать одного кандидата без пробы и
  удалить его при неудачном ручном входе (переиспользуя `createMobileProxy`/
  `deleteProxyByName` из `src/core/proxy/asocks-client.ts`). Листинг локаций
  (`--list-countries`/`--list-states`/`--list-cities`) не меняется.
- `skills/tg-agent-create-v2/scripts/verify-agent.sh` — не меняется: проверяет только
  итоговые файлы, порядок их создания на проверку не влияет.
- Не затрагивается: `skills/tg-agent-create/` (v1), `TelegramService.probeProxy` как метод
  (остаётся в использовании в `src/scripts/provision-mobile-proxy.ts` для репейра
  существующих агентов), `openclaw.json`.
