## Context

`tg-agent-create-v2` (задеплоено, не заархивировано) убрало ручной ввод прокси и текста
`SOUL.md`, но оставило порядок из `tg-agent-create-proxy-provisioning`: все данные аккаунта
(`agentName`, `telegram_user_id`, `apiId`, `apiHash`, `deviceModel`, `phoneNumber`) собираются
одним блоком в Шаге 1, локация прокси выбирается в Шаге 1.1, и только затем в Шаге 2 скрипт
`src/scripts/provision-proxy-for-new-agent.ts` подбирает рабочий прокси циклом
create → `TelegramService.probeProxy` (голый MTProto `connect()`/`disconnect()`, без отправки
кода) → при неудаче delete → до `maxAttempts`. Найденный прокси используется молча — сразу для
`authSendCode`/`authSignIn` (Шаг 4), человеку отдельно не показывается.

Реальная потребность (explore-сессия с пользователем): аккаунт логинится в официальном
Telegram-приложении вручную человеком, и это обязано происходить через **тот же** мобильный
прокси, которым дальше пользуется автоматизированный GramJS-сеанс бота — иначе на аккаунте
одновременно существуют сессии с разных IP/гео. Значит прокси должен существовать и быть выдан
человеку **до** того, как скилл вообще касается аккаунта, а не подбираться в фоне после сбора
всех данных.

Так как финальная проверка теперь всё равно ручная (человек реально логинится через приложение),
пользователь явно подтвердил, что автоматическая `probeProxy`-проверка в этом флоу больше не
нужна — она заменяется на ожидание ответа человека.

## Goals / Non-Goals

**Goals:**
- Подбор прокси — первый шаг `tg-agent-create-v2`, до запроса `apiId`/`apiHash` и прочих данных
  аккаунта (они больше не нужны на этом шаге — `probeProxy` их использовал, а теперь не
  вызывается).
- Прокси выдаётся человеку явным сообщением, скилл ждёт подтверждения ручного входа в
  Telegram-приложение через этот прокси, прежде чем продолжать.
- При неудачном ручном входе — кандидат заменяется новым, до `maxAttempts` попыток, тем же
  паттерном исчерпания попыток, что и сегодня (спросить пользователя: другой регион / больше
  попыток / остановиться).
- `authSendCode`/`authSignIn` используют тот же прокси, что был выдан и подтверждён человеком.
- Существующий CLI `provision-proxy-for-new-agent.ts` не ломается для других потребителей —
  добавляются новые режимы, а не переписывается существующий.

**Non-Goals:**
- Изменение `skills/tg-agent-create/` (v1) — использует тот же скрипт в режиме с `probeProxy`,
  не трогается.
- Изменение `TelegramService.probeProxy` как метода — остаётся в использовании
  `src/scripts/provision-mobile-proxy.ts` (репейр существующих агентов), не трогается.
- Автоматизация самого ручного входа в приложение — вне скоупа, это действие человека вне
  системы; скилл только ждёт его текстового подтверждения.
- Изменение состава итоговых файлов агента (`tg-account.json`, `SOUL.md`, структура workspace) и
  `verify-agent.sh` — порядок шагов меняется, результат — нет.

## Decisions

**Новые режимы в существующем `provision-proxy-for-new-agent.ts`, а не новый скрипт.**
Альтернатива — отдельный скрипт для создания-без-пробы. Отклонено: листинг локаций
(`--list-countries`/`--list-states`/`--list-cities`) и обвязка над `asocks-client.ts`
(`createMobileProxy`/`deleteProxyByName`) уже есть в этом файле и одинаково нужны обоим режимам;
дублировать их ради отдельного файла нет причины. Добавляются два новых режима, существующий
режим с `--api-id`/`--api-hash` (`probeProxy`-цикл) остаётся для v1 без изменений:
- `--create-candidate --agent-id <id> --attempt <n> --country <code> [--state] [--city]` —
  создаёт одного кандидата (`createMobileProxy`), печатает JSON с его данными, без пробы.
- `--delete-candidate <name>` — удаляет кандидата по имени (`deleteProxyByName`), используется
  при неудачном ручном входе.

**Цикл create→показать→ждать→(delete→create) живёт в `SKILL.md`, не в скрипте.**
Раньше весь цикл `create→probe→delete→retry` был внутри одного блокирующего вызова скрипта —
это работало, потому что проверка была автоматической. Теперь между созданием кандидата и тем,
успешен ли он, стоит ответ человека в чате — скрипт не может блокироваться на этом (в отличие от
сетевого запроса, ответ человека — событие вне процесса). Поэтому оркестрация цикла (создать →
показать → дождаться ответа → при неудаче: удалить и создать снова → считать попытки против
`maxAttempts`) описывается шагами в `SKILL.md`, а скрипт даёт только атомарные операции
(создать один / удалить один).

**`apiId`/`apiHash` переезжают в шаг после подтверждения прокси.** Они были нужны только для
`probeProxy`; раз он не вызывается на этом шаге, эти поля не нужны до подтверждения прокси —
запрашивать их раньше не имеет смысла и увеличивает то, что человек должен ввести до того, как
получит хоть какой-то результат (прокси).

**Чек-лист подготовки в `SKILL.md` переписывается**: текущая фраза «прокси эмулятора,
использованный при регистрации номера, не обязан совпадать с прокси, который будет подобран для
дальнейшей работы агента» перестаёт быть верной — это ровно то поведение, которое меняет этот
change. Формулировка заменяется на явное указание, что человек логинится в приложение через
прокси, выданный скиллом на первом шаге.

## Risks / Trade-offs

- **[Trade-off] Подбор прокси становится медленнее по факту диалога** — раньше `probeProxy`-цикл
  до `maxAttempts` мог отработать за секунды без участия человека; теперь каждая попытка требует
  ручного похода в приложение и ответа в чат. → Осознанно принято: цель — ручная проверка, не
  скорость; `maxAttempts` по умолчанию остаётся 5, пользователь может увеличить при плохом пуле.
- **[Риск] Без `probeProxy` явно неживые кандидаты (например, сразу нерабочий SOCKS5) обнаружатся
  только когда человек уже попробовал зайти в приложение** — раньше такие отсеивались
  автоматически до показа человеку. → Не мигрируется отдельная лёгкая TCP/SOCKS5-проверка перед
  выдачей — вне скоупа (см. Non-Goals), при необходимости можно добавить отдельным change, если
  это окажется частым на практике.
- **[Риск] Путаница между двумя режимами одного скрипта** (`probeProxy`-цикл для v1,
  `create-candidate`/`delete-candidate` для v2) — снижается комментарием в шапке файла,
  объясняющим, какой скилл какой режим использует (аналогично уже существующему комментарию про
  отличие от `provision-mobile-proxy.ts`).

## Migration Plan

Миграции данных нет — меняется только процесс создания **новых** агентов через v2. `tg-agent-
create` (v1) и уже созданные агенты не затрагиваются.

Откат: вернуть предыдущую версию `skills/tg-agent-create-v2/SKILL.md` (единый Шаг 1 со всеми
данными, `probeProxy`-цикл в Шаге 2 через уже существующий режим скрипта) — новые режимы скрипта
можно оставить неиспользуемыми либо убрать, они не влияют на существующий режим v1.
