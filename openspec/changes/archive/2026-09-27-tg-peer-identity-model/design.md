## Context

Полное техническое решение — в `docs/design/tg-peer-identity-model/architecture.md`
(парный к `requirements-v1.md`). Здесь — конспект ключевых решений для реализации;
за деталями схемы, алгоритмов и миграции обращаться к тому документу, не дублировать.

Текущее состояние (источник истины — код): `channels.db` хранит
`chatAccessHash`/`channelAccessHash` без провенанса; холодный путь
(`seedPeerCache`/`getChatAccessHash` в review-listener) читает их без проверки
актуальности → баг после переавторизации. Тип peer и членство выводятся неявно из
вида id и из `status`.

## Goals / Non-Goals

**Goals:**
- Не использовать `access_hash`, полученный до текущей авторизации; переполучать по
  стабильному id.
- Явный `peer_type` и отдельный дом членства `membership`.
- Устойчивость join/read/leave к переавторизации и корректность при замене аккаунта.
- Аддитивная, обратимая миграция `channels.db`.

**Non-Goals:**
- Метрики, `write_access`, post-watch, DM-кандидаты, статусные таймеры — колонки не
  трогаем.
- Перевод вне-скоупных потребителей `status` на `membership` и вычистка `status` —
  отдельный будущий change (план сходимости).

## Decisions

1. **Инвалидация `access_hash` сравнением таймстампов** (`access_hash_updated_at >=
   session_authorized_at`), а не тегом эпохи и не эагерным обнулением. `session_authorized_at`
   живёт рядом с `sessionString` в `tg-account.json` — reauth не трогает БД.
   Альтернативы (эпоха, эагерное обнуление) отвергнуты: лишняя сущность/лишняя запись
   по всей БД при reauth. См. architecture.md §2.2.
2. **Reacquire строго по marked id** (проход диалогов), без `ResolveUsername`. Причина:
   `access_hash` нельзя получить из голого id — только «встретить»; агент всегда
   участник reacquire-peer; снимается риск перехвата username. `username` — только для
   join и сверки. См. architecture.md §3.2, §3.6.
3. **`membership` — отдельное поле** с dual-write рядом со `status` на переходный
   период. Альтернатива (выводить из `status`) отвергнута: `status` смешивает членство
   и прикладной режим. `should_leave` остаётся в `status` (pending-действие), в
   `membership` не переносится. См. architecture.md §2.3, §5.1.1.
4. **Миграция — Вариант A (аддитивные `ALTER TABLE`)**. Обратима, не задевает
   вне-скоупных потребителей. Унаследованные `access_hash` без таймстампа считаются
   невалидными и переполучаются на первом обращении. Вариант B (пересоздание) отвергнут
   как рискованный/необратимый. См. architecture.md §5.2.
5. **`linked_broadcast_username`** — first-class хэндл, маппится на уже хранимый
   `channelUsername` (без нового дубля). См. architecture.md §2.1, §5.1.

## Risks / Trade-offs

- [Временное дублирование факта членства (`membership` ↔ членские значения `status`)]
  → dual-write в одной операции держит поля согласованными; вычистка `status` — в
  будущем change с обязательным порядком (сначала перевод читателей, потом вычистка).
- [Стоимость холодного переполучения проходом диалогов после reauth между постановкой
  ревью и кликом ревьюера] → случай редкий, деградация — задержка, не отказ.
- [Неверный дефолт `peer_type` при миграции (broadcast vs megagroup)] → тип не влияет
  на сборку `InputPeer`; уточняется первым живым резолвом.

## Migration Plan

Аддитивная миграция `channels.db` тем же паттерном, что существующие `migrate*Columns`
в `channels.ts`: добавить `peer_type`, `chat_access_hash_updated_at`,
`channel_access_hash_updated_at`, `membership`, `membership_updated_at`,
`migrated_to_id`. `membership` популируется из `status` по таблице отображения
(architecture.md §5.1.1); `*_updated_at` для унаследованных хэшей — NULL (невалидны →
переполучение). Разовый бэкафилл конфигов `session_authorized_at` не обязателен:
отсутствие поля трактуется как «невалидно», первая реавторизация проставит штатно.
Откат — колонки аддитивны, старый код их игнорирует.
