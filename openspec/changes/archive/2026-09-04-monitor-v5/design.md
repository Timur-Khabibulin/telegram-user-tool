## Context

`monitor.ts` (v1) — единственный скилл, который читает ВЕСЬ чат обсуждения:
непрочитанные сообщения (`getDialogsForBatch`+`getMessages`), классифицирует
их (`classifyMessages` → общие сообщения / новые ветки / продолжения),
отвечает на общие сообщения и ведёт диалоговые ветки, копит DM-кандидатов.
`monitor-v3`/`monitor-v4` работают иначе — только с конкретным постом канала
(и, в `only_comment`, с одной конкретной веткой под ним), полностью
игнорируя остальную активность чата.

Изначально рассматривался вариант заменить решение по общим сообщениям на
`generatePostCommentV5` (промпт `monitor-v4`, откалиброванный на постах
канала) — вызывая его на каждое общее сообщение по отдельности, поскольку
его схема ответа не содержит id сообщения и не может выбрать одно из списка
(в отличие от `analyzeChannelMessages`, который в v1 видит весь список общих
сообщений сразу одним вызовом и картину целиком). Это осознанно отклонено:
теряется именно то, ради чего v1 передавал в LLM весь список сразу — общий
контекст батча, а не одно сообщение в изоляции — и стоимость вызовов растёт
(N вызовов вместо одного). Решение по общим сообщениям остаётся полностью
от v1.

## Goals / Non-Goals

**Goals:**
- Читать весь чат обсуждения (непрочитанные, все три бакета классификации)
  — конвейер v1 без изменений по существу, включая решение по общим
  сообщениям и DM-скоринг (`analyzeChannelMessages`+`generateReply`, один
  вызов на канал, видит весь список общих сообщений сразу).
- Обработка ошибок отправки — уровня `monitor-v4` во всех трёх ветках ответа
  (новый тред, продолжение, общее сообщение).

**Non-Goals:**
- Проверка поста канала (веб-превью, гейт по комментариям, `only_comment`) —
  не входит в `monitor-v5` вообще. Это делает `monitor-v4`, параллельно и
  независимо.
- Замена промпта/логики отбора общих сообщений на `generatePostCommentV5`
  или любую другую рубрику `monitor-v4` — рассмотрено и отклонено (Context).
- Изменение `monitor.ts`/`monitor-v4.ts` — не трогаются ни строкой.
- Защита от одновременного включения `monitor`/`monitor-v5` на одного
  агента — сознательно не делается, тот же прецедент, что уже принят для
  `monitor`/`monitor-v2` и `monitor-v3`/`monitor-v4` (общий `channels.status`/
  `lastProcessedAt`, ответственность оператора).

## Decisions

**1. Обработка ошибок отправки — `handlePostCommentSendError` вместо
инлайн-обработки v1, во всех трёх ветках ответа.**
Функция уже общая для `monitor-v3`/`monitor-v4`/`review-listener`
(`core/post-comment-send.ts`) — переиспользуется как есть, `source:
"monitor_v5"` (новое значение `SendErrorSource`). Разница с v1: `PEER_FLOOD`
теперь приостанавливает агента (`PeerFloodError` → прогон завершается
немедленно, как в v4), бан на запись переводит канал в `status = "banned"`
(не только `enqueueBannedChannel`, как было в v1) и считает порог «10
забаненных каналов за сутки» → приостановка агента, запрет формата
переводит канал в `status = "format_error"`. Ни одного из этих статусов v1
не проставлял.

**2. Каданс и батч — те же, что у v1, без изменений.**
`getChannelsBatch(agentId, log, undefined, MONITOR_V5_CHECK_PERIOD_SECONDS)`
— новая константа, равная по значению `CHANNEL_CHECK_PERIOD_SECONDS` (72ч),
но отдельная (тот же приём, что уже применён к `MONITOR_V2_CHECK_PERIOD_SECONDS`
— разные версии могут разойтись по периоду в будущем, физически разные
константы страхуют от такого расхождения «по забывчивости»). Внешний каданс
задачи (`DEFAULT_PERIODIC_SCHEDULE`) — 180 мин (3ч), как у `"monitor"`
сейчас — тот же батч (40) на том же внешнем тике даёт тот же эффективный
период обхода канала (~72ч), что и v1.

## Risks / Trade-offs

- [Trade-off] `monitor-v5` — это фактически `monitor.ts` (v1) + более
  строгая обработка ошибок отправки `monitor-v4`, не более. Отбор и
  генерация ответа на общие сообщения не выигрывают от улучшений,
  сделанных для постов канала (`generatePostCommentV5`) — осознанное
  решение (Context), а не упущение.
- [Trade-off] Общий `channels.status`/`lastProcessedAt` с `monitor`/
  `monitor-v2`/`monitor-v3`/`monitor-v4` — взаимоисключающее включение,
  ответственность оператора (см. Non-Goals), тот же принятый риск, что и
  везде в этой линейке.

## Migration Plan

1. Аддитивные изменения БД/типов: `SendErrorSource += "monitor_v5"`,
   `TaskType += "monitor-v5"`.
2. Новый скилл `monitor-v5.ts`, регистрация в `dispatcher.ts`/`index.ts`
   (`taskTypeParam`, урок из `monitor-v4` — не забыть этот файл).
3. Задеплоить — код неактивен, пока `monitor-v5` не включена ни одному
   агенту.
4. Включить точечно на одном-двух агентах через `scheduler-control`, без
   одновременного `monitor`/`monitor-v2`/`monitor-v3`/`monitor-v4` на тех
   же агентах (Decision Non-Goals), понаблюдать через `llm_log`/`runs`.

Откат: выключить задачу `monitor-v5` в `tasks` для агента — тот же механизм,
что и для любого `TaskType`.
