## Context

Скиллы (`src/skills/*`) возвращают диспетчеру `SkillStatus { status, terminal?, details }`. Диспетчер (`src/scripts/dispatcher.ts`) для каждого прогона сдвигает `nextRun` и шлёт отчёт в Saved Messages через `formatReport`, который сейчас просто оборачивает `details` в `JSON.stringify`. LLM-вызовы идут через `LlmClient` (`complete` — свободный текст, `completeObject` — структурированный JSON со схемой zod); промпты собираются функциями из `src/llm/prompts.ts`.

Два узких места:
- **Отчёт нечитаемый и неполный** — сырой JSON, английские ключи, нет длительности, теряются темы/тексты ответов/кандидаты.
- **`monitor` дорог по LLM** — `scoreForDM` вызывается на каждое general-сообщение каждого канала; плюс отдельные `extractTopics`, `selectRelevantMessage`, `generateReply`. `dm-replies` делает `analyzeSentiment` + `generateDmReply` (2 вызова на тред).

Изменение модифицирует перенесённый код из `task-scheduler` (не архивирован). Промпты в `prompts.ts` ранее переносились «дословно» (R-B2) — здесь это правило осознанно ослабляется: объединённые промпты вводятся ради сокращения стоимости.

## Goals / Non-Goals

**Goals:**
- Отчёт — человекочитаемый текст с длительностью прогона и числом LLM-запросов, единый рендер для всех скиллов.
- `monitor`: путь `generalMessages` — один структурированный LLM-вызов на канал; не более одного ответа на канал; без отдельного шага тем; дешёвый префильтр до LLM.
- `dm-replies`: один LLM-вызов на тред вместо двух, наблюдаемое поведение неизменно.
- Русские `details` у `monitor` и `account-warmup` + текст отправленного ответа в `account-warmup`.

**Non-Goals:**
- Не меняем содержание/ключи `details` у `dm-send`, `dm-replies`, `join-queue` (только форму вывода — она общая).
- Не трогаем треды `monitor` (`generateThreadReply` / `generateThreadContinuation`) — остаются по вызову на тред.
- Не меняем пороги/критерии скоринга DM (`score >= 0.6`) и логику cooldown/лимитов.
- Не вводим prompt caching и не меняем провайдера LLM.

## Decisions

### 1. Замер длительности — в диспетчере, не в скиллах
`dispatcher.main` оборачивает вызов `skill(ctx)`: `const t0 = Date.now()` … `durationMs = Date.now() - t0`, передаёт в `formatReport`.
- **Почему:** время появляется во **всех** отчётах без правки кода скиллов (включая нетронутые `dm-send`/`dm-replies`/`join-queue`). Единая точка.
- **Альтернатива:** каждый скилл сам кладёт длительность в `details` — отвергнуто (дублирование, пришлось бы трогать нетронутые скиллы).

### 1b. Счётчик LLM-запросов — в `LlmClient`, срез в диспетчере
`LlmClient` инкрементирует внутренний счётчик на **каждый фактический запрос к модели** — то есть в каждом месте вызова `generateText` / `generateObject` в `client.ts` (включая ретраи слоёв `completeObject`: нативный structured output → текстовый фидбэк-ретрай). Клиент экспонирует чтение счётчика (например `llm.requestCount`). Диспетчер снимает срез до и после `skill(ctx)`: `llmCalls = llm.requestCount - before` и передаёт в `formatReport`.
- **Почему фактические запросы, а не вызовы `complete`/`completeObject`:** «кол-во запросов к ЛЛМ» должно отражать реальную нагрузку/стоимость; один `completeObject` может стоить 1–3 round-trip из-за ретраев — честно учитываем все.
- **Почему в клиенте, а не в скиллах:** число появляется во **всех** отчётах без правки скиллов; единственный экземпляр `llm` уже общий на прогон, срез по дельте корректен при последовательном выполнении задач.
- **Альтернатива:** считать на уровне методов (`complete`/`completeObject` = 1) — отвергнуто как занижающее реальное число при ретраях.

### 2. `formatReport` — рендер по типу скилла
`formatReport` рендерит человекочитаемый текст: шапка (иконка, agentId, тип, статус, terminal, длительность, `nextRun`) + тело. Тело — это `details`, развёрнутые в строки `Ключ: значение`; вложенные объекты (например «ответов отправлено») — с отступом/подсписком. Русские ключи `monitor`/`account-warmup` приходят прямо из `details` скилла; у нетронутых скиллов ключи остаются английскими, но выводятся так же построчно.
- **Почему построчный generic-рендер, а не отдельная функция на каждый скилл:** меньше кода, нетронутые скиллы получают читаемый вид «бесплатно», не зная про рендер.
- **Альтернатива:** жёстко закодировать формат под каждый тип задачи — отвергнуто как избыточное; generic-обход `details` достаточно.
- Текст ответа/сообщения в `details` обрезается рендером до разумной длины (например 280 симв.), чтобы отчёт не разрастался.

### 3. `monitor` — один структурированный вызов на канал
Новый промпт `analyzeChannelMessages(messages)` → `completeObject` со схемой:
```
{
  "ответитьНа": { "id": number, "текст": string } | null,
  "dmКандидаты": [ { "id": number, "score": number, "reason": string } ]
}
```
- `ответитьНа` — одно сообщение для ответа (или `null`, если нечего): заменяет `selectRelevantMessage` (массив → один). После него — один `generateReply` (или текст ответа кладётся прямо в структуру, см. ниже).
- `dmКандидаты` — заменяет N вызовов `scoreForDM`; скилл фильтрует по `score >= DM_SCORE_THRESHOLD` и пишет `insertDmCandidate` как раньше.
- `extractTopics` из monitor-пути удаляется.
- **Один ответ на канал:** соответствует существующему интенту спеки group-monitoring («одно сообщение, ответ»); код (`z.array`) от него отклонялся.
- **Открытый под-выбор:** включать ли черновик ответа в тот же структурированный вызов (поле `текстОтвета`) или оставить отдельный `generateReply`. Решение: оставить **отдельный `generateReply`** — генерация свободного текста ответа в стиле персоны качественнее отдельным `complete()` с `system=persona`, а структурированный вызов отвечает только за выбор+скоринг. Итог на канал: `1` (анализ) + `0|1` (ответ) вместо `2 + N + S`.

### 4. `monitor` — префильтр до LLM
Перед формированием списка для `analyzeChannelMessages` скилл отбрасывает заведомо непроходные general-сообщения дешёвой эвристикой в коде: длина текста меньше порога (~15 симв.), только эмодзи/пунктуация, отсутствие буквенных символов.
- **Почему:** `scoreForDM` и так отсекал такие сообщения, но платным запросом; теперь они не попадают даже в батч.
- **Риск:** эвристика может отсечь короткое, но осмысленное сообщение — порог делаем консервативным (очень короткие/реакции).

### 5. `dm-replies` — объединённый вызов
Новый промпт `analyzeAndReply(triggerMessage, history, newMessages)` → `completeObject`:
```
{ "sentiment": "positive" | "negative", "ответ": string | null }
```
При `negative` модель не заполняет `ответ` (инструкция в промпте), скилл делает `mark_as_read` и пропускает — как сейчас. При `positive` — `ответ` уже сгенерирован, отправляем.
- **Почему:** позитивные треды (большинство) экономят round-trip (2→1); негативные остаются 1 вызов. Наблюдаемое поведение (negative→skip, positive→reply) не меняется.
- **Альтернатива:** батчить все треды одним вызовом — отвергнуто (разные истории/контексты, большой промпт, риск качества).

## Risks / Trade-offs

- **[Объединённый вызов monitor даёт некачественный JSON]** → `completeObject` уже имеет слой нативного structured output + фидбэк-ретрай + coerce (`llm/client.ts`); схема zod валидирует. При полном провале — скилл вернёт `error`, диспетчер всё равно сдвинет `nextRun` (R-D1).
- **[Один ответ на канал — потеря охвата]** → осознанно: несколько ответов агента в одном чате выглядят как бот-спам; единичный ответ безопаснее для аккаунта и соответствует интенту спеки.
- **[Префильтр отсечёт нужное сообщение]** → консервативный порог; влияет только на отбор кандидата для ответа/DM, не на чтение/`mark_as_read`.
- **[Генерация ответа на негатив в dm-replies впустую]** → исключено: при `negative` поле `ответ` пустое по инструкции промпта, лишней генерации текста нет (один вызов и так делался для sentiment).
- **[Зависимость от неархивированного task-scheduler]** → спек-дельты пишутся против baseline-капабилити (`group-monitoring`, `dm-replies`) + новая `skill-run-report`; конфликтов с дельтами task-scheduler нет, т.к. затрагиваются разные требования.

## Migration Plan

1. Реализация в коде (диспетчер, скиллы, промпты) — обратносовместимо по контракту `SkillStatus`.
2. Деплой на VPS обычным путём (`scp` + перезапуск, как для task-scheduler). Откат — возврат предыдущей версии файлов; БД-схемы не меняются.
3. Проверка: дождаться планового прогона `monitor`/`dm-replies`/`account-warmup`, убедиться в Saved Messages, что отчёт читаем, содержит длительность и новые поля.
