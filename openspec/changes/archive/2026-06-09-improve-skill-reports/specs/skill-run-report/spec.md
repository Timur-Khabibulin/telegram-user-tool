## ADDED Requirements

### Requirement: Отчёт прогона — человекочитаемый текст

Диспетчер SHALL формировать отчёт прогона в Saved Messages как человекочитаемый текст, а НЕ как сырой `JSON.stringify(details)`. Шапка отчёта SHALL содержать статус (иконку успеха/ошибки), идентификатор агента, тип задачи, признак терминального статуса (если есть) и `nextRun`. Тело SHALL разворачивать поля `details` построчно в виде `Ключ: значение`; вложенные объекты SHALL выводиться подсписком с отступом. Длинные текстовые значения (тексты ответов/сообщений) SHALL обрезаться до разумного предела, чтобы отчёт не разрастался. Рендер SHALL быть единым для всех типов скиллов.

#### Scenario: Отчёт читаем, не JSON
- **WHEN** диспетчер завершает прогон любого скилла
- **THEN** в Saved Messages уходит текстовый отчёт со строками `Ключ: значение`, без сырого JSON-дампа

#### Scenario: Нетронутые скиллы получают читаемый вид
- **WHEN** завершается прогон `dm-send`, `dm-replies` или `join-queue`
- **THEN** их `details` (с прежними ключами) выводятся тем же построчным рендером, набор полей не меняется

#### Scenario: Длинный текст обрезается
- **WHEN** поле `details` содержит текст длиннее предела обрезки
- **THEN** в отчёте оно показано усечённым

### Requirement: Длительность прогона в отчёте

Диспетчер SHALL замерять время выполнения каждого скилла (вокруг вызова `skill(ctx)`) и выводить длительность в шапке отчёта по-русски. Замер SHALL выполняться в диспетчере, без изменения кода скиллов, и SHALL присутствовать в отчётах всех типов задач.

#### Scenario: Длительность показана для любого скилла
- **WHEN** диспетчер завершает прогон скилла
- **THEN** шапка отчёта содержит длительность прогона на русском (например «длительность: 12.3 с»)

#### Scenario: Длительность есть и при ошибке
- **WHEN** скилл завершился со статусом `error`
- **THEN** отчёт всё равно содержит длительность прогона

### Requirement: Количество LLM-запросов в отчёте

`LlmClient` SHALL вести счётчик фактических запросов к модели (инкремент на каждый вызов модели, включая внутренние ретраи структурированной генерации) и предоставлять его чтение. Диспетчер SHALL снимать срез счётчика вокруг вызова скилла (разница «после − до») и выводить количество LLM-запросов в шапке отчёта по-русски. Подсчёт SHALL выполняться без изменения кода скиллов и SHALL присутствовать в отчётах всех типов задач.

#### Scenario: Число LLM-запросов показано для любого скилла
- **WHEN** диспетчер завершает прогон скилла
- **THEN** шапка отчёта содержит количество запросов к LLM за этот прогон на русском

#### Scenario: Скилл без LLM рапортует ноль
- **WHEN** завершается прогон `join-queue` (не обращается к LLM)
- **THEN** в отчёте количество LLM-запросов равно 0

#### Scenario: Ретраи учитываются
- **WHEN** структурированный вызов внутри скилла потребовал повторного обращения к модели
- **THEN** счётчик отражает все фактические запросы, а не только число логических вызовов `complete`/`completeObject`

### Requirement: Состав отчёта monitor

`details` скилла `monitor` SHALL использовать русские ключи и содержать: «каналов обработано», «каналов с активностью» (где были непрочитанные сообщения), «каналов пропущено (ошибки)» (где упал `telegram_get_messages`); «ответов отправлено» как объект с «всего» и разбивкой по типам — «новые треды», «продолжения тредов», «общие сообщения»; «dm-кандидатов добавлено» как число.

#### Scenario: monitor рапортует разбивку ответов
- **WHEN** `monitor` отправил ответы разных типов за прогон
- **THEN** «ответов отправлено» содержит «всего» и числа по «новые треды» / «продолжения тредов» / «общие сообщения»

#### Scenario: monitor рапортует счётчики каналов
- **WHEN** прогон `monitor` завершён
- **THEN** отчёт содержит «каналов обработано», «каналов с активностью» и «каналов пропущено (ошибки)»

#### Scenario: DM-кандидаты — только число
- **WHEN** `monitor` записал DM-кандидатов
- **THEN** отчёт содержит «dm-кандидатов добавлено» как число, без перечисления самих кандидатов

### Requirement: Состав отчёта account-warmup

`details` скилла `account-warmup` SHALL использовать русские ключи и SHALL содержать поле «ответ» с текстом отправленного сообщения, когда ответ был отправлен. Если ответ не отправлялся (нет кандидатов / нет релевантного сообщения), поле «ответ» SHALL отсутствовать.

#### Scenario: account-warmup показывает текст ответа
- **WHEN** `account-warmup` отправил ответ на выбранное сообщение
- **THEN** отчёт содержит поле «ответ» с текстом отправленного сообщения

#### Scenario: Ответ не отправлялся
- **WHEN** `account-warmup` не нашёл релевантного сообщения и ничего не отправил
- **THEN** в отчёте поля «ответ» нет
