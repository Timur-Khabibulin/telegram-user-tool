## Context

`monitor-v2` (`src/skills/monitor-v2.ts`) — вторая, независимая версия группового
мониторинга, посещает каждый канал агента примерно раз в
`MONITOR_V2_CHECK_PERIOD_SECONDS` (259200с / 3 дня, шаг «5» цикла обработки).
Канал уже может получить статус `banned` или `format_error` (`channels.status`,
из `telegram-error-handling`) — оба бессрочные, `banned` останавливает
обработку канала (шаг 5.0), `format_error` — только информационный, обработка
продолжается.

Telegram/MTProto не даёт списка «что удалено» — единственный способ узнать,
жив ли конкретный `msgId`, это запросить его явно (`client.getMessages(peer,
{ids})`); удалённые id отсутствуют в ответе. Точечный вариант этого вызова уже
есть — `TelegramService.getMessageById` (`service.ts:613`), используется
гейтом свежести постов (`post-freshness-gate`).

Время отправки собственных сообщений агента в канал сейчас хранится
неполно: `replies.sentAt` — для ответов вне тредов, но
`group_thread_agent_msgs` (сообщения агента внутри тредов) такого поля не
имеет вовсе.

## Goals / Non-Goals

**Goals:**
- Автоматически приостанавливать конкретный канал на 3 дня, если за последние
  14 дней там удалено больше 2 сообщений агента.
- Сделать статусную модель `channels.status` расширяемой по длительности и
  причине, не создавая отдельной таблицы под каждый новый вид статуса.
- Не увеличивать нагрузку на Telegram сверх одного батч-запроса `getMessages`
  на канал за визит, и только если у канала были сообщения агента за окно.
- Не портить существующее поведение `banned`/`format_error` — оба остаются
  бессрочными без единой строки изменений в местах, где они уже
  выставляются.

**Non-Goals:**
- Не меняем `monitor.ts` (v1) — там статусная модель каналов не
  используется и не должна начать использоваться этим изменением.
- Не различаем причину «удалил модератор» / «удалил спам-фильтр» /
  «сообщение возрастное» и т.п. — считаем только факт исчезновения.
- Не боремся с ложноположительными срабатываниями при миграции чата в
  супергруппу (смена пространства `msgId`) — фиксируем как известное
  ограничение.
- Не вводим составной/множественный статус канала — `status` остаётся одним
  полем, «последний статус побеждает» при коллизии.

## Decisions

### 1. Длительность статуса — поле `statusDurationSeconds`, не `statusUntil`

Храним длительность (секунды), а не абсолютное время истечения. При выборе
между «длительность» и «until-timestamp» выбрана длительность, потому что она
явно показывает происхождение статуса (бессрочный vs. временный на N секунд) и
не требует пересчёта при чтении для отображения «осталось столько-то». Истечение
вычисляется на лету: `statusDurationSeconds IS NOT NULL AND now >=
statusUpdatedAt + statusDurationSeconds`. `NULL` = бессрочно — так остаются
`banned`/`format_error` без единой правки существующих call sites
`markChannelStatus`.

### 2. Причина статуса — свободный текст (`status_description`), не таксономия

По аналогии с `send_errors.errorCode` (`channels.ts:751`, комментарий «те же
строки, что код уже вычисляет, без новой таксономии») — `status_description`
не enum, а произвольная строка, которую пишет вызывающий код. Единственный
текущий источник — `messages_deleted: N за 14 дней` для `suspend`. Это
осознанно оставляет поле готовым для будущих причин `suspend` без миграции
схемы.

### 3. Проверка удаления пристёгнута к штатному визиту канала, не отдельный скрипт

Альтернатива — отдельный systemd-таймер/скрипт, проверяющий все каналы всех
агентов раз в сутки. Отклонено: добавляет новую точку входа диспетчера ради
сущности, которая и так посещается раз в 3 дня штатным циклом `monitor-v2`; при
окне проверки в 14 дней такая частота (раз в 3 дня) даёт 4–5 проверок в
пределах окна — этого достаточно, специальное расписание не требуется
(«не плодить лишние сущности», `docs/agent-playbook.md`).

### 4. Источник «сообщений агента» — объединение `replies` и `group_thread_agent_msgs`

Оба типа ответов (вне треда и внутри треда) — это сообщения, реально
отправленные агентом в канал от своего имени, и оба одинаково подвержены
удалению. Ограничиться только `replies` означало бы не видеть удаление
тредовых ответов — по факту решение пользователя: учитывать оба источника
(см. proposal). `group_thread_agent_msgs` получает колонку `sentAt`
(аддитивно, заполняется тем же `now`, что уже вычисляется в
`createThread`/`updateThread` для `lastActivityAt`) — без этого поля нельзя
было бы применить окно 14 дней к тредовым сообщениям.

### 5. Батч-выборка исключает `banned`/`suspend`, не только пропуск на шаге 5.0

Существующий шаг 5.0 (`if (channel.status === "banned") continue`) не
вызывает `markChannelProcessed`, поэтому `lastProcessedAt` у забаненного
канала не обновляется — канал попадает в **каждый** следующий батч
(`getChannelsBatch`, `channels.ts:268`) только чтобы быть немедленно
пропущенным. Для бессрочного `banned` это самоограничивающийся баг (канал
уходит через `leave-banned-channels`), но для temporary `suspend` это было бы
критично: канал забивал бы слот батча все 3 дня простоя, вытесняя реально
назревшие каналы. Решение — фильтровать на уровне SQL-запроса
(`AND status NOT IN ('banned', 'suspend')`), а не чинить `markChannelProcessed`
в шаге 5.0 (минимальное по площади изменение, заодно чинит предсуществующее
поведение для `banned`).

### 6. Место записи события — `send_errors`, не `error_log`

`error_log` (`error-log.ts`) — account-level журнал, пишется вместе с
`upsertRestriction` при событиях, приостанавливающих **весь аккаунт**
(`PEER_FLOOD`, 2 забаненных канала за 2 дня). Приостановка одного канала не
затрагивает остальные каналы агента — это per-channel событие, значит место —
`send_errors` (`channels.ts:769`), уже используемый для канальных событий и
уже агрегируемый в отчёт проблемных каналов (`channels.ts:1042`). Выбор
`error_log` создал бы дублирующий источник и ложно сигнализировал бы про
приостановку всего агента.

## Risks / Trade-offs

- **[Риск] Ложные срабатывания при миграции chat → supergroup** (Telegram
  меняет пространство `msgId` при апгрейде группы, старые id могут «исчезнуть»
  не будучи удалёнными) **→ Митигация**: не устраняется в этой итерации,
  порог в 2 сообщения и окно в 14 дней снижают частость ложных суспендов;
  зафиксировано как известное ограничение, не блокирует запуск.
- **[Риск] `status='suspend'` перезаписывает существовавший `format_error`**
  (single-column статус) **→ Митигация**: осознанно принято — «последний
  статус побеждает» проще составного статуса; обратная коллизия (format_error
  поверх активного suspend) физически невозможна, т.к. suspend полностью
  блокирует обработку канала до отправки, а format_error проставляется только
  при ошибке отправки.
- **[Риск] Лишний Telegram-вызов на визит канала** (`getMessagesExistence`)
  **→ Митигация**: вызывается только если у канала были сообщения агента за
  окно (не на каждый визит вхолостую); чанкуется по 100 id, укладывается в
  существующий бюджет вызовов на канал (наравне с `getMessages`,
  `markAsRead`).
- **[Trade-off] Проверка раз в ~3 дня, а не ежедневно** — решение 3: приемлемо
  для порога «>2 за 14 дней», при необходимости более частой проверки годовое
  решение — отдельный таймер, не в объёме этого изменения.

## Migration Plan

- Все изменения схемы аддитивны (`ALTER TABLE ... ADD COLUMN`, по
  существующему паттерну `migrateStatusColumns`/`migrateChannelIdentityColumns`)
  — не требуют даунтайма и бэкфилла, старые строки получают `NULL`
  (бессрочный статус / нет описания), что эквивалентно текущему поведению.
  Тот же паттерн для `group_thread_agent_msgs.sentAt` — старые строки без
  `sentAt` просто не участвуют в окне проверки удаления (эффективно как «не
  отправляли сообщений» для дат до деплоя).
- Откат — чисто по коду (новые колонки не мешают старой логике, если
  выполнение шага проверки удаления убрать из `monitor-v2.ts`); удаление
  колонок не требуется даже при откате.
