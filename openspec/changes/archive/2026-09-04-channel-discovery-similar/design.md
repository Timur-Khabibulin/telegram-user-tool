## Context

`channel-discovery` (TGStat) уже даёт реестр `discovery.db` (`canonical_link` PK +
`assigned_agent`), нормализацию ссылок, дедуп и доставку в per-agent `join_queue` через
`addJoinQueue`. Эта способность добавляет **второй источник** — нативные рекомендации
Telegram (`channels.getChannelRecommendations`) — переиспользуя всю обвязку реестра и
очереди как есть. Меняется только драйвер: вместо keyword-поиска по внешнему API —
обход графа похожих каналов на живой сессии каждого агента.

Ключевые опорные точки в коде:
- `src/core/db/discovery.ts` — реестр и `normalizeChannelLink` (переиспользуется).
- `src/core/db/join-queue.ts` — `addJoinQueue(agentId, links, log)` (переиспользуется).
- `src/core/discovery/run.ts` — драйв-луп TGStat-версии (структурный образец).
- `src/core/telegram/service.ts` — `getDialogs`, `getFullChannel`; `joinDiscussionGroups`
  (~586–665) содержит образец прямого хопа `username → channel → linked discussion-группа`
  и пейсинга FLOOD_WAIT (паузы 15–60с, retry).

## Goals / Non-Goals

**Goals:**
- Бесплатный источник похожих каналов поверх существующего реестра/очереди, без нового
  хранилища и без изменения поведения `join-queue`/`monitor`.
- Безопасность сессий агентов: обход останавливается по пуш-бэку Telegram, не по объёму.
- Детерминированный обход без LLM.

**Goals (доработка — две роли агентов, см. D10):**
- Развязать **искателей** (кто обходит, на чьих сессиях и seed-каналах) и **получателей**
  (кому достаются найденные каналы). Искателей задаёт оператор; получатели — все агенты
  платформы (`listAgentIds()`).
- Общая цель прогона `target × N` (N = `listAgentIds().length`), а не `target` на искателя.
- Ускорить обход: пауза между MTProto-вызовами 0.8–1.2 с (D9).

**Non-Goals:**
- Параллельный обход агентов-искателей (последовательный — сознательно).
- **Гейт** по вовлечённости: вовлечённость влияет только на порядок обхода seed (D9),
  на отбор каналов в очередь — нет (отбор только по `min_subscribers`, D3). Нативного
  готового ER-показателя в MTProto нет, но сырьё (просмотры + подписчики) доступно дёшево.
- Ограничитель глубины обхода (лимит по общему числу каналов `target × N` — в Goals).
- Обход Premium-усечения.

## Decisions

### D1. Источник — `channels.getChannelRecommendations`, обход графа вширь

От seeds агента вызываем `getChannelRecommendations(channel)`; найденные каналы кладём во
фронтир и раскручиваем дальше (BFS). Дедуп против реестра одновременно обрезает повторный
обход узлов. Альтернатива (глобальные рекомендации без `channel`) отвергнута — не привязана
к теме агента.

### D2. Seeds = все каналы каждого искателя; хоп discussion-группа → broadcast-канал

(Seeds берутся у каждого агента-искателя и сводятся в общий пул прогона — см. D10.)

Агент вступает в **discussion-группы** каналов (`joinDiscussionGroups`), а
`getChannelRecommendations` требует **broadcast-канал**. Поэтому для каждого seed нужен
обратный хоп: `getFullChannel(группа)` → `linkedChatId` → объект broadcast-канала из
`chats` того же ответа. Это зеркало прямого хопа в `joinDiscussionGroups`.

**Сбор «всех каналов агента» — новый код.** Текущий `getDialogs` фильтрует по непрочитанным
и кэширует только верхушку; таблица `channels` хранит `chatId` (id discussion-группы) без
username. Нужен метод, возвращающий все группы/каналы агента из диалогов (без unread-фильтра)
как entity, пригодные для `getFullChannel`. Берём из **всех диалогов агента** (а не только
из таблицы `channels`).

### D3. Гейт качества — только `min_subscribers`, через `getFullChannel`

В объектах из выдачи рекомендаций (`Channel`) числа подписчиков нет — оно в `ChannelFull`.
Поэтому подписчиков узнаём через `getFullChannel` на кандидата (1 вызов). ER не считаем.

### D4. Назначение — round-robin по агентам платформы на фазе распределения (доработка, см. D10)

Найденные каналы НЕ закрепляются за нашедшим искателем. Фаза сбора (D10) копит общий пул
прошедших порог каналов без владельца; фаза распределения раскладывает пул round-robin по
всем `N` агентам платформы, до `target` каждому, и только тогда вызывает
`registerChannel(adminAgentId, canonical, agent)` + `addJoinQueue(agent, …)`.
`registerChannel` по-прежнему `INSERT OR IGNORE` по `canonical_link` PK — инвариант «один
канал — один агент, навсегда» держится на нём. `isKnownChannel` остаётся ранней отсечкой
на фазе сбора (до дорогого `getFullChannel`), отсекая каналы, уже закреплённые прошлыми
прогонами; гарантию даёт PK. Прежний finder-first-wins по искателю заменён распределением.

### D5. Остановка — общая цель `target × N`, 2 FLOOD_WAIT подряд или исчерпание графа

Фаза сбора (D10) завершается по любому из условий:
- **Пул набран** — собрано `target × N` каналов, прошедших порог (общая цель прогона, а не
  на искателя); проверка после каждого попадания в пул. Это основной управляемый оператором
  лимит (`target` × число агентов платформы). Глубиной обход по-прежнему не ограничен.
- **2 FLOOD_WAIT подряд у искателя** — FLOOD_WAIT отрабатываем ожиданием+ретраем; счётчик
  подряд идущих FLOOD_WAIT сбрасывается после успешного вызова; на втором подряд —
  стоп обхода у этого искателя, переход к следующему искателю.
- **графы искателей исчерпаны** — фронтир BFS по всем искателям опустел (новых каналов,
  проходящих дедуп и гейт, больше нет); пул может быть меньше `target × N`.

Жёсткая ошибка на узле (CHANNEL_INVALID, нет рекомендаций) → пропуск узла, в счётчик не идёт.

### D6. Последовательный обход → единственный писатель реестра

Один host-процесс перебирает агентов по очереди, грузит сессии по одной. В `discovery.db`
пишет один обход в каждый момент → конкуренции нет, спец-механизмы (WAL/busy_timeout) не
требуются. Параллельный режим отложен (Non-Goal); при будущем переходе на него
`openDb` реестра нужно будет дополнить `busy_timeout`/WAL.

### D7. Порядок вставок «реестр → join_queue» — как в TGStat-версии

Сначала `registerChannel`, затем `addJoinQueue` (тот же порядок и тот же известный край,
что в `run.ts`). Принят владельцем осознанно — см. Risks.

### D8. Компоненты

- Обход и политика — `src/core/discovery/similar.ts` поверх `TelegramService`: сбор seeds,
  хоп seed→broadcast, `getChannelRecommendations`, гейт подписчиков, фронтир, дедуп, claim,
  push, стоп по FLOOD_WAIT. (Реализовано одним файлом `similar.ts`; ранние редакции дизайна
  упоминали `recommendations.ts`/`run.ts` — фактической структуре соответствует `similar.ts`.)
- Тонкий скрипт `src/scripts/discovery-similar.ts` + операторский скилл `discovery-similar`
  (диалог: порог, опционально агенты и окно вовлечённости; отчёт). Без LLM.

### D9. Приоритизация seeds по вовлечённости (доработка)

Seed-каналы **со всех искателей собираются в общий пул и ранжируются глобально** (не по
каждому искателю отдельно) по убыванию вовлечённости за окно — обход идёт от самого живого
seed к наименее живому через всех искателей. При раннем стопе по общей цели `target × N`
первыми раскручиваются рекомендации каналов с самой живой аудиторией (граф похожих у них
релевантнее). Это **порядок, не гейт** (отбор кандидатов — по-прежнему только
`min_subscribers`, D3). Ветка каждого seed обходится на сессии того искателя, чей это seed
(accessHash привязан к сессии, см. D10).

**Метрика.** `median(просмотры постов в окне) / число подписчиков`. Медиана — устойчива к
выбросам (закреп/виральный пост). Нормировка на подписчиков — уравнивает каналы разного
размера. Форма `median(views) / subs` численно эквивалентна `median(views/subs)` по
порядку, но дешевле — берём её.

**Сбор — 2 вызова на seed, ключевое открытие.** Объект сообщения из истории
(`messages.GetHistory` → `Api.Message.views`) уже несёт просмотры, дату и id для постов
broadcast-канала. Значит отдельный `messages.GetMessagesViews` (существующий `getPostViews`)
не нужен — поштучный сбор просмотров отвергнут. Достаточно:
1. новый тонкий метод `TelegramService` (история постов broadcast за окно → просмотры+даты);
   текущий `getMessages` непригоден — он отбрасывает посты `Api.Channel` и не проецирует
   `views`, у него своя роль (чтение реплик в обсуждениях), не расширяем;
2. `getChannelSubsCount`/`getChannelSubscribers` (уже есть) — число подписчиков на seed.

**Безопасность.** Оба вызова идут через тот же `floodAware` + пейсинг 0.8–1.2 с (D9.1),
что и обход. 2 FLOOD_WAIT подряд на фазе подготовки → `FloodStop` останавливает обход у
этого искателя (D5 действует и здесь). Провал измерения отдельного seed (жёсткая ошибка
после ретрая) → у него вовлечённость «неопределима» → в конец списка, обход продолжается.

**Точка встройки.** Между сборкой общего seed-пула искателей и стартом `while`-BFS: одна
стартовая глобальная сортировка уровня 0. FIFO-очередь дальше сохраняет порядок; кандидаты
уровней 1+ кладутся в конец и не пересортировываются.

### D9.1. Темп обхода — пауза 0.8–1.2 с между MTProto-вызовами (доработка)

`pacingMs` снижается с 3–7 с до **0.8–1.2 с** после каждого MTProto-вызова на всех этапах
(сбор seeds, ранжирование, рекомендации, гейт подписчиков). Read-методы
(`getChannelRecommendations`, `getFullChannel`, `GetHistory`) легче join, а сеть обработки
FLOOD_WAIT (ожидание+ретрай, стоп по 2 подряд — D5) остаётся как страховка от слишком
агрессивного темпа. Оценка времени прогона: ≈ `target × N × 3` MTProto-вызовов × паузу
(≈3 вызова на собранный канал — 1 запрос рекомендаций + ~2 проверки подписчиков), то есть
порядка минут–десятков минут вместо часов. Без Premium рекомендации усечены → кандидатов
на узел меньше → вызовов на канал больше → время выше.

**Параметр окна.** `engagementWindowDays` (дни), дефолт 45 («месяц-два»). Проброс — как у
`min_subscribers`/`target`: скилл → скрипт → `RunSimilarParams` → `SimilarParams` →
`crawlAgentSimilar`; внутри `sinceUnixTs = now - windowDays*86400`.

**Краевые случаи → «неопределима» → в конец (стабильный порядок между такими):** нет постов
в окне; посты без `views`; подписчики `null`; `subscribers = 0` (защита от деления на ноль).

### D10. Две фазы: сбор (искатели) → распределение (все агенты платформы) (доработка)

Прогон разбит на две фазы вместо обхода «агент → его очередь»:

**Фаза 1 — сбор.** Seed-каналы со всех искателей собираются в общий пул, ранжируются
глобально (D9), затем идёт BFS по уровням до общей цели `target × N` (D5). Найденные
каналы копятся в **пул без владельца** (дедуп против реестра `isKnownChannel` + внутри
прогона). Ветка каждого seed обходится на сессии того искателя, чей это seed: `accessHash`
канала действителен только на сессии, где он получен, поэтому ветки нельзя «перемешивать»
между сессиями. Реализуется группировкой обхода по искателю с сохранением глобального
порядка приоритета (искатели обходятся по очереди, как раньше, но с общим счётчиком цели и
общим пулом — стоп по `target × N`, а не по `target` на искателя).

**Фаза 2 — распределение.** Пул раскладывается round-robin по всем `N` агентам платформы,
до `target` каждому (D4): `registerChannel(adminAgentId, canonical, agent)` +
`addJoinQueue(agent, …)`. Получатели = `listAgentIds()` (включая искателей). Если пул меньше
`target × N` — добор равномерный, кому-то достанется меньше.

Развязка «кто ищет / для кого ищем»: один здоровый аккаунт-искатель может наполнить
каналами все агенты платформы; несколько искателей делят общую цель.

## Risks / Trade-offs

- **Premium-усечение** → без Premium `getChannelRecommendations` отдаёт усечённый список
  (~10/узел); кластер беднее. Mitigation: принять как ограничение v1; вынесено в Future
  Work. Опционально позже — детектировать `ChatsSlice.count` и предупреждать оператора.
- **Двойной `getFullChannel`** (на seed + на каждого кандидата) грузит сессию → риск
  FLOOD_WAIT на больших графах. Mitigation: пейсинг (паузы между вызовами) + стоп по D5.
- **Доп. нагрузка приоритизации** (D9): +2 вызова на seed на фазе подготовки до BFS,
  растёт с числом каналов агента. Mitigation: тот же пейсинг и стоп по D5 (2 FLOOD_WAIT
  подряд останавливают агента и на этой фазе); провал одного seed безвреден (в конец списка).
- **Потеря доставки при сбое между `registerChannel` и `addJoinQueue`** → канал в реестре,
  но не в очереди; при повторе дедуп его пропустит. Mitigation: принято осознанно (D7);
  при необходимости — отложенная сверка реестра против очереди (Future Work).
- **Сбор seeds упирается в окно диалогов** → если у агента очень много диалогов, полнота
  seeds ограничена выборкой диалогов. Mitigation: брать все каналы агента из диалогов; при
  нехватке — расширить выборку. BFS частично компенсирует неполноту seeds раскруткой графа.
- **Узлы без username** в выдаче (приватные) не канонизируются. Mitigation: пропускать —
  без username нет `canonical_link` для дедупа/доставки.
- **Гонка с одновременным TGStat-прогоном** за общий реестр. Mitigation: защита на
  `canonical_link` UNIQUE + продуктовое правило «прогоны не перекрываются».

## Open Questions

Нет — ключевые развилки согласованы с владельцем: роли `agents` (искатели) и `target`
(новых на агента платформы, общая цель `target × N`, N = `listAgentIds()`); две фазы
сбор→распределение (D10); round-robin по агентам платформы (D4); обход ветки seed на сессии её
искателя (D10); пауза 0.8–1.2 с (D9.1); стоп по 2 FLOOD_WAIT подряд и Premium как
ограничение.
