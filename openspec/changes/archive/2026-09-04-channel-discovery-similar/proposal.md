## Why

Существующий `channel-discovery` ищет каналы только во внешнем платном агрегаторе
(TGStat) по ключевым словам. У Telegram есть нативный бесплатный сигнал «похожие
каналы» (`channels.getChannelRecommendations`), которым питается блок рекомендаций в
официальном клиенте. Это дешёвый источник профильных каналов от уже проверенных каналов
агента, дополняющий keyword-поиск. Полный контекст —
`docs/design/channel-discovery-similar/channel-discovery-similar-v1.md`.

## What Changes

- Новый **операторский скилл `discovery-similar`**: оператор задаёт порог
  `min_subscribers` и целевое число каналов на агента `target` (и при желании список
  агентов и окно наблюдения вовлечённости), скилл запускает обход и показывает отчёт.
  Без LLM, без ключевых слов.
- **Приоритизация отправных точек по вовлечённости**: перед обходом seed-каналы агента
  упорядочиваются по убыванию вовлечённости аудитории за окно наблюдения (медиана
  просмотров поста / число подписчиков); обход идёт от самого живого канала. Это
  **порядок, а не отбор** — на допуск кандидатов в очередь не влияет (гейт отбора —
  по-прежнему только `min_subscribers`). Упорядочивается только уровень 0. Окно задаёт
  оператор (`engagementWindowDays`, дефолт 45).
- Новый **скрипт обхода** (standalone, запуск оператором): **последовательно** по агентам,
  каждый — на его собственной сессии. Для агента берёт **все его каналы** как seeds,
  обходит граф `getChannelRecommendations` вширь, гейтит кандидатов по `min_subscribers`,
  новые каналы пишет в общий реестр и в `join_queue` агента.
- Новый **источник `recommendations.ts`** поверх `TelegramService`: хоп
  discussion-группа → broadcast-канал (агент вступает в discussion-группы, а рекомендации
  требуют broadcast-канал), вызов `getChannelRecommendations`, гейт подписчиков через
  `getFullChannel` на кандидата.
- **Условия остановки** обхода агента: достижение целевого числа новых каналов `target`,
  либо пуш-бэк Telegram — **2 FLOOD_WAIT подряд → стоп обхода у агента** (FLOOD_WAIT
  отрабатывается ожиданием+ретраем, счётчик обнуляется после успешного вызова), либо
  естественное исчерпание графа. Жёсткая ошибка на узле → узел пропускается, в
  стоп-счётчик не идёт.
- **Назначение — finder-first-wins**: канал достаётся агенту, на чьём обходе найден
  первым; держится на существующем `canonical_link PRIMARY KEY` + `INSERT OR IGNORE`
  реестра. Пересечение каналов между агентами безвредно — второй получает `inserted=false`
  и канал пропускает. Round-robin (как в TGStat-версии) не используется.
- **Доставка** — `addJoinQueue(agent, [canonical])` в `join_queue` агента (`pending`);
  вступление инициирует существующий per-agent таймер `join-queue` (скрипт ничего не
  запускает, центр и агент развязаны).

Вне scope v1 (отложено): параллельный обход агентов, **гейт** по вовлечённости
(вовлечённость влияет только на порядок обхода seed, не на отбор), ограничитель глубины
обхода (лимит по числу каналов `target` — в scope), более тонкое распределение общих
находок между агентами, обход Premium-усечения, seeds из курируемого подмножества.

Примечание: ранее приоритизация по ER значилась как отложенная с обоснованием «нативного
ER в MTProto нет». Это неточно — просмотры постов broadcast-канала доступны напрямую
(`Api.Message.views` из истории), а число подписчиков уже собирается; готового ER-показателя
у Telegram нет, но сырьё для него дёшево. Поэтому приоритизация переведена в scope как
**порядок** обхода (не гейт).

### Доработка: роли `agents`/`target`, две фазы, темп

Заменяет в исходном поведении назначение finder-first-wins (D4) и стоп по `target` на
агента (D5):

- **`agents` — искатели (кто обходит), а не получатели.** Список задаёт оператор;
  используются их сессии и seed-каналы. (Раньше `agents` определял и обход, и закрепление.)
- **`target` — новых каналов на каждого агента платформы за прогон; общая цель = `target × N`**,
  N = `listAgentIds().length`. Цель общая и делится между искателями, а не умножается на их
  число. (Раньше каждый искатель набирал свой `target`.)
- **Две фазы (D10):** *сбор* — seed-каналы всех искателей сводятся в общий пул, ранжируются
  **глобально** по вовлечённости, затем BFS по уровням до `target × N` (ветка seed
  обходится на сессии её искателя); *распределение* — пул раскладывается round-robin по
  всем `N` агентам платформы, до `target` каждому (`registerChannel` + `addJoinQueue`).
- **Темп ускорен:** пауза между MTProto-вызовами снижается с 3–7 с до **0.8–1.2 с** (D9.1).
- Инвариант «один канал — один агент, навсегда» сохраняется (на `canonical_link` PK).

## Capabilities

### New Capabilities
- `similar-channel-discovery`: операторский обход графа похожих каналов через MTProto.
  Фаза сбора — seed-каналы искателей сводятся в общий пул, ранжируются глобально по
  вовлечённости за окно наблюдения, BFS по уровням с гейтом по подписчикам до общей цели
  `target × N`, стоп по 2 FLOOD_WAIT подряд у искателя. Фаза распределения — round-robin по
  всем агентам платформы (до `target` каждому) с закреплением в общий реестр и push в
  `join_queue`. Отчёт оператору.

## Impact

- **Новый код:** скилл `discovery-similar`, скрипт обхода (`src/scripts/`), обход и
  политика в `src/core/discovery/similar.ts`. Для приоритизации — новый метод
  `TelegramService` сбора просмотров постов за окно (история broadcast-канала; см. design.md D9).
- **Переиспользуется без изменений:** реестр `src/core/db/discovery.ts`
  (`registerChannel`/`isKnownChannel`/`normalizeChannelLink`), `addJoinQueue`,
  `TelegramService` (`getChannelRecommendations`, `getFullChannel`, `getDialogs`),
  `FUNNEL_ADMIN_AGENT_ID`, `listAgentIds`.
- **Хранилище:** новых БД нет — пишем в существующие `discovery.db` (реестр) и per-agent
  `join_queue.db`. Обход последовательный → писатель в реестр один, конкуренции нет.
- **Новый сбор seeds:** нужен способ получить **все каналы агента** (текущий `getDialogs`
  фильтрует по непрочитанным) — детали в design.md.
- **Внешние зависимости:** нет — источник нативный MTProto, без платного API.
- **Безопасность аккаунта:** обход на живой сессии агента → пейсинг (паузы, retry на
  FLOOD_WAIT) обязателен, как в `joinDiscussionGroups`.
- **Операционное:** на каждом агенте задача `join-queue` должна быть в расписании, иначе
  очередь копится без обработки.
