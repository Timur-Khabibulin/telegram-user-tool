## Context

Агент мониторит Telegram-группы по расписанию через скилл `telegram-group-monitor`. При каждом прогоне он читает непрочитанные сообщения, выбирает одно релевантное и отвечает на него. Ответ сохраняется в `tg-replies.db` (таблица `replies`: chatId, msgId, replyMsgId, replyText).

Проблема: когда пользователи отвечают на сообщение агента, эти ответы попадают в следующий батч непрочитанных, но агент не умеет их распознавать как часть диалога — не знает контекст и не продолжает цепочку.

Текущая структура данных не позволяет:
- Определить, что входящее сообщение является ответом именно на сообщение агента
- Восстановить цепочку предыдущих сообщений треда
- Управлять жизненным циклом диалога (активен / истёк)

## Goals / Non-Goals

**Goals:**
- Детектировать ответы на сообщения агента через поле `replyToMsgId` в входящих сообщениях
- Восстанавливать полный контекст треда для генерации релевантного ответа
- Поддерживать несколько пользователей в одном треде (один контекст)
- Помечать истекшими треды через 4 дня без активности
- Не нарушать существующий флоу обработки "обычных" сообщений

**Non-Goals:**
- Отдельный скилл или cron для thread-replies (всё в одном прогоне)
- Лимит глубины по количеству ответов (только по времени)
- Ветвление тредов — один ответ агента на все новые сообщения в треде за прогон

## Decisions

### D1: Всё в одном прогоне telegram-group-monitor (Вариант А)

**Решение:** расширить существующий скилл, не создавать отдельный.

**Альтернатива:** отдельный скилл `group-replies` на своём cron.

**Почему А:** `telegram_mark_as_read` вызывается сразу после получения сообщений (шаг 5.2) для идемпотентности. Отдельный скилл не увидит эти сообщения как unread — пришлось бы вводить промежуточную таблицу "pending replies", что сложнее. Вариант А избегает этой проблемы: данные получены, помечены прочитанными, обработаны — всё в одном проходе.

---

### D2: Две новые таблицы — group_threads + group_thread_agent_msgs

**Решение:**

```sql
-- Состояние треда + JSON-цепочка сообщений
group_threads (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    chatId         TEXT    NOT NULL,
    startMsgId     INTEGER NOT NULL,   -- msgId первого сообщения пользователя (T1)
    status         TEXT    NOT NULL DEFAULT 'active',  -- 'active' | 'expired'
    lastActivityAt INTEGER NOT NULL,
    messages       TEXT    NOT NULL    -- JSON: [{role, msgId, fromName?, fromId?, text}]
)

-- Индекс: agentMsgId → threadId (O(1) lookup)
group_thread_agent_msgs (
    agentMsgId  INTEGER NOT NULL,
    chatId      TEXT    NOT NULL,
    threadId    INTEGER NOT NULL REFERENCES group_threads(id),
    PRIMARY KEY (agentMsgId, chatId)
)
```

**Альтернатива:** рекурсивный обход `replies` таблицы (msgId → replyMsgId → msgId...).

**Почему отдельные таблицы:** рекурсия требует N SQL-запросов на глубину N; нет статуса треда; нет `lastActivityAt` для экспирации; нельзя найти "все активные треды" без полного скана. Отдельная таблица даёт O(1) lookup и простую логику в скилле.

---

### D3: Ленивое создание треда

**Решение:** тред создаётся только когда пользователь впервые отвечает агенту. До этого момента детекция идёт через `replies` таблицу (`WHERE replyMsgId = ?`).

**Почему:** большинство ответов агента не получают ответов от пользователей. Создавать тред заранее означало бы накапливать мёртвые записи. Ленивая инициализация минимизирует write-нагрузку.

---

### D4: JSON для цепочки сообщений в group_threads.messages

**Решение:** хранить всю цепочку как JSON-массив в одном поле.

**Альтернатива:** отдельная таблица `group_thread_messages` с одной строкой на сообщение.

**Почему JSON:** цепочка читается целиком при каждом обращении — нормализация не даёт выигрыша. JSON упрощает API инструментов (один объект вместо JOIN). При глубине треда ≤20 сообщений размер JSON незначителен.

---

### D5: replyToMsgId в telegram_get_messages

**Решение:** добавить необязательное поле `replyToMsgId?: number` в каждый элемент результата.

Из GramJS: `m.replyTo?.replyToMsgId` (тип `Api.MessageReplyHeader`).

Это единственный входной сигнал для детекции thread-replies в скилле.

---

### D6: Один ответ агента на несколько новых сообщений в треде

**Решение:** если за один прогон в треде появилось несколько новых сообщений (от одного или разных пользователей), агент генерирует один ответ, учитывая все новые сообщения в контексте.

**Почему:** отправка нескольких сообщений подряд выглядит как спам; один ответ на несколько реплик — естественная манера общения.

---

### D7: Экспирация по времени

**Решение:** при каждом прогоне, перед обработкой thread-replies, вызывать `tg_group_thread_expire` — помечает треды с `lastActivityAt < now - 4 дней` как `expired`. Expired-треды пропускаются.

**Почему 4 дня:** баланс между "диалог ещё актуален" и "человек уже забыл контекст".

## Risks / Trade-offs

- **JSON-цепочка растёт неограниченно** → При очень длинных диалогах JSON может стать большим. Митигация: экспирация по 4 дням естественно ограничивает глубину.
- **peerCache** требует вызова `telegram_get_dialogs` в начале прогона — уже есть в скилле через `tg_channels_sync`.
- **Конкурентность:** если два прогона запустятся одновременно (нестандартная ситуация), возможна двойная запись в тред. Митигация: OpenClaw запускает агентов последовательно по расписанию; риск минимален.
- **replyToMsgId из другого чата:** технически сообщение может быть ответом на сообщение из другого чата (пересланное). GramJS возвращает `replyTo.replyToMsgId` без chatId — нужно проверять только в контексте текущего `chatId` при запросе к `group_thread_agent_msgs`.
