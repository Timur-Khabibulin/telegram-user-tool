## Why

Прокси-гейт `ensureClient` ротирует прокси только при провале preflight-probe (пустой
MTProto-хендшейк). Деградировавший прокси, который проходит probe, но не проводит
авторизованный трафик, не ротируется никогда: probe зелёный → боевое подключение падает
каждый прогон → агент простаивает часами (наблюдение 29.09.2026 — несколько агентов не
работали весь день, десятки провалов подключения, ни одной ротации). Нужен второй триггер
ротации, реагирующий на реальный исход боевого подключения.

Обоснование, доменная модель и требования — `docs/design/proxy-failure-rotation/requirements-v1.md`
(R1–R14, AC-1…AC-13). Проектное решение — `docs/design/proxy-failure-rotation/architecture.md`.

## What Changes

- Вводится **второй триггер ротации прокси** в `ensureClient`, работающий на исходе
  боевого цикла (connect+`getMe`), в дополнение к существующему probe-триггеру.
- Ведётся **персистентный per-agent счётчик подряд идущих провалов связности**
  (`ConnectTimeoutError`): +1 на провальный прогон (весь прогон = +1, не за попытку),
  сброс в 0 при успешном подключении и в момент ротации. Провалы уровня аккаунта
  (бан/отзыв сессии) счётчик не трогают.
- При достижении **порога** (дефолт 2 прогона, конфигурируется через env) прокси
  ротируется **инлайн в том же прогоне**: перебор до **5 кандидатов** asocks, каждый
  проверяется **боевым подключением** (`connect`+`getMe`), а не пустым probe; первый
  прошедший становится текущим прокси, подключение продолжается.
- Счётчик хранится в новой таблице `proxy_health` (per-agent `tasks.db`), с колонкой
  `proxy_key` (host:port) для самолечения при смене прокси вне триггера.
- Счётчик ведут плановые процессы — диспетчер и funnel-tracker (через явный опт-ин);
  долгоживущий gateway, персистентные слушатели (review-listener), ops-скрипты и
  override-подключения его не трогают.
- Существующий probe-триггер и его подбор (10 кандидатов, probe-verify) **не меняются** —
  корректируется только формулировка одного сценария, чтобы не противоречить новому
  триггеру.

## Capabilities

### New Capabilities
- `proxy-failure-rotation`: подсчёт подряд идущих провалов боевого подключения per-agent
  и инлайн-ротация прокси с боевой верификацией кандидата при достижении порога.

### Modified Capabilities
- `guaranteed-proxy-on-connect`: сценарий «probe прошёл, но боевой connect не удался →
  система НЕ запускает подбор, прогон завершается ошибкой» ограничивается по области — он
  остаётся верным для probe-триггера и для одиночного провального прогона, но накопление
  подряд идущих провалов теперь обрабатывает новая способность `proxy-failure-rotation`.

## Impact

- **Код**: `src/core/telegram/service.ts` (`ensureClient` — врезки инкремента/сброса/
  ротации; `verifyConnection` — боевой verify-коллбэк); `src/features/proxy/provision-via-probe.ts`
  (переиспользование `provisionProxyViaProbe` с боевым коллбэком и `maxCandidates=5`,
  verify-агностичные лог-строки); `src/core/config.ts` (`PROXY_FAILURE_ROTATION_THRESHOLD`,
  `PROXY_ROTATION_MAX_CANDIDATES`); новый `src/core/db/proxy-health.ts` (таблица в `tasks.db`);
  `src/scripts/dispatcher.ts` и `src/scripts/periodic/funnel-tracker.ts` — включение
  контекста счётчика (ops-скрипты и персистентные слушатели его не включают).
- **Данные**: новая таблица `proxy_health` в per-agent `tasks.db` (создаётся на шаге
  инициализации диспетчера). Существующие БД и `tg-account.json` по схеме не меняются
  (запись прокси при ротации — прежним `saveProxyToAccountConfig`).
- **Смежные способности**: `mobile-proxy-provisioning` — переиспользуется механизм отбора
  из инвентаря asocks без изменения его требований (меняется только verify-коллбэк и число
  кандидатов на стороне вызывающего). `telegram-connection-errors` — классификация
  `ConnectTimeoutError` vs провал аккаунта используется как есть.
- **Обратимость**: поведение по умолчанию включается для плановых процессов; порог
  конфигурируется через env, при 0/отключении новый триггер не срабатывает.
