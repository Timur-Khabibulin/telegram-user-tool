## Context

Полное проектное решение с заземлением в коде — `docs/design/proxy-failure-rotation/architecture.md`
(§1–§10), требования — `docs/design/proxy-failure-rotation/requirements-v1.md`. Здесь —
сжатый нормативный слой: ключевые решения и их обоснование, без дублирования.

Текущее состояние: `ensureClient` (`src/core/telegram/service.ts`) ротирует прокси только
при провале preflight-probe (`provisionProxyViaProbe`, 10 кандидатов, probe-verify).
Боевой цикл (`connect`+`getMe`, ниже probe-gate) на исчерпании бросает
`ConnectTimeoutError` без ротации. Прокси, проходящий probe и не проводящий боевой трафик,
не ротируется никогда.

## Goals / Non-Goals

**Goals:**
- Второй триггер ротации, реагирующий на исход боевого подключения, при сохранении
  probe-триггера без изменений.
- Персистентный per-agent счётчик подряд идущих провалов связности; ротация с боевой
  верификацией кандидата при достижении порога.
- Восстановление деградировавшего прокси существенно быстрее суток, без участия оператора.

**Non-Goals:**
- Изменение probe-триггера и его подбора (10 кандидатов, probe-verify) — остаётся как есть.
- Изменение требований способности `mobile-proxy-provisioning` — переиспользуется механизм
  отбора, меняется только verify-коллбэк и число кандидатов на стороне вызывающего.
- Отдельный журнал ротаций / таблица истории — исход прогона уже в `runs`/`error_log`.
- Реакция на провал уровня аккаунта — остаётся за механизмом ограничения агента.

## Decisions

- **Точка триггера — врезки в боевой цикл `ensureClient`** (инкремент в точке
  `throw ConnectTimeoutError` после `classifyAccountError`; сброс при успехе `getMe`;
  probe-gate не трогается). Альтернатива — отдельный слой поверх `ensureClient` —
  отклонена: единая точка подключения уже здесь, дублировать нельзя.
- **Боевой verify кандидата — переиспользование `verifyConnection(override)`** как
  коллбэка `provisionProxyViaProbe` (override идёт мимо probe-gate прямо в connect+getMe,
  контракт `(proxy)=>Promise<void>` совпадает). Альтернатива — отдельная
  `provisionProxyViaLiveConnect` — отклонена: дублирует цикл отбора кандидатов против
  «один факт — один дом». Лог-строки отбора делаются verify-агностичными.
- **Хранилище счётчика — таблица `proxy_health` в per-agent `tasks.db`, с колонкой
  `proxy_key` (host:port)**. Альтернатива — поле в `tg-account.json` — отклонена:
  конфиг не дом для часто меняющегося состояния, риск затирания при `saveProxyToAccountConfig`.
  `proxy_key` даёт самолечение при смене прокси вне триггера (probe-подбор, reauth, ручной
  swap): при инкременте несовпадение сохранённого `proxy_key` с текущим стартует счёт с 1.
- **Порог — конфигурируемая константа в `config.ts` с env-override, дефолт 2 прогона**
  (≈5–8 ч при кадансе monitor-v5 2.5–4 ч). Порог 1 отклонён (ротация на транзиентном
  сбое), 4 требования называют недопустимым. Число кандидатов — отдельная константа
  `PROXY_ROTATION_MAX_CANDIDATES=5`, не совпадает с порогом.
- **Область счётчика — плановые/полуплановые процессы (диспетчер, ops-скрипты,
  funnel-tracker) через явный опт-ин контекста прогона**; gateway и override исключены.
  Свёртка «один процесс = ±1» — однократная за процесс отметка на экземпляре сервиса.

## Risks / Trade-offs

- **Стоимость боевого verify: победитель платит один лишний connect+getMe** (проверка +
  финальный рабочий клиент) → ротация редкая (раз в порог провальных прогонов), не каждый
  прогон; adopt-клиента из verify-ветки отклонили в пользу простоты.
- **Имя `provisionProxyViaProbe` при боевом verify вводит в заблуждение** → нейтрализуем
  формулировки лога, файл не переименовываем (probe-триггер использует ту же функцию).
- **Массово деградировавший инвентарь asocks** → при исчерпании 5 кандидатов прогон падает
  штатно (R12), счётчик 0; это проблема поставки прокси, не алгоритма, вариантом B не
  лечится и не должна.
- **Разный каданс процессов (funnel-tracker vs monitor)** → `proxy_key` держит счётчик
  корректным «на текущем прокси» независимо от того, какой процесс его тронул.

## Migration Plan

- Схема `proxy_health` создаётся идемпотентно (`CREATE TABLE IF NOT EXISTS`) на шаге
  инициализации диспетчера — миграция существующих БД не нужна, отсутствие таблицы =
  счётчик 0.
- Откат: отключение через env (порог 0 / выключенный флаг контекста) возвращает прежнее
  поведение без удаления таблицы; probe-триггер работает независимо.
