## Context

`monitor` (`src/skills/monitor.ts`, capability `group-monitoring`) обходит чаты обсуждения по фиксированному периоду (`CHANNEL_CHECK_PERIOD_SECONDS`, 72 часа), классифицирует непрочитанные сообщения (`classifyMessages` → `generalMessages`/`newThreadMessages`/`threadReplies`), выбирает не более одного сообщения для ответа через LLM и скорит DM-кандидатов — без какой-либо проверки, к какому посту канала и когда вышедшему относится сообщение.

Полный анализ проблемы, доменная модель Telegram (канал / чат обсуждения / пост / служебная копия поста / ветка комментариев) и согласованный с координатором алгоритм — в `docs/design/post-freshness-gate/requirements-v1.md` (бизнес-требования, подтверждено) и `docs/design/post-freshness-gate/architecture.md` (техническое решение, подтверждено). Этот design.md — конспект для реализации; при расхождении в деталях источником истины остаются эти два документа.

Ограничение, зафиксированное координатором и не подлежащее пересмотру: решение аддитивное. `monitor.ts` не меняется ни строкой; новая логика живёт в отдельном скилле `monitor-v2`, включаемом по агенту независимо от старого (через уже существующий механизм таблицы `tasks`).

## Goals / Non-Goals

**Goals:**
- Гейтить первый (инициирующий) комментарий агента по свежести поста (< 24 часов с момента публикации).
- Гейтить продолжение уже начатого диалога по возрасту поста (≤ 4 дней от даты публикации, якорь — дата поста, не дата последней активности).
- Полностью исключать из анализа (ни кандидат на ответ, ни кандидат на DM) сообщения вне этих границ, до какого-либо LLM-вызова.
- Не менять поведение пометки прочитанным — выполняется независимо от исхода гейта.
- Дать возможность выбирать вариант мониторинга (v1/v2) на уровне агента, без программной защиты от одновременного включения обоих (осознанное решение координатора — ответственность оператора).

**Non-Goals:**
- Не переделывать и не удалять `monitor.ts` (v1) — она продолжает работать как есть.
- Не решать очистку «мёртвых» каналов по порогам аудитории (`channel-cleanup` — отдельная задача).
- Не вводить отдельный параметр LLM-вызова «это сообщение — пост» для `analyzeChannelMessages` — обсуждалось с координатором, отложено, не входит в эту фичу.
- Не менять расчёт `activityRate` воронки под период `monitor-v2` — согласованная координатором несопоставимость метрики, не блокер.

## Decisions

**Гейт применяется после `classifyMessages`, а не до.** `classifyMessages` вызывается без изменений на полном списке непрочитанных; гейт свежести — отдельный проход по трём готовым бакетам (`generalMessages` → правило первого комментария, `newThreadMessages`/`threadReplies` → правило продолжения), отбрасывающий непрошедшие сообщения. Альтернатива (определять ветку/дату для всех сообщений до классификации) даёт экономию лишь в несколько дешёвых локальных SQLite-запросов на заведомо отсеиваемые сообщения — не стоит усложнения. LLM-вызовов на исключённых сообщениях не будет в любом случае: это гарантирует применение гейта до `analyzeChannelMessages`/`generateThreadReply`.

**Служебная копия поста участвует в анализе, не отбрасывается.** v1 (`TelegramService.getMessages`) сегодня фильтрует сообщения от отправителя-канала как шум — это поведение возникло до этой фичи и не для неё. Координатор подтвердил явно: копия поста — тоже сообщение, она не исключается автоматически; она сама себе корень ветки, а дата берётся из её собственного поля `date` без запроса к Telegram и без кеша. `getMessages` получает новый опциональный параметр `opts?: { includeChannelPosts?: boolean }` (default `false` — v1 не меняется); `monitor-v2` вызывает его с `true`. Копия автоматически попадает в бакет `generalMessages` существующей `classifyMessages` (у неё никогда нет `replyToMsgId`) — правка самой функции классификации не требуется, только аддитивные поля `replyToTopId?`/`isChannelPost?` на входных сообщениях.

**Дата поста ветки — через `replyToTopId` + локальный кеш на 30 дней.** `reply_to_top_id` заполняется Telegram для всех сообщений ветки на любой глубине вложенности (подтверждено официальной документацией) — отдельного запасного пути через `getDiscussionMessage`/канал не нужно. При первой встрече с веткой — один запрос `getMessageById(chatId, replyToTopId)`, результат сохраняется в новую таблицу `thread_post_dates` (`tg-replies.db`) на 30 дней (существенно больше 4-дневного окна правила продолжения — запись остаётся доступной весь срок, пока ветка вообще может быть актуальна, TTL — гигиена объёма, не механизм корректности). При неудаче запроса (сеть, `FLOOD_WAIT`, ветка недоступна) — сообщение исключается по общей стратегии обработки ошибок проекта (не валит канал/прогон).

**R1 и R2 — оба скользящее окно от даты поста, без часового пояса.** Первое (инициирующее) сообщение — `now - postDate < 24 часов` (строгое неравенство); продолжение — `now - postDate ≤ 4 дня` (нестрогое). Симметричная форма исключает зависимость от календарного «дня»/часового пояса.

**Отдельная периодичность обхода для v2.** Новая константа `MONITOR_V2_CHECK_PERIOD_SECONDS = 86400` (24ч), независимая от `CHANNEL_CHECK_PERIOD_SECONDS` (72ч) — последнюю продолжают использовать v1 и расчёт `activityRate` воронки без изменений.

**Выбор варианта на агента — существующий механизм `tasks`, без новой сущности.** `TaskType` расширяется значением `"monitor-v2"`; таблица `tasks` уже поддерживает произвольный набор включённых типов задач на агента (PK `agentId, type`) — оператор включает одну из строк `monitor`/`monitor-v2`. `SKILLS: Record<TaskType, ...>` в диспетчере типизированно требует зарегистрировать `runMonitorV2`.

**Обработка одного батча — последовательно, не параллельно.** Если в одном непрочитанном батче несколько сообщений одной новой (ещё не закешированной) ветки, гейт должен применяться последовательно (`for...of` + `await`, как уже устроены циклы `monitor.ts`) — иначе первый запрос к Telegram за датой ветки задублируется для каждого сообщения этой ветки в том же прогоне.

## Risks / Trade-offs

- **Всплеск точечных запросов `getMessageById` в первые дни после включения `monitor-v2`** (много новых веток одновременно) → ожидаемо и дёшево благодаря кешу на 30 дней; при системном `FLOOD_WAIT` — исключается только конкретное сообщение, канал/прогон не валится.
- **`channels.lastProcessedAt` — общее состояние, не различает вариант монитора** → при одновременном включении `monitor` и `monitor-v2` одному агенту оба варианта сбивают друг другу каденс обхода (последний прогон неважно какого варианта сбрасывает таймер для обоих). Координатор явно решил не защищать от этого в коде — ответственность оператора (не включать оба варианта одному агенту одновременно).
- **`activityRate` воронки использует глобальный 72-часовой знаменатель, а `monitor-v2` физически посещает каналы раз в 24ч** → метрика для агентов на v2 будет систематически занижена. Согласовано координатором как не блокер, коррекция под per-agent период не делается.
- **Допущение «`reply_to_top_id` присутствует у всех сообщений ветки на любой глубине» подтверждено документацией, но не проверено эмпирически на реальном трафике** → если для части сообщений поле не заполнено, такое сообщение ошибочно попадёт под «нет привязки к ветке» вместо корректной оценки правила первого комментария — отказ консервативный (недосчитанный кандидат, не утечка непрошедшего сообщения в LLM), но снижает охват. Митигация: логировать долю таких исключений в метриках гейта прогона для проверки допущения на практике.

## Migration Plan

Полностью аддитивно, миграции данных не требуется:
1. Добавить новые поля/методы `TelegramService`, новую таблицу `thread_post_dates`, новые константы `config.ts`.
2. Добавить `src/core/freshness-gate.ts`.
3. Добавить `src/skills/monitor-v2.ts`, зарегистрировать `"monitor-v2"` в `TaskType` и в `SKILLS` диспетчера.
4. Обновить `skills/scheduler-control/SKILL.md` (документация новой строки типа задачи для оператора).
5. Включение — по агенту, вручную через пульт (`upsertTask` с `type: "monitor-v2"`); откат — `disableTask`/не создавать строку `monitor-v2`, `monitor` при этом не затрагивается.

## Open Questions

- Отдельный параметр LLM-вызова «это сообщение — пост» (чтобы `analyzeChannelMessages` мог явно отличать копию поста от обычного комментария в самом промпте) — обсуждался с координатором, отложен, не входит в эту фичу. `isChannelPost` уже вычислен на уровне данных и может быть передан в промпт без новых Telegram-полей, когда это будет решено отдельно.
