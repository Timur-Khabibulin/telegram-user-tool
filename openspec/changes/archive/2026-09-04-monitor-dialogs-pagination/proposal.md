## Why

`TelegramService.getDialogs()` (`src/core/telegram/service.ts`) запрашивает у Telegram
только окно первых N диалогов (`limit: 200`). Telegram сортирует диалоги по дате
последнего сообщения в чате, а не по числу непрочитанных — поэтому канал, в котором
давно копится непрочитанное, но в который никто не писал в последнее время, со
временем вытесняется за пределы окна другими, более "живыми" чатами. Монитор
(`src/skills/monitor.ts`) при этом помечает такой канал `outcome: "empty"`, хотя
реально не проверял его — карта непрочитанных просто не содержит этот `chatId`.
Это искажает метрики активности (funnel-tracking) и оставляет такие каналы
фактически необслуженными в `tg_channels` графике обхода.

Простое увеличение лимита (100 → 200) снижает частоту проблемы, но не устраняет её:
у агентов с большим количеством каналов окно всё равно конечно. Нужен метод,
дающий достоверный ответ "есть непрочитанное / нет / Telegram не ответил" для
каждого канала из батча монитора, а не только для тех, что попали в первое окно.

## What Changes

- В `TelegramService` добавляется способ получить статус непрочитанности для
  конкретного набора `chatId` (батча монитора), дозапрашивая страницы `getDialogs`
  (пагинация: `offsetId`/`offsetDate`/`offsetPeer` или `iterDialogs`), пока каждый
  `chatId` не встретится в ответе Telegram (с любым `unreadCount`, не только `> 0`),
  либо диалоги не закончатся (пустая страница).
- Вводится явный потолок на число дозапрошенных страниц/диалогов за один прогон
  монитора — защита от вырожденного случая (агент с очень большим числом каналов,
  батч которых не пересекается с первыми страницами) и от риска `FLOOD_WAIT`.
- `peerCache` продолжает заполняться для всех встреченных диалогов на каждой
  странице — без этого `mark_as_read`/`reply` для таких чатов не сработают.
- `monitor.ts` использует новый способ вместо текущего одноразового `getDialogs()`
  для определения, какие каналы из батча реально проверены и пусты, а какие не
  определены (Telegram не ответил даже после исчерпания диалогов или достижения
  потолка страниц) — для последних `outcome` не помечается как "empty" без
  оснований (см. design.md за точное решение по этому случаю).

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `group-monitoring`: способ определения статуса непрочитанности канала из батча
  монитора меняется с "поиск в одном окне `getDialogs(limit)`" на "дозапрос страниц
  до подтверждённого статуса каждого канала батча или исчерпания диалогов/потолка
  страниц". Затрагивает то, как формируется `outcome: "empty"` для каналов,
  не входивших в первое окно.

## Impact

- `src/core/telegram/service.ts` — `getDialogs()` (новый параметр/режим с целевыми
  `chatId` и пагинацией) либо новый метод рядом с ним.
- `src/skills/monitor.ts` — использование нового способа вместо текущего вызова
  `getDialogs()` без аргументов.
- Не затрагивает: `getChannelsBatch` (источник батча из БД), `getDmDialogs()` и
  `listDialogChannels()` (другие потребители того же типа окна, другая зона
  ответственности — не входят в этот change), семантику `active`/`error`.
