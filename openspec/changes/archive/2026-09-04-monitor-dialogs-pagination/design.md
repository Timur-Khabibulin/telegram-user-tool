## Context

`TelegramService.getDialogs()` (`src/core/telegram/service.ts`) — единственный
способ монитора (`src/skills/monitor.ts`) узнать, в каких каналах есть непрочитанные
сообщения. Сейчас это один вызов `client.getDialogs({ limit: 200 })`: GramJS вызывает
`messages.GetDialogs`, который сортирует диалоги по дате последнего сообщения в
диалоге (top message date), не по числу непрочитанных. Из ответа фильтруются группы и
каналы, и среди них — только те, у кого `unreadCount > 0`, в карту
`chatId → readInboxMaxId`. Канал, не вошедший в это окно, монитор считает пустым
(`outcome: "empty"`), хотя его реальный статус не проверялся.

Батч монитора (`getChannelsBatch`, `src/core/db/channels.ts`) отдаёт до 40 каналов
по графику (`lastProcessedAt`), независимо от их позиции в диалогах Telegram. У
агентов, чьё число каналов превышает окно `getDialogs`, часть батча систематически
не пересекается с окном — это и есть искажение, которое чинит этот change.

GramJS даёт пагинацию через `client.iterDialogs({ offsetId, offsetDate, offsetPeer,
limit })` (`node_modules/telegram/client/dialogs.js`) — на каждой итерации продвигает
offset по последнему диалогу страницы. Это стандартный механизм библиотеки, его и
используем вместо ручной пагинации через повторные `getDialogs`.

## Goals / Non-Goals

**Goals:**
- Для каждого `chatId` из батча монитора получить достоверный статус: "есть
  непрочитанное" (с `readInboxMaxId`), "подтверждённо пусто" (диалог встречен,
  `unreadCount = 0`), или "не определено" (Telegram не дал ответа по этому каналу
  даже после исчерпания диалогов или достижения потолка страниц).
- Не увеличивать число MTProto-запросов в типичном случае (когда весь батч
  покрывается первой страницей).
- Сохранить заполнение `peerCache` для всех встреченных по пути диалогов (нужно
  `mark_as_read`/`reply`), как сейчас.
- Явный, настраиваемый потолок на объём дозапросов за один прогон монитора.

**Non-Goals:**
- Полная пагинация "забрать все диалоги агента" — only до покрытия батча или потолка,
  не больше.
- Изменение `getChannelsBatch`, периода обхода, лимита батча (40).
- Изменение `getDmDialogs()` и `listDialogChannels()` — у них то же ограничение
  окна, но другая зона ответственности (dm-replies, channel-discovery-similar),
  правятся отдельными change при необходимости.
- Изменение семантики `outcome: "active"`/`"error"` — меняется только то, как
  обосновывается `outcome: "empty"`.

## Decisions

### Решение 1: новый метод `getDialogsForBatch(chatIds)` вместо изменения сигнатуры `getDialogs()`

`getDialogs()` остаётся как есть (используется только монитором сейчас, но это
публичный метод сервиса с понятной текущей семантикой "одна страница"). Добавляется
новый метод `getDialogsForBatch(chatIds: string[]): Promise<{ found: Map<chatId,
{ readInboxMaxId, unreadCount }>; exhausted: boolean }>`, который инкапсулирует цикл
пагинации и возвращает статус для каждого запрошенного `chatId`.

Альтернатива (отклонена): параметризовать `getDialogs()` опциональным `targetChatIds`.
Отклонена, потому что меняет контракт существующего метода ради одного вызывающего
(монитора) — новый метод яснее по назначению и не ломает остальных потребителей.

### Решение 2: пагинация через `client.iterDialogs`, а не повторные `client.getDialogs`

`iterDialogs` уже инкапсулирует продвижение `offsetId`/`offsetDate`/`offsetPeer` между
страницами (GramJS, `client/dialogs.js`). Ручная пагинация через повторные вызовы
`getDialogs` с самостоятельным расчётом offset — дублирование уже существующей
библиотечной логики, без выгоды.

### Решение 3: критерий остановки — "покрыт весь батч" ИЛИ "диалоги закончились" ИЛИ "достигнут потолок страниц"

Цикл идёт по страницам `iterDialogs` (размер страницы — переиспользуем текущий
`limit: 200` как размер одной страницы пагинации, не общий потолок). На каждой странице:
- для каждого встреченного диалога (группа/канал) — заполняется `peerCache`
  (как сейчас в `getDialogs`) и помечается найденным с его реальным `unreadCount`;
- если все `chatIds` батча найдены — остановка, успех;
- если страница пришла короче своего `limit` — диалоги Telegram закончились,
  остановка (оставшиеся непокрытые `chatId` → статус "не определено");
- если число обработанных страниц достигло потолка (см. Решение 4) — остановка
  (оставшиеся непокрытые → "не определено").

### Решение 4: потолок страниц — константа, не конфиг

`MAX_DIALOG_PAGES` (например, 5 страниц × 200 = 1000 диалогов за прогон) — захардкоженная
константа рядом с методом, не вынесена в конфигурацию агента. Обоснование: это защита
от вырожденного случая (деградация на агентах с экстремально большим числом каналов),
а не штатный параметр тюнинга по агенту — конфигурируемость здесь не нужна (принцип
простоты, agent-playbook.md). Если на практике понадобится тюнинг — заводить отдельно,
когда появится конкретный кейс.

### Решение 5: непокрытые ("не определено") каналы — не помечаются `outcome: "empty"`

В `monitor.ts` канал из батча без подтверждённого статуса (не найден, и пагинация
остановилась по исчерпанию/потолку) обрабатывается так же, как сейчас обрабатывается
ошибка `getMessages` — пропускается с `outcome: "error"` (а не "empty"), не запутывая
метрики активности ложным "пусто". Технически это не ошибка Telegram, а неполное
покрытие, но для целей funnel-tracking важнее не путать "точно пусто" с "не проверено";
`"error"` — ближайший существующий статус с этим смыслом (альтернатива — заводить
четвёртый `outcome`, отклонена как избыточная сложность для одного редкого случая;
при необходимости различать их позже — отдельный change).

## Risks / Trade-offs

- **[Риск]** Рост числа MTProto-запросов и риск `FLOOD_WAIT` на агентах с очень
  большим количеством каналов и батчем, плохо пересекающимся с первыми страницами.
  → **Mitigation**: потолок страниц (Решение 4) + существующий `withFloodRetry` в
  `monitor.ts` оборачивает обращения к Telegram уже сейчас; дозапросы внутри
  `getDialogsForBatch` тоже должны идти через тот же механизм повтора при FLOOD_WAIT.
- **[Риск]** Время прогона монитора увеличивается на агентах, где батч обычно не
  покрывается первой страницей (уже сегодняшняя реальность для агентов с >200
  каналами) → метрики "вовремя" по периоду обхода (72ч) могут начать плыть сильнее.
  → **Mitigation**: это сознательный трейдофф ради точности; если станет проблемой —
  отдельный change на тюнинг периода/батча, не блокирует эту доработку.
- **[Trade-off]** "Не определено" коротко замыкается на `outcome: "error"`, теряя
  различимость с реальными ошибками Telegram в отчётах (`Проблемные каналы` в
  funnel-report). Признано приемлемым — оба случая одинаково требуют внимания
  (канал не обслужен в этом прогоне).

## Migration Plan

Прямое изменение поведения внутри `TelegramService`/`monitor.ts`, без изменений схемы
БД и без флагов совместимости. Деплой — обычным циклом (`scp` файла, `chown root`,
`openclaw gateway restart`), как заведено в `docs/operation.md`. Откат — вернуть
предыдущую версию `service.ts`/`monitor.ts` тем же циклом; данных, требующих
обратной миграции, изменение не создаёт.
