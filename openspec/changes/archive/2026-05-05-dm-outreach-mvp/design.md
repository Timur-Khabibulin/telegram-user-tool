## Context

Агент мониторинга Telegram-групп работает на платформе OpenClaw через три независимых крона. Всё в одном процессе — GramJS-клиент один на все три крона, сессия shared. БД — SQLite через `better-sqlite3`, путь `~/.openclaw/workspace-<agentId>/tg-channels.db`.

Ключевое ограничение из CLAUDE.md: нельзя использовать `client.getEntity(BigInt(...))` для восстановления пиров — in-memory кэш GramJS не переживает перезапуск. `access_hash` должен сохраняться в SQLite и передаваться явно при конструировании `InputPeerUser`.

## Goals / Non-Goals

**Goals:**
- Собирать кандидатов для DM из групповых чатов (Cron 1, доработка)
- Ежедневно отправлять DM топ-кандидатам (Cron 2)
- Обрабатывать входящие DM и вести диалог до 2 обменов (Cron 3)
- Не получать банов: лимит 15 DM/день, пауза 30–60с, cooldown 7 дней

**Non-Goals:**
- Диалог длиннее 2 обменов
- Автоматическое отслеживание подписки
- Аналитика и дашборды
- Ручная модерация очереди

## Decisions

### D-1. access_hash хранится в обеих таблицах, не в памяти

**Решение:** `userAccessHash` сохраняется в `dm_candidates` при записи кандидата и копируется в `dm_history` при отправке DM. Оба крона конструируют `InputPeerUser` явно из БД.

**Альтернативы:**
- `client.getEntity(userId)` — отклонено: зависит от in-memory кэша GramJS, который умирает при рестарте процесса → `PEER_ID_INVALID`
- Отдельный `userPeerCache` Map — отклонено: не переживает рестарт, и между кронами его было бы нужно шарить отдельно

### D-2. Дневной лимит — через dm_history, не in-process счётчик

**Решение:** `dm_history_count_today(agentId)` → `COUNT(*) WHERE sentAt > полночь UTC сегодня`. Скилл SKILL_DM_SEND проверяет лимит перед стартом петли. Инструмент `telegram_send_dm` лимит не проверяет сам.

**Альтернатива:** In-process счётчик — отклонено: сбрасывается при рестарте процесса, что делает ограничение ненадёжным.

### D-3. Курсор по lastAgentMsgAt для чтения DM

**Решение:** `telegram_get_dm_replies` принимает `lastAgentMsgAt` и возвращает только сообщения от пользователя с `date > lastAgentMsgAt`. После каждого ответа агента `lastAgentMsgAt` обновляется в `dm_history`.

**Следствие:** идемпотентность — каждый запуск Cron 3 видит только новые сообщения, без дублей.

### D-4. Таблицы в той же БД (tg-channels.db)

**Решение:** `dm_candidates` и `dm_history` создаются в существующей БД агента. Инструменты в `channels-db.ts` (паттерн уже есть).

**Альтернатива:** отдельная БД — отклонено: усложняет инициализацию без видимых преимуществ для MVP.

### D-5. min-entity фильтрация при записи кандидата

**Решение:** в маппинге `telegram_get_messages` добавляем `userAccessHash` только когда `m.sender instanceof Api.User && m.sender.accessHash != null && !m.sender.min`. Если `min === true` — поле отсутствует, кандидат записывается без `userAccessHash` и не попадёт в топ Cron 2 (инструмент `telegram_send_dm` не сможет построить `InputPeerUser`).

## Risks / Trade-offs

| Риск | Митигация |
|---|---|
| Бан за спам | Лимит 15 DM/день, пауза 30–60с, cooldown 7 дней |
| `USER_PRIVACY_RESTRICTED` у большинства | Считать % `privacy_blocked`; если > 50% — фича нерентабельна |
| min-entity → нет access_hash | Пропускаем таких кандидатов при отправке DM; потери небольшие |
| Очередь растёт быстрее расхода | `expire_old` ежедневно чистит `pending` старше 3 дней |
| Агент зависает в диалоге | Жёсткая логика по `replyCount` и `status`; таймаут 48ч → `done` |

## Migration Plan

1. Деплой плагина с новыми инструментами — обратно совместим, существующие инструменты не меняются (кроме добавления поля `userAccessHash` в ответ `telegram_get_messages`)
2. Таблицы создаются лениво через `dm_candidates_init` и `dm_history_init` при первом запуске скиллов
3. Откат: отключить Cron 2 и Cron 3; Cron 1 продолжит работать в прежнем режиме (запись в `dm_candidates` безвредна)

## Open Questions

- Нужна ли отдельная команда `dm_candidates_init` / `dm_history_init`, или таблицы создаются внутри первых же операций (`INSERT OR IGNORE` с предварительным `CREATE TABLE IF NOT EXISTS`)? Рекомендуется: CREATE TABLE IF NOT EXISTS внутри каждого write-инструмента, чтобы не требовать отдельного шага инициализации.
