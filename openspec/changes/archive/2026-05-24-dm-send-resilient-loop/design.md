## Context

Скилл `dm-send` отправляет DM кандидатам из очереди `dm_candidates`. Текущий алгоритм делает LLM-выборку топ 10–15 кандидатов с учётом diversity (≤3 из одного чата). Проблема: если у нескольких выбранных кандидатов устаревший `accessHash`, весь пул исчерпывается с нулём отправок. `peer_id_invalid` — не признак плохого лида, а признак протухшего хэша; валидность хэша неизвестна заранее.

## Goals / Non-Goals

**Goals:**
- Цикл продолжается при `peer_id_invalid` — кандидат помечается `skipped`, следующий берётся из всей очереди
- Убрать зависимость от LLM-выборки; сортировка по `score DESC` достаточна
- Добавить лимит `sentThisRun ≤ 2` — контроль частоты на уровне прогона
- Сохранить дневной лимит `sentToday ≤ 15` и `floodErrors`-защиту

**Non-Goals:**
- Diversity-ограничение по `sourceChatId`
- Изменение инструментов `telegram_send_dm`, `dm_candidates_get_pending`

## Decisions

### Решение 1: Убрать LLM-шаг выборки

**Выбрано:** алгоритмическая сортировка (`score DESC`) без LLM.

**Альтернативы:**
- Оставить LLM-шаг с `limit: ALL` — избыточно, дорого, непредсказуемо на большом пуле.
- Алгоритм с diversity-счётчиком — от diversity решили отказаться для простоты.

**Ратионал:** LLM-шаг добавлял непредсказуемость и стоимость без существенного выигрыша при наличии `score`.

### Решение 2: Счётчик sentThisRun

**Выбрано:** in-memory счётчик, сбрасывается каждый прогон, максимум 2.

**Ратионал:** позволяет запускать скилл несколько раз в день (например, по cron), не исчерпывая дневной лимит за один запуск. `sentToday` из `dm_history_count_today` по-прежнему защищает суточный потолок.

### Решение 3: peer_id_invalid → skipped, продолжить

**Выбрано:** помечать кандидата `skipped`, переходить к следующему без паузы.

**Ратионал:** `peer_id_invalid` возвращается мгновенно (нет смысла ждать 30–60с). Кандидат с протухшим хэшем не является флуд-угрозой. Статус `skipped` корректен — повторная попытка не имеет смысла, если хэш не обновится.

### Решение 4: Пауза только при успешной отправке

Пауза 30–60с выполняется только в шаге 5d после `ok: true`. Все ошибочные пути (`peer_id_invalid`, `privacy_blocked`, `deactivated`, `flood_wait`) переходят к следующему кандидату без паузы.

## Risks / Trade-offs

- [Длинный цикл при большом числе invalid-кандидатов] → ограничен `sentThisRun=2`: при достижении лимита цикл останавливается, время прогона предсказуемо.
- [LLM-вызов на генерацию DM (5a) тратится впустую при peer_id_invalid] → стоимость одного вызова мала; pre-validation невозможна без попытки отправки.
- [Без diversity кандидаты из одного чата могут идти подряд] → принято как допустимое упрощение.
