## Context

Полный технический разбор — в
[docs/design/channel-write-access/architecture.md](../../../docs/design/channel-write-access/architecture.md)
(схема потока, `WriteAccessSnapshot`, payload события, интеграция с кодом). Здесь —
только ключевые решения, альтернативы и риски уровня change.

Текущий код реализует реактивную модель: `channels.write_access_reason` заполняется из
статуса участника или кода ошибки отправки; постоянные причины удерживают канал
read-only, переменные ведут в ротацию. Требования переписаны на проактивную модель
«статус → действие» (requirements-v1.md). Change идёт поверх ветки `refactoring-2`,
рядом с незаархивированными `tg-peer-identity-model` и `monitor-v5-hash-driven-sync`.

## Goals / Non-Goals

**Goals:**
- Определять препятствия к записи из статусов канала/участника перед отправкой; по
  каждому — однозначное действие (авторотация / suspend / вступление / заявка).
- Журналировать каждый обнаруженный статус в `channel-operations` (ИО).
- Нулевой прирост служебного трафика: переиспользовать единственный `GetParticipant`,
  который precheck monitor-v5 уже делает.

**Non-Goals:**
- Не менять механизмы исполнения (leave-banned → rotation, suspend-таймер, join-очередь)
  — только комбинировать и журналировать их.
- Не мигрировать схему `channels` (колонки `write_access_reason`/`write_access_until`
  остаются мёртвыми до отдельной чистки).
- Не трогать медиа-специфичные `CHAT_SEND_*_FORBIDDEN` и DM-поток.

## Decisions

- **Действие вместо причины; отказ от колонки-гейта.** `classifyWriteAccess(snapshot)`
  возвращает действие; «писать нельзя» выражается через `status` (`banned`/`suspend`) +
  журнал. *Альтернатива* — сохранить `write_access_reason` как признак — отклонена:
  плодит второй дом факта поверх `status`/`membership`, не нужный при однозначном
  действии.
- **Устранение read-only.** Канальные препятствия (`restricted`, `default_banned_rights`,
  `paid`) → `suspend(∞)`, а не read-only. *Альтернатива* (сохранить read-only ради
  сбора DM) отклонена владельцем: канал `paid`/закрытый комментариями ценности для DM
  не несёт, а read-only требует отдельного гейт-признака.
- **Новый тип события `write_access` в журнале**, а не перегрузка `status_change`.
  Причина: покрывает `join_to_send` (не меняет `status`) и несёт рич-payload (R4), не
  ломая аналитику банов/ротации, читающую `status_change`.
- **Асимметрия источников (R2).** Статус участника и флаги группы — живьём из одного
  `GetParticipant`; access-флаги broadcast — из кэша при join. *Альтернатива* (живой
  `GetFullChannel` на обоих объектах) отклонена: удвоение трафика ради редкого события
  (broadcast стал `restricted` между полными проходами) — ловится реактивным резервом.
- **`CHANNEL_PRIVATE` при чтении → авторотация** (не `not_found`). Потеря доступа =
  повод передать канал другому аккаунту (R7). Единая точка — ветка monitor-v5 5.1.

## Risks / Trade-offs

- **[Слияние ветки `CHANNEL_PRIVATE` с `monitor-v5-hash-driven-sync`]** → согласовать
  при реализации: право записи имеет приоритет (`CHANNEL_PRIVATE` со свежим хэшем →
  `banned`/авторотация, а не `not_found`); объединить в одной ветке 5.1.
- **[Задержка обнаружения broadcast-`restricted`]** (кэш, не живьём) → подстраховано
  реактивным резервом при отказе отправки.
- **[slowmode-suspend низкой ценности при cadence 72ч]** → временный suspend с фикс.
  дефолтом длительности, без доп. `GetFullChannel`; при желании можно опереться только
  на существующий `retryOnFloodWait`.
- **[Потеря read-only режима]** → осознанный выбор владельца: `paid`/`restricted`/
  «все замьючены» больше не читаются; если позже понадобится сбор DM с таких каналов —
  отдельный change.

## Migration Plan

- Схема БД не мигрируется. Колонки `write_access_reason`/`write_access_until` перестают
  писаться (мёртвые); чтение их снимается вместе с `setWriteAccessReason`/
  `clearWriteAccessReason`.
- Роллбэк: обратим на уровне кода (revert). Мёртвые колонки данных не теряют.
- Согласование с `tg-peer-identity-model`: dual-write `membership` идёт через
  `markChannelStatus` — новый писатель не вводится.
