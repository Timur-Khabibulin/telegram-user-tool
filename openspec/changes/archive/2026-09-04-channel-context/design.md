## Context

`channels` (per-agent `tg-channels.db`) хранит только служебное состояние обхода
каналов (`lastProcessedAt`, `status`, идентичность привязанного broadcast-канала).
Смысл содержания канала — о чём он, для кого, что заходит у аудитории — нигде не
собирается и не хранится. Ближайшая существующая фича, `channel-content-analysis`,
делает похожий сбор (посты + LLM-анализ), но она on-demand, оценивает топ m% каналов
по размеру, и результат — разовый CSV-отчёт оператору, не персистентное состояние
канала. Она не подходит как основа: нужен другой набор входных данных (about, закреп,
комментарии — не только посты), другая гранулярность результата (один текст на канал,
не на пост) и другое назначение (персистентный факт о канале, читаемый кодом, а не
разовая выгрузка человеку).

Идентичность привязанного broadcast-канала (`channelId`/`channelAccessHash`/
`channelUsername`) уже кэшируется в `channels` фичей `channel-content-analysis`
(`cacheChannelIdentities`, вызывается на синхронизации в мониторах) — эта способность
её только читает, не резолвит заново.

`avg_views`/`subs_count` уже существуют в `channels` — их завела `channel-coverage-report`
(кэш с TTL 30 дней, обновляется отдельным месячным скриптом `channel-coverage-update.ts`).
Формула `avg_views` уже вынесена в переиспользуемую функцию `computeAvgViews()` в
`core/telegram/service.ts`.

## Goals / Non-Goals

**Goals:**
- Регулярно (раз в 90 дней на канал) собирать about, закреп, посты за 90 дней (≤100 шт)
  и комментарии к ним, одним LLM-вызовом получать компактный JSON-профиль канала
  (позиционирование, автор, аудитория, коммуникационный код, отличительные черты,
  устойчивые мотивы, триггеры вовлечения, слабые для комментирования типы постов,
  контекст для будущих постов, изменения во времени, качество данных — фиксированная
  схема, см. D6) и сохранять его сериализованным (`JSON.stringify`) в
  `channels.channel_context` (колонка остаётся `TEXT` — новой колонки под структуру не
  заводим).
- Тем же прогоном пересчитывать `avg_views`/`subs_count` (общий кэш с существующей
  `channel-coverage-report`), не заводя для них вторых, дублирующих колонок.
- Дать два входа с общей логикой отбора и обработки: периодическая задача диспетчера
  (батч 20, период 8ч, без фильтра по статусу канала) и ручной OpenClaw-тул (батч
  параметризован оператором: `agents` + `count`).
- Устойчивость к сбоям: ошибка на одном канале или одном агенте не должна прерывать
  обработку остальных.

**Non-Goals:**
- Использование `channel_context` в промпте monitor-v4 — только сбор и хранение,
  подключение к решению о комментарии — отдельный будущий change.
- Изменение `channel-coverage-report`/`channel-coverage-update.ts` — их TTL-цикл
  (30 дней, колонка `coverage_updated_at`) не трогается и не заменяется.
- Изменение `channel-content-analysis` — способности не объединяются, у каждой свой
  триггер, свой набор каналов и свой результат.
- Отдельная структурная колонка/таблица под поля профиля — `channel_context` остаётся
  единственной колонкой (`TEXT`), хранящей сериализованный JSON целиком; выборочный
  доступ к отдельным полям (например, только `качество_данных`) средствами SQL не
  предоставляется — при необходимости читающий код десериализует JSON сам.

## Decisions

### D1. Отдельная новая способность, не расширение `channel-content-analysis`
Обоснование в Context. Альтернатива (добавить в `channel-content-analysis` персистентность
и about/закреп/комментарии) отвергнута: у неё другой триггер (on-demand vs периодика),
другой охват каналов (топ m% vs все резолвленные) и другая гранулярность (пост vs канал) —
совмещение усложнило бы обе способности ради поверхностного сходства («обе смотрят на
посты канала»).

### D2. Отбор каналов: переиспользовать резолвленную идентичность, без фильтра по статусу
Источник — те же каналы, что отдаёт `getAnalysisChannels` (`channelResolved=1 AND
channelId IS NOT NULL`) — резолв уже сделан на синхронизации мониторов, повторный резолв
не нужен. В отличие от `getPostWatchChannels` (используется в monitor-v3/v4), `status`
(`banned`/`suspend`) **не фильтруется** — оператор явно решил анализировать содержание
канала независимо от того, может ли агент в нём сейчас писать: `channel_context` описывает
канал как источник контента, а не как канал для активности агента.

Отбор в батч: `channel_context_updated_at IS NULL OR <= now - 90d`, `ORDER BY
channel_context_updated_at ASC` (NULL — первыми через `COALESCE`/`IS NULL DESC` в SQL —
никогда не анализированные каналы имеют приоритет над устаревшими), `LIMIT N`.

### D3. `avg_views`/`subs_count` — общий кэш с `channel-coverage-report`, `coverage_updated_at` не трогаем
Значения делят смысл и должны делить хранилище («один факт — один дом»): эта способность
пишет в существующие `avg_views`/`subs_count`, используя уже существующие
`getChannelSubsCount()` и `computeAvgViews()` — не заводит собственных колонок-дублей.
`coverage_updated_at` остаётся в исключительном ведении `channel-coverage-update.ts` —
явное решение оператора не расширять blast radius на чужую фичу. Следствие (см. Risks):
после прогона `avg_views` может быть свежее, чем показывает `coverage_updated_at`
— принятая асимметрия, не баг.

### D4. Посты за 90 дней ≤100 — фильтрация в core-модуле, без изменения сигнатуры `getRecentPosts`
`getRecentPosts(channel, n)` уже отдаёт до `n` последних постов за один вызов
(`client.getMessages(peer, { limit: n })`); при `n=100` это одновременно и предел
количества, и достаточная выборка для отсечки по дате. Отбор постов «не более 100 за
последние 90 дней» реализуется как `getRecentPosts(channel, 100)` + фильтр по
`date >= now - 90d` в core-модуле новой способности — без нового метода и без изменения
существующих вызывающих (`channel-content-analysis`, `channel-niche.ts`), которые
продолжают получать «последние n» без даты. Альтернатива (научить `getRecentPosts`
принимать `sinceDate`) отвергнута — усложнила бы сигнатуру ради одного вызывающего.

### D5. Закреплённый пост — расширение `getChannelGateInfo` + новый метод чтения текста по id
`getChannelGateInfo()` уже делает один `GetFullChannel` и возвращает `subscribers`/
`linkedChatId`/`about` — `fullChat.pinnedMsgId` достаётся из того же ответа без
дополнительного вызова, добавляется как ещё одно поле (`pinnedMsgId: number | null`,
аддитивно, существующие вызывающие поле игнорируют). Текст самого закреплённого
сообщения — новый метод по образцу `getMessageById` (сейчас отдаёт только `{ date }`),
принимает `chatId`/`msgId`, отдаёт `{ text }` (или null, если сообщения нет — удалено/
недоступно). Разделение на два вызова (get info, потом текст по id), а не один
комбинированный метод — переиспользует уже существующий примитив «сообщение по id»
вместо третьей полу-дублирующей реализации внутри `getChannelGateInfo`.

### D6. Один LLM-вызов на канал, структурированный JSON-профиль без персоны в system-промпте
Все собранные данные (title, about, закреп отдельным блоком, посты + их комментарии)
уходят в один вызов `llm.completeObject()` с фиксированной zod-схемой
(`channelContextSchema` в `core/channel-context/run.ts`) — не `complete()`, результат
проверяется/типизируется на структуру. System-промпт персону агента не использует — по
аналогии с решением monitor-v4-comment-signal для `generatePostCommentV4` (профиль
канала должен быть нейтральным анализом контента, а не окрашен характером конкретного
агента, который лишь наблюдатель, не участник этого анализа).

Промпт (`analyzeChannelContext`) прошёл через две версии по ходу ревью оператором:
v1 — свободный размеченный текст без схемы (13 секций, явная оценка уверенности
каждого вывода отдельно); v2 (действующая) — компактный JSON-профиль с меньшим числом
полей, ориентированный не на «полный обзор канала», а только на устойчивые,
отличительные признаки, которые *действительно стоит переносить* на оценку будущих
постов (позиционирование, автор, аудитория, коммуникационный код, отличительные черты
[3-5], контентные паттерны, устойчивые мотивы с уровнем поддержки на мотив [сильная/
умеренная/слабая], триггеры вовлечения, слабые для комментирования типы постов,
контекст для будущих постов [3-7 фактов], изменения во времени [nullable], и единая
общая оценка качества исходных данных [высокое/среднее/низкое] — не по-секционно, как
в v1). Результат `JSON.stringify`-ится и пишется как есть в `channels.channel_context`
(`TEXT`) — без изменения модели данных (см. Non-Goals).

Переход v1→v2 — реальная смена формата действующих данных, не только промпта: уже
проанализированные каналы (несколько сотен на момент перехода) хранят `channel_context`
в виде свободного текста v1, новые/повторные прогоны после деплоя v2 будут писать JSON.
До естественного обновления (TTL 90 дней) в `channels.channel_context` платформы будут
сосуществовать оба формата — читающий код (будущая интеграция с monitor-v4, вне скоупа
этого change) должен либо игнорировать несовместимые с `JSON.parse` значения, либо
явление снимается принудительным сбросом `channel_context_updated_at` затронутых строк
(операционный шаг, не часть кода этого change).

### D10. Логирование LLM-вызовов — `withLlmLogging`, общая для диспетчера и OpenClaw-плагина
Промпт тяжёлый (about + закреп + до 100 постов с комментариями на канал) — полезно
видеть фактический запрос/ответ при отладке (в т. ч. риск упереться в контекстное окно,
см. Risks). Логирование пишется в тот же `llm_log` (`core/db/llm-log.ts`), что уже
использует `monitor-v3`/`monitor-v4` (monitor-v3-post-comment-scoring), под
`skillType = "channel-context"`. Обёртка `withLlmLogging` вынесена из `dispatcher.ts` в
`core/db/llm-log.ts` и переиспользуется в обоих входах (диспетчер — периодическая
задача; `index.ts` — ручной тул `tg_channel_context_run`, по агенту внутри цикла), а не
дублируется — раньше обёртка жила только в `dispatcher.ts` и не была нужна
OpenClaw-плагину, т. к. логирование там ни для одного тула ранее не подключалось.

### D7. Общее ядро в `core/channel-context/run.ts`, два тонких входа
Экспортирует функцию, принимающую `agentId`, `limit` (20 у диспетчера, `count` у ручного
тула) и зависимости (`tg`, `llm`, `log`) — по образцу `core/channel-analysis/run.ts`.
- **Периодическая задача** (`skills/channel-context.ts`): новый тип задачи диспетчера,
  период 8ч (запись в `DEFAULT_PERIODIC_SCHEDULE`, `tasks.ts`, и таблицу в
  `task-scheduling.md`), `limit=20`, вызывается с `agentId` из `SkillContext`.
- **Ручной тул** (`index.ts`, по образцу `tg_channel_content_analysis`): параметры
  `agents: string[]`, `count: number`; последовательно по агентам (своя MTProto-сессия
  на агента, отключение между ними) вызывает то же ядро с `limit=count`.

Оба входа отбирают каналы одной и той же функцией (D2) — различие только в источнике
`agentId`/`limit`, не в логике отбора или обработки.

### D8. Обработка FLOOD_WAIT — свой локальный flood-aware враппер в core-модуле, не импорт из `skills/util.ts`
`skills/util.ts` (`withFloodRetry`/`FloodAbortError`) технически переиспользуем (не
зависит от `SkillContext`, только от `{ warn }`), но `core/` в этом проекте
принципиально не зависит от `skills/` (архитектура: скиллы зависят от ядра, не наоборот;
существующие core-модули вроде `channel-analysis/run.ts` и скрипт `channel-niche.ts`
уже решают эту же задачу локальным `makeFloodAware`, а не импортом из `skills/`).
Новый core-модуль заводит собственный локальный flood-aware враппер по этому же
образцу (2 FLOOD_WAIT подряд → остановка обработки текущего агента, с записью причины
в статистику прогона), сохраняя направление зависимостей.

### D9. Изоляция сбоев — по образцу `channel-analysis/run.ts`
`try/catch` вокруг обработки каждого канала (сбой → запись в список пропущенных с
причиной, переход к следующему) и вокруг каждого агента (сбой агента не прерывает
остальных агентов батча/списка). Прогон завершается сводкой: сколько каналов
обработано, сколько пропущено и почему.

## Risks / Trade-offs

- **Рассинхрон `avg_views` и `coverage_updated_at`** (см. D3) → `channel-coverage-report`
  может показывать значение как «устаревшее по таймстампу», хотя оно уже свежее.
  Митигация: не требуется — известный и принятый побочный эффект, не влияющий на
  корректность (`avg_views` при этом всегда актуальнее или равно тому, что предполагает
  `coverage_updated_at`, никогда не хуже).
- **Размер LLM-промпта для активных каналов** — до 100 постов, у каждого — ВСЕ его
  комментарии без верхнего предела (`getPostComments` намеренно не ограничивает
  количество, design.md monitor-v4-comment-signal, Decision 2). У канала с активной
  дискуссией под каждым постом это может дать очень большой промпт (стоимость токенов,
  риск упереться в контекстное окно модели). Явно вынесено в Open Questions — не
  митигируется в этом change без отдельного решения оператора.
- **Нагрузка на MTProto-сессию агента** — на канал уходит до 100 `getPostComments` +
  1 `getRecentPosts` + 1 `getChannelGateInfo` + 1 запрос текста закрепа + 1
  `getChannelSubsCount`; на батч из 20 каналов это может быть заметное число вызовов за
  один прогон. Митигация: те же приёмы пейсинга/флуд-обработки, что уже используются в
  `channel-analysis/run.ts`/`channel-niche.ts` (пауза между вызовами, локальный
  flood-aware враппер, D8).
- **Рост числа периодических типов задач** — `task-scheduling.md` уже фиксирует открытую
  модель ёмкости диспетчера (раздел «Модель ресурсов и ёмкости», незавершённая). Новый
  тип задачи добавляет нагрузку без пересчёта модели под новый тип — известный
  предсуществующий пробел проекта, не решается этим change.

## Migration Plan

- Аддитивная миграция `channels`: `channel_context TEXT`, `channel_context_updated_at
  INTEGER` — по образцу `migrateStatusColumns`/`migratePostWatchColumns` (`PRAGMA
  table_info` + `ALTER TABLE ... ADD COLUMN`, выполняется при `initChannels`).
  Существующие строки получают `NULL` → естественно попадают в первый батч отбора (D2).
- Новый тип задачи регистрируется в `DEFAULT_PERIODIC_SCHEDULE` (`tasks.ts`, период 8ч) —
  существующие агенты получают задачу тем же механизмом бутстрапа расписания, что и
  остальные периодические типы (без ручных миграций по агентам).
- Откат: тип задачи можно выключить через существующий механизм `enabled=0` в `tasks`
  (per-agent или платформенно), либо просто перестать вызывать; колонки `channels`
  можно оставить (данные не мешают, аддитивная миграция необратима так же, как и у
  остальных колонок `channels`).

## Open Questions

- Нужен ли верхний предел на число/объём комментариев, уходящих в один LLM-вызов на
  пост (см. Risks) — сейчас `getPostComments` не ограничивает количество, и явного
  решения оператора по потолку для этой способности не было.
- Итоговое число `N=20` в батче диспетчера и период 8ч выбраны оператором без расчёта
  под конкретный типичный размер `channels` на агента — если на практике 90-дневное
  окно не успевает покрыть все каналы агента (агентов с сотнями каналов), потребуется
  пересмотр без данных из прод-эксплуатации.
