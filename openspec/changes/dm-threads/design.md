## Context

Агент ведёт DM-переписку с пользователями из Telegram-групп через два скилла: `dm-send` (инициация) и `dm-replies` (обработка ответов). Текущая модель данных (`dm_history`) хранит только первое сообщение агента и метаданные (`replyCount`, `status`), что приводит к потере контекста в многоходовых диалогах. Проверка ответов реализована через poll-модель: на каждом прогоне `dm-replies` перебирает все активные записи и вызывает `telegram_get_dm_replies` для каждой — O(N) API-вызовов.

Инструменты плагина (`telegram_send_dm`, `telegram_get_messages`, `telegram_mark_as_read`) остаются без изменений. Добавляется один Telegram-инструмент и полностью заменяется набор DB-инструментов.

## Goals / Non-Goals

**Goals:**
- Хранить полную цепочку переписки (sliding window 50 сообщений) для контекстных ответов LLM
- Перейти на push-модель проверки ответов: `telegram_get_dm_dialogs` → фильтр по `dm_threads` — O(1) API-вызовов вместо O(N)
- Убрать искусственный лимит в 2 ответа — тред живёт пока есть активность
- Увеличить cooldown с 7 до 14 дней, привязать к `lastActivityAt` вместо `sentAt`
- Автоматически обновлять `accessHash` и `userName` из свежих peer-данных при каждом прогоне `dm-replies`

**Non-Goals:**
- Миграция данных из `dm_history` в `dm_threads` — начинаем с чистого листа
- Изменение `telegram_send_dm`, `telegram_get_messages`, `telegram_mark_as_read`
- Изменение `dm_candidates_*` инструментов
- Изменение алгоритма скилла `group-monitoring`
- Аналитика/отчётность по DM-диалогам

## Decisions

### Решение 1: Одна таблица dm_threads с JSON-полем messages

**Выбрано:** таблица `dm_threads` с колонкой `messages TEXT` (JSON-массив объектов `{role, msgId, text, sentAt}`), UNIQUE по `userId`.

**Альтернативы:**
- Отдельная таблица `dm_messages` с FK на `dm_threads` — нормализация, но избыточная для SQLite; при чтении всё равно нужен весь массив целиком для LLM-контекста.
- Хранение messages в отдельном файле — усложняет атомарность обновлений.

**Ратионал:** JSON-in-SQLite — стандартный паттерн для структур с фиксированным окном. Sliding window 50 записей гарантирует ограниченный размер. При cooldown 14 дней и частоте 2-3 обмена в день реалистичный максимум — 20-30 сообщений.

### Решение 2: Push-модель через telegram_get_dm_dialogs

**Выбрано:** новый инструмент `telegram_get_dm_dialogs` возвращает список личных чатов с `unreadCount > 0`, затем `dm_threads_get_by_users` фильтрует по совпадению с тредами.

**Альтернативы:**
- Polling каждого треда через `telegram_get_messages` — текущая модель, O(N) API-вызовов.
- Webhook/update handler — требует MTProto long-polling, несовместимо с cron-моделью OpenClaw.

**Ратионал:** один вызов `GetDialogs` с фильтром по `InputPeerUser` вместо N вызовов `GetHistory`. Масштабируется без роста API-нагрузки.

### Решение 3: dm_threads_get_by_users обновляет accessHash/userName

**Выбрано:** инструмент принимает актуальные peer-данные из `telegram_get_dm_dialogs` и в одной транзакции обновляет `userAccessHash`/`userName`, затем возвращает треды.

**Альтернативы:**
- Отдельный инструмент `dm_threads_update_peer` — лишний шаг в алгоритме скилла.
- Обновление при отправке (`telegram_send_dm`) — не решает проблему протухших хэшей до отправки.

**Ратионал:** accessHash протухает при перезапуске процесса (GramJS in-memory кэш). Обновление при каждом прогоне `dm-replies` гарантирует актуальность перед отправкой ответа. Атомарность транзакции исключает race condition.

### Решение 4: Cooldown 14 дней по lastActivityAt с удалением треда

**Выбрано:** `dm_threads_exists` проверяет наличие треда и считает дни с `lastActivityAt`. При `cooldownActive: false` (>14 дней) — `dm_threads_delete` удаляет тред, создаётся новый с чистым контекстом.

**Альтернативы:**
- Soft-delete с полем `archivedAt` — усложняет запросы, данные старого диалога не нужны для нового.
- Обнуление `messages` без удаления — нарушает UNIQUE constraint при создании нового треда.

**Ратионал:** физическое удаление проще и чище. Старый контекст бесполезен для нового диалога — новый `triggerMessage` берётся из свежего сообщения в группе.

### Решение 5: Sentiment analysis как отдельный LLM-шаг в dm-replies

**Выбрано:** перед генерацией ответа — отдельный LLM-запрос для оценки тональности последнего сообщения (`positive` / `negative`). При `negative` — `mark_as_read`, пропуск (тред сохраняется, cooldown работает).

**Ратионал:** отдельный запрос с простым JSON-ответом дешевле и предсказуемее, чем объединение с генерацией ответа (где модель может "забыть" проверить тональность).

### Решение 6: mark_as_read последним в dm-replies

**Выбрано:** `telegram_mark_as_read` вызывается после всех шагов обработки (отправка ответа + обновление треда), а не сразу после чтения.

**Альтернативы:**
- mark_as_read сразу после get_messages (паттерн из group-monitoring) — если агент упадёт между чтением и ответом, сообщение пользователя потеряется.

**Ратионал:** в `dm-replies` каждое сообщение требует индивидуального ответа. Потеря сообщения пользователя критичнее, чем повторная обработка. В `group-monitoring` наоборот — идемпотентность важнее, потому что агент обрабатывает массовый поток.

## Risks / Trade-offs

- [Sliding window 50 обрезает старые сообщения] → `triggerMessage` хранится в отдельном поле и никогда не теряется. Для LLM-контекста 50 последних сообщений более чем достаточно.

- [Потеря DM-сообщения при сбое между send и update_msgs] → Сообщение доставлено пользователю (Telegram подтвердил). На следующем прогоне `telegram_get_dm_dialogs` покажет unread от пользователя, агент ответит заново. Дубль ответа предпочтительнее молчания.

- [telegram_get_dm_dialogs возвращает DM от незнакомых пользователей] → `dm_threads_get_by_users` вернёт `notFound` для userId без тредов — они просто игнорируются. Тред создаётся только через `dm-send`.

- [Протухший accessHash при отправке ответа в dm-replies] → `dm_threads_get_by_users` обновляет accessHash из свежих peer-данных `telegram_get_dm_dialogs`. Если ошибка всё же произошла — `peer_id_invalid` → mark_as_read, следующий прогон обновит хэш.

- [Удаление dm_history_* и telegram_get_dm_replies — breaking change] → Одновременный деплой новых и удаление старых инструментов. Существующие диалоги в `dm_history` считаются завершёнными, миграция не требуется.
