# Private Invite Links — персональные ссылки в приватный канал

Три режима одного инструмента `tg_private_invite_links` — создание, повтор зависших
вставок, проверка соответствия. Реестр ссылок (`private-invites.db` у
`FUNNEL_ADMIN_AGENT_ID`, таблица `private_invite_links`) хранит поле `post_updated`:
`0` — ссылка создана, но не подтверждена вставленной в пост; `1` — подтверждено.

---

## Режим 1 — Создать ссылки (обычный)

Этот режим создаёт по одной инвайт-ссылке в приватный канал для **каждого агента из
списка, который укажет пользователь** — список не выводится автоматически, его нужно
явно спросить или взять из запроса. Ссылка требует подтверждения заявки на вступление
(request-to-join), не имеет лимита по времени и числу использований, не требует платной
подписки, и называется в Telegram так же, как `agentId` агента.

```
tg_private_invite_links({ agentIds: ["agent4", "agent7"] })
```

Инструмент выполняет две последовательные операции:
1. От имени `REPORT_AGENT_ID` (администратор приватного канала) создаёт по ссылке на
   каждый `agentId` из списка, сохраняет в реестр ссылок (`post_updated=0`).
2. От имени каждого агента из списка — редактирует его собственный закреплённый пост:
   убирает старые строки-ссылки (если были) и дописывает новую ссылку тремя строками в
   конец текста. Остальной текст поста не меняется. При успехе — `post_updated=1`.

Список `agentIds` **обязателен** в этом режиме — скилл не берёт «все агенты» сам, только
те, что явно запрошены. Повторный вызов для уже обработанного агента **перезаписывает**
его ссылку в реестре и в посте (не создаёт вторую) и сбрасывает `post_updated` в 0.

## Режим 2 — Повторить вставку для зависших (retryPendingOnly)

Используй, когда часть ссылок создалась, но не вставилась в пост (например, упал
таймаут подключения агента) — обычно видно по прошлому вызову режима 1, где
`insertSkipped` не пуст. `agentIds` не нужен и не передаётся.

```
tg_private_invite_links({ retryPendingOnly: true })
```

Берёт всех агентов с `post_updated=0` из реестра сам, **не создаёт новых ссылок** —
только повторяет вставку в пост уже существующей ссылкой из БД. При успехе выставляет
`post_updated=1`.

## Режим 3 — Проверить соответствие (verifyOnly)

Используй для контроля: убедиться, что ссылка в реестре реально совпадает с тем, что
стоит в закреплённом посте агента (пост мог быть отредактирован вручную или другим
процессом). Ничего не создаёт и не редактирует.

```
tg_private_invite_links({ verifyOnly: true })
tg_private_invite_links({ verifyOnly: true, agentIds: ["agent28", "agent31"] })
```

Без `agentIds` проверяет всех агентов реестра; со списком — только их. Для каждого
читает реальный текст поста и сравнивает со ссылкой в БД, возвращает `matched`/
`mismatched`/`verifyErrors`.

---

## Показать результат пользователю

Во всех трёх режимах отдать `text` из результата как есть — там уже посчитана сводка
(создано/вставлено/совпадает/расхождение/ошибки, в зависимости от режима) и по каждому
пропуску/расхождению/ошибке отдельная строка с причиной. Частичная неудача — не ошибка
всего вызова, агенты обрабатываются независимо; сообщи пользователю, для кого не
получилось и почему (обычно: нет личного канала/поста, сессия агента недоступна, либо
`connect timed out` — временная проблема, а не окончательный отказ).

---

## Ограничения и заметки

- `retryPendingOnly` и `verifyOnly` нельзя передавать одновременно — вызов завершится
  ошибкой.
- Правка поста (режимы 1 и 2) переносит только текст — форматирование (жирный,
  ссылки-превью и т. п.), если оно было, не сохраняется.
- `REPORT_AGENT_ID` должен оставаться администратором приватного канала с правом
  создавать инвайт-ссылки — если прав нет, шаг создания ссылок (режим 1) завершится
  ошибкой для всех агентов сразу (это видно в `createErrors`). Режимы 2 и 3 создание
  ссылок не выполняют, этого ограничения не касаются.
