# Private Invite Links — персональные ссылки в приватный канал

Три режима — создание, повтор зависших вставок, проверка соответствия. Реестр ссылок
(`private-invites.db` у `FUNNEL_ADMIN_AGENT_ID`, таблица `private_invite_links`) хранит
поле `post_updated`: `0` — ссылка создана, но не подтверждена вставленной в пост;
`1` — подтверждено.

Прогон идёт последовательно по агентам (подключение к сессии каждого через прокси +
правка поста) и на большом списке пробивает per-tool-call таймаут runtime агента
(~90 s), убивающий синхронный вызов тула на середине. Поэтому запускаем ops-скрипт
**отсоединённым фоновым процессом** через `systemd-run` — возврат мгновенный, прогон
живёт в своём юните, отчёт приходит в Saved Messages получателя отчётов.

---

## Шаг 1 — Определить режим и список агентов

- **Обычный** (создать+вставить) — спросить у оператора **agentIds** (обязателен, не
  берётся «все агенты» сам; например `agent4, agent7`).
- **retryPendingOnly** — повторить вставку для агентов с `post_updated=0` (ссылка
  создана, но не вставилась, например из-за таймаута подключения). `agentIds` не нужен.
- **verifyOnly** — проверить соответствие ссылки в реестре реальному посту, ничего не
  меняя. Без `agentIds` — все агенты реестра, со списком — только они.

`retryPendingOnly` и `verifyOnly` вместе задавать нельзя.

---

## Шаг 2 — Запустить прогон (в фоне, detached)

Выполнить на ВПС (cwd плагина), флагами по выбранному режиму:

```
systemd-run \
  --unit="tg-invite-links-$(date +%s)" \
  --property=Type=oneshot \
  --property=WorkingDirectory=/root/openclaw-plugins/telegram-user-tool \
  --property=EnvironmentFile=-/root/.openclaw/secrets.env \
  --collect \
  /root/openclaw-plugins/telegram-user-tool/node_modules/.bin/tsx \
    src/scripts/ops/private-invite-links.ts \
    <ФЛАГИ РЕЖИМА>
```

Флаги по режиму:
- Обычный: `--agent-ids agent4,agent7`
- Повтор: `--retry-pending-only`
- Проверка: `--verify-only` (опционально `--agent-ids agent4,agent7`)

Обычный режим: скрипт от имени `REPORT_AGENT_ID` создаёт по ссылке на каждый агент
(request-to-join, без лимитов, название = `agentId`), сохраняет в реестр
(`post_updated=0`), затем от имени каждого агента дописывает ссылку тремя строками в
хвост его закреплённого поста (существующие строки-ссылки заменяются, остальной текст
не трогается); при успехе `post_updated=1`. Сбой одного агента не останавливает
остальных.

---

## Шаг 3 — Подтвердить запуск

`systemd-run` возвращает управление сразу — прогон уже идёт в фоне. Сообщить
оператору, что прогон запущен, и что **итоговый отчёт придёт в Saved Messages
получателя отчётов** (`REPORT_AGENT_ID`) по завершении — тот же адресат, что у
ежедневной сводки. Синхронно ждать результат в чате не нужно.

Отчёт содержит сводку по режиму (создано/вставлено — для обычного и повтора;
совпадает/расхождение/ошибка — для проверки) и построчные причины пропусков,
расхождений и ошибок.

Ход прогона до отчёта можно смотреть в journal его юнита:
`journalctl -u tg-invite-links-<...> -f` (имя юнита — из вывода `systemd-run`).

---

## Ограничения и заметки

- Правка поста (обычный режим и повтор) переносит только текст — форматирование
  (жирный, ссылки-превью и т. п.), если оно было, не сохраняется.
- `REPORT_AGENT_ID` должен оставаться администратором приватного канала с правом
  создавать инвайт-ссылки — если прав нет, шаг создания ссылок (обычный режим)
  завершится ошибкой для всех агентов сразу. Повтор и проверка создание ссылок не
  выполняют, этого ограничения не касаются.
- Приватные ссылки этот скилл создаёт после того, как публичные каналы уже созданы
  (`tg-agent-channel-setup`).
