# Scheduler Control — пульт управления расписанием

Этот скилл управляет **расписанием** задач агента, а не выполняет их. Сами задачи
выполняет standalone-диспетчер (`dispatcher.ts`), который systemd-таймер будит по
расписанию. Пульт лишь правит строки в таблице `tasks` агента и включает/выключает
его heartbeat-таймер — через инструменты `tg_scheduler_*`.

> Это новая модель вместо `openclaw cron add` / `CronCreate`. Cron-задачи больше
> не создаём — расписание хранится в БД агента.

За один запуск скилла пользователь просит **одно** действие. Алгоритм: получить от
пользователя agentId и тип задачи → понять, какое именно действие просят → выполнить
**только его** → сообщить итог.

---

## Шаг 2 — Получить agentId и тип задачи от пользователя

### 2.1 — Показать список типов и получить agentId

Вывести пользователю список управляемых типов задач:

| type | что делает |
|---|---|
| `monitor` | мониторинг групп: читает непрочитанные, ведёт треды, отвечает, отбирает DM-кандидатов |
| `monitor-v2` | то же самое, плюс гейт свежести поста (первый комментарий — пост младше 24ч; продолжение диалога — не старше 4 дней от поста); независимая версия, не совмещать с `monitor` на одном агенте |
| `monitor-v3` | комментирует последний пост публичного канала через веб-превью, если он младше 24ч (гейт свежести от текущего момента); независимая версия |
| `monitor-v4` | то же назначение, что `monitor-v3`, но комментирует последний пост фиксированного, уже закрытого календарного дня — «позавчера» (не скользящее окно свежести); общие поля статуса канала с `monitor-v3` — не совмещать с ним на одном агенте |
| `monitor-v5` | читает весь чат обсуждения, как `monitor` (v1) — общие сообщения, диалоговые ветки, DM-кандидаты — но решение по общим сообщениям принимает через селективный промпт `monitor-v4`; проверки постов канала не делает вовсе; общий `status`/`lastProcessedAt` с `monitor` — не совмещать с ним на одном агенте |
| `dm-send` | ежедневная отправка DM топ-кандидатам из групп |
| `dm-replies` | ответы на входящие личные сообщения (продолжение тредов) |
| `account-warmup` | прогрев аккаунта: читает случайные чаты и один раз отвечает |
| `join-queue` | обработка очереди вступления в группы обсуждений (конечная задача) |
| `leave-banned` | выход из каналов с `CHAT_WRITE_FORBIDDEN`, удаление их данных и пометка в реестре |

### 2.2 — Получить выбор пользователя (обязательный шаг)

**Обязательный шаг: нельзя переходить к Шагу 3, пока не получены `agentId` и `type`.**

- Если в исходном запросе пользователь уже однозначно назвал `agentId`, задачу и
  действие (напр. «останови dm-send у agent-42») — считать это выбором и идти к 2.3.
- Иначе — **СТОП.** Показать список из 2.1, спросить `agentId`, с какой задачей и что
  сделать, и **ждать ответа**. Не вызывать никаких инструментов до получения ответа.
- Исключение: действие «показать расписание/статус» не требует выбора типа задачи, но
  `agentId` нужен и для него — можно сразу к Шагу 3-D, как только известен `agentId`.

### 2.3 — Определить действие и параметры

Из выбора пользователя определить **ровно одно** действие и извлечь параметры:

- **`type`** задачи — один из списка 2.1 (нужен для всех действий, кроме «показать»).
- **`schedule`** и **`tz`** — нужны только для создания/изменения расписания. Если
  пользователь их явно не указал — не подставлять ничего самому: не передавать эти
  поля инструменту вовсе, он вычислит дефолт сам (Шаг 3-A).

Сопоставить выбор с действием и перейти к соответствующему пункту Шага 3:

| Запрос пользователя | Действие | Перейти к |
|---|---|---|
| «запусти / включи / настрой задачу X», «поменяй расписание X на …» | создать/изменить | Шаг 3-A |
| «останови / выключи / убери задачу X» | остановить | Шаг 3-B |
| «запусти X прямо сейчас / внепланово / разово» | внеплановый запуск | Шаг 3-C |
| «покажи расписание / какие задачи запущены / статус» | показать | Шаг 3-D |

Если после ответа пользователя действие всё ещё неоднозначно — **СТОП**, уточнить и
ждать ответа.

---

## Шаг 3 — Выполнить выбранное действие

Выполнить **ровно один** из пунктов ниже — тот, что определён в Шаге 2. Остальные
пропустить. После вызова инструмента сразу перейти к Шагу 4.

### Шаг 3-A — Создать или изменить задачу

Если пользователь **явно** указал `schedule`/`tz` — передать их как есть. Если нет —
не подставлять дефолт самому и не передавать эти поля инструменту вовсе: он вычислит
их сам. Для периодических задач (`monitor`, `monitor-v2`, `join-queue`,
`account-warmup`, `dm-replies`) дефолтная фаза старта распределяется round-robin
между агентами (agent-schedule-offset) — одинаковый период у всех, но не совпадающее
время старта, чтобы агенты не били Telegram/LLM синхронно. Для календарных
(`dm-send`, `leave-banned`) — фиксированное время без смещения.

Вызвать:

```
tg_scheduler_upsert_task(
  agentId: <agentId>,
  type:    <тип задачи>,
  schedule: <cron-выражение>,   // только если пользователь указал явно
  tz:       <таймзона>          // только если пользователь указал явно
)
```

Инструмент сам делает upsert строки и, если это первая активная задача агента,
поднимает таймер. В ответе запомнить `schedule`, `tz` (фактически применённые —
важно, если они были вычислены, а не переданы), `timerEnabled` и `systemctl`. → Шаг 4.

### Шаг 3-B — Остановить задачу

```
tg_scheduler_remove_task(agentId: <agentId>, type: <тип задачи>)
```

Выключает задачу (`enabled=0`); если активных задач не осталось — гасит таймер.
В ответе запомнить `timerDisabled` и `systemctl`. → Шаг 4.

### Шаг 3-C — Внеплановый запуск

```
tg_scheduler_trigger_now(agentId: <agentId>, type: <тип задачи>)
```

Выставляет `nextRun=now` и пинает сервис. Задача должна уже существовать и быть
включена. В ответе запомнить `systemctl`. → Шаг 4.

### Шаг 3-D — Показать расписание

```
tg_scheduler_list_tasks(agentId: <agentId>)
```

Возвращает все задачи: `type`, `schedule`, `tz`, `lastRun`, `nextRun`, `enabled`.
`lastRun`/`nextRun` — Unix-время в секундах. → Шаг 4.

---

## Шаг 4 — Сообщить итог

Кратко подтвердить пользователю результат выполненного действия:

- **3-A:** какая задача и с каким расписанием создана/изменена — взять `schedule`/`tz`
  из **ответа инструмента** (не из того, что было передано в вызове: если поля не
  указывались, инструмент вычислил их сам); если `timerEnabled=true` — что таймер
  агента запущен.
- **3-B:** какая задача остановлена; если `timerDisabled=true` — что таймер агента
  погашен (активных задач не осталось).
- **3-C:** что задача поставлена на внеплановый запуск.
- **3-D:** список задач с расписанием; `lastRun`/`nextRun` перевести в
  человекочитаемые дату/время в `tz` задачи.

Если в ответе инструмента `systemctl.ok === false` — сообщить пользователю об
ошибке управления таймером (строка в БД при этом уже записана).

## Ограничения и заметки

- Конечная задача `join-queue` (R-A3): когда очередь вступлений исчерпана,
  диспетчер сам выставляет ей `enabled=0`, но таймер не трогает. Если это была
  единственная активная задача — таймер останется включённым; чтобы погасить,
  останови задачу через Шаг 3-B.
- Управление таймером требует прав на systemd (gateway работает от root).
- Не более одной задачи на агента выполняется одновременно (одна сессия Telegram);
  разные типы задач у одного агента диспетчер выполняет последовательно.
- Тихие часы: с 23:00 до 03:00 (Asia/Yekaterinburg) `nextRun` не назначается
  ни одной задаче, кроме `leave-banned` — расчёт срока сам переносит его на
  ближайший момент после окна, а не откладывает уже назревшую задачу до конца
  окна. Сбор статистики (`funnel-tracker`) — отдельный таймер вне этого
  механизма, окном не затрагивается.
