# Channel Context — ручной запуск анализа контекста каналов

Операторский скилл: по заданным агентам вне очереди запускает тот же анализ контекста
каналов, что обычно идёт фоновой периодической задачей диспетчера (раз в 8 часов, батч
20 каналов на агента). Результат — обновлённое текстовое описание канала в БД
(`channels.channel_context`), не отчёт оператору файлом.

---

## Шаг 1 — Собрать параметры

При вызове скилла **одним сообщением** запроси у оператора, что нужно:

> Чтобы вне очереди обновить контекст каналов, мне нужно:
>
> • **агенты** — у каких агентов анализировать каналы (по каждому отдельно, на его сессии).
>
> • **count** — сколько каналов на агента обработать за этот запуск.

Зафиксируй `agents`, `count`. Если что-то не указано — переспроси только недостающее
(`agents` непуст, `count > 0`).

Если оператор спросит, какие именно каналы попадут в обработку — поясни: отбираются
каналы с уже резолвленной идентичностью привязанного broadcast-канала, у которых анализ
контекста никогда не строился (в приоритете) либо устарел (старше 90 дней). Статус
канала (`banned`/`suspend`) не исключает его из отбора — анализ описывает канал как
источник контента, не как канал для активности агента.

## Шаг 2 — Запустить анализ

```
tg_channel_context_run(
  agents: <список агентов>,
  count:  <каналов на агента>
)
```

Прогон идёт последовательно по агентам на их сессиях. Сбой на отдельном канале или
агенте не валит прогон — пропускается с записью причины.

## Шаг 3 — Показать отчёт

Выведи оператору поле `report` из ответа: сколько каналов отобрано, сколько
проанализировано и сколько пропущено с причинами. Само описание канала не выводится в
чат — оно в БД (`channels.channel_context`), при необходимости смотреть его отдельно
(SSH/дамп БД, см. `docs/operation.md`).
