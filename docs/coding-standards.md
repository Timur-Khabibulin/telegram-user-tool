# Стандарт чистого кода (TypeScript)

> **О чём документ.** Общие принципы и практики написания кода на TypeScript,
> основанные на индустриальных стандартах (Clean Code Р. Мартина, SOLID,
> Google / Microsoft style guides). Применяются ко всему коду репозитория и
> **не привязаны к конкретным фичам**.
>
> Конвенции, специфичные для этого проекта (OpenClaw SDK, GramJS, устройство
> плагина), — в [CLAUDE.md](../CLAUDE.md).

---

## 1. Принципы чистого кода

- **Код пишется, чтобы его читали люди.** Оптимизируем под чтение и понимание, а
  не под скорость написания. Читаемость важнее краткости.
- **Осмысленные имена.** Имя раскрывает намерение: зачем сущность существует и
  как используется. Произносимые, без «магических» чисел и непринятых
  сокращений.
- **DRY** — не дублировать знание: один факт системы описан в одном месте.
- **KISS** — простейшее работающее решение предпочтительнее «умного».
- **YAGNI** — не реализовывать впрок то, что не требуется сейчас.
- **Boy Scout Rule** — оставляй код чище, чем нашёл.

## 2. SOLID

| Принцип | Суть |
|---|---|
| **SRP** (Single Responsibility) | У модуля одна причина для изменения — одна ответственность. |
| **OCP** (Open/Closed) | Открыт для расширения, закрыт для модификации. |
| **LSP** (Liskov Substitution) | Подтип заменяет базовый тип без поломки поведения. |
| **ISP** (Interface Segregation) | Узкие интерфейсы; клиент не зависит от того, чем не пользуется. |
| **DIP** (Dependency Inversion) | Зависим от абстракций, не от реализаций (инъекция зависимостей). |

## 3. Строгая типизация

- Все строгие флаги `tsconfig` включены: `strict`, `noImplicitAny`,
  `strictNullChecks`, `strictFunctionTypes`, `noImplicitThis` и т. д.
- **`any` запрещён.** Описывать точные `interface`/`type`. Для действительно
  неизвестного — `unknown` с последующим сужением, а не `any`.
- **Иммутабельность.** Предпочитать `const`; для данных — `readonly`,
  `ReadonlyArray`, `as const`. Не мутировать объекты, созданные не здесь.
- Публичные контракты типизировать явно, не полагаться на вывод «как
  получилось». Избегать `as`-кастов; если каст неизбежен — обоснован
  комментарием.

## 4. Именование

- `camelCase` — переменные и функции.
- `PascalCase` — типы, интерфейсы (**без префикса `I`**), классы, enum.
- `UPPER_CASE` — глобальные константы (неизменяемые compile-time значения).
- Булевы — с префиксом `is` / `has` / `should`. Без венгерской нотации.

## 5. Функции и абстракции

- Одна функция — один уровень абстракции; ранний возврат вместо глубокой
  вложенности.
- **Абстракцию вводить, когда есть минимум два реальных применения**, а не
  заранее (избегать преждевременного обобщения).
- Композиция предпочтительнее наследования.
- Чистые функции (без побочных эффектов) — там, где это возможно; побочные
  эффекты изолировать.

## 6. Обработка ошибок

- **Ошибки не проглатываются.** Пустой `catch {}` запрещён: минимум —
  логирование с контекстом, обычно — проброс или преобразование в результат.
- Два подхода, выбор по ситуации:
  - **Исключения** — для исключительных, непредвиденных ситуаций (позиция Google
    и clean-code-typescript). Кастомные классы ошибок, когда `Error`
    недостаточно для передачи контекста.
  - **Типизированный результат** (`Result`-объект / дискриминированный union) —
    для ожидаемых ветвлений, где «ошибка» это штатный исход.
  - В одном модуле придерживаться единого подхода, не смешивать хаотично.
- Освобождение ресурсов — через `try/finally`, даже при ошибке.

## 7. Комментарии и самодокументируемость

- Комментарий объясняет **«почему»**, код объясняет **«что»**.
- Самодокументируемые имена вместо поясняющих комментариев-костылей.
- Не оставлять закомментированный код — для истории есть система контроля версий.

## 8. Асинхронность

- `async/await` вместо цепочек `.then`.
- Никаких «висящих» промисов: каждый промис либо `await`, либо осознанно
  обработан.
- Обрабатывать `unhandledRejection` / `uncaughtException` на уровне точки входа.

## 9. Инструменты и единообразие

- Единый формат через линтер/форматтер (ESLint + Prettier); форматирование не
  обсуждается вручную.
- Отключение правил линтера — только точечно и с обоснованием в комментарии.
- Код в файле единообразен по стилю; новый код читается как окружающий.
