# Расписание задач по умолчанию

Дефолты, которые подставляются при создании задачи (`tg_scheduler_upsert_task`),
если `schedule`/`tz` не переданы явно. Источник истины — код
(`src/core/db/tasks.ts`, `DEFAULT_PERIODIC_SCHEDULE` / `DEFAULT_CALENDAR_SCHEDULE`);
этот документ описывает те же значения для человека, при расхождении верить коду.

## Календарные задачи

Фиксированное время запуска раз в сутки, без фазового смещения.

| Тип | Время запуска | Часовой пояс |
|---|---|---|
| `dm-send` | 14:00 | Asia/Yekaterinburg |

Гранулярность проверки — heartbeat-тик диспетчера каждые `DISPATCHER_TICK_MINUTES`
(10 минут, `src/core/config.ts`): раз в тик диспетчер смотрит, не настало ли время
очередной задачи по её `nextRun`, а не сам период задачи.

## Тихие часы (нерабочее время)

С **23:00 текущего дня до 03:00 следующего** по Asia/Yekaterinburg (UTC+5) не
должна выполняться ни одна задача, кроме:

- сбора статистики (`funnel-tracker`) и ротации забаненных каналов
  (`channel-rotation`) — отдельные systemd-таймеры вне таблицы `tasks`, этого
  окна не касаются и продолжают работать как обычно;
- `leave-banned` — периодическая (180 мин), но осознанно оставлена в
  `QUIET_HOURS_EXEMPT_TASKS` (leave-banned-human-pacing) и может тикать и
  внутри этого окна.

В это окно задачи не назначаются: `nextRun` не может попасть внутрь окна и
автоматически переносится на ближайший момент после 03:00.

## Модель ресурсов и ёмкости (черновик)

Цель — предсказуемая работа при росте числа агентов: посчитать, сколько
одновременных прогонов система выдерживает без деградации, и заложить это в
модель расписания. Раздел ведётся по мере уточнения (черновик).

### Пик RSS одного прогона, по скиллу (МБ)

Источник — `dispatcher_runs.peakRssKb` (VPS, выборка по прогонам).

| Скилл | n | avg | p50 | p90 | p95 | max |
|---|---|---|---|---|---|---|
| monitor-v2 | 212 | 141.3 | 134.5 | 168.0 | 183.4 | 206.1 |
| account-warmup | 56 | 135.6 | 132.1 | 153.0 | 160.4 | 171.7 |
| leave-banned | 12 | 127.2 | 125.7 | 132.8 | 133.4 | 133.4 |
| join-queue | 921 | 125.9 | 125.1 | 131.6 | 138.4 | 149.4 |

### Рабочие допущения модели

- **Потребление памяти одного прогона периодического скилла одним агентом** —
  p95 `monitor-v2` = **183.4 МБ**. Взят самый тяжёлый периодический скилл и его
  p95 (не avg/max), чтобы модель закладывала запас под выбросы, не будучи
  завязанной на редкий абсолютный максимум.
- **Длительность прогона периодического скилла — меньше 10 минут в лучшем
  случае** (то есть короче одного heartbeat-тика диспетчера). Это допущение,
  не измеренная величина — в `dispatcher_runs`/`runs` пока не сведена
  статистика по длительности; при построении модели помечать явно как
  предположение, требующее проверки по реальным `durationMs` из `runs.db`.
- **Память на прогон, округлённо: 190 МБ** (183.4 округлено вверх).
- **Потолок ёмкости слайса: `MemoryMax = 3420 МБ`, `C = 16` параллельных
  прогонов — опровергнуто на практике, откачено на `MemoryMax = 2G`.**
  При деплое `3420 МБ` (predictable-agent-scheduling, 30.07) вызвал реальный
  system-wide OOM: VPS — **3.8 ГБ RAM всего**, а не 4 ГБ, как предполагалось
  при расчёте; 3420 МБ слайсу не оставляли системе достаточно памяти —
  ядро убило `openclaw-gateway` и SSH-сессию (`dmesg`: `global_oom`,
  `CONSTRAINT_NONE`, вне `tg-agents.slice`). Немедленно откачено на `2G`.
  Модель (`C=16`, запас 380 МБ) требует пересчёта под фактические ~3.8 ГБ
  RAM всего сервера — решение по новому целевому потолку не принято.

## Методология расчёта ёмкости и устойчивости

### 1. Статическая проверка (структурная ёмкость)

Отвечает на вопрос «хватает ли ёмкости в среднем при идеальном равномерном
разбросе по расписанию», без учёта деградации во времени. Необходимая, но не
достаточная проверка (см. §2).

Число слотов фазового пространства типа задачи: `S = период / DISPATCHER_TICK_MINUTES`.
При round-robin-распределении худший тик даёт `⌈N / S⌉` агентов, назревших
одновременно.

**Один тип задачи, работающий у всех агентов:**

```
⌈N / S⌉ ≤ C  ⟹  N_max = C × S
```

**Несколько независимо распределённых типов у всех агентов (консервативная
оценка, без учёта возможного наложения одного агента в обоих типах на одном
тике):**

```
Σᵢ ⌈N / Sᵢ⌉ ≤ C
```

**Применение при `C = 16`:**

| Сценарий | Периоды (текущий код) | N_max (24ч) | N_max (с тихими часами) |
|---|---|---|---|
| только `monitor-v2` | 180 мин → S=18 | 288 | 240 |
| `join-queue` + `account-warmup` | 240 мин (S=24) + 300 мин (S=30) | 210 | ≈177 |

### 2. Причины появления очереди сверх статической проверки

Очередь = момент, когда суммарная нагрузка тика `L(t) = due(t) + carryover(t-1)`
превышает ёмкость `C`. Четыре независимых источника:

1. **Структурное превышение** — `N > N_max` из §1. Статично, предсказуемо,
   не зависит от времени.
2. **Инфляция длительности прогона** — если `service_time > 10 мин` хотя бы у
   части прогонов, они переходят в `carryover(t+1)`, складываясь с новым
   `due(t+1)`. Под `CPUQuota` длительность сама растёт с нагрузкой
   (`service_time(t) ≈ base × g(L(t)/C)`) — это обратная связь, не константа.
3. **Коррелированные всплески `due(t)`**, не покрываемые round-robin:
   массовое включение задачи у пачки агентов за короткое окно; внеплановый
   запуск (`triggerTaskNow`) поверх обычного расписания.
4. **Ретрай-шторм при убийстве процесса** (специфика `dispatcher.ts`):
   `advanceTask()` вызывается после обработки каждой задачи внутри цикла по
   `due`; если процесс убит cgroup OOM-killer'ом (SIGKILL, не пойманное
   исключение), `nextRun` необработанных им задач не сдвигается — на
   следующем тике они снова `due`, без бэкоффа. Положительный контур: чем
   выше `L(t)`, тем больше убийств, тем больше неавансированных задач в
   `due(t+1)`.

### 3. Два режима деградации (разное поведение → разный вклад в очередь)

| Ресурс | Поведение при превышении | Эффект |
|---|---|---|
| CPU (`CPUQuota`) | Плавное урезание кванта (processor-sharing) | `service_time` растёт непрерывно с `L(t)` — постепенное накопление `carryover` |
| Memory (`MemoryMax`) | Жёсткий cutoff — OOM-killer убивает процесс целиком | Не деградация, а потеря прогресса + немедленный ретрай без бэкоффа (контур п.4) |

### 4. Динамическая проверка (симуляция по тикам)

Статическая проверка (§1) не воспроизводит ни п.2, ни п.3, ни п.4 из §2. Для
проверки устойчивости (сходится система к стационарному режиму или уходит в
разгон) нужна дискретно-временная симуляция по тикам (10 мин), с состоянием:

- множество агентов с их фазами по типам (детерминировано, round-robin);
- множество процессов «в полёте» (`in_flight`) с оставшимся временем до
  завершения;
- функция замедления `g(L(t))` — калибруется по фактическим `durationMs` из
  `runs.db` (сейчас не собрано — открытый вход, см. ниже);
- проверка памяти на каждом тике: `Σ RSS(in_flight)` против `MemoryMax` → при
  превышении выбор и убийство процесса(ов) (OOM-эвристика, обычно наибольший
  RSS), без `advanceTask` для не обработанных им задач;
- метрики на выходе: `carryover(t)` во времени, число ретраев/убийств,
  задержка относительно номинального `nextRun`.

Распределение `service_time` для калибровки — не одна точка, а p50/p95/max по
скиллу (таблица выше), чтобы видеть, как редкие тяжёлые прогоны статистически
провоцируют п.2 и п.4 из §2 даже при `N` ниже структурного `N_max`.

### 5. Открытые входы, требуемые для завершения модели

- Распределение `durationMs` прогонов по скиллу (`runs.db`) — сейчас не
  собрано, нужно для калибровки `g(L(t))` и проверки допущения «< 10 мин».
- Расхождение принятого потолка (`MemoryMax = 3420 МБ`) с текущим значением в
  `tg-agents.slice` (`MemoryMax=2G`) — нужно решение, поднимаем ли лимит
  слайса до целевого значения или пересчитываем модель под текущие 2 ГБ.
- Политика ретрая/бэкоффа после несостоявшегося (убитого) прогона — сейчас в
  коде её нет (`advanceTask` — единственная точка сдвига `nextRun`, и она
  пропускается именно в кризисный момент, п.4 §2); это и есть корень
  контура положительной обратной связи, требующий отдельного решения.

## Требования

1. Период задачи `join-queue` должен составлять 4 часа.
2. Период задачи `leave-banned` должен составлять 3 часа (leave-banned-human-pacing).
3. В окно 23:00–03:00 по Asia/Yekaterinburg (тихие часы) `nextRun` не должен
   назначаться ни одной задаче из таблицы `tasks`, кроме `leave-banned`. Сбор
   статистики (`funnel-tracker`) выполняется в это время (00:10 UTC+5) —
   отдельным systemd-таймером, вне таблицы `tasks`.
4. Сдвиг `nextRun` должен выполняться до исполнения скилла, а не после, и
   рассчитываться от предыдущего планового `nextRun`, а не от фактического
   времени старта.
5. Число одновременно исполняющихся прогонов диспетчера (по всем агентам и
   типам задач вместе) не должно превышать `C` — независимо от того, сколько
   задач назрело на одном тике, сколько типов совпало у одного агента,
   произошло ли массовое включение задачи или внеплановый запуск.
6. Лимит памяти `tg-agents.slice` должен соответствовать значению, принятому
   в модели ёмкости.
7. Диспетчер должен фиксировать длительность и потребление ЦП каждого
   прогона по типу скилла в агрегируемом виде.
