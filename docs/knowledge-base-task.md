# ТЗ: База знаний проекта для контекста ИИ-агента

> Документ описывает задачу по наведению порядка в документации проекта.
> Цель — дать ИИ-агенту (и человеку) полный и непротиворечивый контекст:
> от бизнес-целей до правил кода и эксплуатации.

---

## 1. Проблема

Проект пережил смену архитектуры: раньше это были скиллы для OpenClaw
(агент читал `SKILL.md` на естественном языке и сам вызывал инструменты),
теперь это автономные TypeScript-скрипты, которые запускаются systemd-таймерами,
сами вызывают LLM и исполняют скиллы как код.

Документация это переключение не отразила. Сейчас:

- `CLAUDE.md` описывает старую, уже несуществующую архитектуру (плагин,
  `channels-db.ts` в корне, 5 MTProto-инструментов). Это первый файл, который
  читает агент каждую сессию.
- Нет единого обзора системы «как она устроена сейчас».
- Нет описания проекта для бизнеса, нет роадмапа, нет общего списка задач.
- Нет описания эксплуатации: соответствия путей сервер↔проект, конфигурации, секретов.
- Решения зафиксированы в разных местах и частично противоречат коду.
- Одна и та же фича описана в `docs/`, в `openspec/changes/` и в `openspec/specs/`
  одновременно — гарантированный дрейф.

Из-за этого агент при разработке не видит цельный контекст и принимает решения,
которые мешают развивать проект.

## 2. Цель

Построить базу знаний по слоям, где:

- у каждого типа знания один дом (нет дублирования);
- каждый слой меняется со своей частотой и имеет понятного владельца;
- агент от точки входа (`CLAUDE.md`) за пару переходов доходит до любого ответа;
- любое техническое решение принимается с пониманием влияния на развитие проекта.

## 3. Принципы

1. **Один факт — один дом.** Дублировать знание запрещено.
2. **Тонкая точка входа.** `CLAUDE.md` маленький: ведёт командами и ссылками,
   а не пересказывает всё. Детали подгружаются по ссылкам, когда нужны.
3. **Документация = код.** Версионируется, обновляется в том же изменении, что
   вводит новое соглашение. Устаревшее удаляется — устаревшая инфа сбивает агента.
4. **Разделяем аудитории:** человек ↔ агент, и система разработки ↔ продукт
   (runtime-агент «Мария» и его персона в `SOUL.md`).
5. **Поведение системы — в OpenSpec.** Человеческие документы объясняют и
   обосновывают, но не дублируют правила поведения.
6. **Решения — в ADR** с обоснованием и отвергнутыми вариантами.
7. **Меньше контекста — лучше.** Важен сигнал, а не объём.

## 4. Целевая структура

| Слой | Файл / каталог | Для кого | Как часто меняется |
|---|---|---|---|
| Точка входа / индекс | `CLAUDE.md` | агент + человек | редко |
| Карта базы знаний | `docs/README.md` | агент + человек | редко |
| Описание проекта для бизнеса | `docs/product.md` | человек → агент | редко |
| Роадмап | `docs/roadmap.md` | оба | средне |
| Бэклог будущих задач | `docs/backlog.md` | оба | часто |
| Архитектура репозитория (код) | `docs/architecture.md` | оба | при смене архитектуры кода |
| Эксплуатация | `docs/operation.md` | агент + оператор | при смене инфраструктуры |
| Конфигурация и секреты | `docs/configuration.md` | агент + оператор | при смене конфига |
| Стандарт кода | `docs/coding-standards.md` (есть) | агент | редко |
| Архитектурные решения | `docs/decisions/NNNN-title.md` (ADR) | оба | только дополняется |
| Этапы разработки | `docs/workflow.md` | агент | редко |
| Правила поведения агента | `docs/agent-playbook.md` | агент | редко |
| Аналитика по фиче (для человека) | `docs/design/<feature>/<краткое-имя>-vN.md` | человек | по версиям |
| Поведение фич (для агента) | `openspec/changes/` → `specs/` → `archive/` + `config.context` | агент | по жизненному циклу |
| Конфиг runtime-продукта | `SOUL.md` (персона; пометить как данные) | runtime | по продукту |

## 5. Что должен содержать каждый документ

### `CLAUDE.md` — точка входа
- Что за проект в 2–3 фразах.
- Как запускается система: точка входа (`src/scripts/dispatcher.ts`), команда запуска.
- Основные команды: сборка, запуск, деплой, просмотр логов.
- Ссылка на `docs/README.md` как на единый каталог базы знаний.
- **Не содержит:** каталога документов и карты навигации (они в `docs/README.md`),
  описания фич, поведения, истории — только вступление, команды и указатель.

### `docs/README.md` — карта базы знаний (единственный каталог)
- Полный список всех документов базы знаний, по одной строке назначения на каждый.
- Маршрутизация «за каким вопросом — в какой документ».
- Для кого документ и как часто меняется.
- Рекомендуемый порядок чтения для нового агента или человека.
- **Это единственное место с каталогом** — `CLAUDE.md` его не дублирует.

### `docs/product.md` — описание проекта для бизнеса
- Что это за продукт и какую задачу бизнеса он решает.
- Цели и задачи проекта.
- Кто пользователи, для кого это.
- Ценность и ключевые сценарии использования.
- **Не содержит:** технических деталей реализации.

### `docs/roadmap.md` — роадмап
- Направления развития по этапам/горизонтам.
- Что планируется и зачем (связь с целями из `product.md`).
- **Не содержит:** мелких задач — они в `backlog.md`.

### `docs/backlog.md` — бэклог будущих задач
- Список будущих задач и идей, которые ещё не в работе.
- Краткое описание и приоритет каждой.

### `docs/architecture.md` — архитектура репозитория (только код)
- Компоненты кода и их роли: `dispatcher`, `skills`, `core/db`, `llm`,
  `telegram service` — как код организован и как части взаимодействуют.
- Поток управления **в коде**: диспетчер выбирает назревшие задачи и
  последовательно вызывает скиллы (без расписания/таймера — это эксплуатация).
- Слой данных как код: модули `src/core/db/*` и за что каждый отвечает
  (какие сущности хранит) — на уровне кода, без серверных путей.
- Внешние интеграции называются только как код-модули (`src/llm`,
  `src/core/telegram`); провайдеры/ключи/эндпоинты — не здесь, а в `configuration.md`.
- **Не содержит:** серверных путей и размещения баз (в `operation.md`),
  состава конфигурации/секретов (в `configuration.md`), обоснований решений
  (в `decisions/`).

### `docs/operation.md` — эксплуатация
- Таблица соответствия путей репозиторий ↔ сервер.
- Физическое размещение на сервере, включая пути к файлам баз (`*.db`).
- systemd-юниты и таймеры: что делают, по какому расписанию.
- Как деплоить (rsync, что исключается из синка), как перезапустить, как сделать
  разовый прогон.
- Где логи и как их читать (journald).
- Развёртывание конфигурации: **как** разместить файлы конфига/секретов на сервере
  (по путям и составу из `configuration.md`; сам состав здесь не переописывается).
- Сюда сворачивается содержимое нынешнего `deploy/README.md`.

### `docs/configuration.md` — конфигурация и секреты
- Какие внешние сервисы используются (LLM: codex OAuth + запасной OpenAI; Telegram).
- Какие переменные/ключи/файлы конфига нужны и **в каком файле лежат значения** —
  состав конфигурации, без самих значений секретов (значения в `local.properties`,
  который не в гите).
- Где конфиг в коде (`src/core/config.ts`).
- Сюда добавляются будущие внешние сервисы при их появлении.
- **Не содержит:** инструкций по развёртыванию (как ставить — в `operation.md`).

### `docs/coding-standards.md` — стандарт кода (уже есть)
- Принципы и правила написания кода на TypeScript: именование, типизация,
  обработка ошибок, асинхронность. Оставить как есть.

### `docs/decisions/NNNN-title.md` — архитектурные решения (ADR)
- Одно решение на файл.
- Контекст (почему встал вопрос), само решение, последствия, отвергнутые варианты.
- Дата и статус (принято / заменено другим решением).
- Только дополняется; старые решения не переписываются.

### `docs/workflow.md` — этапы разработки
- Этапы от идеи до релиза (Explore → Design → Implement → Review → Archive) —
  стандартная последовательность.
- На каждом этапе: что делать, какие документы читать и обновлять, какие инструменты.
- Правило связи аналитики фичи (design doc) и OpenSpec.
- **Не содержит:** критериев выбора (например, когда нужен change, а когда прямой
  фикс) — это в `agent-playbook.md`; workflow на них ссылается.

### `docs/agent-playbook.md` — правила поведения агента
- Когда идти в интернет (свежие практики, документация библиотек).
- Когда идти на VPS (через skill `vps`).
- Критерий: когда заводить OpenSpec change, а когда допустим прямой фикс
  (единственный дом для этого правила).
- На что опираться при решениях и как оценивать влияние на масштабирование.
- В каком порядке читать базу знаний.

### `docs/design/<feature>/<краткое-имя>-vN.md` — аналитика по фиче
- Папка на фичу, версии аналитики внутри (`<краткое-имя>-v1.md`, `-v2.md`, …).
- Актуальная версия = последняя; предыдущие остаются как история.
- По шаблону `docs/design/_template.md`:
  1. Проблема / Контекст
  2. Цели
  3. Как работает
  4. Архитектура
  5. Модель данных (если есть)
  6. Альтернативы (что ещё рассматривали и почему отказались)
  7. Метрики успеха
  8. Future Work
- Секций «Не-цели» и «Статус» нет — статус смотрят в OpenSpec.

### OpenSpec (`openspec/`)
- `specs/` — текущее поведение системы по способностям (источник истины для агента).
- `changes/` — активные изменения (proposal / tasks / delta specs).
- `archive/` — заархивированные изменения (история).
- `config.yaml → context` — краткая выжимка о проекте и архитектуре (из `product.md`
  и `architecture.md`).

### `SOUL.md` — конфиг runtime-продукта
- Персона runtime-агента: контент продукта (как агент говорит и себя ведёт).
- Это данные продукта, не документация для разработки и не инфра-конфигурация
  (техническая конфигурация и секреты — в `configuration.md`).

## 6. Аналитика по фиче и OpenSpec: как не дублировать

По каждой фиче — два представления, потому что человеку и агенту удобны разные форматы.

**Design doc** (`docs/design/<feature>/`) — для человека. Объясняет простым языком:
какая была проблема, что решили сделать, как это работает, как устроены данные,
какие были другие варианты и почему выбрали этот, как меряем успех.

**OpenSpec** — для агента. Точный список требований и сценариев «при условии X
система делает Y». Всегда отражает, как система ведёт себя **прямо сейчас**.

Правило разграничения (они про разное, поэтому дрейфа нет):

| Аспект | Design doc | OpenSpec |
|---|---|---|
| Для кого | человек | агент |
| Содержит | проблема, цели, как работает, архитектура, отвергнутые варианты, метрики | точные требования и сценарии поведения |
| Не содержит | статус изменений, гранулярные сценарии | обоснование, отвергнутые варианты, объяснения |
| Где смотреть текущее поведение | нет → ведёт в OpenSpec | да, источник истины |

Правила поведения — только в OpenSpec. Обоснование и объяснение — только в
дизайн-доке. Статус изменений — только в OpenSpec.

## 7. Этапы разработки (`docs/workflow.md`)

1. **Explore** — обдумать идею, прояснить требования.
2. **Design** — написать `docs/design/<feature>/<краткое-имя>-vN.md`; параллельно
   завести OpenSpec change.
3. **Implement** — писать код по `docs/coding-standards.md`; каждое архитектурное
   решение фиксировать новым ADR.
4. **Review** — сверить с требованиями фичи.
5. **Archive** — заархивировать OpenSpec change, обновить `specs/`; если менялась
   архитектура — обновить `docs/architecture.md`; если инфраструктура —
   `docs/operation.md`.

## 8. Объём работ

**Создать:**
- `docs/product.md`, `docs/roadmap.md`, `docs/backlog.md`;
- `docs/architecture.md` (архитектура репозитория — только код);
- `docs/operation.md`, `docs/configuration.md`;
- `docs/README.md` (карта базы знаний);
- `docs/workflow.md`, `docs/agent-playbook.md`;
- каталог `docs/decisions/` (ADR) и `docs/design/` с шаблоном `_template.md`.

**Переписать:**
- `CLAUDE.md` под текущую архитектуру (скрипты / dispatcher / systemd) —
  сделать тонкой точкой входа с картой источников истины.

**Заполнить:**
- `openspec/config.yaml` → поле `context`.

**Перенести / удалить:**
- `docs/dm-threads-design.md`, `docs/funnel-tracking-design.md`,
  `docs/group-threads-feature.md`, `featureDMOutreachSpec.md` → в `docs/design/<feature>/`
  под единый шаблон;
- `deploy/README.md` → свернуть в `docs/operation.md` (или оставить ссылкой);
- заархивировать завершённые OpenSpec changes, чтобы `specs/` догнал реальность;
- вычистить корень: `=`, файлы сессий, `todo/`, `bug-reports/`;
- определить судьбу `skills/*/SKILL.md` против `src/skills/*.ts` (что источник истины).

## 9. Вне объёма

- Рефакторинг кода.
- Изменение поведения скиллов.
- Настройка CI.

## 10. Критерии приёмки

1. `CLAUDE.md` соответствует фактическому коду (точка входа, пути, как
   запускается система).
2. От `CLAUDE.md` агент доходит до любого ответа (бизнес / архитектура /
   эксплуатация / процесс / решение) за два перехода по ссылкам.
3. Ни один факт не описан в двух местах. Дизайн-док не содержит правил поведения —
   только ссылки на OpenSpec.
4. У каждого документа один владелец и понятная частота обновления.
5. Зафиксированы правила: когда агент идёт в интернет, когда на VPS, когда
   заводит OpenSpec change.

## 11. Порядок реализации

1. **Фундамент:** `CLAUDE.md` + `docs/architecture.md` + `docs/product.md` +
   `openspec/config.yaml context`.
2. **Эксплуатация:** `docs/operation.md`, `docs/configuration.md`.
3. **Стратегия:** `docs/roadmap.md`, `docs/backlog.md`, `docs/README.md`.
4. **Процесс и решения:** `docs/workflow.md`, `docs/agent-playbook.md`,
   каталог ADR, шаблон аналитики фичи.
5. **Уборка:** перенос старых дизайн-доков, архивация changes, чистка корня.
