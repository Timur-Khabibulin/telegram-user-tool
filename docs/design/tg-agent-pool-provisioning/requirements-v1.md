# Требования: Расщепление авторегистрации на пул обезличенных аккаунтов и развёртывание персоны — v1

> **О чём документ.** Проблема, доменная модель, цель, требования и критерии
> приёмки — уровень бизнес-аналитики (что и почему, для кого). Техническое
> решение (как именно это реализуется) сюда не входит — это отдельный
> документ `architecture.md` (архитектор), парный к этому.

## 1. Проблема и контекст

Сегодня превращение купленного Telegram-аккаунта в рабочего агента выполняет
один монолитный скилл авторегистрации. За один прогон он делает всё сразу:
подбирает мобильный прокси, восстанавливает сессию из tdata, чистит прошлое
состояние аккаунта, меняет 2FA, сбрасывает чужие сессии, регистрирует вторую
(агентскую) сессию, применяет персону (профиль, фото, username, публичный
канал) и атомарно переносит результат в рабочий каталог агента. У скилла два
режима: без канала (mode A) и с каналом (mode B). Отдельная способность
`persona-channel-setup` умеет доводить канал персоны уже зарегистрированным
агентам.

Из-за слитности «подготовки аккаунта» и «применения персоны» подготовку нельзя
делать заранее и впрок: чтобы получить готовых агентов под персону, нужно каждый
раз проходить весь тяжёлый и рискованный путь целиком, а число агентов
фиксируется в момент подготовки, а не в момент, когда бизнес решил развернуть
персону.

При этом в системе уже есть **пул обезличенных аккаунтов**
(`workspace-emptyAccount*`), из которого фича замены забаненных аккаунтов
(`banned-account-replacement`) берёт готовый аккаунт при бане. Пул-аккаунт по
инварианту несёт только зарегистрированную сессию, tdata и прокси — без персоны.
Чего в системе нет — автоматического **производителя** этого пула: аккаунты в
него сейчас попадают не штатным процессом.

Боль испытывают операторы, которые готовят и разворачивают агентов: они не могут
накопить запас подготовленных аккаунтов заранее и по требованию быстро получить
нужное число агентов под выбранную персону.

## 2. Цель

1. Разделить единый процесс на две независимые фазы вокруг общего пула
   обезличенных аккаунтов:
   - **Фаза 1 (производитель пула)** — из купленных аккаунтов делает
     обезличенные пул-аккаунты, которые можно копить впрок.
   - **Фаза 2 (потребитель пула)** — по требованию превращает нужное количество
     пул-аккаунтов в рабочих агентов под выбранную персону.
2. Дать возможность накапливать пул подготовленных аккаунтов заранее и
   отвязать момент выбора числа агентов и персоны от момента подготовки
   аккаунтов.
3. Сделать фазу 2 вторым штатным потребителем того же пула, параллельным замене
   забаненных аккаунтов, с безопасным (без двойного потребления) забором
   аккаунтов из общего пула.
4. Вынести общие для всех аккаунтов учётные данные в отдельную заготовку
   платформы, чтобы персона не хранила общих технических значений.
5. Вывести из употребления монолитный скилл авторегистрации (mode A и mode B) и
   способность `persona-channel-setup`, переведя их функции на две новые фазы.

## 3. Доменная модель

Термины предметной области. Telegram/MTProto-понятия подтверждены внешними
источниками (раздел 9); платформенные понятия пула и агента — существующими
OpenSpec-спеками (`banned-account-replacement`, `tg-agent-autoregistration`,
`persona-channel-setup`, `mobile-proxy-provisioning`).

| Термин | Что это |
|---|---|
| Купленный аккаунт | Telegram-аккаунт, приобретённый на стороне и переданный платформе в виде архива tdata; на входе несёт унаследованное чужое состояние (профиль, фото, публичные каналы, чужие активные сессии, чужой 2FA-пароль). |
| tdata | Формат локального хранилища Telegram Desktop; содержит ключи авторизации аккаунта, из которых восстанавливается рабочая сессия. Один архив = один аккаунт. |
| Bootstrap-сессия | MTProto-сессия, восстановленная из tdata купленного аккаунта; используется для первичной подготовки аккаунта и приёма кода при регистрации второй сессии. |
| Агентская (вторая) сессия | Независимая MTProto-сессия, регистрируемая платформой для повседневной работы агента, отдельная от bootstrap-сессии. |
| 2FA-пароль (облачный пароль) | Пароль двухэтапной проверки Telegram (two-step verification, протокол SRP). У купленного аккаунта — заданный продавцом; платформа приводит его к общему известному значению. |
| Активные сессии аккаунта | Авторизованные устройства/сессии Telegram-аккаунта. Чужие сессии — унаследованные от продавца, подлежат сбросу. |
| Публичный канал | Канал Telegram с публичным username. На число публичных каналов, которыми администрирует один аккаунт, Telegram накладывает лимит; при его превышении создание канала отклоняется ошибкой `CHANNELS_ADMIN_PUBLIC_TOO_MUCH`. |
| Персональный (закреплённый) канал | Публичный канал персоны, ассоциированный с аккаунтом как его личный (закреплённый) канал. |
| Общий приватный канал воронки | Единственный на весь флот приватный канал Telegram, куда ведут заявки на вступление; администрируется агентом-получателем отчётов. На агента отдельного приватного канала не создаётся. |
| Персональная инвайт-ссылка | Индивидуальная ссылка-приглашение конкретного агента в общий приватный канал воронки (вступление по одобрению заявки). Служит меткой источника вступления (title = идентификатор агента) и вставляется в закреплённый пост публичного канала агента. |
| username | Публичное имя пользователя аккаунта в Telegram; уникально в пределах Telegram. |
| Мобильный прокси | Прокси мобильного типа из существующего инвентаря внешнего сервиса asocks; кандидаты не создаются и не удаляются платформой. |
| Персона | Шаблон идентичности агента: имя, био, префикс `nick`, набор фото профиля, контент публичного канала. Определяет «кем» становится аккаунт. |
| Общая заготовка учётных данных | Общие для всех аккаунтов технические значения платформы: apiId/apiHash и общий 2FA-пароль. Не относится к конкретной персоне. |
| Пул обезличенных аккаунтов | Набор подготовленных аккаунтов, невидимых рабочему контуру платформы и ожидающих потребления. Уже потребляется заменой забаненных аккаунтов. |
| Пул-аккаунт | Отдельный обезличенный аккаунт пула: несёт рабочую агентскую сессию, tdata, прокси и общий 2FA — без персоны и без username. Имеет числовую метку K. |
| Числовая метка пул-аккаунта (K) | Порядковый идентификатор аккаунта в пуле. Транзиентна: освобождается при потреблении аккаунта и может переиспользоваться со временем. |
| Рабочий агент | Аккаунт с применённой персоной, видимый рабочему контуру платформы. Имеет числовую метку N. |
| Числовая метка агента (N) | Порядковый идентификатор рабочего агента. |
| Потребитель пула | Процесс, забирающий аккаунт из пула. Их два и они конкурируют за общий пул: развёртывание персоны (фаза 2) и замена забаненных аккаунтов. |
| Агент-получатель отчётов | Аккаунт, в чьи Saved Messages доставляется итоговый отчёт прогона. |

## 4. Ограничения среды

Внешние факты, значимые для любого варианта решения (перенесены из текущей
авторегистрации; сверены с указанными спеками).

- **Прокси — существующий инвентарь.** Кандидаты мобильного прокси берутся из
  инвентаря asocks по региону; платформа их не создаёт и не удаляет. Для каждой
  попытки подключения берётся следующий ещё не использованный кандидат, до
  заданного предела попыток. Исчерпание кандидатов/попыток — неуспех для этого
  аккаунта.
- **Bootstrap-сессия — из tdata без локального passcode.** Рабочая сессия
  восстанавливается из tdata купленного аккаунта без TDesktop-passcode.
- **Телефон и текущий 2FA — не из сайдкаров tdata.** Номер телефона аккаунта
  берётся с живого аккаунта (`getMe()`); текущий 2FA-пароль — из ввода
  оператора. Сайдкар-файлы tdata (`Accounts.txt`, `Password2FA.txt`) не
  читаются.
- **Приём кода второй сессии — окно 2 минуты.** Код входа для агентской сессии
  принимается на живую bootstrap-сессию; если код не пришёл вовремя (таймаут или
  код пришёл как SMS вместо сообщения в приложении) — аккаунт помечается статусом
  `needs_manual_code`.
- **Обе сессии остаются активными.** После регистрации агентской сессии
  bootstrap-сессия не завершается — аккаунт оканчивает фазу 1 с двумя
  одновременно активными сессиями.
- **Лимит публичных каналов на аккаунт.** Telegram ограничивает число публичных
  каналов, которыми администрирует один аккаунт; при превышении создание канала
  отклоняется (`CHANNELS_ADMIN_PUBLIC_TOO_MUCH`).
- **Пул невидим рабочему контуру.** Аккаунты пула не перечисляются как рабочие
  агенты и не подхватываются диспетчером, планировщиком, воронкой и discovery до
  их подстановки под агента.
- **Detached-прогон.** Прогон выполняется как фоновая задача, не ограниченная
  таймаутом отдельного вызова инструмента; итоговый отчёт доставляется в Saved
  Messages агента-получателя отчётов, а не возвращается синхронно.
- **Атомарность в пределах файловой системы.** Забор аккаунта из пула и
  промоушен готового аккаунта выполняются как атомарное переименование каталога
  в пределах одной файловой системы.

## 5. Алгоритм

Не фиксируется в этой версии: конкретный вариант решения ещё не согласован
отдельно с координатором.

## 6. User Stories

US-1. Как оператор пула, я хочу заранее готовить из купленных аккаунтов запас
обезличенных пул-аккаунтов, чтобы не проходить тяжёлую подготовку в момент, когда
срочно нужны агенты. `(R1–R11, R13–R16)`

US-2. Как оператор пула, я хочу повторно завершить только регистрацию агентской
сессии для аккаунта, у которого код не пришёл вовремя, чтобы не проходить заново
уже применённую к аккаунту подготовку. `(R12)`

US-3. Как оператор развёртывания, я хочу по требованию превратить нужное
количество пул-аккаунтов в рабочих агентов под выбранную персону, чтобы получать
агентов тогда и в том объёме, когда это решил бизнес. `(R17–R25)`

US-4. Как оператор платформы, я хочу, чтобы фаза 2 и замена забаненных аккаунтов
безопасно забирали аккаунты из общего пула, чтобы один аккаунт не достался двум
процессам сразу. `(R19, R29)`

US-5. Как оператор платформы, я хочу, чтобы замена забаненного аккаунта сама
наделяла обезличенный пул-аккаунт идентичностью персоны при заборе, чтобы строго
обезличенный пул не оставлял подставленного агента без username. `(R28)`

US-6. Как оператор платформы, я хочу, чтобы общие технические значения (общие
apiId/apiHash и общий 2FA-пароль) лежали в отдельной заготовке, а не в персоне,
чтобы персона описывала только идентичность и общие значения не дублировались по
персонам. `(R26, R27)`

US-7. Как оператор пула и оператор развёртывания, я хочу получать по завершении
прогона отчёт с исходом по каждому аккаунту в известном месте, чтобы видеть, что
удалось, а что требует ручного разбора. `(R15, R16, R23, R24, R25)`

US-8. Как оператор платформы, я хочу, чтобы прежний монолитный скилл
авторегистрации и способность доводки канала были выведены из употребления,
чтобы оставался один непротиворечивый путь подготовки и развёртывания агентов.
`(R30)`

## 7. Требования

### Фаза 1 — производитель пула

**R1.** Когда оператор запускает фазу 1, система должна принять на вход: список
ссылок на tdata-архивы (по одному аккаунту на ссылку), текущий 2FA-пароль пачки,
регион прокси и предел числа попыток прокси.

**R2.** По каждому входному аккаунту система должна подобрать рабочий мобильный
прокси из существующего инвентаря, беря следующего ещё не использованного
кандидата до заданного предела попыток. Если ни один кандидат не подошёл в
пределах попыток, то система должна пометить аккаунт статусом `proxy_failed` и
перейти к следующему.

**R3.** По каждому входному аккаунту система должна восстановить рабочую
bootstrap-сессию из его tdata.

**R4.** По каждому входному аккаунту система должна удалить все публичные каналы,
которыми администрирует этот аккаунт, чтобы последующее применение персоны (фаза
2 или замена забаненного) не упёрлось в лимит публичных каналов на аккаунт.

**R5.** По каждому входному аккаунту система должна сменить 2FA-пароль с текущего
(введённого оператором) на общий известный 2FA-пароль платформы.

**R6.** По каждому входному аккаунту система должна завершить все прочие активные
сессии аккаунта, унаследованные от продавца.

**R7.** По каждому входному аккаунту система должна зарегистрировать вторую
(агентскую) MTProto-сессию, приняв код входа на живую bootstrap-сессию. Если код
не получен в отведённое окно, то система должна пометить аккаунт статусом
`needs_manual_code` и перейти к следующему.

**R8.** Фаза 1 не должна применять персону: не задавать профиль, имя, био, фото и
username и не создавать каналов персоны. Персона фазе 1 неизвестна.

**R9.** Система должна считать пул-аккаунт готовым тогда и только тогда, когда
одновременно: зарегистрирована рабочая агентская сессия, установлен общий
2FA-пароль платформы, отсутствуют чужие активные сессии. Готовый пул-аккаунт не
несёт персоны и username.

**R10.** По готовому аккаунту система должна сформировать пул-аккаунт с числовой
меткой K, содержащий его учётные и подключенческие данные (creds, прокси,
устройство, агентская сессия) без персоны и без username, вместе с его tdata.

**R11.** Система должна присваивать метку K как «максимальная присутствующая на
диске метка пул-аккаунтов + 1»; при пустом пуле следующая метка равна 1.
Освободившиеся при потреблении метки могут переиспользоваться со временем; отдельный
сквозной счётчик-максимум не ведётся.

**R12.** Система должна предоставлять способ повторить только регистрацию
агентской сессии для аккаунта в статусе `needs_manual_code`, не повторяя
подготовку аккаунта (смену 2FA, сброс сессий, удаление каналов). Если аккаунт не
в статусе `needs_manual_code`, то система должна отказать без попытки
подключения.

**R13.** По завершении обработки каждого аккаунта фазы 1 система должна
присваивать ему один из терминальных статусов: `done` (пул-аккаунт готов),
`proxy_failed`, `setup_failed` (отклонён шаг подготовки — смена 2FA, сброс
сессий или удаление унаследованных каналов), `needs_manual_code`.

**R14.** Если обработка одного аккаунта завершается ошибкой, то система должна
продолжить обработку остальных аккаунтов пачки.

**R15.** По завершении прогона фазы 1 система должна доставить отчёт с исходом по
каждому аккаунту в Saved Messages агента-получателя отчётов, а не возвращать его
синхронно вызывающему.

**R16.** Система должна делать пул-аккаунт видимым как элемент пула только после
полной сборки всех его артефактов, выполняя перенос в пул одной атомарной
операцией. Аккаунт в статусе, отличном от `done`, должен оставаться в промежуточном
хранилище до ручного разбора и не переиспользоваться автоматически.

### Фаза 2 — потребитель пула (персона → агенты)

**R17.** Когда оператор запускает фазу 2, система должна принять на вход:
выбранную персону и количество M — сколько агентов требуется.

**R18.** Система должна брать из пула аккаунты в порядке «старейший первым»,
добирая до запрошенного числа M пригодных аккаунтов (пропуская невалидные по
R19). Если пригодных аккаунтов оказалось меньше M — из-за пустого или
исчерпанного пула, либо из-за того, что часть аккаунтов невалидна, — система
должна наделить персоной все доступные пригодные аккаунты (частичный успех) и
явно сообщить о нехватке в отчёте (см. R25), не отказывая в прогоне целиком.

**R19.** Забор пул-аккаунта система должна выполнять атомарно, исключая двойное
потребление: один и тот же аккаунт не может достаться одновременно фазе 2 и
замене забаненных; проигравший в гонке за один аккаунт должен брать следующий
свободный. Перед потреблением система должна проверить пригодность аккаунта,
подключившись его агентской сессией; если аккаунт нерабочий или ограничен
(мёртвая сессия, бан/заморозка), он не потребляется под агента, помечается
статусом `account_invalid` (см. R24) и уходит в карантин, а система берёт
следующий свободный пул-аккаунт (симметрично поведению замены забаненных).

**R20.** По каждому взятому пригодному аккаунту система должна через его агентскую
сессию (не через bootstrap): задать username как префикс `nick` персоны плюс
случайный человекочитаемый суффикс; задать профиль (имя, био); загрузить все фото
персоны; создать публичный канал персоны, опубликовать в нём пост персоны и
закрепить канал как персональный; сгенерировать агенту персональную
инвайт-ссылку в общий приватный канал воронки (вступление по одобрению заявки) и
вставить эту ссылку в закреплённый пост публичного канала агента. Отдельный
приватный канал на агента не создаётся — используется существующий механизм
персональных инвайт-ссылок.

**R21.** По каждому успешно настроенному аккаунту система должна записать в его
конфигурацию персону и превратить пул-аккаунт в рабочего агента с числовой меткой
N, сделав его видимым рабочему контуру платформы.

**R22.** Система должна присваивать метку N как «максимальная существующая метка
рабочих агентов + 1».

**R23.** Если настройка одного аккаунта в фазе 2 завершается ошибкой, то система
должна продолжить обработку остальных аккаунтов.

**R24.** По завершении обработки каждого взятого аккаунта фазы 2 система должна
присваивать ему один из трёх терминальных статусов: `done` — персона применена
целиком (username, профиль, все фото, публичный канал с постом и закрепом,
персональная инвайт-ссылка в общий приватный канал воронки, вставленная в
закреплённый пост), аккаунт переведён в рабочего агента;
`setup_failed` — аккаунт подключился своей агентской сессией, но шаг применения
персоны отклонён Telegram (например `USERNAME_OCCUPIED`, `FLOOD_WAIT`, ошибка
создания канала), в агенты не переведён; `account_invalid` — взятый из пула
аккаунт при подключении оказался нерабочим или ограниченным (мёртвая сессия,
бан/заморозка), под агента не потреблён и уходит в карантин. Статус `skipped` в
фазе 2 не вводится: по инварианту пул-аккаунт обезличен и канала персоны у него
быть не может.

**R25.** По завершении прогона фазы 2 система должна вернуть отчёт с исходом по
каждому обработанному аккаунту и итоговой строкой вида «запрошено M, создано X;
пул исчерпан / Y аккаунтов невалидны», явно отражающей нехватку при частичном
успехе. Отдельный durable-механизм оповещения (как у замены забаненных) не
требуется.

### Общая заготовка учётных данных

**R26.** Система должна хранить общие для всех аккаунтов технические значения
(общие apiId/apiHash и общий 2FA-пароль) в отдельной общей заготовке платформы,
вне шаблона персоны. Шаблон персоны не должен содержать этих значений.

**R27.** Общую заготовку учётных данных должна читать только фаза 1
(производитель). Потребителям пула (фаза 2 и замена забаненных) она не нужна:
apiId/apiHash уже содержатся в конфигурации пул-аккаунта.

### Следствие для замены забаненных аккаунтов

**R28.** Поскольку пул-аккаунт теперь строго обезличен (без username), при
потреблении пул-аккаунта заменой забаненного система должна наделить этот аккаунт
идентичностью персоны заменяемого агента, включая применение username, — так же,
как это делает фаза 2 при заборе.

**R29.** Оба потребителя пула (фаза 2 и замена забаненных) должны потреблять
аккаунты в едином согласованном порядке «старейший первым».

### Вывод прежних способностей из употребления

**R30.** Система должна вывести из употребления монолитный скилл авторегистрации
(оба режима — без канала и с каналом) и способность доводки публичного канала
`persona-channel-setup`; их функции должны покрываться фазой 1 и фазой 2.

## 8. Критерии приёмки

**AC-1.** После прогона фазы 1 по пачке купленных аккаунтов в пуле присутствуют
новые пул-аккаунты по числу аккаунтов, дошедших до `done`; каждый из них несёт
рабочую агентскую сессию, общий 2FA-пароль платформы и не несёт персоны и
username.

**AC-2.** Для каждого аккаунта пачки фазы 1 отчёт в Saved Messages
агента-получателя отчётов содержит ровно один из статусов `done` /
`proxy_failed` / `setup_failed` / `needs_manual_code`.

**AC-3.** Аккаунт, не дошедший до `done`, не появляется в пуле и остаётся в
промежуточном хранилище до ручного разбора; сбой одного аккаунта не прерывает
обработку остальных.

**AC-4.** Метка нового пул-аккаунта равна максимальной присутствующей метке пула
плюс один; при пустом пуле первый созданный аккаунт получает метку 1.

**AC-5.** Повтор регистрации агентской сессии возможен для аккаунта в статусе
`needs_manual_code` без повторного применения смены 2FA/сброса сессий/удаления
каналов; для аккаунта в ином статусе повтор отклоняется без подключения.

**AC-6.** После прогона фазы 1 у обработанного до `done` аккаунта нет публичных
каналов, которыми он администрирует (унаследованные удалены).

**AC-7.** Фаза 2 по запросу с персоной и количеством M превращает взятые из пула
аккаунты в рабочих агентов с применённой персоной (username из `nick` персоны +
случайный суффикс, профиль, все фото, публичный канал персоны с постом,
закреплённый как персональный, персональная инвайт-ссылка в общий приватный
канал воронки, вставленная в закреплённый пост публичного канала); каждый
становится видимым рабочему контуру платформы.

**AC-8.** Метка нового рабочего агента равна максимальной существующей метке
агентов плюс один.

**AC-9.** При одновременной работе фазы 2 и замены забаненных один и тот же
пул-аккаунт не потребляется дважды; проигравший в гонке процесс берёт следующий
свободный аккаунт.

**AC-10.** При замене забаненного аккаунта подставленный обезличенный
пул-аккаунт получает идентичность персоны заменяемого агента, включая username.

**AC-11.** Общие apiId/apiHash и общий 2FA-пароль читаются из отдельной общей
заготовки платформы; шаблон персоны их не содержит, и фаза 2 к этой заготовке не
обращается.

**AC-12.** Прежний монолитный скилл авторегистрации (оба режима) и способность
`persona-channel-setup` помечены как выведенные из употребления; получение
готовых агентов возможно связкой фазы 1 и фазы 2.

**AC-13.** Когда пригодных пул-аккаунтов меньше запрошенного M (пул пуст или
исчерпан, либо часть аккаунтов невалидна), фаза 2 наделяет персоной все доступные
пригодные аккаунты и возвращает отчёт с итоговой строкой, где явно указаны
запрошенное M, число созданных агентов X и причина нехватки (пул исчерпан /
Y аккаунтов невалидны); прогон не отклоняется целиком.

**AC-14.** Каждый обработанный фазой 2 аккаунт получает ровно один из статусов
`done` / `setup_failed` / `account_invalid`; статус `skipped` не используется.

**AC-15.** Если взятый из пула аккаунт при подключении оказался невалидным или
ограниченным, он помечается `account_invalid`, уходит в карантин и не переводится
в агенты, а фаза 2 берёт следующий свободный пул-аккаунт, продолжая добор до M.

## 9. Источники

- Telegram Desktop, формат локального хранилища `tdata` — устройство и назначение
  каталога с ключами авторизации: <https://github.com/telegramdesktop/tdesktop>.
- MTProto, авторизация и сессии — <https://core.telegram.org/mtproto> и
  <https://core.telegram.org/api/auth>.
- Two-step verification (облачный 2FA-пароль, протокол SRP), метод
  `account.getPassword` / смена пароля — <https://core.telegram.org/api/srp>.
- Управление активными сессиями (`account.getAuthorizations`,
  `auth.resetAuthorizations`) — <https://core.telegram.org/api/auth>.
- Публичные каналы и лимит администрируемых публичных каналов, ошибка
  `CHANNELS_ADMIN_PUBLIC_TOO_MUCH`; проверка/установка username канала
  (`channels.checkUsername`, `channels.updateUsername`) —
  <https://core.telegram.org/api/channel> и
  <https://core.telegram.org/method/channels.checkUsername>.
- Приватные каналы и инвайт-ссылки с одобрением заявок на вступление
  (`chatlists`/`chatInviteImporter`, join-request approval) —
  <https://core.telegram.org/api/invites>.
- Мобильные прокси, инвентарь и поиск (`/proxy/search`) — asocks.com.
- OpenSpec-спеки платформы: `tg-agent-autoregistration`, `persona-channel-setup`,
  `banned-account-replacement`, `mobile-proxy-provisioning`, `private-invite-links`
  (общий приватный канал воронки `FUNNEL_PRIVATE_CHANNEL_ID`, персональная
  инвайт-ссылка агента и вставка её в закреплённый пост).
