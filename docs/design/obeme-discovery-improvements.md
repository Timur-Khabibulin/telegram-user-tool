# obeme (автопоиск похожих каналов) — рекомендации по доработке

Анализ VPS-скрипта `src/scripts/ops/obeme-start.ts` и рекомендации по улучшению.
Документ — предложения с обоснованием; выбор варианта за человеком, код не меняется
до принятия решения.

## Контекст: где рождается FLOOD_WAIT

Диагноз подтверждён по коду:

- `resolveChannelByUsername` → `contacts.ResolveUsername` (`service.ts:1809`) — самый жёстко
  лимитируемый метод Telegram (защита от перебора username). Это **единственный источник
  FLOOD_WAIT** в прогоне.
- `getChannelRecommendations` (`service.ts:1869`) и `getChannelGateInfo` (`service.ts:1918`)
  принимают готовый `InputChannel` с access_hash — резолва не делают и не флудят. Поэтому
  ~2136 проверок кандидатов за прогон проходят, а ~100 резолвов семян — флудят.
- Кандидат из `getChannelRecommendations` приходит **уже с access_hash** (`service.ts:1880`),
  но obeme его выбрасывает и сохраняет только username.

### Пример из индустрии

За основу сравнения взят открытый парсер похожих каналов:
**https://github.com/MargotP/telegram_similar_channels_finder**

Он «быстрее», потому что на каждое семя делает лишь `get_entity()` + один
`GetChannelRecommendations`, без обогащения кандидатов, без BFS и без пауз. Ключевое
техническое отличие: Telethon `get_entity()` сначала смотрит **персистентный кэш
сущностей** и делает `ResolveUsername` только при промахе — тогда как наш
`resolveChannelByUsername` вызывает сырой RPC каждый раз, в обход существующего
`peerCache` (`service.ts:269`, `805`). Оговорка: «быстрее» ≠ «не флудит» — при большом
числе свежих некэшированных username тот же парсер поймает FLOOD_WAIT, лимит серверный
и от библиотеки не зависит.

## Рекомендации (по приоритету «эффект / объём работы»)

### 1. Убрать сырой `ResolveUsername` — резолвить через кэш/access_hash

**Проблема:** `resolveChannelByUsername` (`service.ts:1809`) вызывает сырой
`contacts.ResolveUsername` на каждое семя в обход уже существующего `peerCache`.

**Предложение:** резолвить семена из `peerCache`/сохранённого access_hash (или через
GramJS `getInputEntity`, который сам проверяет кэш), а `ResolveUsername` дёргать только
при промахе кэша.

**Оговорка:** даёт эффект, если семена — из наших прошлых находок или есть в диалогах
искателя. Для впервые встреченных внешних username первый резолв неизбежен.

### 2. Развязать discovery и обогащение

**Проблема:** сам обход рекомендаций дёшев (access-hash-пространство, без резолвов), а
медленное и объёмное — per-candidate `getChannelGateInfo` на тысячи кандидатов с паузами
3–12 с.

**Предложение:** «найти похожие» и «проверить кандидата» — разные этапы со своим
троттлингом. Discovery можно гнать быстро (как парсер MargotP), обогащение — отдельно и
асинхронно.

**Эффект:** прогон discovery ускоряется на порядок; пейсинг настраивается под каждый
этап отдельно.

### 3. Сохранять access_hash найденных кандидатов

**Проблема:** кандидат приходит из `getChannelRecommendations` с access_hash
(`service.ts:1880`), но obeme его выбрасывает и пишет только username. Когда этот канал
позже становится семенем — снова резолв.

**Предложение:** персистить `(channelId, access_hash)` при находке (per-account) и
подавать будущие блоки семян хэндлами, а не username. Прямо усиливает п.1 — граф
расширяется без резолвов.

### 4. Удалить листание (`maybeBrowse`)

**Проблема:** антидетект-рудимент; сам код признаёт, что защищает «от наблюдателя,
которого у Telegram нет», полезных данных не даёт (метрики считает конвейер).

**Предложение:** удалить ради простоты. Эффект на флуд/скорость минимальный (гейт 12%),
но уходит лишний код и запросы.

## Порядок внедрения

1. Снять источник флуда — **п.1** (при необходимости с фундаментом **п.3**). Решает
   главную боль.
2. **п.2** — ради скорости прогона.
3. **п.4** — попутное упрощение.

## Открытый вопрос (блокирует выбор)

**Откуда берутся `imports/obeme/blocks/*.txt`?**

- Если из наших прежних находок → работают п.1/п.3 (почти убирают резолв).
- Если это внешние курированные списки → первый резолв каждого username неизбежен, и
  п.1/п.3 покрывают только повторные заходы.

Без ответа нельзя оценить, насколько п.1/п.3 снимают флуд. После ответа — оформить в
OpenSpec change с конкретным планом.
