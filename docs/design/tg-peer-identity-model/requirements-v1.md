# Требования: Модель хранения идентичности Telegram-сущностей (peer) — v1

> **О чём документ.** Проблема, доменная модель, цель, требования и критерии
> приёмки — уровень бизнес-аналитики (что и почему, для кого). Техническое
> решение (как именно это реализуется — схема хранения, имена полей, механизм
> инвалидации, таймстампы) сюда не входит: это отдельный документ
> `architecture.md` (архитектор), парный к этому.

## 1. Проблема и контекст

Платформа запускает Telegram-агентов. Агент — это один Telegram-аккаунт, который
работает от своего имени через MTProto: вступает в каналы и чаты, читает в них
сообщения и выходит из них (операции join / read / leave). Платформа управляет
несколькими агентами и заменяет аккаунты при банах.

Чтобы выполнить любую операцию над peer (каналом, супергруппой, группой), агенту
нужен идентификатор этой сущности **плюс** `access_hash` — «пропуск» к ней.
`access_hash` действителен только в пределах одной авторизации конкретного
аккаунта (одной `sessionString`): он не переносится ни на новую авторизацию того
же аккаунта, ни на другой аккаунт.

Платформа регулярно **переавторизует** агента (получает новую `sessionString`) и
**заменяет** аккаунты. Поэтому ранее сохранённый `access_hash` после
переавторизации или замены аккаунта может оказаться недействительным. Если
платформа применит устаревший `access_hash`, обращение к peer не состоится —
операция join / read / leave сломается.

Боль: без явной модели, **что** платформа хранит о peer, **что** из этого
стабильно, а **что** привязано к авторизации и должно считаться эфемерным,
операции над каналами и чатами перестают работать после переавторизации или
замены аккаунта, а платформа рискует потерять связь с уже известным ей peer.

Кого затрагивает: агента (не может выполнить операцию по недействительному
пропуску) и оператора платформы (агенты выпадают из каналов после ротации
аккаунтов и переавторизации).

## 2. Цель

1. Определить минимальный набор сведений о peer, который платформа хранит.
2. Для каждого сведения определить жизненный цикл: когда оно появляется, когда
   обновляется, когда становится недействительным.
3. Разделить сведения на **стабильные** (переживают переавторизацию и смену
   аккаунта) и **привязанные к авторизации** (действительны только в рамках
   текущей `sessionString`).
4. Обеспечить, чтобы операции join / read / leave выполнялись корректно и
   переживали переавторизацию агента и замену аккаунта.

### Вне скоупа (Non-Goals)

Модель описывает **только идентичность peer и факт членства** агента —
сведения, достаточные для операций join / read / leave и для устойчивости к
переавторизации. Peer в скоупе модели — это **Channel** (каналы и супергруппы)
и **basic group** (`Chat`) как полноценные рабочие типы. В модель не входят:

- **User и DM-кандидаты** — их идентичность проектируется отдельной моделью, вне
  этого документа;
- прикладные метрики канала (охват, число подписчиков, перцентили активности);
- право записи в канал/чат;
- отслеживание постов и анализ контента;
- статусные таймеры и жизненный цикл прикладных состояний.

## 3. Доменная модель

Термины Telegram (MTProto) в объёме, необходимом для модели идентичности peer.
Источник — внешняя документация Telegram/MTProto (см. раздел 9), не код проекта.

| Термин | Что это |
|---|---|
| **Peer** | Всё, с чем можно вести диалог. Три типа: User, Chat (basic group), Channel. |
| **User** | Обычный пользователь или бот. Агент-аккаунты платформы — это User. |
| **Chat (basic group)** | «Базовая» группа до ~200 участников, без админ-инструментов. Обращение по одному `id`, `access_hash` не требуется. |
| **Channel** | Один тип сущности `channel`, различается флагами: `broadcast=true` — канал (вещание, пишут только админы); `megagroup=true` — супергруппа. Обращение требует `id` + `access_hash`. |
| **Супергруппа-обсуждение (linked chat)** | Комментарии под постами broadcast-канала — это привязанная к нему супергруппа. Канал и его обсуждение — **разные сущности** со своими идентификаторами; связь между ними стабильна. |
| **`id` (внутренний)** | Числовой идентификатор сущности. Диапазоны у разных типов пересекаются, поэтому `id` без указания типа неоднозначен. |
| **Marked id (Bot API id)** | `id` с закодированным типом: User — положительный; Chat — `-id`; Channel/супергруппа — префикс `-100…`. Снимает неоднозначность. Глобальный и постоянный. |
| **`access_hash`** | «Пропуск» к сущности; обязателен в паре с `id` для обращения к Channel. Привязан к аккаунту и к авторизации; между аккаунтами и авторизациями непереносим. |
| **`username` (`@name`)** | Публичный изменяемый алиас. Разрешается в `id`. Как строгий идентификатор не годится: изменяем на стороне Telegram, может сменить владельца. |

### Жизненный цикл сведений о peer

| Сведение | Область уникальности | Стабильность |
|---|---|---|
| Marked `id` | глобальная | Постоянный. Переживает переавторизацию, смену аккаунта, смену `username`. |
| Тип peer (User / Chat / Channel; для Channel — broadcast или megagroup) | — | Постоянный, за исключением миграции basic group → супергруппа (см. ниже). |
| `username` | глобальная | Изменяем на стороне Telegram; может смениться или отвязаться. |
| Связь broadcast-канал ↔ супергруппа-обсуждение | глобальная | Стабильная. |
| `access_hash` | per-account, per-authorization | Действителен только в рамках текущей авторизации аккаунта. При новой авторизации или на другом аккаунте недействителен. |

### Миграция basic group → супергруппа

Когда basic group упирается в лимит участников, требует публичной ссылки,
истории для новых участников или гранулярной модерации, Telegram конвертирует её
в супергруппу. При этом идентификатор **меняется** (сущность была `chat`,
становится `channel`): прежняя сущность помечается недействительной, а связь
указывает на новую сущность-супергруппу. Для платформы это означает: один и тот
же по смыслу чат меняет идентификатор и тип.

## 4. Ограничения среды

Внешние факты, значимые для любого варианта решения (из доменной модели, раздел 3):

- **О1.** Обращение к Channel (каналу или супергруппе) невозможно без пары
  `id` + `access_hash`.
- **О2.** `access_hash` действителен только в пределах одной авторизации
  (одной `sessionString`) конкретного аккаунта. Он не переносится на новую
  авторизацию того же аккаунта и не переносится на другой аккаунт.
- **О3.** Marked `id`, тип peer, `username` и связь канал ↔ обсуждение —
  глобальны и не зависят от того, какой аккаунт и какая авторизация обращаются к
  peer. `username` при этом может измениться на стороне Telegram.
- **О4.** Обращение к basic group (`Chat`) выполняется по одному `id`;
  `access_hash` для неё не существует и не требуется.
- **О5.** Миграция basic group в супергруппу меняет идентификатор и тип peer;
  прежняя сущность становится недействительной.

## Логическая модель данных

Что платформа хранит о peer — на логическом уровне (сущности, атрибуты, связи,
жизненный цикл каждого атрибута). Отличие от §3: §3 описывает внешние термины
Telegram, а этот раздел — состав данных самой платформы, выведенный из требований
R1–R6. Уровень логический: без физической схемы, имён колонок, типов и индексов.

### Сущность: Peer

Канал или чат, с которым работает агент.

| Атрибут | Что это | Жизненный цикл |
|---|---|---|
| Идентификатор (стабильный, ключ) | Стабильный идентификатор сущности; переживает переавторизацию и смену аккаунта (R1). | Создаётся при первом появлении/вступлении. Не инвалидируется, кроме миграции типа (см. ниже). |
| Закрепление за агентом (стабильное) | За каким агентом закреплён peer (множество peer, за которые агент отвечает). Ведётся отдельно от per-account сведений; переживает замену аккаунта (R1, AC-3). | Создаётся при закреплении peer за агентом. Не инвалидируется сменой аккаунта. |
| Тип peer | broadcast-канал / супергруппа-megagroup / basic group. Определяет, нужен ли access-credential (R4, R5). | Создаётся вместе с peer, стабилен. Меняется только при миграции basic group → супергруппа. |
| Публичный username | Публичный алиас; необязателен. | Создаётся при появлении. Обновляется, если изменён на стороне Telegram. Может отсутствовать/отвязаться. |
| Отображаемое название | Название peer для отображения. | Создаётся при появлении. Обновляется при изменении на стороне Telegram. |
| Access-credential | В терминах §3 — `access_hash`; «пропуск» к сущности. Есть у Channel-типов, отсутствует у basic group (R5, О4). | Создаётся при получении в рамках текущей авторизации. Обновляется при переполучении (R4). Недействителен, если относится к прошлой авторизации (R2, R3). |
| Провенанс access-credential | Сведения, позволяющие определить, относится ли access-credential к текущей авторизации агента (актуальность credential относительно момента авторизации). Логический атрибут, механизм сравнения не фиксируется (R2, R3). | Создаётся/обновляется вместе с access-credential. Используется, чтобы признать credential действительным или недействительным. |
| Связь с broadcast-каналом | Для супергруппы-обсуждения — ссылка на её broadcast-канал (R1). | Создаётся при выявлении связи, стабильна. |
| Access-credential привязанного канала | Access-credential broadcast-канала, к которому привязана супергруппа-обсуждение. Подчиняется тем же правилам актуальности, что и собственный access-credential (R2–R4). | Как у access-credential. |
| Состояние членства (per-account) | Членство КОНКРЕТНОГО аккаунта агента в peer: участник / вышел / забанен / не найден. Ведётся per-account, не переносится при замене аккаунта (AC-3). | Создаётся при первом появлении. Меняется по событиям join / leave / ban / исчезновения из диалогов. При замене аккаунта у нового аккаунта членство отсутствует, пока он не вступит повторно. |

### Сущность: Авторизация агента

Логический факт — момент установления текущей авторизации (текущей сессии)
агента, относительно которого оценивается актуальность access-credential (R2, R3).
Фиксируется только как факт данных; где и как он хранится — вне логической модели.

| Атрибут | Что это | Жизненный цикл |
|---|---|---|
| Момент текущей авторизации | Точка отсчёта, относительно которой access-credential считается действительным или относящимся к прошлой авторизации. | Создаётся/обновляется при каждой новой авторизации агента (новая `sessionString`). |

### Связи

- **Супергруппа-обсуждение ↔ broadcast-канал** — 1:1, стабильная. Супергруппа-
  обсуждение ссылается ровно на один broadcast-канал; broadcast-канал имеет не
  более одной привязанной супергруппы-обсуждения.
- **Peer → Авторизация агента** — актуальность access-credential каждого Peer
  оценивается относительно текущей авторизации агента.

### Жизненный цикл (сводно)

- **Стабильные атрибуты** (идентификатор, тип, связь с broadcast-каналом,
  закрепление за агентом): создаются при первом появлении/вступлении, не
  инвалидируются, переживают замену аккаунта. Исключение — тип и идентификатор
  при миграции basic group → супергруппа (R6): прежняя сущность становится
  недействительной, преемственность сохраняется через связь со новой супергруппой.
- **Изменяемые атрибуты** (username, отображаемое название): создаются при
  появлении, обновляются вслед за изменениями на стороне Telegram.
- **Per-account атрибуты** (access-credential и credential привязанного канала,
  провенанс credential, состояние членства): относятся к конкретному аккаунту
  агента и его текущей авторизации, не переносятся при замене аккаунта.
  Access-credential создаётся при получении в текущей авторизации, обновляется при
  переполучении, становится недействительным, если относится к прошлой авторизации.
  Состояние членства меняется по событиям join / leave / ban / исчезновения из
  диалогов; после замены аккаунта у нового аккаунта членство отсутствует, пока он
  не вступит повторно в закреплённые за агентом peer.

Физическая схема и миграция текущей БД — в architecture.md.

## 6. User Stories

US-1 (R1). Как оператор платформы, я хочу, чтобы платформа постоянно помнила
стабильные сведения о каждом известном канале и чате (маркированный
идентификатор, тип, публичный `username`, связь канал ↔ обсуждение, закрепление
peer за агентом), чтобы находить нужный peer и знать, за каким агентом он
закреплён, независимо от переавторизации агента и замены аккаунта.

US-2 (R2, R3). Как агент, я хочу, чтобы после новой авторизации платформа не
использовала `access_hash`, полученный в прошлой авторизации, чтобы не обращаться
к peer по недействительному пропуску и не ломать операцию.

US-3 (R4). Как агент, я хочу, чтобы при отсутствии действительного `access_hash`
платформа переполучала его в рамках текущей авторизации перед операцией, чтобы
join / read / leave выполнялись корректно после переавторизации и замены
аккаунта.

US-4 (R5). Как агент, я хочу полноценно вступать в basic group, читать в ней и
выходить из неё по одному идентификатору без `access_hash`, чтобы работать с
такими группами наравне с каналами и супергруппами.

US-5 (R6). Как оператор платформы, я хочу, чтобы при миграции basic group в
супергруппу платформа не теряла этот чат, чтобы агент продолжал работать с ним
после смены идентификатора.

## 7. Требования

**R1.** Система должна постоянно хранить стабильные сведения о каждом известном
peer: маркированный идентификатор, тип peer, публичный `username` (если есть),
связь broadcast-канал ↔ супергруппа-обсуждение, закрепление peer за агентом
(множество peer, за которые агент отвечает). Закрепление ведётся отдельно от
per-account сведений и переживает замену аккаунта.

**R2.** Пока сохранённый `access_hash` относится к прошлой авторизации агента
(получен до текущей `sessionString`), система должна считать его недействительным
и не использовать для обращения к peer.

**R3.** Когда агент проходит новую авторизацию (создаётся новая `sessionString`),
система должна прекратить использовать ранее сохранённые `access_hash` как
действительные.

**R4.** Когда требуется операция join / read / leave над Channel, а действительный
`access_hash` отсутствует, система должна заново получить `access_hash` в рамках
актуальной авторизации перед использованием. Идентификация нужного peer при этом
опирается на стабильные сведения (R1).

**R5.** Система должна поддерживать basic group как полноценный рабочий тип peer
наравне с Channel: выполнять над ней операции join / read / leave по
идентификатору, без `access_hash`.

**R6.** Когда basic group мигрирует в супергруппу со сменой идентификатора,
система не должна терять этот чат: она должна сохранить преемственность между
прежней сущностью и новой супергруппой и продолжить операции (R5 для basic group,
R4 для получившейся супергруппы).

## 8. Критерии приёмки

**AC-1.** После переавторизации агента (новая `sessionString`) операции
join / read / leave по ранее известному каналу выполняются успешно: стабильные
сведения о канале сохранены, а `access_hash` получен заново в текущей авторизации.

**AC-2.** `access_hash`, полученный до текущей авторизации агента, не
используется для обращения к peer.

**AC-3.** После замены Telegram-аккаунта агента закрепление каналов за агентом
(множество peer, за которые агент отвечает) сохранено; агент повторно вступает в
эти каналы и восстанавливает членство и доступ; сведения о членстве и доступе
прошлого аккаунта (`access_hash`) не используются. По завершении новый аккаунт
состоит в тех же закреплённых за агентом каналах, что и до замены.

**AC-4.** Операции join / read / leave над basic group выполняются успешно по
одному идентификатору, без `access_hash`.

**AC-5.** После миграции basic group в супергруппу чат остаётся доступен
платформе и не теряется, несмотря на смену идентификатора и типа; операции над
получившейся супергруппой продолжаются.
