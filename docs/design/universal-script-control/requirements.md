# Универсальное управление операторскими скриптами — требования

Design-doc (аналитика фичи). Только бизнес-способности и поведение (ЧТО и зачем).
Механизм исполнения вне процесса сервиса (HOW) — за архитектором, здесь не описывается.

Статус: требования согласованы с оператором на 2026-06-25. Открытые вопросы закрыты.

---

## 1. Контекст и проблема

Операторский скилл со скриптом сейчас исполняется **внутри процесса сервиса OpenClaw**
(гейтвея). Из-за этого жизнь скрипта привязана к состоянию гейтвея:

- При перезапуске или падении сервиса идущий прогон обрывается, а уже проделанная
  работа теряется. Реальный инцидент: прогон `discovery-similar` 24.06.2026 нашёл
  подходящие каналы, но они не попали в общий реестр, потому что сервис перезапустился
  до записи результата. Корень — скрипт копит находки в памяти и пишет их только во
  второй фазе из in-memory pool; до этого момента результат нигде не зафиксирован.
- Оператор не может остановить уже запущенный скрипт — приходится ждать, пока он сам
  завершится или умрёт вместе с сервисом.

Сегодня на платформе есть два способа запуска: (а) операторский скилл в OpenClaw —
исполняется в процессе сервиса; (б) скрипты планировщика ОС (диспетчер агентских задач,
сбор воронки) — исполняются отдельными процессами и отчитываются в Saved Messages.

**Цель.** Сделать запуск и остановку единообразными для всех операторских скриллов со
скриптом: скрипт исполняется вне процесса сервиса OpenClaw (его жизнь не зависит от
состояния гейтвея), а оператор управляет прогоном (запуск, просмотр, остановка) из чата.
Итог прогона приходит в Saved Messages — как уже делают диспетчер и сбор воронки.

**Охват.** Все операторские скрипты, которые сегодня исполняются в процессе сервиса:
`discovery-similar` (поиск похожих каналов), `channel-content-analysis` (анализ контента
топ-каналов), `channel-discovery` (поиск каналов через TGStat).

**Граница (вне объёма).**
- Задачи планировщика по расписанию (`monitor`, `dm-send`, `dm-replies`,
  `account-warmup`, `join-queue`, `leave-banned`) не меняются — они уже исполняются
  отдельными процессами.
- Конкретный механизм исполнения вне сервиса — HOW, оставлен архитектору.

## 1.5 Типы прогонов

По источнику запуска прогоны делятся на:

| Тип | Кто запускает | Механизм |
|---|---|---|
| Плановые | systemd-таймер | `tg-agent@{id}.timer` → диспетчер → скилл |
| Периодические платформенные | systemd-таймер | `tg-funnel-tracker.timer`, `tg-daily-summary.timer` → скрипт |
| Операторские | Оператор из чата | OpenClaw-инструмент → скрипт |

Эта фича затрагивает только **операторские прогоны**.

---

## 1.6 Контракт скрипта

Скрипт — единица работы внутри операторского прогона. Требования к его поведению:

1. **Результат.** По завершении (в любом исходе: штатное завершение, остановка оператором, непредвиденная ошибка) скрипт производит результат, достаточный для понимания того, что было сделано и что не получилось.

2. **Граница ответственности.** Скрипт отвечает только за свой результат. Доставка результата оператору — ответственность обработчика, не скрипта. Скрипт не взаимодействует с оператором напрямую в ходе работы.

3. **Реакция на остановку.** Скрипт способен получить сигнал остановки, завершить текущую единицу работы и сформировать частичный результат по тому, что успело выполниться.

4. **Прозрачность ошибки.** При непредвиденном сбое скрипт раскрывает информацию об ошибке в своём результате, а не теряет её.

## 2. User Stories (роль — оператор)

| ID | История | MoSCoW |
|---|---|---|
| US-1 | Запускать скилл со скриптом так, чтобы прогон жил независимо от сервиса OpenClaw — перезапуск/падение сервиса не обрывает идущую работу. | Must |
| US-2 | Сразу после запуска получить подтверждение с идентификатором прогона, не дожидаясь завершения в чате. | Must |
| US-3 | Получить понятный отказ, если такой скрипт уже выполняется, — чтобы не плодить дубли. | Must |
| US-4 | В любой момент видеть список выполняющихся операторских прогонов по всей платформе. | Must |
| US-5 | Остановить любой идущий операторский прогон из чата по идентификатору. | Must |
| US-6 | Получать итог прогона в Saved Messages по завершении (в т.ч. если сервис был недоступен в момент завершения). | Must |
| US-7 | При моей остановке получать в Saved Messages итог того, что успело собраться до остановки. | Must |
| US-8 | При аварийном падении скрипта получать в Saved Messages отчёт об ошибке с причиной. | Must |
| US-9 | Быть уверенным, что найденное по ходу прогона не теряется при остановке или сбое. | Must |

## 3. Acceptance Criteria (Given/When/Then)

### AC-1 — Внепроцессное исполнение (US-1)
- **Given** оператор запускает операторский скилл со скриптом, **When** скрипт стартует,
  **Then** он исполняется как самостоятельная работа, не как часть процесса сервиса OpenClaw.
- **Given** идёт прогон, **When** сервис OpenClaw перезапускается или падает, **Then**
  прогон продолжает выполняться и доходит до завершения.

### AC-2 — Неблокирующий запуск с идентификатором (US-2)
- **Given** оператор запустил скилл со скриптом, **When** прогон стартовал, **Then**
  оператор сразу получает в чате подтверждение с идентификатором прогона (= имя скилла).
- **Given** старт не состоялся, **When** оператор отправил команду запуска, **Then** он
  получает в чате понятное сообщение об отказе с причиной.

### AC-3 — Единственность прогона на скилл (US-3) [Q1]
- **Given** прогон скилла `X` уже выполняется, **When** оператор повторно запускает
  скилл `X`, **Then** запуск отклоняется с понятным сообщением, что прогон уже идёт
  (с идентификатором текущего прогона), новый прогон не создаётся.
- **Given** прогон скилла `X` завершился (любым образом), **When** оператор снова
  запускает `X`, **Then** запуск проходит штатно.

### AC-4 — Просмотр выполняющихся прогонов (US-4) [Q2, Q8]

**Статусная модель операторского прогона:**
- `running` — прогон выполняется
- `stopping` — получена команда остановки, идёт финализация (дописывает текущий шаг, отправляет итог)

- **Given** есть выполняющиеся операторские прогоны, **When** оператор запрашивает
  список, **Then** он видит **все** операторские прогоны по всей платформе (любого агента
  и не привязанные к агенту вовсе) со статусами `running` и `stopping`;
  по каждому — идентификатор (имя скилла), статус, время старта. Список **не** ограничен агентом.
- **Given** выполняющихся операторских прогонов нет, **When** оператор запрашивает
  список, **Then** он получает явный ответ «нет выполняющихся прогонов».
- **Given** в фоне работают задачи планировщика (диспетчер, сбор воронки), **When**
  оператор запрашивает список, **Then** они в списке **не** показываются (только
  операторские скрипты).

### AC-5 — Остановка любого прогона (US-5) [Q2, Q9]
- **Given** операторский прогон в статусе `running`, **When** любой оператор отдаёт команду
  остановки с его идентификатором, **Then** прогон переходит в статус `stopping`,
  запускается мягкая остановка (см. AC-6), и оператор получает подтверждение в чате.
  Право остановки не ограничено агентом или ролью.
- **Given** прогон в статусе `stopping`, **When** оператор повторно отдаёт команду остановки,
  **Then** он получает сообщение, что прогон уже останавливается.
- **Given** прогона с таким идентификатором среди выполняющихся нет, **When** оператор
  пытается его остановить, **Then** он получает понятное сообщение, что активного прогона нет.

### AC-6 — Мягкая остановка с фиксацией и итогом (US-7) [Q5, п.5-поправка]
- **Given** оператор остановил прогон, **When** прогон получает сигнал остановки, **Then**
  скрипту даётся момент дописать текущий шаг — зафиксировать уже собранное и отправить
  итог в Saved Messages, после чего прогон завершается.
- **Given** скрипт не завершился мягко в пределах предельного времени мягкого завершения
  (значение параметра — за архитектором), **When** это время истекло, **Then** прерывание
  становится жёстким.
- **Given** мягкая остановка прошла, **When** прогон завершился, **Then** в Saved Messages
  приходит сообщение с итогом того, что успело собраться до остановки (не пустое
  «прогон прерван»).

### AC-7 — Итог по завершении в Saved Messages (US-6) [Q7]
- **Given** прогон дошёл до естественного завершения, **When** работа окончена, **Then**
  итог приходит в Saved Messages обработчикам скрипта в том же формате отчёта, что у
  диспетчера и сбора воронки.
- **Given** сервис OpenClaw был недоступен в момент завершения прогона, **When** прогон
  завершился, **Then** итог всё равно доставляется в Saved Messages обработчикам скрипта
  (скрипт отправляет отчёт самостоятельно, независимо от состояния гейтвея).

### AC-8 — Отчёт об аварийном падении скрипта (US-8) [Q6]
- **Given** скрипт прогона аварийно завершился сам (ошибка скрипта, не остановка
  оператором и не падение сервиса), **When** прогон оборвался, **Then** в Saved Messages
  обработчикам скрипта приходит отчёт со статусом **error** и текстом исключения.

## 4. ТЗ-резюме (что поведение должно делать)

1. **Внепроцессность.** Скрипт операторского скилла исполняется как самостоятельная
   работа вне жизненного цикла сервиса OpenClaw; перезапуск/падение сервиса не прерывает
   прогон.
2. **Неблокирующий запуск.** Команда запуска сразу возвращает идентификатор прогона; чат
   не блокируется до конца работы.
3. **Единственность по имени скилла.** Пока прогон скилла идёт, повторный запуск того же
   скилла отклоняется с понятным сообщением. Идентификатор прогона = имя скилла.
4. **Просмотр — общеплатформенный.** Список выполняющихся операторских прогонов по всей
   платформе, не ограниченный агентом; задачи планировщика в него не входят.
5. **Остановка — общеплатформенная, мягкая.** Любой оператор останавливает любой
   операторский прогон по идентификатору. Остановка мягкая: скрипт дописывает текущий
   шаг, фиксирует собранное и шлёт итог в Saved Messages, затем завершается; по истечении
   предельного времени мягкого завершения (параметр, значение за архитектором) —
   жёсткое прерывание.
6. **Доставка итога в Saved Messages** — в едином формате с диспетчером и сбором воронки:
   при естественном завершении, при ручной остановке (итог частичного сбора) и при
   аварийном падении (статус error + причина). Доставка гарантируется даже если сервис
   был недоступен в момент завершения прогона.
7. **Инкрементальная сохранность.** Результаты становятся durable по мере получения, а не
   одной записью в финале.

**Допущения и ограничения (зафиксированы, не решаются в этом документе):**
- **Права на остановку.** Возможность остановить прогон зависит от прав сервиса OpenClaw
  на управление внешней работой. Недостаточно прав — способность «остановить» ограничена;
  решение за архитектором.
- **Без ролей (Q9).** Любой оператор управляет любым прогоном; ролей и ограничений
  доступа нет.
- **Контракты не трогаем.** Статус-модель скиллов и таблица прогонов в рамках этой
  способности не пересматриваются (на статус-модель завязаны скиллы планировщика —
  менять только отдельно и с согласованием).
