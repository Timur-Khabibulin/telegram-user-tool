# Универсальное управление операторскими скриптами — архитектура

Design-doc (HOW). Источник требований (ЧТО) — [requirements.md](requirements.md),
требования согласованы с оператором на 2026-06-25. Здесь проектируется механизм
внепроцессного исполнения, просмотра и остановки операторских скриптов.

Статус: предложение архитектора, ожидает утверждения. Прикладной код не написан.

Флаги systemd в документе подтверждены по официальной документации (systemd
TRANSIENT-SETTINGS, манпейджи `systemd-run(1)` / `systemctl(1)`), а не по памяти —
ссылки в разделе «Источники».

---

## 1. Резюме рекомендации

Перевести три операторских скрипта (`discovery-similar`, `channel-content-analysis`,
`channel-discovery`) с исполнения **внутри процесса гейтвея** на исполнение
**отдельными процессами под управлением systemd** — по образцу уже существующих
standalone-скриптов (`dispatcher.ts`, `funnel-tracker.ts`).

Рекомендуемый механизм запуска — **транзиентные юниты `systemd-run`** (Вариант A):
гейтвей не исполняет логику, а лишь формирует команду запуска отдельного процесса с
детерминированным именем юнита `tg-script-<имя>.service`. Имя юнита = естественный
мьютекс (единственность прогона, AC-3), общий префикс даёт бесплатный список
(`systemctl list-units 'tg-script-*'`, AC-4) и остановку (`systemctl stop`, AC-5).
Мягкая остановка — штатная связка systemd `SIGTERM → (TimeoutStopSec) → SIGKILL`
(AC-6). Отчёт в Saved Messages шлёт сам процесс скрипта в едином формате с
диспетчером (AC-7/AC-8), независимо от состояния гейтвея (AC-1).

Инкрементальная сохранность (AC-9) для `discovery-similar` решается **отдельно от
механизма запуска**: двухфазная модель (накопить пул в памяти → записать в финале)
сворачивается в одну фазу — каждый прошедший гейты канал закрепляется в реестре и
ставится в очередь немедленно (`registerChannel` уже идемпотентен).

Гейтвей работает от root (подтверждено `openclaw.service` в operation.md и
`User=root` в юнитах) — прав на `systemd-run`/`systemctl` достаточно.

## 2. Выбранный вариант и обоснование

### 2.1 Сравнение механизмов

| Критерий | A. `systemd-run` (транзиентный юнит) | B. Шаблонный юнит `tg-script@<имя>.service` | C. `spawn` detached + PID-файл |
|---|---|---|---|
| Внепроцессность (AC-1) | да: процесс ведёт systemd | да: процесс ведёт systemd | да, но «сирота» без супервизора |
| Неблокирующий старт (AC-2) | да: `systemd-run` стартует асинхронно и возвращается | да: `systemctl start` возвращается сразу | да |
| Единственность по имени (AC-3) | имя юнита `--unit=` — естественный лок; повторный старт → ошибка «уже существует» | `%i`-инстанс — естественный лок | свой lock-файл: гонки, протухшие PID |
| Передача параметров прогона | в `ExecStart` инлайном при запуске — хранилище не нужно | `%i` несёт только имя; параметры — из внешнего хранилища (env-файл/таблица) | в argv процесса |
| Просмотр списка (AC-4) | `systemctl list-units 'tg-script-*' --state=running` | то же | обход каталога PID-файлов + проверка живости каждого PID |
| Мягкая остановка (AC-6) | `-p TimeoutStopSec=` + `-p KillSignal=` транзиентно | те же свойства в unit-файле | `kill -TERM`, таймер на `kill -KILL` руками |
| Доставка отчёта (AC-7/8) | скрипт шлёт сам | скрипт шлёт сам | скрипт шлёт сам |
| Ресурсные лимиты | `--slice=tg-agents.slice` (переиспользуем) | `Slice=` в unit-файле | вне slice, без лимитов |
| Новые файлы деплоя | нет (юнит транзиентный) | новый `tg-script@.service` в `deploy/systemd/` | нет |
| Совместимость с текущим кодом | как `scheduler-control.ts`: тонкий гейтвей → `execFile(systemctl/systemd-run)` | как `scheduler-control.ts` | свой код супервизии |
| Главный минус | команда запуска длиннее (параметры инлайном) | параметрам нужен **внешний store** — лишняя сущность | ручная супервизия: гонки, протухшие локи, нет лимитов |

### 2.2 Почему A

Решающее отличие A от B — **передача параметров прогона**. Операторские скрипты
принимают богатый типизированный ввод (`discovery-similar`: `minSubscribers`,
`target`, `agents`, `theme`, `minAvgViews`, `minTopicScore`, `postsCount`,
`minEngagementRate`; `channel-content-analysis`: `agents`, `n`, `m`). Шаблонный юнит
(Вариант B) умеет нести через `%i` только одну строку — имя скилла. Чтобы донести
параметры до процесса, B вынужден завести **внешнее хранилище** (env-файл на прогон
или таблицу `script_runs(skill, params_json)`), которое скрипт читает на старте. Это
прямо нарушает принцип простоты из `agent-playbook.md` (не плодить таблицы и
абстракции) и вдобавок задевает «контракты не трогаем» из требований (статус-модель и
таблица прогонов в рамках этой способности не пересматриваются).

Вариант A формирует `ExecStart` с параметрами **инлайном в момент запуска** —
ровно там, где параметры уже есть (вызов инструмента гейтвея). Никакого хранилища
прогонов: транзиентный юнит сам несёт точную команду. Это минимальное решение,
повторяющее установившийся в проекте паттерн «тонкий инструмент гейтвея → системный
механизм через `execFile`» (`scheduler-control.ts`).

Вариант C (ручной `spawn` + PID-файл) отвергнут: воспроизводит то, что systemd уже
даёт из коробки (супервизия, единственность через имя, списки, остановка по сигналам
с таймаутом, ресурсные slice), и привносит классические грабли — гонки на lock-файле,
протухшие PID, процессы вне ресурсных лимитов.

## 3. Компоненты и поток

### 3.1 Новые и изменяемые компоненты

| Компонент | Расположение | Роль |
|---|---|---|
| Пульт скриптов | `src/core/script-control.ts` (новый) | тонкие обёртки `startScript` / `listRunningScripts` / `stopScript` над `systemd-run`/`systemctl` через `execFileAsync`. Аналог `scheduler-control.ts`, без зависимости от OpenClaw |
| Точки входа скриптов | `src/scripts/ops/discovery-similar.ts`, `channel-analysis.ts`, `channel-discovery.ts` (новые) | standalone-`main`: разбор argv → вызов core-`run*` → отчёт в Saved Messages → exit. Образец — `funnel-tracker.ts`/`dispatcher.ts` |
| Общий рендер отчёта/ошибки | `src/core/script-report.ts` (новый, вынести из `dispatcher.ts`) | единый формат `formatReport`/`extractError` для диспетчера и операторских скриптов (AC-7/8 «в том же формате») |
| Кооперативная отмена | сигнатуры core-`run*` (`similar.ts` и др.) | приём токена отмены, проверка в точках цикла и в паузах `pacingMs` (AC-6) |
| Инструменты гейтвея | `index.ts` | существующие `tg_discovery_similar_run` / `tg_channel_content_analysis` / `tg_discovery_run` становятся **тонкими лаунчерами** (вызывают `startScript`, сразу возвращают id). Добавляются `tg_scripts_running` (AC-4) и `tg_script_stop` (AC-5) |

Логика обхода/анализа (`src/features/discovery/*`, `src/features/channel-analysis/*`) **не
переписывается под новый запуск** — её вызывают новые точки входа вместо `run()`-обёртки
гейтвея. Меняется только то, что требует AC-9 (см. §5).

### 3.2 Идентификатор и имена

- Идентификатор прогона (показывается оператору, принимается в list/stop) = **имя
  скилла**: `discovery-similar`, `channel-content-analysis`, `channel-discovery`.
- Имя юнита = `tg-script-<имя>.service`. Один префикс `tg-script-` отделяет
  операторские прогоны от задач планировщика (`tg-agent@*`, `tg-funnel-tracker`,
  `tg-daily-summary`) — поэтому список и остановка их не задевают (AC-4: планировщик
  в список не входит).

### 3.3 Запуск (AC-1, AC-2, AC-3)

`startScript(name, args)` в `script-control.ts`:

1. Проверить единственность: `systemctl is-active --quiet tg-script-<name>.service`.
   Активен → вернуть отказ «прогон <name> уже идёт» (AC-3), новый не создавать.
2. Иначе запустить транзиентный юнит:

```
systemd-run
  --unit=tg-script-<name>.service          # детерминированное имя (лок + адресуемость)
  --collect                                 # выгрузить юнит после завершения (даже при ошибке)
  --slice=tg-agents.slice                   # те же CPUQuota/MemoryMax, что у агентов
  --working-directory=/root/openclaw-plugins/telegram-user-tool
  -p EnvironmentFile=-/root/.openclaw/codex-auth/.env   # тот же доступ к LLM
  -p TimeoutStopSec=<grace>                 # бюджет мягкой остановки (AC-6)
  -p KillSignal=SIGTERM                     # по умолчанию SIGTERM, фиксируем явно
  -p StandardOutput=journal -p StandardError=journal
  -- node_modules/.bin/tsx src/scripts/<entry>.ts <параметры прогона инлайном>
```

`systemd-run` стартует процесс асинхронно в фоне и возвращается сразу — чат не
блокируется (AC-2). Инструмент возвращает идентификатор `<name>` и статус «запущен».
Сбой запуска (юнит уже существует, нет прав и т.п.) `execFile` отдаёт как ошибку —
гейтвей превращает её в понятное сообщение об отказе (AC-2, вторая ветка).

Все флаги подтверждены как поддерживаемые для транзиентных сервисов: `--unit`,
`--collect`, `--working-directory`, `--slice`; свойства `EnvironmentFile=`,
`TimeoutStopSec=`, `KillSignal=`, `Slice=`, `StandardOutput=/StandardError=` —
в списке TRANSIENT-SETTINGS (см. «Источники»).

### 3.4 Просмотр (AC-4)

`listRunningScripts()`:

```
systemctl list-units 'tg-script-*.service' --state=running --no-legend --plain
# по каждому найденному юниту — время старта:
systemctl show <unit> -p ExecMainStartTimestamp --value
```

Глоб `tg-script-*` (fnmatch — подтверждено манпейджем `systemctl(1)`) ловит только
операторские прогоны по всей платформе, не ограничиваясь агентом: имя юнита не несёт
`agentId`. Задачи планировщика под другими префиксами в выборку не попадают. Пустая
выборка → инструмент отвечает «нет выполняющихся прогонов».

`systemctl list-units` не отдаёт JSON — парсим табличный `--no-legend --plain`,
старт берём отдельным `systemctl show -p ExecMainStartTimestamp` (надёжнее парсинга
человекочитаемой таблицы).

### 3.5 Остановка (AC-5, AC-6)

`stopScript(name)`:

1. `systemctl is-active --quiet tg-script-<name>.service` → если не активен, вернуть
   «активного прогона <name> нет» (AC-5, вторая ветка).
2. `systemctl stop tg-script-<name>.service` — systemd шлёт главному процессу
   `KillSignal` (SIGTERM), ждёт `TimeoutStopSec`, по истечении — SIGKILL.

Скрипт ставит обработчик `SIGTERM`, который **не убивает процесс**, а взводит флаг
отмены в общем токене. Логика обхода/анализа проверяет токен:

- на границах уровней BFS и между кандидатами;
- внутри отменяемой паузы `pacingMs` (sleep резолвится сразу при отмене).

Увидев отмену, скрипт прекращает сбор, переходит к финализации: уже найденное к этому
моменту **уже durable** (AC-9, §5), затем шлёт в Saved Messages итог по факту собранного
(не пустое «прервано», AC-6) и выходит с кодом 0 в пределах `TimeoutStopSec`. Если не
успел (например, застрял в долгом ожидании `FLOOD_WAIT`), systemd добивает SIGKILL —
данные не теряются благодаря инкрементальной записи, теряется лишь финальное сообщение.

**Бюджет мягкой остановки** задаётся одной константой `SCRIPT_STOP_GRACE_SEC` в
`script-control.ts` и прокидывается в `-p TimeoutStopSec=`. Предлагается **120 с**:
покрывает завершение текущего MTProto-шага плюс одну отправку отчёта в Saved Messages,
не растягивая `systemctl stop` надолго. Значение в одном месте — меняется без правки
скриптов.

### 3.6 Отчёт (AC-7, AC-8)

Отчёт шлёт **сам процесс скрипта** в конце работы — как `dispatcher.ts`/
`funnel-tracker.ts` (`tg.loadAccount(admin)` → `tg.sendSavedMessage(formatReport(...))`).
Поскольку процесс отдельный, доставка не зависит от того, жив ли гейтвей в момент
завершения (AC-7, вторая ветка). При аварии скрипта `main().catch` формирует отчёт
со статусом **error** и локализованной причиной через общий `extractError`/`formatError`
(AC-8) — единообразно с диспетчером.

### 3.7 ASCII-диаграмма потока

```
 Оператор (чат)            Гейтвей (root)                      systemd / процесс скрипта
 ─────────────            ──────────────                      ──────────────────────────
   "запусти X"  ───►  tg_*_run (тонкий)
                       startScript("X", args)
                         is-active? нет ──► systemd-run --unit=tg-script-X.service …
                                                      │  (старт асинхронный, фон)
                       ◄── id="X", "запущен"          ▼
   ◄── подтверждение                            [ процесс tsx src/scripts/X.ts ]
                                                   loadAccount(агент) → обход/анализ
                                                   находка → registerChannel+queue (durable)
   "что выполняется?" ─► tg_scripts_running                       │
                       list-units 'tg-script-*'                   │ (гейтвей может
   ◄── [X, старт 12:30]   --state=running                         │  перезапускаться —
                                                                  │  прогон не зависит)
   "останови X"  ───► tg_script_stop                              │
                       systemctl stop tg-script-X  ─SIGTERM─►  обработчик: флаг отмены
                       ◄── "остановка запущена"                   финализация: durable уже,
   ◄── подтверждение                                              отчёт ─► Saved Messages
                                              (TimeoutStopSec истёк ─SIGKILL─► выход)
                                              естественное завершение ─► отчёт ─► Saved Messages
```

## 4. Покрытие Acceptance Criteria

| AC | Как покрывается |
|---|---|
| **AC-1** внепроцессность | скрипт исполняется транзиентным юнитом под systemd; перезапуск/падение гейтвея не влияет на запущенный процесс |
| **AC-2** неблокирующий запуск + отказ | `systemd-run` стартует асинхронно, инструмент сразу возвращает id; ошибка `execFile` → понятное сообщение об отказе |
| **AC-3** единственность по имени | `--unit=tg-script-<name>.service` — лок; пре-проверка `is-active` даёт дружелюбный отказ с текущим id; `--collect` выгружает завершённый/упавший юнит, поэтому повторный запуск после завершения проходит |
| **AC-4** общеплатформенный список | `list-units 'tg-script-*' --state=running`; глоб без `agentId` → все прогоны; планировщик под другими префиксами исключён; пустая выборка → явный ответ |
| **AC-5** остановка любого | `tg_script_stop` → `systemctl stop <unit>`; нет активного юнита → понятное сообщение; прав root достаточно, ролей нет (Q9) |
| **AC-6** мягкая остановка | `SIGTERM` → флаг отмены → финализация (фиксация + итог) → выход; `TimeoutStopSec` (120 с) → `SIGKILL`; ранее собранное сохранено (AC-9) |
| **AC-7** итог по завершении | скрипт сам шлёт отчёт в Saved Messages общим `formatReport`; отдельный процесс → доставка не зависит от доступности гейтвея |
| **AC-8** отчёт об аварии | `main().catch` → отчёт status=error + причина через `extractError`/`formatError`, единообразно с диспетчером |
| **AC-9** сохранность по ходу | одно-фазная durable-запись каждой находки (см. §5) |

## 5. Инкрементальная сохранность для discovery-similar (AC-9)

### 5.1 Корень потери (текущее состояние кода)

`src/features/discovery/similar.ts` работает в две фазы:

- `collectByLevels` копит прошедшие гейты каналы в **in-memory `pool: string[]`**
  (без владельца) — на диск ничего не пишется;
- `distribute` (вызывается **только после** полного сбора) раскладывает пул
  round-robin и лишь тогда вызывает `registerChannel` + `addJoinQueue`.

Любой обрыв (перезапуск гейтвея, остановка, сбой) до фазы `distribute` теряет весь
пул — это и есть инцидент 24.06.2026.

### 5.2 Решение: свернуть две фазы в одну, писать на каждой находке

Назначать владельца и фиксировать канал **в момент прохождения всех гейтов**, внутри
обхода, а не в финале:

- ведём сквозной round-robin-индекс по `allAgents` и счётчики назначенного на агента;
- как только кандидат прошёл гейты — выбираем следующего агента, у которого добрано
  меньше `target`, и **сразу** `registerChannel(admin, canonical, agent)` +
  `addJoinQueue(agent, [canonical])`;
- обход останавливается, когда все агенты добрали по `target` (та же цель `target × N`).

`registerChannel` уже идемпотентен (`INSERT OR IGNORE` по `canonical_link` PK), а
`isKnownChannel` отсеивает известное **до** дорогих гейтов — поэтому повторный запуск
после обрыва естественно пропускает уже записанное и до-добирает остаток. Отдельная
функция `distribute` и in-memory `pool` исчезают; вместо пула — счётчики для отчёта.

### 5.3 Что это меняет и trade-off

- **Плюс:** каждая находка durable сразу; обрыв в любой момент не теряет ничего, что
  прошло гейты (AC-9, обе ветки).
- **Минус (осознанный):** при обрыве и повторном запуске распределение round-robin
  может оказаться чуть менее равномерным, чем за один непрерывный прогон (часть
  каналов уже закреплена). Требования просят durability и отсутствие потерь, а не
  идеально равномерную раскладку между перезапусками — допустимо.
- Семантика гейтов, FLOOD_WAIT-логики и приоритизации seeds не меняется.

### 5.4 Два других скрипта охвата

Принцип AC-9 — «результат durable по мере получения» — применяется и к ним, но детали
определяются **по их коду на этапе реализации** (здесь не выдумываем):

- `channel-content-analysis`: результат — CSV-артефакт. Durable по ходу = дописывать
  строки в файл CSV на диске по мере обработки каналов (а не собирать всю строку в
  памяти к финалу); финализация при остановке отправляет уже накопленный CSV.
- `channel-discovery` (TGStat): проверить, пишет ли он в реестр/очередь по каналу или
  тоже накапливает к финалу; при накоплении — применить тот же приём, что в §5.2.

Это отдельные задачи плана (§8), не блокирующие перенос запуска.

## 6. Изменения в деплое (systemd)

- **Новых unit-файлов для скриптов не требуется** — юниты транзиентные, их создаёт
  `systemd-run` в рантайме. `deploy/systemd/` не пополняется.
- Новые точки входа (`src/scripts/ops/discovery-similar.ts`, `channel-analysis.ts`,
  `channel-discovery.ts`) и `src/core/script-control.ts` едут на сервер вместе с `src/`
  обычным деплоем (`scp`/skill `vps`) — `daemon-reload` не нужен (юнитов не меняем).
- Переиспользуются: `tg-agents.slice` (ресурсные лимиты через `--slice=`),
  `EnvironmentFile=-/root/.openclaw/codex-auth/.env` (доступ к LLM),
  `WorkingDirectory=/root/openclaw-plugins/telegram-user-tool`.
- Требование к среде: на хосте доступен `systemd-run` (подтверждено в задаче), гейтвей
  работает от root (подтверждено `User=root`/`openclaw.service`).
- `operation.md` дополнить разделом про операторские прогоны: имена юнитов
  `tg-script-*`, команды просмотра/остановки, журнал (`journalctl -u tg-script-<name>`).

## 7. Риски и открытые вопросы

| # | Риск / вопрос | Влияние | Что делаем |
|---|---|---|---|
| R1 | Гейтвей под `User=openclaw` (а не root) | `systemd-run`/`systemctl stop` системных юнитов потребуют root/polkit-грантов — иначе способность «остановить/запустить» недоступна (зафиксировано в требованиях как ограничение) | сейчас гейтвей от root — работает; при миграции на `openclaw` завести polkit-правило на `start/stop tg-script-*` либо `--user`-инстанс systemd. Документировать |
| R2 | SIGTERM не прерывает текущий `await` (долгий `FLOOD_WAIT`-sleep) | финальный отчёт при остановке может не уйти до SIGKILL | данные durable (AC-9) — теряется только итог-сообщение; снижаем риск отменяемым `sleep`, проверяющим токен |
| R3 | `TimeoutStopSec=120` подобран без замера на бою | слишком мало — жёсткое прерывание раньше финализации; слишком много — `stop` висит | вынесено в одну константу `SCRIPT_STOP_GRACE_SEC`; калибровать по логам, дефолт 120 с |
| R4 | Разные скрипты на одном агенте параллельно | `discovery-similar` и `channel-content-analysis` оба грузят сессии агентов; единственность — по имени скилла, не по агенту → два разных скрипта могут одновременно открыть одну сессию | вне объёма требований (уникальность per-skill). Зафиксировать как известное ограничение; при необходимости позже — лок на агента |
| R5 | `list-units` без JSON, парсинг таблицы | хрупкость к формату вывода | `--no-legend --plain` стабилизирует вывод; старт берём отдельным `systemctl show -p ExecMainStartTimestamp` |
| Q1 | Сохранять ли строку операторского прогона в `runs`? | требования просят «контракты не трогаем»; `runs`-таблица — для скиллов планировщика | по умолчанию **не** писать в `runs`; отчёт — только в Saved Messages. Подтвердить с оператором |

## 8. Крупноблочный план задач

1. **Общий рендер отчёта.** Вынести `formatReport`/`extractError`/`renderDetails` из
   `dispatcher.ts` в `src/core/script-report.ts`; диспетчер начинает использовать общий
   модуль (поведение не меняется).
2. **Пульт скриптов.** `src/core/script-control.ts`: `startScript` (с пре-проверкой
   единственности и сборкой команды `systemd-run`), `listRunningScripts`, `stopScript`;
   реестр `имя скилла → точка входа`; константа `SCRIPT_STOP_GRACE_SEC`.
3. **Кооперативная отмена.** Ввести токен отмены и отменяемый `sleep`; протянуть проверки
   в `discovery/similar.ts` (границы уровней, между кандидатами, в паузах) и в остальные
   охватываемые скрипты.
4. **Инкрементальная сохранность discovery-similar.** Свернуть `collectByLevels` +
   `distribute` в одну фазу с durable-записью на каждой находке (§5.2); удалить
   in-memory-пул как носитель результата.
5. **Точки входа скриптов.** `src/scripts/ops/discovery-similar.ts`, `channel-analysis.ts`,
   `channel-discovery.ts`: разбор argv, обработчик SIGTERM → отмена, вызов core-`run*`,
   отчёт в Saved Messages, error-отчёт в `catch`, корректный exit.
6. **Тонкие лаунчеры в гейтвее.** Переключить `tg_discovery_similar_run`,
   `tg_channel_content_analysis`, `tg_discovery_run` с инлайн-исполнения на `startScript`
   (сразу возвращают id). Добавить `tg_scripts_running` (AC-4) и `tg_script_stop` (AC-5).
7. **Durable по ходу для двух других скриптов.** По их коду применить принцип AC-9:
   CSV-инкремент для `channel-content-analysis`; per-channel запись для `channel-discovery`
   (§5.4).
8. **Документация.** `operation.md` — раздел про операторские прогоны (юниты `tg-script-*`,
   просмотр/остановка/журнал); `architecture.md` — `script-control` и новые точки входа.
