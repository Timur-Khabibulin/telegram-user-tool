# Требования: Мультиперсонность в распределении каналов — v1

> **О чём документ.** Проблема, доменная модель, цель, требования и критерии
> приёмки уровня бизнес-аналитики (что и почему). Техническое решение (раскладка
> по таблицам, миграции, механика water-fill) — задача архитектора, в парном
> `architecture.md`, сюда не входит.

## 1. Проблема и контекст

Платформа запускает Telegram-агентов; агент — один Telegram-аккаунт, у которого в конфиге задано поле `persona` (имя шаблона персоны). Ранее персона фактически была одна, и в общем реестре найденных каналов (одна БД на админ-агента) действовал инвариант **«один канал — один агент на всю платформу»**: канал уникален глобально и закреплён ровно за одним агентом.

С появлением нескольких персон этот инвариант неверен. Один и тот же канал допустимо прорабатывать агентами разных персон одновременно — это разные «лица», не конкурирующие между собой. Глобальная уникальность канала при этом:
- блокирует назначение канала агенту другой персоны, если канал уже занят в первой;
- при ротации переносит канал между агентами без учёта персоны;
- в отчёте оперирует устаревшей сущностью «пул».

Затронуты способности: channel-discovery, channel-distribution, channel-rotation, redistribute, funnel-report.

## 2. Цель

1. Заменить глобальный инвариант канала на **«один канал — один агент в рамках персоны»**: у агентов разных персон каналы могут совпадать, у агентов одной персоны — нет.
2. Сделать **персону единицей таргетинга** для дискавери, распределения и ротации: любой прогон идёт в рамках одной персоны, платформа сама выбирает активных агентов этой персоны и балансирует нагрузку между ними.
3. Привести отчётность и вспомогательные способности в соответствие: колонка «персона» вместо «пул»; депрекейт устаревшей «пул»-механики и similar-дискавери (отдельной под-задачей, см. раздел 5).
4. Перенести существующие данные так, чтобы текущие закрепления сохранили смысл в новой модели.

## 3. Доменная модель

| Термин | Что это |
|---|---|
| Агент | Один Telegram-аккаунт со своей персоной, работающий от своего имени через MTProto. |
| Персона | Значение поля `persona` в конфиге агента (имя шаблона персоны). Два агента с одинаковым значением `persona` = одна персона; с разными значениями = разные персоны. Персона — единица группировки агентов для всех операций с каналами. |
| Активный агент персоны | Агент, который пригоден быть целью назначения/ротации по **существующему критерию пригодности** (тот же, что и раньше; нового критерия не вводится) **и** принадлежит целевой персоне. То есть к прежнему критерию активности добавляется только фильтрация по персоне: среди активных агентов рассматриваются лишь принадлежащие целевой персоне. |
| Канал | Telegram-канал, найденный или переданный на проработку. Идентифицируется глобально. |
| Реестр каналов | Общий на админ-агента перечень известных каналов и их закреплений за персонами. |
| Закрепление (за персоной) | Факт «канал принадлежит персоне». Существует **в разрезе персоны**: один и тот же канал может иметь независимые закрепления в нескольких персонах. **Принадлежность канала персоне сохраняется всегда**, пока канал в проработке этой персоны. |
| Агентский слот закрепления | Внутри закрепления канала за персоной — привязка к конкретному агенту этой персоны. В рамках одной персоны у канала не более одного агентского слота. Слот **может быть пустым** (агент отсутствует) — например, когда прежний агент забанен, до момента ротации; при этом само закрепление канала за персоной не теряется. Физическое представление пустого слота (nullable-агент и т.п.) — задача архитектора. |
| Прогон | Однократное исполнение способности (дискавери / распределение / ротация). Всегда выполняется в рамках ровно одной персоны. |

Диаграмма не требуется: фича описывается инвариантом и правилами разреза по персоне, порядок действий между акторами при этом не является частью бизнес-правила.

## 4. Ограничения среды

1. Telegram не запрещает нескольким аккаунтам (агентам) состоять в одном и том же канале — совпадение каналов у агентов разных персон технически допустимо.
2. Каждый агент имеет ровно одно значение `persona` в конфиге; персона агента всегда определима.
3. Реестр каналов — один на админ-агента; операции разных персон работают с одним и тем же реестром.
4. На момент перехода на новую модель все каналы в реестре принадлежат единственной персоне `maria`; каналов без владельца на практике нет.

## 5. Вне рамок (out of scope)

- **Депрекейт «пул»-механики (`agent_pools`) и similar-дискавери** — выполняется отдельной под-задачей. similar-дискавери и связанная «пул»-механика **не переводятся** на мультиперсонность, а помечаются как устаревшие. В депрекейт-пометке проставляется дата последнего изменения соответствующего кода, чтобы было видно, какие правки в них не вошли.
- **Смена значения `persona` у существующего агента в дальнейшей эксплуатации** — поведение при изменении поля `persona` у уже работающего агента (что происходит с его закреплениями) в этой фиче не рассматривается.
- Проектирование схемы БД, миграций, алгоритма water-fill и раскладки закреплений по таблицам — задача архитектора.
- Изменение критерия «активности/пригодности» агента как цели — используется существующий.

## 6. User Stories

**US-1 (R1, R4).** Как оператор, я хочу, чтобы при дискавери и первом распределении канал считался «уже занятым» только внутри целевой персоны, чтобы канал, проработанный другой персоной, всё равно попадал в работу к нужной персоне.

**US-2 (R2, R3).** Как оператор, я хочу задавать цель распределения именем персоны, а не списком агентов, чтобы не смешивать агентов разных персон в одном прогоне и не распределять каналы вручную по агентам.

**US-3 (R5).** Как платформа, я хочу при уходе канала из-за бана заполнять пустой агентский слот другим активным агентом той же персоны, чтобы канал оставался в проработке своей персоны и не «перетекал» в чужую.

**US-4 (R6).** Как платформа, я хочу считать стартовую нагрузку для балансировки в рамках персоны, чтобы каналы распределялись между агентами одной персоны равномерно и предсказуемо.

**US-5 (R7).** Как платформа, я хочу при очистке канала у агента снимать только его закрепление в рамках его персоны, чтобы не затронуть назначения того же канала в других персонах.

**US-6 (R8).** Как оператор, я хочу видеть в ежедневном отчёте по агентам колонку «персона» вместо «пул», чтобы соотносить агентов с актуальной сущностью группировки.

**US-7 (R9).** Как платформа, я хочу получать полный список каналов реестра без фильтрации по персоне, чтобы операции над всем реестром (например, обслуживание метаданных) видели каждый канал один раз независимо от числа персон.

**US-8 (R10).** Как оператор, я хочу, чтобы существующие закрепления при переходе на новую модель сохранились с корректной персоной, чтобы не потерять текущее распределение каналов.

**US-9 (R3, R11).** Как оператор, я хочу выполнять принудительное перераспределение по готовому списку в рамках персоны (без пинов на конкретного агента), чтобы одним механизмом покрывать и первичное, и повторное распределение.

## 7. Требования

| # | Требование |
|---|---|
| **R1** | Система должна допускать не более одного агентского слота канала в рамках одной персоны и одновременно допускать независимые закрепления того же канала в разных персонах. |
| **R2** | Любой прогон дискавери, распределения или ротации система должна выполнять в рамках ровно одной персоны. Смешивание агентов разных персон в одном прогоне не допускается. |
| **R3** | Единицей таргетинга для распределения (distribution), принудительного перераспределения (redistribute) и запросов через админ-бот система должна принимать имя персоны. По имени персоны система сама выбирает её активных агентов и распределяет каналы между ними. Указание конкретного агента как цели не поддерживается. |
| **R4** | При дискавери и первом распределении проверку «канал уже закреплён» система должна выполнять в рамках целевой персоны. Канал, закреплённый в другой персоне, является валидным кандидатом для целевой персоны. |
| **R5** | Когда канал покинут из-за бана агентом персоны P, агентский слот канала в персоне P становится пустым, при этом принадлежность канала персоне P сохраняется. Система должна заполнить пустой слот другим активным агентом персоны P, когда он доступен. Если доступного активного агента в персоне P нет, слот остаётся пустым, а канал по-прежнему принадлежит персоне P; канал не переносится в другую персону. Если один и тот же канал покинут из-за бана сразу в нескольких персонах, он подлежит независимой ротации в каждой из них; принадлежность канала каждой из этих персон сохраняется. |
| **R6** | При балансировке (water-fill) система должна считать стартовую нагрузку агентов в рамках персоны, для которой выполняется прогон. |
| **R7** | При очистке канала у агента система должна удалять только закрепление этого канала в рамках его персоны и не изменять закрепления того же канала в других персонах. |
| **R8** | В ежедневном отчёте по агентам система должна выводить колонку «персона» вместо колонки «пул». |
| **R9** | Система должна предоставлять список всех каналов реестра без фильтрации по персоне, при котором каждый канал присутствует один раз независимо от количества его закреплений в разных персонах. |
| **R10** | При миграции существующих данных система должна перенести каждое действующее закрепление, проставив персону `maria` (единственную персону реестра на момент перехода). |
| **R11** | redistribute сливается с distribution: принудительное перераспределение система должна выполнять по имени персоны теми же правилами дедупа (R4) и балансировки (R6), что и распределение. Возможность закрепить канал за конкретным агентом убирается. |
| **R12** | Если у целевой персоны нет ни одного активного агента, прогон распределения/перераспределения/дискавери система должна отклонить с сообщением («в персоне нет активных агентов») до обработки входа, не выполняя пустой прогон и не теряя каналы молча. Указание несуществующей персоны система также должна отклонять с сообщением. |

## 8. Критерии приёмки

**AC-1 (US-1, R4) — канал занят в другой персоне.**
Дано: канал C закреплён за агентом персоны Б; запускается дискавери/распределение для персоны А, C входит во вход.
Когда: прогон обрабатывает C.
Тогда: C рассматривается как валидный кандидат для персоны А и может быть закреплён за активным агентом персоны А; закрепление C в персоне Б не изменяется.

**AC-2 (US-1, R4) — канал уже занят внутри целевой персоны.**
Дано: канал C уже закреплён за агентом персоны А; запускается прогон для персоны А, C входит во вход.
Когда: прогон обрабатывает C.
Тогда: C не создаёт второго агентского слота в персоне А (дедуп в рамках персоны).

**AC-3 (US-2, R2, R3) — таргетинг только по персоне.**
Дано: оператор задаёт распределение/перераспределение.
Когда: цель прогона указывается.
Тогда: цель принимается как имя персоны; платформа сама подбирает активных агентов этой персоны; способа указать конкретного агента или смешать агентов разных персон в одном прогоне нет.

**AC-4 (US-3, R5) — ротация заполняет пустой слот внутри персоны.**
Дано: канал C покинут из-за бана агентом X персоны Б (слот канала в персоне Б пуст); в персоне Б есть другой активный агент Y.
Когда: выполняется суточная ротация.
Тогда: агентский слот C в персоне Б заполняется агентом Y (агентом персоны Б), а не агентом другой персоны.

**AC-5 (US-3, R5) — нет доступного активного агента в персоне.**
Дано: канал C покинут из-за бана агентом X персоны Б; других доступных активных агентов в персоне Б нет.
Когда: выполняется ротация.
Тогда: агентский слот C в персоне Б остаётся пустым, принадлежность C персоне Б сохраняется; закрепления C в других персонах не затрагиваются; C не переносится в другую персону.

**AC-6 (US-3, R5) — бан в двух персонах одновременно.**
Дано: канал C закреплён в персонах А и Б; в обеих агент забанен (оба слота пусты); в персоне А есть доступный активный агент, в персоне Б — нет.
Когда: выполняется ротация.
Тогда: слот C в персоне А заполняется активным агентом персоны А; слот C в персоне Б остаётся пустым; принадлежность C сохраняется и за А, и за Б; ротация в персонах идёт независимо.

**AC-7 (US-4, R6) — балансировка в рамках персоны.**
Дано: у агентов персоны А разная стартовая нагрузка; распределяется набор каналов на персону А.
Когда: выполняется балансировка.
Тогда: стартовая нагрузка считается только по закреплениям в рамках персоны А; каналы других персон на балансировку не влияют.

**AC-8 (US-5, R7) — очистка не задевает другие персоны.**
Дано: канал C закреплён за агентом персоны А и, независимо, за агентом персоны Б.
Когда: у агента персоны А канал C очищается.
Тогда: закрепление C в персоне А снимается; закрепление C в персоне Б сохраняется без изменений.

**AC-9 (US-6, R8) — колонка отчёта.**
Дано: формируется ежедневный отчёт по агентам.
Когда: отчёт построен.
Тогда: в нём присутствует колонка «персона» и отсутствует колонка «пул».

**AC-10 (US-7, R9) — полный список реестра.**
Дано: канал C закреплён в двух персонах.
Когда: запрашивается список всех каналов реестра без фильтра по персоне.
Тогда: C присутствует в списке один раз.

**AC-11 (US-8, R10) — миграция закреплений.**
Дано: до перехода в реестре есть каналы, закреплённые за агентами; все они принадлежат единственной персоне `maria`.
Когда: выполнена миграция.
Тогда: у каждого перенесённого закрепления проставлена персона `maria`; двойных закреплений внутри одной персоны не возникает.

**AC-12 (US-9, R11) — redistribute как распределение по персоне.**
Дано: готовый список каналов для принудительного перераспределения на персону А.
Когда: запускается redistribute.
Тогда: перераспределение идёт по имени персоны с теми же правилами дедупа (в рамках персоны) и балансировки; закрепить канал за конкретным агентом нельзя.

**AC-13 (US-2, R12) — целевая персона без активных агентов.**
Дано: оператор запускает распределение/перераспределение/дискавери на персону, у которой нет ни одного активного агента (либо указывает несуществующую персону).
Когда: прогон инициируется.
Тогда: прогон отклоняется с сообщением до обработки входа; каналы не классифицируются и не теряются; частичного/пустого исполнения не происходит.

## 9. Нефункциональные требования

| # | Требование |
|---|---|
| **NFR-1 (идемпотентность)** | Повторный прогон дискавери/распределения с тем же входом и тем же стартовым состоянием реестра не должен создавать дублирующих закреплений и не должен менять результирующее распределение. |
| **NFR-2 (детерминизм балансировки)** | При одинаковом входе и одинаковом стартовом состоянии персоны результат балансировки должен быть воспроизводим. |
| **NFR-3 (обратимость)** | Необратимые шаги миграции (изменение/удаление существующих закреплений) выполняются в соответствии с принципом обратимости проекта; удаление исходных данных — только с явного подтверждения оператора. |
