# Требования: Мультиаккаунтный failover ChatGPT/codex-подписок с классификацией ошибок и cooldown по остатку лимита — v1

> **О чём документ.** Проблема, доменная модель, цель, требования и критерии приёмки —
> уровень бизнес-аналитики (что и почему, для кого). Техническое решение (как именно
> это реализуется) — в парном `architecture.md` (архитектор).
>
> Модель добавляет к LLM-слою **пул из нескольких codex-аккаунтов** с переключением по
> строгому приоритету и **классификацию ошибок ответов**: только исчерпание лимита
> подписки ставит аккаунт на cooldown до даты сброса, остальные классы ошибок аккаунт не
> выводят из оборота. DeepSeek сохраняется как финальный предохранитель.

## 1. Проблема и контекст

LLM-слой платформы генерирует ответы агентов и скоринг DM-кандидатов. Primary-провайдер —
подписка ChatGPT, доступ к которой идёт через codex-бэкенд библиотекой
`@openai-oauth/ai-sdk`. Fallback — DeepSeek (потокенная тарификация). Сегодня на каждый
прогон диспетчера собирается один клиент: **один** codex-аккаунт как primary и DeepSeek
как единственный fallback, связанные каскадом «при ошибке primary — перейти на DeepSeek».

Текущее поведение имеет три дефекта, подтверждённые логами диспетчера за 02.10.2026:

1. **Ошибки не классифицируются.** Каскад на следующую модель срабатывает на любую
   ошибку без разбора причины: исчерпание лимита, ошибка схемы structured output,
   сетевой сбой трактуются одинаково. За сутки зафиксировано 156 ошибок схемы
   («Invalid schema for response_format», HTTP 400) — это дефект формата запроса, а не
   лимита, но каскад реагировал на них так же, как на лимит.
2. **Primary — единственный codex-аккаунт.** Когда у него исчерпывается лимит подписки
   («The usage limit has been reached», 34 случая за сутки), единственный путь — сразу в
   DeepSeek, хотя у платформы может быть несколько оплаченных ChatGPT-подписок, чей лимит
   ещё не израсходован.
3. **Предохранитель фактически отключён.** На аккаунте DeepSeek нулевой баланс
   («Insufficient Balance», 190 случаев за сутки), поэтому после перехода на fallback
   генерация всё равно не проходит.

Цель бизнеса — **не упираться в лимит подписки «любой ценой»**: иметь несколько
codex-аккаунтов и переключаться между ними, когда у текущего кончается лимит, расходуя
квоту каждой подписки прежде, чем прибегать к потокенному DeepSeek.

Отдельная сложность: наивное решение «ставить аккаунт на паузу при любой ошибке» выведет
исправный аккаунт из оборота на 156 ошибках схемы, которые к лимиту отношения не имеют.
Поэтому классификация ошибок — обязательное условие, а не улучшение.

Аудитория: сам LLM-слой (автоматический выбор доступного аккаунта без участия человека) и
оператор платформы (следит за расходом квот подписок, балансом DeepSeek и за тем, какой
аккаунт сейчас обслуживает генерацию).

## 2. Цель

- Завести **пул из нескольких codex-аккаунтов** и переключаться между ними по **строгому
  приоритету** (аккаунт A → аккаунт B → … → DeepSeek), чтобы израсходовать квоту каждой
  подписки прежде, чем уходить в потокенный DeepSeek.
- **Классифицировать ошибки** ответов LLM-слоя по причине, чтобы разные классы вели к
  разной реакции, а не к единому каскаду «на любую ошибку».
- Ставить аккаунт на **cooldown только при исчерпании лимита подписки**, с
  недоступностью до **момента сброса лимита**; остальные классы ошибок (схема, сеть,
  протухший токен) аккаунт из оборота не выводят.
- Определять доступность аккаунта **по сохранённой дате сброса**, а не пробным запросом к
  модели, чтобы проверка доступности не тратила квоту подписки.
- Сохранить DeepSeek как **финальный предохранитель** в конце приоритета; зафиксировать
  зависимость: предохранитель имеет смысл только при ненулевом балансе DeepSeek.
- Сделать переключения между аккаунтами **наблюдаемыми**, чтобы оператор видел, какой
  аккаунт обслуживает генерацию, какой выведен на cooldown и до какого момента.

## 3. Доменная модель

Термины подтверждены документацией ChatGPT/codex-бэкенда и наблюдаемыми ответами его
эндпоинтов (см. §9), не кодом проекта.

### 3.1. Термины

| Термин | Что это |
|---|---|
| LLM-слой | Компонент платформы, формирующий ответы агентов и скоринг кандидатов через внешнего LLM-провайдера. Собирается на каждый прогон диспетчера |
| Прогон диспетчера | Одно исполнение задач по расписанию в отдельном короткоживущем процессе. Между прогонами состояние в оперативной памяти не сохраняется |
| Провайдер | Внешний сервис генерации. В системе их два рода: ChatGPT-подписка через codex-бэкенд и DeepSeek |
| codex-аккаунт | Отдельная учётная запись ChatGPT-подписки, доступ к которой идёт через codex-бэкенд по собственному OAuth-токену. Имеет собственную квоту лимита подписки, независимую от других аккаунтов |
| DeepSeek | Провайдер с потокенной тарификацией (оплата по балансу). В приоритете всегда последний — финальный предохранитель |
| Лимит подписки | Ограничение объёма использования ChatGPT-подписки на временном окне. У codex-аккаунта два окна одновременно: **primary** (5-часовое, `limit_window_seconds = 18000`) и **secondary** (недельное, `604800`) |
| Остаток лимита | Насколько окно израсходовано (`used_percent`) и когда оно сбросится (`reset_at` — точный unix-timestamp сброса, `reset_after_seconds` — сколько до сброса). Доступны по обоим окнам |
| Исчерпание лимита | Состояние, когда окно израсходовано и подписка отклоняет запросы (`limit_reached = true`, `allowed = false`, непустой `rate_limit_reached_type`). У codex проявляется ответом «The usage limit has been reached» (HTTP 429) |
| Эндпоинт остатка лимита | Запрос, возвращающий остаток лимита codex-аккаунта по обоим окнам **без обращения к модели** (без траты квоты генерации): `GET https://chatgpt.com/backend-api/wham/usage`. Отвечает и «сколько осталось» (`used_percent`), и «когда сброс» (`reset_at`) |
| Заголовки остатка в ответе codex | Семейство заголовков `x-codex-primary-*` / `x-codex-secondary-*` (`-used-percent`, `-reset-at`), `x-codex-rate-limit-reached-type` на каждом ответе генерации. Альтернативный источник остатка, по наблюдениям местами пустой или `-1` — менее надёжный, чем эндпоинт остатка лимита |
| Класс ошибки | Категория причины неуспеха ответа LLM-слоя, определяющая реакцию системы (см. §6.1). Основные классы: исчерпание лимита, ошибка схемы, транзиентная ошибка, ошибка авторизации 401, ошибка авторизации 403, ошибка кода, прочее |
| Ошибка схемы | Отклонение запроса из-за несоответствия схемы structured output строгому `json_schema` (у codex — «Invalid schema for response_format», HTTP 400). Относится к формату запроса, не к лимиту и не к работоспособности аккаунта |
| cooldown аккаунта | Период, на который codex-аккаунт выведен из оборота после исчерпания лимита. Длится до сохранённого момента сброса лимита. Пока аккаунт на cooldown, система к нему не обращается |
| Failover строгим приоритетом | Переключение провайдеров в фиксированном порядке приоритета: первый доступный codex-аккаунт по списку, при его недоступности — следующий, и так до DeepSeek в конце. Не round-robin: порядок детерминирован и не чередуется |
| Хранилище состояния cooldown | Место хранения признака «аккаунт на cooldown до <момент сброса>», общее на хост и переживающее завершение прогона, — чтобы решение о доступности аккаунта принималось по накопленному состоянию, а не терялось с каждым короткоживущим процессом |
| Структурированный вывод (structured output) | Режим, в котором от модели требуется ответ по заданной схеме. Внутри LLM-слоя имеет несколько уровней деградации (нативный structured output → текстовая генерация → приведение), исход которых относится к одной и той же модели |

### 3.2. Почему классификация обязательна

Исчерпание лимита и ошибка схемы приходят от одного и того же провайдера, но означают
разное. Исчерпание лимита — это свойство **аккаунта** на данный момент времени: аккаунт
временно непригоден, и его следует вывести на cooldown. Ошибка схемы — это свойство
**запроса**: аккаунт полностью исправен, непригоден сам запрос. Если cooldown ставить на
любую ошибку, то 156 ошибок схемы за сутки выведут из оборота исправные аккаунты, хотя
их квота не израсходована. Поэтому на cooldown ведёт **только** класс «исчерпание
лимита».

### 3.3. Почему доступность проверяется по дате, а не пробным запросом

У эндпоинта остатка лимита есть точный момент сброса (`reset_at`). Это позволяет **до**
обращения к модели знать, доступен ли аккаунт, не тратя квоту на пробный запрос. Пробная
генерация «проверить, работает ли аккаунт» расходовала бы лимит той самой подписки,
доступность которой проверяется, — что противоречит цели «не упираться в лимит».

## 4. Ограничения среды

- Прогоны — отдельные короткоживущие процессы; состояние в оперативной памяти между ними
  не сохраняется. Признак cooldown аккаунта, чтобы иметь смысл, должен сохраняться между
  прогонами и переживать перезапуск процесса.
- Квоты codex-аккаунтов независимы: исчерпание лимита у одного аккаунта не влияет на
  остаток других. Это и делает осмысленным пул из нескольких аккаунтов.
- У каждого codex-аккаунта лимит считается по двум окнам одновременно (5-часовому и
  недельному). Исчерпание любого из них делает аккаунт недоступным; момент сброса у окон
  разный. Для cooldown значим ближайший момент, когда аккаунт снова станет доступен.
- Остаток лимита можно получить без траты квоты генерации — через эндпоинт остатка
  лимита (`GET /backend-api/wham/usage`), отвечающий по токену аккаунта. Заголовки
  остатка в ответах генерации — второй возможный источник, но по наблюдениям менее
  надёжный (пустые значения, `-1`).
- Библиотека `@openai-oauth/*` сама остаток лимита не разбирает: поле `usage` в её
  ai-sdk — это токены запроса/ответа, а не лимиты подписки. Остаток лимита приложение
  получает самостоятельно.
- Ошибки от библиотеки доступны приложению как ai-sdk-ошибка вызова API с полями кода
  HTTP-статуса и заголовков ответа — по ним и возможна классификация.
- DeepSeek как предохранитель работает только при ненулевом балансе. На момент
  составления документа баланс нулевой («Insufficient Balance»), то есть предохранитель
  фактически отключён; это внешняя зависимость, а не поведение системы.
- Риск скоррелированной блокировки пула codex-аккаунтов (нарушение условий использования
  при их совместной эксплуатации) **принят** владельцем; вероятность не оценивалась.
  Требование как-либо снижать этот риск в данную фичу не входит.

## 5. User Stories

**US-1 (R3, R6).** Как LLM-слой, при исчерпании лимита у текущего codex-аккаунта я хочу
переключаться на следующий аккаунт пула по строгому приоритету, чтобы израсходовать квоту
каждой подписки прежде, чем прибегать к потокенному DeepSeek.

**US-2 (R1, R2).** Как LLM-слой, я хочу классифицировать ошибку ответа по причине, чтобы
на исчерпание лимита реагировать иначе, чем на ошибку схемы или сетевой сбой.

**US-3 (R4, R5).** Как LLM-слой, при исчерпании лимита я хочу запомнить момент сброса и
вывести аккаунт на cooldown до этого момента, чтобы не обращаться к заведомо недоступному
аккаунту до сброса его лимита.

**US-4 (R7).** Как LLM-слой, я хочу определять доступность аккаунта по сохранённой дате
сброса, а не пробным запросом к модели, чтобы проверка доступности не тратила квоту
подписки.

**US-5 (R2).** Как оператор платформы, я хочу, чтобы ошибка схемы и транзиентные сбои не
выводили аккаунт на cooldown, чтобы исправный аккаунт не выпадал из оборота из-за дефекта
запроса или единичного сбоя сети.

**US-6 (R8, R9).** Как оператор платформы, я хочу, чтобы DeepSeek оставался последним в
приоритете как финальный предохранитель, чтобы при недоступности всех codex-аккаунтов
генерация всё же проходила — при условии ненулевого баланса DeepSeek.

**US-7 (R10).** Как LLM-слой, я хочу сохранять состояние cooldown между прогонами и
перезапусками процесса, чтобы решение о доступности аккаунта принималось по накопленному
состоянию, а не начиналось заново в каждом короткоживущем прогоне.

**US-8 (R11).** Как оператор платформы, я хочу видеть в логах, какой аккаунт обслуживает
генерацию, когда и почему произошло переключение и до какого момента аккаунт на cooldown,
чтобы контролировать расход квот подписок и состояние предохранителя.

## 6. Требования

- **R1.** Система должна классифицировать каждую неуспешную попытку ответа LLM-слоя в один
  из классов ошибок (§7.1) по сигнатуре ответа (код HTTP-статуса, текст тела, значимое
  поле), а не трактовать любую ошибку единообразно.
- **R2.** На cooldown аккаунта должен выводить **только** класс «исчерпание лимита».
  Классы «ошибка схемы», «транзиентная ошибка», «ошибка авторизации 401/403», «ошибка
  кода», «прочее» не должны выводить codex-аккаунт на cooldown.
- **R3.** Переключение провайдеров должно идти по **строгому приоритету**: первый
  доступный codex-аккаунт по заданному порядку, при его недоступности — следующий, и так
  до DeepSeek в конце списка. Чередование аккаунтов по кругу (round-robin) не
  применяется.
- **R4.** Когда у codex-аккаунта зафиксировано исчерпание лимита, система должна
  запомнить момент сброса его лимита и вывести аккаунт на cooldown до этого момента.
- **R5.** Момент сброса для cooldown система должна определять по остатку лимита аккаунта
  (`reset_at` по окну, которое исчерпано). При исчерпании по нескольким окнам аккаунт
  должен оставаться на cooldown до наиболее позднего из их моментов сброса (до момента,
  когда аккаунт снова станет доступен по всем окнам).
- **R6.** При недоступности текущего codex-аккаунта (cooldown или неуспех класса, ведущего
  к переключению) система должна перейти к следующему доступному аккаунту пула по
  приоритету в пределах того же прогона; дойдя до конца списка codex-аккаунтов — к
  DeepSeek.
- **R7.** Доступность codex-аккаунта перед обращением система должна определять по
  сохранённой дате сброса из хранилища состояния cooldown, а не пробным запросом к модели.
  Аккаунт, у которого cooldown ещё не истёк, должен считаться недоступным и пропускаться;
  аккаунт, у которого момент сброса уже наступил, должен снова считаться доступным.
- **R8.** DeepSeek должен оставаться в приоритете последним (финальным предохранителем) и
  использоваться, только когда все codex-аккаунты недоступны.
- **R9.** Документ фиксирует внешнюю зависимость: предохранитель DeepSeek обеспечивает
  прохождение генерации только при ненулевом балансе DeepSeek. Поддержание ненулевого
  баланса — условие работоспособности предохранителя (операционная зависимость, не
  поведение системы).
- **R10.** Состояние cooldown (признак «аккаунт недоступен до <момент сброса>») должно
  сохраняться между прогонами, быть общим на хост и переживать перезапуск процесса.
- **R11.** Переключения между провайдерами и постановка аккаунта на cooldown должны быть
  наблюдаемыми: в журнал должно попадать, какой аккаунт/провайдер обслуживает генерацию,
  факт и причина (класс ошибки) переключения и момент, до которого аккаунт выведен на
  cooldown.
- **R12.** Класс «ошибка схемы» (schema_error) должен **записываться в лог без повтора и
  без фолбэка**: текущий вызов завершается неуспехом, переход к следующему провайдеру не
  выполняется, аккаунт на cooldown не ставится и остаётся в обороте.
- **R13.** Класс «транзиентная ошибка» (сеть/таймаут/5xx) должен **записываться в лог без
  повтора и без фолбэка**; переход к следующему провайдеру не выполняется, аккаунт на
  cooldown не ставится.
- **R14.** Проверка остатка лимита (и как источник момента сброса для cooldown, и как
  проверка доступности) не должна расходовать квоту генерации codex-аккаунта.
- **R15.** Повторный запрос выполняется **только** в двух случаях: (а) «исчерпание
  лимита» — переход к следующему провайдеру по приоритету и повтор запроса; (б) «ошибка
  401» — обновление OAuth-токена и повтор на том же провайдере. Во всех остальных классах
  ошибок повтор и фолбэк не выполняются: ошибка пишется в лог, вызов завершается
  неуспехом.
- **R16.** Класс «401» (невалидный/протухший токен) должен приводить к обновлению
  OAuth-токена аккаунта и повтору запроса на **том же** провайдере (без перехода к
  следующему). Если обновление токена не удалось — ошибка пишется в лог без дальнейшего
  повтора; cooldown по лимиту не ставится.
- **R17.** Класс «403» (доступ запрещён) должен записываться в лог как ошибка; повтор и
  фолбэк не выполняются; cooldown по лимиту не ставится.
- **R18.** Ошибки времени исполнения в коде LLM-слоя (исключения вида
  `AttributeError`/`UnboundError` и подобные, не являющиеся ответом API) должны
  записываться в лог; повторные вызовы и фолбэк не выполняются.
- **R19.** Неуспех LLM-вызова (любой класс, завершающийся неуспехом по R12–R18) по
  **одному рабочему элементу** прогона (канал, тред, пост, DM-кандидат) не должен
  прерывать весь прогон: ошибка логируется, элемент пропускается, прогон продолжается со
  следующего элемента. Останавливать прогон целиком допустимо только по отдельным явным
  сигналам, не связанным с классификацией LLM-ошибок (например, PEER_FLOOD).

### 6.1. Классы ошибок (AS IS → TO BE)

AS IS по всем классам одинаков и отражает текущий код: функция решения о повторе
возвращает «повторять» на любую ошибку, поэтому происходит каскад на следующую модель при
любой причине; состояние между прогонами не хранится, аккаунт на cooldown не ставится,
остаток лимита не запрашивается.

| Класс ошибки | Сигнатура (HTTP / текст тела / поле) | Провайдер | Поведение AS IS | Поведение TO BE |
|---|---|---|---|---|
| `usage_limit` (исчерпание лимита) | HTTP 429; текст «The usage limit has been reached»; `rate_limit_reached_type` непуст; `limit_reached = true`, `allowed = false` | codex | Каскад на следующую модель (DeepSeek), состояние не сохраняется, аккаунт не бенчится | Записать в лог; взять момент сброса по остатку лимита (`reset_at` исчерпанного окна); вывести аккаунт на cooldown до момента сброса; **перейти к следующему доступному провайдеру по приоритету и повторить запрос** (в конце списка codex-аккаунтов — DeepSeek). Единственный класс, при котором делается переход к следующему провайдеру с повтором (R3, R4, R5, R6, R15) |
| `schema_error` (ошибка схемы) | HTTP 400; текст «Invalid schema for response_format …» (напр. отсутствует обязательное поле в `required`) | codex | Каскад на следующую модель, как при любой ошибке; причина не различается | Записать в лог; **фолбэк и повтор НЕ делать**, перейти дальше (вызов завершается неуспехом). Аккаунт исправен, из оборота не выводится (R2, R12, R15) |
| `transient` (транзиентная: сеть/таймаут/5xx) | HTTP 5xx; сетевой таймаут/разрыв; прочие временные сбои транспорта | codex, DeepSeek | Каскад на следующую модель; аккаунт не бенчится | Записать в лог; **повтор и фолбэк НЕ делать**, перейти дальше. Аккаунт из оборота не выводится (R2, R13, R15) |
| `auth_401` (токен невалиден/протух) | HTTP 401 | codex | Каскад на следующую модель; токен не обновляется | Записать в лог; **обновить OAuth-токен аккаунта и повторить запрос на том же провайдере** (без перехода к следующему). Если обновление токена не удалось — лог, без дальнейшего повтора. Cooldown не ставится (R16) |
| `auth_403` (доступ запрещён) | HTTP 403 | codex | Каскад на следующую модель | Записать в лог как ошибку; **повтор и фолбэк НЕ делать**. Cooldown не ставится (R17) |
| `runtime_error` (ошибка кода) | исключение времени исполнения в коде LLM-слоя (вида `AttributeError`/`UnboundError` и подобные), не ответ API | — (внутреннее) | Не выделяется отдельно; исключение всплывает наверх | Записать в лог; **никаких повторных вызовов и фолбэка** (R18) |
| `other/unknown` (прочее) | ошибка, не подпавшая ни под один класс выше | codex, DeepSeek | Каскад на следующую модель | Записать в лог; **повтор и фолбэк НЕ делать** (консервативно), аккаунт из оборота не выводить (R2, R15) |

## 7. Критерии приёмки

- **AC-1 (R1).** Каждая неуспешная попытка ответа относится ровно к одному классу из
  §6.1 по своей сигнатуре; ошибка схемы и исчерпание лимита различаются и не смешиваются.
- **AC-2 (R12, R15).** Ответ класса «ошибка схемы» пишется в лог, не вызывает повтор и
  фолбэк и не выводит аккаунт на cooldown; вызов завершается неуспехом, аккаунт остаётся
  доступен для последующих обращений.
- **AC-3 (R13, R15).** Транзиентная ошибка пишется в лог, не вызывает повтор и фолбэк и не
  выводит аккаунт на cooldown.
- **AC-4 (R3, R6).** При исчерпании лимита у аккаунта A система обращается к следующему
  доступному codex-аккаунту (B, затем C, …) по заданному порядку, а не к DeepSeek, пока в
  пуле есть доступный codex-аккаунт.
- **AC-5 (R4, R5).** При исчерпании лимита аккаунт помечается недоступным до момента
  сброса, взятого из остатка лимита; при исчерпании по нескольким окнам — до наиболее
  позднего из моментов сброса.
- **AC-6 (R7, R14).** Доступность аккаунта на cooldown определяется по сохранённой дате
  без обращения к модели: до наступления момента сброса аккаунт пропускается, после —
  снова используется; проверка не расходует квоту генерации.
- **AC-7 (R8).** DeepSeek вызывается только после того, как все codex-аккаунты
  недоступны; пока доступен хотя бы один codex-аккаунт, DeepSeek не вызывается.
- **AC-8 (R10).** Cooldown, установленный в одном прогоне, виден в следующем прогоне после
  перезапуска процесса и учитывается при выборе аккаунта; состояние общее на хост.
- **AC-9 (R11).** В журнале по каждому переключению присутствует: какой аккаунт/провайдер
  обслуживал генерацию, класс ошибки — причина переключения, на какой аккаунт/провайдер
  переключились и до какого момента выведен на cooldown аккаунт, исчерпавший лимит.
- **AC-10 (R9).** Зависимость от ненулевого баланса DeepSeek зафиксирована: при нулевом
  балансе предохранитель фактически не срабатывает — это состояние среды, не дефект логики
  переключения.
- **AC-11 (R15, R16).** Ошибка 401 приводит к обновлению OAuth-токена и повтору запроса на
  том же провайдере; при неуспехе обновления — запись в лог без повтора. Переход к другому
  провайдеру при 401 не происходит.
- **AC-12 (R17).** Ошибка 403 пишется в лог как ошибка; повтор и фолбэк не выполняются;
  cooldown не ставится.
- **AC-13 (R18).** Исключение времени исполнения в коде LLM-слоя пишется в лог; повторные
  вызовы и фолбэк не выполняются.
- **AC-14 (R15).** Переход к следующему провайдеру с повтором не происходит ни при одном
  классе, кроме «исчерпание лимита»; повтор на том же провайдере — только при «401».
- **AC-15 (R19).** При неуспехе LLM-вызова по одному элементу (например, одному каналу в
  monitor-v5) прогон логирует ошибку и продолжает обработку остальных элементов; прогон не
  завершается целиком из-за ошибки одного элемента.
