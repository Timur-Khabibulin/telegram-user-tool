# Design Doc: Выход из забаненных каналов — v1

> Аналитика фичи для человека. Нормативное поведение (требования + сценарии) —
> в `openspec/changes/leave-banned-channels/`, не здесь.

## 1. Проблема / Контекст

Админ канала может забанить аккаунт агента на запись. После этого монитор при
попытке ответить получает `CHAT_WRITE_FORBIDDEN`, но **продолжает каждый цикл
заходить в этот канал и пытаться писать** — впустую жжёт флуд-бюджет аккаунта,
копит ошибки и шумит в отчёте-воронке. Сейчас система ошибку только логирует
(`send_errors` как `reply_failed`), но никак не реагирует: забаненные каналы
накапливаются и остаются в работе агента.

## 2. Цели

1. Распознавать именно `CHAT_WRITE_FORBIDDEN` (а не любую ошибку ответа) и
   ставить такой канал в очередь на обработку.
2. Выходить из забаненного канала (`leaveChannel`), чтобы он не возвращался
   через синхронизацию диалогов и не тратил ресурсы агента.
3. Полностью удалять рабочие данные агента по этому каналу.
4. Помечать канал забаненным в реестре, чтобы будущая логика переназначения
   могла учесть это (сама логика переназначения — вне скоупа).

## 3. Как работает

```
МОНИТОР (per-agent)                  СКИЛЛ-ГИГИЕНА (per-agent, по расписанию)
  ответ → CHAT_WRITE_FORBIDDEN        для каждого chatId из banned_channels:
  → enqueue chatId в banned_channels    1. resolve chatId → canonical_link
     (только эта ошибка; прочие            (GetFullChannel.username, best-effort)
      без изменений)              ─────►  2. leaveChannel(chatId)
                                          3. удалить данные агента по chatId
                                          4. реестр: пометить banned_at
                                             (только если resolve удался)
                                          5. удалить строку из banned_channels
```

- **Триггер — только `CHAT_WRITE_FORBIDDEN`.** Прочие ошибки ответа
  (`reply_failed`, `flood_wait`, `peer_id_invalid`) ведут себя как раньше и в
  очередь не попадают.
- **Реактивно**, без проактивного опроса прав: канал попадает в очередь только
  после фактической неудачной попытки записи.
- **Выход обязателен раньше удаления.** `syncChannels` каждый прогон добирает
  каналы из диалогов: если удалить данные, но не выйти — следующий синк вернёт
  канал. Поэтому сначала `leaveChannel`, потом чистка.
- **Resolve реестра — best-effort.** `chatId` монитора часто относится к
  группе-обсуждению, у которой может не быть публичного username. Если username
  не резолвится — выход и чистка данных всё равно выполняются, пропускается
  только пометка реестра (шаг 4). Надёжная связь `chatId↔canonical_link` — см.
  Future Work.

## 4. Архитектура

| Компонент | Изменение |
|---|---|
| `service.ts` | новый метод `leaveChannel(chatId)` (MTProto `channels.LeaveChannel`); резолв username по `chatId` (`GetFullChannel`) |
| `monitor.ts` | различать `CHAT_WRITE_FORBIDDEN` отдельно от прочих не-flood ошибок ответа → `enqueueBannedChannel` |
| новый скилл `leave-banned-channels` | per-agent, в диспетчере; читает `banned_channels`, исполняет шаги 2–5; регистрируется в `dispatcher.ts` и планируется задачей |
| `db/channels.ts` | таблица `banned_channels` + функции enqueue/get/delete; функция полной чистки данных по `chatId` |
| `db/discovery.ts` | колонка `banned_at` в `discovered_channels` + пометка бана |

Скилл, а не standalone-скрипт: исполнение per-agent с уже подключённым клиентом
агента ложится на существующий паттерн диспетчера (как `monitor`/`dm-send`).

## 5. Модель данных

### `banned_channels` — очередь работ (per-agent, `tg-channels.db`)

| Поле | Тип | Описание |
|---|---|---|
| chatId | TEXT PK | канал с `CHAT_WRITE_FORBIDDEN` |
| detectedAt | INTEGER | unix-сек момента обнаружения |

Временная: строка удаляется после выхода+чистки (шаг 5). `INSERT OR IGNORE` —
повторные ошибки по тому же каналу не плодят дублей.

### `discovered_channels` — пометка бана (реестр, `discovery.db`)

Добавляется колонка `banned_at INTEGER` (NULL = активен). При бане:
`UPDATE … SET banned_at = ? WHERE canonical_link = ?`. `assigned_agent`
оставляем (видно, какой агент забанен); строку не удаляем (канал остаётся в
реестре).

### Удаление рабочих данных агента по `chatId`

**`tg-channels.db`:** `channels`, `channel_visits`, `dm_candidates`
(`sourceChatId`), `banned_channels` (последней).
**`tg-replies.db`:** `replies`, `group_threads`, `group_thread_agent_msgs`.

**НЕ удаляем:**
- `send_errors` — история ошибок для отчёта (наблюдаемость, не рабочее состояние);
- `dm_threads` — активные личные диалоги с пользователями из канала: бан на
  запись в канал не мешает писать им в личку (другой peer).

## 6. Альтернативы

**Проактивный опрос прав** (`GetParticipant(self)` → `bannedRights`) ловил бы бан
даже без попытки записи, но это +1 API-вызов на каждый канал каждого агента
(тысячи вызовов) — отклонено в пользу реактивного следа.

**Отдельная таблица `channel_bans(link, agent)`** для чёрного списка
переназначения — отклонено как избыточное: пометки `banned_at` +
сохранённого `assigned_agent` на строке реестра достаточно, чтобы будущая
логика исключила забаненного агента.

**Чистка через чтение `send_errors`** как очереди — отклонено: `send_errors`
служит отчётности; использовать лог как очередь работ связало бы действие с
форматом отчёта. Отдельная таблица-очередь `banned_channels` имеет одну цель.

**Логика инлайн в мониторе** — отклонено: необратимая хирургия (leave +
удаление данных + правка реестра) выносится в изолированный проход; монитор
остаётся «читает/отвечает/логирует».

## 7. Метрики успеха

- Канал с `CHAT_WRITE_FORBIDDEN` после ближайшего прогона гигиены исчезает из
  данных агента и не возвращается синхронизацией.
- Агент перестаёт тратить попытки записи на забаненные каналы.
- В реестре у забаненного канала проставлен `banned_at`.

## 8. Future Work

- **Явная связь `chatId ↔ canonical_link`** при вступлении (join): сохранять
  chatId рядом со ссылкой, чтобы пометка реестра не зависела от best-effort
  резолва по username (закрывает дыру §3 для групп без публичного username).
- **Переназначение** освободившегося/забаненного канала на другого агента с
  учётом пометки бана — отдельная задача.
- **Проактивная проверка прав** для «тихих» банов (бан есть, но попытки записи
  ещё не было) — если понадобится.
