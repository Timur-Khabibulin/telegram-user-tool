# Design Doc: Потенциальный охват в отчёте-воронке — v1

> Аналитика фичи для человека. Объясняет, что делает система и как, и почему так
> решили. Нормативное поведение (требования + сценарии) — в `openspec/`, не здесь.

## 1. Проблема / Контекст

Отчёт-воронка показывает сколько сообщений отправил агент за день (этап 4), но
не показывает, какую аудиторию эти сообщения потенциально охватили. Оператор не
может быстро оценить «вес» дня — ответить в канале на 200 человек или на 5 000
разница существенная, но в текущем отчёте она невидима.

## 2. Цели

- Добавить в отчёт-воронку метрику **«потенциальный охват»** — суммарный средний
  охват каналов, куда агент отправил сообщения за сутки.
- Вывести метрику по агентам: новый столбец «Охват» в таблице code-блока текста
  отчёта и новый столбец в CSV (со строкой ИТОГО).

## 3. Как работает

### 3.1 Формула

```
потенциальный_охват(агент) =
    SUM(channels.avg_views)
    по DISTINCT chatId из replies.sentAt ∈ [startSec, endSec)
    WHERE channels.avg_views IS NOT NULL
```

Шаги:
1. Из `tg-replies.db` агента берём `DISTINCT chatId` по `sentAt` за отчётное окно —
   это каналы, куда агент реально написал.
2. Для каждого такого `chatId` берём `avg_views` из `tg-channels.db`.
3. Суммируем, игнорируя NULL.

`avg_views` уже посчитан и хранится в `channels.avg_views` — новых MTProto-запросов
не требуется.

**Почему `replies`, а не `channel_visits` с `outcome='active'`:** `outcome='active'`
означает «монитор нашёл активность в канале», но агент мог её не ответить. Метрика
о реально отправленных сообщениях — только `replies`.

### 3.2 Вывод в отчёте

**Текст сообщения:** новый столбец `Охват` в таблице code-блока — шестой после `Отпр`:

```
Агент   Кан  Просм  Актив  Отпр   Охват
────────────────────────────────────────
agent1    120     8      3    12   84000
agent2     95     6      2     9   41200
────────────────────────────────────────
Итого     215    14      5    21  125200
```

Легенда под таблицей дополняется: `Охват — потенциальный охват (avg_views каналов с ответами)`.

**CSV-вложение:** новый столбец `потенциальный_охват` после `ошибок_отправки` (этап 4),
строка ИТОГО — сумма по агентам.

### 3.3 Граничные случаи

| Ситуация | Результат |
|---|---|
| Агент не отправил ни одного сообщения за сутки | 0 |
| Все каналы с ответами имеют `avg_views IS NULL` | 0 |
| `tg-replies.db` не существует | 0 (не ошибка) |
| `tg-channels.db` не существует | 0 (не ошибка) |

## 4. Архитектура

| Компонент | Новый? | Изменение |
|---|---|---|
| `src/core/db/channels.ts` | существующий | новая функция `sumAvgViewsForRepliedChannels(agentId, chatIds)` |
| `src/core/db/replies.ts` | существующий | новая функция `getDistinctRepliedChatIds(agentId, startSec, endSec)` |
| `src/features/funnel/funnel-collect.ts` | существующий | новое поле `potentialReach: number` в `AgentFunnelRow`; сбор в блоке этапов 1-4 |
| `src/features/funnel/funnel-report.ts` | существующий | строка в тексте + столбец в CSV |

Все данные берутся из локальных БД агента — MTProto-сессия не нужна.

## 5. Модель данных

Новых таблиц и полей не требуется. Используются существующие:

| Таблица | БД | Поля |
|---|---|---|
| `replies` | `tg-replies.db` (per-agent) | `chatId`, `sentAt` |
| `channels` | `tg-channels.db` (per-agent) | `chatId`, `avg_views` |

SQL для расчёта на агента (выполняется в памяти через два запроса, т.к. БД разные):

```sql
-- 1. tg-replies.db: получить DISTINCT chatId за окно
SELECT DISTINCT chatId FROM replies
WHERE sentAt >= :startSec AND sentAt < :endSec;

-- 2. tg-channels.db: суммировать avg_views по этим chatId
SELECT COALESCE(SUM(avg_views), 0) AS potential_reach
FROM channels
WHERE chatId IN (:chatIds)
  AND avg_views IS NOT NULL;
```

Два отдельных запроса вместо ATTACH, потому что `funnel-collect.ts` уже работает
с двумя БД агента раздельно (`repliesDbPath`, `channelsDbPath`) — не нарушаем
установленный паттерн.

## 6. Альтернативы

**`channel_visits.outcome='active'` вместо `replies`.**
Отвергнуто: `active` означает «были новые сообщения в канале», а не «агент ответил».
Метрика о реально отправленных сообщениях требует `replies`.

**Отдельная строка вне code-блока.**
Отвергнуто: метрика привязана к агенту, разбивка по агентам важна оператору.
Строка вне блока показывала бы только платформенную сумму, без детализации по агентам.

**Дельта к предыдущему дню.**
Не нужна: охват каналов меняется медленно (avg_views пересчитывается раз в месяц),
дельта не несёт смысловой нагрузки.

## 7. Метрики успеха

- В таблице code-блока появляется столбец «Охват» с ненулевыми значениями
  по агентам в дни активной работы.
- В CSV появляется столбец `потенциальный_охват` с корректными значениями по агентам.

## 8. Future Work

- Разбивка потенциального охвата по агентам в тексте (сейчас только платформенная сумма).
- Предупреждение о доле каналов с `avg_views IS NULL` среди ответивших (если таких много,
  метрика занижена без очевидной причины).
