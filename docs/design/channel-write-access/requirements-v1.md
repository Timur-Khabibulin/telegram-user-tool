# Требования: Право писать в канал — v1

> **О чём документ.** Проблема, доменная модель, цель, требования и критерии
> приёмки — уровень бизнес-аналитики (что и почему, для кого). Техническое
> решение (как именно это реализуется) — в парном `architecture.md` (архитектор).

## 1. Проблема и контекст

Сейчас платформа узнаёт о невозможности писать в канал только постфактум — из
ошибки отправки комментария (`CHAT_WRITE_FORBIDDEN`). При этом два разных случая
сваливаются в один жизненный статус канала:

- **Структурный (постоянный) запрет** — писать нельзя никому: администратор закрыл
  комментарии для всех рядовых участников. Смена аккаунта не поможет.
- **Персональный (переменный) бан** — ограничен именно наш аккаунт. Смена аккаунта
  может помочь.

Так как различия нет, суточная авторотация переносит структурно закрытые каналы
между аккаунтами вхолостую, изнашивая живые аккаунты о заведомо непишущиеся каналы.

Наблюдения за 14 дней (обоснование ценности):

| Метрика | Значение |
|---|---|
| Уникальных ротированных каналов | ~497 |
| Из них структурно закрыты (не смог написать ни один аккаунт платформы) | ~24% |
| Медианное время «слот агента занят без единого ответа» | ~4 дня |
| Медиана «вход в канал → первый отказ записи» | ~3 дня |
| Доля отказов записи в первые сутки | ~39% |

Аудитория: платформа (автоматические скиллы отправки и ротации) и владелец,
принимающий решение о судьбе канала.

## 2. Цель

- Узнавать право писать **проактивно** (при вступлении и перед ответом), а не только
  через провал отправки.
- **Различать причину** невозможности писать по фиксированному перечню (структурная
  или персональная).
- **Использовать причину в решениях**: не тратить попытки отправки и слоты агентов на
  каналы, где писать нельзя; ротировать только там, где смена аккаунта может помочь;
  структурно закрытые каналы удерживать read-only для чтения.

## 3. Доменная модель

### Термины

| Термин | Что это |
|---|---|
| Broadcast-канал | Канал вещания, откуда берутся посты; комментарии в нём не пишутся напрямую |
| Группа обсуждения | Привязанный к broadcast-каналу чат (`linked_chat_id`), куда пишутся комментарии |
| Постоянная величина | `default_banned_rights` — ограничения записи по умолчанию для всех рядовых участников группы обсуждения |
| Переменная величина | Персональный статус нашего участника: конструктор `ChannelParticipant*` (обычный / self / admin / creator / **banned** / **left**) |
| Инвертированные флаги прав | В `ChatBannedRights` `true` = действие **запрещено**; `until_date` — срок ограничения (значение <30 сек или >366 дней трактуется как «навсегда») |
| «Не участник» | `GetParticipant(self)` бросает ошибку `USER_NOT_PARTICIPANT` — это ошибка, а не статус участника |
| Slow-mode | Интервал между сообщениями; ошибка `SLOWMODE_WAIT_N` — временная задержка, не запрет |

### Модель двух величин

Право писать рассматривается всегда для **одного аккаунта (агента)** в конкретном
канале и складывается из двух величин:

| Величина | Что описывает | Источник (Telegram) | Когда определяется |
|---|---|---|---|
| **Постоянная** | Можно ли писать «в принципе» любому рядовому участнику | `default_banned_rights` группы обсуждения | **Только при вступлении**; далее считается стабильной |
| **Переменная** | Персональные ограничения нашего аккаунта: забанен/ограничен, до какого срока | Живой `GetParticipant(self)`; либо ошибка при отправке | **На живую перед каждой отправкой**, не из кэша |

**Эффективное право писать сейчас** = постоянная разрешает запись **И** переменная не
ограничивает.

**Гранулярность — бинарная.** Значим факт «есть ли право отправить хоть что-то (хотя
бы текст)». Типы контента (фото/видео/медиа) не различаются.

**Признак и причина.** При невозможности писать хранится единый признак «писать
нельзя» + одна **причина** из перечня ниже, отдельно от статуса жизненного цикла
канала. `until_date` хранится справочно; снятие персонального ограничения
фиксируется живой проверкой, отдельная плановая переоценка срока не нужна.

**Где проверяется.** Комментарии пишутся в **группу обсуждения** (`linked_chat_id`
broadcast-канала), поэтому и постоянная величина, и участие, и переменная величина
проверяются у **группы обсуждения**, а не у broadcast-канала. За счёт этого случай
«вошли в broadcast-канал, но не состоим в группе обсуждения / удалены из неё»
корректно проявляется как `USER_NOT_PARTICIPANT` → причина `not_participant`.

### Мэппинг сигналов Telegram → наши причины

| Статус (Telegram) | Как получается из Telegram | Когда получаем статус | Тип | Наше название | Что делаем |
|---|---|---|---|---|---|
| `default_banned_rights.send_messages=true` у группы обсуждения | `GetFullChannel` группы обсуждения → объект channel, поле `default_banned_rights` | при вступлении | постоянный | `members_restricted` | оставляем read-only, не ротируем |
| Нет `linked_chat_id` | `GetFullChannel` broadcast-канала — нет привязанной группы обсуждения | при вступлении | постоянный | `no_discussion` | фиксируется на уровне очереди вступления; канал не вступлён, не ротируется |
| `channelParticipantBanned` c `banned_rights.send_messages=true`, `left=false` (+`until_date`) | `GetParticipant(self)` в группе обсуждения | при попытке отправки | переменный | `account_muted` | ротируем |
| `channelParticipantBanned` c `left=true`, либо ошибка `USER_BANNED_IN_CHANNEL` | `GetParticipant(self)` / ошибка при отправке | при попытке отправки | переменный | `account_kicked` | ротируем |
| `USER_NOT_PARTICIPANT` / `channelParticipantLeft` | `GetParticipant(self)` в группе обсуждения | при попытке отправки | переменный (удаление = бан) | `not_participant` | ротируем |
| Голый `CHAT_WRITE_FORBIDDEN` без объясняющего сигнала | Ошибка при отправке (проактивно не виден) | при попытке отправки | переменный (по умолчанию) | `CHAT_WRITE_FORBIDDEN` | ротируем |
| `ALLOW_PAYMENT_REQUIRED` | Ошибка при отправке | при попытке отправки | постоянный (канал-уровневое, для всех) | `paid` | оставляем read-only, не ротируем |
| `SLOWMODE_WAIT_N` | Ошибка при отправке | при попытке отправки | временный | `slowmode` | не помечаем cannot_write; ждём/повторяем |
| `PEER_FLOOD` | Ошибка при отправке | при попытке отправки | уровень аккаунта, не канал | — (ограничение агента) | не приписываем каналу; обрабатываем на уровне агента |
| `channelParticipant` / `channelParticipantSelf` / `Admin` / `Creator` И `default_banned_rights` разрешает | `GetParticipant(self)` + `default_banned_rights` группы обсуждения | при вступлении (подтверждается при попытке отправки) | — | `can_write` | пишем |

## 4. Ограничения среды

- У Telegram нет единого поля «причина запрета» — причина реконструируется из статуса
  участника и/или кода ошибки отправки.
- Проактивная проверка (`default_banned_rights` + `GetParticipant`) не видит скрытые
  цензы: «комментировать могут только подписчики основного канала», «участник должен
  состоять N дней», антиспам-бот/капчу. Эти ограничения проявляются только как голый
  `CHAT_WRITE_FORBIDDEN` при отправке (причина `CHAT_WRITE_FORBIDDEN`). Аналогично
  `paid` виден только при отправке. Поэтому проактивная проверка снижает, но не
  обнуляет холостые попытки — отказ-отправка остаётся резервным источником.
- Живой `GetParticipant` перед каждой отправкой — дополнительный вызов на каждый
  ответ; частота служебных вызовов влияет на риск антиспам-ограничений аккаунта.

## 6. User Stories

**US-1 (R2, R3).** Как платформа, при вступлении агента в канал я хочу определить в
группе обсуждения, стали ли мы участником и разрешает ли базовое право писать, и
сохранить это разово, — чтобы заранее знать каналы, где агент писать не сможет в
принципе.

**US-2 (R1, R4, R5, R17).** Как платформа, прежде чем отправить комментарий, я хочу на
живую проверить переменную величину в группе обсуждения и учесть постоянную, — чтобы
не тратить попытку отправки там, где сейчас нельзя, опираясь на актуальное состояние.

**US-3 (R6, R7).** Как владелец, я хочу, чтобы при невозможности писать система
классифицировала причину по фиксированному перечню и хранила её единым признаком, —
чтобы решения принимались по причине, а не по обобщённому «banned».

**US-4 (R8, R9, R10).** Как владелец, я хочу, чтобы при постоянной причине канал
оставался read-only без ротации и выхода, а при переменной — ротировался, — чтобы не
изнашивать живые аккаунты о непишущиеся каналы и при этом сохранять чтение канала для
сбора DM-кандидатов.

**US-5 (R14).** Как платформа, при отказе отправки я хочу обновлять признак и причину
по коду ошибки, — чтобы ловить причины без проактивного сигнала (`CHAT_WRITE_FORBIDDEN`,
`paid`).

**US-6 (R12, R13).** Как платформа, я хочу не помечать канал непишущимся из-за
slow-mode и не приписывать каналу глобальный антиспам аккаунта (`PEER_FLOOD`), — чтобы
причина канала не смешивалась с временными и аккаунт-глобальными ограничениями.

## 7. Требования

- **R1.** Система должна определять право писать для аккаунта в канале как сочетание
  постоянной и переменной величин: право есть, только когда постоянная разрешает
  запись И переменная не ограничивает.
- **R2.** Система должна проверять участие и права записи в привязанной группе
  обсуждения, а не в broadcast-канале.
- **R3.** Постоянную величину система должна снимать один раз при вступлении и далее
  считать стабильной (периодически не перечитывать).
- **R4.** Переменную величину система должна проверять на живую перед каждой
  отправкой, а не брать из кэша.
- **R5.** Право система должна оценивать бинарно — наличие возможности отправить хотя
  бы текст; типы контента не различать.
- **R6.** При невозможности писать система должна хранить единый признак «писать
  нельзя» с ровно одной причиной из перечня §3, отдельно от статуса жизненного цикла
  канала и не подменяя его.
- **R7.** Причину система должна классифицировать по мэппингу §3 (сигнал/ошибка →
  причина).
- **R8.** Если причина постоянная (`no_discussion`, `members_restricted`, `paid`),
  система должна оставлять канал read-only: не ротировать, не выходить, продолжать
  читать (в том числе для сбора DM-кандидатов), попытки отправки не инициировать.
- **R9.** Если причина переменная (`account_muted`, `account_kicked`,
  `not_participant`, `CHAT_WRITE_FORBIDDEN`), система должна считать канал кандидатом
  на ротацию.
- **R10.** Причину `not_participant` система должна трактовать как переменную
  (удаление приравнивается к бану) и вести к ротации, а не к read-only.
- **R11.** `until_date` система должна хранить справочно; снятие персонального
  ограничения должна фиксировать живой проверкой перед отправкой, без отдельной
  плановой переоценки срока.
- **R12.** Если получен `SLOWMODE_WAIT_N`, система не должна помечать канал «писать
  нельзя»; ограничение временное — ждать и повторять.
- **R13.** Если получен `PEER_FLOOD`, система не должна приписывать его конкретному
  каналу; это ограничение уровня аккаунта, обрабатывается на уровне агента.
- **R14.** При отказе отправки система должна обновлять признак и причину по коду
  ошибки; отказ-отправка — резервный источник, дополняющий проактивную проверку
  (причины `CHAT_WRITE_FORBIDDEN` и `paid` видны только реактивно).
- **R15.** Система не должна заметно повышать риск антиспам-ограничений аккаунта
  служебными проверками: постоянная величина снимается разово, переменная — живым
  вызовом только перед отправкой.
- **R16.** Сохранённый признак права система должна поддерживать согласованным с
  реальным состоянием: живая проверка перед прогоном отправок снимает признак, если
  ограничение снято, а отказ-отправка обновляет признак и причину по коду ошибки;
  расхождение не накапливается.
- **R17.** Если для канала в текущем прогоне зафиксирована причина «писать нельзя»
  (проактивно перед отправкой ИЛИ по первой же неудачной отправке), система не должна
  инициировать остальные отправки в этот канал в этом прогоне.

## 8. Критерии приёмки

- **AC-1 (R2, R3).** При вступлении агента в канал система один раз определяет в
  группе обсуждения, стал ли аккаунт участником и разрешает ли постоянная величина
  запись, и сохраняет результат; периодического перечитывания постоянной величины нет.
- **AC-2 (R8).** Если у канала нет привязанной группы обсуждения, фиксируется признак
  «писать нельзя» с причиной `no_discussion`, канал остаётся read-only.
- **AC-3 (R8).** Если постоянная величина запрещает запись всем рядовым участникам,
  фиксируется причина `members_restricted`, канал остаётся read-only.
- **AC-4 (R1, R4).** Перед отправкой комментария система выполняет живой
  `GetParticipant` в группе обсуждения и оценивает эффективное право (постоянная
  разрешает И переменная не ограничивает).
- **AC-5 (R5).** Если эффективное право даёт отправить хотя бы текст, отправка
  выполняется; типы контента при этом не различаются.
- **AC-6 (R6).** Если эффективное право не даёт писать, отправка не выполняется, а
  признак «писать нельзя» и причина обновляются; хранится ровно одна причина из
  перечня §3.
- **AC-7 (R7, R10).** Сигналы классифицируются в причины по мэппингу §3:
  `channelParticipantBanned` с `send_messages=true`, `left=false` → `account_muted`;
  `left=true` или `USER_BANNED_IN_CHANNEL` → `account_kicked`; `USER_NOT_PARTICIPANT`
  или `channelParticipantLeft` → `not_participant`; голый `CHAT_WRITE_FORBIDDEN` →
  `CHAT_WRITE_FORBIDDEN`; `ALLOW_PAYMENT_REQUIRED` → `paid`.
- **AC-8 (R9, R10).** Канал с переменной причиной (`account_muted`, `account_kicked`,
  `not_participant`, `CHAT_WRITE_FORBIDDEN`) остаётся кандидатом на ротацию.
- **AC-9 (R8).** Канал с постоянной причиной (`no_discussion`, `members_restricted`,
  `paid`) не ротируется и не покидается: агент продолжает его читать, попытки отправки
  по нему не инициируются.
- **AC-10 (R11).** Если ранее зафиксированное персональное ограничение снято (живая
  проверка показывает участника без запрета), признак «писать нельзя» снимается без
  отдельной плановой переоценки срока.
- **AC-11 (R12).** При `SLOWMODE_WAIT_N` канал не помечается «писать нельзя»;
  фиксируется временный характер.
- **AC-12 (R13).** При `PEER_FLOOD` ограничение не приписывается каналу и трактуется
  как ограничение всего аккаунта.
- **AC-13 (R14, R16).** При провале отправки признак и причина обновляются по коду
  ошибки; последующие решения используют обновлённое значение.
- **AC-14 (R17).** При зафиксированной в прогоне причине `cannot_write` для канала
  последующие отправки в этот канал в этом же прогоне не выполняются.
