# Требования: Право писать в канал

> **О чём документ.** Проблема, доменная модель, цель, требования и критерии приёмки —
> уровень бизнес-аналитики (что и почему, для кого). Техническое решение (как именно
> это реализуется) — в парном `architecture.md` (архитектор).
>
> Диаграмма домена — `participant-rights-model.puml` в этой же папке (иллюстрирует
> раздел «Доменная модель»).
>
> Модель проактивная: препятствия к записи определяются из статусов канала и участника
> **перед попыткой отправки комментария**, а не только по факту ошибки отправки.
> Реактивная классификация ошибок отправки сохраняется как резервный источник (R16).

## 1. Проблема и контекст

Комментарий к посту пишется в группу обсуждения broadcast-канала. Если о невозможности
писать узнавать только из ошибки отправки, платформа тратит попытку отправки (и
связанный антиспам-бюджет живого аккаунта), чтобы лишь затем узнать о запрете. При этом
часть препятствий известна из текущего состояния канала и участника **до** попытки:
аккаунт вышел из группы, аккаунт забанен, канал ограничен самим Telegram, включён
вступительный ценз или slow-mode.

Модель делает эти проверки проактивными: перед попыткой отправки проверяются статусы
канала (конструктор `Chat`, флаги `channel.*`) и статус участника (`ChannelParticipant`),
каждый обнаруженный статус фиксируется в журнале операций над каналом, а по каждому
выполняется однозначно заданное действие — авторотация, suspend, вступление, подача
заявки или запись события. Скрытые препятствия, невидимые проактивно (платные
сообщения, скрытые цензы, антиспам-бот/капча), остаются за реактивной обработкой ошибки
отправки (резерв).

Аудитория: платформа (автоматические скиллы отправки, ротации и вступления) и владелец,
разбирающий историю канала по журналу операций.

## 2. Цель

- Определять препятствия к записи **проактивно** — из статусов канала и участника перед
  попыткой отправки, а не только по факту ошибки.
- **Разделять уровень канала и уровень аккаунта**: препятствие, действующее для всех
  (ограничение канала самим Telegram, slow-mode), обрабатывать иначе, чем препятствие,
  касающееся только нашего аккаунта (выход, бан, потеря доступа, неучастие).
- **Вести историю по каналу**: каждый обнаруженный статус фиксировать в журнале операций
  над каналом (далее — ИО) с сопутствующими полями.
- **Применять к каждому статусу однозначно заданное действие** (§3.5), без обобщённой
  трактовки «писать нельзя».

## 3. Доменная модель

Термины и связи подтверждены официальной TL-схемой Telegram (см. §9 и
`participant-rights-model.puml`), не кодом проекта.

### 3.1. Термины

| Термин | Что это |
|---|---|
| Broadcast-канал | Канал вещания (`channel.broadcast`), откуда берутся посты; комментарии в нём напрямую не пишутся |
| Группа обсуждения | Супергруппа (`channel.megagroup`), привязанная к broadcast-каналу, куда пишутся комментарии |
| ИО | Журнал операций над каналом (`channel-operations`) — дом событий по каналу, куда записывается каждый обнаруженный статус |
| Авторотация | Постановка канала на передачу другому аккаунту платформы (распределение); применяется, когда препятствие касается только нашего аккаунта и смена аккаунта может помочь |
| Suspend | Приостановка канала (существующий статус с авто-снятием по таймеру); применяется, когда препятствие действует для всех аккаунтов и смена аккаунта не поможет |
| Уровень канала | Статус, действующий для всех рядовых участников (ограничение канала самим Telegram, slow-mode) |
| Уровень аккаунта | Статус, касающийся именно нашего аккаунта в этом канале (выход, бан, потеря доступа, неучастие) |
| Инвертированные флаги прав | В `ChatBannedRights` `true` = действие **запрещено**; `until_date` — срок (`0`, значение < 30 сек или > 366 дней = «навсегда») |

### 3.2. Тип `Chat` (контейнер канала)

Абстрактный TL-тип `Chat` возвращается одним из конструкторов; сам конструктор — уже
статус:

| Конструктор | Значение для домена |
|---|---|
| `chat` | Базовая группа; значим флаг `chat.left` (аккаунт вышел / не состоит) |
| `chatForbidden` | Базовая группа без доступа: доступ к чату потерян |
| `channel` | Канал/супергруппа; значимы флаги ниже |
| `channelForbidden` | Канал/супергруппа без доступа: доступ потерян |

Значимые флаги и поля `channel`:

| Поле | Флаг | Значение |
|---|---|---|
| `left` | `flags.2?true` | Аккаунт вышел / не состоит — уровень аккаунта |
| `restricted` | `flags.9?true` | Канал ограничен самим Telegram; при `true` заполнен `restriction_reason` — уровень канала |
| `restriction_reason` | `flags.9?Vector<RestrictionReason>` | Список причин; элемент `restrictionReason{ platform, reason, text }` |
| `slowmode_enabled` | `flags.22?true` | Включён slow-mode (интервал между сообщениями) — уровень канала, временный |
| `join_to_send` | `flags.28?true` | Писать может только вступивший; не-участник при отправке получает `CHAT_GUEST_SEND_FORBIDDEN` |
| `join_request` | `flags.29?true` | Вступление только по одобряемой заявке |
| `broadcast` / `megagroup` | `flags.5?` / `flags.8?` | Тип канала: вещание или супергруппа |

### 3.3. Тип `ChannelParticipant` (статус нашего аккаунта в канале)

| Конструктор | Значение для домена |
|---|---|
| `channelParticipant` / `channelParticipantSelf` / `channelParticipantAdmin` / `channelParticipantCreator` | Аккаунт состоит в канале |
| `channelParticipantBanned` | Аккаунт забанен/ограничен. Поля: `left` (`true` = выгнан; отсутствует = остался, но ограничен/мьют), `kicked_by:long`, `date:int`, `banned_rights:ChatBannedRights` |
| `channelParticipantLeft` | Аккаунт не состоит (только поле `peer`) |

### 3.4. Наборы прав

- `ChatBannedRights` — инвертированные флаги (`true` = запрещено), в т.ч. `send_messages`
  (`flags.1?true`) и `until_date:int`. Вложен в `channelParticipantBanned.banned_rights`
  (переменная, персональная) и в `channel.default_banned_rights` (постоянная, для всех).
- `ChatAdminRights` — прямые флаги (`true` = разрешено); в домене «право писать рядового
  участника» не участвует (значим лишь для ошибки `CHAT_ADMIN_REQUIRED`).

### 3.5. Статус → действие

| Статус / поле | Уровень | Действие |
|---|---|---|
| `channel.left = true` | аккаунт | авторотация |
| `chat.left` | аккаунт | авторотация |
| `chatForbidden` | аккаунт | авторотация |
| `channelForbidden` | аккаунт | авторотация |
| `channelParticipantBanned` | аккаунт | авторотация; в ИО — `kicked_by` + `date` + `banned_rights` |
| `channelParticipantLeft` | аккаунт | авторотация |
| `channel.restricted` | канал | suspend; причина `restriction_reason` в ИО; канал не читаем |
| `channel.restriction_reason` | канал | запись события в ИО (`platform`/`reason`/`text`) |
| `channel.slowmode_enabled` | канал | suspend временный (авто-снятие по таймеру) |
| `channel.join_to_send` (аккаунт не участник) | канал | вступить в группу обсуждения |
| `channel.join_request` | канал | подать заявку на вступление + сразу авторотация |
| `default_banned_rights.send_messages = true` (все рядовые участники замьючены) | канал | suspend бессрочный |
| `paid` / `ALLOW_PAYMENT_REQUIRED` (виден только реактивно) | канал | suspend бессрочный |

Разделение уровней задаёт разные действия: статусы **уровня аккаунта** ведут к
**авторотации** (другой аккаунт может сработать), статусы **уровня канала** ведут к
**suspend** или устраняющему действию (вступление / заявка), поскольку смена аккаунта
результата не изменит.

## 4. Ограничения среды

- У Telegram нет единого поля «можно ли писать». Право реконструируется из конструктора
  `Chat`, флагов `channel.*`, конструктора `ChannelParticipant` и вложенных
  `ChatBannedRights`.
- Проверка выполняется **перед попыткой отправки комментария**: статус участника — в
  группе обсуждения (комментарии пишутся туда); статусы доступа канала (`left`,
  `restricted`, `chatForbidden`/`channelForbidden`) актуальны и на broadcast-канале, и на
  группе обсуждения — проверяются на обоих.
- `slowmode_enabled` — штатное и временное состояние (снимается само); ведёт к
  **временному** suspend с авто-снятием, а не к постоянной приостановке.
- `restricted` — ограничение со стороны самого Telegram, постоянное и для всех; снятие не
  зависит от смены аккаунта, поэтому авторотация исключена.
- Проактивная проверка не видит скрытые препятствия (платные сообщения `paid`, скрытые
  цензы «только подписчики»/«состоять N дней», антиспам-бот/капчу) — они проявляются лишь
  ошибкой отправки; реактивная классификация остаётся резервным источником (R16).
- `GetFullChannel`/`GetParticipant` — служебные вызовы; их частота влияет на
  антиспам-риск. Проверка привязана к моменту перед отправкой (не к каждому чтению),
  чтобы не наращивать служебный трафик.

## 6. User Stories

**US-1 (R1, R2).** Как платформа, перед попыткой отправки комментария я хочу проверять
статусы канала (конструктор `Chat`, флаги `channel.*`) и статус участника
(`ChannelParticipant`) — на группе обсуждения и на broadcast-канале, — чтобы заранее знать
препятствие и применить заданное действие, а не узнавать о нём из провала отправки.

**US-2 (R3, R4).** Как владелец, я хочу, чтобы каждый обнаруженный статус фиксировался в
журнале операций над каналом (для `channelParticipantBanned` — с `kicked_by`, `date`,
`banned_rights`; для `restriction_reason` — с причинами ограничения), — чтобы иметь по
каждому каналу историю причин и дат.

**US-3 (R5).** Как платформа, я хочу различать статусы уровня канала (для всех) и уровня
аккаунта (только наш аккаунт), — чтобы ставить канал в suspend там, где смена аккаунта не
поможет, и на авторотацию там, где может.

**US-4 (R6, R7, R8, R9).** Как платформа, при статусе уровня аккаунта (`channel.left`,
`chat.left`, `chatForbidden`, `channelForbidden`, `channelParticipantBanned`,
`channelParticipantLeft`) я хочу ставить канал на авторотацию, — чтобы передать канал
другому аккаунту, для которого препятствие может отсутствовать.

**US-5 (R10, R12).** Как платформа, при статусе уровня канала (`restricted` — постоянно,
`slowmode_enabled` — временно) я хочу ставить канал в suspend (временный при slow-mode),
— чтобы не гонять по авторотации канал, где ни один аккаунт сейчас писать не сможет.

**US-6 (R13, R14).** Как платформа, при вступительном цензе (`join_to_send` — вступить;
`join_request` — подать заявку и передать канал ротацией) я хочу выполнять устраняющее
действие вместо простого отказа, — чтобы получить доступ к комментированию там, где он
открыт после вступления.

**US-7 (R16).** Как платформа, я хочу сохранить реактивную классификацию ошибок отправки
как резерв, — чтобы ловить препятствия, невидимые проактивно (`paid`, скрытые цензы,
`CHAT_WRITE_FORBIDDEN`).

## 7. Требования

- **R1.** Перед попыткой отправки комментария система должна проверять статусы канала
  (конструктор `Chat`; флаги `channel.left`, `restricted`, `restriction_reason`,
  `slowmode_enabled`, `join_to_send`, `join_request`) и статус участника
  (`ChannelParticipant`).
- **R2.** Статус участника, вступительные цензы (`join_to_send`, `join_request`,
  `ChannelParticipant`) и флаги права записи (`left`, `restricted`, `slowmode_enabled`,
  `default_banned_rights`) система должна проверять проактивно на **группе обсуждения**
  (комментарии пишутся туда). Потерю доступа к каналу (`chatForbidden`/`channelForbidden`/
  `CHANNEL_PRIVATE`) система должна распознавать реактивно при чтении и вести к
  авторотации. Флаг `restricted` самого broadcast-канала (канал читаем, но помечен
  Telegram) проактивно право записи NOT гейтит — комментирование определяется группой
  обсуждения.
- **R3.** При обнаружении каждого статуса из §3.5 система должна фиксировать событие в
  журнале операций над каналом (ИО, `channel-operations`).
- **R4.** При `channelParticipantBanned` система должна записать в ИО `kicked_by`, `date`
  и `banned_rights`; при заполненном `channel.restriction_reason` — причины ограничения
  (`platform`, `reason`, `text`).
- **R5.** Система должна различать статусы уровня канала (`restricted`, `slowmode_enabled`)
  и уровня аккаунта (`channel.left`, `chat.left`, `chatForbidden`, `channelForbidden`,
  `channelParticipantBanned`, `channelParticipantLeft`) и применять к ним разные действия
  по §3.5.
- **R6.** Если `channel.left = true` или `chat.left`, система должна ставить канал на
  авторотацию.
- **R7.** Если получен конструктор `chatForbidden` или `channelForbidden` (доступ
  потерян), система должна ставить канал на авторотацию.
- **R8.** Если статус участника — `channelParticipantBanned`, система должна ставить канал
  на авторотацию (запись полей в ИО — по R4).
- **R9.** Если статус участника — `channelParticipantLeft` (аккаунт не состоит), система
  должна ставить канал на авторотацию.
- **R10.** Если `channel.restricted = true`, система должна ставить канал в suspend,
  записать причину `restriction_reason` в ИО и прекратить чтение канала.
- **R11.** Если заполнено `channel.restriction_reason`, система должна записать событие в
  ИО (по R4).
- **R12.** Если `channel.slowmode_enabled = true`, система должна ставить канал во
  **временный** suspend с авто-снятием по истечении интервала (существующий механизм
  таймерного снятия suspend).
- **R13.** Если `channel.join_to_send = true` и аккаунт не состоит в группе обсуждения,
  система должна инициировать вступление в группу обсуждения существующим механизмом
  вступления.
- **R14.** Если `channel.join_request = true`, система должна подать заявку на вступление и
  сразу поставить канал на авторотацию (не дожидаясь одобрения).
- **R15.** При интерпретации `banned_rights` система должна учитывать инверсию флагов
  `ChatBannedRights` (`send_messages = true` = «отправка запрещена») и конвенцию
  `until_date` (`0`, < 30 сек или > 366 дней = «навсегда»).
- **R16.** Проактивная проверка статусов должна **дополнять**, а не заменять реактивную
  классификацию ошибок отправки; реактивная классификация остаётся резервным источником
  для препятствий, невидимых проактивно (`paid`, скрытые цензы, `CHAT_WRITE_FORBIDDEN`).
- **R17.** Если постоянная величина группы обсуждения запрещает запись всем рядовым
  участникам (`default_banned_rights.send_messages = true`), система должна ставить канал
  в suspend бессрочный (уровень канала — смена аккаунта не поможет), не в авторотацию.
- **R18.** Если при отправке получен `ALLOW_PAYMENT_REQUIRED` (`paid`), система должна
  ставить канал в suspend бессрочный (уровень канала). `paid` виден только реактивно —
  это резервная ветка (R16), проактивного сигнала нет.

## 8. Критерии приёмки

- **AC-1 (R1, R2).** Перед попыткой отправки система получает статус участника и флаги
  группы обсуждения; потеря доступа к каналу (`CHANNEL_PRIVATE`) распознаётся реактивно
  при чтении и ведёт к авторотации.
- **AC-2 (R3).** При обнаружении любого статуса из §3.5 в ИО появляется событие с этим
  статусом.
- **AC-3 (R4).** При `channelParticipantBanned` в ИО присутствуют `kicked_by`, `date`,
  `banned_rights`; при заполненном `restriction_reason` в ИО присутствуют `platform`,
  `reason`, `text`.
- **AC-4 (R5, R6, R7, R8, R9).** Для каждого статуса уровня аккаунта (`channel.left`,
  `chat.left`, `chatForbidden`, `channelForbidden`, `channelParticipantBanned`,
  `channelParticipantLeft`) канал ставится на авторотацию.
- **AC-5 (R10, R11).** При `channel.restricted = true` канал ставится в suspend, причины
  из `restriction_reason` записаны в ИО, чтение канала прекращено.
- **AC-6 (R12).** При `channel.slowmode_enabled = true` канал ставится во временный
  suspend и снимается автоматически по истечении интервала.
- **AC-7 (R13).** При `channel.join_to_send = true` и неучастии аккаунта инициируется
  вступление в группу обсуждения; авторотация и suspend не применяются.
- **AC-8 (R14).** При `channel.join_request = true` подаётся заявка на вступление и канал
  ставится на авторотацию.
- **AC-9 (R15).** Записанные и интерпретируемые `banned_rights` учитывают инверсию
  (`send_messages = true` = запрет) и конвенцию `until_date`.
- **AC-10 (R16).** Реактивная классификация ошибок отправки продолжает срабатывать как
  резерв для препятствий, не обнаруженных проактивной проверкой.
- **AC-11 (R17).** При `default_banned_rights.send_messages = true` в группе обсуждения
  канал ставится в suspend бессрочный (не авторотация), событие фиксируется в ИО.
- **AC-12 (R18).** При `ALLOW_PAYMENT_REQUIRED` канал ставится в suspend бессрочный;
  препятствие зафиксировано реактивной веткой и записано в ИО.
