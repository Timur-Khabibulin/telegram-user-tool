## 1. Контекст и принцип миграции

### 1.1. Проблема

Сейчас задачи `telegram-group-monitor`, `dm-send`, `dm-replies`,
`account-warmup`, `join-queue` выполняет LLM-агент OpenClaw по cron. Агент на
каждом прогоне ходит по десяткам инструментов — это дорого по токенам, хотя
логика детерминирована, а LLM нужна только для генерации текста.

### 1.2. Цель

Перенести логику в standalone TypeScript-скрипты, запускаемые планировщиком ОС
напрямую — без участия агента. Экономия токенов на оркестрации: плановые прогоны
~100 %, ручные ~95 %. OpenClaw остаётся тонким пультом управления расписанием.

### 1.3. Принцип: миграция, а не переработка

**Логика скиллов не меняется.** Она переносится один-в-один из формата `SKILL.md`
(где её исполняет LLM) в формат TypeScript-скрипта (где её исполняет код).
Поведение, лимиты, пороги, паузы и обработка ошибок каждого скилла сохраняются.
Единственное, что остаётся за LLM, — **генерация текста и JSON** (ответы, DM,
скоринг, выбор сообщений).

## 2. Требования

### 2.1. Функциональные

- Задачи разных типов работают по **разным расписаниям**.
- Расписанием можно управлять из Telegram: создать / остановить / запустить
  внепланово.
- Плановые прогоны **не тратят токены** на оркестрацию.
- Каждый прогон по завершении формирует **статус-отчёт** и записывает его в
  `runs`/journald (правило R-D1). Отчёт в Saved Messages рядовому агенту не
  отправляется (stop-agent-run-reports).

### 2.2. Ограничения (constraints)

1. **Не более одной задачи на агента одновременно** — две задачи с одной
   `sessionString` дают конфликт авторизации Telegram. Разные агенты —
   параллельно.
2. **Новая задача агента встаёт в очередь, а не пропускается.**
3. **Логирование не самописное** — системный механизм (journald).
4. **Контроль нагрузки** при росте числа агентов.
5. **Время прогона ограничено 1 часом.**

## 3. Правила выполнения

| # | Правило |
|---|---------|
| **R-A1** | Расписание задаётся **cron-выражением + часовой пояс** — этого достаточно, чтобы полностью описать период задачи (и интервальные «каждые N», и календарные «в 14:00»). |
| **R-D1** | Каждый прогон возвращает **статус-модель**: основной статус (`success`) и альтернативные (`error` и т. п.) + детали. Статус **записывается в `runs`** (per-agent `tasks.db`) и **эмитится строкой в journald**; отчёт в Saved Messages рядовому агенту не отправляется (stop-agent-run-reports). **`nextRun` сдвигается всегда** — и при успехе, и при ошибке (задача с ошибкой не застревает назревшей, а идёт в следующий плановый срок). Прогон ограничен **1 часом**. |
| **R-A3** | Конечные задачи (`join-queue`) завершаются через **терминальный статус**: когда очередь исчерпана, прогон возвращает признак завершения, по которому задача **выключается** (перестаёт выбираться планировщиком). Пока очередь не пуста — ведёт себя как обычная периодическая. |
| **R-B2** | Логика всех скиллов переносится в код **без изменения поведения**; за LLM — только генерация текста/JSON (см. 1.3). |

## 4. Идентификаторы и данные

| # | Правило |
|---|---------|
| **R-E1** | `agentId === agentName` — единый идентификатор агента (он же передаётся диспетчеру). |
| **R-E2** | Персона агента — `SOUL.md` в папке агента, создаваемой скиллом `tg-agent-create`. Это единственный источник истины для персоны. |
| **R-E3** | Один `accountId` (Telegram-сессия) обслуживает ровно одного агента (один-к-одному). |
| **R-D2** | Данные переносятся бесшовно: пути БД и `tg-account.json` не меняются — треды, кандидаты, cooldown, `sessionString` работают без миграции данных. |
