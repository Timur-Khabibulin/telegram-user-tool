# Планировщик задач Telegram-агентов: архитектура

> **О чём документ.** Как реализован планировщик standalone-задач: структура
> кода, диспетчер, расписание, systemd, поведение во времени, решения.
>
> **Парный документ:** [requirements.md](./requirements.md) — *что* система
> делает и по каким правилам (R-*). LLM-слой — [llm-layer.md](./llm-layer.md).
> **Граница:** здесь — механизмы и структура; требования и правила задаются в
> `requirements.md`, сюда не дублируются — только ссылки на R-*.

---

## 1. Обзор решения

**Один systemd-юнит на агента — диспетчер.** Юнит `tg-agent@<agentId>.service`
запускает `dispatcher.ts`, который по БД определяет, какие задачи агента назрели,
и выполняет их **последовательно** в одном процессе.

### 1.1. Ключевой принцип: очередь принадлежит агенту, а не типу задачи

Вывод из ограничения «1 задача на агента» (requirements §2.2.1). Раз ресурс
(сессия Telegram) общий для всех задач агента, точка сериализации одна — на
агента. Все типы задач проходят через один диспетчер, поэтому параллельных задач
внутри агента не бывает по построению, без внешних локов.

Это паттерн **Actor Model** (актор = агент, mailbox = очередь запусков) и **Kafka
partitioning** (ключ = `agentId`): сериализация по ключу, параллелизм между
ключами.

### 1.2. Схема верхнего уровня

```
┌──────────────────────────────────────────────────────────┐
│  tg-agent@agent1.timer   (heartbeat, напр. каждые 10 мин) │
│  tg-agent@agent2.timer   (heartbeat, сдвинут RandomizedDelaySec) │
└──────────┬───────────────────────┬───────────────────────┘
           │ start-job             │ start-job
┌──────────▼──────────┐  ┌─────────▼───────────┐
│ tg-agent@agent1     │  │ tg-agent@agent2     │   ← параллельно
│  dispatcher.ts      │  │  dispatcher.ts      │
│   читает tasks (БД) │  │   читает tasks (БД) │
│   → monitor         │  │   → dm-send         │
│   → dm-send         │  │                     │
│  (последовательно)  │  │                     │
└──────────┬──────────┘  └─────────────────────┘
           │ stdout
┌──────────▼──────────────────────────────────┐
│  journald → journalctl -u tg-agent@agent1   │
└──────────────────────────────────────────────┘

Все юниты входят в slice tg-agents.slice (общие лимиты ресурсов).
```

## 2. Структура каталогов

Отражает слои: чистое ядро → оркестрация → точка входа, плюс изолированный
LLM-слой. Один источник логики для плагина и диспетчера.

```
src/
├── core/                     # чистое ядро, без импортов OpenClaw
│   ├── telegram/             # MTProto: connect, dialogs, messages, send, reply, peerCache
│   ├── db/                   # channels, dm-threads, join-queue, replies, tasks
│   ├── config.ts             # загрузка tg-account.json, пути к данным
│   └── logger.ts             # интерфейс Logger { info, warn, error }
│
├── llm/                      # LLM-слой (см. llm-layer.md)
│   ├── client.ts             # LlmClient: codex primary + fallback
│   └── prompts.ts            # каталог промптов
│
├── skills/                   # оркестрация — портированная логика скиллов (R-B2)
│   ├── monitor.ts            # runMonitor
│   ├── dm-send.ts            # runDmSend
│   ├── dm-replies.ts         # runDmReplies
│   ├── account-warmup.ts     # runAccountWarmup
│   └── join-queue.ts         # runJoinQueue (конечная, R-A3)
│
├── scripts/
│   └── dispatcher.ts         # точка входа: --agent <id>; создаёт схему tasks
│
└── index.ts                  # OpenClaw-плагин — тонкая обёртка над core/

deploy/
└── systemd/                  # инфраструктура (§3.5)
    ├── tg-agent@.service
    ├── tg-agent@.timer
    └── tg-agents.slice
```

- `core/` и `llm/` не знают про планировщик и OpenClaw.
- `skills/` — сегодняшние `SKILL.md`, переписанные в код (R-B2), зовут `core/` и
  `llm/`.
- `dispatcher.ts` выбирает назревшие задачи и вызывает нужный `skills/*`.
- `index.ts` остаётся обёрткой над `core/` — без второй копии логики.

## 3. Строительные блоки

### 3.1. Ядро `core/`

Чистые модули без единого импорта OpenClaw:

- Telegram-операции (connect, get_dialogs, get_messages, send_dm, reply),
  `peerCache`, `ensureClient`.
- Вся SQL-логика (`channels-db`, `dm-threads-db`, `join-queue-db`, `replies-db`,
  `tasks`).
- Логика вынута из тел `execute()` в обычные экспортируемые функции.

Используется и диспетчером, и плагином OpenClaw — одна копия логики.

### 3.2. Диспетчер `dispatcher.ts`

Точка входа на агента. Запускается как `dispatcher.ts --agent <agentId>`.

```
0. создать схему tasks, если её нет (идемпотентно)
1. загрузить tg-account.json агента
2. SELECT задачи где enabled=1 AND nextRun <= now()   ← что назрело
3. если пусто → выйти (за секунду, токены не тратятся)
4. connect к Telegram (один клиент на весь прогон)
5. для каждой назревшей задачи последовательно:
      выполнить (monitor / dm-send / dm-replies / …)
      сформировать статус-модель, записать в runs + journald            (R-D1)
      UPDATE lastRun = now(),
             nextRun = cron-parser(schedule, tz).next()              (R-D1: всегда)
      если задача вернула терминальный статус → enabled = 0          (R-A3)
6. disconnect, выйти
```

Один процесс на прогон — поэтому параллельных задач агента не существует.
Реализует правила R-D1 (статус/запись в БД/безусловный сдвиг `nextRun`) и R-A3
(самовыключение конечных задач). Отчёт в Saved Messages рядовому агенту больше
не отправляется (stop-agent-run-reports) — наблюдаемость прогонов через `runs`
(таблица `run-log`) и journald.

### 3.3. Таблица расписания `tasks`

Хранит расписание в БД, а не в таймере (см. ADR §6.5). Поле `schedule` —
cron-выражение + `tz` (R-A1). Схему создаёт диспетчер при старте (§3.2, шаг 0).

```
agentId | type       | schedule     | tz                 | lastRun | nextRun  | enabled
--------|------------|--------------|--------------------|---------|----------|--------
agent1  | monitor    | 0 */3 * * *  | Asia/Yekaterinburg | 12:00   | 15:00    | 1
agent1  | dm-send    | 0 14 * * *   | Asia/Yekaterinburg | 14:00   | next 14:00 | 1
agent1  | dm-replies | */30 * * * * | Asia/Yekaterinburg | 12:00   | 12:30    | 1
```

Уникальность по `(agentId, type)`; выборка по `(enabled, nextRun)`. После каждой
задачи диспетчер пересчитывает срок:
`nextRun = cronParser.parseExpression(schedule, { tz, currentDate: now }).next()`.

Лежит в `~/.openclaw/workspace-<agentId>/tasks.db` рядом с остальными БД агента.
Существующие cron-расписания переносятся 1:1 — выражение и TZ те же, что в
setup-скиллах.

### 3.4. Конечные задачи (R-A3)

`join-queue` обрабатывает очередь каналов батчами. Когда очередь пуста, прогон
возвращает терминальный статус, и диспетчер выставляет `enabled=0` — таймер
перестаёт выбирать задачу. Пока очередь не пуста — обычная периодическая задача
(сдвиг `nextRun`, следующий батч). Отдельного механизма самоудаления не нужно:
«конечность» = терминальный статус прогона.

### 3.5. systemd: сервис + таймер + slice

```ini
# tg-agent@.service  — шаблон, %i = agentId
[Service]
Type=oneshot
ExecStart=/usr/bin/npx tsx /opt/tg/current/scripts/dispatcher.ts --agent %i
Slice=tg-agents.slice
TimeoutStartSec=3600       # потолок времени прогона — 1 час (R-D1)

# tg-agent@.timer  — heartbeat
[Timer]
OnCalendar=*:0/10          # проверять каждые 10 минут
RandomizedDelaySec=60      # разнести старты агентов во времени

# tg-agents.slice  — общие лимиты на всех агентов
[Slice]
CPUQuota=60%
MemoryMax=1G
ConcurrencySoftMax=4       # одновременно не более 4 диспетчеров
```

#### Где лежат юниты

На диске — **три файла, независимо от числа агентов** (шаблоны, `@` в имени):

```
/etc/systemd/system/
├── tg-agent@.service     ← один шаблон на всех агентов
├── tg-agent@.timer       ← один шаблон на всех агентов
└── tg-agents.slice       ← один slice на всех агентов
```

Под агента создаётся не файл, а **инстанс** шаблона: при
`systemctl enable --now tg-agent@agent1.timer` systemd подставляет `%i = agent1`
и кладёт симлинк-указатель «включён» в `timers.target.wants/`. Добавление N-го
агента не плодит конфиги — только один `systemctl enable`.

#### Установка юнитов

Эти три файла — **инфраструктура сервера**, не часть релиза кода. Кладутся один
раз; при обновлении кода не трогаются.

```bash
cp deploy/systemd/tg-agent@.service /etc/systemd/system/
cp deploy/systemd/tg-agent@.timer   /etc/systemd/system/
cp deploy/systemd/tg-agents.slice   /etc/systemd/system/
systemctl daemon-reload
```

`daemon-reload` нужен только при изменении самих шаблонов, не при обновлении кода.

### 3.6. OpenClaw-скилл — пульт управления

Скилл **не запускает задачу напрямую**. Он управляет строками в `tasks` и
включает/выключает heartbeat-таймер агента:

```sql
INSERT INTO tasks (agentId, type, schedule, tz, nextRun, enabled)
VALUES ('agent1', 'dm-send', '0 14 * * *', 'Asia/Yekaterinburg', <calc>, 1)
ON CONFLICT(agentId, type) DO UPDATE SET schedule=excluded.schedule, enabled=1;
```

- Первая задача агента → дополнительно `systemctl enable --now tg-agent@agent1.timer`.
- Вторая задача тому же агенту → только INSERT (таймер уже крутится).
- Немедленный прогон → `UPDATE ... SET nextRun='now'` + `systemctl start tg-agent@<agentId>.service`.
- Не осталось активных задач → `systemctl disable --now ...timer`.

### 3.7. LLM-слой

Генерация текста (ответы, DM, скоринг, выбор сообщений) — прямые вызовы LLM на
подписке Codex OAuth с failover. Детальный дизайн — отдельный Design Doc
[llm-layer.md](./llm-layer.md).

## 4. Поведение во времени

### 4.1. Плановый прогон

```
12:00  timer → start-job → сервис свободен → диспетчер стартует
        tasks: dm-send назрел → выполняет → записывает runs → сдвигает nextRun → выходит
```

### 4.2. Перекрытие прогонов (главный сценарий)

```
12:00  диспетчер выполняет dm-send (занимает 25 мин)
12:10  timer → сервис занят → job в очередь systemd      очередь: [1]
12:20  timer → job уже есть → COALESCING (слияние)        очередь: [1]
12:25  диспетчер завершился → systemd берёт job → стартует снова
        tasks: dm-replies назрел → выполняет
```

**Очередь к агенту всегда максимум 1** (coalescing) — выполнение ограничения
«очередь, не пропуск» встроенными средствами systemd, без `flock`. Часть тиков
штатно попадает в занятый сервис и встаёт в очередь — это норма, лишние процессы
не плодятся. «Повторный» запуск чаще всего отрабатывает вхолостую за секунду
(`SELECT` + `exit`, connect к Telegram только если что-то назрело).

### 4.3. Выбор интервала heartbeat (тик ≠ период задачи)

Интервал таймера — это **granularity планирования**, не период задач (периоды в
`nextRun`). Тик задаёт максимальную задержку старта: задача с `nextRun=13:00` при
тике 10 мин выполнится в `[13:00, 13:10]`.

| Тик | Холостых прогонов | Задержка старта |
|---|---|---|
| 1 мин | много (но каждый ~секунда) | ≤ 1 мин |
| 10 мин | умеренно | ≤ 10 мин |
| 30 мин | мало | ≤ 30 мин |

Правило: **тик мельче самого короткого периода задачи**. Минимум — `dm-replies`
(30 мин), тик 10 мин достаточен. Фиксированный heartbeat проще динамического
перепланирования (последнее — оптимизация на будущее).

### 4.4. Внеплановый запуск из Telegram

```
скилл: UPDATE tasks SET nextRun='now' WHERE agentId='agent1' AND type='dm-send'
скилл: systemctl start tg-agent@agent1.service
  свободен → стартует сразу, видит nextRun=now → выполняет
  занят    → start-job коалесцируется → выполнит после текущего прогона
```

### 4.5. Завершение, краш, таймаут

Диспетчер `Type=oneshot` — при любом завершении сервис → `inactive`. Два исхода:

- **Нормальное завершение (success или error).** Задача дошла до конца, статус
  записан в `runs`, `nextRun` сдвинут (R-D1) — повтора в этот же срок нет.
- **Краш или убийство по таймауту** (`TimeoutStartSec`, 1 ч). Процесс умер до
  `UPDATE` → `nextRun` не сдвинут → задача осталась назревшей и выполнится на
  следующем тике.

Повторный прогон не задваивает работу: модель идемпотентна между запусками
(`mark_as_read` сразу после чтения, прогресс по каналам в `lastProcessedAt`).

## 5. Сквозные аспекты

### 5.1. Сериализация задач агента

- **Внутри прогона** — задачи последовательны в одном процессе (одна сессия).
- **Между прогонами** — systemd job coalescing не даёт второй экземпляр юнита
  (очередь = max 1).

Внешний лок (`flock`) не нужен — точка сериализации одна по построению.

### 5.2. Логирование

Приложение пишет в **stdout** (12-factor); systemd направляет его в **journald**
с тегом юнита — строки параллельных агентов не перемешиваются.

```bash
journalctl -u tg-agent@agent1        # один агент
journalctl -u "tg-agent@*" -f        # все агенты в реальном времени
```

Ротация — через `journald.conf`. Внутри `core/` — инжектируемый интерфейс
`Logger`: плагин передаёт `api.logger`, диспетчер — свой (stdout). Гейт уровня
через `LOG_LEVEL` (GramJS DEBUG шумный). Логи (journald) ≠ команды (чат с
ботом) — разные каналы; отчёт о прогоне в Saved Messages рядовому агенту не
отправляется (stop-agent-run-reports), статус прогона — в `runs` (R-D1).

### 5.3. Контроль ресурсов

Все агенты в `tg-agents.slice`:

- `CPUQuota` / `MemoryMax` — потолок суммарной нагрузки группы.
- `ConcurrencySoftMax=N` — одновременно активны не более N диспетчеров;
  остальные ждут в очереди job'ов systemd (не падают). Встроенный семафор.

`RandomizedDelaySec` в таймере разносит старты во времени.

## 6. Архитектурные решения (ADR)

### 6.1. Почему systemd, а не cron

cron не имеет понятий лока и очереди: каждый тик форкает процесс вслепую,
перекрытия исполняются параллельно. systemd даёт single-instance (coalescing),
очередь job'ов и логирование (journald) из коробки.

### 6.2. Почему диспетчер, а не «юнит на задачу» + flock

Альтернатива (юнит на тип задачи + общий `flock`) даёт: очередь в ядре без
гарантии порядка; рост числа «спящих» процессов в `activating`. Диспетчер убирает
flock: один процесс на агента, очередь — нативный systemd job queue (max 1).

### 6.3. Почему не Redis / BullMQ / Kafka / Celery сейчас

- **BullMQ + Redis** — готовый job queue, но требует Redis. Оправдан при 20+
  агентах. Целевой путь миграции (§7.4).
- **Kafka** — потоковая обработка, оверкилл.
- **Celery** — Python; проект на TS.

Для масштаба < 20 агентов systemd dispatcher покрывает требования без зависимостей.

### 6.4. Почему возим исходники, а не бинарник

`better-sqlite3` нативный — `.node` нельзя вшить, ставится на сервере отдельно.
Возим исходники (`core/` + `skills/` + `scripts/`), запуск через `tsx`.

### 6.5. Почему расписание в БД (cron-выражение), а не в таймерах / `intervalSec`

Один `.timer` триггерит один `.service` — разные периоды в одном таймере не
описать. Периоды в `tasks` + heartbeat решают это. cron-выражение (а не
`intervalSec`) нужно, т.к. есть календарные расписания (`dm-send` `0 14 * * *`),
которые `intervalSec` выразил бы с дрейфом (R-A1).

## 7. План миграции

### 7.1. Вынос логики в `core/`

Снять завязки на OpenClaw, оставив плагин обёрткой над `core/`:

| Точка | Где | Как снять |
|---|---|---|
| `definePluginEntry` | `index.ts` | в скриптах не нужен |
| `api.registerTool` | все файлы | функции зовутся напрямую |
| формат `{ content: [...] }` | все файлы | обычные объекты |
| TypeBox-схемы `Type.Object` | инструменты | обычные TS-аргументы |
| тип `PluginLogger` | `index.ts` + db | свой `Logger` интерфейс |
| path-алиасы `../openclaw/...` | `tsconfig.json` | убрать после выноса типов |

Портируется как есть: GramJS-операции, SQL-логика, `replies-db.ts`, загрузка
конфига, пути к данным.

### 7.2. Дисциплина перехода

Пока агент не переведён полностью — он обслуживается **ЛИБО** OpenClaw, **ЛИБО**
скриптами, не обоими (иначе два клиента на одной сессии).

### 7.3. Дистрибутив и обновление

- **Код** — заливать в любой момент; идущий процесс доработает на старом, новый
  подхватится следующим запуском.
- **Библиотеки** — `npm install` нельзя при работающем воркере (подмена нативного
  `.node` → краш); ставить в окно простоя.
- **Приём** — релизы в папки с датой + атомарный симлинк `current`; откат =
  вернуть симлинк.

### 7.4. Путь на BullMQ при росте

Бизнес-логика (`core/`, `skills/`) не трогается. Меняется слой «как задача
попадает в диспетчер»: systemd timer → BullMQ repeat-jobs, `tasks` → очередь
Redis с `globalConcurrency: 1`. Триггеры: видимость очереди, retry с backoff,
агентов 20+.

## 8. Риски и открытые вопросы

- **Версия systemd.** `ConcurrencySoftMax` появился в systemd 261 — проверить
  версию; если старее, ограничивать через `CPUQuota` слайса.
- **Долгий прогон дольше периода.** При прогоне регулярно длиннее интервала
  задача начнёт «отставать» (coalescing спасает от наложения) — нужен мониторинг
  длительности.
- **LLM-лимиты / эндпоинт** — см. [llm-layer.md](./llm-layer.md) §9.
