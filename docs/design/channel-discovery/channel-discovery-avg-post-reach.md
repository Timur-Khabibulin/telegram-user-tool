# Design Doc: Channel Discovery — гейт по среднему охвату публикации

> Аналитика фичи для человека. Объясняет, что делает система и как, и почему так
> решили. Нормативное поведение (требования + сценарии) — в `openspec/`, не здесь.
> Базовая архитектура: `channel-discovery-v1.md`. Этот документ — аддитивная фича
> поверх v1.

---

## 1. Проблема / Контекст

Channel Discovery v1 отсекает каналы только по числу подписчиков. Размер — ненадёжный прокси качества: каналы с десятками тысяч подписчиков, но мёртвой аудиторией (низкий охват, накрученные боты) проходят единственный гейт и засоряют список каналов агентов.

Нужен второй порог, который отсекает «крупные, но мёртвые» каналы до того, как они попадут в очередь вступления.

TGStat предоставляет готовый агрегированный средний охват публикации для каждого найденного канала. Если агрегатор не располагает данными — охват считается вручную по последним постам канала через Telegram.

Аналог этого гейта есть в скилле `discovery-similar`: там охват всегда считается вручную через Telegram, так как TGStat не используется. Здесь основной источник — агрегатор, Telegram как резерв.

---

## 2. Бизнес-требования

**BR-1.** Агенты должны вступать только в каналы с живой аудиторией. Канал с низким охватом не даёт ни DM-кандидатов, ни ответов на реплики — его мониторинг пустой расход ресурсов агента.

**BR-2.** Порог среднего охвата оператор задаёт через скилл при запуске discovery. Значение зависит от ниши и языка аудитории — системного дефолта нет.

**BR-3.** Если оператор не задал порог, фильтр по охвату не применяется и поведение остаётся как в v1.

**BR-4.** Если агрегатор не вернул данные об охвате — система вычисляет средний охват вручную по последним публикациям канала. Если и это не удалось — канал не проходит гейт.

**BR-5.** Количество каналов, отсеянных по гейту охвата, отражается в отчёте оператору.

**BR-6.** Аккаунт, используемый для ручного вычисления охвата, задаётся оператором через скилл. Без указанного аккаунта ручное вычисление не производится и канал не проходит гейт.

---

## 3. Цели

- Отсекать «крупные, но мёртвые» каналы по среднему охвату публикации до вступления.
- Не усложнять запуск: гейт включается только если оператор задал порог — без порога поведение v1 без изменений.
- Не менять структуру реестра `discovered_channels`, `join_queue` и flow вступления.

---

## 4. Как работает

Оператор задаёт параметры как раньше (ключевые слова, `n`, `minSubscribers`). Опционально добавляет `min_avg_post_reach` и `agent_id` (агент-аккаунт для резервного расчёта).

Если `min_avg_post_reach` задан, скрипт для каждого кандидата, прошедшего дедуп и гейт по подписчикам:

1. Запрашивает TGStat `channels/stat` с `channelId = tgId` кандидата.
2. Читает `avg_post_reach` из ответа.
3. Если `avg_post_reach <= min_avg_post_reach` — кандидат отсеивается.
4. Если вызов завершился ошибкой (HTTP-ошибка, `status != "ok"`) — система переходит к резервному расчёту: читает последние публикации канала через агент-аккаунт, заданный оператором, и вычисляет средний охват по просмотрам (BR-4, BR-6). Если у кандидата нет доступного идентификатора для обращения к каналу — кандидат отсеивается без резервного запроса.

Кандидаты, прошедшие оба гейта, идут в round-robin и `join_queue` как раньше.

**Обновлённый порядок гейтов:**

```
channels/search
  → нормализация ссылки
  → дедуп против реестра (isKnownChannel)
  → гейт: подписчики (participantsCount >= minSubscribers)
  → гейт: avg_post_reach  [НОВЫЙ — только если min_avg_post_reach задан]
  → registerChannel → addJoinQueue
```

Дедуп идёт до обоих гейтов: нет смысла запрашивать стат по уже известному каналу. Гейт по подписчикам идёт перед вызовом `channels/stat`: нет смысла тратить API-вызов на канал, который отсеется более дешёвой проверкой.

**Отчёт оператору:** к существующим строкам добавляется счётчик кандидатов, отсеянных по новому гейту. Строка показывается только если `min_avg_post_reach` был задан (BR-5).

## 5. Архитектура

### Новая функция в `tgstat.ts`

`getChannelStat(tgId: number, token: string, log: Logger): Promise<{ avgPostReach: number }>`

Вызывает GET `channels/stat?channelId=<tgId>&token=<token>` через существующий `callApi`. Бросает ошибку при HTTP != 2xx или `status != "ok"`. Возвращает только `avgPostReach` (поле `avg_post_reach` из ответа) — ничего лишнего.

Комментарий-шапка модуля обновляется: `channels/stat` теперь используется и должен быть перечислен в списке методов.

### Изменения в `run.ts`

**`RunParams`:** добавляется поле `minAvgPostReach?: number` — опционально, без дефолта (BR-2, BR-3). Если не задано — гейт не применяется. Добавляется поле `avgReachAgentId?: string` — идентификатор агент-аккаунта для резервного MTProto-расчёта охвата (BR-6).

**`RunResult`:** добавляется поле `rejectedByAvgReach: number` — счётчик кандидатов, отсеянных новым гейтом (включая fail-closed). Всегда присутствует; при отключённом гейте равен 0.

**Цикл в `runDiscovery`:** после гейта `minSubscribers`, если `p.minAvgPostReach` задан:

- Если `c.tgId == null` — `rejectedByAvgReach++`, `continue` (fail-closed).
- Вызов `getChannelStat(c.tgId, ...)`. При ошибке — `rejectedByAvgReach++`, `continue` (fail-closed, BR-4).
- Если `stat.avgPostReach <= p.minAvgPostReach` — `rejectedByAvgReach++`, `continue`.

**`renderReport`:** если `p.minAvgPostReach` был задан — добавить строку `• отсеяно по охвату: <rejectedByAvgReach>` (BR-5).

### Изменения в `skills/channel-discovery/SKILL.md`

**Шаг 1** — добавить два необязательных параметра:

> • *(необязательно)* **min_avg_post_reach** — минимальный средний охват публикации
>   (просмотры на пост по данным TGStat). Если не указан — фильтр по охвату не
>   применяется.
>
> • *(необязательно)* **agent_id** — идентификатор агент-аккаунта платформы для
>   самостоятельного расчёта охвата при недоступности данных агрегатора (BR-6).

**Шаг 3** — добавить `minAvgPostReach` и `avgReachAgentId` в аргументы `tg_discovery_run` (если заданы).

### Что не меняется

`discovery.db` (схема `discovered_channels`), `join_queue`, `monitor`, round-robin, дедуп.

## 6. Альтернативы

### ERR% вместо avg_post_reach

TGStat `channels/stat` возвращает и `err_percent` — вовлечённость, нормированную по подписчикам. ERR сравнимее между каналами разного размера. Однако минимальный порог по подписчикам уже задан, выборка относительно однородна. Средний охват понятнее оператору — «1 000 просмотров на пост» проще для интерпретации, чем «1.2% ERR». Оставляем `avg_post_reach`.

### Считать охват через MTProto (как в discovery-similar)

Запрашивать последние посты канала через Telegram-сессию — актуальные данные, независимость от TGStat. Как основной (единственный) источник вместо TGStat — отклонено: TGStat агрегирует показатель без аутентифицированного сеанса, дешевле и быстрее. Как резервный источник при недоступности данных агрегатора — принято (BR-4, BR-6): сессия задействуется только в fallback-случаях, что оправдывает архитектурную стоимость.

### Fail-open при ошибке channels/stat

Если стат недоступен — пропускать кандидата в очередь. Не теряем потенциальных кандидатов при временных ошибках API. Но неизвестный охват — риск засорить очередь каналами, которые гейт должен был отсечь. Отклонено в пользу резервного MTProto-расчёта (BR-4): данные получаем независимо от агрегатора, решение принимается на основе реальных значений.

### Обязательный параметр

Симметрично `minSubscribers` — явно требует осознанного выбора от оператора. Но если цель — только фильтр по подписчикам, параметр превращается в помеху. Оставляем опциональным (BR-3).

## 7. Метрики успеха

- **`rejectedByAvgReach` в отчёте прогона** — если 0 при заданном пороге, порог слишком низкий или стат по каналам системно недоступен.
- **Инвариант резервного расчёта** — при ошибке TGStat канал не отсеивается без попытки самостоятельного расчёта через агент-аккаунт; счётчик `rejectedByAvgReach` при ошибке агрегатора не должен расти, если MTProto-расчёт дал результат.
- **API-расход** — число вызовов `channels/stat` за прогон равно числу кандидатов, прошедших дедуп и гейт подписчиков. Оператор отслеживает через TGStat-кабинет. Без `min_avg_post_reach` расход нулевой — поведение v1.

## 8. Future Work

- **ERR% как дополнительный порог** рядом с `avg_post_reach` — аналог `minEngagementRate` из `discovery-similar`. Отложено: один параметр проще для первого запуска фичи.
- **Кеш `channels/stat` внутри прогона** — сейчас не нужен (дедуп убирает повторные вхождения одного канала по разным ключевым словам до вызова стата). Актуален при multi-pass логике.
