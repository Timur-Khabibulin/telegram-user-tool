# Design Doc: Поиск каналов и вступление — v1

> Аналитика фичи для человека. Объясняет, что делает система и как, и почему так
> решили. Нормативное поведение (требования + сценарии) — в `openspec/`, не здесь.
> Версии: `channel-discovery-v1.md`, `-v2.md`, … — новая версия при существенном
> изменении фичи; актуальна последняя.

## 1. Проблема / Контекст

Платформа запускает несколько Telegram-агентов; каждому нужен поток профильных
каналов для мониторинга и DM-воронки. Ручной подбор каналов не масштабируется на рост
числа агентов. Без централизации разные агенты вступали бы в одни и те же каналы —
дублируя работу и пересекаясь между собой.

Нужен централизованный поиск каналов из внешних источников, единый реестр без дублей
и раскладка каналов по агентам так, чтобы они **не пересекались**.

## 2. Цели

**Автоматизировать поиск Telegram-каналов и их загрузку в агентов** — заменить ручной
подбор и распределение каналов автоматическим конвейером.

Задачи, ведущие к цели:

- Централизованный поиск новых каналов по теме (ключевые слова).
- Единый реестр всех найденных каналов с дедупликацией.
- Раскладка по агентам без пересечений: один канал — один агент, навсегда.
- Отбор по качеству: порог подписчиков (ПДП) + вовлечённость (ER).
- Доставка назначенных каналов в очередь вступления агента (`join_queue`).

## 3. Как работает

Разделы ниже идут в порядке выполнения — от запроса оператора до вступления агента.

### 3.1 Два контура

Центральный оркестратор (один на всю платформу, глобальный взгляд) и агент (существующая
машинерия).

**Контур 1 — Центральный оркестратор:**

1. **Discovery — поиск каналов** из внешних источников.
2. **Единый реестр** — найденные каналы складываются в одну общую базу, дубли
   отсекаются.
3. **Assignment — распределение по агентам** так, чтобы у разных агентов они **не
   пересекались**.
4. **Push — доставка** назначенных каналов в очередь вступления агента (`join_queue`).

**Контур 2 — Агент (существующее):**

5. **Постепенное вступление** — задача `join-queue` берёт каналы из очереди и вступает.
6. **Подхват в мониторинг** — после вступления канал появляется в диалогах и
   автоматически подхватывается `monitor` (`syncChannels`) в таблицу `channels`.
7. **Обработка** — `monitor` обрабатывает канал в общем цикле.

```
[ЦЕНТР, периодически]
  discovery → единый реестр (dedupe) → assignment (без пересечений)
            → push в join_queue агента
                     │
                     ▼
[АГЕНТ, по расписанию]
  join-queue → постепенно вступает
  monitor    → syncChannels подхватывает канал → обрабатывает
```

### 3.2 Кто что исполняет

Три исполнителя с разной природой запуска. Граница важна: всё детерминированное — в
скрипте, LLM — только генерация текста (ключевых слов).

| Этап | Исполнитель | Запуск | LLM |
|---|---|---|---|
| Ввод сферы | OpenClaw-скилл | по запросу оператора | — |
| Подсказка ключевых слов | OpenClaw-скилл | по запросу | ✅ генерация |
| Уточнение списка | OpenClaw-скилл | по запросу | — |
| Поиск, фильтр, отбор | discovery-скрипт | батч | нет |
| Дедуп в реестр | discovery-скрипт | батч | нет |
| Assignment по агентам | discovery-скрипт | батч | нет |
| Push в `join_queue` | discovery-скрипт | батч | нет |
| Вступление | per-agent `join-queue` | по расписанию (systemd) | нет |

**discovery-скрипт не использует LLM** — поиск, фильтр по подписчикам, расчёт ER,
дедуп, делёж списка детерминированы. Это согласуется с принципом «LLM только для
текста».

### 3.3 Поток оператора (UC-1: поиск по сфере)

- **Актор:** оператор. **Когда:** хочет найти каналы по теме, но не знает заранее
  точных ключевых слов.
- **Поток:**
  1. Оператор свободно вводит сферу (например, «психология»).
  2. LLM предлагает ключевые слова по этой сфере.
  3. Оператор уточняет список — что-то оставляет, что-то убирает/добавляет.
  4. Оператор задаёт `N` (целевое число каналов), `min_subscribers` и `er_min`. Перед
     запросом порога ER скилл в первом сообщении объясняет, **как считается ER**
     (вовлечённость по охвату, нормированный %), чтобы оператор выставил осмысленное
     значение.
  5. Согласованные параметры уходят в discovery-скрипт.
- **Результат:** новые каналы по сфере найдены, отфильтрованы, распределены по агентам
  и поставлены в очередь вступления.

### 3.4 Отбор каналов: фильтры и метрика качества

Каналы фильтруются и отбираются по двум критериям.

**Фильтр по числу подписчиков (ПДП).** Каналы ниже порога `min_subscribers`
отсеиваются.

**Метрика качества = ER / ERR.** Качество меряем вовлечённостью по охвату — нормированный
%, сравнимый между каналами любого размера. ИЦ (индекс цитирования) не берём — он
абсолютный и size-biased (завязан на размер канала), несравним между крупным и нишевым.
Каналы с ER ниже `er_min` отсеиваются.

**Порядок гейтов:** сначала по подписчикам, затем по ER — ER определяется только для
кандидатов, прошедших порог подписчиков, чтобы не тратить работу на заведомо отсеянные.

### 3.5 Порядок отбора (инкрементальный)

Скрипт ищет и фильтрует, **пока не наберёт `N` новых каналов** или не исчерпает
пространство поиска — без «собрать всё и отрезать» (глобальный top-N по ER отвергли:
дороже — тратит все запросы даже когда `N` уже набран). Резерва нет. `N` — на весь
прогон, не на агента.

**Пространство поиска** = все ключевые слова × все страницы выдачи.
Пагинация зависит от сервиса:

- **TGStat — без пагинации:** на слово ровно одна страница (до 100 каналов).
- **telemetr.me / telemetr.io — с пагинацией:** на слово перебираем страницы
  (`offset` / `skip`), пока выдача не кончится.

Цикл (внешний — по словам, внутренний — по страницам, где они есть):

1. Запрос страницы → кандидаты (ссылка, число подписчиков).
2. Дедуп против реестра по нормализованной ссылке (`https://t.me/<username>`, lowercase,
   без `@` и хвостового `/`) — известные каналы пропускаем. Источники discovery отдают
   только публичные каналы с username, поэтому приватных invite-ссылок без username
   (`t.me/+<hash>`, `t.me/joinchat/<hash>`) в выдаче не бывает — нормализация и
   дедуп рассчитаны на публичный username. (Такие ссылки могут встретиться только при
   backfill из `join_queue` — см. §5.3.)
3. Гейт по `min_subscribers`.
4. Гейт по ER: канал с ER ниже `er_min` отбрасываем.
5. Прошедшие накапливаем.

Условия остановки:

- **Набрали `N`** → стоп, остальные запросы не делаем.
- **Пространство исчерпано** (кончились слова и — где есть — страницы), а
  `N` не набрано → стоп с тем, что собрали.

### 3.6 Раскладка по агентам (assignment) и доставка

- **Делёж в рамках прогона.** Набранные новые каналы делятся между агентами round-robin
  поровну в пределах прогона; накопленную нагрузку не учитываем (учёт нагрузки отвергли
  ради простоты — перекос со временем мал и допустим).
- **Закрепление навсегда.** Назначение `channel → agentId` фиксируется в реестре
  (поле `assigned_agent`) и не меняется между прогонами — это и даёт непересечение
  каналов между агентами **во времени**, а не только внутри прогона.
- **Доставка.** В `join_queue` агента кладётся **нормализованная** каноническая ссылка
  (та же, по которой дедуплицирует реестр) через `addJoinQueue`. Очередь дедуплицирует
  по точному `link UNIQUE` без собственной нормализации, поэтому единая каноническая
  форма обязательна — иначе один канал попал бы в очередь дважды (`t.me/Foo/` vs
  `t.me/foo`).
- **Новый агент на платформе.** Назначение необратимо (из вступлённых каналов не выходим),
  поэтому ребаланса нет — новые каналы просто начинают распределяться и на него.

### 3.7 Завершение и отчёт оператору

По завершении скрипт сообщает оператору результат: сколько каналов найдено и
распределено по агентам и достигнут ли `N`. Если пространство исчерпано раньше `N`
(нашли < `N`) — это явно отражается в отчёте (например «найдено 320 из 500;
слова исчерпаны»), чтобы оператор расширил список слов или снизил
пороги.

### 3.8 Триггер вступления (развязка центр/агент)

discovery-скрипт заканчивается на наполнении `join_queue` агентов и **ничего не
запускает**. Вступление инициирует существующий per-agent таймер `join-queue` на
ближайшем тике. Центр и агент развязаны: центр пишет только в `join_queue.db` агента,
про его инфраструктуру ничего не знает.

> Операционное предусловие: на каждом агенте задача `join-queue` должна быть в
> расписании (`tasks`), иначе очередь копится без обработки.

> Предусловие одиночного запуска: discovery-скрипт — единственный писатель в
> `discovery.db`, запускается оператором по одному прогону за раз. Параллельный запуск
> двух прогонов не предусмотрен; на случай ошибочного двойного старта реестр защищён
> на уровне транзакций и `UNIQUE`-ключей (см. §5), но как продуктовое правило прогоны
> не должны перекрываться.

## 4. Архитектура

Задействованные компоненты:

| Компонент | Новый? | Ответственность |
|---|---|---|
| OpenClaw-скилл discovery | новый | диалог с оператором, генерация ключевых слов (LLM), запуск скрипта |
| discovery-скрипт | новый | поиск, фильтр, отбор, дедуп, assignment, push (без LLM) |
| Единый реестр `discovery.db` | новый | каналы, дедуп, персист назначения `channel → agent`; в workspace `agent1` (как `funnel.db`) |
| `join_queue` агента | существует | очередь ссылок на вступление |
| `join-queue` / `monitor` | существует | вступление и подхват канала в `channels` |

Скилл и скрипт развязаны с агентами: единственная точка записи в сторону агента —
его `join_queue.db`.

**Входы discovery-скрипта.** Параметры поиска и порога задаёт оператор при вызове
скилла, они прокидываются в скрипт аргументами; доступ и провайдер — config/секрет.

| Параметр | Источник | Обяз. | Зачем |
|---|---|---|---|
| `keywords[]` | оператор → скилл → аргумент | ✅ | по чему искать |
| `max_channels_per_run` (N) | оператор → аргумент | ✅ | целевое число каналов за прогон |
| `min_subscribers` | оператор → аргумент | ✅ | порог ПДП |
| `er_min` | оператор → аргумент | ✅ | порог качества (ER); скилл объясняет расчёт |
| `api_token` | секрет (env/config) | ✅ | доступ к источнику (TGStat) |
| `language` | config | — | язык контента (`russian`) |
| `country` | config | — | география поиска (`russia` для RU-задачи) |
| `source` | config | — | провайдер (`tgstat`; резерв telemetr.me) |
| `agents[]` | config | — | кому распределять (по умолчанию все, `listAgentIds()`) |

## 5. Модель данных

Фича добавляет одно новое общее для всех агентов хранилище — реестр `discovery.db` — и **читает**
существующие per-agent БД при backfill. Реестр живёт в workspace админ-агента
(`~/.openclaw/workspace-<FUNNEL_ADMIN_AGENT_ID>/discovery.db`, по умолчанию `agent1`) —
тот же приём, что и `funnel.db`. Стиль и реализация — как в `core/db/funnel.ts` /
`join-queue.ts`: `better-sqlite3`, snake_case-колонки, идемпотентная `CREATE TABLE IF NOT
EXISTS`, API возвращает camelCase через `AS`-алиасы.

Реестр — единственный источник истины о том, **какие каналы уже известны** и **какому
агенту назначен каждый канал**. Очередь `join_queue` агента и таблица `channels` остаются
как есть и не меняются.

### 5.1 Таблица `discovered_channels`

Одна строка — один уникальный канал на всю платформу (не дублируется между агентами).
У реестра ровно одна задача: знать, **какой канал уже известен** (дедуп) и **какому
агенту он назначен** (непересечение). Для этого достаточно двух полей; ничего сверх —
статусов, метрик, времён, провайдера — реестру для этой задачи не нужно.

| Колонка | Тип | Ключ / огранич. | Назначение |
|---|---|---|---|
| `canonical_link` | TEXT | **PRIMARY KEY** | каноническая ссылка `https://t.me/<username>` (lowercase, без `@`/хвостового `/`) — ключ дедупа и значение, кладущееся в `join_queue` |
| `assigned_agent` | TEXT | NOT NULL | агент-владелец канала; присваивается один раз и неизменен |

```sql
CREATE TABLE IF NOT EXISTS discovered_channels (
    canonical_link TEXT PRIMARY KEY,
    assigned_agent TEXT NOT NULL
);
```

`canonical_link` как PK — единственный инвариант, гарантирующий «один канал — одна
строка — один агент». Дедуп — по совпадению `canonical_link`: известный канал в реестр
повторно не попадает. Уникальность ссылки делает невозможным назначение одного канала
двум агентам — инвариант непересечения держится на БД, а не на коде раскладки.

> Метрики отбора (`subscribers`, `er`), провайдер находки и времена в реестре **не
> хранятся**: это входы фильтра на момент поиска, решение по ним уже принято (канал либо
> вставлен, либо нет). Хранить их после решения незачем.

### 5.2 Связь с `join_queue`

Схемной связи между БД нет. discovery-скрипт просто пишет `canonical_link` в `join_queue`
агента через `addJoinQueue(assigned_agent, [canonical_link])` — это и есть «новый список в
БД агента». Единственное требование: в очередь идёт ровно та же нормализованная ссылка,
что и ключ дедупа реестра, иначе один канал попал бы в очередь дважды (`t.me/Foo/` vs
`t.me/foo`), т.к. `join_queue` дедуплицирует по точному `link UNIQUE` без своей
нормализации. Таблицу `channels` discovery не трогает.

### 5.3 Backfill реестра (разовый, ручной, перед продом)

Перед запуском оператор **разово вручную** заносит в реестр уже известные каналы всех
агентов — чтобы discovery не назначил уже вступлённый канал другому агенту (иначе
пересечение). Дальше реестр поддерживает сам discovery, дедуп идёт как обычно по
`canonical_link`.

Это операционная задача оператора, а не часть автоматического конвейера: канал заносится
по его публичной ссылке с `assigned_agent` его текущего владельца. Ссылки каналов,
вступлённых через очередь, берутся из `join_queue.link` агента.

Backfill — необратимая правка общего реестра, выполняется оператором осознанно и один раз.

## 6. Источники discovery

Цель — по согласованным ключевым словам найти каналы и получить **ссылку на
вступление**. Рынок делится на сервисы с программным API и каталоги без API (только
скрейпинг). Данные из открытой документации; цены с пометкой «проверить» снимаются
регистрацией.

**Категория 1 — сервисы с API:**

| Критерий | TGStat | telemetr.me | telemetr.io |
|---|---|---|---|
| RU-каналы | ✅ RU-first, ~3M | ✅ RU-ориентир, большая RU-база | мультиязык, RU-доля меньше |
| Поиск по слову | ✅ `q` | ✅ `query` | ✅ `term` |
| Поиск по категории | ✅ `category` | ✅ `category[]` | ✅ `category` |
| Фильтр языка | `language` | ✅ `language[]=ru` | `language` |
| Фильтры качества | `participants_count` | подписчики, ER, views, verified, sort | members/ER/verified/sort |
| **Join-ссылка в выдаче** | ✅ `link` (1 запрос) | ✅ username → `t.me/...` (1 запрос) | ⚠️ только 2-м запросом `/channel/info` |
| Стр. за запрос / пагинация | 100, без пагинации | 20 + `offset` | 30/100 + `skip` |
| Авторизация | токен | Bearer-токен | ключ через бота |
| Цена | от 1 500 ₽/мес (поиск на тарифе S+; точная сумма — проверить) | API во всех тарифах: Эконом 2 750 ₽ / Профи 4 900 ₽ / Бизнес 21 000 ₽ / Корпорация 49 000 ₽ (за мес при оплате 3 мес) | Free 1000 req → S $25 / M $65 / L $199 / XL $499 |
| Главный минус | нет пагинации (охват — перебором слов) | маленькая страница (20); лимит «каналов/день» (Эконом 200) | join-ссылка дорогая (×2 запроса), RU-доля меньше |

Лимиты API telemetr.me по тарифам: Эконом 1 000 запросов/мес, Профи 10 000, Бизнес
100 000, Корпорация 300 000. Нюанс: связывающим может оказаться не квота запросов, а
лимит «каналов в день» — проверить на токене, считается ли каждый канал из выдачи
поиска против него.

**Стоимость — сбор ~5 000 каналов за месяц** (допущение: потери на дедуп ~30–40%):

| Показатель | TGStat | telemetr.me | telemetr.io |
|---|---|---|---|
| Запросов (поиск) | ~100 (по 100, ссылка внутри) | ~250 (по 20, ссылка внутри) | ~50 |
| Доп. запросов за ссылку | 0 | 0 | ~5 000 (`/channel/info` на канал) |
| Всего запросов/мес | ~100 | ~250 | ~5 080 |
| Подходящий тариф | базовый | Эконом | S/M |
| Стоимость/мес | ~1 500 ₽ | ~2 750 ₽ | ~$25–65 |
| Рост цены с объёмом | почти нет | почти нет | линейный (2-й запрос на канал) |

**Категория 2 — без API (только скрейпинг).** Веб-каталоги и биржи без публичного API;
discovery возможен лишь парсингом страниц (хрупко, против ToS, без SLA):

| Сервис | RU-каналы | Охват | Примечание |
|---|---|---|---|

Отдельные под-типы: боты (`@SearcheeBot` ~2.1M, `@FindTGChatsBot` ~100k) — доступ через
бот-интерфейс, не API; Apify — скрейпинг-как-услуга (по сути парсит данные TGStat).

**Решение.** Основной источник под RU-задачу — **TGStat** (дешевле, страница 100,
join-ссылка в выдаче). Близкий второй/резерв — **telemetr.me** (RU-ориентир, join-ссылка
в выдаче, прозрачные цены). **telemetr.io** — последний (дороже из-за второго запроса за
ссылкой, RU-доля меньше). Приоритет: **TGStat → telemetr.me → telemetr.io**.

## 7. Метрики успеха

- **Покрытие прогона:** найдено/распределено каналов vs целевой `N` (как часто
  упираемся в исчерпание пространства).
- **Доля дедуп-потерь:** сколько найденного отсеялось как уже известное.
- **Инвариант непересечения:** число каналов, назначенных более чем одному агенту = 0.
- **Качество:** медиана ER распределённых каналов.
- **Стоимость:** запросов к API за прогон и за 1 000 распределённых каналов.
