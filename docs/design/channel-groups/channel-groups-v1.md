# Design Doc: Группы каналов / кампания бренда — v1

> Аналитика фичи для человека. Объясняет, что делает система и как, и почему так
> решили. Нормативное поведение (требования + сценарии) — в `openspec/`, не здесь.
> Этот документ — этап аналитики (ФТ + алгоритмы). Код не пишется.
> Источник истины по сущностям и полям — `channel-groups-er.puml`.

## 1. Проблема / Контекст

Сейчас (`channel-discovery-v1`) найденные каналы раскладываются по агентам платформы
round-robin, реестр хранит только две колонки (`canonical_link`, `assigned_agent`),
метрики канала не сохраняются. Это решает дедуп и непересечение, но не даёт ответить на
бизнес-вопрос: **с каких тематических направлений идёт больше подписчиков** в общий
приватный канал бренда.

Каналы нужно группировать по признакам (тема + размер + вовлечённость), назначать
аккаунты в эти группы и измерять приток подписчиков **per-группа** через её именованную
invite-ссылку. Это первый шаг к «кампаниям агентов».

## 2. Цели

1. Объединять каналы бренда в **группы** по признакам (тема, диапазон подписчиков,
   диапазон ER).
2. Понимать, **какая группа даёт больше подписчиков** в общий приватный канал бренда
   (атрибуция per-группа: абсолют + дневная дельта).
3. Заложить основу под «кампании агентов»: бренд = кампания, группа = направление.

Не-цели v1: per-канальная атрибуция внутри группы; ребаланс уже назначенных каналов;
изменение персоны аккаунтов.

## 3. Доменная модель

Четыре сущности (см. `channel-groups-er.puml`):

| Сущность | Ключ | Назначение |
|---|---|---|
| **brand** | `id` | личность/бренд (сейчас «Мария»): `name`, `persona` (SOUL.md), `topics_a` (темы, текст). Владеет группами и реестром каналов. |
| **group** | `id` | направление кампании: `brand_id`, `name`, `topics_b` (подмножество тем, текст), `subs_min/subs_max`, `er_min/er_max`, `invite_link` (своя ссылка с меткой группы на ОБЩИЙ приватный канал бренда). Владеет аккаунтами. |
| **account** | `agent_id` | агент / Telegram-аккаунт; принадлежит **ровно одной** группе (`group_id` обязателен). Публичный канал аккаунта содержит invite-ссылку его группы. |
| **discovered_channel** | `canonical_link` | общий реестр каналов бренда (расширяет таблицу `discovered_channels` из `channel-discovery`): `brand_id`, `source` (`discovery`\|`similar` — откуда найден), `topic` (текст, одна тема), `subscribers`, `er`, `group_id` (NULL=без группы), `assigned_agent` (NULL=не назначен), `status` (assigned\|unassigned). |

`group_id`/`assigned_agent` у канала — **результат раскладки**, не структурная связь:
канал относится только к бренду.

### 3.1 Реверсы относительно `channel-discovery-v1` (зафиксировано явно)

| Что было (v1) | Что становится | Причина |
|---|---|---|
| Реестр = 2 колонки (`canonical_link`, `assigned_agent`); метрики не хранятся | Реестр хранит `source`, `topic`, `subscribers`, `er`, `group_id`, `status` | У атрибутов появился потребитель — группировка по признакам |
| Раскладка round-robin по всем агентам платформы | Раскладка по признакам в группу, затем round-robin **внутри** группы | Нужна атрибуция per-направление |
| Канал либо назначен, либо не в реестре | Появляется `status` и пул `unassigned` (канал в реестре, но без группы) | Канал может не подойти ни одной группе — его нельзя терять |

> Аналогичный реверс относительно `channel-discovery-similar-v1`: поиск похожих
> раньше распределял находки round-robin прямо по агентам платформы; теперь он лишь
> **пишет их в общий реестр бренда** с `source=similar`, а закрепление за группой/аккаунтом
> делает общий матчинг (FT-5 → FT-6). Сид похожего поиска — **все каналы группы** (а не
> seed-каналы агентов-искателей платформы).

## 4. Как работает (поток)

1. **Источники наполнения реестра** — два, оба пишут в общий реестр бренда: **discovery**
   (внешний сервис, по ключевым словам) и **similar** (поиск похожих по MTProto, сид —
   все каналы группы). Источник находит канал, считает `subscribers`, `er`, определяет
   `topic`, пишет строку со `status=unassigned`, `group_id=NULL`, `assigned_agent=NULL`
   и `source` (`discovery`|`similar`).
2. **Пере-матч пула (по запросу оператора).** Оператор вручную запускает повторный
   прогон `unassigned`-каналов против текущих критериев групп (только чтение реестра,
   без внешних вызовов). Автоматически в начале прогона не выполняется.
3. **Матчинг** каждого подходящего канала: ищется единственная группа, чьи критерии
   (тема ∩, диапазон подписчиков, диапазон ER) канал удовлетворяет.
   - подошёл одной → назначается группе, `status=assigned`;
   - не подошёл ни одной → остаётся `unassigned`, показывается оператору;
   - две группы подойти не могут (критерии непересекающиеся — инвариант группы).
4. **Round-robin внутри группы**: назначенный канал раздаётся одному из аккаунтов
   группы; ссылка кладётся в `join_queue` этого аккаунта.
5. **Атрибуция**: раз в день по `invite_link` каждой группы снимается число вступивших
   (`GetChatInviteImporters`) — абсолют и дневная дельта; строится отчёт «какая группа
   дала больше подписчиков».

## 5. Функциональные требования

Формат: User Story + Acceptance Criteria. AC даны в Given/When/Then (Gherkin-стиль),
тестируемы.

---

### FT-1. Создание бренда

> **Как** оператор,
> **я хочу** создать бренд (личность) с именем, персоной и описанием тем,
> **чтобы** под ним заводить группы-направления и общий реестр каналов.

**AC:**
- Given системе нужен новый бренд
  When оператор создаёт бренд с `name`, `persona` (SOUL.md) и `topics_a` (темы, текст)
  Then бренд создаётся; под ним можно заводить группы (FT-2) и наполнять реестр (FT-5).
- Given бренд создаётся
  When `name` пустой
  Then создание отклоняется с ошибкой валидации.
- Given бренд существует
  Then он владеет своими группами, аккаунтами (через группы) и реестром каналов; данные
  одного бренда не пересекаются с данными другого.

---

### FT-2. Управление группами: создание

> **Как** оператор бренда,
> **я хочу** создать группу с темами, диапазоном подписчиков и диапазоном ER,
> **чтобы** задать правило, по которому каналы будут попадать в это направление.

**AC:**
- Given бренд существует
  When оператор создаёт группу с `name`, `topics_b` (непустой), `subs_min ≤ subs_max`,
  `er_min ≤ er_max`
  Then группа создаётся с `brand_id` этого бренда.
- Given существуют другие группы того же бренда
  When создаваемая группа имеет критерии, **пересекающиеся** с критериями любой из них
  (см. FT-3)
  Then создание **отклоняется** с указанием конфликтующей группы; группа не создаётся.
- Given создаётся группа
  When оператор задаёт `invite_link` (даётся при создании; может быть задан отдельно
  или изменён позже — В1)
  Then группа сохраняется с этой ссылкой как точкой атрибуции (FT-8).
- Given задан некорректный диапазон (`subs_min > subs_max` или `er_min > er_max`)
  When оператор отправляет форму
  Then создание отклоняется с ошибкой валидации диапазона.

---

### FT-3. Инвариант непересечения критериев групп

> **Как** оператор,
> **я хочу**, чтобы критерии разных групп одного бренда не пересекались,
> **чтобы** ни один канал не мог подойти двум группам одновременно.

**AC:**
- Given две группы одного бренда
  When у них есть **общая тема** T И их диапазоны подписчиков пересекаются И их диапазоны
  ER пересекаются
  Then это считается пересечением критериев и **запрещено** (проверяется при создании
  FT-2 и расширении FT-12).
- Given у двух групп нет общей темы
  Then их диапазоны могут пересекаться — пересечения критериев нет (тема разводит их).
- Given проверка непересечения
  Then два диапазона `[a1..b1]` и `[a2..b2]` пересекаются ⇔ `a1 ≤ b2 И a2 ≤ b1`
  (границы **включительны** — В7).

> Замечание: пересечение тем двух групп определяется **сравнением через LLM** (В4) —
> LLM решает, есть ли общая тема. Детерминированного строкового правила нет.

---

### FT-4. Привязка аккаунтов к группе

> **Как** оператор,
> **я хочу** привязать аккаунты к группе,
> **чтобы** каналы группы раздавались её аккаунтам, а в их публичных каналах стояла
> invite-ссылка этой группы.

**AC:**
- Given группа существует
  When оператор привязывает аккаунт к группе
  Then у аккаунта `group_id` = id этой группы.
- Given аккаунт уже привязан к группе X
  When оператор привязывает его к группе Y
  Then перепривязка **запрещена** (В5): аккаунт остаётся в группе X.
- Given аккаунт без группы (`group_id` пуст)
  When по нему запускается раздача каналов
  Then он не получает каналов (каждый аккаунт обязан принадлежать ровно одной группе).

---

### FT-5. Наполнение реестра из источников (discovery + similar) и метрики канала

> **Как** система,
> **я хочу** при находке канала любым источником сохранять в реестр его источник, тему,
> число подписчиков и ER,
> **чтобы** канал можно было назначить в группу по признакам, а по `source` — понимать,
> откуда он появился.

**AC:**
- Given канал найден **внешним сервисом (discovery)** по ключевым словам
  When он проходит гейты discovery (подписчики, ER)
  Then в реестр пишется строка: `canonical_link` (нормализованная), `brand_id`,
  `source=discovery`, `topic`, `subscribers`, `er`, `status=unassigned`, `group_id=NULL`,
  `assigned_agent=NULL`.
- Given канал найден **поиском похожих (similar)**, сид которого — **все каналы группы**
  When он проходит гейт по подписчикам
  Then в **тот же общий реестр бренда** пишется строка с `source=similar` и теми же
  полями (`topic`, `subscribers`, `er`, `status=unassigned`, `group_id=NULL`,
  `assigned_agent=NULL`); далее канал матчится в группу наравне с discovery-находками
  (FT-6).
- Given канал уже есть в реестре (по `canonical_link`)
  When любой источник находит его снова
  Then строка **не дублируется и не обновляется** — дедуп как в v1 (В6); `source`
  остаётся от первой находки.
- Given поле `source`
  Then это enum со значениями `discovery | similar` — провенанс канала в реестре.

> `topic` — одна тема на канал (текст). В **discovery** определяется как тема оператора
> при старте поиска + анализ описания/нескольких постов (LLM, В2). В **similar**
> ключевых слов и темы оператора нет — `topic` определяется **только анализом
> описания/постов** (LLM). ER у similar-находки **вычисляется при записи в реестр** (в
> similar v1 гейт был только по подписчикам). Правило «одна тема на канал, метрики в
> реестре» едино для обоих источников.

---

### FT-6. Матчинг канала в группу

> **Как** система,
> **я хочу** для каждого `assigned`-кандидата найти единственную подходящую группу,
> **чтобы** назначить ему `group_id` детерминированно.

**AC:**
- Given канал с `topic`, `subscribers`, `er`
  When существует группа, для которой `topic` соответствует `group.topics_b` **по оценке
  LLM** (В4) И `subscribers ∈ [subs_min..subs_max]` И `er ∈ [er_min..er_max]`
  Then канал назначается этой группе: `group_id` = id группы, `status=assigned`.
- Given канал не подошёл **ни одной** группе
  Then `status` остаётся `unassigned`, `group_id=NULL`, `assigned_agent=NULL`; канал
  виден оператору в списке unassigned (FT-10).
- Given канал
  When по критериям ему подходят **две** группы
  Then это нарушение инварианта FT-3 и в норме невозможно; при обнаружении канал
  назначается **в первую** из подошедших групп, а оператору выводится **warning** об
  ошибке непересечения (В8). Прогон не останавливается.
- Given группа без привязанных аккаунтов
  Then она **не является целью матчинга**: подходящий по критериям канал в неё не
  назначается и остаётся `unassigned`, пока в группу не привяжут аккаунт (В9).

---

### FT-7. Round-robin раздача внутри группы и доставка в join_queue

> **Как** система,
> **я хочу** раздавать назначенные группе каналы её аккаунтам round-robin и класть
> ссылку в `join_queue` аккаунта,
> **чтобы** аккаунты группы равномерно вступали в её каналы.

**AC:**
- Given группе назначены новые каналы и у группы ≥ 1 аккаунт
  When выполняется раздача
  Then каналы распределяются round-robin между аккаунтами группы; каждому каналу
  проставляется `assigned_agent`.
- Given каналу проставлен `assigned_agent`
  Then его `canonical_link` (та же нормализованная форма, что и ключ дедупа) кладётся в
  `join_queue` этого аккаунта через `addJoinQueue`; discovery сам не вступает.
- Given группа без аккаунтов
  When канал по критериям подходит этой группе
  Then назначение **запрещено** (В9): канал в неё не назначается и остаётся `unassigned`
  (см. FT-6).
- Given сбой между записью `assigned_agent` в реестр и `addJoinQueue`
  Then при повторе канал уже `assigned`, дедуп пропустит его, а `addJoinQueue` повторно
  не вызовется → канал назначен, но в очередь не попал. **Риск принят как есть** (как в
  discovery v1, В10); специальной компенсации в v1 не делаем.

---

### FT-8. Invite-ссылка группы как точка атрибуции

> **Как** оператор,
> **я хочу** задать группе её именованную invite-ссылку на общий приватный канал бренда,
> **чтобы** приток подписчиков можно было атрибутировать на группу.

**AC:**
- Given общий приватный канал бренда один
  When у группы задаётся `invite_link` (при создании группы либо отдельно/позже — В1)
  Then это ссылка-приглашение в этот общий канал с меткой именно этой группы; смена
  ссылки допускается.
- Given у двух групп бренда
  When сравниваются их `invite_link`
  Then они различны (каждая группа — своя ссылка; иначе атрибуция смешается).
- Given у аккаунта группы есть публичный канал
  Then в нём размещена `invite_link` его группы; публичный канал наполняет **оператор
  вручную** (В3) — система этого не делает.

---

### FT-9. Атрибуция: подписчики на группу и отчёт

> **Как** оператор,
> **я хочу** видеть, сколько подписчиков пришло по invite-ссылке каждой группы (абсолют
> и дневная дельта),
> **чтобы** понимать, какое направление даёт больше подписчиков.

**AC:**
- Given у группы задан `invite_link`
  When раз в день запускается сбор атрибуции
  Then по `GetChatInviteImporters(invite_link)` снимается число вступивших (абсолют) и
  сохраняется снапшот с датой.
- Given есть снапшот за предыдущий день той же группы
  Then дневная дельта = текущий абсолют − предыдущий; сохраняются и дельта, и абсолют
  (как в `funnel-metrics`).
- Given предыдущего снапшота нет
  Then дельта = 0 (или помечается недоступной), абсолют = текущее значение.
- Given собраны снапшоты всех групп за день
  When строится отчёт
  Then отчёт ранжирует группы по приросту подписчиков (дельта) за день/период и
  показывает абсолют — «какая группа дала больше подписчиков».
- Given у аккаунта (agent1) нет прав на канал (`CHAT_ADMIN_REQUIRED`)
  Then метрика по этой ссылке помечается недоступной, сбор остальных продолжается
  (изоляция сбоев, как в `funnel-metrics`).
- Given повторный запуск сбора в тот же день
  Then снапшот за этот день не дублируется (защита от двойного прогона).

---

### FT-10. Видимость пула unassigned оператору

> **Как** оператор,
> **я хочу** видеть каналы, не подошедшие ни одной группе,
> **чтобы** решить — расширить группу, завести новую или оставить как есть.

**AC:**
- Given в реестре есть `unassigned`-каналы
  When оператор запрашивает их список
  Then он получает их `canonical_link`, `topic`, `subscribers`, `er`.
- Отдельный отчёт/уведомление об unassigned после прогона **не требуется** (В11) —
  только запрос on-demand.

---

### FT-11. Пере-матч пула unassigned (ручной запуск)

> **Как** оператор,
> **я хочу** по своему решению заново прогнать `unassigned`-каналы против текущих
> критериев групп,
> **чтобы** после расширения диапазона или заведения новой группы подходящие каналы
> попали в неё — но только когда я этого захочу.

**AC:**
- Given в реестре есть каналы со `status=unassigned`
  When **оператор вручную запускает пере-матч** (не автоматически в начале прогона)
  Then каждый такой канал прогоняется через матчинг (FT-6), **только читая реестр**, без
  внешних вызовов (метрики уже сохранены).
- Given unassigned-канал теперь подходит расширенной группе
  Then он назначается ей (`status=assigned`) и далее раздаётся аккаунту (FT-7).
- Given unassigned-канал по-прежнему не подходит ни одной группе
  Then он остаётся `unassigned`.
- Given пере-матч
  Then он **не трогает** каналы со `status=assigned` (нет ребаланса).

---

### FT-12. Управление группами: расширение диапазонов (только расширение)

> **Как** оператор,
> **я хочу** расширять диапазоны подписчиков/ER и набор тем существующей группы,
> **чтобы** будущие находки попадали в неё, не осиротив уже вступлённые каналы.

**AC:**
- Given группа с диапазоном `[subs_min..subs_max]` / `[er_min..er_max]` и набором тем
  When оператор задаёт новые границы, где `subs_min' ≤ subs_min` и `subs_max' ≥ subs_max`
  (и аналогично для ER), а набор тем — надмножество прежнего
  Then изменение применяется.
- Given группа
  When оператор пытается **сузить** любой диапазон (`subs_min' > subs_min`,
  `subs_max' < subs_max`, `er_min' > er_min`, `er_max' < er_max`) или **убрать** тему
  Then изменение **отклоняется** (сужение запрещено: вступление в каналы необратимо,
  сужение осиротило бы уже назначенный канал).
- Given группа A расширяется по теме T
  When расширенный диапазон пересекается с диапазоном соседней группы B по той же теме T
  Then расширение **отклоняется** с указанием границы группы B (расширение упирается в
  границы соседней группы — иначе пересечение критериев, FT-3).
- Given расширение применилось
  Then оно влияет **только на будущие находки и пере-матч пула**; уже назначенные каналы
  не перераспределяются (нет ребаланса).

## 6. Основные алгоритмы

Псевдокод. Диапазоны, round-robin, атрибуция — детерминированы. Сравнение тем —
**через LLM** (В4); `topic` канала определяется LLM в discovery (В2).

### 6.1. Матчинг одного канала

```
matchChannelToGroup(channel, groupsOfBrand):
    candidates = []
    for g in groupsOfBrand:
        if accountsOf(g) is empty: continue              # В9: группа без аккаунтов — не цель
        if not llmTopicMatches(channel.topic, g.topics_b): continue   # сравнение тем — LLM (В4)
        if not (g.subs_min <= channel.subscribers <= g.subs_max): continue
        if not (g.er_min   <= channel.er          <= g.er_max):   continue
        candidates.append(g)
    if len(candidates) == 0:
        return UNASSIGNED                                # FT-6: остаётся в пуле
    if len(candidates) >= 2:
        warn('criteria overlap: ' + channel.link + ' -> ' + ids(candidates))  # В8: warning, не стоп
    return candidates[0]                                 # одна — она; несколько — первая (В8)
```

### 6.2. Пере-матч пула unassigned (ручной запуск оператором)

```
rematchPool(brand):                                     # запускается оператором вручную
    for ch in registry.where(brand_id=brand.id, status='unassigned'):   # только чтение

        if result is a group:

        # else: остаётся unassigned, ничего не делаем
    # assigned-каналы не трогаем (нет ребаланса)
```

### 6.3. Валидация непересечения критериев (создание/расширение группы)

```
validateNoOverlap(brand, candidateGroup, mode):     # mode = create | expand
    if candidateGroup.subs_min > candidateGroup.subs_max: reject('subs range')
    if candidateGroup.er_min   > candidateGroup.er_max:   reject('er range')

    if mode == 'expand':
        old = current(candidateGroup)
        # запрет сужения (FT-12)
        if candidateGroup.subs_min > old.subs_min: reject('subs narrowing')
        if candidateGroup.subs_max < old.subs_max: reject('subs narrowing')
        if candidateGroup.er_min   > old.er_min:   reject('er narrowing')
        if candidateGroup.er_max   < old.er_max:   reject('er narrowing')
        if not topicsSuperset(candidateGroup.topics_b, old.topics_b): reject('topic removed')

    for g in groupsOf(brand) where g.id != candidateGroup.id:
        if llmTopicsOverlap(candidateGroup.topics_b, g.topics_b)          # общая тема — LLM (В4)
           and rangesOverlap(candidateGroup.subs_*, g.subs_*)             # a1<=b2 and a2<=b1
           and rangesOverlap(candidateGroup.er_*,   g.er_*):
            reject('criteria overlap with group ' + g.id)                 # FT-3
    accept()
```

### 6.4. Round-robin внутри группы

```
distributeWithinGroup(group, channels):
    accounts = accountsOf(group)              # account.group_id == group.id
    if len(accounts) == 0:
        return                                # В9: пустых групп матчинг не выбирает; защита
    i = rrCursor(group)                        # курсор сохраняется на группу
    for ch in channels:
        acct = accounts[i % len(accounts)]
        ch.assigned_agent = acct.agent_id      # 1) пишем в реестр
        addJoinQueue(acct.agent_id, [ch.canonical_link], log)  # 2) доставка
        i += 1
    saveRrCursor(group, i)
```

> Порядок шагов (реестр → join_queue) и риск молчаливой потери при сбое между ними — §8,
> вопрос В10. Обратный порядок (join_queue → реестр) даёт лишь безвредную повторную
> доставку при повторе.

## 7. Влияние (этап аналитики — для архитектора)

- **Модель данных:** реестр каналов расширяется до полей `source`, `topic`,
  `subscribers`, `er`, `group_id`, `status` (реверс v1). Новые сущности `brand`, `group`,
  `account`-binding, снапшоты атрибуции per-группа. Где физически живут
  `brand`/`group`/`account` (в `discovery.db` или отдельно) — на этап архитектуры.
- **Два источника наполнения реестра:** discovery (внешний сервис, по ключевым словам) и
  similar (граф похожих по MTProto, сид — все каналы группы). Оба пишут в один реестр
  бренда с `source`; раскладку по группам делает общий матчинг. Поведение similar
  меняется относительно `channel-discovery-similar-v1` (через реестр+матчинг вместо
  прямого round-robin) — реверс зафиксирован в §3.1.
- **Существующее переиспользуем, не дублируем:** discovery-конвейер (поиск/гейты/дедуп),
  обход похожих (`getChannelRecommendations`) из similar-discovery, `addJoinQueue`,
  нормализация `canonical_link`, механика `GetChatInviteImporters` и модель снапшот+дельта
  из `funnel-metrics`.
- **LLM:** определение `topic` канала в discovery (тема оператора + анализ
  описания/постов, В2) и сравнение тем при матчинге и проверке непересечения (В4).
  Диапазоны, round-robin, атрибуция — детерминированы.

## 8. Известные риски

- **Молчаливая потеря доставки** при сбое между записью `assigned_agent` в реестр и
  `addJoinQueue` (унаследовано от discovery v1). **Риск принят как есть** (В10): в v1
  специальной компенсации не делаем.
- **Сравнение тем через LLM** (В4): матчинг (FT-6) и проверка непересечения (FT-3)
  зависят от стабильности оценок LLM — недетерминизм может давать разные решения на
  одних и тех же темах. Заложить устойчивый промпт/формат на этапе архитектуры.
- **Определение `topic`** канала в discovery (В2): тема оператора при старте + анализ
  описания/постов через LLM, единым правилом для поиска по сервисам и по похожим.
