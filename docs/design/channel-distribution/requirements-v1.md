# Требования: распределение каналов по агентам через Telegram-бот — v1

> **О чём документ.** Что система должна делать и по каким правилам при
> распределении списка каналов по агентам, инициируемом администратором
> платформы через Telegram-бот. Уровень бизнес-аналитики (что и почему, для
> кого). Техническое решение (как именно это реализуется) сюда не входит — это
> отдельный документ `architecture.md`, парный к этому.
>
> **Статус.** Ранее открытые вопросы закрыты заказчиком; их итоговые решения
> учтены в требованиях и критериях приёмки. Незакрытым остаётся один
> эксплуатационный пункт вне рамок требований — как именно настраивается
> уполномоченный чат (см. «Вне рамок»).

---

## 1. Проблема и контекст

Сейчас распределить список каналов по агентам может только разработчик —
вручную, через среду разработки, запуская специальные скрипты. Администратор
платформы (человек, не разработчик) этого сделать не может.

Это узкое место: любое добавление каналов зависит от разработчика и его
доступности. Операционная функция подключения новых каналов удерживается
внутри команды разработки, что замедляет рост охвата и увеличивает риск
задержек.

Заинтересованные лица:
- **Администратор платформы** — хочет самостоятельно распределять каналы, без
  обращения к разработчику.
- **Владелец платформы** — хочет, чтобы изменение распределения выполняли
  только уполномоченные лица.
- **Разработчик** — хочет быть исключённым из рутинной операции подключения
  каналов.

---

## 2. Цель

1. Дать администратору платформы возможность самостоятельно, без участия
   разработчика, распределить список каналов по выбранным агентам через
   Telegram-бот.
2. По итогам распределения гарантировать, что каждый добавленный канал
   действительно начал обрабатываться: помещён в процесс вступления агента, а
   процесс вступления целевых агентов запущен.
3. Сохранять приложенные к каналам метрики как справочные данные, не влияющие
   на распределение, с допущением произвольного меняющегося состава метрик.
4. Обеспечить администратору прозрачность: статус задачи в ходе выполнения и
   понятный итог по завершении (сколько каналов добавлено, сколько пропущено,
   сколько с ошибкой).
5. Поддерживать общий реестр каналов в состоянии, отражающем фактическое
   закрепление каналов за агентами.
6. Обеспечить аудит: сохранять загруженные файлы, историю результатов прогонов
   и журнал выполнения.

## 3. Доменная модель

Термины предметной области. Понятия платформы — из `docs/product.md`; понятия
Telegram — по документации Telegram (раздел 9).

| Термин | Что это |
|---|---|
| Агент | Один Telegram-аккаунт со своей персоной, работающий автономно от своего имени через MTProto. Данные у каждого агента свои. Понятие платформы (`docs/product.md`). |
| agentId | Идентификатор агента на платформе, по которому агент указывается в наборе целей распределения. |
| Персона | Общий шаблон поведения и стиля общения, на который ссылается один или несколько агентов. Понятие платформы (`docs/product.md`). |
| Канал (в контексте этой фичи) / группа обсуждения | Telegram-сообщество, в которое агент вступает и где ведёт активность. В терминологии Telegram это группа (супергруппа), в том числе группа обсуждения, привязанная к каналу-вещателю, где участники общаются и комментируют. В отличие от канала-вещателя (одностороннее вещание), группа допускает участие многих участников. Идентифицируется ссылкой. Понятие Telegram (раздел 9). |
| Ссылка на канал | Публичный указатель на конкретный Telegram-канал/группу по имени канала, формата `t.me/<channelusername>`, по которому агент может в него вступить. Пригласительные и приватные ссылки в рамках этой фичи не поддерживаются. Понятие Telegram (раздел 9). |
| Метрики канала | Справочные характеристики канала (например число подписчиков, число комментариев), опционально приложенные администратором к каналу отдельными колонками таблицы. Состав метрик произвольный и меняется во времени. Справочные данные, не влияющие на распределение. |
| Реестр каналов | Общий для платформы перечень: какой канал за каким агентом закреплён. Один канал закреплён ровно за одним агентом. Понятие платформы. |
| Процесс вступления (join-queue) | Фоновый процесс агента, который по очереди вступает в закреплённые за агентом каналы. Может быть включён или выключен. Понятие платформы (`docs/product.md`: «Вступление в группы. Обрабатывает очередь вступления в группы обсуждений»). |
| Администратор платформы | Человек (не разработчик), управляющий платформой; инициирует распределение через Telegram-бот. |
| Распределение | Операция: разложить список каналов из загруженной таблицы по указанному набору агентов, поставить каналы в процесс вступления и обновить реестр. |

## 4. Ограничения среды

- **Интерфейс — Telegram-бот.** Всё взаимодействие (загрузка таблицы, выбор
  агентов, запуск, статус, итог) происходит в диалоге с ботом; отдельного
  веб-интерфейса нет.
- **Входные данные — таблица CSV.** Список каналов администратор передаёт файлом
  CSV. Поддерживаются разделители: запятая, точка с запятой, табуляция. Колонка
  со ссылками распознаётся по заголовку `link`; все прочие колонки трактуются
  как метрики канала (имя метрики = заголовок колонки).
- **Единица распределения — канал.** Одна строка таблицы = один канал.
- **Набор агентов — диапазоны agentId.** Целевые агенты задаются одним или
  несколькими диапазонами agentId.
- **Единственность закрепления.** В реестре канал в любой момент закреплён ровно
  за одним агентом.
- **Асинхронность вступления.** Помещение канала в процесс вступления не
  означает мгновенного вступления: фактическое вступление выполняет фоновый
  процесс агента в своём порядке и темпе.
- **Объём загрузки.** Искусственных ограничений на число каналов и число целевых
  агентов не вводится, но действует технический потолок транспорта Telegram: один
  файл не более 20 МБ, о чём администратор предупреждается в стартовом сообщении.

## 6. User Stories

US-1 (R5, R16, R20, R21). Как администратор платформы, я хочу загрузить в бот
таблицу со списком каналов, чтобы передать системе перечень каналов для
распределения без обращения к разработчику.

US-2 (R6, R17). Как администратор платформы, я хочу указать набор агентов одним
или несколькими диапазонами agentId, которым распределить каналы, чтобы
контролировать, между кем распределяется загруженный список.

US-3 (R1, R2, R6). Как администратор платформы, я хочу одной командой запустить
распределение загруженного списка по выбранным агентам, чтобы система сама
разложила каналы и начала работу без ручных действий разработчика.

US-4 (R7, R8). Как администратор платформы, я хочу, чтобы после распределения
процесс вступления у целевых агентов был гарантированно запущен, чтобы
добавленные каналы действительно начали обрабатываться, а не остались
неактивными.

US-5 (R3). Как администратор платформы, я хочу, чтобы приложенные к каналам
метрики сохранялись как справочные данные, чтобы позже опираться на них при
анализе, при этом состав метрик может меняться со временем.

US-6 (R10). Как администратор платформы, я хочу видеть статус запущенной задачи
(идёт / завершена), чтобы понимать, закончилась ли обработка.

US-7 (R9). Как администратор платформы, я хочу по завершении получить сводку с
количеством каналов по исходам (сколько добавлено, сколько пропущено, сколько с
ошибкой), чтобы оценить результат распределения и при необходимости принять
меры.

US-8 (R4, R14). Как администратор платформы, я хочу, чтобы общий реестр каналов
отражал фактическое закрепление каналов за агентами, чтобы реестр оставался
достоверным источником о распределении. В рамках этой фичи распределение
затрагивает только новые каналы; уже закреплённые каналы не переназначаются.

US-9 (R18). Как владелец платформы, я хочу, чтобы запускать распределение можно
было только из настроенного уполномоченного чата, чтобы исключить
несанкционированные изменения распределения каналов.

US-10 (R26, R27, R28). Как администратор платформы, я хочу, чтобы загруженные
файлы, результаты прогонов и ход выполнения сохранялись, чтобы иметь возможность
позже разобрать, что и когда было распределено.

## 7. Требования

### Всегда действует

- **R1.** Система должна закреплять каждый распределяемый канал ровно за одним
  агентом из указанного набора.
- **R2.** Система должна относить каждую строку загруженной таблицы ровно к
  одному исходу: добавлена, пропущена (с причиной) или ошибка (с причиной).
- **R3.** Система должна сохранять метрики каналов как справочные данные о
  канале с произвольным меняющимся составом и не использовать их при
  распределении каналов между агентами.
- **R4.** Система должна поддерживать общий реестр каналов в состоянии,
  отражающем фактическое закрепление каналов за агентами. В рамках этой фичи
  изменяются только закрепления новых каналов; уже закреплённые каналы не
  переназначаются.
- **R19.** Система должна давать одинаковый результат распределения при
  одинаковых входных данных и одном и том же состоянии реестра.
- **R20.** Система должна распознавать колонку со ссылками по заголовку `link`, а
  все прочие колонки таблицы трактовать как метрики канала, где имя метрики равно
  заголовку колонки.
- **R21.** Система должна принимать таблицы CSV с разделителем «запятая», «точка
  с запятой» или «табуляция».
- **R27.** Система должна вести историю результатов каждого прогона задачи
  распределения, доступную для последующего просмотра.
- **R28.** Система должна вести журнал выполнения задач распределения.

### По событию

- **R5.** Когда администратор загружает таблицу, система должна принять для
  обработки список каналов из неё вместе с опциональными колонками метрик.
- **R6.** Когда администратор задал набор агентов и запустил распределение,
  система должна распределить новые каналы так, чтобы выровнять итоговое число
  закреплённых каналов у целевых агентов: учитывая уже имеющуюся у каждого агента
  нагрузку, отдавать больше новых каналов тем целевым агентам, у кого каналов
  сейчас меньше.
- **R7.** Когда канал распределён агенту, система должна поместить этот канал в
  процесс вступления соответствующего агента.
- **R8.** Когда по итогам распределения агент получил хотя бы один канал, система
  должна обеспечить, что процесс вступления этого агента запущен, и включить его,
  если он был выключен.
- **R9.** Когда задача завершена, система должна предоставить администратору итог
  в виде количества каналов по исходам: сколько добавлено, сколько пропущено,
  сколько завершилось ошибкой.
- **R26.** Когда администратор загружает таблицу, система должна сохранить
  загруженный файл в выделенном хранилище для последующего аудита.

### По состоянию

- **R10.** Пока задача распределения не завершена, система должна давать
  администратору узнать её текущее состояние (идёт / завершена).

### Обработка ошибок

- **R11.** Если строка таблицы не содержит ссылки на канал, то система должна не
  распределять эту строку и отнести её к исходу «пропущена» с причиной.
- **R12.** Если один и тот же канал встречается в загруженной таблице более
  одного раза, то система должна закрепить его один раз, а повторные вхождения
  отнести к исходу «пропущена» (дубликат).
- **R13.** Если канал из таблицы уже закреплён за тем же агентом, которому он
  назначается, то система должна не создавать повторного закрепления и повторной
  постановки в процесс вступления.
- **R14.** Если канал из таблицы уже закреплён за другим агентом (не тем, кому
  назначается сейчас), то система должна отнести его к исходу «пропущена» и не
  изменять существующее закрепление.
- **R15.** Если ссылка в строке не соответствует поддерживаемому формату
  `t.me/<channelusername>`, то система должна не прерывать обработку остальных
  строк и отнести строку к исходу «ошибка» с причиной. Проверка существования и
  доступности канала в область распределения не входит — это этап процесса
  вступления.
- **R16.** Если загруженный файл не является корректной таблицей ожидаемого
  формата или в нём отсутствует колонка с заголовком `link`, то система должна не
  запускать распределение и сообщить администратору причину отклонения.
- **R17.** Если набор целевых агентов пуст, не распознан или содержит неизвестный
  (несуществующий) agentId, то система должна не запускать распределение и
  сообщить администратору; наличие неизвестного агента в наборе приводит к
  отклонению всей задачи до старта.
- **R18.** Если запрос на распределение поступает не из настроенного
  уполномоченного чата, то система должна отклонить его и не выполнять
  распределение.
- **R24.** Если поступает запрос на новую задачу распределения, пока предыдущая
  задача не завершена, то система должна не принимать новую задачу до завершения
  текущей; одновременно выполняется не более одной задачи распределения.
- **R25.** Если при обработке отдельных строк возникают ошибки, то система должна
  зафиксировать успешно добавленные каналы (частичный успех) и не отменять их.

## 8. Критерии приёмки

- **AC-1 (R2).** По завершении задачи каждая строка исходной таблицы отнесена
  ровно к одному исходу: добавлена, пропущена (с причиной) или ошибка (с
  причиной).
- **AC-2 (R1).** Каждый добавленный канал закреплён ровно за одним агентом из
  указанного набора.
- **AC-3 (R7).** Каждый добавленный канал помещён в процесс вступления
  назначенного ему агента.
- **AC-4 (R8).** Для каждого агента, получившего хотя бы один канал, по
  завершении задачи процесс вступления запущен.
- **AC-5 (R3).** Метрики каналов доступны как справочные данные и не повлияли на
  то, какому агенту достался канал.
- **AC-6 (R10, R9).** До завершения администратор может увидеть, что задача идёт;
  по завершении — что она завершена, с доступом к итогу.
- **AC-7 (R9).** Итог задачи показывает количество каналов по исходам: сколько
  добавлено, сколько пропущено, сколько с ошибкой.
- **AC-8 (R11, R12, R14).** К исходу «пропущена» отнесены строки без ссылки,
  повторяющиеся каналы и каналы, уже закреплённые за другим агентом.
- **AC-9 (R15).** К исходу «ошибка» отнесены строки со ссылкой не в поддерживаемом
  формате `t.me/<channelusername>`.
- **AC-10 (R14).** Канал, уже закреплённый за другим агентом, пропущен, и его
  существующее закрепление не изменено.
- **AC-11 (R16, R17).** Некорректный файл, отсутствие колонки `link` или
  неизвестный агент в наборе не приводят к распределению; администратор получает
  причину отклонения.
- **AC-12 (R18).** Запрос не из уполномоченного чата не приводит к распределению.
- **AC-13 (R6).** По итогам распределения новые каналы распределены в сторону
  выравнивания итогового числа закреплённых каналов у целевых агентов: агентам с
  меньшей текущей нагрузкой достаётся больше новых каналов.
- **AC-14 (R25).** При сбое на части строк успешно добавленные каналы остаются
  закреплёнными и не отменяются.
- **AC-15 (R24).** Пока задача распределения не завершена, новая задача не
  запускается.
- **AC-16 (R26, R27, R28).** Загруженный файл сохранён в выделенном хранилище;
  результат прогона доступен в истории; ход выполнения отражён в журнале.
- **AC-17.** Причины пропуска и ошибок в итоге сформулированы понятно для
  администратора-нетехнического специалиста, без терминологии реализации.
