> администратором через Telegram-бот. Источник требований (WHAT) —
> [requirements-v1.md](requirements-v1.md) (R1..R28, US-1..US-10, AC-1..AC-17);
> правила и ограничения оттуда сюда не дублируются, только ссылки на R-*.

> варианты с рекомендацией — финальный выбор за заказчиком (agent-playbook.md:
> «Решение принимает человек»). Разделы «Открытые вопросы» и часть «Модель
> данных» сознательно оставлены на решение заказчика, а не додуманы.

> **Образцы структуры:** `docs/design/task-scheduler/architecture-v1.md`,
> `docs/design/tg-agent-autoregistration/architecture.md`.

## 1. Контекст и связь с кодом

Распределение «сырого» списка каналов по агентам уже существует в репозитории —
но только как **ручные CLI-скрипты разработчика** (`src/scripts/ops/`):

| Скрипт | Что делает | Балансировка |
|---|---|---|
| `distribute-channels.ts` | список ссылок (одна на строку) → агенты из `--agents` | round-robin по порядку `--agents`, без учёта нагрузки |
| `distribute-pool.ts` | уже зарегистрированные, но неназначенные каналы discovery → агенты | — |
| `import-agent-pool.ts` | CSV `agentId;link;pool_name`, агент задан per-row | прямое назначение из файла |
| `redistribute-channels.ts` | принудительное переназначение готового CSV | `forceAssignChannel` (override) |

Все они опираются на одни и те же примитивы ядра. Новая фича — это **не новый
алгоритм поверх нового хранилища, а новый фронт-энд (Telegram-бот) и оркестрация
поверх тех же примитивов**, доступные администратору-нетехнарю.

### 1.1 Примитивы ядра, которые фича переиспользует

| Примитив | Файл | Роль в фиче |
|---|---|---|
| `normalizeChannelLink(raw)` | `core/db/discovery.ts:95` | канонизация ссылки; единая точка валидации формата (R15) и дедупа (R12) |
| `getChannelStatus(admin, link)` | `core/db/discovery.ts:286` | известен ли канал и кому назначен → ветвление R13/R14 |
| `registerChannel(admin, link, agent)` | `core/db/discovery.ts:130` | занести НОВЫЙ канал с назначением (`INSERT OR IGNORE`) |
| `assignmentCounts(admin)` | `core/db/discovery.ts:228` | число закреплённых каналов по агентам — вход балансировки R6 |
| `addJoinQueue(agent, [link])` | `core/db/join-queue.ts:61` | постановка канала в очередь вступления агента (R7) |
| `upsertTask`, `computeDefaultSchedule("join-queue")`, `listTasks` | `core/db/tasks.ts` | запуск/включение процесса вступления (R8) |
| Bot API-клиент (`fetch`, без фреймворка) | `core/review-bot-api.ts` | образец единственной существующей Bot API-интеграции платформы |

MTProto-резолв ссылок в фиче **не используется**: обнаружение «канал недоступен /
не существует» — зона ответственности процесса вступления (`join-queue`), а не
распределения. Распределение работает только с текстом ссылок и SQLite — сетевой
работы нет (см. §2, §6.3, §6.6).

### 1.2 Соседние механизмы, с которыми надо скоординироваться

- **`channel-rotation`** (заархивирован `2026-09-06`, деплоится): кросс-агентный
  суточный скрипт `src/scripts/periodic/channel-rotation.ts`, переносит каналы в
  статусе `leaved_from_banned` менее загруженному агенту. Уже ввёл:
  - `countActiveChannels(agent)` (`core/db/channels.ts:1556`) — счётчик нагрузки
    по `channels.db`;
  - `features/channel-rotation/plan.ts::planRotation` — балансировщик
    (сортировка по нагрузке один раз + round-robin, тай-брейк `Math.random()`);
  - релакс инварианта `channel-registry` «assignment SHALL NOT change» → теперь
    допускаются ДВА механизма смены назначения (ручной override + rotation).

  Влияние на дизайн разобрано в §6.5 и §8. **Вывод коротко:** переиспользуем
  `forceAssignChannel`/примитивы реестра, но НЕ переиспользуем ни `planRotation`
  (её `Math.random()` нарушает R19-детерминизм, а цель балансировки у неё иная),
  ни счётчик нагрузки `countActiveChannels` (distribution меряет нагрузку по
  реестру `assignmentCounts`, не по `channels.db` — см. §6.5).

- **`channel-metrics`** (`features/channel-metrics/run.ts`, skill `channel-metrics`):
  скрипт, который по CSV-списку ссылок считает через MTProto `subs_count`,
  `avg_views`, `comments_open`, `is_broadcast` и пишет непустой `error` для
  нерезолвящихся ссылок. **Его выход и есть типичный вход этой фичи**: CSV с
  колонкой `link` + колонки-метрики. Это важно для §6.4 (модель метрик) и §6.6
  (глубина валидации R15).

## 2. Обзор решения

**Один сервис** (`distribution-listener`); поток не является LLM-циклом — весь он
детерминирован (agent-playbook.md, ADR 0001 «scripts-over-openclaw-agent»).
Распределение — это только запись ссылок в SQLite, без обращений к Telegram
(существование/доступность канала обнаружит процесс вступления, §6.6), поэтому оно
выполняется **инлайн** внутри listener'а: обработка занимает единицы секунд,
кратковременная занятость long-poll на это время приемлема. Отдельный worker /
oneshot-процесс не нужен.

```
┌──────────────────────────────────────────────────────────────────┐
│ Администратор ── Telegram ──► Distribution-бот (свой bot-токен)    │
│   1) /<команда> — вход в режим приёма                              │
│   2) CSV-файл (document, ≤20 МБ) + диапазоны agentId               │
│   3) спрашивает статус / получает сводку                          │
└───────────────┬────────────────────────────────────────────────────┘
                │ getUpdates (long-poll, единственный на этот бот)
┌───────────────▼───────────────────────────────────────────────────┐
│ distribution-listener.ts   persistent systemd (Restart=always),    │
│                            один процесс на платформу               │
│  • авторизация по чату (R18, default-deny)                         │
│  • команда → режим приёма; приём файла → сохранение (R26)          │
│  • валидация формата CSV + колонка link (R16)                      │
│  • разбор диапазонов agentId, проверка существования (R17)         │
│  • R24: одна задача за раз (проверка по channel-distribution.db)   │
│  ├─ ИНЛАЙН оркестрация (features/channel-distribution/run.ts):     │
│  │    • формат ссылки (R15) / нет ссылки (R11) / дубль (R12)       │
│  │    • владелец: тот же агент (R13) / другой (R14)                │
│  │    • план балансировки (plan.ts, R6/R19)                        │
│  │    • registerChannel по одному  (R1)                            │
│  │    • addJoinQueue БАТЧЕМ: один вызов на целевого агента (R7)    │
│  │    • upsertTask join-queue целям (R8)                           │
│  │    • счётчики added/skipped/error → distribution_tasks (R2/R9)  │
│  │    • детализация исходов → journald (R28)                       │
│  • статус по запросу (R10) / сводка по завершении (R9)             │
└────────────────────────────────────────────────────────────────────┘
        stdout → journald (journalctl -u tg-distribution-listener)  (R28)
```

**Почему инлайн в одном сервисе, а не listener + отдельный worker.** Резолва ссылок
через MTProto в фиче нет (утверждённое решение — существование канала проверяет
join-queue, §6.6), поэтому тяжёлой сетевой работы, ради которой раньше выделялся
oneshot-worker, не осталось: распределение — быстрые записи в SQLite. Выносить их в
отдельный процесс незачем — это была бы лишняя сущность (agent-playbook.md:
«простота»). Единственное внешнее ограничение — один `getUpdates`-long-poll на
bot-токен — уже соблюдено тем, что distribution-бот отдельный от review-бота (§6.2).

## 3. Структура кода

Отражает слои репозитория (`core/` → `features/` → `scripts/`), как в
task-scheduler и tg-agent-autoregistration.

```
src/
├── core/
│   ├── distribution-bot-api.ts        # НОВЫЙ. Bot API-клиент: getUpdates(message+document),
│   │                                  #   getFile+download, sendMessage. По образцу review-bot-api.ts
│   └── db/
│       ├── distribution.ts            # НОВЫЙ. channel-distribution.db: только таблица задач (§5)
│       └── discovery.ts               # +metrics_json (§6.4)
│
├── features/
│   └── channel-distribution/
│       ├── plan.ts                    # НОВЫЙ. Чистая балансировка R6/R19 (без I/O), тестируется отдельно
│       └── run.ts                     # НОВЫЙ. Оркестрация: дедуп→план→register→queue→join-task.
│                                      #   Обычный модуль (функция), listener зовёт ИНЛАЙН, не подпроцессом
│
└── scripts/
    └── periodic/
        └── distribution-listener.ts   # НОВЫЙ. persistent-сервис (образец review-listener.ts):
                                       #   транспорт (Bot API) + вызов features/.../run.ts инлайн

deploy/systemd/
└── tg-distribution-listener.service   # НОВЫЙ. Type=simple, Restart=always (образец tg-review-listener.service)
```

`core/` и `features/` не знают про systemd и про бота как транспорт; listener —
единственное место, где транспорт (Bot API) встречается с оркестрацией.
Отдельного systemd-юнита под саму работу распределения нет — она выполняется в
процессе listener'а (§2).

## 4. Механика потока

Поток **command-initiated**: сначала спец-команда переводит бота в режим приёма,
затем администратор присылает файл и диапазоны.

```
Вход в режим (US-1)
  admin ─/<команда>─► listener
  listener: авторизация по чату? (R18) ── нет ─► молча игнор / отказ (AC-12), стоп
            да ─► ответ «Пришлите CSV (не более 20 МБ) и диапазоны agentId»,
                  чат переходит в режим ожидания входных данных

Загрузка (US-1, R5, R26)
  admin ─document + текст с диапазонами agentId─► listener
  listener: сохранить файл в distribution-uploads/<ts>-<name>.csv (R26)
            распарсить CSV (разделитель , ; \t — R21), найти колонку link (R20)
            нет link-колонки / битый файл ─► отказ с причиной (R16, AC-11), стоп
            развернуть диапазоны → набор agentId (US-2, R17)
            пусто / не распознан / есть несуществующий agentId ─► отказ (R17, AC-11), стоп

Распределение (US-3, инлайн; R1/R2/R6/R7/R11..R15/R19/R25)
  listener: R24 — есть незавершённая задача? ── да ─► отказ «дождитесь текущей» (AC-15), стоп
            нет ─► INSERT distribution_tasks(status='running', file, agents, requester)
  план балансировки: раскладку каналов по агентам считает plan.ts заранее (R6/R19)
  для каждой строки CSV по порядку (одна SQLite-транзакция, без сети):
     нет ссылки            ─► outcome=skipped, reason=«нет ссылки»        (R11)
     дубль в этом файле    ─► outcome=skipped, reason=«дубликат»          (R12)
     формат ≠ t.me/<user>  ─► outcome=error,   reason=«неподдерж. формат» (R15, только формат)
     уже закреплён за этим же целевым агентом ─► outcome=skipped (идемпотентно, R13)
     уже закреплён за ДРУГИМ агентом          ─► outcome=skipped, reason=«занят»(R14)
     иначе: registerChannel(admin, link, agent) по одному  (R1)
            outcome=added; метрики строки → discovered_channels.metrics_json (R3)
     каждый исход пишется в journald сразу (R28); частичный успех уже зафиксирован в реестре (R25)
  постановка в очередь БАТЧЕМ (R7): каналы группируются по целевому агенту,
     addJoinQueue(agent, [все его каналы]) — один вызов на агента
  для каждого агента, получившего ≥1 канал:
     upsertTask(agent,'join-queue', computeDefaultSchedule) + enable dispatcher-таймер (R8)
  UPDATE distribution_tasks: status='done', счётчики added/skipped/error

Статус и сводка (US-6/US-7, R9/R10)
  admin ─«статус?»─► listener читает distribution_tasks → «идёт / завершена»
  по завершении listener отдаёт сводку в тот же чат: added / skipped / error (R9, AC-7),
     причины сформулированы для нетехнаря (AC-17)
```

Обнаружение «канал недоступен / не существует» здесь НЕ выполняется — это зона
процесса вступления (`join-queue`), куда канал попал на шаге `addJoinQueue` (§6.6).

Порядок разбора строк детерминирован (по порядку CSV), план балансировки
детерминирован (§6.5) → одинаковый вход + одинаковое состояние реестра дают
одинаковый результат (R19).

## 5. Модель данных

### 5.1 Новая БД `channel-distribution.db`

Лежит в workspace админ-агента (`workspaceDir(FUNNEL_ADMIN_AGENT_ID)`) — тот же
приём, что `discovery.db`/`funnel.db`/`private-invites.db` (платформенные данные в
одном месте). Новая функция пути `distributionDbPath(adminAgentId)` в `config.ts`.

Одна таблица — `distribution_tasks` (уровень прогона). Детализацию по каналам
(какой пропущен/с ошибкой и почему) отдельной таблицей НЕ храним: это дублировало
бы журнал (agent-playbook.md: «один факт — один дом»). Per-канальные исходы — в
journald (R28), исходный файл — в `distribution-uploads/` (R26).

```
distribution_tasks
  id            INTEGER PK
  status        TEXT     -- 'running' | 'done'
  file_path     TEXT     -- сохранённый CSV (R26)
  agents_spec   TEXT     -- исходная строка диапазонов (аудит)
  requester_id  TEXT     -- инициатор: чат/аккаунт (аудит)
  added_count   INTEGER
  skipped_count INTEGER
  error_count   INTEGER
  created_at    INTEGER
  finished_at   INTEGER
```

- **R24** (одна задача за раз): перед `INSERT` проверить `SELECT 1 ... WHERE
  status != 'done' LIMIT 1`; есть строка — отказать (AC-15). Сериализация проста
  по построению — обработка инлайн в единственном процессе listener'а, второй
  задачи параллельно не возникает.
- **R27** (история прогонов): строки `distribution_tasks` не удаляются — каждый
  прогон остаётся с его счётчиками, временами и ссылкой на сохранённый файл.
- **R9** (сводка): три счётчика в `distribution_tasks`; детализация исходов —
  журнал прогона в journald.
- **R28** (журнал): stdout listener'а → journald (`journalctl -u
  tg-distribution-listener`), как у остальных сервисов.

## 6. Ключевые решения (варианты с рекомендацией)

### 6.1 Технология бота

| | **A (рекоменд.)** raw `fetch` Bot API | **B** grammy / telegraf | **C** bot-сессия на GramJS |
|---|---|---|---|
| Новая зависимость | нет | да (фреймворк + транзитивные) | нет (GramJS уже есть) |
| Консистентность со стеком | **полная** — уже есть `core/review-bot-api.ts` тем же приёмом | чужой стек, второй способ ходить в Telegram | GramJS есть, но боты через MTProto — нетипично |
| Загрузка документа (CSV) | `getFile` + скачать `api.telegram.org/file/bot<token>/<path>` — руками, но просто | из коробки | возможно (`downloadMedia`), но свой путь |
| Диалог (команда → файл+агенты) | обработчики вручную (поток простой, 2 шага) | удобные сцены/wizard | вручную |
| Сопровождение | наш код (мал), апстрим — только рантайм `fetch` | апстрим фреймворка | апстрим GramJS |

**Рекомендация: A.** На платформе уже есть ровно один Bot API-клиент, написанный
на голом `fetch` без фреймворка (`core/review-bot-api.ts`: `sendMessage`,
`editMessageText`, `answerCallbackQuery`, long-poll `getUpdates`, inline-кнопки,
default-deny фильтрация). Фича добавляет к этому паттерну лишь: обработку `message`
с `document` и `getFile` + скачивание файла. Поток **command-initiated**: спец-команда
`/<команда>` переводит бота в режим приёма, затем администратор присылает CSV-файл
и диапазоны agentId; выбор агентов — текстом (список/диапазоны), inline-кнопки не
нужны (утверждено заказчиком), поэтому `callback_query` фиче не требуется. grammy
оправдан, только если диалог станет заметно сложнее (много шагов, состояние сцен) —
это триггер к пересмотру, но не сегодня.

**Потолок транспорта.** Bot API `getFile` ограничивает скачиваемый файл 20 МБ. Для
текстового CSV каналов это практически недостижимо (сотни тысяч строк). Принят как
данность транспорта (чанкования нет, утверждено); стартовое сообщение бота на входе
в режим приёма явно предупреждает «файл не более 20 МБ».

### 6.2 Топология: один сервис, обработка инлайн

**Решение (утверждено):** отдельный bot-токен + один persistent listener
(`tg-distribution-listener.service`, `Type=simple`, `Restart=always` — копия
`tg-review-listener.service`). Задача распределения обрабатывается **инлайн** в
процессе listener'а; отдельного worker/oneshot нет.

Обоснование инлайн-обработки. Раньше рассматривался вынос работы в отдельный
oneshot-процесс — ради тяжёлого MTProto-резолва ссылок. Это решение отменено:
существование/доступность канала проверяет процесс вступления, не распределение
(§6.6), поэтому у распределения не осталось сетевой работы — это быстрые записи в
SQLite (единицы секунд). Держать под такую работу отдельный процесс — лишняя
сущность (agent-playbook.md: «простота»). Кратковременная занятость
`getUpdates`-цикла на время записи приемлема; запрос статуса R10 обслуживается
между апдейтами.

Почему отдельный bot-токен, а не общий с review-ботом. `getUpdates`-long-poll на
бота допустим ровно один одновременно, и его уже держит `review-listener`; вторая
фича на том же токене означала бы гонку за апдейтами или переписывание узкого
default-deny `review-bot-api` под две роли. Отдельный токен даёт и изоляцию
сбоя/деплоя. Цена — одна новая операционная сущность (секрет + сервис), принята
осознанно (§9).

### 6.3 Что делает listener в ходе задачи

Всё — в одном процессе, без сети:

1. Приём файла (`getFile` + скачивание), сохранение в `distribution-uploads/` (R26).
2. Парсинг CSV (R20/R21), разбор диапазонов agentId (R17).
3. Вызов `features/channel-distribution/run.ts` **как обычной функции** (инлайн):
   валидация формата ссылок (R15), дедуп/владелец (R12/R13/R14), план балансировки
   (R6/R19), `registerChannel` + `addJoinQueue` батчем, `upsertTask` целям (R8),
   счётчики в `distribution_tasks`.
4. Ответ администратору: статус (R10) и итоговая сводка (R9) в тот же чат.

MTProto-сессия не открывается вовсе — ни в listener'е, ни где-либо в фиче.

### 6.4 Модель метрик каналов (R3, R20)

**Факт из кода (проверено grep):** фиксированные колонки метрик в
`discovered_channels` — `sub_count`, `avg_views`, `p50_user`, `p90_users`,
`comments_per_day` — и функция `setChannelMetrics` (`discovery.ts:152`) **не
имеют ни одного вызывающего и ни одного читателя** во всём `src/`. Они
фактически мёртвые: писать в них нечему, читать их некому. Это снимает риск
поломки существующих потребителей при смене модели.

Требование R3/R20: метрики — справочные, произвольного меняющегося состава, имя
метрики = заголовок колонки CSV; на распределение не влияют.

| | **A (рекоменд.)** одно поле `metrics_json` | **B** таблица ключ-значение | **C** оставить фикс. колонки |
|---|---|---|---|
| Произвольный меняющийся состав (R20) | да (любые ключи в JSON) | да | нет — состав жёсткий |
| Соответствие формулировке заказчика («одно поле, формат вроде JSON») | буквальное | нет | нет |
| Новые сущности (простота) | +1 колонка | +1 таблица, +строки на канал | 0, но требование не закрыто |
| Запрашиваемость по метрике | слабая (JSON-извлечение) | сильная (SQL по ключу) | сильная, но состав фикс. |

**Рекомендация: A** — добавить `metrics_json TEXT` в `discovered_channels`
(аддитивная миграция, как все прочие в проекте); фича пишет туда JSON-объект
`{<заголовок колонки>: <значение>, ...}` из всех не-`link` колонок CSV. Пять
легаси-колонок **оставить на месте** (не удалять) — обратимость и дисциплина
аддитивных миграций; так как читателей нет, физический DROP не требуется для
работы фичи и может быть сделан отдельной разовой гигиеной позже. B (ключ-значение)
предпочесть, только если заказчику важна выборка каналов по конкретной метрике —
но R3 явно говорит «не влияют на распределение», то есть аналитическая выборка вне
рамок → сильная запрашиваемость сейчас не нужна (простота).

**Обязательная проверка перед физическим удалением легаси-колонок:** grep по всему
репозиторию, включая `.claude/skills/*/` и `*.py` — у `funnel.db` уже был скрытый
внешний SQL-читатель (skill `funnel-stats`); для `discovery.db` таких пока не
найдено, но правило то же (см. память проекта о скрытых потребителях схемы).

### 6.5 Алгоритм балансировки R6 (детерминированность R19)

R6/AC-13 требуют **выровнять ИТОГОВОЕ число закреплённых каналов**: агенту с
меньшей текущей нагрузкой достаётся больше новых. R19 требует детерминизма.

| | **A** greedy/water-fill (рекоменд.) | **B** сортировка+round-robin (как rotation) | **C** переиспользовать `planRotation` |
|---|---|---|---|
| Выравнивает ИТОГ (AC-13) | **да** — каждый канал наименее загруженному с учётом уже назначенного в прогоне | частично — уравнивает только НОВЫЕ за круг, не итог при большом стартовом перекосе | как B |
| Детерминизм (R19) | да (тай-брейк по `agentId`) | да, если тай-брейк детерминирован | **нет** — `planRotation` использует `Math.random()` |
| Риск залпа на одного агента | да — но это и есть цель R6 (подтянуть отстающего) | ниже (rotation ради этого её и выбрал) | ниже |

**Решение: A** — детерминированный water-fill: держим текущую нагрузку каждого
целевого агента (старт = `assignmentCounts`, см. ниже), каждый следующий канал
отдаём агенту с минимальной текущей нагрузкой, при равенстве — меньший `agentId`;
после назначения инкрементим его нагрузку. Это буквальное прочтение R6/AC-13 и
удовлетворяет R19. Чистую функцию кладём в `features/channel-distribution/plan.ts`
(зеркало `channel-rotation/plan.ts`, тестируется без БД).

**Почему НЕ переиспользуем `planRotation` (C):** её `Math.random()`-тай-брейк
прямо нарушает R19, а её цель обратна R6 — rotation СПЕЦИАЛЬНО избегает
«подтягивания» одного агента, чтобы не спровоцировать залповое вступление
забаненного (health-риск). У admin-инициированного распределения цель явно иная —
выровнять. Поэтому два балансировщика сосуществуют с РАЗНЫМИ целями осознанно
(§8). Это надо явно записать в спеки, иначе будущий читатель решит, что один из
них — ошибка.

**«Текущая нагрузка» = `assignmentCounts` (реестр `discovered_channels`)**
(утверждено заказчиком), НЕ `countActiveChannels` (`channels.db`, которым меряет
нагрузку `channel-rotation`). Причина: `channels.db` наполняется только ПОСЛЕ
фактического вступления, а join асинхронен — только что распределённые каналы там
ещё не видны, поэтому два прогона подряд свалили бы пачки на одного и того же
агента. `assignmentCounts` самосогласован (та же БД, куда фича пишет) и
детерминирован (R19). Следствие: определения «нагрузки» у distribution и rotation
намеренно разные — это часть разграничения трёх балансировок (§8).

### 6.6 Валидация ссылки (R11/R12/R14/R15)

Распределение проверяет только ФОРМАТ ссылки; существование и доступность канала
оно не проверяет вовсе (утверждено заказчиком).

- **Формат (R15).** Только `t.me/<channelusername>`. `normalizeChannelLink`
  канонизирует; отдельный предикат отбраковывает `t.me/+...`, `t.me/joinchat/...`,
  `t.me/c/...` и пустой username → outcome `error`.
- **Нет ссылки (R11)** → `skipped` (не `error`). **Дубль в файле (R12)** →
  `skipped`. **Занят другим агентом (R14)** → `skipped`, назначение не трогаем.
  Разделение «пропущена» и «ошибка» — по таблице в §4.
- **Существование/доступность — НЕ здесь.** Обнаружение «канал недоступен / не
  существует» — зона ответственности процесса вступления (`join-queue`), который
  фактически обращается к Telegram при попытке вступить. Распределение лишь ставит
  канал в очередь; нерезолвящийся канал всплывёт позже как ошибка вступления, а не
  как исход распределения. Поэтому MTProto-резолва в фиче нет — ни
  `resolveChannelByUsername`, ни открытия сессии; распределение остаётся чистой
  SQLite-операцией (см. §2, §6.3).

### 6.7 Авторизация по чату (R18)

Авторизация — по ЧАТУ (утверждено заказчиком), тем же приёмом, что у
review-listener: один настроенный уполномоченный чат, а не список отдельных
аккаунтов.

**Решение:** `CHANNEL_DISTRIBUTION_CHAT_ID` в `~/.openclaw/secrets.env`, читается в
`config.ts` из `process.env` — прямой аналог `TELEGRAM_REVIEW_CHAT_ID`. listener
сверяет `chat.id` входящего апдейта с настроенным; не совпал → запрос
игнорируется/отклоняется (AC-12), default-deny — тот же принцип, что уже применён
в `getReviewCallbackUpdates`. Сама процедура настройки чата — вне рамок (заявлено
в requirements «Вне рамок»); в рамках — только механизм чтения.

### 6.8 Аудит (R26/R27/R28)

- **R26** (файлы): каталог `distribution-uploads/` в workspace админ-агента
  (новый путь в `config.ts`, приём как `reportsDir`), имя с UTC-timestamp —
  прогоны не перезатирают друг друга.
- **R27** (история результатов): `distribution_tasks` (§5.1), строки не удаляются;
  детализация исходов по каналам — в журнале прогона (journald).
- **R28** (журнал выполнения): journald сервиса `tg-distribution-listener`.

Три разных носителя для трёх разных фактов — дублирования знания нет.

**Сосуществование, не вытеснение.** `distribute-channels.ts` и соседи остаются

скрипты в этом change не переписывать** (обратимость, узкий скоуп). Если позже

функцией — отдельной задачей, не здесь.

## 8. Влияние на OpenSpec

Затрагиваемые capability и предлагаемая структура change `channel-distribution`:

```
openspec/changes/channel-distribution/
├── proposal.md
├── design.md            # это архитектурное решение, перенесённое в формат change
├── tasks.md
└── specs/
    ├── channel-distribution/spec.md   # ADDED — вся новая способность
    ├── channel-registry/spec.md       # MODIFIED — модель метрик + разграничение балансировок
    └── channel-metrics/spec.md        # MODIFIED (опц.) — если семантика метрик уезжает в JSON
```

- **ADDED `channel-distribution`:** приём CSV (R5/R16/R20/R21), исходы строки
  (R2/R11..R15/R25), балансировка R6/R19, постановка в очередь и запуск join
  (R7/R8), задача и статус (R24/R10), сводка (R9), авторизация по чату (R18), аудит
  (R26/R27/R28).

- **MODIFIED `channel-registry`:** два пункта.
  1. **Модель метрик.** Сейчас `channel-registry` не описывает метрики явно, но
     схема несёт мёртвые фикс-колонки. Зафиксировать: метрики хранятся как единое
     поле произвольного состава (`metrics_json`), справочно, на назначение не
     влияют (R3).
  2. **Разграничение балансировок.** Существующее требование
     «Round-robin assignment within a run … accumulated load is not taken into
     account» **прямо противоречит R6** (который учитывает накопленную нагрузку).
     Разрешить конфликт НЕ переписыванием discovery-требования, а разграничением
     областей: discovery-поток остаётся round-robin без учёта истории;
     channel-distribution определяет СВОЁ load-aware требование. Явно
     задокументировать, что на платформе теперь ТРИ разные балансировки с разными
     целями: discovery (round-robin), rotation (health-spread), distribution
     (load-equalize). Без этой записи любой из трёх выглядит как баг относительно
     двух других.

- **Координация с `channel-rotation`** (уже в `openspec/specs/`): инвариант
  «assignment SHALL NOT change» rotation уже релаксировал под два механизма.
  channel-distribution в НОРМАЛЬНОМ потоке **не переназначает** уже закреплённые
  каналы (R14 — чужой канал пропускается), поэтому ТРЕТИЙ релакс инварианту не
  нужен — фича укладывается в существующие пункты «New agent» / «Round-robin».
  Это надо явно проверить при написании дельты, чтобы случайно не ввести второй
  независимый релакс одного инварианта.

## 9. Решённые вопросы и риски

**Решённые вопросы** (ранее — развилки, закрыты заказчиком):

1. **Глубина валидации R15** → только формат `t.me/<channelusername>`;
   существование и доступность — зона `join-queue`, MTProto-резолва в фиче нет (§6.6).
2. **«Текущая нагрузка» для R6** → `assignmentCounts` (реестр), не
   `countActiveChannels` (§6.5).
3. **Модель метрик** → одно поле `metrics_json` (§6.4).
4. **Выбор агентов** → текстом: список и/или один или несколько диапазонов agentId;
   inline-кнопки / `callback_query` не нужны (§6.1).
5. **Сводка и статус** → в тот же чат, где бот (§4).
6. **Лимит объёма** → искусственных лимитов нет; потолок транспорта Bot API 20 МБ
   на файл принят как данность, стартовое сообщение предупреждает администратора;
   чанкования нет (§6.1).

**Риски:**

- **Расхождение канонизации ссылок** (тот же риск, что отмечен в
  `channel-rotation` design): если канал ранее занесён в реестр под ссылкой,
  отличной от текущей `normalizeChannelLink` (например ручным
  `import-agent-pool` с нестандартной ссылкой), дедуп R12/R14 может не распознать
  его как известный. Не ломает распределение, но искажает `assignmentCounts`.
  Разовая гигиена реестра — вне рамок.
- **Зависшая задача R24:** `distribution_tasks.status` — источник истины «занято».
  Если listener убит между `status='running'` и `'done'` (краш, рестарт деплоя),
  строка останется `running` и заблокирует новые задачи (R24). Нужна политика
  снятия зависшей задачи (таймаут по `created_at` → пометить прерванной) —
  предложить на этапе реализации. Повторный прогон того же файла не задваивает
  данные: `registerChannel` и `addJoinQueue` — `INSERT OR IGNORE`, уже добавленные
  каналы распознаются как «занятые» (R13/R14) и пропускаются.
- **Отдельный bot-токен** — новая операционная сущность (секрет, мониторинг
  сервиса). Осознанная цена изоляции от review-бота (§6.2).
