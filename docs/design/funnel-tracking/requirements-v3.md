# Воронка v3: требования

> **О чём документ.** User Stories и Acceptance Criteria для очередного
> набора изменений отчёта воронки (funnel-tracking) поверх уже действующей
> версии, зафиксированной в
> [funnel-tracking-v2.md](./funnel-tracking-v2.md) и
> [requirements-v2.md](./requirements-v2.md). Документ фиксирует только то,
> что согласовано; вопросы, возникавшие в ходе анализа, обсуждались и сняты
> до записи документа.
>
> **Состав изменений:** убрать интенсивность из показателя «каналы с
> активностью»; заменить показатель «сообщений отправлено» на «каналы с
> отправкой» и полностью исключить личные сообщения (DM) из отчёта; добавить
> разбивку заявок в приватный канал по агенту; ограничить отчёт активными
> агентами; добавить в CSV ежедневную разбивку отправленных сообщений по
> каналам.

---

## US-1 — Убрать интенсивность из показателя «каналы с активностью»

**Как** координатор, читающий отчёт воронки,
**я хочу** видеть по каждому агенту только количество каналов с активностью
за отчётный день,
**чтобы** показатель не содержал интенсивность сообщений в час, которая для
оценки конверсии не используется и добавляет отчёту visual noise без
практической пользы.

**Acceptance Criteria:**

- Дано: сформирован отчёт воронки за отчётный день.
  Тогда: показатель «каналы с активностью» в текстовом сообщении отображает
  только число каналов, без интенсивности сообщений в час в любом виде (ни
  в скобках, ни отдельным столбцом).
- Дано: сформировано CSV-вложение отчёта.
  Тогда: в CSV отсутствует столбец интенсивности сообщений в час; столбец
  количества каналов с активностью остаётся.
- Дано: у агента за отчётный день нет ни одного активного канала.
  Тогда: показатель отображается как 0, как и до этого изменения.

---

## US-2 — Заменить «сообщений отправлено» на «каналы с отправкой»

**Как** координатор, оценивающий охват рассылки агента,
**я хочу** видеть количество каналов/групп, куда за отчётный день отправлено
хотя бы одно сообщение (без учёта личных сообщений),
**чтобы** показатель отражал охват по каналам, а не суммарное число попыток
отправки, и не смешивал переписку в группах с личными сообщениями.

Далее в документе показатель называется «каналы с отправкой» — только для
краткости ссылки на него, определение показателя не меняется.

**Acceptance Criteria:**

- Дано: агент за отчётный день отправил несколько сообщений в один и тот же
  канал/группу.
  Тогда: в показатель «каналы с отправкой» этот канал засчитывается один
  раз, независимо от числа отправленных в него сообщений.
- Дано: агент за отчётный день отправлял только личные сообщения (DM), без
  сообщений в группы/каналы.
  Тогда: показатель «каналы с отправкой» для этого агента равен 0.
- Дано: сформирован отчёт воронки.
  Тогда: ни в текстовом сообщении, ни в CSV-вложении личные сообщения не
  учитываются ни в этом показателе, ни в каком-либо другом показателе
  отчёта, ни в каком-либо агрегате (включая итоговую строку).
- Дано: сформирована итоговая строка отчёта (сумма по всем агентам).
  Тогда: итоговое значение показателя «каналы с отправкой» — сумма значений
  по агентам, тем же способом, что и остальные суммируемые по агентам
  показатели отчёта.
- Дано: личные сообщения исключены из отчёта воронки.
  Тогда: замены или компенсирующего показателя по числу отправленных личных
  сообщений нигде в отчёте не вводится — исключение окончательное и не
  требует альтернативного отражения этой активности в этом отчёте.

## US-3 — Заявки в приватный канал в разбивке по агенту

**Как** координатор, оценивающий вклад каждого агента в привлечение
подписчиков приватного канала,
**я хочу** видеть число заявок в приватный канал не только суммарно по
платформе, но и по каждому агенту отдельно — и в текстовом сообщении, и в
CSV,
**чтобы** понимать, чья персональная пригласительная ссылка приводит заявки,
а чья — нет.

**Предпосылка (вне этого требования):** у каждого активного агента должна
существовать собственная пригласительная ссылка в приватный канал. Создание
и хранение этих ссылок реализовано отдельным изменением
(`private-invite-links`): реестр «агент → ссылка» — таблица
`private_invite_links`, генерация — инструмент `tg_private_invite_links` по
списку агентов, вызываемый оператором. Регенерация ссылки для нового
активного агента (или после её отзыва) — отдельная ручная операция
оператора, не автоматизирована и не входит в это требование.

**Acceptance Criteria:**

- Дано: у агента настроена персональная пригласительная ссылка, и по ней
  зафиксированы заявки за отчётный день.
  Тогда: число заявок этого агента отображается отдельным столбцом и в
  текстовой таблице отчёта, и в CSV-вложении, в формате «дельта (текущий
  абсолют)» — как и остальные показатели-снапшоты отчёта (просмотры поста,
  подписчики канала).
- Дано: у агента ещё нет сохранённого предыдущего значения по его ссылке
  (например, ссылку только что завели).
  Тогда: показывается только текущий абсолют без дельты — так же, как это
  уже происходит для других показателей-снапшотов при отсутствии
  предыдущего значения.
- Дано: агент активен (проходит фильтр US-4), но персональная
  пригласительная ссылка для него ещё не настроена.
  Тогда: в его ячейке показателя «заявки по агенту» — прочерк («—»), и в
  тексте, и в CSV; прочерк не равнозначен нулю и не должен подменяться на 0.
- Дано: подсчитывается итоговое (платформенное) число заявок в приватный
  канал.
  Тогда: это итоговое число — сумма заявок по персональным ссылкам всех
  агентов (включая агентов с прочерком, которые дают в сумму 0 и не
  блокируют расчёт итога); отдельного, независимого от разбивки по агентам
  способа подсчёта платформенного итога больше нет — итог всегда равен этой
  сумме по определению, расхождения между ними не бывает.
- Дано: агент исключён из отчёта фильтром активности (US-4).
  Тогда: заявки по этому агенту не показываются нигде в отчёте, как и
  остальные его показатели, и не участвуют в платформенном итоге.

## US-4 — Учитывать в отчёте только активных агентов

**Как** координатор, читающий отчёт воронки,
**я хочу** видеть в отчёте только агентов с включённым мониторингом,
**чтобы** отчёт не показывал агентов, которые в текущий момент не работают,
и не требовал вручную отличать их от работающих.

Мониторинг агента — это периодическая задача с заданным интервалом
выполнения (действующая версия или прежняя миграционная версия — обе
покрывают одну и ту же функцию мониторинга). Агент считается активным, если
включён хотя бы один монитор **или** задача прогрева аккаунта
(`account-warmup`); неактивным — если не выполняется ни то, ни другое.
Прогрев добавлен как альтернатива монитору позже: агент на прогреве (ещё без
настроенного монитора) уже работает от своего имени и должен считаться
активным. Активность проверяется по текущему состоянию задач на момент
формирования отчёта, а не по истории их включённости в течение отчётного
дня — истории включённости в системе не хранится, поэтому отдельное правило
«был активен весь отчётный день» не вводится.

**Acceptance Criteria:**

- Дано: у агента на момент формирования отчёта включён хотя бы один монитор
  (любой версии) или задача `account-warmup`.
  Тогда: агент присутствует в отчёте — и в текстовом сообщении, и в CSV —
  со всеми показателями за отчётный день.
- Дано: у агента на момент формирования отчёта отключены все версии монитора
  и `account-warmup`.
  Тогда: агент отсутствует полностью — ни в тексте, ни в CSV, ни каким-либо
  отдельным упоминанием (пометкой, отдельным списком и т.п.) — независимо
  от того, была ли у него активность в течение самого отчётного дня.
- Дано: мониторинг агента был включён в течение отчётного дня, но к моменту
  формирования отчёта уже отключён.
  Тогда: агент в отчёт не включается — используется состояние на момент
  формирования отчёта, а не состояние в течение дня.
- Дано: у агента на момент формирования отчёта одновременно включены обе
  версии задачи мониторинга.
  Тогда: агент присутствует в отчёте один раз (не дублируется).
- Дано: агент только что стал активным (мониторинг включили), и данных за
  отчётный день по нему ещё нет.
  Тогда: агент присутствует в отчёте, его показатели за день отображаются
  как отсутствие данных/ноль — так же, как для любого агента без
  активности за день, без специальной обработки.

## US-5 — Ежедневная разбивка по каналам в CSV

**Как** координатор, анализирующий детальную картину рассылки,
**я хочу** видеть в CSV-вложении, в какие именно каналы и сколько сообщений
каждый агент отправил за отчётный день, с переходимой ссылкой на каждый
канал,
**чтобы** можно было разобрать по каждому каналу, куда именно уходят
сообщения агента, и сразу перейти в канал, не ограничиваясь агрегированным
показателем «каналы с отправкой».

**Acceptance Criteria:**

- Дано: сформировано CSV-вложение отчёта.
  Тогда: в нём присутствует построчная разбивка «агент — канал — число
  сообщений за отчётный день», отдельно от основной построчной таблицы по
  агентам.
- Дано: агент отправил за отчётный день сообщения в несколько разных
  каналов.
  Тогда: для каждого канала — отдельная строка разбивки с числом сообщений
  именно в этот канал.
- Дано: строка разбивки для конкретного канала.
  Тогда: канал в ней идентифицируется переходимой ссылкой (URL) на этот
  канал, а не только названием или техническим идентификатором.
- Дано: канал, в который агент не отправлял сообщений в отчётный день (в
  том числе если канал был просмотрен монитором без отправки).
  Тогда: этот канал не появляется строкой в разбивке.
- Дано: разбивка считается для отчётного дня.
  Тогда: границы дня — те же границы суток часового пояса UTC+5, что
  используются во всём остальном отчёте (не границы суток UTC).
- Дано: личные сообщения (DM).
  Тогда: они не входят в разбивку — разбивка охватывает только сообщения в
  группы/каналы, как и показатель «каналы с отправкой» из US-2.
- Дано: агент исключён из отчёта фильтром активности (US-4).
  Тогда: разбивка по его каналам в CSV не включается.

---

## Сквозное требование — границы отчётного дня

**Acceptance Criteria:**

- Дано: любой показатель отчёта воронки, вычисляемый «за отчётный день»
  (включая новую разбивку по каналам из US-5).
  Тогда: началом и концом отчётного дня служат границы суток часового
  пояса UTC+5 — то же правило, что уже действует для остальной аналитики
  отчёта; отдельного, отличающегося правила для новой разбивки не вводится.
