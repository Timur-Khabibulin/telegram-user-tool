# Funnel Tracking — Design Doc

## Problem

Несколько агентов работают параллельно и ведут трафик в единый приватный Telegram-канал через пост в своих публичных каналах. Сейчас невозможно понять:

- насколько активен каждый агент в группах и DM-рассылке
- насколько растёт охват (просмотры поста в публичном канале, подписчики публичных каналов)
- как растёт приватный канал в целом

---

## Goals

1. Собирать ежедневные метрики активности и охвата по каждому агенту
2. Собирать общий прирост приватного канала (без атрибуции по агентам)
3. Отправлять ежедневный сводный отчёт в Telegram

---

## Non-Goals

- **Атрибуция вступлений в приватный канал по user_id** — не в скоупе первой итерации (см. Future Work)
- Уникальные инвайт-ссылки на приватный канал
- Real-time дашборд
- Отслеживание кликов на профиль агента (Telegram API не предоставляет эти данные)
- Хранение истории переписки пользователей в публичных каналах

---

## Воронка

```
Агент пишет в группы / отправляет DMs
             │
             ▼
Пользователь замечает агента → переходит в профиль
             │
             ▼
Публичный канал агента (закреплён в профиле аккаунта; свой у каждого)
             │  подписывается, видит пост со ссылкой
             ▼
Просмотры поста канала
             │  кликает ссылку
             ▼
Приватный канал (единый) ← цель
```

Измеряемые шаги: активность в группах → личные сообщения → просмотры поста канала → прирост публичного канала → прирост приватного канала.

---

## Архитектура

Один **Tracking Agent** запускается по cron раз в день (oneshot-скрипт + systemd-таймер — зеркало `daily-summary`). Он динамически обнаруживает все активные агенты через `listAgentIds()` (читает директории `~/.openclaw/workspace-<agentId>/`), подключается к каждому через отдельный `TelegramClient` (каждый — через свой прокси) и собирает метрики.

**Публичный канал агента определяется автоматически** — это канал, закреплённый в профиле аккаунта (personal channel). Его ID и ID единственного поста берутся из `users.GetFullUser(self)` → `personalChannelId` / `personalChannelMessage`. Отдельный конфиг со списком публичных каналов не нужен.

```
Tracking Agent (один cron, раз в день)
    │
    ├── listAgentIds() → [agent1 … agentN] из ~/.openclaw/workspace-*/
    │
    ├── для каждого агента:
    │     ├── tg-replies.db  → COUNT replies.sentAt за день       (ответы в группах)
    │     ├── tg-channels.db → COUNT dm_history.sentAt за день    (личные сообщения)
    │     ├── users.GetFullUser(self) → personalChannelId + personalChannelMessage
    │     │        (публичный канал из профиля + id его единственного поста)
    │     ├── GetMessagesViews(channel, [postId]) → просмотры поста   (снапшот)
    │     └── GetFullChannel(channel) → participantsCount            (подписчики, снапшот)
    │
    ├── через agent1 (админ приватного канала):
    │     └── GetChatInviteImporters(privateChannel, requested=true) → заявки на вступление (снапшот)
    │
    └── формирует дельты, пишет daily_stats, шлёт отчёт в Saved Messages agent1
```

**Почему один агент, а не cron на каждого:** при N агентах единый tracking agent проще конфигурировать, логика агрегации сосредоточена в одном месте.

**Обнаружение агентов:** `listAgentIds()` — существующая утилита платформы, читает `~/.openclaw/workspace-<agentId>/` и возвращает список `agentId`. Tracking agent вызывает её в начале каждого прогона — список агентов всегда актуален без ручной конфигурации.

**Идентификация приватного канала:** agent1 — **админ** приватного канала (не создатель). Его ID не выводится из профиля (профильный канал agent1 — это его публичный канал). Поэтому ID приватного канала задаётся **одним значением** при запуске скрипта — аргумент `--private-channel <id>` (по аналогии с `--admin agent1` в `daily-summary`). `access_hash` резолвится в рантайме из `getDialogs` agent1 (канал есть в его диалогах как у участника), по той же конвенции peerCache, что и в остальном коде. Это единственная ручная настройка фичи. Альтернатива без конфига — вытащить инвайт-ссылку из поста публичного канала и резолвить через `CheckChatInvite` (см. Alternatives).

**Граница дня:** агрегация ведётся по **завершившемуся дню UTC+5** — переиспользуем `startOfUtcPlus5Day` / `finishedDayWindow` из `features/funnel/runs-summary`. Таймер срабатывает в 19:00 UTC = 00:00 UTC+5 (как у `daily-summary`), поэтому окна «Воронки» и «Дневной сводки» совпадают.

**Устойчивость:** подключение и сбор метрик по каждому агенту обёрнуты в try/catch — мёртвая сессия/прокси одного агента пропускается с пометкой в отчёте, прогон остальных не срывается.

## MTProto-вызовы

| Метрика | MTProto-метод | Кто вызывает | Права |
|---|---|---|---|
| Публичный канал агента + id поста | `users.GetFullUser(InputUserSelf)` → `personalChannelId`, `personalChannelMessage` | каждый агент (свой профиль) | — |
| Просмотры поста | `messages.GetMessagesViews(channel, id=[postId], increment=false)` | каждый агент | участник канала |
| Подписчики публичного канала | `channels.GetFullChannel` → `participantsCount` | каждый агент | участник |
| Заявки на вступление в приватный канал | `messages.GetChatInviteImporters(peer, requested=true)` → длина списка | только agent1 | admin с правом `invite_users` |

Примечания:

- `access_hash` публичного канала берётся из массива `chats` ответа `GetFullUser` — отдельный resolve не нужен.
- В канале всегда **ровно один пост**, поэтому `personalChannelMessage` однозначно его идентифицирует; вопрос «первый/последний пост» не стоит, id поста стабилен между прогонами.
- Если у аккаунта не задан профильный канал (`personalChannelId` пуст) — агент пропускается с пометкой в отчёте.
- **Заявки = pending (вариант A):** `GetChatInviteImporters(requested=true)` отдаёт текущие **неодобренные** заявки. Дельта между снапшотами корректно отражает новые заявки, пока их не одобряют массово; одобрение уменьшает pending и может дать отрицательную дельту. Более устойчивая альтернатива (кумулятивный счёт через `GetAdminLog`) — см. Future Work.
- **Права agent1:** чтение заявок требует админ-права `invite_users`. Если agent1 добавлен админом с урезанными правами — вызов вернёт `CHAT_ADMIN_REQUIRED`. Проверить на живом аккаунте до реализации.

## Data Model

Все таблицы хранятся в БД `~/.openclaw/workspace-agent1/funnel.db` (отдельного «трекинг-агента» не заводим — скрипт пишет в workspace agent1, он же получатель отчёта).

### `channel_snapshots` — снапшоты метрик каналов

| Поле | Тип | Описание |
|---|---|---|
| id | INTEGER PK | автоинкремент |
| agent_id | TEXT | Идентификатор агента |
| snapped_at | INTEGER | Unix timestamp снапшота |
| public_channel_subs | INTEGER | Подписчики публичного канала агента |
| post_id | INTEGER | ID поста канала на момент снапшота (диагностика) |
| post_views | INTEGER | Просмотры поста канала |
| private_pending_requests | INTEGER | Кол-во неодобренных заявок на вступление в приватный канал (только для agent1, иначе NULL) |

Дельта считается на лету: значение текущего снапшота минус значение предыдущего снапшота того же `agent_id`.

**Защита от двойного прогона** реализуется через эту же таблицу: перед записью нового снапшота tracking agent проверяет, есть ли уже запись с `agent_id = ?` и `snapped_at` в пределах текущего дня UTC+5 (от `startOfUtcPlus5Day`). Если да — прогон пропускается. Отдельная таблица состояния не нужна.

### `daily_stats` — предвычисленные дневные агрегаты

| Поле | Тип | Описание |
|---|---|---|
| date | TEXT | Дата дня UTC+5 (YYYY-MM-DD) |
| agent_id | TEXT | Идентификатор агента |
| group_replies | INTEGER | Ответов в групповых чатах за день |
| dms_sent | INTEGER | Личных сообщений отправлено за день |
| post_views_delta | INTEGER | Прирост просмотров поста канала за день |
| post_views_abs | INTEGER | Абсолютное значение просмотров поста на момент снапшота |
| public_subs_delta | INTEGER | Прирост подписчиков публичного канала за день |
| public_subs_abs | INTEGER | Абсолютное значение подписчиков публичного канала на момент снапшота |
| private_requests_delta | INTEGER | Прирост заявок на вступление в приватный канал за день (только agent1) |
| private_requests_abs | INTEGER | Кол-во неодобренных заявок на момент снапшота (только agent1) |

---

## Источники данных по метрикам

| Метрика | Источник | Инкрементальность |
|---|---|---|
| `group_replies` | **`tg-replies.db`** → таблица `replies`, COUNT по `sentAt` за день UTC+5 | читается из существующей БД агента, новые записи за день |
| `dms_sent` | **`tg-channels.db`** → таблица `dm_history`, COUNT по `sentAt` за день UTC+5 | читается из существующей БД агента, новые записи за день |
| `post_views_delta` | MTProto `GetMessagesViews` по `personalChannelMessage`, снапшот раз в день, дельта = текущий − предыдущий | полное значение в `channel_snapshots`, дельта и абсолют в `daily_stats` |
| `public_subs_delta` | MTProto `GetFullChannel.participantsCount`, снапшот раз в день | полное значение в `channel_snapshots`, дельта и абсолют в `daily_stats` |
| `private_requests_delta` | MTProto `GetChatInviteImporters(requested=true)` через agent1, снапшот раз в день | снапшот pending-заявок в `channel_snapshots`, дельта и абсолют в `daily_stats` |

> `replies` и `dm_history` лежат в **разных** файлах БД (`tg-replies.db` и `tg-channels.db` соответственно) — это два отдельных подключения на агента.

**Инкрементальность для снапшотов:** tracking agent хранит последний снапшот в `channel_snapshots`. При каждом прогоне делает новый снапшот и вычитает предыдущее значение. Защита от двойного прогона — через проверку наличия снапшота за текущий день UTC+5 в `channel_snapshots`.

## Формат ежедневного отчёта

Отчёт отправляется в **Saved Messages (Избранное) agent1** через `sendMessage("me", ...)` на аккаунте agent1.

```
📊 Воронка за 25 мая

Агент      Группы  Личные  Просмотры поста  Подписчики канала
────────────────────────────────────────────────────────────
agent_1      24       3    +150 (4320)       +12 (1240)
agent_2      18       2     +89 (2910)        +8  (870)
agent_3       0       0     +45 (1180)        +3  (340)
agent_4      32       5     +12  (890)        +5  (520)
agent_5       8       1     +34 (2100)        +2  (210)
────────────────────────────────────────────────────────────
Итого        82      11    +330              +30

Заявки в приватный канал: +13 (847)
```

**Колонки:**
- **Группы** — ответов в групповых чатах за день (из `replies`)
- **Личные** — личных сообщений отправлено за день (из `dm_history`)
- **Просмотры поста** — прирост просмотров поста публичного канала агента за день; в скобках — абсолютное значение на момент снапшота
- **Подписчики канала** — прирост подписчиков публичного канала агента за день; в скобках — абсолютное значение на момент снапшота
- **Заявки в приватный канал** — прирост неодобренных заявок на вступление за день + текущее число заявок в скобках; только от agent1

---

## Success Metrics

- Отчёт отправляется ежедневно без ручного вмешательства
- Данные не дублируются при повторных запусках (защита через проверку `channel_snapshots` по дню UTC+5)
- Все снапшоты канала доступны для ретроспективного анализа

## Alternatives Considered

**Атрибуция по уникальным инвайт-ссылкам**
Каждому агенту — своя ссылка на приватный канал. Атрибуция была бы абсолютной. Отклонено: требует замены ссылок во всех публичных каналах, усложняет управление при росте числа агентов.

**Cron на каждого агента**
Каждый агент самостоятельно пишет свои метрики. Отклонено: усложняет конфигурацию при N агентах, логика агрегации размазывается. Один tracking agent чище.

**Только агрегаты без снапшотов**
Хранить только `daily_stats` без сырых `channel_snapshots`. Отклонено: теряется возможность пересчитать дельты при ошибке или пропуске прогона.

**Явный конфиг ID публичных каналов**
Хранить `publicChannelId` в каждом `tg-account.json`. Отклонено: профильный канал (personal channel) даёт ID автоматически через `users.GetFullUser`, ручной конфиг на агента не нужен. Остаётся только один ID приватного канала (для agent1).

**Авто-определение приватного канала из ссылки в посте**
Распарсить инвайт-ссылку из поста публичного канала и резолвить через `CheckChatInvite` (agent1 уже участник → `ChatInviteAlready` с `access_hash`) — приватный канал без ручного конфига. Отложено: для первой итерации проще передать ID аргументом `--private-channel`; парсинг текста поста + обработка форматов ссылок добавляют хрупкости. Кандидат на config-free апгрейд.

> Развилка «первый пост / последний пост» (рассматривалась в ранних итерациях) неактуальна: в канале всегда ровно один пост, его id берётся из `personalChannelMessage` и стабилен.

## Future Work

**Атрибуция вступлений в приватный канал по агентам:**

1. Tracking agent через каждый аккаунт вызывает `channels.GetAdminLog` с фильтром `join` для своего публичного канала — получает `(user_id, joined_at)`
2. Через agent1 вызывает `channels.GetAdminLog` для приватного канала — получает `(user_id, joined_at)`
3. JOIN по `user_id`: если пользователь сначала подписался на публичный канал агента X, а затем вступил в приватный — вступление атрибутируется агенту X
4. Вступления без совпадения помечаются как неатрибутированные

Это требует хранения `public_subs(user_id, agent_id, subscribed_at)` и `private_joins(user_id, joined_at, attributed_agent_id)`, а также решения по окну атрибуции (сколько дней между подпиской и вступлением считается валидным).

**Кумулятивный счёт заявок (вариант B):**
Заменить снапшот pending (`GetChatInviteImporters`) на чтение `channels.GetAdminLog` приватного канала с фильтром join/invite — события `participantJoinByRequest` с таймстемпами дают точный счёт заявок за день UTC+5, не зависящий от того, одобрены они или нет. Устойчивее снапшота, но требует пагинации лога. Если каждый агент будет использовать **свою** инвайт-ссылку на приватный канал, `GetChatInviteImporters(link=...)` / события лога по ссылке дадут и атрибуцию заявок по агентам.

**Open questions для атрибуции:**
- Окно атрибуции: через сколько дней подписка на публичный канал перестаёт учитываться?
- Куда отправлять расширенный атрибуционный отчёт — в Saved Messages agent1 (как основной) или в отдельный служебный чат?
- Privacy: нужно ли хранить `user_id` долгосрочно?
