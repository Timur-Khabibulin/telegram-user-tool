# Post freshness gate — архитектура

Design-doc (HOW). Источник требований (ЧТО) — [requirements-v1.md](requirements-v1.md),
подтверждён координатором. Бизнес-правила R1–R5 и алгоритм (раздел 5 требований) не
пересматриваются — здесь проектируется, в каком компоненте, какими структурами данных
и каким кодом этот алгоритм реализуется.

Статус: предложение архитектора, ожидает утверждения. Прикладной код не написан.

Обязательное ограничение (прямое указание пользователя, не предмет обсуждения):
**решение аддитивное**. `src/skills/monitor.ts` не меняется ни строкой и продолжает
работать как сейчас. Новая логика живёт в отдельном скилле, включаемом по агенту
независимо от старого.

Поведение полей `reply_to_top_id`/`reply_to_msg_id`/`fwd_from.channel_post` Telegram
(разделы 2.2–2.3 ниже) подтверждено официальной документацией, а не по памяти —
ссылки в разделе «Источники».

---

## 1. Резюме решения

Добавляется вторая, независимая версия мониторинга групп — скилл `monitor-v2`
(`src/skills/monitor-v2.ts`) и новый `TaskType` `"monitor-v2"`. Она переиспользует
весь существующий конвейер `monitor.ts` (синхронизация каналов, батч, классификация
сообщений на general/newThread/threadReply, LLM-отбор ответа, DM-скоринг, отправка,
запись прогресса) и добавляет один новый шаг между классификацией и LLM-вызовом:
**гейт свежести** (`src/core/freshness-gate.ts`), который по каждому сообщению трёх
классифицированных бакетов проверяет R1 (первому комментарию — с момента публикации
поста прошло менее 24 часов) или R2 (продолжению — не больше 4 дней) и отбрасывает
несоответствующие (R3) до какого-либо обращения к LLM.

Ключевое техническое решение: **служебная копия поста в чате обсуждения — тоже
сообщение, участвующее в гейте и в LLM-отборе ответа**, а не шум, который можно
отбросить на сетевом уровне. `monitor-v2` получает такие сообщения (v1 их
фильтрует — это не трогается), определяет для них дату поста из их собственного
поля даты (без запроса к Telegram и без кеша — случай B алгоритма требований), и
даёт им пройти через тот же гейт R1/R2/R3, что и обычным комментариям.

Для обычных комментариев (случай A алгоритма) дата поста ветки определяется через
`replyToTopId` сообщения и кэшируется на 30 дней в новой таблице `thread_post_dates`
(`tg-replies.db`), чтобы не запрашивать её у Telegram повторно.

Периодичность обхода для `monitor-v2` — новая константа `MONITOR_V2_CHECK_PERIOD_SECONDS`
(24 часа, R5), независимая от `CHANNEL_CHECK_PERIOD_SECONDS` (72 часа), которую
продолжают использовать `monitor` (v1) и расчёт `activityRate` воронки — без изменений.

Выбор варианта на агента — существующий механизм: таблица `tasks` уже хранит набор
активных `TaskType` на агента (`agentId, type` — PK), значит «какой монитор работает
у агента» — это просто вопрос того, какая из двух строк (`monitor` / `monitor-v2`)
у него включена. Новой сущности для переключателя не требуется. Программной защиты от
одновременного включения обоих вариантов **не делается** — явное решение координатора
(раздел 6, риск 2).

## 2. Ключевые технические решения

### 2.1 Где применяется гейт: после классификации, а не до

**Вариант A (выбран).** `classifyMessages` (существующая функция `core/db/channels.ts`)
вызывается без изменений на полном списке непрочитанных сообщений; гейт свежести
применяется отдельным проходом по трём уже готовым бакетам (`generalMessages` →
кандидаты R1, `newThreadMessages`/`threadReplies` → кандидаты R2), отбрасывая из
каждого не прошедшие сообщения.

**Вариант B (отклонён).** Определять принадлежность к ветке и дату поста для всех
сообщений до классификации, исключать не прошедшие R1/R2/R3 сразу, и только потом
классифицировать выжившие.

Разница между вариантами — только в том, тратятся ли на заведомо отсеиваемые
сообщения несколько дешёвых локальных SQLite-запросов `classifyMessages`
(`findThreadByAgentMsgId`/`findReplyByReplyMsgId`). LLM-вызовов на этих сообщениях в
любом случае не будет (это гарантирует сам факт применения гейта до `analyzeChannelMessages`/
`generateThreadReply` — AC-3), поэтому выигрыш B — не более нескольких SQLite-чтений
на сообщение. Вариант A проще: `classifyMessages` используется как есть, гейт — чистая
надстройка над её результатом, без прикосновения к её внутренностям. Выбран A
(простота).

**Как в это укладывается служебная копия поста.** `classifyMessages` уже (без единой
правки) направляет в `generalMessages` любое сообщение без `replyToMsgId` — в текущем
коде это первая проверка цикла (`if (msg.replyToMsgId === undefined) { generalMessages.push(msg); continue; }`).
Служебная копия поста никогда не является ответом ни на что (у неё нет заголовка
ответа вовсе — она сама начинает ветку), то есть `replyToMsgId` у неё всегда не
определён — она автоматически попадает в `generalMessages`, если конвейер получения
сообщений её не отфильтрует раньше (см. §2.3). Никакой правки самой `classifyMessages`
для этого не требуется — только: (а) не отфильтровывать копию до классификации,
(б) научить гейт распознавать этот случай (§2.3).

Соответствие бизнес-категорий и бакетов:

| Бизнес-категория (требования) | Бакет `classifyMessages` | Правило гейта |
|---|---|---|
| Первый (инициирующий) комментарий агента (R1) — адресован либо самому посту (его копии), либо другому пользователю под этим постом | `generalMessages` (обе формы адресации садятся в этот бакет — см. выше) | `now − postDate < 24 часов` |
| Продолжение уже начатого диалога (R2) | `newThreadMessages`, `threadReplies` | `now − postDate ≤ 4 дня` |

Обоснование соответствия: `generalMessages` — сообщения, чей непосредственный
родитель не является собственным сообщением агента (ни активный тред, ни прежний
ad-hoc ответ), плюс сообщения вовсе без родителя (сама копия поста) — то есть ещё не
было ответа агента под этим постом. Именно из этого бакета LLM (`analyzeChannelMessages`)
выбирает кандидата на **первый** ответ агента — теперь в их числе может оказаться и
сама копия поста. `newThreadMessages`/`threadReplies` — по построению продолжение
переписки, которую агент уже начал; копия поста туда попасть не может (у неё нет
`replyToMsgId`, а значит нет пути в эти бакеты) — это структурно верно, так как R2
описывает только продолжение уже начатого диалога, а не сам пост.

### 2.2 Как определяется корень ветки и дата поста для обычного комментария (случай A алгоритма)

По официальной документации Telegram (`core.telegram.org/api/threads`,
`core.telegram.org/api/discussion`) `reply_to_top_id` заполняется Telegram для
**всех** сообщений внутри ветки обсуждения, включая прямые ответы на закреплённую
служебную копию поста — идентификатор ветки остаётся постоянным на любой глубине
вложенности. Это подтверждает, что случай A алгоритма требований (шаг 2: «сообщение
несёт привязку к корню ветки через `replyToTopId`») достаточен сам по себе для всех
обычных пользовательских комментариев (в том числе самых первых, отвечающих прямо на
копию) — отдельный запасной путь через `replyToMsgId` не нужен.

Технически: `reply_to_top_id` = поле `replyTo.replyToTopId` объекта сообщения GramJS
(`Api.MessageReplyHeader`). `TelegramService.getMessages` уже читает
`m.replyTo?.replyToMsgId` — по аналогии добавляется чтение `m.replyTo?.replyToTopId`
в новое опциональное поле `TgMessage.replyToTopId`. Это чисто аддитивное расширение
интерфейса — `monitor.ts` (v1) это поле не читает, поведение v1 не меняется.

Определение даты публикации по корню (`rootId = replyToTopId`) для обычного
комментария:
1. Проверить кэш `thread_post_dates` по `(chatId, rootId)`.
2. При промахе — один точечный запрос `client.getMessages(peer, { ids: [rootId] })`
   (новый метод `TelegramService.getMessageById(chatId, msgId)`), взять `.date`
   найденного сообщения (это и есть служебная копия поста — она физически лежит в
   чате обсуждения под этим id, дата её — дата пересылки/публикации). Результат
   сохраняется в кэш на 30 дней (требования, «Где хранится определённая дата»).

Это ровно случай A шага 4 алгоритма требований: корень уже известен из поля
сообщения, дата запрашивается один раз и кэшируется.

### 2.3 Служебная копия поста участвует в анализе (случай B алгоритма)

Требования (шаг 2, раздел 5) описывают второй случай: непрочитанное сообщение само
является служебной копией поста (несёт `channel_post` в `fwd_from`) — тогда корень
ветки — id этого же сообщения, а дата берётся из его собственного поля без запроса к
Telegram и без сохранения в кэш.

Текущий v1-код (`TelegramService.getMessages`) отбрасывает такие сообщения:
`if (m.sender instanceof Api.Channel) { ... skip ... }`. Это поведение возникло **до**
этой фичи и не для неё — v1 не в курсе гейта свежести и не должен становиться местом
для его решений. Оно остаётся неизменным для v1 (аддитивность), но **не переносится**
в `monitor-v2`: `monitor-v2` должен видеть копию поста как обычное сообщение,
пропускать её через гейт (R1 — она безальтернативно попадает в `generalMessages`, см.
§2.1) и, при прохождении гейта, давать LLM (`analyzeChannelMessages`) увидеть её как
кандидата — LLM решает, писать ли открывающий комментарий, тем же единственным
вызовом, что и для любого другого сообщения.

**Технически:**
- `TelegramService.getMessages` получает новый опциональный параметр
  `opts?: { includeChannelPosts?: boolean }` (по умолчанию `false` — сохраняет
  сегодняшнее поведение v1 бит-в-бит; `monitor.ts` вызывает функцию без этого
  параметра). При `includeChannelPosts: true` фильтр `sender instanceof Api.Channel`
  не применяется — такие сообщения остаются в результате.
- Новое опциональное поле `TgMessage.isChannelPost?: boolean` — `true`, если у
  сообщения присутствует `m.fwdFrom?.channelPost` (наличие поля, не его значение:
  `channelPost` несёт id исходного поста *в канале*, а не в чате обсуждения — для
  гейта важен сам факт «это копия», а не это число, поэтому хранится булев признак,
  а не число). Существующее маппирование `fromName`/`fromId` в `getMessages` уже
  корректно обрабатывает отправителя-канал (ветка `?? (m.sender as any)?.title`) —
  правка не нужна.
- Гейт (`evaluateFreshness`, §3.3), встретив `isChannelPost === true`: `postDate = msg.date`
  (собственное поле даты сообщения), запись в `thread_post_dates` НЕ создаётся —
  дословно по алгоритму («обращение к Telegram и локальное сохранение даты для этого
  случая не выполняются»). `rootId` отдельно нигде не используется — не нужен, так
  как дата уже есть на руках.
- `classifyMessages`/`ClassifyInputMessage` не меняются в логике — только получают
  аддитивные поля `replyToTopId?: number` и `isChannelPost?: boolean`, которые
  проезжают насквозь до бакета `generalMessages` (см. §2.1).
- DM-кандидаты: копия поста никогда не станет `dm_candidates` — существующая проверка
  `insertDmCandidate`-вызова (`if (!m || !m.userAccessHash) continue`) уже отсеивает
  её (у отправителя-канала нет `userAccessHash`), без правок.
- Отправка ответа на копию — обычный `tg.replyToMessage(chatId, copyMsgId, text)`,
  без изменений `TelegramService`: ответ на любое сообщение чата (включая копию поста)
  — стандартная операция Telegram.

**Явно вне охвата этой правки.** Отдельный параметр LLM-вызова «это сообщение —
пост» (чтобы `analyzeChannelMessages` мог отличать копию от обычного комментария в
самом промпте) обсуждался с координатором, но отложен и не зафиксирован в
`requirements-v1.md` — не проектируется здесь. `isChannelPost` уже вычислен на уровне
данных (см. выше) и может быть передан в промпт без дополнительных телеграм-полей,
когда это будет решено отдельно.

### 2.4 Хранилище дат публикации: новая таблица в `tg-replies.db`

| Вариант | Где | Обоснование |
|---|---|---|
| **A (выбран)** | новая таблица `thread_post_dates` в `tg-replies.db` (`core/db/replies.ts`) | тот же файл уже хранит `group_threads` — тоже данные «про ветку»; модуль уже открывается классификацией на каждый прогон |
| B | новая таблица в `tg-channels.db` (`core/db/channels.ts`) | тоже приемлемо (там уже соседствуют `channel_visits`/`send_errors`/`banned_channels`), но семантически дальше от «ветки» |
| C | отдельный файл БД | лишняя сущность — данные разовые (30 дней, одна колонка полезной нагрузки), не оправдывает свой файл |

Схема (используется только для случая A — обычный комментарий; случай B, §2.3, эту
таблицу не трогает):

```sql
CREATE TABLE IF NOT EXISTS thread_post_dates (
    chatId      TEXT    NOT NULL,
    topMsgId    INTEGER NOT NULL,
    postDate    INTEGER NOT NULL,  -- unix-секунды даты публикации поста
    firstSeenAt INTEGER NOT NULL,  -- unix-секунды сохранения записи (TTL-якорь)
    PRIMARY KEY (chatId, topMsgId)
);
```

Новые функции `core/db/replies.ts` (аддитивно, существующие функции не трогаются):
`getThreadPostDate(agentId, chatId, topMsgId): number | null`,
`saveThreadPostDate(agentId, chatId, topMsgId, postDate, log): void`,
`expireOldThreadPostDates(agentId, olderThanSeconds, log): { expired: number }` —
жёсткое `DELETE` (не мягкий статус, как у `group_threads.status='expired'`): запись
не несёт для отчётов/аудита никакой ценности после истечения TTL, это чистая
гигиена объёма (дословно так и сформулировано в требованиях).

### 2.5 Переключатель варианта на агента: существующий механизм `tasks`, без новой сущности

`core/db/tasks.ts`: `TaskType` расширяется значением `"monitor-v2"`. Таблица `tasks`
уже поддерживает произвольный набор включённых типов задач на агента (PK
`(agentId, type)`) — это ровно то, что нужно для «выбрать вариант монитора по
агенту»: оператор включает ОДНУ из строк `monitor` / `monitor-v2` через
`upsertTask`/`disableTask` (пульт `scheduler-control`), вторую не создаёт. Новой
таблицы, колонки или флага не требуется.

`dispatcher.ts`: `SKILLS` — `Record<TaskType, ...>` — типизированно требует
добавить `"monitor-v2": runMonitorV2`; забыть об этом при добавлении TaskType
невозможно, компилятор укажет на пробел.

**Общее состояние, которое НЕ различает вариант.** `channels.lastProcessedAt`
(единственная колонка «когда канал последний раз обходили», `core/db/channels.ts`)
не привязана к варианту монитора — её обновляет `markChannelProcessed` вызовом из
любого варианта. `getChannelsBatch` уже принимает `periodSeconds` параметром (v1
передаёт 72ч, v2 будет передавать 24ч) — но если для одного агента одновременно
включить ОБА `TaskType`, они будут писать в ОДНУ и ту же колонку `lastProcessedAt` с
РАЗНЫМИ ожидаемыми периодами: последний прогон (неважно какого варианта) сбрасывает
таймер для обоих. **Координатор явно решил не защищать от этого в коде** (раздел 6,
риск 2) — это на ответственности оператора, включающего расписание.

## 3. Компоненты и поток

### 3.1 Новые и изменяемые компоненты

| Классификация | `src/core/db/channels.ts` | `ClassifyInputMessage` += `replyToTopId?: number`, `isChannelPost?: boolean` (аддитивно, `classifyMessages` логику не меняет — поля просто проезжают насквозь, см. §2.1/2.3) |

### 3.2 Поток `monitor-v2` (по каналу, после получения непрочитанных)

Шаги 1–3 (загрузка аккаунта, синхронизация каналов, кэш идентичности) и шаг 4
(`getChannelsBatch` с `MONITOR_V2_CHECK_PERIOD_SECONDS`) — идентичны `monitor.ts`,
переиспользуются как есть (никакой новой логики). Различие начинается на уровне
одного канала:

1. `getMessages(chatId, readInboxMaxId, LIMIT, { includeChannelPosts: true })` —
   единственное отличие от вызова в v1: копии постов НЕ отфильтровываются; каждое
   сообщение несёт `replyToTopId` и/или `isChannelPost`.
2. `markAsRead` — без изменений по существу, по максимальному id ВСЕХ полученных
   сообщений (R4 выполняется независимо от исхода гейта, как и сейчас). Побочный
   эффект включения копий в выдачу: если единственным непрочитанным в чате была
   свежая копия поста без единого комментария, `monitor-v2` теперь корректно
   пометит её прочитанной (в v1 этот случай молча пропускает `markAsRead` из-за
   пустого результата после фильтра — известная деталь v1, не в объёме этой фичи).
3. `classifyMessages(agentId, chatId, messages, log)` — без изменений; копия поста
   попадает в `generalMessages` (см. §2.1), обычные комментарии — во все три бакета
   как раньше.
4. **Новый шаг** — гейт свежести применяется к каждому сообщению трёх бакетов
   (`generalMessages`, включая возможную копию поста, как `isContinuation=false`;
   сообщения внутри `newThreadMessages[].messages` и `threadReplies[].newMessages`
   как `isContinuation=true`): не прошедшие исключаются из бакета/записи (R3); если
   запись (`NewThreadEntry`/`ThreadReplyEntry`) лишается всех сообщений — исключается
   целиком.
5. Дальше — тот же конвейер `monitor.ts`: `generateThreadReply` /
   `generateThreadContinuation` / `analyzeChannelMessages` + отправка + запись —
   работает только с прошедшими гейт сообщениями (в том числе, возможно, с копией
   поста как одним из кандидатов `generalMessages`). Отдельно считаются метрики
   гейта: число исключённых по R3 с разбивкой по причине
   (`no_thread` / `date_unresolved` / `stale`), для отчёта скилла.

Диаграмма решения гейта на одном сообщении — см. `gate-flow.puml` в этой же папке.

### 3.3 Гейт свежести (`core/freshness-gate.ts`)

```ts
export interface FreshnessGateDeps {
  getCachedPostDate(chatId: string, topMsgId: number): number | null;
  fetchAndCachePostDate(chatId: string, topMsgId: number): Promise<number | null>; // сеть + запись в кэш; null при неудаче
}

export type GateOutcome =
  | { pass: true; rule: "R1" | "R2" }
  | { pass: false; rule: "R3"; reason: "no_thread" | "date_unresolved" | "stale" };

export interface FreshnessGateMessage {
  chatId: string;
  date: number;                 // собственная дата сообщения (для случая B)
  replyToTopId?: number;        // случай A
  isChannelPost?: boolean;      // случай B
}

export async function evaluateFreshness(
  deps: FreshnessGateDeps,
  msg: FreshnessGateMessage,
  isContinuation: boolean,
  nowSec: number,
): Promise<GateOutcome>;
```

Реализация (без Telegram/БД внутри — вызывающий, `monitor-v2.ts`, подставляет
конкретные `getThreadPostDate`+`saveThreadPostDate`/`getMessageById`):

1. Определить `postDate`:
   - `msg.isChannelPost === true` → `postDate = msg.date`; кэш не читается и не
     пишется (случай B, дословно по алгоритму).
   - иначе, `msg.replyToTopId !== undefined` → кэш `(chatId, replyToTopId)`; при
     промахе — `fetchAndCachePostDate` (один сетевой запрос + запись в кэш); при
     неудаче (сеть, `FLOOD_WAIT` после исчерпания `withFloodRetry`, сообщение не
     найдено/удалено) → `{ pass: false, rule: "R3", reason: "date_unresolved" }` —
     «общая стратегия обработки ошибок» из требований (раздел 5): не валит канал/
     прогон, исключается только это сообщение, как и любое другое, не прошедшее
     R1/R2.
   - ни того, ни другого → `{ pass: false, rule: "R3", reason: "no_thread" }`.
2. Порог и знак сравнения берутся по `isContinuation` — R1 требует строгого «менее
   24 часов» (`<`), R2 — нестрогого «не более 4 дней» (`≤`), в точности по формулировкам
   раздела 4 требований:
   - `isContinuation=false` (R1): `nowSec - postDate < POST_FRESHNESS_FIRST_COMMENT_MAX_AGE_SECONDS` → `pass: true`; иначе `{ pass: false, rule: "R3", reason: "stale" }`.
   - `isContinuation=true` (R2): `nowSec - postDate <= POST_FRESHNESS_CONTINUATION_MAX_AGE_SECONDS` → `pass: true`; иначе `{ pass: false, rule: "R3", reason: "stale" }`.

R1 и R2 симметричны по форме (оба — скользящее окно от даты поста, различаются
только порогом и строгостью сравнения) — часовой пояс гейту не нужен ни для одного
из правил, `startOfUtcPlus5Day`/любая иная привязка ко «дню» в этом модуле не
используется.

Почему `FLOOD_WAIT` на `getMessageById` (случай A) не прерывает весь прогон (в
отличие от `get_dialogs_for_batch`/`get_messages`, где `FloodAbortError` останавливает
`monitor-v2` целиком): это точечный запрос за ОДНОЙ веткой, кэшируемый на 30 дней —
блэст-радиус отказа ограничен одним сообщением, а не всем каналом. Тот же принцип,
что уже применяется к «нашли ошибку — пропустить это, не ронять прогон» в
`get_messages`/`sendReply` `monitor.ts`. Случай B вообще не обращается к Telegram —
для него этот риск не существует.

**Один запрос на ветку — включая сообщения одного батча.** Требования (раздел 5, шаг
4) фиксируют: запрос к Telegram за датой ветки выполняется один раз, «в момент
первой встречи с веткой». В одном непрочитанном батче могут прийти НЕСКОЛЬКО
сообщений одной и той же новой (ещё не закэшированной) ветки — например, три
подряд идущих новых комментария под одним постом. Чтобы не выполнить по запросу на
каждое из них, `monitor-v2` обязан применять гейт к сообщениям одного канала
**последовательно** (`for...of` + `await`, как уже устроены циклы `monitor.ts` —
`Promise.all` по сообщениям здесь не годится): после первого запроса запись уже
в `thread_post_dates`, и следующее сообщение той же ветки в том же прогоне находит
кэш, а не бьёт по сети повторно.

## 4. Покрытие требований

| Правило / AC | Как покрывается |
|---|---|
| **R1** первый комментарий — с момента публикации поста прошло <24ч (адресован посту или другому пользователю под ним) | гейт, `isContinuation=false`; для копии поста — `msg.isChannelPost`, собственная дата; для комментария — случай A (`replyToTopId` + кэш/запрос) |
| **R2** продолжение ≤4 дней от даты поста | гейт, `isContinuation=true`, `nowSec - postDate ≤ 4×86400` |
| **R3** непрошедшие не анализируются вовсе — ни как кандидат на ответ, ни как кандидат на DM | гейт применяется строго до `analyzeChannelMessages`/`generateThreadReply`/`generateThreadContinuation`/`generateReply` — исключённые сообщения не достигают ни одного LLM-вызова; скоринг DM-кандидатов (`dmКандидаты`) — часть того же вызова `analyzeChannelMessages`, поэтому исключённое сообщение автоматически не участвует и в нём |
| **R4** пометка прочитанным не меняется | `markAsRead` вызывается по всем полученным сообщениям (включая копии постов) до гейта, как в v1 — гейт этот шаг не видит |
| **R5** периодичность обхода 24ч | `MONITOR_V2_CHECK_PERIOD_SECONDS = 86400`, передаётся в `getChannelsBatch` только вызовом `monitor-v2` |
| **AC-1** охват (бизнес-цель) | требования сами фиксируют: измеримый прокси не определён, отдельного технического решения не требует |
| **AC-2** диалог ограничен по возрасту поста | обеспечивается R2 гейта, проверяемо по факту (счётчик `stale`-исключений в отчёте скилла) |
| **AC-3** нет LLM-вызова на исключённых | гейт — до LLM-вызовов (см. R3); включение копий поста в конвейер не создаёт нового пути к LLM в обход гейта — они проходят тот же гейт, что и остальные |
| **AC-4** пометка прочитанным без регресса | см. R4 |
| **AC-5** обход не реже раза в 24ч | `getDueTasks`/`nextRun` планировщика с `schedule` пульта, выставленным на ≤24ч для `monitor-v2` — ответственность оператора при настройке расписания (как и сейчас для любого `TaskType`), не код. **Уточнение:** `getChannelsBatch` отдаёт не более `DEFAULT_BATCH_LIMIT` (40) каналов за вызов — тот же лимит, что уже ограничивает v1 относительно её 72-часовой цели. Если у агента каналов больше, чем покрывает один батч за период между запусками `monitor-v2`, часть каналов не уложится в 24ч — это существующий параметр (`limit` `getChannelsBatch`), а не новая проблема v2; оператор задаёт `schedule`/`limit` так, чтобы суммарно покрыть все каналы агента за 24ч, как сейчас делает это для 72ч у v1 |

## 6. Риски и открытые вопросы

Нумерация ниже — идентификаторы строк этой таблицы, не ссылки на правила R1–R5
требований (совпадение цифр со случаем ниже, если есть, — совпадение, не отсылка).

| # | Риск / вопрос | Влияние | Что делаем |
|---|---|---|---|
| 1 | `getMessageById` на новую ветку (случай A) — точечный сетевой запрос на каждую впервые встреченную ветку в рамках 30-дневного окна | много новых веток в первые дни после включения `monitor-v2` → всплеск точечных запросов | ожидаемо и дёшево (кэш 30 дней), не требует спец-обработки; при системном `FLOOD_WAIT` — см. §3.3 (не валит прогон) |
| 2 | `channels.lastProcessedAt` — общее состояние, не различает вариант монитора (раздел 2.5) | одновременное включение `monitor` и `monitor-v2` на одного агента искажает каденс обхода обоим | **решено координатором: программную защиту не добавлять**, ответственность оператора (не включать оба варианта одновременно на одном агенте) |
| 3 | Метрика воронки `activityRate` использует глобальный `CHANNEL_CHECK_PERIOD_SECONDS` (72ч) как знаменатель; агенты на `monitor-v2` физически посещаются раз в 24ч | `activityRate` для агентов на `monitor-v2` будет систематически занижен | уже согласовано заказчиком как не блокер (требования, раздел 1); коррекция под per-agent период не делается |
| 4 | `reply_to_top_id` присутствует у всех сообщений ветки на любой глубине вложенности (в т.ч. у самых первых ответов на корень) — вывод из официальной документации (раздел 7, «Источники»), не из эмпирической проверки на реальном трафике | если для части сообщений (например, самых первых ответов на копию поста) это поле окажется не заполнено, такое сообщение ошибочно попадёт под `no_thread` (R3) вместо корректной оценки R1 — отказ консервативный (недосчитанный кандидат, не утечка непрошедшего сообщения в LLM), но снижает охват (AC-1) | принять как рабочее допущение; при внедрении — логировать долю сообщений без `replyToTopId`/`isChannelPost` в метриках гейта (`no_thread` уже считается отдельно, см. §3.2) для эмпирической проверки допущения на реальном трафике |
| Q1 | Отдельный параметр LLM-вызова «это сообщение — пост» (для промпта `analyzeChannelMessages`) | без него LLM видит копию поста как обычное сообщение канала-отправителя — решение (писать/не писать открывающий комментарий) принимает по тому же содержимому, без явной подсказки о роли сообщения | отложено координатором, не входит в эту правку (см. §2.3, «Явно вне охвата»). `isChannelPost` уже вычислен на уровне данных — техническое дополнение промпта, когда будет решено отдельно, не потребует новых полей |
