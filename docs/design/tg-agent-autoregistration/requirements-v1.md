# tg-agent-autoregistration: требования

> **О чём документ.** Что система должна делать и по каким правилам — при
> массовой автоматической регистрации Telegram-агентов из готовых tdata-сессий.
>
> **Парный документ:** [tg-agent-autoregistration-sequence.puml](./tg-agent-autoregistration-sequence.puml)
> — сценарий по шагам, кто что вызывает.
> **Граница:** здесь — требования и правила; порядок вызовов и участники —
> в диаграмме. Дубли не допускаются: каждое правило задаётся здесь один раз,
> диаграмма на него опирается.

---

## 1. Контекст и цель

### 1.1. Проблема

Онбординг агента сейчас — штучная операция (`skills/tg-agent-create`,
`tg-agent-create-v2`). При масштабировании до десятков аккаунтов, купленных/
подготовленных заранее в виде tdata-сессий, штучный процесс не подходит.

### 1.2. Цель

По одному вызову скилла превратить пачку tdata-архивов в пачку полностью
рабочих агентов платформы: со своим мобильным прокси, сменённым 2FA,
уникальным профилем и каналом одной выбранной персоны, вторичной (агентской)
MTProto-сессией — с прозрачным статусом по каждому аккаунту там, где
потребовалось ручное вмешательство.

## 2. Требования

### 2.1. Функциональные

- Оператор запускает через OpenClaw с параметрами: `megaLinks`,
  `startAgentNumber`, `proxyRegion`, `maxProxyAttempts`, `personName`.
- Персона выбирается **один раз на весь прогон** — все аккаунты пачки получают
  контент (профиль, канал, apiId/apiHash) одной персоны.
- На аккаунт: скачать tdata → подобрать рабочий мобильный прокси → сменить
  2FA, сбросить прочие сессии, применить профиль (имя/username/фото/дату
  рождения/био), создать публичный канал с постом и закрепить его в профиле →
  зарегистрировать вторую (агентскую) MTProto-сессию → записать финальные
  артефакты агента.
- По каждому аккаунту — ровно один статус: `done` / `proxy_failed` /
  `setup_failed` / `needs_manual_code`.
- По завершении пачки — итоговый отчёт оператору.

### 2.2. Ограничения (constraints)

1. Аккаунты обрабатываются **последовательно**, не параллельно.
2. `apiId`/`apiHash` — общие в рамках персоны, не индивидуальные на аккаунт.
3. Диапазон создаваемых `agentId` не должен пересекаться с уже существующими
   агентами и с незавершённым стейджингом прошлого прогона.
4. Недорегистрированный аккаунт не должен быть виден `listAgentIds()` — иначе
   его подхватят платформенные cron-скрипты (`discovery`, `distribute-channels`,
   `distribute-pool`, `channel-coverage-update`, `backfill-schedule-defaults`,
   `join-queue-backfill`), у которых нет готового `tg-account.json` для него.
5. Смена 2FA-пароля необратима на самой tdata-сессии — повторный прогон после
   частичного сбоя не гарантированно идемпотентен на этом шаге.
6. Восстановление `needs_manual_code` — полностью ручное (оператор скачивает
   tdata с ВПС), процесс не предоставляет для этого отдельного автоматизма.

## 3. Правила выполнения

| # | Правило |
|---|---------|
| **R-1** | Ошибка подбора прокси (`proxy_failed`) и ошибка подготовки аккаунта после успешного коннекта (`setup_failed`) — разные статусы. Смена прокси не помогает при `setup_failed` (причина не в сети), поэтому при ней подбор прокси прекращается сразу, без исчерпания `maxProxyAttempts`. |
| **R-2** | `currentPassword` для `updateTwoFaSettings` берётся из `tdata/Password2FA.txt` (едет с архивом), `newPassword` — из `default_agent_data.json` персоны (поле `2fa`). |
| **R-3** | `phoneNumber` для аккаунта — из `tdata/Accounts.txt`, не запрашивается отдельно и не хранится в манифесте — манифеста в архиве нет, есть только `tdata/`. |
| **R-4** | `username` = `nick` (префикс из `profile_data.json`) + случайный **человекочитаемый** постфикс (не хеш-подобный) — обеспечивает уникальность при общем `nick` на персону. |
| **R-5** | Фото профиля — **все** файлы `photo_profile_N`, найденные в шаблоне персоны, загружаются по очереди (`uploadProfilePhoto`), а не только первое. |
| **R-6** | Название канала — `channelName` из `profile_data.json`. Совпадение названия у всех каналов персоны допустимо (Telegram не требует уникальности отображаемого имени, только username/публичной ссылки). |
| **R-7** | До статуса `done` данные аккаунта живут в стейджинге `~/.openclaw/tg-agent-autoregistration/staging/agent<N>/`, а не в `~/.openclaw/workspace-agent<N>/` — это ограничивает видимость для `listAgentIds()` (см. constraint 4). В `workspace-agent<N>` аккаунт переносится атомарно только на `done`. |
| **R-8** | Перед скачиванием чего-либо проверяется диапазон `startAgentNumber..+N` на пересечение с `listAgentIds()` и со стейджингом прошлого прогона; при пересечении прогон не стартует. |
| **R-9** | Все терминальные статусы, кроме `done` (`proxy_failed`, `setup_failed`, `needs_manual_code`), оставляют запись в стейджинге **до ручного разбора оператором** — автоматической очистки или повторного взятия того же `agentId` нет; следующий прогон с пересекающимся диапазоном упрётся в R-8, пока запись не разберут вручную. Для `needs_manual_code` доступен точечный ретрай второй сессии (`tg_agent_autoregistration_retry_code`, R-9a) — без него дальнейший шаг тот же: оператор вручную скачивает `tdata` с ВПС и завершает вход. |
| **R-9a** | Ретрай `needs_manual_code` (`tg_agent_autoregistration_retry_code`) повторяет только `authSendCode`/`readIncomingCode`/`authSignIn` — подготовка аккаунта (2FA/сессии/профиль/канал, R-13) не повторяется: она уже применена к реальному Telegram-аккаунту, а повторный `updateTwoFaSettings` с прежним `currentPassword` упадёт (пароль уже сменён). Требует, чтобы запись в стейджинге всё ещё была `needs_manual_code` — на любой другой статус отказывает. |
| **R-10** | Перед всем остальным (до проверки диапазона ID и до скачивания) читаются шаблоны персоны `personName`. Если папки `templates/<personName>/` нет или не хватает обязательного файла из R-D1 — скилл сообщает оператору об ошибке и останавливается, ничего не скачивая. |
| **R-11** | `N` (число создаваемых агентов за прогон) = число ссылок в `megaLinks`. Соответствие один-к-одному-к-одному: одна ссылка = один архив = один аккаунт. |
| **R-12** | На каждую попытку внутри подбора прокси (до `maxProxyAttempts` раз на аккаунт) запрашивается **новый** кандидат у asocks — кандидаты не переиспользуются между попытками. |
| **R-13** | Перед применением нового профиля и канала персоны аккаунт **безусловно** очищается от прежнего состояния: все существующие фото профиля удаляются, все публичные каналы, которыми аккаунт уже админит, удаляются — независимо от того, упирается ли аккаунт в лимит публичных каналов. Необратимая операция; явное решение координатора выполнять её автоматически в каждом прогоне без подтверждения на аккаунт — отступление от общего принципа проекта («Обратимость», `docs/agent-playbook.md`), сознательно принятое для этого процесса. Отказ удалить канал (например, `CHANNEL_TOO_LARGE` — нельзя удалить канал больше 1000 участников) — обычная ошибка Telegram API при подготовке, ведёт к `setup_failed` (R-1). |

## 4. Идентификаторы и данные

| # | Правило |
|---|---------|
| **R-D1** | Шаблоны персоны: `~/.openclaw/tg-agent-autoregistration/templates/<personName>/` — `post.txt`, `photo_profile_1.*..N.*`, `channel_photo.*`, `channel_post_photo.*` (расширение файла — любое, сохраняется и едет в Telegram вместе с именем файла), `default_agent_data.json` `{apiId, apiHash, 2fa}`, `profile_data.json` `{name, nick, birthdate, bio, channelName}`, `SOUL.md`. Модель устройства персоной не задаётся — подбирается автоматически (см. R-D3, `src/core/device-pool.ts`), не пересекаясь с уже используемыми другими агентами. |
| **R-D2** | Вход на аккаунт — только `<номер аккаунта>/tdata/` из архива Mega: стандартные файлы Telegram Desktop + `Accounts.txt` (телефон) + `Password2FA.txt` (текущий пароль 2FA). Никакого стороннего манифеста в архиве нет. |
| **R-D3** | Стейджинг в процессе: `~/.openclaw/tg-agent-autoregistration/staging/agent<N>/` — `tdata/`, `status.json` `{status, error?, updatedAt}`, `device.json` (устройство, подобранное для агента — персистится при первом назначении, чтобы ретрай `needs_manual_code` не подбирал новое; в `done` не переезжает, см. R-D4). |
| **R-D4** | Итог (`done`): `~/.openclaw/workspace-agent<N>/` — `tg-account.json` `{apiId, apiHash, sessionString, proxy, device}` (все поля текущей схемы), `SOUL.md` (из шаблона персоны), `tdata/` (перенесена из стейджинга). |
| **R-D5** | Таймаут `readIncomingCode` — фиксированная константа **2 минуты**, не параметр запуска. |

## 5. Вне рамок (Future work)

- Идемпотентный ретрай `setup_failed`, когда 2FA уже сменён частично выполненным прогоном.
- Параллельная обработка нескольких аккаунтов одновременно.
- Отдельная верификация read-back по каждому MTProto-вызову — не нужна, ошибки Telegram API (RPCError с кодом) уже дают достаточный статус.
