## 5. Алгоритм (опционально)
Согласованный порядок действий, которым требования (раздел 7) соблюдаются на

## 6. User Stories
Формат «Как `<роль>`, я хочу…, чтобы…», метка `US-N (R-номер)` — привязка к
конкретному требованию из раздела 7.

Шаблон:
```
US-N. Как <роль>, я хочу <цель/функцию>, чтобы <ценность/причина>.
```

Проверка по INVEST:
- **Independent** — не зависит от других историй.
- **Negotiable** — описывает потребность, не жёсткий механизм реализации.
- **Valuable** — обязательно называет ценность («чтобы…»).
- **Estimable** — по формулировке понятен объём работы.
- **Small** — одна история = одна ценность; два разных «чтобы» — разделить на две истории.
- **Testable** — к истории можно сформулировать критерий приёмки.

Роль — конкретный актор, не абстрактный «пользователь».

## 7. Требования
Пронумерованные бизнес-правила (`R1`, `R2`, …). Только то, чего хочет бизнес —
без технического решения (как именно проверяется/реализуется — раздел
`architecture.md`, не этот документ).

Шаблон формулировки (по типу условия):

| Тип | Формула |
|---|---|
| Всегда действует | Система должна `<реакция>` |
| По событию | Когда `<триггер>`, система должна `<реакция>` |
| По состоянию | Пока `<состояние>`, система должна `<реакция>` |
| Обработка ошибки | Если `<нежелательное условие>`, то система должна `<реакция>` |
| Опциональная функция | Если включена `<функция>`, система должна `<реакция>` |

Проверка требования — 6 критериев:

| Критерий | Суть | Как проверяется |
|---|---|---|
| Полнота | Все ли аспекты описаны, нет ли пропусков | Чек-лист сценариев, включая ошибки; искать «белые пятна» |
| Однозначность | Требование трактуется всеми одинаково | Расплывчатые термины («быстро», «удобно») заменять на конкретные значения |
| Непротиворечивость | Требование не конфликтует с другими частями документа | Сверять с остальными требованиями на противоречащие условия/значения |
| Необходимость | В требовании только нужная информация | Убирать детали, не влияющие на поведение системы |
| Осуществимость | Требование реализуемо в имеющихся условиях | Проверять на технически/физически невозможные условия |
| Тестируемость | По требованию можно проверить, выполнено оно или нет | Должен существовать хотя бы один проверяющий сценарий |

## 8. Критерии приёмки
`AC-N`, сформулированные на уровне результата (раздел 2), а не выбранного
механизма. Если критерий неотделим от ещё не выбранного варианта решения —
явно пометить его статус.
