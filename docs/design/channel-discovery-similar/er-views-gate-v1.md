# ТЗ: Гейт кандидатов по ER и avg views — discovery-similar

**Статус: реализовано.** Гейт в коде (`src/core/discovery/similar.ts`). Один
нюанс по сравнению с этим ТЗ: `getRecentPosts(channel, 20)` для гейта
вовлечённости и выборка постов для тематического LLM-гейта объединены в один
вызов на канал, через общий параметр `postsCount` (дефолт 20) — см. п.1 раздела
«Что проверить при реализации» ниже, решение принято разработчиком по месту.

## 1. Контекст и проблема

В пайплайне `collectByLevels` (`src/core/discovery/similar.ts`) кандидат проходит
цепочку гейтов:

```
подписчики → группа обсуждения → тема (LLM)
```

Тематический LLM-гейт дорогой (вызов модели на каждого кандидата) и не отсекает
каналы, которые тематически подходят, но фактически «мёртвые» или мелкие по
вовлечённости (низкий ER, низкие просмотры на пост). Нужно отсекать такие каналы
**до** LLM-вызова, чтобы не тратить его на заведомо неинтересные находки.

## 2. Решение

Новый порядок гейтов:

```
подписчики → группа обсуждения → ER/avg views (НОВЫЙ) → тема (LLM)
```

### User Story

> Как оператор платформы, запускающий поиск похожих каналов, я хочу отсекать
> кандидатов с низкой вовлечённостью (мало просмотров относительно числа
> подписчиков, либо абсолютно мало просмотров) до тематической LLM-проверки, чтобы
> не тратить LLM-вызовы на каналы, которые тематически подходят, но фактически
> мёртвые или искусственно раздутые по подписчикам.

### Расчёт метрик кандидата

1. Берутся последние 20 постов кандидата (`getRecentPosts(channel, 20)`,
   существующий метод `service.ts:1188`, отдаёт от новых к старым, с `views`).
2. Два самых свежих поста отбрасываются (просмотры «не дозрели»).
3. По оставшимся постам (до 18, не требуется ровно 18) считается **average** (не
   median) просмотров — `avgViews`.
4. `ER = avgViews / subscribers`.
5. Закреплённые посты **не фильтруются** — выборка строится строго по позиции в
   истории (последние N минус 2 самых свежих), без проверки pinned-флага.
6. Если после отбрасывания 2 свежих постов выборка пуста (канал с 1-2 постами) —
   **fail-closed**, гейт не пройден.

### Пороги

| Параметр | Обязательность | Дефолт | Описание |
|---|---|---|---|
| `minAvgViews` | обязателен | нет дефолта | абсолютный порог просмотров; задаётся оператором каждый прогон (зависит от ниши/языка) |
| `minEngagementRate` | опционален | 0.1 | порог ER |

**Правило отсева (строгое сравнение, симметрично `minTopicScore`):** кандидат
отсеивается, если `avgViews <= minAvgViews` **или** `ER <= minEngagementRate`.
Проходит гейт только если оба значения строго больше порогов.

### Окно постов — единое правило для seeds и кандидатов

Существующая seed-приоритизация (`gatherAndScoreSeeds`) использует
`engagementWindowDays` — date-based окно через `getRecentPostViews(channel,
sinceUnixTs)`. Это окно **заменяется** на то же count-based правило, что в новом
гейте кандидатов: последние N постов, минус 2 самых свежих, без фильтра по дате.

Меняется **только определение окна** (date-based → count-based). Агрегация для
seeds остаётся **median** (устойчивость к выбросам нужна для приоритизации seeds,
в отличие от кандидатов, где оператор осознанно выбрал average).

### Счётчик отсева

Один агрегированный счётчик `lowEngagement` в `SkipCounts` (рядом с существующими
`lowSubscribers`, `noLinkedChat`, `offTopic`) — засчитывает кандидата при отсеве по
любой из причин (ER, avg views, или обе), без разбивки на под-причины. Отображается
в `renderSimilarReport` аналогично существующим счётчикам.

### Логирование

- Принятые кандидаты: ER и avg views добавляются в существующую строку лога
  (`similar.ts:352`).
- Отклонённые: НЕ логируются построчно — только через агрегированный счётчик
  `lowEngagement`.

## 3. Acceptance Criteria (Gherkin)

```gherkin
Feature: Гейт кандидатов по ER и avg views

  Scenario: Кандидат проходит гейт
    Given кандидат имеет avgViews > minAvgViews
    And кандидат имеет ER > minEngagementRate
    When гейт применяется к кандидату
    Then кандидат передаётся в тематический LLM-гейт

  Scenario: Кандидат отсеивается по avg views
    Given кандидат имеет avgViews <= minAvgViews
    When гейт применяется к кандидату
    Then кандидат не передаётся в LLM-гейт
    And счётчик skips.lowEngagement увеличивается на 1
    And построчный лог отказа не создаётся

  Scenario: Кандидат отсеивается по ER
    Given кандидат имеет ER <= minEngagementRate
    When гейт применяется к кандидату
    Then кандидат не передаётся в LLM-гейт
    And счётчик skips.lowEngagement увеличивается на 1

  Scenario: Кандидат отсеивается по обоим условиям
    Given кандидат имеет avgViews <= minAvgViews и ER <= minEngagementRate
    When гейт применяется к кандидату
    Then счётчик skips.lowEngagement увеличивается ровно на 1 (не на 2)

  Scenario: Недостаточно постов для расчёта (fail-closed)
    Given у кандидата 2 или менее постов в истории
    When гейт применяется к кандидату
    Then кандидат не проходит гейт (fail-closed)
    And счётчик skips.lowEngagement увеличивается на 1

  Scenario: minAvgViews не указан
    Given оператор запускает discovery-similar без флага --min-avg-views
    When скрипт валидирует аргументы
    Then скрипт завершается с ошибкой валидации до начала сбора кандидатов

  Scenario: Закреплённый пост в выборке
    Given среди последних 20 постов кандидата есть закреплённый пост за пределами 2 самых свежих
    When считается avgViews
    Then закреплённый пост участвует в расчёте average без исключения

  Scenario: Приоритизация seeds — окно по количеству постов
    Given seed-канал имеет историю постов
    When считается median вовлечённости seed-канала
    Then окно выборки постов строится по количеству (последние N минус 2 свежих), не по дате
    And агрегация остаётся median (не average)
```

## 4. Раздел для разработчика

**Файлы:**
- `src/core/discovery/similar.ts` — основная логика (`collectByLevels`,
  `gatherAndScoreSeeds`, `SimilarParams`, `SkipCounts`)
- `src/scripts/discovery-similar.ts` — CLI-параметры (`--min-er`,
  `--min-avg-views`), валидация по аналогии с `--theme`/`--agents` (строки 56-71)
- `skills/discovery-similar/SKILL.md` — описание шагов (требует обновления
  финальными решениями)

**Что проверить при реализации:**
1. `getRecentPosts(channel, 20)` вызывается отдельно от `getRecentPostTexts(n)`
   тематического гейта — объединение вызовов вне скоупа этого ТЗ, решает
   разработчик по месту. **Сделано:** объединены в один вызов через общий
   параметр `postsCount`, `getRecentPostTexts` удалён как избыточный.
2. CLI требует `--min-avg-views` обязательным (нет дефолта); `--min-er`
   опционален, дефолт 0.1.
3. `engagementWindowDays` в `SimilarParams` (`similar.ts:94`) меняет семантику на
   count-based — имя параметра можно оставить или переименовать (например,
   `engagementWindowPosts`) — на усмотрение разработчика, бизнес-требование —
   единое правило окна для seeds и кандидатов.
4. `SkipCounts` (`similar.ts:106-109`) получает новое поле `lowEngagement: number`.
5. `renderSimilarReport` и лог сводки (`similar.ts:432`) получают строку с
   `lowEngagement`.
6. Строка лога принятого кандидата (`similar.ts:352`) дополняется ER и avgViews.

**Не делать (явный отказ оператора от усложнения):**
- Не вводить раздельные счётчики по причине отсева (ER vs avg views).
- Не фильтровать закреплённые посты.
- Не переключать seeds-приоритизацию с median на average.
