# Design Doc: Поиск похожих каналов — v2 (параллельный)

> Аналитика фичи для человека. Объясняет, что делает система и как, и почему так
> решили. Нормативное поведение (требования + сценарии) — в `openspec/`, не здесь.
> Версии: `channel-discovery-similar-v1.md`, `-v2.md` — актуальна последняя,
> предыдущая остаётся как история.

## 1. Проблема / Контекст

В v1 искатели обрабатываются кооперативно: на каждом уровне обхода все они идут по
очереди, каждый открывает и закрывает свою Telegram-сессию раз в уровень. При трёх
искателях по 30 минут каждый суммарное время прогона — ~90 минут.

Кроме того, кооперативный обход сложен в сопровождении: нужно явно отслеживать
очерёдность искателей на каждом уровне, управлять несколькими сессиями в рамках
одного прохода. При падении одного искателя внутри уровня логика становится
нетривиальной.

Нужно сократить время прогона и упростить реализацию.

## 2. Цели

- Запускать всех искателей **одновременно**: время прогона = время самого медленного
  искателя, а не сумма.
- Каждый искатель работает **независимо**: своя Telegram-сессия, свой обход графа
  похожих, своя сортировка seed-каналов по вовлечённости — падение одного не влияет
  на других.
- Сохранить **непересечение каналов** между агентами: один канал — один агент,
  дедупликация через реестр.
- Сохранить **отдельную фазу распределения**: назначение агентов round-robin
  запускается строго после завершения всех искателей.
- Добавить **per-searcher статистику** в отчёт оператору: сколько нашёл каждый
  искатель, сколько отсеял по каждому гейту.

## 3. Как работает

Оператор запускает скрипт с теми же параметрами, что и раньше. Интерфейс запуска
не меняется.

Система запускает **все искатели одновременно**. Каждый искатель на своей сессии:

1. Берёт каналы, которые уже есть у него в базе данных, — без обращений к Telegram.
2. Запрашивает последние посты каждого seed-канала, считает вовлечённость (медиана
   просмотров / подписчики) и сортирует seed-каналы от самого «живого» к наименее
   активному.
3. Обходит граф похожих в ширину: от seed-каналов → к их рекомендациям →
   к рекомендациям найденных кандидатов и т.д.
4. Каждый кандидат проходит цепочку гейтов — те же, что в v1:
   - **Подписчики** ≥ минимальному порогу
   - **Группа обсуждения** присутствует
   - **Вовлечённость** (ER и средний просмотр на пост) выше порогов (fail-closed)
   - **Тематическая релевантность** (LLM-оценка) выше порога (fail-closed)
5. Прошедший все гейты кандидат записывается в реестр **без назначения агента**.
   Если запись прошла — общий счётчик найденных увеличивается.
6. Когда суммарное число найденных каналов достигает цели (`target × N`, где N —
   число агентов платформы) — каждый искатель при очередной проверке останавливается.

После того как все искатели завершились, запускается **фаза распределения**: каналы
без назначенного агента раскладываются round-robin по агентам платформы
(до `target` каждому) и ставятся в очереди вступления.

Оператор получает отчёт: суммарно найдено, найдено каждым искателем, отсеяно по
каждому гейту (per-searcher), у кого поиск прерван ограничениями Telegram или упал
с ошибкой, распределение новых каналов по агентам.

**Допустимый overshoot.** Из-за параллельной природы несколько искателей могут
одновременно найти новые каналы в момент достижения цели — итоговое число найденных
незначительно превышает `goal`. Это штатное поведение.

## 4. Архитектура

**Параллельный запуск.** Все искатели стартуют одновременно как независимые задачи.
Каждый держит собственную Telegram-сессию открытой на весь прогон — открывается
один раз при старте, закрывается после завершения обхода.

**Общее состояние — только реестр.** Искатели не разделяют ни сессии, ни очередь
обхода. Единственная точка синхронизации — реестр каналов (`discovery.db`): запись
атомарна, один канал попадает ровно тому искателю, который первым его зарегистрировал.
В памяти дополнительно хранится разделяемый счётчик найденных каналов — он служит
условием остановки.

**Регистрация без агента.** В v1 канал сразу закреплялся за агентом в момент находки.
В v2 искатели только фиксируют кандидатов в реестре без агента; кому достанется
канал — решает отдельная фаза распределения после завершения всех искателей.

**Темп и защита аккаунтов** — без изменений: пауза 0.8–1.2 с между обращениями к
Telegram, одиночный FLOOD_WAIT ждётся и повторяется, два подряд останавливают обход
этого искателя (остальные продолжают).

## 5. Модель данных

В реестре `discovered_channels` поле `assigned_agent` сейчас обязательно — канал при
регистрации сразу получает агента. В v2 искатели регистрируют каналы без агента:
поле становится необязательным. Каналы с незаполненным агентом образуют «пул»
текущего незавершённого прогона; фаза распределения заполняет их до конца прогона.

Дедупликация по уникальной ссылке канала работает без изменений.

## 6. Альтернативы

### Общий кеш посещённых каналов между искателями

Синхронизировать список уже запрошенных каналов, чтобы не делать одинаковые запросы
к Telegram дважды. При типичном числе искателей (2–4) с разными seed-наборами
выигрыш незначительный, а усложнение — реальное. Отклонено в пользу простоты.

### Назначение агента прямо во время обхода

Назначать агента найденному каналу немедленно, не откладывая в отдельную фазу; это
избежало бы изменения схемы реестра. При параллельном обходе синхронизация
счётчика назначения между независимыми искателями усложнила бы логику. Отдельная
фаза распределения сохраняет детерминизм назначения и разделяет ответственности.

## 7. Метрики успеха

- **Скорость прогона:** время с N искателями ≈ время с 1 искателем (не N×T₁) —
  подтверждается по меткам времени начала и конца прогона в логах.
- **Корректность дедупликации:** ни один канал не назначен двум агентам за один
  прогон — инвариант уникальности ссылки в реестре.
- **Статистика per-searcher:** отчёт содержит найдено и отсеяно по каждому гейту
  отдельно на каждого искателя — оператор видит вклад каждого.
- **Устойчивость к падениям:** ограничения Telegram или ошибка сессии одного
  искателя не останавливают остальных; в отчёте — явная пометка по каждому.

## 8. Future Work

- **Глобальная приоритизация seeds** — двухэтапный старт: сначала все искатели
  параллельно собирают и оценивают свои seeds, затем строится единый ранжированный
  список для обхода. Усложняет синхронизацию, отложено.
- **Общий кеш посещённых каналов** — исключение дублирующих обращений к Telegram
  при пересечении seed-графов нескольких искателей.
- **Учёт Premium** — Telegram отдаёт усечённый список похожих каналов без Premium;
  расширение охвата для аккаунтов без Premium (унаследовано из v1).
