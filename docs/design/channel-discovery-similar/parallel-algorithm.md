# Алгоритм параллельного поиска похожих каналов

## Задача

Скрипт `discovery-similar` работает последовательно по всем агентам. Нужно сделать так, чтобы каждый агент работал параллельно: сортировка seed-каналов по вовлечённости и дальнейший поиск похожих происходят независимо внутри каждого агента, все агенты запущены одновременно.



## Входные данные

| Параметр | Описание |
|---|---|
| `searchers` | Агенты, которые выполняют поиск (их сессии и seed-каналы) |
| `allAgents` | Все агенты платформы — кому распределяются найденные каналы |
| `target` | Целевое число новых каналов на каждого агента платформы |
| `minSubscribers` | Минимальный порог подписчиков кандидата |
| `minAvgViews` | Минимальный средний просмотр на пост кандидата |
| `minEngagementRate` | Минимальная вовлечённость аудитории кандидата |
| `minTopicScore` | Минимальная оценка тематической релевантности (0..1) |
| `theme` | Тема прогона — единая для всех искателей |
| `postsCount` | Число последних постов канала для оценки вовлечённости и темы |

## Общие переменные

- `goal = target × N`, где N — число агентов платформы
- `totalCollected = 0` — счётчик успешно найденных и зарегистрированных каналов
- `roundRobinIndex = 0` — индекс текущего агента для назначения канала
- Реестр каналов — `discovery.db` (единственная точка дедупликации и распределения)

---

## Алгоритм

Все искатели запускаются **одновременно и независимо**. Каждый искатель выполняет следующие шаги на своей сессии.

---

### Шаг 1. Сбор отправных точек (seeds)

Искатель берёт все каналы, которые уже есть у него в базе данных. Сетевых вызовов на этом шаге нет — данные берутся из локального кеша (`channelResolved = 1`).

---

### Шаг 2. Оценка вовлечённости seeds

Для каждого seed-канала искатель:
1. Запрашивает последние `postsCount` постов
2. Исключает `ENGAGEMENT_SKIP_FRESH` самых свежих постов (их просмотры ещё не «дозрели»)
3. Считает медиану просмотров по оставшимся постам
4. Делит медиану на число подписчиков → **оценка вовлечённости seed**

Каналы, у которых вовлечённость измерить не удалось (нет постов, нет данных о подписчиках), получают оценку «неопределено» и уходят в конец списка.

После оценки seed-каналы **сортируются по убыванию вовлечённости** — обход начнётся с самых живых каналов.

---

### Шаг 3. Обход графа похожих (BFS по уровням)

Обход идёт в ширину: сначала рекомендации всех seed-каналов (уровень 0), затем рекомендации найденных кандидатов (уровень 1), и так далее. На следующий уровень переходят только каналы, прошедшие все гейты.

**Для каждого кандидата из рекомендаций:**

#### Дедупликация
Канал уже есть в `discovery.db` → пропустить.
Обеспечивает непересечение как с предыдущими прогонами, так и с находками параллельных искателей текущего прогона.

#### Гейт 1 — Подписчики
Число подписчиков ниже `minSubscribers` → пропустить.

#### Гейт 2 — Группа обсуждения
У канала нет привязанной группы обсуждения → пропустить.
Агенту некуда вступать: вступление происходит в группу обсуждения, не в сам канал.

#### Гейт 3 — Вовлечённость аудитории
Запрашиваются последние `postsCount` постов. Считается средний просмотр на пост и ER (средний просмотр / подписчики). Если хотя бы один показатель ниже порога или данных недостаточно → пропустить (fail-closed).

#### Гейт 4 — Тематическая релевантность (LLM)
LLM оценивает описание канала и тексты постов (те же, что на Гейте 3 — без повторного запроса к Telegram). Если оценка ниже `minTopicScore` или оценить нечем → пропустить (fail-closed).

#### Регистрация
Канал прошёл все гейты:
1. Записать в `discovery.db`, назначив агента по round-robin: `allAgents[roundRobinIndex % N]`
2. Если запись прошла успешно (канал не был зарегистрирован конкурирующим искателем в этот же момент): `roundRobinIndex++`, `totalCollected++`, поставить в очередь вступления назначенного агента
3. Добавить кандидата в очередь следующего уровня BFS

#### Условие остановки
После каждой успешной регистрации: если `totalCollected >= goal` → искатель завершает работу. Остальные параллельные искатели также останавливаются при следующей проверке.

---

### Шаг 4. Завершение сессии

Искатель закрывает соединение с Telegram.

---

## Темп работы и защита аккаунтов

Между каждым обращением к Telegram — пауза 0.8–1.2 секунды. Это защита от антифлуд-ограничений Telegram.

- **Один FLOOD_WAIT** — искатель ждёт указанное время и повторяет запрос
- **Два FLOOD_WAIT подряд** — искатель останавливается; аккаунт не подвергается дальнейшему риску; остальные искатели продолжают
- **Ошибка сессии** — искатель пропускается, остальные продолжают

---

## Конкурентная безопасность

Единственная точка синхронизации между параллельными искателями — `discovery.db`. Запись в реестр атомарна (`INSERT OR IGNORE`): если два искателя одновременно нашли один и тот же канал, в реестр попадёт только первый. Второй увидит, что запись не прошла, и не засчитает канал в `totalCollected`.

Проверка условия остановки и инкремент счётчиков (`totalCollected`, `roundRobinIndex`) происходят между двумя обращениями к Telegram — в JS event loop этот участок не прерывается конкурирующими корутинами.

---

## Результат

По завершении всех искателей:
- Найденные каналы зарегистрированы в `discovery.db` с привязкой к агентам платформы
- Каналы поставлены в очереди вступления соответствующих агентов
- Оператор получает отчёт: сколько каналов найдено суммарно, сколько каждым искателем, сколько отсеяно по каждому гейту, у кого из искателей поиск прерван и по какой причине
