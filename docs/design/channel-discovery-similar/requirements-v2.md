# Discovery-similar v2: требования

> **О чём документ.** User Stories и Acceptance Criteria для параллельного алгоритма
> `discovery-similar`, готовые для разработчика.
>
> **Парный документ:** [analytics-parallel-algorithm.md](./analytics-parallel-algorithm.md) —
> что меняется (проблема, архитектура, альтернативы). Здесь — кому это нужно и зачем,
> плюс тестируемые критерии приёмки.
>
> **Граница:** поведение гейтов (подписчики, группа обсуждения, вовлечённость, LLM-тема)
> и логика вступления в каналы не меняются — этот документ касается только параллельного
> запуска искателей, per-searcher статистики и поведения при сбоях.

---

## 1. Проблема и кому она мешает

**Оператор платформы** запускает `discovery-similar` с несколькими искателями, чтобы
пополнить очереди вступления агентов новыми каналами. Сейчас искатели работают
последовательно — при трёх искателях прогон занимает в три раза больше времени, чем
с одним. Оператор вынужден либо терпеть долгие прогоны, либо ограничивать число
искателей в ущерб охвату.

Кроме того, в текущем отчёте нет разбивки по искателям: если один искатель нашёл
много каналов, а другой — мало, оператор не видит этого из отчёта и не может
диагностировать причину.

---

## 2. User Stories

### US-1 — Параллельный запуск искателей

**Как** оператор платформы, запускающий поиск похожих каналов с несколькими искателями,
**я хочу**, чтобы все искатели работали одновременно, а не по очереди,
**чтобы** время прогона не зависело от числа искателей, а определялось только самым
медленным из них.

**Acceptance Criteria:**

- AC-1.1: При запуске с N искателями все N сессий открываются в начале прогона, не
  одна за другой.
- AC-1.2: Каждый искатель держит свою Telegram-сессию открытой на весь обход — она
  не закрывается и не переоткрывается между уровнями графа.
- AC-1.3: Прогон с двумя искателями завершается не позже, чем одиночный прогон с
  наиболее медленным из них (плюс константный оверхед на запуск и распределение).
- AC-1.4: Фаза распределения каналов по агентам запускается строго после того, как
  **все** искатели завершили работу — независимо от того, как они завершились (по
  цели, по исчерпанию графа или по остановке).

### US-2 — Per-searcher статистика в отчёте

**Как** оператор платформы, читающий итоговый отчёт прогона,
**я хочу** видеть для каждого искателя отдельно: сколько каналов он нашёл и сколько
отсеял по каждому гейту,
**чтобы** понимать вклад каждого искателя и диагностировать причины малого охвата
(мало seed-каналов, высокий отсев по подписчикам, частые ограничения Telegram и т.п.).

**Acceptance Criteria:**

- AC-2.1: В отчёте для каждого искателя присутствует строка с числом каналов,
  успешно зарегистрированных от его имени за прогон.
- AC-2.2: В отчёте для каждого искателя присутствуют счётчики отсева по каждому
  гейту: мало подписчиков, нет группы обсуждения, низкая вовлечённость, тема ниже
  порога.
- AC-2.3: В отчёте присутствует агрегированная строка суммарных значений по всем
  искателям (для быстрого взгляда на итог прогона).
- AC-2.4: Строка отчёта по искателю, прерванному FLOOD_WAIT или упавшему с ошибкой
  сессии, помечается явно с указанием причины — рядом с его счётчиками.

### US-3 — Независимость искателей при сбоях

**Как** оператор платформы,
**я хочу**, чтобы сбой одного искателя (ошибка сессии или двойной FLOOD_WAIT) не
прерывал работу остальных,
**чтобы** прогон приносил максимальный результат даже при частичной недоступности
аккаунтов.

**Acceptance Criteria:**

- AC-3.1: Если у искателя не поднимается сессия при старте, остальные искатели
  продолжают работу. Прогон не прерывается и доходит до фазы распределения.
- AC-3.2: Если искатель получает два FLOOD_WAIT подряд и останавливается,
  остальные искатели продолжают работу до достижения общей цели или исчерпания
  своих графов.
- AC-3.3: В отчёте для каждого проблемного искателя указана причина остановки:
  «ошибка сессии» (с текстом ошибки) или «прерван FLOOD_WAIT».
- AC-3.4: После сбоя искателя счётчик общей цели `totalCollected` не сбрасывается —
  каналы, найденные до сбоя, сохраняются в реестре и участвуют в фазе распределения.

---

## 3. Бизнес-правила

- **BR-1.** Фаза распределения каналов по агентам запускается **только после**
  завершения всех искателей. Каналы без назначенного агента в реестре — это пул
  текущего прогона; распределение заполняет их по round-robin до `target` на агента.

- **BR-2.** Допустимый overshoot цели. При параллельном поиске итоговое число
  найденных каналов может незначительно превысить `goal` — это нормально. «Собрано
  X/Y» при X > Y в отчёте не является ошибкой.

- **BR-3.** Один канал — один агент. Канал, уже зарегистрированный в реестре
  (в текущем или прошлом прогоне), не регистрируется повторно — дублирующая запись
  молча отбрасывается. Инвариант непересечения держится на уникальности ссылки в
  реестре, а не на логике обхода.

- **BR-4.** Сортировка seed-каналов — per-searcher. Каждый искатель сортирует только
  свои seed-каналы по вовлечённости; глобального ранжирования всех seeds платформы
  нет. Следствие: при раннем стопе по цели находки разных искателей вносятся
  наравне, независимо от качества их seed-наборов.

- **BR-5.** Цепочка гейтов не меняется. Порядок проверки каждого кандидата строго:
  подписчики → группа обсуждения → вовлечённость (ER + средний просмотр) →
  тематическая релевантность (LLM). LLM-вызов происходит до регистрации в реестре.
