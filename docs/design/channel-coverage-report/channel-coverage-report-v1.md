# Design Doc: Отчёт о среднем охвате каналов — v1

> Аналитика фичи для человека. Объясняет, что делает система и как, и почему так
> решили. Нормативное поведение (требования + сценарии) — в `openspec/`, не здесь.

## 1. Проблема / Контекст

Платформа управляет несколькими агентами, каждый из которых мониторит десятки каналов.
Оператор не имеет единого взгляда на аудиторную ценность этих каналов: каналы хранятся
раздельно в per-agent БД, метрика охвата нигде не считается. Без охвата нельзя быстро
понять, в каких каналах больше всего аудитории и на каких стоит фокусировать DM-воронку.

## 2. Цели

- Дать оператору единый список всех каналов платформы со средним охватом.
- Отсортировать список по убыванию охвата — самые аудиторные каналы сверху.
- Обеспечить актуальность данных без ручного труда (обновление раз в месяц).

## 3. Как работает

### 3.1 Запуск отчёта

Оператор вызывает скилл из OpenClaw. Скилл:

1. Собирает каналы из таблицы `channels` всех агентов (только вступлённые).
2. Достаёт кэшированный `avg_views` из БД.
3. Сортирует по `avg_views` DESC; каналы с NULL — в конце.
4. Формирует CSV или Excel файл.
5. Отправляет файл в Saved Messages агента.

Вся тяжёлая работа (запросы к Telegram API) происходит **не при вызове скилла**, а
при фоновом обновлении кэша — скилл всегда работает быстро.

### 3.2 Формула среднего охвата

```
Берутся последние 11 постов канала, упорядоченные по дате (новые первые).
Пропускается 1-й (самый свежий) пост.
Берутся посты с позиции 2 по 11 — итого 10 постов.
avg_views = SUM(views по 10 постам) / 10
```

Первый пост пропускается намеренно: у только что опубликованного поста просмотры ещё
накапливаются и не репрезентативны.

Если в канале менее 2 постов — `avg_views` остаётся NULL.

### 3.3 Кэш и обновление

`avg_views` хранится в таблице `channels` per-agent БД. Считается дорого (запросы к
Telegram API), поэтому кэшируется и пересчитывается только в двух случаях:

1. **Плановый пересчёт раз в месяц** — запускается по расписанию для всех каналов,
   у которых `avg_views_updated_at IS NULL OR avg_views_updated_at <= now() - 30 * 86400`.
2. **При добавлении нового канала** — пересчёт только для него, немедленно.

### 3.4 Состав отчёта

| Колонка | Источник |
|---|---|
| Название | `channels.title` |
| Ссылка | `t.me/{channelUsername}` (если `channelUsername` не NULL; иначе пусто) |
| `chat_id` | `channels.chatId` |
| Средний охват | `channels.avg_views` |
| Дата пересчёта | `channels.avg_views_updated_at` (human-readable) |
| Агент | `agent_id` (определяется по пути к БД агента) |

Список единый, без группировки по агентам.

## 4. Архитектура

| Компонент | Новый? | Ответственность |
|---|---|---|
| OpenClaw-скилл (channel-coverage) | новый | собрать данные из всех агентов, сформировать файл, отправить в Saved Messages |
| Скрипт пересчёта avg_views | новый | запросить посты канала через MTProto, посчитать охват, обновить кэш в `channels` |
| Таблица `channels` | расширяется | добавляются два новых поля: `avg_views`, `avg_views_updated_at` |
| systemd-таймер | существующий | запускает скрипт пересчёта по расписанию раз в месяц |

Скилл и скрипт пересчёта разделены: скилл только читает кэш и формирует отчёт,
скрипт только обновляет кэш. Это позволяет вызывать их независимо.

## 5. Модель данных

Фича расширяет существующую таблицу `channels` в per-agent БД (`tg-channels.db`).

### Существующие поля (используются в отчёте)

| Поле | Тип | Назначение |
|---|---|---|
| `chatId` | TEXT PK | первичный ключ, id чата в Telegram |
| `title` | TEXT NOT NULL | название канала |
| `channelUsername` | TEXT | username; используется для ссылки `t.me/{username}` |
| `channelId` | TEXT | Telegram peer id |
| `channelAccessHash` | TEXT | access hash для MTProto |

### Новые поля

| Поле | Тип | Описание |
|---|---|---|
| `avg_views` | REAL | кэш среднего охвата. NULL = ещё не считалось или < 2 постов |
| `avg_views_updated_at` | INTEGER | Unix timestamp последнего успешного пересчёта. NULL = никогда не считалось |

```sql
ALTER TABLE channels ADD COLUMN avg_views REAL;
ALTER TABLE channels ADD COLUMN avg_views_updated_at INTEGER;
```

Индекс на `avg_views_updated_at` не нужен: при текущих объёмах полный скан таблицы
одного агента пренебрежимо мал.

## 6. Альтернативы

**Считать охват на лету при вызове скилла.**
Отвергнуто: запрос постов 100+ каналов через MTProto занял бы минуты и блокировал бы
скилл. Кэш обязателен.

**Хранить охват в отдельной таблице.**
Отвергнуто: `avg_views` — атрибут канала, хранить его рядом с каналом проще и
очевиднее. Отдельная таблица добавила бы JOIN без пользы.

**Пересчёт раз в неделю.**
Охват канала меняется медленно; рост аудитории за неделю несущественен для ранжирования.
Раз в месяц достаточно и снижает нагрузку на Telegram API.

## 7. Метрики успеха

- Скилл отрабатывает и присылает файл за < 5 секунд (данные из кэша).
- Все каналы всех агентов присутствуют в отчёте.
- После планового пересчёта у всех каналов `avg_views IS NOT NULL` (кроме тех,
  где < 2 постов).

## 8. Future Work

- **Ручной пересчёт через скилл** — сейчас пересчёт только плановый или при добавлении.
  Если понадобится принудительный пересчёт без ожидания месяца, можно добавить параметр
  `--recalculate` к скиллу.
- **Фильтры в отчёте** — по агенту, по минимальному охвату.
