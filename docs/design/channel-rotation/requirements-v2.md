# Требования: Раскладка каналов в авторотации по истории посещений — v2

> **О чём документ.** Проблема, доменная модель, цель, требования и критерии
> приёмки — уровень бизнес-аналитики (что и почему, для кого). Техническое
> решение (как именно это реализуется) — в парном `architecture.md` (архитектор).

## 1. Проблема и контекст

Авторотация переназначает каналы, покинутые агентом из-за бана, другому активному
агенту той же персоны. Сейчас целевой агент выбирается **по нагрузке** — round-robin
по числу активных каналов, наименее загруженному первым.

Такой выбор не учитывает, кто уже держал этот канал: канал может снова достаться
агенту, который его уже пробовал (и, возможно, там же был забанен), в то время как
агенты, ещё не пробовавшие канал, его не получают. Это снижает шанс закрепить канал
за аккаунтом, у которого он ещё может «прижиться».

Меняется **только правило выбора целевого агента** (было: по нагрузке; стало: по
истории посещений). Остальное поведение авторотации не меняется — см. §4.

Аудитория: платформа (скилл авторотации каналов) и владелец, отвечающий за
распределение каналов между аккаунтами персоны.

## 2. Цель

- Убрать нагрузку агента как фактор выбора целевого агента.
- Распределять канал агенту, у которого этого канала **ещё не было**, перебирая всех
  активных агентов персоны, прежде чем возвращать канал уже пробовавшему аккаунту.
- Сохранить поведение «нет подходящего агента → канал остаётся нераспределённым».

## 3. Доменная модель

| Термин | Что это |
|---|---|
| Персона | Набор агентов (аккаунтов), между которыми распределяются каналы |
| Активный агент персоны | Агент персоны, доступный для назначения каналов в текущем прогоне |
| Агент-источник | Агент, у которого канал только что был помечен покинутым из-за бана и от которого канал перераспределяется |
| Событие `assigned` | Запись в журнале операций о назначении канала агенту-получателю; пишется как ротацией, так и распределением |
| visit-count (агента по каналу) | Сколько раз этот канал уже назначался данному агенту-получателю — число событий `assigned` по каналу для этого агента в разрезе персоны |
| Круг (round) | Этап раздачи, на котором минимальный visit-count среди подходящих агентов равен k: на круге k канал получают агенты с visit-count = k. Круги возникают как следствие правила «минимальный visit-count», отдельным механизмом не задаются |
| Нераспределённый канал (`unassigned`) | Канал, которому в прогоне не нашлось подходящего целевого агента |

Модель внутренняя (история владения каналом внутри персоны), внешними источниками
Telegram не подтверждается и в них не нуждается.

## 4. Ограничения среды

- **Глубина истории.** Журнал операций ведётся с ~2026-09-12; назначения, сделанные
  раньше, в истории не видны и в visit-count не учитываются.
- **Оба источника событий `assigned`.** И авторотация, и распределение каналов пишут
  событие `assigned`; оба типа засчитываются в visit-count как «канал был у агента».
- **Неизменяемая часть авторотации.** Формирование списка кандидатов (каналы,
  покинутые из-за бана, с публичным именем), группировка кандидатов по персоне
  источника, применение назначения (закрепление за целевым агентом, постановка в
  очередь вступления, снятие у источника) и суточный запуск остаются как есть.
  Изменяется только правило выбора целевого агента. Нормативное описание неизменной
  части — существующая способность `channel-rotation` (`openspec/specs/`).

## 6. User Stories

**US-1 (R1, R2, R3, R4).** Как платформа, при перераспределении канала я хочу
выбирать целевого агента по наименьшему числу прошлых назначений этого канала, а не по
нагрузке, — чтобы канал сначала пробовали агенты, у которых его ещё не было.

**US-2 (R5).** Как платформа, при выборе целевого агента я хочу исключать агента-
источник, — чтобы не возвращать канал тому же аккаунту, от которого он только что
перераспределяется.

**US-3 (R6).** Как владелец, я хочу, чтобы канал проходил всех активных агентов
персоны по одному разу, прежде чем повторяться, — чтобы у каждого аккаунта был шанс
удержать канал до повторной попытки.

**US-4 (R7).** Как платформа, если подходящего целевого агента нет, я хочу оставлять
канал нераспределённым, — чтобы не назначать канал некорректно и сохранить текущее
безопасное поведение.

## 7. Требования

- **R1.** Система не должна учитывать нагрузку агента (число его активных каналов)
  при выборе целевого агента для канала.
- **R2.** Для канала система должна вычислять visit-count каждого активного агента
  персоны как число событий `assigned` по этому каналу для этого агента-получателя в
  разрезе персоны.
- **R3.** Система должна назначать канал активному агенту персоны с **минимальным**
  visit-count.
- **R4.** Если минимальный visit-count имеют несколько агентов, система должна
  выбирать целевого агента среди них **случайно**.
- **R5.** Система должна исключать агента-источник из числа кандидатов на получение
  канала.
- **R6.** Система должна раздавать канал по кругам как следствие правила минимального
  visit-count: пока есть активные агенты с visit-count = 0, канал достаётся им; когда
  у всех подходящих агентов visit-count ≥ 1, минимум становится 1, и канал достаётся
  агентам с visit-count = 1, и так далее.
- **R7.** Если подходящего целевого агента нет (активен только агент-источник),
  система должна оставлять канал нераспределённым (`unassigned`).

## 8. Критерии приёмки

- **AC-1 (R1).** При равном visit-count у нескольких агентов выбор не зависит от числа
  их активных каналов: более загруженный и менее загруженный агенты равноправны.
- **AC-2 (R2, R3).** Канал назначается активному агенту персоны с наименьшим числом
  прошлых событий `assigned` по этому каналу.
- **AC-3 (R4).** Если наименьший visit-count имеют несколько агентов, целевым может
  оказаться любой из них; выбор между ними случайный.
- **AC-4 (R5).** Агент-источник не получает перераспределяемый канал ни при каком
  visit-count.
- **AC-5 (R6).** Пока среди подходящих агентов есть visit-count = 0, канал достаётся
  агенту с visit-count = 0; повтор к уже державшему канал агенту происходит только
  после того, как канал прошёл всех подходящих агентов по разу.
- **AC-6 (R7).** Если единственный активный агент персоны — источник, канал остаётся
  нераспределённым.

## 9. Источники

- Неизменяемая часть поведения авторотации — существующая способность
  `channel-rotation` (`openspec/specs/`). Внешних источников (Telegram API) доменная
  модель не требует.
