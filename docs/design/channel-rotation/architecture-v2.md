# Раскладка авторотации по истории посещений — архитектура v2

Design-doc (КАК). Источник требований (ЧТО) — [requirements-v2.md](requirements-v2.md).
Парный к v2; предыдущая логика («по нагрузке») — [requirements-v1.md](requirements-v1.md)
и текущий код `src/features/channel-rotation/`. Здесь фиксируется техническое решение по
факту кода на ветке `refactoring-2`.

Развилки, где выбор за владельцем, помечены **[решение владельца]** — до подтверждения в
код не идёт (принцип проекта «решение принимает человек»).

Статус: черновик архитектуры, до кода.

---

## 1. Резюме решения

Меняется **одно правило** — выбор целевого агента в `plan.ts`: вместо round-robin по
нагрузке (`countActiveChannels`) канал получает активного агента персоны с **минимальным
visit-count** (число прошлых `assigned`-событий по этому каналу для агента в разрезе
персоны), случайно среди равных, исключая источник. Круги (R6) возникают сами как
следствие роста минимума — отдельного механизма кругов нет.

Два следствия для структуры кода:

1. **`plan.ts` упрощается.** Round-robin с курсором и сортировкой целей по нагрузке
   больше не нужен. Каждый кандидат выбирается **независимо** (см. §2.1, почему это
   корректно): своя история канала, нагрузка не участвует. Курсор убирается.
2. **`run.ts`**: `loadByAgent = countActiveChannels(...)` заменяется на построение
   visit-count по журналу операций; `countActiveChannels` теряет единственного
   потребителя (§4).

Неизменное (§5): сбор кандидатов, группировка по персоне, применение назначения
(`setAssignmentAgent` → `addJoinQueue` → `deleteChannelRow`), суточный таймер,
`resolvePersonaTargets`, поведение `unassigned`.

## 2. Новое правило выбора (`plan.ts`)

### 2.1 Почему выбор per-candidate независим и корректен

Текущий round-robin двигал курсор между кандидатами, чтобы **размазать нагрузку** внутри
прогона. v2 убирает нагрузку как фактор (R1, AC-1), поэтому размазывать нечего. Каждый
кандидат — это **отдельный канал** со своей историей владения; visit-count одного канала
для агента не зависит от того, кому в этом же прогоне достался другой канал (это разные
`chat_id`, разные записи `assigned`). Один канал не может быть кандидатом дважды за прогон
(источник у `leaved_from_banned` ровно один). Значит:

- назначения, сделанные для других кандидатов в этом прогоне, **не влияют** на visit-count
  текущего кандидата — курсор/аккумулятор внутри прогона не нужен;
- несколько каналов персоны могут в одном прогоне достаться одному агенту — это допустимо
  по v2 (нагрузка больше не критерий).

Отсюда: `plan.ts` перебирает кандидатов независимо, без общего состояния между ними.

### 2.2 Алгоритм на кандидата

Для кандидата с `sourceAgentId` и `chatId`:

1. `pool = activeAgentIds \ { sourceAgentId }` (R5). Пусто → `unassigned` (R7, AC-6).
2. Для каждого `a ∈ pool`: `vc(a) = visitCount(chatId, a)` (отсутствует в структуре ⇒ `0`).
3. `min = min(vc(a))`; `winners = { a ∈ pool : vc(a) === min }`.
4. Целевой агент — **случайный** из `winners` (R4, AC-3). Круги (R6) — следствие: пока есть
   `vc=0`, min=0 и канал идёт непробовавшим; когда у всех `vc≥1`, min растёт.

Пустая история (все `vc=0`) → случайный среди всех не-источников (круг 1) — покрывается
шагами 2-4 без спец-ветки (AC-5, edge §6).

### 2.3 Сигнатура `plan.ts` — как передавать visit-count [решение владельца]

`plan.ts` остаётся чистым (без I/O): visit-count приходит готовой структурой из `run.ts`.

| | **A (рекомендуется)** — вложенная `Map<chatId, Map<agentId, number>>` | **B** — функция `visitCount(chatId, agentId): number` | **C** — поле в `RotationCandidate` |
|---|---|---|---|
| Чистота plan | Полная (данные, не I/O) | Полная, но fn может скрывать I/O — хуже для теста | Полная |
| Тестируемость | Простой литерал Map в тесте | Нужно мокать fn | Данные в кандидате — просто |
| Отсутствующий агент = 0 | `inner.get(a) ?? 0` | fn возвращает 0 | `?? 0` |
| Связность | run строит Map, plan читает | plan зовёт callback | смешивает вход канала и историю |

**Рекомендация A.** `planRotation(candidates, activeAgentIds, visitsByChannel)`, где
`visitsByChannel: ReadonlyMap<string, ReadonlyMap<string, number>>` ключом `chatId`.
Отсутствие агента во внутренней карте трактуется как `0` — историю с нулями не материализуем.
Сигнатура-дельта против текущей: третий параметр `loadByAgent: Map<string,number>` →
`visitsByChannel`.

### 2.4 Тай-брейк «случайно среди равных» [решение владельца]

| | **A (рекомендуется)** — `Math.random()` внутри plan | **B** — инжектируемый `rng: () => number` |
|---|---|---|
| Прецедент | Текущий `plan.ts` уже использует `Math.random()` (tieBreak) | Нового параметра нет сейчас |
| Тест | Проверять принадлежность результата `winners` (не точное равенство) | Детерминированный выбор в тесте |

**Рекомендация A** — не плодить параметр; тесты проверяют инвариант «результат ∈ множество
минимальных не-источников», а не конкретного агента (для R4 это и есть корректная проверка).
B оставить как опцию, если владелец захочет детерминированные тесты выбора.

### 2.5 Убирается из `plan.ts`

- сортировка целей по нагрузке (`loadByAgent`, `tieBreak`) — заменяется на min-visit-count;
- курсор round-robin (`cursor`, `idx`, `attempts`) — не нужен при независимом выборе;
- **сортировка кандидатов по `statusUpdatedAt`** — служила только детерминизму курсора;
  без курсора на результат не влияет. Рекомендуется убрать (простота); можно оставить —
  поведенчески нейтрально. **[решение владельца, минорное]**

Сохраняется: тип `RotationCandidate` (нужен `chatId` — уже есть), `RotationAssignment`,
`RotationPlanResult` (`assignments` + `unassigned`), контракт «только источник активен →
`unassigned`».

## 3. Подсчёт visit-count (`channel-operations.ts` + `run.ts`)

### 3.1 Что считаем

Для канала (`chatId`) в разрезе персоны — число `assigned`-событий на каждого
агента-получателя (`attrs.newAgentId`). Это буквально `WHERE` из `getOwnershipTimeline`
(тот же мост `chat_id` ↔ `canonical_link` через `channel_identity`, тот же фильтр
`persona`) + `GROUP BY newAgentId` + `COUNT(*)`. `newAgentId IS NULL` (пустой слот,
`setAssignmentAgent(..., null)`) в счёт не идёт — это не визит к агенту.

### 3.2 Где живёт функция запроса [решение владельца]

| | **A (рекомендуется)** — новая `getChannelVisitCounts(admin, chatId, persona)` | **B** — переиспользовать `getOwnershipTimeline` + счёт в JS |
|---|---|---|
| Новая сущность | +1 функция чтения (рядом с `getOwnershipTimeline`, тот же паттерн, что `aggregateBansByAgent`) | 0 новых функций |
| Данные из БД | `COUNT` — только пары `{agent, count}` | Тянет все строки timeline, счёт в run.ts |
| Ясность | Возвращает готовый `Record<agentId, number>` | Логика счёта в оркестраторе |
| Дом логики журнала | В `channel-operations.ts` (владелец журнала — «один факт, один дом») | Счёт утекает в `run.ts` |

**Рекомендация A.** Новая read-функция в `channel-operations.ts`, зеркало
`getOwnershipTimeline` с `GROUP BY json_extract(attrs,'$.newAgentId')`:

```
getChannelVisitCounts(adminAgentId, chatId, persona): Record<agentId, number>
  -- SELECT newAgentId, COUNT(*) FROM operations
  -- WHERE type='assigned'
  --   AND (chat_id=@chatId OR canonicalLink IN (SELECT canonical_link FROM channel_identity WHERE chat_id=@chatId))
  --   AND (@persona IS NULL OR persona=@persona)
  --   AND json_extract(attrs,'$.newAgentId') IS NOT NULL
  -- GROUP BY newAgentId
```

Владелец журнала уже единственный дом таких запросов (§ шапки `channel-operations.ts`) —
класть счёт в `run.ts` (B) нарушило бы это.

### 3.3 Батч vs per-channel [решение владельца]

| | **A (рекомендуется)** — per-channel: один вызов на кандидата | **B** — один батч-запрос на всех кандидатов персоны/прогона |
|---|---|---|
| Число запросов | N (кандидатов в прогоне) | 1 |
| Индекс | `idx_ops_chat_type_ts (chat_id, type, ts)` на каждый вызов | тот же, но `chat_id IN (...)` + мост усложняют SQL |
| Мост `canonical_link` | Как в `getOwnershipTimeline` (проверенный) | Коррелированный по набору chat_id — сложнее и ошибкоопаснее |
| Сложность реализации | Низкая (зеркало готового запроса) | Выше (группировка по `chat_id`+`newAgentId`, сбор моста для набора) |

**Рекомендация A (per-channel).** Ротация — **суточный** батч-джоб, не в горячем пути;
кандидатов за прогон реалистично десятки (каналы `leaved_from_banned` с username по всем
персонам). N дешёвых индексированных запросов на `idx_ops_chat_type_ts` незначимы, а мост
`chat_id ↔ canonical_link` переиспользуется 1:1 из `getOwnershipTimeline` без нового SQL.
Батч (B) — преждевременная оптимизация: экономит на джобе, который и так идёт раз в сутки,
ценой более сложного и ошибкоопасного запроса.

Сложность A: `O(N)` запросов, каждый `O(log M)` по индексу (M — размер журнала). Для
суточного джоба при N в десятки — доли секунды.

### 3.4 Сбор в `run.ts`

Внутри цикла по персоне, до `planRotation`: для каждого кандидата группы вызвать
`getChannelVisitCounts(adminAgentId, candidate.chatId, persona)` и сложить во вложенную
`Map<chatId, Map<agentId, number>>` (вариант A §2.3). Затем
`planRotation(group, activeAgents, visitsByChannel)`. `adminAgentId` и `persona` уже в
области видимости цикла; `candidate.chatId` есть в `RotationCandidate`.

## 4. Что убрать из `run.ts`

- импорт `countActiveChannels` (строка 15) и построение `loadByAgent` (строка 84) —
  заменяются на visit-count (§3.4);
- третий аргумент вызова `planRotation` — `loadByAgent` → `visitsByChannel`.

**`countActiveChannels` в `channels.ts` [решение владельца, минорное].** Проверено
grep'ом по репозиторию: **единственный код-потребитель — `run.ts`** (прочие вхождения —
docs/memory/archive). После правки функция становится мёртвой. Рекомендация: удалить её из
`channels.ts` (нет мёртвого кода); допустимо оставить (безвредно, DB-слой). Решение
владельца — трогать ли DB-слой ради чистки.

`resolvePersonaTargets` и порядок его результата — не трогаем: детерминированная сортировка
там остаётся (нужна другим потребителям), для v2 порядок целей не важен (выбор по min +
random), но и не мешает.

- **`run.ts`**: `collectCandidates` (getRotationCandidates = `leaved_from_banned` с

  назначения (`setAssignmentAgent` → `addJoinQueue` → `deleteChannelRow`), учёт
  `skippedNoUsername`/`unresolvedPersona`, сводка прогона.
- **Суточный таймер** запуска — как есть.
- **Поведение `unassigned`** (нет цели → слот `agent_id=NULL`, строку канала у источника
  не удаляем) — как есть.
- Нормативная неизменная часть — существующая способность `channel-rotation`
  (`openspec/specs/`).

## 6. Edge-cases (§5 требований)

| Случай | Поведение | Требование |
|---|---|---|
| Пустая история (все `vc=0`) | min=0, `winners` = все не-источники, случайный из них (круг 1) | AC-5 |
| Только источник активен | `pool` пуст → `unassigned` | R7, AC-6 |
| Журнал с ~2026-09-12 | Ранние назначения не видны, `vc` их не учитывает — как есть, отдельной обработки не требует | §4 требований |
| Оба источника `assigned` (ротация и распределение) | Оба типа пишут `assigned`, оба засчитываются `COUNT`'ом — фильтра по `source` нет | §4 требований |
| Кандидат без `assigned`-истории у части агентов | Отсутствие агента в `Record` = `vc=0` (не «нет данных») | R2/R6 |
| `newAgentId=null` (пустой слот в истории) | Исключён `WHERE ... IS NOT NULL` — не визит | R2 |

## 8. Тестирование

`plan.ts` остаётся чистым и должен получить юнит-тест (сейчас `plan.test.ts` нет —
проверено). Покрыть по AC:

- AC-1: при равном `vc` более/менее загруженный равноправны (нагрузка в сигнатуре
  отсутствует — проверяется самим типом);
- AC-2/AC-5: канал уходит агенту с min `vc`; пока есть `vc=0` — только им;
- AC-3: при нескольких минимальных результат ∈ множество минимальных не-источников
  (инвариант, не точный агент — §2.4);
- AC-4: источник не выбирается ни при каком `vc`;
- AC-6: только источник активен → `unassigned`.

Запуск — как у существующих юнит-тестов проекта (`node --import tsx --test …`).

## 9. Развилки (решение владельца)

1. **Передача visit-count в `plan.ts`** — вложенная Map `chatId→agentId→count` (A, реком.)
   vs lookup-функция (B) vs поле кандидата (C). §2.3.
2. **Функция запроса** — новая `getChannelVisitCounts` в `channel-operations.ts` (A, реком.)
   vs переиспользовать `getOwnershipTimeline` + счёт в `run.ts` (B). §3.2.
3. **Батч vs per-channel** — per-channel N запросов (A, реком.) vs один батч (B). §3.3.
4. **Тай-брейк** — `Math.random()` inline (A, реком.) vs инжектируемый `rng` (B). §2.4.
5. **Удаление мёртвого `countActiveChannels`** из `channels.ts` — удалить (реком.) vs
   оставить. §4. *Минорное.*
6. **Сортировка кандидатов по `statusUpdatedAt`** в `plan.ts` — убрать (реком.) vs
   оставить (нейтрально). §2.5. *Минорное.*
