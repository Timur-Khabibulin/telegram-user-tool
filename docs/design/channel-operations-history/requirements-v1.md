# Требования: История операций с каналами — v1

> **О чём документ.** Что система должна фиксировать и по каким правилам в
> централизованном журнале операций над каналами, чтобы отвечать на вопрос
> «сколько раз и когда канал был забанен у конкретного агента» и показывать
> тайм-линию владения каналом. Уровень бизнес-аналитики (что и почему, для
> кого). Техническое решение (как именно это реализуется, включая механизм
> дедупликации и хранение) сюда не входит — это отдельный документ
> `architecture.md`, парный к этому.
>
> **Статус.** Требования утверждены заказчиком, открытых вопросов нет.

---

## 1. Проблема и контекст

Каналы закреплены за агентами и могут переходить между ними: при первом
добавлении канал назначается агенту; если агента забанили в канале, канал
автоматически уезжает («ротация») к другому активному агенту, чтобы продолжить
работу под другим аккаунтом.

Сейчас невозможно определить, сколько раз и когда конкретный канал был забанен
на том или ином агенте. Причины:

- Пер-агентная база хранит по каналу только последний статус и одну метку
  времени — предыдущие значения затираются при перезаписи.
- При ротации строка канала у прежнего агента удаляется полностью вместе со
  статусом, временем и любой пер-агентной историей.

Из-за этого история банов теряется, и её нельзя восстановить ретроспективно.

Заинтересованные лица:
- **Аналитик** — хочет считать баны канала по агентам, чтобы оценивать
  «выгорание» связки канал↔аккаунт.
- **Оператор** — хочет видеть тайм-линию владения каналом, чтобы понимать, где
  канал сейчас и почему он уехал.

---

## 2. Цель

1. Вести централизованный (один на платформу) неизменяемый журнал операций над
   каналами, переживающий ротацию каналов между агентами.
2. По журналу отвечать на главный вопрос: сколько раз и в какие моменты канал
   переходил в статус «banned» у конкретного агента.
3. По журналу показывать тайм-линию владения каналом (кому и когда он
   назначался).
4. Заложить модель операции, расширяемую под будущие типы операций без
   изменения структуры уже накопленных записей.

## 3. Доменная модель

Термины предметной области. Понятия платформы — из `docs/product.md` и контекста
задачи; понятия Telegram — по документации Telegram/MTProto (раздел 9).

| Термин | Что это |
|---|---|
| Агент | Один Telegram-аккаунт со своей персоной, работающий через MTProto. За каждым агентом закреплён набор каналов. Понятие платформы (`docs/product.md`). |
| agentId | Идентификатор агента на платформе. |
| Канал | Telegram-сообщество (канал/группа обсуждения), в котором работает агент. |
| chatId | Идентификатор канала — marked peer id вида `-100…`. Глобален в Telegram: одинаков для всех аккаунтов/агентов, стабилен и переживает ротацию, применим к любому каналу рабочего набора (в т.ч. к дискуссионной группе без собственного публичного username). Понятие Telegram (раздел 9). |
| access_hash | Пер-аккаунтный реквизит доступа к каналу, свой у каждого агента. В идентификации канала не участвует. Понятие Telegram (раздел 9). |
| canonical_link / username | Публичная ссылка канала вида `https://t.me/<username>`. Есть у каждого канала рабочего набора: вступление в системе возможно только по публичному username, приватные invite-каналы (`t.me/+hash`) не поддерживаются и в рабочий набор не входят. У дискуссионной группы без собственного username ссылкой служит username родительского broadcast-канала. Человекочитаемый реквизит, не ключ. |
| Статус канала | Состояние обработки канала у агента. Значения, относящиеся к этим требованиям: `banned` (агент забанен в канале), `suspend` (сообщения агента массово удалены; временный, снимается по таймеру), `leaved_from_banned` (терминальный: агент вышел после бана), `leaved_manual` (терминальный: агент вышел по решению оператора). Прочие состояния канала (в т.ч. `should_leave`, `format_error`, `only_comment`, `sleep`, `not_found`) в этот журнал не попадают. |
| Ротация | Автоматический уезд забаненного канала от одного агента к другому активному: у прежнего агента строка канала удаляется, в реестре меняется владелец, целевой агент вступает в канал. |
| Операция | Единица журнала: зафиксированный факт действия над каналом. Неизменяема. |
| Тип операции | Классификатор операции. В v1: «Смена статуса канала», «assigned» (смена владельца), «joined» (вступление). Расширяем. |
| Реквизиты операции | Список пар key:value, состав которых зависит от типа операции. |
| Источник (актор) | Инициатор операции: оператор / монитор / таймер / модуль. |
| assigned | Событие центрального реестра: каналу назначен/переназначен агент-владелец. Не является значением статуса. |
| joined | Событие успешного вступления агента в канал. Не является значением статуса. |

## 4. Ограничения среды

- **Централизованность обязательна.** Журнал не может лежать в пер-агентном
  хранилище: оно хранит только последний статус и удаляется при ротации.
  Поэтому журнал — общий на платформу.
- **Ключ канала — chatId.** Единственный идентификатор, глобальный и стабильный
  для всех агентов, переживающий ротацию и применимый к приватным каналам без
  username. Пер-аккаунтный access_hash в идентификации не участвует.
- **Множественные точки записи одного перехода.** Один и тот же переход статуса
  (в частности, `banned`) фиксируется из нескольких мест системы (мониторы
  разных версий, модуль отправки комментариев). Это создаёт риск дублирующих
  записей об одном фактическом переходе.
- **Нет ретроспективы.** История до внедрения журнала недоступна и не
  реконструируется. Журнал наполняется только с момента внедрения.
- **Автоматические операции без человека-инициатора.** Снятие статуса `suspend`
  выполняет периодический системный процесс — у такой операции нет
  человека-инициатора.

## 5. User Stories

US-1 (R7, R8, R10, R13, R16). Как аналитик, я хочу видеть, сколько раз и в какие
моменты конкретный канал переходил в статус `banned` у конкретного агента, чтобы
оценивать «выгорание» связки канал↔аккаунт.

US-2 (R4, R16). Как аналитик, я хочу, чтобы баны канала корректно относились к
тому агенту, у которого они произошли, в том числе для каналов, сменивших
владельца после ротации, чтобы подсчёт по агентам оставался достоверным.

US-3 (R4, R16). Как аналитик, я хочу учитывать баны для любого канала рабочего
набора, включая каналы, чья дискуссионная группа не имеет собственного username,
чтобы охват подсчёта не зависел от наличия у канала собственного username.

US-4 (R11, R14, R17). Как оператор, я хочу видеть тайм-линию владения каналом
(кому и когда он назначался и переназначался), чтобы понимать, где канал сейчас
и почему он уехал.

US-5 (R18). Как аналитик, я хочу агрегировать число банов по агенту за период,
чтобы сравнивать аккаунты по частоте банов.

US-6 (R5). Как владелец продукта, я хочу, чтобы модель операции позволяла
добавлять новые типы операций без изменения уже накопленных записей, чтобы
развивать журнал без переломных миграций.

US-7 (R19). Как аналитик, я хочу, чтобы выгрузки явно отражали границу доступности
данных, чтобы не принимать отсутствие записей за прошлое за «ноль банов».

## 6. Требования

### Всегда действует

- **R1.** Система должна вести журнал операций централизованно — один журнал на
  всю платформу.
- **R2.** Система должна хранить операции как неизменяемые записи (append-only):
  операция фиксирует свершившийся факт и не редактируется и не удаляется в ходе
  обычной работы.
- **R3.** Каждая операция должна иметь общую часть: уникальный идентификатор,
  время, тип операции, идентификатор канала, источник и список реквизитов
  key:value.
- **R4.** Система должна использовать в качестве идентификатора канала в журнале
  `chatId` — глобальный, стабильный, переживающий ротацию и применимый к любому
  каналу рабочего набора (в т.ч. к дискуссионной группе без собственного
  username). `canonical_link`/username хранится как вторичный человекочитаемый
  реквизит, не как ключ.
- **R5.** Разные типы операций могут иметь разный состав реквизитов. Добавление
  нового типа операции не должно изменять структуру и валидность ранее
  накопленных записей и не должно влиять на запросы по существующим типам.
- **R6.** Каждая операция должна нести источник (актор): оператор, монитор,
  таймер или модуль.

### Реквизиты по типам операций

- **R7.** Операция типа «Смена статуса канала» должна нести реквизиты:
  `oldAgentId`, `newAgentId`, `oldStatus`, `newStatus`, источник.
- **R8.** Тип «Смена статуса канала» должен фиксировать строго следующие
  переходы и никакие другие: переход в `banned`; переход в `suspend`; снятие
  `suspend`; переход в `leaved_from_banned`; переход в `leaved_manual`. Переход в
  `should_leave` в v1 не фиксируется (см. раздел «Вне рамок»).
- **R11.** Операция типа «assigned» (смена владельца канала) должна нести
  реквизиты: `oldAgentId` (пустой при первичном назначении канала), `newAgentId`,
  источник.
- **R12.** Операция типа «joined» (вступление агента в канал) должна нести
  реквизиты: `agentId`, источник.

### По событию

- **R13.** Когда происходит один из учитываемых переходов статуса (R8), система
  должна зафиксировать операцию типа «Смена статуса канала».
- **R14.** Когда в реестре меняется владелец канала (включая первичное
  назначение и переназначение при ротации), система должна зафиксировать
  операцию типа «assigned».
- **R15.** Когда агент успешно вступает в канал, система должна зафиксировать
  операцию типа «joined».

### Правила подсчёта и дедупликации

- **R9.** Один фактический переход статуса должен соответствовать одной учётной
  единице в журнале. Несколько записей об одном и том же переходе, порождённых
  разными точками кода, не должны задваивать этот переход в выгрузках. Механизм
  дедупликации определяется на уровне архитектуры.
- **R10.** «Новым баном» считается вход в статус `banned` из состояния, не
  являющегося `banned`. Повторная простановка `banned` при уже действующем
  `banned`, без промежуточного выхода из этого состояния, не должна порождать
  новый бан. Повторный бan засчитывается только если между двумя `banned` было
  фактическое покидание состояния бана (выход/сброс/ротация с последующим
  вступлением).

### Запросы к данным

- **R16.** По журналу должно быть возможно получить количество и моменты
  переходов канала (по `chatId`) в статус `banned` у конкретного агента, включая
  каналы, сменившие владельца после ротации, и приватные каналы без username.
- **R17.** По журналу должно быть возможно получить тайм-линию владения каналом:
  последовательность операций «assigned» с временами и парами
  (`oldAgentId`, `newAgentId`).
- **R18.** По журналу должно быть возможно получить агрегат числа банов по
  агенту за заданный период.

### Границы данных

- **R19.** Журнал наполняется только с момента внедрения; ретроспектива до этого
  момента недоступна. Выгрузки за период, начинающийся раньше даты старта сбора,
  должны явно отражать границу доступности данных и не представлять отсутствие
  записей за прошлое как отсутствие банов.
- **R20.** В v1 пользовательский интерфейс не предоставляется: журнал
  накапливает данные, доступные для разовых выгрузок аналитиком.

## 7. Критерии приёмки

- **AC-1 (R16, R7, R8, R13).** Для заданных канала и агента выгрузка возвращает
  число переходов в `banned` и список их моментов времени.
- **AC-2 (R4, R16).** После ротации канала каждый бан отнесён к тому агенту, у
  которого он произошёл; подсчёт по агентам не смешивает баны разных владельцев.
- **AC-3 (R4, R16).** Бан канала, чья дискуссионная группа не имеет собственного
  username, фиксируется и учитывается наравне с остальными, с ключом канала
  `chatId`.
- **AC-4 (R14, R17).** Тайм-линия владения каналом содержит операции «assigned» с
  временами и парами (`oldAgentId`, `newAgentId`); при первичном назначении
  `oldAgentId` пуст.
- **AC-5 (R18).** Агрегат банов по агенту за период возвращает по каждому агенту
  число банов за этот период.
- **AC-6 (R2).** Записи журнала не изменяются и не удаляются в ходе обычной
  работы; повторная фиксация того же факта не переписывает прежнюю запись.
- **AC-7 (R9).** Несколько записей об одном фактическом переходе (например,
  `banned` из разных точек кода) не увеличивают число банов в выгрузке.
- **AC-8 (R10).** Повтор `banned → banned` без промежуточного выхода из `banned`
  не увеличивает счётчик банов; повторный бан после фактического покидания
  состояния бана — увеличивает.
- **AC-9 (R8).** В журнал типа «Смена статуса канала» попадают только переходы из
  R8; переходы в состояния, не входящие в список, отсутствуют.
- **AC-10 (R6).** У каждой операции указан источник из набора: оператор, монитор,
  таймер, модуль. У операции снятия `suspend` источник — таймер.
- **AC-11 (R5).** Введение нового типа операции с собственным набором реквизитов
  не нарушает читаемость ранее накопленных записей и результаты запросов по
  существующим типам.
- **AC-12 (R19).** Выгрузка за период, начинающийся раньше даты старта сбора,
  явно показывает границу доступности данных.

## 8. Краевые случаи

| Случай | Решение |
|---|---|
| Идентичность канала после ротации | Ключ канала — `chatId` (глобальный, стабильный). Ротация не меняет `chatId`, операции разных владельцев связываются по одному ключу (R4). |
| Каналы без собственного username | Покрыты: ключ `chatId` не требует собственного username канала; баны учитываются (R4, R16, AC-3). Истинно приватных каналов (`t.me/+hash`) в рабочем наборе нет — вступление возможно только по публичному username. |
| Тайм-линия владения без собственного username | Достижима: у каждого канала рабочего набора есть публичная ссылка (родительского broadcast-канала), поэтому событие `assigned` в реестре есть у всех каналов набора. Отдельного «приватного» пробела не существует (R17). |
| `assigned` и `joined` — не статусы | Это отдельные типы операций со своими реквизитами; в парах `oldStatus`/`newStatus` они не участвуют (R11, R12). |
| Первичное назначение канала | Операция «assigned» с пустым `oldAgentId` — штатная ситуация (R11, AC-4). |
| Снятие `suspend` по таймеру | Фиксируется как «Смена статуса» с `newStatus` = активный; источник — таймер; человека-инициатора нет (R8, R6, AC-10). |
| Дублирующая запись одного перехода из разных точек кода | Один фактический переход = одна учётная единица; дедупликация — на уровне архитектуры (R9, AC-7). |
| Повтор `banned → banned` | Новый бан не создаётся (R10, AC-8). |
| Отсутствие ретроспективы | Журнал стартует «с нуля»; выгрузки помечают границу доступности данных (R19, AC-12). |
| Ротация как последовательность операций | Уезд забаненного канала отражается набором операций с одним `chatId`: «Смена статуса» → `leaved_from_banned` у источника; «assigned» (old=A, new=B) в реестре; «joined» (agentId=B) у цели. Последующий бан у B — новая операция «Смена статуса». |

## Вне рамок

- Механизм дедупликации записей об одном переходе (R9), схема хранения журнала,
  индексы и способ построения выгрузок — уровень `architecture.md`, не этих
  требований.
- Пользовательский интерфейс и регулярные отчёты по журналу — в v1 не входят
  (R20).
- Фиксация перехода в `should_leave` — в v1 не входит. Статус выставляется
  оператором вручную, минуя прикладной модуль; кодовой точки записи для него нет,
  поэтому программно журналировать этот переход нечем. Терминальный
  `leaved_manual` (выход по решению оператора) при этом фиксируется штатно — у
  него есть кодовая точка записи.
