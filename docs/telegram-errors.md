# Ошибки MTProto/GramJS и поведение системы

Каталог RPC-ошибок Telegram, с которыми сталкивается платформа, и целевое
(to be) поведение системы на них. Единый дом для этого знания — при добавлении
обработки новой ошибки обновлять и эту таблицу (принцип «один факт — один
дом», `agent-playbook.md`).

Каждая errorMessage встречается в таблицах один раз. Если одна и та же ошибка
по-разному обрабатывается в разных местах (например, при вступлении в канал
и при отправке сообщения), это описано внутри одной строки, а не дублированием
строки в нескольких таблицах.

## Как это устроено

Коды и тексты ошибок приходят от сервера Telegram как есть. Исключение —
`FLOOD_WAIT_N` / `FLOOD_PREMIUM_WAIT_N` / `SLOWMODE_WAIT_N`: библиотека GramJS
перехватывает их по шаблону, подменяет текст на вид `"A wait of N seconds is
required..."` и отдельно передаёт число секунд ожидания. Поэтому в проекте
флуд определяется по числу секунд ожидания, а не парсингом текста ошибки.

Источник кодов: собственные данные библиотеки GramJS + общая база данных
ошибок Telegram API (Telethon `errors.csv`), которой пользуются все
MTProto-библиотеки.

`Обработка to be` — целевое поведение в формате «если _, то должен _»; пусто
или «—» — решение ещё не принято либо изменений не требуется.

### 2. Просмотр новых каналов и вступление в них

Ошибки 13–22 возникают при вступлении в канал через скилл `join-queue`, в
рамках одной попытки, объединяющей три шага: поиск канала по username,
получение информации о канале и вступление. `FLOOD_WAIT_N` в этом же месте —
см. №9.

Правило перехода очереди между прогонами (относится ко всем строкам ниже
сразу, не к одной ошибке): если строка очереди имеет статус `error`, то на
следующих прогонах она должна игнорироваться (не браться в очередной батч).
Если строка имеет статус `skipped`, то перед взятием следующего батча она
должна быть переведена в статус `pending`. Это меняет текущую модель
состояний `join_queue`, где сейчас всё наоборот: `error` ретраится
автоматически несколько раз, а `skipped` — постоянный статус, снимается
только вручную.

## Новые сущности (to be)

**Таблица ограничений агентов** (`agent_restrictions`) — общая на всех
агентов, одна БД на всю платформу, не отдельная база на каждого агента. Одна
строка на `agentId` внутри этой общей таблицы; наличие строки означает, что
агент ограничен, отсутствие — что нет.

| Поле | Значение |
|---|---|
| `agentId` | первичный ключ |
| `restriction_type` | `banned` \| `need_update_session` \| `suspend` |
| `reason` | сырой `errorMessage` ошибки, вызвавшей ограничение |
| `restriction_duration` | длительность в секундах; `NULL` = бессрочно (`banned`, `need_update_session`). Для `suspend` — по умолчанию 3 дня (259200 сек), инициатор ограничения может задать своё значение |
| `restricted_at` | unix-время создания записи |

Истечение временного ограничения (`suspend`) = `restricted_at + restriction_duration`.
Диспетчер перед запуском любой задачи агента должен проверять эту таблицу: если
есть активная запись (`banned`/`need_update_session` — всегда; `suspend` — пока
`restricted_at + restriction_duration > now`), задача не запускается. Для
`suspend` после истечения срока запись должна быть удалена, задачи возобновляются
автоматически. Для `banned`/`need_update_session` запись снимается только вручную.

**Лог ошибок аккаунта** — своя таблица у каждого агента (отдельная база на
каждого агента, как остальные данные агента), не общая. Поле `agentId` в
схеме не нужно — принадлежность записи агенту уже определяется тем, в чьей
БД она лежит. Append-only, отдельно от `agent_restrictions` — это история
всех срабатываний, а не текущее состояние:

| Поле | Значение |
|---|---|
| `skill_type` | тип задачи/скилла, в рамках которого возникла ошибка |
| `errorMessage` | сырой текст ошибки |
| `occured_at` | unix-время возникновения |

Пишется при каждом возникновении ошибок №1–6, №8, №11, №12, №21, №29, а также
при срабатывании нового правила «10 каналов banned за сутки» (см. `agent_restrictions.
restriction_type` в разделе «Статусные модели») — независимо от того,
создаётся ли/обновляется ли при этом запись в `agent_restrictions`. Для этого
правила `errorMessage` = `"channels_banned"` (фиксированная строка, не сырой
текст ошибки Telegram — правило не привязано к одной конкретной ошибке).

## Статусные модели (to be)

Для каждого поля со статусом среди сущностей, затронутых этим документом:
какие значения оно принимает, на каком шаге какого скилла проставляется и
обновляется, когда снимается, на каком шаге проверяется и что означает.
Сущности без статусного поля (например `banned_channels` — очередь без
статуса, только наличие/отсутствие строки) сюда не входят.

### `channels.status`

| Статус | Когда ставится | Когда снимается | Что означает |
|---|---|---|---|
| *(нет статуса)* | Начальное состояние канала | — | Канал в обычной работе, ограничений нет |
| `banned` | №23 (в контексте отправки сообщения) или №24 | Устарело — этот раздел описывает раннюю версию модели. Актуальное поведение (`leave-banned-human-pacing`, `leave-banned-terminal-status`): `banned` ставит канал в очередь на выход, после успешного выхода статус становится `leaved_from_banned` (терминальный, запись `channels` не удаляется) | Право писать в этот канал/группу отозвано именно у этого агента |
| `format_error` | №25, №26 или №27 | Не определено — открытый вопрос, отложен на отдельное обсуждение | Канал отклоняет способ отправки — тип контента (текст/медиа, №25/№26) либо требует оплату за сообщение (№27), который агент не поддерживает; сам канал не забанен |

**Где ставится/обновляется:** в скилле `monitor-v2` — на шаге обработки
исхода попытки отправить ответ в канал, сразу после получения ошибки от
Telegram по этой попытке, до перехода к следующему каналу. `banned`
проставляется на этом шаге при получении соответствующей ошибки.
`format_error` — на этом же шаге, обновляется заново при каждом повторном
получении соответствующей ошибки для этого канала.

**Где проверяется:** в скилле `monitor-v2`, на шаге непосредственно перед
обработкой канала (перед тем как проверять/отвечать на сообщения в этом
канале). Правило: если `status='banned'` — канал пропускается, обработка
переходит к следующему; если статус любой другой (включая `format_error` или
отсутствие статуса) — канал обрабатывается как обычно.

### `join_queue.status`

| Статус | Когда ставится | Когда снимается | Что означает |
|---|---|---|---|
| `pending` | Начальное состояние при добавлении ссылки в очередь | Уходит из этого статуса при взятии в батч (→ `processing`) | Ссылка ожидает обработки |
| `processing` | Строка взята в текущий батч на обработку | Возврат в `pending`, если строка не обновлена дольше таймаута обработки (завис прогон); иначе переход в `joined`/`skipped`/`error` по итогу попытки | Вступление в канал по этой ссылке выполняется прямо сейчас |
| `joined` | Успешное вступление | Не снимается — терминальный | Агент состоит в канале |
| `skipped` | №9 (`FLOOD_WAIT_N`, после исчерпания 2 повторов) или №21 (`CHANNELS_TOO_MUCH`) | To-be: перед взятием каждого следующего батча строка переводится обратно в `pending` — то есть снимается автоматически на каждом прогоне | Временная причина отказа (флуд/лимит аккаунта), может исчезнуть сама — вступление стоит повторить |
| `error` | №13–20, №22 (см. также №23 в join-контексте — формально остаётся на этой же общей ветке обработки, см. открытый вопрос по разделению этой ветки) | Не снимается автоматически (to-be) — постоянная причина отказа | Канал непригоден для вступления по причине, не зависящей от повторных попыток (не существует, уже состоим, приватный и т.п.) |

**Где ставится/обновляется:** в скилле `join-queue` — на шаге обработки
исхода одной попытки вступления, сразу после получения ответа от Telegram по
конкретной ссылке, до перехода к следующей ссылке в этом же батче. Отдельно —
на шаге формирования батча, в начале прогона, до обработки отдельных ссылок:
`pending`/`error` переводятся в `processing` (взяты в работу); зависшие
`processing` (не завершённые дольше таймаута обработки) возвращаются в
`pending`; to-be добавляет на этом же шаге переход `skipped` → `pending`.

**Где проверяется:** на шаге формирования батча, в начале каждого прогона
скилла `join-queue`, до обработки отдельных ссылок — именно на этом шаге
решается, какие строки войдут в очередной батч.

### `agent_restrictions.restriction_type`

| Статус | Когда ставится | Когда снимается | Что означает |
|---|---|---|---|
| *(строки нет)* | Начальное состояние агента | — | Агент не ограничен, задачи выполняются по расписанию |
| `banned` | №5, №6, №11 или №12, в любом месте возникновения ошибки | Автоматически — успешной авто-заменой аккаунта из пула (суточный свип `banned-account-replacement`, снимает `banned` последним шагом после активации нового аккаунта) либо вручную человеком (`restriction_duration=NULL`) | Аккаунт удалён/забанен Telegram целиком (№5/№6) либо заморожен Telegram до прохождения проверки/апелляции (№11/№12) |
| `need_update_session` | №1, №2, №3, №4 или №8 | Только вручную человеком (`restriction_duration=NULL`) | Сессия или конфигурация аккаунта невалидны, нужна ручная переиздача сессии/правка `tg-account.json` |
| `suspend` | Два независимых триггера: (1) №29, `restriction_duration=86400` (сутки, явно переопределяет дефолт); (2) **новое правило** — у агента есть минимум 10 каналов со `status='banned'`, у КАЖДОГО из которых `statusUpdatedAt` не ранее, чем сутки назад (то есть все десять попадают в окно последних 24 часов) — тогда `restriction_duration=259200` (3 дня, дефолт) | Автоматически, когда `restricted_at + restriction_duration ≤ now` — запись удаляется, задачи возобновляются | Временный анти-спам бан со стороны Telegram (триггер 1) или подозрительно частые баны каналов подряд (триггер 2) |

Одна строка на `agentId` — новое основание для ограничения не может возникнуть,
пока действует текущее: диспетчер не запускает задачи ограниченного агента, а
значит и ошибки, порождающие ограничение, физически не могут произойти, пока
ограничение активно. Конфликтов между типами не бывает по построению.

**Где ставится/обновляется:**
- №1–4, №8, №5/№6 (при подключении к Telegram) — это не шаг конкретного
  скилла, а шаг завершения прогона любого скилла с ошибкой подключения:
  подключение к Telegram нужно каждому скиллу, поэтому проверка и запись
  должны происходить в общей точке после завершения прогона скилла, а не
  внутри отдельного скилла.
- №29 (`PEER_FLOOD`) — эта ошибка может возникнуть в любом скилле, где
  отправляется сообщение (сейчас это `dm-send` и `monitor-v2`), на шаге
  обработки исхода попытки отправки конкретного сообщения, сразу после
  получения этой ошибки от Telegram — не только в `dm-send`.
- №11/№12 (заморозка аккаунта) — в отличие от №1–4/№8/№5/№6 выше, эти ошибки
  возникают не при подключении, а при отдельных вызовах API уже подключённого
  клиента; замечены в скиллах `channel-activity-update` (при получении
  истории чата) и `monitor-v2` (при отметке чата прочитанным), возможны и в
  других местах, где скилл вызывает Telegram API. Ставится на шаге обработки
  исхода конкретного вызова, сразу после получения ошибки, независимо от
  скилла и метода.
- **Новое правило (10 банов каналов за сутки)** — в скиллах `monitor-v2` и
  `monitor-v3`, на том же шаге, где каналу проставляется `status='banned'`
  (см. выше): сразу после этого действия дополнительно считается число
  каналов агента со `status='banned'`, у которых `statusUpdatedAt` попадает в
  последние 24 часа; при достижении 10 (посчитанных на этот момент) — тем же
  шагом создаётся/обновляется ограничение с `reason="channels_banned"`
  (фиксированная строка, не сырой `errorMessage` — правило не привязано к
  одной ошибке) и `restriction_duration=259200`, в отличие от триггера №29.

**Где проверяется:** диспетчером, на шаге, предшествующем запуску любой
задачи агента — перед каждым запуском, для любого агента (это уже основное
правило раздела «Новые сущности» выше, здесь повторено для полноты
статусной модели).

### `dm_candidates.status`

| Статус | Когда ставится | Когда снимается | Что означает |
|---|---|---|---|
| `pending` | Начальное состояние при создании кандидата | Остаётся в этом статусе (не потребляется), если попытка отправки пропущена из-за №9 (флуд, до исчерпания повторов) или прервана из-за №29 (`PEER_FLOOD`) — кандидат не считается обработанным | Кандидат ожидает попытки отправки DM |
| `sent` | Успешная отправка DM | Не снимается — терминальный | DM отправлено |
| `privacy_blocked` | №30 | Не снимается — терминальный | Получатель закрыл приём сообщений от незнакомцев |
| `deactivated` | №5 или №6, когда ошибка возникает при отправке DM конкретному получателю | Не снимается — терминальный | Аккаунт получателя удалён/забанен (одновременно с этим агенту создаётся/обновляется `agent_restrictions` типа `banned` — см. выше) |
| `skipped` | №31, №32, №33, №34 и любая другая непредвиденная ошибка | Не снимается — терминальный | Отправить DM этому кандидату не удалось по причине, не подпадающей под отдельную обработку |

**Где ставится/обновляется:** в скилле `dm-send` — на шаге обработки исхода
попытки отправки DM конкретному кандидату, сразу после получения ответа от
Telegram по этому кандидату, до перехода к следующему кандидату в списке. При
№9 (до исчерпания повторов) и №29 этот шаг не завершается определением
статуса — кандидат остаётся `pending`.

**Где проверяется:** на шаге отбора кандидатов, в начале прогона скилла
`dm-send`, до обработки отдельных кандидатов — отбираются кандидаты,
ожидающие отправки, в порядке приоритета.
