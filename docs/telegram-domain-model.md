# Доменная модель Telegram (MTProto)

Справка по сущностям Telegram на уровне MTProto (тот уровень, на котором платформа
работает через GramJS): какие бывают сущности, как устроены их идентификаторы, сколько
они живут, и чем basic group отличается от супергруппы. Внешнее знание про Telegram
API, не специфичное для этого репозитория.

Источники: [Peer database](https://core.telegram.org/api/peers),
[chat constructor](https://core.telegram.org/constructor/chat),
[channel constructor](https://core.telegram.org/constructor/channel),
[Telethon: peers](https://docs.telethon.dev/en/v2/concepts/peers.html).

## Основные сущности (peers)

Всё, с чем можно вести диалог, — это **peer**. Есть три типа peer плюс secret chat:

| Сущность | Конструктор peer | Что это |
|---|---|---|
| **User** | `PeerUser` | обычный пользователь или бот. Агент-аккаунты платформы — это User |
| **Chat** | `PeerChat` | «базовая» группа (basic group) — маленькая группа до ~200 участников, без админ-инструментов |
| **Channel** | `PeerChannel` | и **каналы** (broadcast), и **супергруппы** (megagroup) — один тип `channel`, различается флагами |
| Secret chat | — | end-to-end чат, живёт только на устройстве; через клиент-библиотеки MTProto обычно не используется |

Ключевой момент: **канал и супергруппа — это одна сущность `channel`**, отличаются
флагами:
- `broadcast = true` → канал (вещание, пишут только админы). В коде метрик — `is_broadcast`.
- `megagroup = true` → супергруппа.

Комментарии под постами канала — это привязанная к каналу супергруппа-обсуждение
(linked chat). Отсюда метрика `comments_open`.

## Идентификаторы

Два разных числа, которые постоянно смешивают: `id` (сама сущность) и `access_hash`
(пропуск к ней).

### 1. `id` — идентификатор сущности

- Числовой ID, у каждого типа своё пространство. Диапазоны **пересекаются** между
  типами: user, chat и channel могут иметь одинаковый числовой `id`, поэтому `id` без
  указания типа неоднозначен.
- Раньше умещался в 32 бита, сейчас Telegram расширил до ~52 бит (порядок 2^40 и выше).
- **Постоянный и глобальный.** Один и тот же для всех, кто его видит, не меняется со
  временем. Переживает смену username, номера телефона, ротацию аккаунтов. Поэтому
  marked `chatId` годится как стабильный ключ канала.

### 2. Marked ID (Bot API ID) — тип, закодированный в числе

Чтобы одним числом закодировать тип + id (снять неоднозначность пересекающихся
диапазонов):

- **User**: положительный → `id`
- **Chat** (basic group): `-id`
- **Channel/супергруппа**: `-(10¹² + id)`, то есть префикс `-100…`

Пример: канал с внутренним `id = 1234567890` → marked `-1001234567890`. Это тот `-100…`,
что виден в ссылках `t.me/c/...` и в API. Marked ID тоже глобальный и постоянный.

### 3. `access_hash` — «пропуск» к сущности

- Чтобы что-либо сделать с peer, нужен `InputPeer`, а он требует пару
  **`id` + `access_hash`**. Без access_hash обратиться к сущности нельзя.
- **Привязан к аккаунту.** Для одного и того же канала у разных аккаунтов разные
  access_hash. **Нельзя переносить между аккаунтами** и между разными auth-сессиями
  одного аккаунта. Переиспользуется только между MTProto-сессиями одной auth-сессии.
- **Срок жизни:** явного TTL нет, обычно не меняется, пока аккаунт живёт, но не
  гарантированно вечен — при некоторых серверных операциях обновляется. Библиотеки
  (GramJS/Telethon) держат локальный кэш сущностей и обновляют access_hash из свежих
  объектов. Правило: не хардкодить access_hash, брать из актуального кэша сессии.
- Варианты: **full** (полный доступ), **min** (усечённый, только служебное — напр. фото
  профиля, писать нельзя), **zero** (для ботов, когда хэша нет).

### 4. Прочие идентификаторы

- **`username`** (`@name`) — публичный изменяемый алиас, не идентификатор в строгом
  смысле. Разрешается в `id` через `resolveUsername`. Как стабильный ключ не годится.
- **Инвайт-ссылка** (`t.me/+hash`) — отзываемый токен приглашения, не ID сущности.
- **`message id`** — не глобальный: у каналов/супергрупп уникален в пределах канала, в
  личках/basic-группах — per-account. Постоянен до удаления.
- **`pts` / `qts` / seq** — не идентификаторы, а счётчики состояния для синхронизации.

### Сводка по «сколько живёт»

| Идентификатор | Область уникальности | Стабильность |
|---|---|---|
| `id` / marked `chatId` | глобальная | постоянный, переживает ротацию аккаунтов, смену username/телефона |
| `access_hash` | **per-account** | живёт с аккаунтом, может обновляться; между аккаунтами непереносим |
| `username` | глобальная | изменяемый, может сменить владельца |
| invite link | глобальная | отзываемый токен, не ID |
| `message id` | канал: по каналу; DM/basic: per-account | постоянен до удаления |

**Вывод для платформы:** как ключ канала/чата хранить marked `id` (глобальный,
стабильный), а `access_hash` считать эфемерным per-account кэшем — его переполучает
каждый аккаунт сам. Это развязка, нужная при авто-замене банов и мультиперсоне.

## Chat (basic group) vs супергруппа

Терминология: «обычная группа» в UI — это тип **`chat`** (basic group). «Супергруппа» —
это **`channel`** с `megagroup=true`. То есть супергруппа и канал — один конструктор
`channel`, а basic group — другой конструктор `chat`. Различие «chat vs супергруппа» —
это различие двух разных классов сущностей.

### С точки зрения модели

| | `chat` (basic group) | супергруппа (`channel` + `megagroup`) |
|---|---|---|
| Конструктор | `chat` | `channel` |
| peer | `PeerChat` | `PeerChannel` |
| marked ID | `-id` | `-100…` (`-(10¹² + id)`) |
| Нужен `access_hash`? | **Нет** | **Да** |
| Как отдаётся состояние | целиком в объекте | объект + отдельный `channelFull`, апдейты по `pts` |
| Лимит участников | ~200 | до 200 000 |
| История для новых | видят только с момента вступления | доступна вся с начала |

Самое глубокое отличие — **как синхронизируется состояние**. Basic group — «плоский»
лёгкий объект: сервер присылает его целиком, порядок апдейтов отслеживается общим полем
`version`. Супергруппа/канал — отдельный поток обновлений со своим счётчиком `pts` (как
отдельный диалог); поэтому масштабируется до сотен тысяч участников.

Второе: у `chat` **нет `access_hash`** — обращение по одному `id`. У `channel`
access_hash обязателен и он per-account.

### С точки зрения набора полей

**`chat` (basic group)** — минимальный набор:
- `id`, `title`, `photo`, `participants_count`, `date`, `version`
- права: `admin_rights`, `default_banned_rights`
- флаги: `creator`, `left`, `deactivated`, `call_active`, `call_not_empty`, `noforwards`
- `migrated_to` (InputChannel) — заполнено, если группу апгрейднули в супергруппу; тогда
  же взводится `deactivated`. Это «надгробие»: basic group становится неактивной, а
  `migrated_to` указывает на новый `channel`.

Чего у `chat` нет: `access_hash`, `username`/`usernames`, `restriction_reason`,
`banned_rights`, `slowmode`, `join_to_send`/`join_request`,
`broadcast`/`megagroup`/`gigagroup`/`forum`.

**супергруппа (`channel`)** — расширенный набор:
- основа: `id`, **`access_hash`**, `title`, `photo`, `date`, `participants_count`
- публичность: `username`, `usernames` (несколько), `has_link`, `has_geo`
- права шире: `admin_rights`, `banned_rights` (индивидуальные баны — у `chat` их нет),
  `default_banned_rights`
- модерация/режимы: `slowmode_enabled`, `join_to_send`, `join_request`, `noforwards`,
  `restriction_reason`
- маркеры типа: `broadcast`, `megagroup`, `gigagroup`, `forum`
- статусы: `verified`, `scam`, `fake`

Формат прав разный: в basic group бан участника — фактически кик (нет per-user
`banned_rights`), в супергруппе есть полноценный `ChatBannedRights` с гранулярными
ограничениями и таймаутами.

### С точки зрения пользователя

| Возможность | basic group | супергруппа |
|---|---|---|
| Участников | до ~200 | до 200 000 |
| История для новичка | не видна (только новое) | видна вся |
| Публичный `@username` / ссылка | нет | да |
| Гранулярные права/муты/баны | нет | да |
| Медленный режим, заявки на вступление | нет | да |
| Закреп нескольких сообщений, темы (forum) | нет | да |
| Админ-лог, статистика | нет | да |

Как только группа упирается в лимит, нужна история, публичная ссылка или нормальная
модерация — Telegram (авто или по действию админа) **конвертирует её в супергруппу**.
При этом `id` меняется (был `chat`, стал `channel`), старый объект помечается
`deactivated`, а `migrated_to` связывает старую сущность с новой.

**Вывод для платформы:** агент почти всегда работает с `channel` (каналы и
супергруппы). basic group встречается редко и требует другого кода — нет access_hash,
другой формат прав, и она может мигрировать в `channel` со сменой ID. Ветки под
peer-типы должны обрабатывать миграцию `chat → channel` (`migrated_to`/`deactivated`),
иначе агент потеряет чат после апгрейда.
