# Архитектура репозитория (код)

Документ описывает компоненты кода и структуру репозитория.

## Компонентная архитектура

Реализовано по [ADR 0007](decisions/0007-core-vs-features-split.md): `src/core/`
разделён на инфраструктуру (`core/`) и готовые капабилити (`features/`), перенос
выполнен и задеплоен. Ниже — описание слоёв; полное дерево каталогов — в самом
ADR и в разделе «Структура репозитория» ниже.

Это платформа на несколько агентов: у каждого агента свой каталог данных и персона,
диспетчер запускается отдельно на каждого агента (`--agent <id>`).

**`index.ts`** — точка входа OpenClaw-плагина. Регистрирует интерактивные
инструменты, описывает параметры (TypeBox), оборачивает результат в формат
OpenClaw. Логики не содержит — только вызывает `core/` и `features/`.

**`src/core/`** — инфраструктура и технические клиенты: код, который сам по
себе не производит результата для пользователя, а даёт возможности, из которых
строятся фичи. Telegram-клиент (MTProto), доступ к данным (SQLite), клиент
tdata, конфигурация, логирование, клиент Telegram Bot API.

**`src/features/`** — готовые капабилити со своей оркестрацией и конкретным
результатом (отчёт, метрика, побочный эффект): поиск каналов, анализ каналов,
прокси-провижининг, регистрация/реавторизация агентов, воронка. Вызываются из
`index.ts` как интерактивные инструменты и/или из `src/scripts/`/`src/skills/`
как задачи по расписанию — реализация одна, вызывающих сторон может быть
несколько.

**`src/skills/`** — реализация задач диспетчера в контракте
`(SkillContext) => Promise<SkillStatus>`. Вызывается диспетчером
(`src/scripts/dispatcher.ts`) по таблице `tasks`. Отвечает за циклическое,
планируемое поведение агента; сама логику не несёт — обращается к
`core/`/`features/`.

**`src/scripts/`** — standalone-точки входа, запускаемые напрямую (systemd,
CLI, вручную): планировщик (`dispatcher.ts`), периодические/персистентные
процессы (`periodic/`), разовые операционные скрипты для оператора (`ops/`).

**`src/llm/`** — доступ к модели: вызов LLM и промпты скиллов.

Скилл получает зависимости через `SkillContext` (`agentId`, `persona`, `tg`, `llm`,
`log`) и не зависит от OpenClaw. Скиллы вызываются диспетчером по реестру
`TaskType → скилл`.

## Способы запуска скиллов

| Вариант | Сервис | Тип процесса | Ограничения |
|---|---|---|---|
| Диспетчер (основной) | `tg-agent@{id}.service` | oneshot, root | `TimeoutStartSec=3600` |
| OpenClaw-плагин | `openclaw` | долгоживущий, root | **лимит 1 час на выполнение одного инструмента** |
| Командная строка | SSH-сессия | одноразовый | только для отладки, не целевой режим |

## Структура репозитория

Подробное дерево `core/` и `features/` — в [ADR 0007](decisions/0007-core-vs-features-split.md).

```
index.ts        OpenClaw-плагин (точка входа)
src/
  scripts/      standalone-точки входа
    dispatcher.ts  диспетчер (запускается на каждого агента)
    periodic/      периодические/персистентные процессы (свой systemd timer/service)
    ops/           разовые операционные скрипты оператора
  skills/       реализация задач
  llm/          доступ к LLM
  core/         инфраструктура без зависимости от OpenClaw
    telegram/   MTProto поверх GramJS
    db/         слой данных (SQLite)
  features/     готовые капабилити: discovery, channel-analysis, channel-metrics,
                channel-context, channel-preview, proxy, tg-agent-autoregistration,
                tg-agent-reauth-from-tdata, funnel, activity-percentile

skills/    SKILL.md — наследие до переноса логики в код (см. decisions/0001)
deploy/    systemd-юниты
openspec/  спецификации и изменения
docs/      база знаний
```

## Слой данных

Модули `src/core/db/` работают с SQLite через `better-sqlite3`. Каждый модуль
управляет своими таблицами:

| Модуль (`core/db/`) | Таблицы | Данные |
|---|---|---|
| `channels.ts` | `channels`, `dm_candidates` | каналы и состояние их обработки; очередь DM-кандидатов |
| `replies.ts` | `replies`, `group_threads`, `group_thread_agent_msgs`, `thread_post_dates` | ответы агента, треды диалогов в группах; кеш дат публикации постов веток (`monitor-v2`, 30 дней) |
| `dm-threads.ts` | `dm_threads` | контекст личных диалогов |
| `dm-history.ts` | `dm_history` | устаревшая история DM (заменяется `dm_threads`) |
| `join-queue.ts` | `join_queue` | очередь вступления в группы обсуждений |
| `tasks.ts` | `tasks` | расписание задач агента |
| `runs.ts` | `runs` | журнал прогонов |
| `error-log.ts` | `error_log` | append-only лог срабатываний ошибок аккаунта (per-agent) |
| `agent-restrictions.ts` | `agent_restrictions` | ограничения агентов платформы (одна БД на всю платформу, в workspace админ-агента) |
| `funnel.ts` | `channel_snapshots`, `daily_stats` | метрики воронки (только у админ-агента) |
| `pending-reviews.ts` | `pending_reviews` | очередь ручного подтверждения комментариев перед отправкой (post-comment-review); статус (pending/approved/rejected) хранится в той же строке, отдельного лога решений нет |
